## Database Basics

#### Databases and DBMSs: Why Use a DB Instead of Files?
ONE: A **Database** is an organized collection of data, and a **DBMS** is software that manages that data so **many people can use it at the same time, safely, and quickly**.
LIKE: Think of a bank. If you keep your money under the mattress (files), it gets confusing who took how much, and if there is a fire, you lose it all. A bank (DBMS) keeps an accurate ledger, keeps balances straight even with many tellers working at once, and protects the records even in a power outage.
STEP:
1. **Problem ① with storing in plain files**: If 100 people edit the same file at once, there is no telling whose changes will survive.
2. **Problem ②**: If the power goes out mid-save, the file can be left half-written and corrupted.
3. **Problem ③**: If the same information is copied into several files, only one gets updated and they drift apart.
4. **What a DBMS does for you**: Sorts out simultaneous access (Concurrency Control), guarantees all-or-nothing for grouped work (Transaction), recovers after failures (Recovery), blocks rule violations (Integrity guaranteed by Constraints), searches quickly (Index), and manages permissions.
5. And with a common language called **SQL**, you just say "what you want," and the DBMS decides "how to find it."
WHY: Data that must never be wrong and gets many simultaneous requests, like shopping orders, bank transfers, and member info, cannot be handled safely without a DBMS.
USE: MySQL, PostgreSQL, Oracle, SQL Server (relational), MongoDB, Redis, Cassandra (NoSQL).
KEY: The three goals a good data system must meet are **Reliability** (works correctly even when things fail), **Scalability** (has a way to cope as load grows), and **Maintainability** (easy for many people to run and change over time).
END: A DBMS is a bank for data. It handles simultaneous access, failures, and duplication for you.

#### The Relational Model and Keys
ONE: The **Relational Model** stores data in **tables (Tables)** and connects tables with **Keys**.
LIKE: Think of a school's rosters. There is a "student roster" and a separate "club roster," and the club roster lists only student IDs instead of names. Look up the student ID in the student roster and you get the rest of the info.
STEP:
1. **Table (Relation)**: A table about one subject. Example: students.
2. **Row (Tuple)**: One line of the table, i.e., one record. One student.
3. **Column (Attribute)**: One kind of cell in the table. Name, student ID, major.
4. **Schema**: The blueprint that defines the Table name, Column names and Types, and rules (Constraints).
5. **Key**: A Column that identifies Rows or links to another Table.
| Key | Meaning |
| Super Key | A combination of Columns that uniquely identifies a Row (extra Columns are allowed) |
| Candidate Key | A minimal combination that is unique and cannot be reduced further |
| Primary Key (PK) | The Candidate Key chosen as the representative. No NULLs or duplicates |
| Alternate Key | The remaining Candidate Keys not chosen as the PK |
| Foreign Key (FK) | A Column pointing to another Table's PK. Prevents pointing to Rows that don't exist |
6. **Referential Integrity**: A Foreign Key can only point to Rows that actually exist. If you try to write a nonexistent student ID into the club roster, the DB refuses.
WHY: Splitting information into Tables by subject and linking them with Keys means you don't write the same information multiple times, and when it changes you fix it in only one place.
END: A relational DB is "tables + links via Keys." The PK is each row's ID card, and the FK is an arrow pointing to another table.

### How is a DBMS different from just saving to a file?
E: If 100 people edit one Excel file at the same time, there is no telling whose changes will survive, and if the power goes out mid-save, the file gets corrupted. A DBMS is the bank clerk who prevents these accidents.
A: A DBMS provides Concurrency Control for simultaneous access by many users, Transactions and failure Recovery, Integrity guaranteed by Constraints, a Query Language like SQL, fast search through Indexes, and permission management. With a File System, the Application has to implement these features itself, so data duplication and inconsistency creep in easily.

### What are a Table·Row·Column·Schema in the Relational Model?
A: The Relational Model represents data as Tables (Relations); a Row (Tuple) is one Record, and a Column (Attribute) is one field. A Schema is the blueprint defining the Table name, Column names and Data Types, and Constraints, and Tables relate to each other through Keys.

### What kinds of Keys are there?
E: They are ways of identifying a student. Things that point to exactly one person, like a student ID or a Social Security Number, are Candidate Keys; the student ID chosen as the representative is the Primary Key; and something like the "homeroom teacher number" on a class list, which points to another Table, is a Foreign Key.
| Key | Meaning |
| Super Key | A combination of Columns that uniquely identifies a Row (unneeded Columns may be included) |
| Candidate Key | A minimal Super Key that stays unique and cannot be reduced further |
| Primary Key (PK) | The Candidate Key chosen as the representative; no NULLs + no duplicates |
| Alternate Key | The remaining Candidate Keys not chosen as the Primary Key |
| Foreign Key (FK) | A Column referencing another Table's Primary Key; guarantees Referential Integrity |
A: A Super Key satisfies only uniqueness, a Candidate Key satisfies both uniqueness and minimality, and the Primary Key is one of the Candidate Keys and cannot be NULL. A Foreign Key points to another Table's Primary Key and prevents references to Rows that don't exist (Referential Integrity).

## SQL

#### SQL Basics: SELECT and Execution Order
ONE: **SQL** is a language where you only tell the DB **"what you want."** The DB decides "how to find it."
LIKE: It is like a restaurant where you just order "one spicy lasagna," and the kitchen decides where to get the ingredients and in what order to cook.
STEP:
1. **CRUD**: Create (INSERT), Read (SELECT), Update (UPDATE), Delete (DELETE).
2. **SELECT basics**: `SELECT column FROM table WHERE condition ORDER BY sort LIMIT count`.
3. **WHERE**: Keeps only the Rows that match the condition.
4. **GROUP BY**: Groups equal values together to build aggregates like COUNT, SUM, and AVG.
5. **HAVING**: Filters **groups after** grouping. WHERE filters **Rows before** grouping, so it cannot use aggregate functions.
6. **Logical execution order**: It differs from the order you write it: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. That is why an alias given in SELECT cannot be used in WHERE.
```sql
SELECT dept, AVG(salary) AS avg_sal
FROM employees
WHERE hire_year >= 2020        -- 1) filter Rows first
GROUP BY dept                  -- 2) group by department
HAVING AVG(salary) > 5000      -- 3) filter groups
ORDER BY avg_sal DESC;         -- 4) sort
```
KEY: SQL is a **Declarative** language. Since the DB decides "how," a Query can get faster when the DB engine improves, without changing the Query.
END: SQL is a language that only says "what," and WHERE filters Rows while HAVING filters groups.

#### JOIN: Combining Multiple Tables
ONE: **JOIN** is the way to **combine several Tables linked by Keys into one result**. The kinds differ in whether Rows without a match are kept or dropped.
LIKE: Say you combine a "student list" and a "club membership list." INNER keeps only students on both lists, and LEFT keeps every student and leaves the club blank if they have none.
STEP:
1. **INNER JOIN**: Keeps only Rows that have a match on both sides.
2. **LEFT (OUTER) JOIN**: Keeps every Row from the left Table, filling with NULL when there is no match on the right.
3. **RIGHT (OUTER) JOIN**: The reverse; keeps everything on the right.
4. **FULL OUTER JOIN**: Keeps both sides, with NULL on whichever side has no match.
5. **CROSS JOIN**: Makes every combination. Number of Rows = m × n.
6. **SELF JOIN**: Uses the same Table twice. Example: viewing "an employee and that employee's manager" together from the employee Table.
```sql
-- find customers who have never placed an order
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```
KEY: **Finding what's missing**, like "customers with no orders" or "members who signed up but never did anything," is classically done with a LEFT JOIN and then picking Rows where the right side is NULL.
END: Only matches is INNER, keeping all of one side is LEFT/RIGHT, and keeping everything is FULL.

#### Subqueries and Views
ONE: A **Subquery** is a Query inside a Query, and a **View** is a **virtual Table**: a Query saved under a name.
LIKE: A Subquery is, when finding "students taller than average," first calculating "the average height" separately and plugging it in. A View is giving a frequently used, complicated search condition a name like "honor roll" and pulling it out like a table.
STEP:
1. **Subquery**: Uses another Query's result as a value or temporary Table, as in `WHERE salary > (SELECT AVG(salary) FROM emp)`.
2. Subqueries can go in the WHERE, FROM, and SELECT positions.
3. **View**: Created with `CREATE VIEW top_students AS SELECT ...`, and afterward used like a Table, as in `SELECT * FROM top_students`.
4. A regular View does not store data separately; it runs the original Query every time it is queried.
5. **Security**: Showing only a View that leaves out sensitive Columns (Social Security Numbers, etc.) lets you safely share just the needed information.
6. **Materialized View**: A View that actually stores its results. Lookups are fast, but it must be recomputed (Refresh) when the source changes.
END: A Subquery is a Query inside a Query, and a View is a saved Query with a name.

#### Categories of SQL Commands: DDL · DML · DCL · TCL
ONE: SQL commands split by what they do: **structure definition (DDL)**, **data manipulation (DML)**, **permissions (DCL)**, and **Transactions (TCL)**.
LIKE: In library terms: building and removing bookshelves (DDL), putting in, taking out, and finding books (DML), handing out and taking back keys (DCL), and "confirm/cancel this reorganizing job" (TCL).
STEP:
1. **DDL (Data Definition)**: CREATE, ALTER, DROP, TRUNCATE. Works on Table structure.
2. **DML (Data Manipulation)**: SELECT, INSERT, UPDATE, DELETE. Works on data (SELECT alone is sometimes called DQL).
3. **DCL (Data Control)**: GRANT, REVOKE. Gives and takes away permissions.
4. **TCL (Transaction Control)**: COMMIT, ROLLBACK, SAVEPOINT. Confirms or cancels a Transaction.
5. **DELETE vs TRUNCATE vs DROP**: DELETE removes Rows one by one and can be Rolled back. TRUNCATE empties the whole Table quickly but, depending on the DBMS, cannot be Rolled back. DROP removes the Table itself.
END: Structure is DDL, data is DML, permissions are DCL, and confirm·cancel is TCL.

### What kinds of JOINs are there?
E: They are ways of combining a "student list" and a "club membership list." INNER keeps only students on both lists, and LEFT keeps every student and leaves the club blank if they have none.
| JOIN | Result |
| INNER JOIN | Only Rows that match on both sides |
| LEFT (OUTER) JOIN | All of the left Table + matching Rows on the right (NULL if none) |
| RIGHT (OUTER) JOIN | All of the right Table + matching Rows on the left |
| FULL OUTER JOIN | Everything on both sides, NULL on the side without a match |
| CROSS JOIN | Every combination (Rows = m × n) |
| SELF JOIN | A Table with itself (e.g., an employee and that employee's manager) |
A: INNER JOIN shows only Rows that meet the Join condition, and LEFT/RIGHT OUTER JOIN show every Row of one Table plus the matching Rows, filling with NULL where there are none. FULL OUTER keeps both sides, CROSS makes every combination, and SELF uses the same Table twice. "Finding customers who have never ordered" by doing a LEFT JOIN and picking Rows where the right side is NULL is the classic example.

### What is the difference between WHERE and HAVING, and how does GROUP BY work?
E: WHERE is filtering students before splitting them into classes, and HAVING is computing each class's average and then picking only "classes averaging 80 or higher."
A: GROUP BY groups Rows with the same value to build Aggregates like COUNT·SUM·AVG. WHERE filters individual Rows before Groups are formed, so it cannot use Aggregate Functions, while HAVING filters Groups by their aggregate results after Groups are formed. The logical execution order is FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
```sql
SELECT dept, AVG(salary) AS avg_sal
FROM employees
WHERE hire_year >= 2020        -- filter Rows first
GROUP BY dept
HAVING AVG(salary) > 5000      -- filter Groups
ORDER BY avg_sal DESC;
```

### What are Subqueries and Views?
A: A Subquery is a Query inside another Query that produces a value or temporary Table, as in `WHERE salary > (SELECT AVG(salary) FROM emp)`. A View is a virtual Table, a Query saved under a name, which simplifies complex Queries and helps security by hiding sensitive Columns. A regular View stores no data and runs the original Query each time it is queried.

### What is the difference between DDL, DML, DCL, and TCL?
| Category | What it does | Commands |
| DDL (Data Definition) | Creates and changes Table structure | CREATE, ALTER, DROP, TRUNCATE |
| DML (Data Manipulation) | Reads·adds·updates·deletes data | SELECT, INSERT, UPDATE, DELETE |
| DCL (Data Control) | Gives and takes away permissions | GRANT, REVOKE |
| TCL (Transaction Control) | Confirms·cancels Transactions | COMMIT, ROLLBACK, SAVEPOINT |
A: DDL works on the Schema, DML on data, DCL on permissions, and TCL on Transactions. DELETE removes Rows one by one and can be Rolled back, TRUNCATE empties the whole Table quickly but cannot be Rolled back in some DBMSs, and DROP removes the Table itself. SELECT is sometimes classified separately as DQL (Data Query Language).

## Normalization and Anomalies

#### Anomalies
ONE: If you store **several kinds of information mixed together** in one Table, strange problems arise when inserting·updating·deleting. These are Anomalies.
LIKE: If one ledger records "student, enrolled course, professor's office number" all together, problems arise. A new professor with no students can't be recorded, if an office moves you have to fix hundreds of lines, and if the last student drops, the professor's info disappears too.
STEP:
1. **Insertion Anomaly**: You can't insert something unless other data exists. With no enrolled students, there is nowhere to store a new professor's info.
2. **Update Anomaly**: The same information is duplicated across many lines, so updating only some of them makes them disagree. If you fix the office number on only a few lines, you can't tell which one is right.
3. **Deletion Anomaly**: Deleting some data also wipes out information you needed. Delete the last enrollment record and the professor's info is gone too.
4. The cause in every case is **"information about several subjects duplicated in one Table."**
5. **Fix**: Split Tables by subject (a student Table, a professor Table, an enrollment Table). This is Normalization.
END: Mixing several subjects in one Table tangles inserting·updating·deleting. Splitting by subject fixes it.

#### Functional Dependencies and Normal Forms
ONE: A **Functional Dependency (X → Y)** is the relationship "knowing X determines Y uniquely," and **Normalization** is the process of splitting Tables by the principle "each piece of information lives only in the Table of the thing that determines it."
LIKE: Knowing the student ID determines the name, so "student ID → name." Then the name only needs to live in the student Table, where the student ID is the owner. There is no need to write the name again in the enrollment Table.
STEP:
1. **Functional Dependency**: If X values are equal, Y values are always equal. Student ID → name, department → department chair.
2. **1NF**: Every cell holds **one** value that cannot be split further (Atomic Value). Violation example: two numbers like "555-0101, 555-0102" in the phone number cell.
3. **2NF**: 1NF + when the Key has several Columns, no Column may depend on **only part** of the Key (remove Partial Dependency). Violation example: the Key is (student ID, course), but "student name" depends only on the student ID.
4. **3NF**: 2NF + no non-Key Column may **determine another non-Key Column** (remove Transitive Dependency). Violation example: student ID → department → department chair. Move the department chair to the department Table.
5. **BCNF**: Every determinant (Determinant, the left side of the arrow) must be a Candidate Key. Slightly stricter than 3NF.
6. Higher levels mean less duplication and fewer Anomalies, but more Tables and more JOINs.
| Normal Form | Condition | Violation example |
| 1NF | One value per cell | Two numbers in the phone number cell |
| 2NF | Remove partial dependency | With the (student ID, course) Key, name depends only on student ID |
| 3NF | Remove transitive dependency | Student ID → department → department chair |
| BCNF | Every determinant is a Candidate Key | Classroom → course, but classroom is not a Key |
END: Normalization is asking "who owns this information?" and keeping it only in the owner's Table. Going 1NF → 2NF → 3NF → BCNF reduces duplication.

#### Denormalization
ONE: **Deliberately allowing duplication** for read performance. In exchange, writes get more complicated and the risk of inconsistency grows.
LIKE: By the rules of tidying, each item should live in one place, but keeping an extra pair of scissors in both the living room and the kitchen cuts down on time spent hunting for them. The catch is that when you replace the scissors, you have to replace all of them.
STEP:
1. Heavy normalization splits Tables into small pieces, so drawing a single screen takes several JOINs.
2. As data grows, JOINs get slow.
3. **Denormalization**: Put information that is frequently read together into one Table, or store values that are expensive to compute every time (like a post's comment count) in advance.
4. In exchange, when the original changes, the copies must be updated too. Miss even one and the values disagree.
WHY: For services with far more reads than writes (most web services), making reads fast is often more important.
END: Denormalization is the choice of "deliberately allowing duplication for read speed," and it pays the price of write complexity.

### What are Insertion·Update·Deletion Anomalies?
E: If one ledger records "student, enrolled course, professor's office number" all together, problems arise. A new professor with no students can't be recorded (Insertion), if an office moves you have to fix hundreds of student lines (Update), and if the last student drops, the professor's info disappears too (Deletion).
A: Anomalies are problems caused by several kinds of information being duplicated in one Table. An Insertion Anomaly is being unable to insert something without other data, an Update Anomaly is inconsistency from updating only some copies of a duplicated value, and a Deletion Anomaly is losing needed information along with the data being deleted; they are fixed by splitting Tables through Normalization.

### What are 1NF·2NF·3NF and BCNF? What is a Functional Dependency?
E: A Functional Dependency X → Y means "knowing X determines Y uniquely." Knowing the student ID determines the name, so student ID → name. Normalization is the tidying principle "each piece of information lives only in the Table of the thing that determines it."
| Normal Form | Condition | Violation by example |
| 1NF | Every cell holds one value that cannot be split (Atomic Value) | Two numbers like "555-0101, 555-0102" in the phone number cell |
| 2NF | 1NF + no Column depends on only part of a Composite Key (remove Partial Dependency) | With the (student ID, course) Key, "student name" depends only on student ID |
| 3NF | 2NF + no non-Key Column determines another non-Key Column (remove Transitive Dependency) | Student ID → department → department chair |
| BCNF | Every Determinant is a Candidate Key | "Classroom → course," but classroom is not a Candidate Key |
A: A Functional Dependency X → Y is the relationship where equal X values always mean equal Y values. 1NF allows only Atomic Values, 2NF removes Partial Functional Dependencies, 3NF removes Transitive Functional Dependencies, and BCNF is the state where every Determinant is a Candidate Key. Moving up the levels reduces duplication and Anomalies but increases Tables and JOINs.

### When do you Denormalize?
A: Denormalization deliberately allows duplication for read performance, done when there are so many JOINs that lookups are slow or when computing aggregate values (like comment counts) every time is a burden. In exchange, changing data requires updating several places together, which complicates writes and raises the risk of inconsistency.

## Indexes

#### How an Index Works
ONE: An **Index** is a data structure that **stores, separately and sorted,** the values of a particular Column along with the locations of their Rows. It lets you find things in O(log n) instead of scanning everything in O(n).
LIKE: It is the "index" at the back of a thick book. Instead of flipping from the first page to find a word, you look up the page number in the index and go straight to that page.
STEP:
1. Without an Index, finding `WHERE email = 'a@b.com'` means looking through the whole Table from start to finish (**Full Table Scan**, O(n)).
2. If you create an Index on the email Column, the DB stores email values and Row locations separately in a sorted structure.
3. Now it searches the sorted structure quickly (O(log n)) and goes straight to the matching Row.
4. **B+Tree**: The structure of most DB Indexes. Each Node is sized to a Disk Page, so the height is low (few Disk reads), and the Leaves are linked, so it is also strong at range queries and sorting (topic 06).
5. **Hash Index**: Very fast for equality (=) searches, but it has no order, so it cannot do range searches (`BETWEEN`, `>`) or sorting.
WHY: With a million rows, a Full Scan takes a million comparisons, while an Index takes about 20.
END: An Index is a book's index. Because it is sorted, you go straight to what you want without flipping through everything.

#### The Cost of Indexes and When Indexes Go Unused
ONE: Indexes are not free. They **use more space and slow down writes**. And if you write the condition wrong, the Index **goes unused** even though it exists.
LIKE: Every time you add content to a book, you have to update its index too. And words like "the" and "a" are useless in an index even if listed, because they appear on almost every page.
STEP:
1. **Space cost**: Indexes are stored separately, so they use more Disk.
2. **Write cost**: Every INSERT·UPDATE·DELETE has to update not just the Table but the Indexes too. The more Indexes, the slower the writes.
3. So you don't create an Index on every Column; you choose based on **the conditions you search by most often**.
4. **When Indexes go unused ①**: Columns with few distinct values (low **Cardinality**, like gender). You end up reading half the Table, so a Full Scan may be better.
5. **②**: Conditions that wrap the Column in a function. `WHERE YEAR(created) = 2026` cannot use the sorted order. Change it to `WHERE created >= '2026-01-01' AND created < '2027-01-01'`.
6. **③**: LIKE with a leading %. `'%kim'` gives no starting point. `'kim%'` is fine.
7. **④**: Comparisons where differing Types trigger automatic conversion, conditions that skip the first Column of a Composite Index, and very small Tables.
KEY: Whether an Index is actually used is checked with **EXPLAIN**, which shows the Execution Plan. Don't guess; check.
END: Indexes make reads fast at the cost of space and writes. Functions·a leading %·low Cardinality make Indexes useless.

#### Clustered Index vs Non-Clustered Index
ONE: A **Clustered Index** means the Table data **itself** is stored sorted in Index order, and a **Non-Clustered Index** is a **separate** list that points to where the data is.
LIKE: Clustered is like a dictionary, where the book's content itself is sorted alphabetically. Non-Clustered is like the index at the back of a book, a separately gathered list that points to page numbers in the main text.
STEP:
1. **Clustered Index**: Rows are laid out on Disk in Index Key order. There is only one way to sort the data, so you can make **only one** per Table.
2. Range searches (`WHERE id BETWEEN 100 AND 200`) are very fast, because the wanted Rows sit next to each other.
3. In MySQL InnoDB, the Primary Key is the Clustered Index.
4. **Non-Clustered (Secondary) Index**: A structure separate from the data. You can make several.
5. After finding a match, you have to go one more step to fetch the actual Row. In InnoDB, a Secondary Index points to the Primary Key value, and that PK is looked up once more in the Clustered Index.
6. **Covering Index**: If every Column the Query needs is inside the Index, you finish by reading just the Index without fetching the Row, which is very fast.
END: Clustered is the data itself being sorted (only one); Non-Clustered is a separate index (several allowed).

#### Many Kinds of Indexes: Composite · Covering · Inverted · Vector
ONE: Indexes are not just one B+Tree. There are separate Indexes for **bundles of several Columns**, **finishing a Query with the Index alone**, **word search**, and **finding similar things**.
LIKE: Library catalogs come in many kinds too: a catalog sorted by "author + publication year," a catalog that even includes summaries of the books, a catalog of "books where this word appears," and a recommendation list of "books similar to this one."
STEP:
1. **Composite Index**: An Index that bundles several Columns. With `(last_name, first_name)`, it is sorted like a phone book: by last name first, then by first name within the same last name.
2. That is why you must use it **starting from the left Column** to benefit from the Index (**Leftmost Prefix**). Searching by `last_name` alone is OK; searching by `first_name` alone can't really use the Index.
3. **Covering Index**: When every Column the Query needs is in the Index, so the Table doesn't need to be read.
4. **Inverted Index**: "Word → list of documents containing that word." It is the basic structure of search engines (Elasticsearch) and Full-Text Search.
5. **Spatial Index**: For location searches like "stores within 1 km of me" on a map.
6. **Vector Index**: Stores sentences·images converted into numeric Vectors (Embeddings) and quickly finds "the most similar one." Used in AI search (RAG) (topic 16).
END: Bundled and sorted is Composite (left first), finishing with the Index alone is Covering, word search is Inverted, and finding similar things is a Vector Index.

### What is an Index? Why is it built as a B+Tree?
E: It is the "index" at the back of a thick book. Instead of flipping from the first page to find a word, you look up the page number in the index right away.
A: An Index is a separate data structure that stores a particular Column's values and Row locations in sorted order, letting you find things in O(log n) instead of scanning the whole Table in O(n). Most use a B+Tree, because each Node is sized to a Disk Page so the height is low and Disk reads are few, and the Leaves are linked so it is also strong at Range Queries·sorting (see 06 Data Structure). A Hash Index is fast for equality (=) searches but cannot do range searches.

### What are the downsides of Indexes, and when does an Index go unused even though it exists?
E: Every time you add content to a book, you have to update its index too, and words like "the" or "a" are useless in an index even if listed, because they appear on almost every page.
A: Indexes use more storage, and every INSERT·UPDATE·DELETE must update the Index too, which slows writes. Also, the Optimizer may choose a Full Table Scan over the Index for Columns with few distinct values (low Cardinality, like gender), conditions that apply a function to the Column (`WHERE YEAR(created) = 2026`), LIKE with a leading % (`'%kim'`), Implicit Type Conversion, conditions that don't use the first Column of a Composite Index, and small Tables. Check the actual Execution Plan with EXPLAIN.

### Clustered Index vs Non-Clustered Index?
E: Clustered is like a dictionary, where the book's content itself is sorted alphabetically, and Non-Clustered is like the index at the back of a book, a separately gathered list that points to locations in the main text.
A: A Clustered Index stores the Table data itself in Index Key order, so only one can exist per Table, and range lookups are very fast (in MySQL InnoDB, the Primary Key). A Non-Clustered (Secondary) Index is a structure separate from the data that points to Row locations (in InnoDB, Primary Key values), so you can make several, but after finding a match you have to read the data once more.

### What are a Composite Index and a Covering Index?
E: A Composite Index is a catalog sorted "last name → first name," like a phone book, so you have to search by last name first; a Covering Index is when the catalog card already has all the needed information, so you never have to open the main text.
A: A Composite Index sorts several Columns bundled in order, and to use it efficiently your conditions must start with the leftmost Column (Leftmost Prefix Rule). A Covering Index is when every Column the Query needs is in the Index, so the result comes from the Index alone without reading the Table (or Clustered Index) again; with no extra Disk reads, it is fast.

## Transactions and Concurrency Control

#### Transactions and ACID
ONE: A **Transaction** is a bundle of work that must **"either all happen or none of it happens,"** and the four properties that guarantee this are **ACID**.
LIKE: When A sends B $100, "subtract from A's account" and "add to B's account" are one bundle. If only the subtraction happens and the addition doesn't, the money vanishes.
STEP:
1. **Atomicity**: Every operation in the bundle succeeds, or if even one fails, everything is canceled (Rollback). There is no in-between state.
2. **Consistency**: Rules (like no negative balances) hold before and after the Transaction. In practice, this holds only if not just the DB but also the Application defines the right rules.
3. **Isolation**: Even when several Transactions run at once, they don't see or interfere with each other's in-between states.
4. **Durability**: Once COMMITted, a result does not disappear even in a power outage or failure.
5. Usage: `BEGIN` → several SQL statements → `COMMIT` on success, `ROLLBACK` if something goes wrong.
| Property | Meaning | Transfer example |
| Atomicity | All or nothing | The withdrawal and deposit both happen or neither does |
| Consistency | Rules are kept | The balance never goes negative |
| Isolation | No interference between concurrent runs | Other transfers can't see the in-between state |
| Durability | Permanent once confirmed | The record survives a power outage after completion |
WHY: It is essential for things like transfers, orders, and seat reservations, where a "half-done state" is a major incident.
END: A Transaction is an "all or nothing" bundle, and ACID is the four parts of that promise.

#### Isolation Levels and Their Anomalies
ONE: Perfect Isolation is slow, so the DB lets you pick an **Isolation Level** to **tune the balance between correctness and speed**. The lower the level, the faster, but strange things can happen.
LIKE: A Dirty Read is seeing a friend's message draft before they even hit "send," a Non-Repeatable Read is reading the same post twice and finding its content changed in between, and a Phantom Read is running the same search twice and seeing a new post that wasn't there before.
STEP:
1. **Dirty Read**: Reading a value another Transaction has not yet COMMITted. If that Transaction Rolls back, you saw a value that never existed.
2. **Non-Repeatable Read**: Reading the same Row twice and getting different values because another Transaction changed and COMMITted it in between.
3. **Phantom Read**: Querying twice with the same condition and getting a different number of results because another Transaction added·deleted Rows in between.
4. The 4 isolation levels (stricter as you go down):
| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read |
| Read Uncommitted | Occurs | Occurs | Occurs |
| Read Committed | Prevented | Occurs | Occurs |
| Repeatable Read | Prevented | Prevented | Occurs (per the SQL standard) |
| Serializable | Prevented | Prevented | Prevented |
5. **Defaults**: MySQL InnoDB uses Repeatable Read (and blocks most Phantoms with Next-Key Locks); PostgreSQL·Oracle·SQL Server use Read Committed.
WHY: Running every Transaction one at a time in order is perfect but far too slow. Each service picks which anomalies it can tolerate to gain speed.
END: The isolation level is a dial for "how strictly to keep Transactions apart." Stricter is more correct; looser is faster.

#### Snapshot Isolation and Write Skew
ONE: **Snapshot Isolation** lets each Transaction see **a photo (Snapshot) taken at its start time**. It prevents many problems, but it cannot prevent **Write Skew**, where Transactions **change different Rows and break a rule together**.
LIKE: A married couple has the rule that the sum of their two account balances must always be 0 or more. The husband and wife both check "the total is enough" at the same time, and each withdraws a large amount from their own account. Each thought they were following the rule, but the total ends up negative.
STEP:
1. **Snapshot Isolation**: A Transaction works while looking at a photo of the data from when it started. Even if someone else changes things midway, my photo doesn't change, so there are no Dirty Reads or Non-Repeatable Reads. It is usually implemented with MVCC.
2. **Write Skew**: Two Transactions each read the same condition (checking the total) and, based on that result, change **different Rows** (each their own account).
3. They didn't change the same Row, so it isn't detected as a conflict. That is why Snapshot Isolation can't prevent it.
4. Another example: the rule is "at least 1 doctor on call," but two doctors check "someone else is on" at the same time and each takes themselves off call, leaving 0.
5. **Fix**: Use the Serializable level, or explicitly Lock the Rows you checked (`SELECT ... FOR UPDATE`).
6. **3 ways to implement Serializable**: actually running one at a time in order, **2PL** (pessimistic, blocking with Locks), and **SSI (Serializable Snapshot Isolation)** (optimistic, running first and checking for conflicts at COMMIT time).
WHY: It is easy to think "Repeatable Read is safe," but in logic that reads several Rows at once and makes a decision, Write Skew causes real bugs.
END: Snapshot Isolation is working from a photo, and Write Skew, where changing different Rows breaks a rule, is prevented with Serializable or explicit Locks.

#### 2PL and MVCC: Ways to Control Concurrency
ONE: **2PL** keeps order **by blocking with Locks**, and **MVCC** keeps **multiple versions** so reads and writes don't block each other.
LIKE: 2PL is like a library where nobody can edit a book while it is checked out, and MVCC is like showing other people a copy from before the edits even while someone is editing the book.
STEP:
1. **Kinds of Locks**: **Shared Lock** (for reading, several can hold it together) and **Exclusive Lock** (for writing, only one can hold it).
2. **2PL (Two-Phase Locking)**: Splits into a phase where Locks are **only acquired** (Growing) and a phase where they are **only released** (Shrinking). Once a Lock has been released even once, no new Lock is ever acquired. Following this rule makes the result the same as running the Transactions one at a time in some order (Serializability).
3. Downsides of 2PL: Readers and writers wait for each other, and Deadlocks can happen.
4. **MVCC (Multi-Version Concurrency Control)**: When changing data, it doesn't overwrite but creates a new version. Old versions are also kept for a while.
5. A reading Transaction sees the version as of its own point in time (Snapshot). Depending on the Isolation Level, that is the version as of the Transaction's start or as of each Query's start.
6. So **reads don't block writes, and writes don't block reads**. Only simultaneous writes to the same Row are treated as conflicts.
USE: PostgreSQL, MySQL InnoDB, and Oracle use MVCC. Old versions are cleaned up later (VACUUM in PostgreSQL).
END: Guarding by blocking is 2PL; avoiding by splitting into versions is MVCC. Most modern DBs are built on MVCC.

#### COMMIT · ROLLBACK, WAL, and Recovery
ONE: A DB **writes the changes to a Log first, before** changing the data (**WAL, Write-Ahead Logging**). So even after a failure, it reads the Log, redoes work that finished, and undoes work that didn't.
LIKE: If you write down what you're doing in a journal first, then even in a power outage you can read the journal, redo what was finished, and undo what wasn't.
STEP:
1. **COMMIT**: Confirms the Transaction's changes. From this moment on, they must not disappear (Durability).
2. **ROLLBACK**: Returns to the state before the Transaction started.
3. **WAL**: Before changing the data files, it first writes "what will change and how" in order at the end of a Log file. Writing a Log is appending to the end of a file, so it is fast.
4. A COMMIT is complete the moment the Log is safely recorded on Disk. The actual data files can be updated slowly later.
5. **Recovery after a failure**: Reading the Log, it reapplies COMMITted Transactions (**Redo**) and cancels Transactions that were not COMMITted (**Undo**).
6. This protects Atomicity and Durability together.
USE: WAL is also used for Replication. Sending the Primary's Log to a Replica and replaying it the same way produces a copy.
END: "Journal first, act later." Thanks to WAL, even after a failure, confirmed work is saved and unfinished work is undone.

### What are Transactions and ACID?
E: When A sends B $100, "subtract from A's account" and "add to B's account" are one bundle. If only the subtraction happens and the addition doesn't, the money vanishes.
A: A Transaction is a logically single unit of work, and it must guarantee the ACID properties.
| Property | Meaning | Transfer example |
| Atomicity | Everything succeeds or everything is canceled | The withdrawal and deposit both happen or neither does |
| Consistency | From a state that respects Constraints to another that does | The balance never goes negative |
| Isolation | No cutting in on each other even when run concurrently | Other transfers can't see the in-between state |
| Durability | Once Committed, it survives failures | The record survives a power outage after the transfer completes |

### What are the 4 Isolation Levels, and what are Dirty Reads·Non-Repeatable Reads·Phantom Reads?
E: A Dirty Read is seeing a friend's message draft before they even hit "send," a Non-Repeatable Read is reading the same post twice and finding its content changed in between, and a Phantom Read is running the same search twice and seeing a new post that wasn't there before.
| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read |
| Read Uncommitted | Occurs | Occurs | Occurs |
| Read Committed | Prevented | Occurs | Occurs |
| Repeatable Read | Prevented | Prevented | Occurs (per the SQL standard) |
| Serializable | Prevented | Prevented | Prevented |
A: The Isolation Level is a control between performance and correctness; the higher the level (further down the table), the fewer the anomalies but the lower the concurrent throughput. A Dirty Read is reading uncommitted data, a Non-Repeatable Read is getting a changed value when rereading the same Row, and a Phantom Read is Rows appearing or disappearing when querying again with the same condition. The defaults are Repeatable Read for MySQL InnoDB (which also blocks most Phantoms with Next-Key Locks) and Read Committed for PostgreSQL·Oracle·SQL Server.

### What are Lock-based Concurrency Control (2PL) and MVCC?
E: 2PL is like a library where nobody can edit a book while it is checked out, and MVCC is like showing other people a copy from before the edits even while someone is editing.
A: 2PL (Two-Phase Locking) guarantees Serializability by splitting into a Growing Phase that only acquires Locks and a Shrinking Phase that only releases them, using Shared Locks (reading) and Exclusive Locks (writing). In exchange, waiting and Deadlocks can occur. MVCC (Multi-Version Concurrency Control) keeps multiple Versions of the data so reads see a Snapshot from a particular point in time (the Transaction's start or each Query's start, depending on the Isolation Level); since reads and writes don't block each other, PostgreSQL·MySQL InnoDB·Oracle use it.

### What are COMMIT and ROLLBACK, and Logs and Recovery?
E: If you write down what you're doing in a journal first, then even in a power outage you can read the journal, redo what was finished, and undo what wasn't.
A: COMMIT confirms a Transaction's changes, and ROLLBACK returns to the state before the Transaction started. The DB uses WAL (Write-Ahead Logging), recording changes in a Log before changing the data, so after a failure it reapplies Committed work from the Log (Redo) and cancels uncommitted work (Undo), protecting Atomicity and Durability.

### What is Write Skew, which can occur even under Snapshot Isolation?
E: If a married couple both check "the total of our two accounts is enough" at the same time and each withdraws a large amount from their own account, each thought they followed the rule, but the total goes negative.
A: Write Skew is an anomaly where two Transactions read the same condition and, based on that result, modify different Rows, so the rule (Invariant) breaks when viewed together. Since they don't modify the same Row, Snapshot Isolation's (MVCC-based Repeatable Read's) write-conflict check doesn't catch it. It is prevented by using Serializable Isolation (SSI, 2PL) or Locking the Rows you read with `SELECT ... FOR UPDATE`.

## SQL vs NoSQL, Distributed Databases

#### Choosing a Data Model: Relational · Document · Graph · Key-Value · Wide-Column
ONE: The Data Model is **what shape you store data in**. There are tables (Relational), single-chunk documents (Document), networks of relationships (Graph), simple Key-Value, and more, and you choose to fit **the shape of the data and how it is used**.
LIKE: A relational DB is an Excel ledger with fixed columns, so it is accurate and good at linking things together. A Document DB is a free-form storage box, a Graph DB is a map of connections, and Key-Value is a locker you open just by looking at the ticket number.
STEP:
1. **Relational (SQL)**: Strong at structured data and many-to-many relationships. JOINs, rules guaranteed by the Schema, ACID Transactions. In exchange, hierarchical data gets split across several Tables.
2. **Document (MongoDB, etc.)**: Puts related information all together in one JSON-like document. Good for reading in one go (Locality) and easy to change structure. In exchange, JOINs and many-to-many relationships are weak.
3. **Graph (Neo4j, etc.)**: Points (Nodes) and relationships (Edges) are central. Strong at exploring deep relationships like "friends of friends of friends," weak at large aggregations.
4. **Key-Value (Redis, DynamoDB)**: Pulls out a Value directly by Key. Very fast and simple. Widely used for Caches and Sessions.
5. **Wide-Column (Cassandra, HBase)**: Strong at huge volumes of writes and horizontal scaling. In exchange, queries aren't flexible. Used for Logs and time-series data.
6. **Schema-on-Write vs Schema-on-Read**: Relational DBs check the format when writing. Saying a Document DB's "Schema is flexible" doesn't mean there is no Schema; it means **it is interpreted when reading**. In the end, the code still assumes a shape for the data.
| Kind | Strengths | Weaknesses | Good fit |
| Relational | JOINs, rule guarantees, Transactions | Hierarchical data gets split | Payments, orders, members |
| Document | Reading as one chunk, flexible structure | Weak JOINs·many-to-many | Product details, content |
| Graph | Deep relationship exploration | Large aggregations | Friend recommendations, fraud detection |
| Key-Value | Very fast | Simple search features | Cache, Session |
| Wide-Column | Massive writes, horizontal scaling | Low query flexibility | Logs, time series |
KEY: Neither "SQL vs NoSQL" is always better. A single service often uses several DBs together, like PostgreSQL for orders, Redis for caching, and Elasticsearch for search.
END: Look at the data's shape and access pattern first, then choose the Data Model. Relational is strong at correctness·relationships; the NoSQL family is strong at flexibility·scale.

#### Replication
ONE: **Copying the same data onto several servers**. The service stays alive even if one dies, and reads can be spread across several machines.
LIKE: It is like making several copies of an important document and keeping them in different offices. Even if one office burns down, the document survives, and people can each read it at whichever office is closest.
STEP:
1. **Single-Leader (most common)**: Only one Leader (Primary) accepts writes and passes changes on to the Followers (Replicas). The Followers share the reads. It is simple and has no write conflicts. If the Leader dies, one Follower must be promoted to the new Leader (**Failover**).
2. **Multi-Leader**: Accepts writes in several places. Used for multiple datacenters or offline editing, but if the same data is changed in two places at once, the conflict must be resolved.
3. **Leaderless**: Write to any server and read from several. With n replicas, writing to w and reading from r with **w + r > n** guarantees that at least one of the servers read has the latest value (**Quorum**).
4. **Synchronous vs Asynchronous**: Synchronous replication COMMITs only after a Follower confirms receipt, so it is safe, but one slow Follower slows everything down. Asynchronous replication is fast, but if the Leader suddenly dies, recent writes can be lost. In practice, a common compromise is to make just one Follower synchronous.
5. **Strange things caused by Replication Lag**: A post you just wrote disappears when you refresh (violating read-your-writes), time seems to go backward with each refresh (violating monotonic reads), and a reply shows up before the original post (violating causal order).
6. **Ways to resolve conflicts**: Last Write Wins (simple but can lose data), detecting concurrent writes with version information and merging, and data structures that merge automatically (**CRDTs**).
KEY: Picking where to read from based on the situation, like "read my own just-written post from the Leader," greatly reduces Replication Lag problems.
END: Replication is keeping the same data in several places, and you have to weigh safety (synchronous) vs speed (asynchronous) along with replication lag problems.

#### Sharding (Partitioning)
ONE: When the data doesn't fit on one server or there are too many writes, you **split the data and store the pieces on different servers**. This is Sharding.
LIKE: When a phone book gets too thick, you split it into two volumes, A–M and N–Z. Replication is copying the same phone book many times, and Sharding is splitting the contents into separate books.
STEP:
1. **Splitting by Key range (Range)**: Names A–M go to server 1, N–Z to server 2. Range searches are easy, but data or requests can pile up in a particular range (e.g., splitting by date piles today's data onto one server).
2. **Splitting by the Key's Hash**: The Hash value decides the server. Data spreads evenly, but range searches have to look at every server.
3. **Hot Spot**: Requests piling onto one very popular Key (like a celebrity's account) are not solved automatically by any method. You handle it yourself, for example by appending a random number to the Key to split it into several.
4. **Rebalancing**: Adding·removing servers means moving data. Splitting by "Hash % number of servers" is avoided because changing the number of servers moves almost every Key. Instead, you create a large number of small Partitions from the start and distribute them among servers, or use **Consistent Hashing**.
5. **Downside**: JOINs and Transactions that span several Shards become hard. That is why it is important to choose Keys so that data used together often lands on the same Shard.
| Aspect | Replication | Sharding |
| What it does | Copies the same data to several places | Splits data and spreads it across several places |
| What you gain | Failure protection, spreading reads | Scaling storage·writes |
| Difficulties | Replication lag, conflicts | JOINs·Transactions across Shards |
END: Replication is copying, Sharding is splitting. In practice, each Shard has its own Replicas, so the two are used together.

#### CAP Theorem
ONE: A theorem saying that in a distributed system, **when the Network splits (Partition)**, you must choose between **having everyone see the same latest data (Consistency)** and **responding to every request (Availability)**.
LIKE: The phone line between two bank branches goes down. You can pick only one: "stop transactions until we can confirm with each other" (Consistency) or "each keeps accepting transactions for now" (Availability).
STEP:
1. **Consistency (C)**: Every Node shows the same latest data (here meaning linearizability, a strong consistency where it looks as if there is only one copy).
2. **Availability (A)**: Every live Node responds to every request.
3. **Partition Tolerance (P)**: The system keeps working even when the Network splits and Nodes can't reach each other.
4. As long as you connect several servers over a Network, a Partition will happen eventually. So P is effectively not something you can give up.
5. So the real question is **"when a Partition happens, which do you protect, C or A?"**
6. **CP**: Rejects or delays some requests to keep consistency. For data that must not be wrong, like bank balances and inventory.
7. **AP**: Keeps responding even if it briefly shows old data. For data that can be briefly out of sync, like like-counts and feeds on social networks.
KEY: Even normally, with no Partition, there is a tug-of-war with Latency: "raising consistency makes things slower." So real design is less a C/A either-or and more "how much consistency to buy at what speed."
END: When the Network splits, you have to choose between "stopping to stay correct (CP)" and "responding anyway (AP)."

### What is the difference between SQL (Relational) and NoSQL? When do you use which?
E: A Relational DB is an Excel ledger with fixed columns, so it is accurate and good at linking things together. NoSQL is a free-form storage box, so you can put anything in quickly and easily split the boxes across several warehouses.
| Kind | How it stores | Representative products | Good fit |
| Key-Value | One Value per Key | Redis, DynamoDB | Cache, Session |
| Document | JSON-like Documents | MongoDB | Data whose structure changes often |
| Wide-Column | A different bundle of Columns per Row | Cassandra, HBase | Massive writes, Logs·Time Series |
| Graph | Nodes and relationships (Edges) | Neo4j | Friend recommendations, relationship exploration |
A: A Relational DB's strengths are a fixed Schema, JOINs, and ACID Transactions, which suit data where correctness and relationships matter, like payments·orders, and it mainly improves performance by Scaling Up a bigger Server. NoSQL has a flexible Schema and makes Scaling Out (horizontal scaling) across many Servers easy, which suits large·fast-changing data, but depending on the product, JOINs or Strong Consistency may be weak. Rather than one always being better, you choose based on the data's shape and consistency requirements, and many services use both.

### What is the CAP Theorem?
E: The phone line between two bank branches goes down (Network Partition). At that point you can pick only one: "stop transactions until we can confirm with each other" (Consistency) or "each keeps accepting transactions for now" (Availability).
A: The CAP Theorem states that a distributed system cannot guarantee Consistency (every Node has the same latest data), Availability (every request gets a response), and Partition Tolerance (it works even when the network splits) all at the same time. In real distributed environments, Network Partitions are unavoidable, so it is understood as choosing whether to prioritize Consistency (CP) or Availability (AP) when a Partition occurs.

### What is the difference between Sharding and Replication?
E: Sharding is splitting a phone book into two volumes, A–M and N–Z, and Replication is making several copies of the same phone book.
A: Sharding splits data by Key and stores different parts on several Servers to scale writes and storage capacity. Replication copies the same data to several Servers to spread reads and protect against failure (High Availability), usually with the Primary accepting writes and Replicas sharing the reads. Sharding makes JOINs·Transactions across Shards hard, and with Replication, Replication Lag can make Replicas briefly show old data.

### In Leader-based Replication, what problems does Replication Lag cause, and how are they solved?
E: Changes to the original ledger (Leader) reach the copies (Followers) late, so looking at a copy, something you just wrote may not be there yet, or time may seem to run backward.
A: With asynchronous Replication, Followers lag behind the Leader, which can cause Read-Your-Writes violations (data you just wrote isn't visible), Monotonic Read violations (data goes back in time with each refresh), and Causal Order violations (a reply appears before the original post). These are mitigated by sending a user's reads right after they write to the Leader, having one user always read from the same Replica, and delivering causally related writes in the same order.

## Practical Topics

#### Storage Engines: B-Tree vs LSM-Tree
ONE: The way a DB stores data on Disk (its Storage Engine) falls into two broad kinds: **B-Trees, which overwrite in place**, and **LSM-Trees, which collect writes and write them out in order all at once**.
LIKE: A B-Tree is like finding the right page in an organized binder and editing it right there. An LSM-Tree is like piling new notes in a basket on your desk, filing them in order as a new folder when the basket fills, and occasionally merging several folders to tidy up.
STEP:
1. **The B-Tree family (most relational DBs)**: Splits data into fixed-size Pages and **overwrites the Page in place** when a value changes. A failure mid-overwrite could corrupt it, so it records to the WAL first.
2. B-Trees give predictable, fast reads. Any Key is found in a few Page reads.
3. **The LSM-Tree family (RocksDB, Cassandra, etc.)**: Collects writes first in a sorted Buffer in Memory.
4. When the Buffer fills, it writes it to Disk **in order, all at once,** as a sorted file (**SSTable**). Disks are fast at sequential writes, so write throughput is very high.
5. As files pile up, it merges several files in the background and cleans out deleted values (**Compaction**).
6. Reads may have to check several files, which can be slow. So it uses a **Bloom Filter**, which quickly tells you "this file definitely does not have that Key."
| Aspect | B-Tree | LSM-Tree |
| How it writes | Overwrite in place + WAL | Collect and write in order |
| Strengths | Stable read latency | Write throughput, compression |
| Weaknesses | Writes are relatively slow | Checking several files on reads, Compaction cost |
| Examples | MySQL InnoDB, PostgreSQL | RocksDB, Cassandra, LevelDB |
KEY: These are only general tendencies; real performance has to be measured with your own service's workload.
END: For read-heavy work, B-Trees tend to win; for explosive write volumes, LSM-Trees tend to win.

#### OLTP and OLAP
ONE: **OLTP** is **"quickly reading and writing a few rows"** to handle user requests, and **OLAP** is **"scanning millions of rows to aggregate"** for analysis. Their purposes differ, so they store data differently.
LIKE: OLTP is a store's checkout counter. It quickly processes each customer's payment one at a time. OLAP is the headquarters analytics team. It gathers a month of nationwide sales and analyzes "which products sold well."
STEP:
1. **OLTP (Online Transaction Processing)**: Reads and writes a few Rows by Key, like orders, payments, and signups. Fast responses and correctness matter. PostgreSQL, MySQL.
2. **OLAP (Online Analytical Processing)**: Scans a huge number of Rows to aggregate, like "total sales by region last month." Used by analysts and dashboards.
3. **Row-Oriented**: Stores all the Columns of a Row together. Good for OLTP, which reads one person's info as a whole.
4. **Column-Oriented**: Stores values of the same Column together. You can read only the Columns you need, like "add up just the sales Column," and similar values in a row compress well. Good for OLAP.
5. **Data Warehouse**: A DB just for analysis. Data is moved from the operational DB (OLTP) through **ETL/ELT** (extract·transform·load). It is separated so analysis Queries don't slow down the live service.
6. **Star Schema**: The classic design for analysis. A central record of events (**Fact Table**, e.g., sales records) is surrounded by descriptive info (**Dimension Tables**, e.g., products, stores, dates).
| Aspect | OLTP | OLAP |
| Access | Read and write a few rows by Key | Scan millions of rows to aggregate |
| Users | End users, apps | Analysts, dashboards |
| Storage | Row-oriented | Column-oriented + compression |
| Examples | PostgreSQL, MySQL | Data Warehouses (BigQuery, Snowflake, etc.) |
END: Split service processing into OLTP (row-oriented) and analysis into OLAP (column-oriented), and move data with ETL.

#### Redis and Caching
ONE: **Redis** is a very fast Key-Value store that keeps data **in Memory**. It is most often used as a **Cache** that keeps frequently read data up front.
LIKE: Instead of going all the way to the warehouse (Disk DB), you keep the things you look for most often in the drawer next to the checkout counter (Memory).
STEP:
1. Memory is much faster than Disk, so Redis usually responds in under 1 ms.
2. It supports not just simple strings but data structures like List, Hash, Set, and **Sorted Set** (sorted by score).
3. By default it executes commands one after another in a single Thread, so each individual command is Atomic.
4. **Cache usage pattern (Cache-Aside)**: Look in Redis first; if it isn't there, read from the DB and put it into Redis. From then on, take it straight from Redis.
5. Give Cache entries an expiration time (**TTL**) so stale values don't linger. When the original changes, the Cache must be deleted or updated (Cache Invalidation).
6. Data in Memory disappears when the power goes off, so if needed it is saved to Disk as a Snapshot (**RDB**) or a command Log (**AOF**).
USE: A Cache in front of the DB, storing login Sessions, limiting request counts (Rate Limiting), real-time rankings with Sorted Sets, and Pub/Sub messaging.
KEY: Remember "the Cache is not the original." Even if the Cache disappears, it must be rebuildable from the original DB.
END: Redis is a fast drawer in Memory, and caching frequently read data greatly reduces the load on the DB.

#### SQL Injection
ONE: An attack where, when user input is **concatenated directly into a SQL statement**, the attacker mixes SQL code into the input to **change the meaning of the Query**.
LIKE: Someone writes "John Smith, and also open the vault door" in the "name" field of an order form, and the clerk follows the sentence as an instruction.
STEP:
1. Dangerous code: concatenating input as a string, like `"SELECT * FROM users WHERE id = '" + input + "'"`.
2. If an attacker enters `' OR '1'='1`, the Query becomes `WHERE id = '' OR '1'='1'`. '1'='1' is always true, so every user is returned.
3. It can bypass login, leak data, or even delete Tables in bad cases.
4. **Core defense: Prepared Statements (Parameter Binding)**: Send the SQL statement's template and the values separately. The value slots are left as `?`, and input is passed only as a "value," so it is never interpreted as SQL syntax.
5. **Defenses used alongside**: Using an ORM, validating input, giving the DB account only the minimum permissions it needs (Least Privilege), and hiding DB details in error messages.
```sql
-- dangerous: concatenating strings
"SELECT * FROM users WHERE id = '" + input + "'"
-- safe: pass only the value to the Placeholder (?)
SELECT * FROM users WHERE id = ?
```
KEY: HTTPS only encrypts the transmission path; it does not prevent SQL Injection. The fundamental fix is Prepared Statements.
END: Concatenate input into SQL and the input becomes a command. Separate the template from the values (Prepared Statement) and it is blocked.

#### Stored Procedures
ONE: A feature that **stores several SQL statements inside the DB like a function** and calls them by name.
LIKE: It is like telling the staff member in charge "please handle task #3," instead of explaining a complicated, frequent task every time.
STEP:
1. Bundle several SQL statements and conditionals with `CREATE PROCEDURE` and store them in the DB.
2. The Application runs it with `CALL name(arguments)`.
3. **Pros**: Running several SQL statements in one call reduces Network round trips. Permissions can be granted per Procedure.
4. **Cons**: Business logic gets scattered inside the DB, making version control, Testing, and Debugging hard. It ties you to one DB product's syntax, making it hard to move to another DB.
5. So these days, logic usually lives in Application code, and Stored Procedures are used only where performance really demands it.
END: A Stored Procedure is a stored function inside the DB. It is fast but hard to manage, so today it is used sparingly.

### What is Redis? What is it used for?
E: It is keeping the things you look for most often in the drawer next to the checkout counter (Memory) instead of going all the way to the warehouse (Disk DB).
A: Redis is a Key-Value Store that keeps data in Memory and supports data structures like List·Hash·Set·Sorted Set in addition to String, making it very fast. It is used for Caching, login Sessions, Rate Limiting, rankings using Sorted Sets, Pub/Sub messaging, and more. By default, commands execute one after another in a single Thread, so individual commands are Atomic, and Memory data can be persisted to Disk with RDB Snapshots or AOF Logs.

### What are the pros and cons of Stored Procedures?
A: A Stored Procedure is several SQL statements stored inside the DB like a function and called by name. Its advantages are fewer Network Round Trips and the ability to grant permissions per Procedure. On the other hand, Business Logic gets scattered in the DB, making Version control·Testing·Debugging hard and tying you to a specific DB product, so these days Logic usually lives in Application code.

### What is SQL Injection? How do you prevent it?
E: Someone writes "John Smith, and also open the vault door" in the "name" field of an order form, and the clerk follows the sentence as an instruction.
A: SQL Injection is an attack where, when user input is merged directly into a SQL statement, the attacker uses input like `' OR '1'='1` to change the Query's meaning, bypassing authentication or leaking data. The core defense is the Prepared Statement (Parameter Binding), which separates input from SQL and passes it only as a value, used together with an ORM, Input Validation, Least Privilege for DB accounts, and hiding Error Messages.
```sql
-- dangerous: concatenating strings
"SELECT * FROM users WHERE id = '" + input + "'"
-- safe: pass only the value to the Placeholder (?)
SELECT * FROM users WHERE id = ?
```

### What is the difference between B-Tree and LSM-Tree storage engines?
E: A B-Tree is like finding the right page in a binder and editing it right there, and an LSM-Tree is like collecting new notes in a basket, filing them in order as a new folder, and occasionally merging folders to tidy up.
A: A B-Tree overwrites fixed-size Pages in place and uses a WAL to guard against failures; its read latency is stable, so most relational DBs use it. An LSM-Tree collects writes in a sorted Buffer in Memory (Memtable), writes them sequentially as sorted files (SSTables), and merges them with background Compaction, giving good write throughput and compression. In exchange, reads must check several files, which is compensated with Bloom Filters; RocksDB·Cassandra are representative.

### What is the difference between OLTP and OLAP?
E: OLTP is a store checkout counter that quickly processes each customer's payment, and OLAP is the headquarters analytics team that gathers a month of nationwide sales to analyze.
A: OLTP reads and writes a small number of Rows by Key in response to user requests, where fast responses and Transactions matter, and it uses row-oriented storage. OLAP is analytical work that scans millions of Rows to aggregate, using column-oriented storage (Column Store), which reads only the needed Columns and compresses well, and Data Warehouses. Data from the operational DB is moved to the Warehouse through ETL/ELT and is often designed as a Star Schema made of Fact Tables and Dimension Tables.
