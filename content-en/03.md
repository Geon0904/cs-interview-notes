## OS Basics

#### The Operating System and the Kernel
ONE: An **Operating System (OS)** is the program that manages hardware like the CPU, Memory, and Disk so many programs can share it **safely and fairly**, and its core part is the **Kernel**.
LIKE: Picture a mall food court with dozens of restaurants. Each restaurant (program) focuses only on selling food, while the food court's general manager (OS) handles electricity, gas, storage assignments, and cleaning schedules. The core staff member in the manager's office who actually touches the equipment is the Kernel.
STEP:
1. **What if there were no OS?** Every program would have to handle hardware directly, and one program could overwrite another program's Memory at will.
2. **What the OS does ①**: Makes hardware easy to use. A program just says "open this file" and does not need to know how the Disk circuitry works.
3. **What the OS does ②**: Hands out resources. It divides CPU time, Memory space, files, and the network among programs.
4. **What the OS does ③**: Protects programs from each other (Isolation). If one program crashes or misbehaves, the other programs and the system stay safe.
5. **Kernel**: The core of the OS that manages hardware directly. Things like a file browser or the settings app may come with the OS, but they are not the Kernel.
6. **User Mode / Kernel Mode**: A CPU has two modes. Ordinary programs run in **User Mode**, where they cannot use dangerous Instructions (controlling hardware directly, touching someone else's Memory). Only the Kernel runs in **Kernel Mode**, where every Instruction is allowed.
WHY: So that one program's Bug or malicious code cannot wreck the whole computer. Dangerous work is locked away so only the trusted Kernel can do it.
USE: Windows, macOS, Linux, Android, and iOS are all Operating Systems, and most servers run on the Linux Kernel.
KEY: When a program needs the Kernel's help, it can ask only through the official entrance, the **System Call** (the next concept).
END: The OS is the general manager that runs, divides, and protects the hardware for everyone, and only the Kernel in Kernel Mode can do dangerous work.

#### System Calls
ONE: The **official entrance through which an ordinary program asks the Kernel for things** like "read this file" or "create a new Process."
LIKE: Restaurant staff cannot touch the gas valves or the breaker box themselves. When they need something, they hand a standard request form to the manager's office window: "Please bring ingredients from storage (read)," "Please hire one more worker (fork)." That request form is a System Call.
STEP:
1. A program wants to read a file, but in User Mode it cannot touch the Disk directly.
2. So it calls a System Call such as `read`. The CPU then **switches into Kernel Mode** with a special Instruction (`syscall` on x86-64).
3. The Kernel checks that the request is safe (does this program have permission to read this file?) and actually fetches the data from the Disk.
4. It hands the result to the program and **returns to User Mode**.
5. Functions we use every day, like Python's `open()` or C's `printf()`, ultimately call System Calls inside.
| Area | Typical System Calls |
| Files | open, read, write, close |
| Processes | fork, exec, wait, exit |
| Memory | mmap, brk |
| Network | socket, connect, send, recv |
WHY: To let only the Kernel do dangerous work while still letting programs use the features they need, there has to be an "official window."
CON: Switching between User Mode and Kernel Mode has a cost. That is why reading data in one big chunk is faster than reading it 1 Byte at a time many times (Buffering).
END: A System Call is the only official window for a program to hand work to the Kernel, and each call takes a quick trip into Kernel Mode.

#### Interrupts
ONE: A **signal that tells the CPU "something needs handling right now!"** The CPU pauses what it was doing, handles it, and comes back.
LIKE: If the doorbell rings while you are cooking, you mark where you were, answer the door, and come back to keep cooking. That is far more efficient than walking to the door every second to check whether anyone is there (Polling).
STEP:
1. **Hardware Interrupt**: When you press a key, data arrives over the network, or a Disk read finishes, the device sends the CPU a signal.
2. **Timer Interrupt**: An alarm that goes off at regular intervals. The OS uses it to take back control periodically so no program can hog the CPU.
3. **Software Interrupt / Exception**: Events that happen while a program runs, like dividing by zero, accessing Memory that is not present (Page Fault), or making a System Call.
4. **Handling, step ①**: The CPU saves the state of what it was doing (Registers, the PC).
5. **Handling, step ②**: It looks up "this Interrupt is handled by this function" in the **Interrupt Vector Table** and runs that handler (the **ISR, Interrupt Service Routine**).
6. **Handling, step ③**: When the handler finishes, the CPU restores the saved state and returns to what it was doing.
WHY: Devices never know when something will happen. Checking constantly (Polling) wastes the CPU, while Interrupts let it react only when something actually happens.
USE: Keyboard input, mouse movement, network packets arriving, and many programs taking turns to run (Timer Interrupts) all depend on Interrupts.
END: An Interrupt is a "call me when something happens" approach. The CPU saves its state → handles it → restores and returns.

### What are the OS and the Kernel? Why separate User Mode and Kernel Mode?
E: Restaurant staff (ordinary programs) must not touch the gas valves or the breaker box directly. When they need something, they ask the building manager (Kernel), and only the manager has access to dangerous equipment.
A: The Kernel is the core of the OS that manages Hardware directly. The CPU blocks dangerous Instructions (Device control, access to another Process's Memory) in User Mode and allows them only in Kernel Mode. This separation keeps one program's Bug or malicious code from bringing down the whole system.

### What is a System Call?
E: It is an official request form staff hand to the manager: "Please bring a file from storage (read)," "Please hire one more worker (fork)."
A: A System Call is the entrance a user program uses to access Kernel features (Files, Processes, Network, Memory). Calling one switches to Kernel Mode via a Trap Instruction (syscall on x86-64); the Kernel handles the work and returns to User Mode. read, write, open, fork, and exec are typical examples.

### What is an Interrupt, and how is it handled?
E: If the doorbell rings while you're cooking, you mark where you were, answer the door, and come back to continue. That is far more efficient than the cook checking the door every second (Polling).
A: An Interrupt is a signal that tells the CPU "something needs handling now." There are Hardware Interrupts such as the keyboard, Timer, and Disk, and Software Interrupts such as System Calls and Exceptions (division by zero, Page Fault). The CPU saves its current state, finds the handler (ISR, Interrupt Service Routine) in the Interrupt Vector Table and runs it, then restores the state and returns to what it was doing.

## Process

#### Programs, Processes, and the Address Space
ONE: A **Program** is an executable file stored on Disk, and a **Process** is that Program loaded into Memory and **actually running**.
LIKE: A Program is a cookbook on the shelf, and a Process is a restaurant open for business using that cookbook. You can even open two restaurants from the same cookbook, just as you can open several Chrome windows.
STEP:
1. A Program (for example, `chrome.exe`) is a file sitting quietly on Disk. It does nothing.
2. When you run it, the OS sets aside space in Memory and loads the Program. Now it is a Process.
3. The OS gives each Process a number (**PID, Process ID**) and resources (Memory space, open files, CPU time).
4. Each Process gets its own Memory space (**Address Space**). It cannot see or touch another Process's space.
5. The Address Space is divided into four regions.
| Region | What goes there | Food court analogy |
| Code (Text) | The machine Instructions to run | Recipes posted on the wall |
| Data | Global variables, static variables | Basic seasonings that always sit in the same spot |
| Heap | Data created at run time with malloc/new | Extra shelves borrowed as needed (grows upward) |
| Stack | Local variables and the Return Address for each function call | Plates stacked and cleared for each order (grows downward) |
WHY: Separating each Process's space means one program crashing leaves the others safe, and programs cannot snoop on each other's data.
USE: The list you see in Task Manager (Windows) or `ps`·`top` (Linux) is the list of Processes.
KEY: The Heap grows upward from low addresses and the Stack grows downward from high addresses, so they grow toward each other.
END: A Program is the cookbook, and a Process is a restaurant open for business. Each restaurant has its own separate storage (Address Space).

#### The PCB and Process States
ONE: The OS keeps an information card called a **PCB (Process Control Block)** for each Process, and a Process moves through the states **New → Ready → Running → Waiting → Terminated**.
LIKE: The manager keeps a file card for each restaurant. It records the shop number, whether it is open right now, and how far the cook got, so when a cook steps away to another shop and comes back, they can pick up right where they left off by reading the card.
STEP:
1. **What goes in the PCB**: The PID, the current state, the Program Counter (where the next Instruction is), Register values, the Priority, Memory information (the Page Table), and the list of open files.
2. **New**: The Process is just being created.
3. **Ready**: It is ready to run and waiting for its turn on the CPU. It is an order ticket in line waiting for a cook.
4. **Running**: It is running on the CPU right now. Only one Process can be Running on a CPU Core at any instant.
5. **Waiting (Blocked)**: It is waiting for something, like a Disk read or keyboard input, so it cannot run even if a CPU is free. It is an order ticket waiting for an ingredient delivery.
6. **Terminated**: It has finished running.
7. **When the state changes**: A Timer Interrupt during Running → back to Ready; requesting I/O → Waiting; the I/O finishing → back to Ready.
WHY: The CPU takes turns running Processes. To pause and later resume, you need to save "how far it got" somewhere, and that place is the PCB.
USE: The letters you see in Linux `top`, like `R` (Running), `S` (Sleeping, i.e., waiting), and `Z` (Zombie), are Process states.
END: The PCB is a Process's file card, and a Process moves between Ready (in line) ↔ Running (executing) ↔ Waiting (blocked).

#### fork · exec · wait: Creating Processes
ONE: On Unix/Linux you **clone the current Process with fork()**, **switch to a different Program with exec()**, and **wait for the child to finish with wait()**.
LIKE: fork is cloning the whole restaurant to open an identical branch next door, exec is replacing the branch's sign and menu with a completely different restaurant, and wait is the original restaurant waiting for the branch's closing report.
STEP:
1. **fork()**: Makes a nearly exact copy of the current Process (the Parent) to create a Child Process. The code, the variable values, and the current position are all the same.
2. From the line after fork(), **both** the Parent and the Child run. To tell them apart, look at the return value: the Parent gets the Child's PID and the Child gets 0.
3. **exec()**: Overwrites the current Process's Memory with a new Program. The PID stays the same, but what it does changes completely.
4. When you type `ls` in a terminal, the Shell uses fork() to make a copy of itself, and that Child uses exec() to become the `ls` Program.
5. **wait()**: The Parent waits until the Child finishes and receives the Child's result (Exit Status).
6. **Output order**: After fork, the Parent and the Child are Scheduled separately. Which runs first is up to the OS, so without Synchronization like wait, you cannot guarantee the order of their output.
```c
pid_t pid = fork();
if (pid == 0) {            // Child
    execlp("ls", "ls", NULL);
} else {                   // Parent
    wait(NULL);            // wait until the Child finishes
}
```
KEY: Calling fork() n times in a row makes 2ⁿ Processes, because every newly created Process also runs the next fork.
WHY: Splitting it into "clone + switch" lets the Child set up its input/output connections and environment however it likes before becoming the new Program. The Shell's `>` redirection is implemented this way.
END: fork = clone, exec = switch, wait = wait. All three happen every time you type a command in a terminal.

#### Zombie Processes and Orphan Processes
ONE: A **Zombie** is a Process that has finished but whose parent never collected its result, so only its record remains; an **Orphan** is a Process left alone because its parent finished first.
LIKE: A Zombie is like a branch that has closed, but the original restaurant never signed the closing paperwork, so its name stays in the directory. An Orphan is like a branch left on its own because the original restaurant closed first.
STEP:
1. When a Child finishes, the OS cleans up its Memory but keeps a small record of "how it ended" (the Exit Status) so the Parent can check it.
2. When the Parent calls wait(), it collects that record, and only then does the record disappear.
3. **Zombie Process**: The Parent never called wait(), so the record lingers. It uses almost no Memory, but it occupies a slot in the Process Table (a PID).
4. If countless Zombies pile up, PIDs run out and no new Processes can be created.
5. **Orphan Process**: A Child whose Parent finished first. On Linux a Process such as init (PID 1) adopts it and later cleans it up with wait() on the parent's behalf.
WHY: When a server program keeps creating Children but forgets to wait, Zombies pile up and cause real outages.
USE: In `ps`, a state shown as `Z` or `<defunct>` is a Zombie. The fix is to make the Parent call wait() or to terminate the Parent (then init adopts and cleans up the Zombies).
END: Finished but not cleaned up is a Zombie; parentless is an Orphan. A parent must always reap its children with wait().

### What is a Process? How is it different from a Program?
E: A Program is a cookbook on the shelf, and a Process is a restaurant actually open for business with that cookbook. You can open two restaurants from the same cookbook (several Chrome windows).
A: A Program is an Executable stored on Disk, and a Process is that file loaded into Memory and running. A Process receives its own resources from the OS, such as an Address Space, Register state, and open Files.

### How is a Process Address Space organized?
| Region | What goes there | Food court analogy |
| Code (Text) | The machine Instructions to run | Recipes posted on the wall |
| Data | Global variables, static variables | Basic seasonings that always sit in the same spot |
| Heap | Data created at run time with malloc/new | Extra shelves borrowed as needed (grows upward) |
| Stack | Local variables and the Return Address for each Function Call | Plates stacked and cleared for each order (grows downward) |
A: A Process Address Space is divided into the Code, Data, Heap, and Stack regions. The Heap grows upward from low Addresses and the Stack grows downward from high Addresses, so they grow toward each other.

### What is in a PCB?
E: It is the file card the manager keeps for each restaurant. It records the shop number, whether it is open now, and how far the cook got, so the cook can continue right away after coming back.
A: A PCB (Process Control Block) is the bundle of information the OS keeps for each Process, including the PID, the Process State, the Program Counter and Register values, Scheduling information (Priority), Memory management information (the Page Table), and the list of open Files. During Context Switching, the state is saved into it and loaded back from it.

### What are the Process States?
E: Reservation taken (New) → in line waiting for a cook (Ready) → being cooked (Running) → waiting for an ingredient delivery (Waiting) → closed for the day (Terminated).
A: A Process moves between the New, Ready, Running, Waiting (Blocked), and Terminated states. A Timer Interrupt while Running sends it to Ready, requesting I/O sends it to Waiting, and when the I/O finishes it returns to Ready.

### How do fork(), exec(), and wait() work? Why isn't the output order fixed after fork?
E: fork is cloning the whole restaurant to open an identical branch next door, exec is replacing the branch's sign and menu with a completely different restaurant, and wait is the original restaurant waiting for the branch's closing report. Whether the original or the branch serves customers first is up to the manager (Scheduler).
A: fork() clones the current Process to create a Child, returning the Child's PID to the Parent and 0 to the Child. exec() overwrites the current Process's Memory with a new Program, and wait() pauses the Parent until the Child finishes. After fork, the Parent and the Child are Scheduled independently, so without Synchronization such as wait, the output order cannot be guaranteed.
M: Calling fork() n times in a row creates 2ⁿ Processes in total, because every Process runs the next fork.

### What are Zombie Processes and Orphan Processes?
E: A Zombie is a branch that closed, but the original restaurant never signed the closing paperwork, so only its name remains in the directory; an Orphan is a branch left alone because the original restaurant closed first.
A: A Zombie Process has terminated, but its Parent has not collected its Exit Status with wait(), so its entry remains in the Process Table. An Orphan Process is a Child whose Parent terminated first; on Linux a Process such as init (PID 1) adopts it and cleans it up instead.

## Thread

#### Threads vs Processes
ONE: A **Thread** is a **flow of execution running concurrently** inside one Process. Threads in the same Process share Memory, and each keeps only its own record of "how far it got."
LIKE: If a Process is an independent restaurant, Threads are the order tickets being worked on at the same time inside it. The tickets share the same kitchen and storage, and each has only its own progress notes (Registers) and its own workspace (Stack). They cannot use another restaurant's storage.
STEP:
1. A Process starts with a single Thread (the Main Thread).
2. Create more Threads and several jobs run at once inside one Process. Example: a browser drawing the page while downloading a file.
3. **What they share**: Code, Data (global variables), the Heap, and open files.
4. **What each has separately**: a Stack, Registers, and a Program Counter, because each may be running a different function.
5. So Threads can pass data instantly through a single variable, but problems arise if they modify the same variable at the same time (Synchronization, covered later).
| Aspect | Process | Thread |
| Memory | Independent Address Space | Shares Code·Data·Heap; only the Stack is separate |
| Cost to create and switch | High | Low |
| Exchanging data | Needs IPC | Directly through shared variables (needs synchronization) |
| Impact of a crash | Other Processes are safe | Can take down the whole Process |
WHY: To do several things at once within one program while being much lighter than creating several Processes.
USE: A web server hands each request to its own Thread, and a game handles graphics, sound, and networking on different Threads.
END: A Process is the building and a Thread is a flow of work inside it. Threads are lightweight, but because they share Memory they must be used carefully.

#### Multi-Thread vs Multi-Process
ONE: To do many things at once you can use **several Threads** or **several Processes**. Threads are light and fast; Processes are safe and sturdy.
LIKE: When customers pile up, working more order tickets in the same building (Multi-Thread) is cheap and fast, but everyone shares one kitchen, so you have to avoid bumping into each other. Opening another building (Multi-Process) is expensive, but if one restaurant catches fire, the others are fine.
STEP:
1. **Multi-Thread pros**: Low cost to create and switch. Memory is shared, so data passes instantly without copying.
2. **Multi-Thread cons**: Modifying shared data at the same time gets tangled (Race Condition). If one Thread hits a fatal error, the whole Process dies.
3. **Multi-Process pros**: Memory is separated, so if one dies the rest survive. It also provides security isolation.
4. **Multi-Process cons**: Higher creation cost and Memory use. Exchanging data requires IPC.
5. **How to choose**: Threads when speed and data sharing matter; Processes when stability and isolation matter.
USE: Chrome runs each tab in its own Process, so one frozen tab does not affect the others (Multi-Process). Many server programs, on the other hand, handle requests with a Thread Pool (Multi-Thread).
END: Multi-Thread for light and fast, Multi-Process for safe and sturdy.

#### User-Level Threads and Kernel-Level Threads
ONE: A **User-Level Thread** is managed by the program (a Library) without the Kernel knowing, and a **Kernel-Level Thread** is known to and managed directly by the Kernel.
LIKE: A User-Level Thread is like extra order tickets the restaurant's shift lead hands out unofficially. The general manager (Kernel) does not know they exist, so it sends that restaurant only one cook. A Kernel-Level Thread is an order ticket officially registered with the manager, so the manager can send several cooks to work on them at once.
STEP:
1. **User-Level Thread**: The Library switches between Threads itself. It never asks the Kernel, so switching is very fast.
2. Downside: the Kernel sees the Process as having only one Thread (Many-to-One). So if one Thread makes a System Call that waits, like a Disk read, the whole Process stops, and it uses only one CPU Core even if there are several.
3. **Kernel-Level Thread**: The Kernel knows about and Schedules each Thread. They can truly run at the same time on multiple Cores, and when one waits, the others keep running.
4. Downside: creating and switching them goes through the Kernel, so they cost a bit more.
5. Linux and Windows map each Thread we create 1:1 to a Kernel Thread (the **One-to-One Model**).
USE: There is also a model (Many-to-Many) that runs many very light execution units on a small number of Kernel Threads, like goroutines in the Go language.
END: User-Level is fast but limited because the Kernel does not know about it; Kernel-Level is a bit heavier but uses multiple Cores properly.

### What is the difference between a Process and a Thread?
E: A Process is an independent restaurant, and a Thread is an order ticket being worked on at the same time inside it. The tickets share the same kitchen and storage, and each has only its own notes on "how far it got" (Registers) and its own workspace (Stack). They cannot use another restaurant's storage.
A: A Process is a unit of execution with its own Address Space and resources, and a Thread is a flow of execution inside a Process. Threads in the same Process share Code·Data·Heap·open Files and have only their own Stack·Registers·PC. So Threads are light to create and switch and easy to communicate between, but a fatal error in one Thread terminates the whole Process.
| Aspect | Process | Thread |
| Memory | Independent Address Space | Shares Code·Data·Heap; only the Stack is separate |
| Cost to create and switch | High | Low |
| Communication | Needs IPC | Directly through shared variables (needs Synchronization) |
| Impact of an error | Other Processes are safe | Can terminate the whole Process |

### Why use Multi-Thread instead of Multi-Process?
E: When customers pile up, working more order tickets in the same building (Multi-Thread) is cheaper and faster than opening another building (Multi-Process). But everyone uses the same kitchen, so you have to avoid bumping into each other.
A: Threads share an Address Space, so creation, Context Switching, and Memory costs are lower and data can be exchanged without IPC. In exchange, shared data needs Synchronization and an error in one Thread spreads to the rest. When stability and security matter, you choose Multi-Process (for example, Chrome's separate tabs).

### What is the difference between User-Level Threads and Kernel-Level Threads?
E: A User-Level Thread is an extra order ticket the shift lead hands out unofficially inside the restaurant, so the general manager (Kernel) does not know it exists. That makes switching fast, but the manager sends only one cook per restaurant.
A: User-Level Threads are managed by a Library without the Kernel's knowledge, so switching is fast, but in the Many-to-One Model a Blocking System Call from one Thread stops them all and multiple Cores cannot be used. Kernel-Level Threads are Scheduled directly by the Kernel and run in parallel across Cores, but cost more to create and switch. Linux and Windows connect User Threads and Kernel Threads One-to-One.

## Context Switching and IPC

#### Context Switching
ONE: The work of **saving the current state and loading the next one's state** when the CPU switches the running Process (or Thread) to another.
LIKE: When a cook switches from ticket A to ticket B, they jot "chopped the onions" on A, read B's notes, and pick up from there. Cooking stops while they write and read notes, so switching too often is a loss.
STEP:
1. Entry into Kernel Mode happens because of a Timer Interrupt or a System Call.
2. The current Process's Registers and Program Counter are saved into its PCB, and its state changes from Running → Ready (or Waiting).
3. The Scheduler picks the next Process to run.
4. The chosen Process's Registers and Program Counter are loaded from its PCB back into the CPU. If it is a different Process, the Memory map (Page Table) is switched too.
5. Returning to User Mode, the new Process continues from where it stopped.
WHY: To make one CPU Core look like it runs many programs "at the same time," it has to switch between them every tiny slice of time. Each switch is a Context Switch.
CON: No useful work happens while saving and restoring. On top of that, after switching to a new Process, the Cache and TLB still hold the previous Process's data (they have gone "cold"), so things are slow for a while.
KEY: Switching between Threads of the same Process does not require changing the Memory map (Page Table), so it is lighter than switching between Processes.
END: Context Switching is "take a note → read the next note → continue," and it is necessary but not free.

#### IPC (Inter-Process Communication)
ONE: Processes have separate Memory, so they cannot exchange data directly. Instead they talk through **communication methods (IPC)** provided by the OS.
LIKE: Restaurants cannot walk into each other's storage. Instead they communicate through a pipe between shops (Pipe), a shared mailbox (Message Queue), a jointly used storeroom (Shared Memory), the phone (Socket), or a buzzer (Signal).
STEP:
1. **Pipe**: A one-way channel: put something in one end and it comes out the other. The Shell's `ls | grep txt` is a Pipe.
2. **Message Queue**: A mailbox you put messages into and take them out of, one message at a time.
3. **Shared Memory**: Connects the same physical Memory to two Processes. There is no copying, so it is the fastest, but you must handle synchronization yourself so they do not modify it at the same time.
4. **Socket**: The network communication method. It can talk not only within the same computer but with other computers.
5. **Signal**: Sends only a very short notification. Pressing Ctrl+C in a terminal sends a SIGINT Signal that stops the program.
| Method | Analogy | Characteristics |
| Pipe | One-way pipe | One direction, usually between Parent and Child (anyone can use a Named Pipe) |
| Message Queue | Shared mailbox | Put in and take out message by message |
| Shared Memory | Shared storeroom | Fastest; synchronization is up to you |
| Socket | Phone | Can talk to other computers too |
| Signal | Buzzer | Short notifications only |
WHY: Separating Processes made things safe, so there has to be an official channel for when they need to cooperate.
KEY: Pipes, Message Queues, and Sockets copy data through the Kernel, while Shared Memory looks at the same space without copying, which makes it fast but puts more responsibility on you.
END: IPC is the OS's official channel for separated Processes to talk. Shared Memory for speed, Pipes for simplicity, Sockets for distance.

### Explain Context Switching and list its steps.
E: When a cook switches from ticket A to ticket B, they write "chopped the onions" on A, read B's notes, and continue. Cooking stops while they write and read notes, so switching often is a loss.
A: Context Switching is the work of saving the current state and loading the next one's state when the CPU switches the running Process (or Thread). No useful work happens during saving and restoring, and the Cache and TLB go Cold, which creates Overhead.
1. Enter Kernel Mode through a Timer Interrupt or a System Call.
2. Save the current Process's Registers·PC into its PCB and change its state (Running → Ready or Waiting).
3. The Scheduler picks the next Process to run.
4. Restore the Registers·PC from the new Process's PCB, and switch the Address Space (Page Table) too if it is a different Process.
5. Return to User Mode; the new Process runs from where it stopped.
M: Switching between Threads of the same Process does not require changing the Address Space, so it is lighter than switching Processes.

### What are the IPC (Inter-Process Communication) methods?
| Method | Analogy | Characteristics |
| Pipe | A one-way pipe between two shops | One direction, usually between Parent and Child (anyone can use a Named Pipe) |
| Message Queue | Shared mailbox | Put in and take out Message by Message |
| Shared Memory | A storeroom two shops share | Fastest, but you must handle Synchronization yourself |
| Socket | Phone | Can communicate with other computers too |
| Signal | Buzzer | Delivers only short notifications (e.g., SIGINT from Ctrl+C) |
A: Processes have separate Memory, so they communicate through IPC provided by the OS. Pipes, Message Queues, and Sockets copy data through the Kernel, while Shared Memory connects the same Physical Memory to both sides, which is fast but leaves Synchronization entirely up to you.

## CPU Scheduling

#### CPU Scheduling and the Scheduler
ONE: **Deciding who gets the CPU next** among the Processes lined up in the Ready state is CPU Scheduling, and the OS component that decides is the **Scheduler**.
LIKE: A cook (CPU Core) can handle only one order ticket at a time. When tickets are piling up, the head chef who decides "what to work on next" is the Scheduler.
STEP:
1. There are usually far more Processes than CPU Cores, so they must take turns in some order.
2. There are several **criteria for good Scheduling**.
3. **CPU Utilization**: The fraction of time the CPU is working rather than idle. Higher is better.
4. **Throughput**: The number of jobs finished per unit of time. More is better.
5. **Waiting Time / Turnaround Time**: Time spent waiting in line / time from arrival to completion. Shorter is better.
6. **Response Time**: Time from a request to the first response. It matters for programs that must react immediately when you press a key.
7. **Kinds of Schedulers**: Short-term (decides which Process gets the CPU next, on a millisecond scale), Medium-term (temporarily moves some Processes out to Disk when Memory is short), and Long-term (decides which jobs to load into Memory, mainly in Batch systems).
WHY: The criteria conflict. Running short jobs first lowers average waiting time, but long jobs can keep getting pushed back. So you need rules that fit the situation.
END: The Scheduler is the head chef deciding "who's next?", balancing efficiency, fairness, and quick response.

#### Scheduling Algorithms: FCFS · SJF · SRTF · Priority · RR
ONE: Rules for handing the CPU to Processes waiting in line: **first come first served**, **shortest first**, **most important first**, **take turns a little at a time**, and so on.
LIKE: Imagine setting the line rules at a grocery store with only one checkout lane. You could go strictly in arrival order, let people with fewer items go first, let VIPs go first, or give each person one minute at a time in rotation.
STEP:
1. **FCFS (First-Come First-Served)**: Handle jobs to completion in arrival order. Simple, but if the person in front has an overflowing cart, everyone behind waits a long time (the **Convoy Effect**).
2. **SJF (Shortest Job First)**: Run the job with the shortest running time first. It gives the shortest average waiting time. But running times are hard to know in advance, and long jobs can keep getting pushed back.
3. **SRTF (Shortest Remaining Time First)**: SJF, except that when a shorter job arrives, the current job stops and yields (Preemptive).
4. **Priority**: Run the highest-priority job first. Important work gets done first, but low-priority jobs may never run.
5. **RR (Round Robin)**: Each job runs for a fixed short slice (**Time Quantum**); if it does not finish, it goes to the back of the line. Everyone gets a turn quickly, so response is fast.
6. **Example**: P1 (24 ms), P2 (3 ms), and P3 (3 ms) arrive at the same time. In FCFS order (P1→P2→P3), the waiting times are 0, 24, 27 → average 17 ms. In SJF order (P2→P3→P1), they are 0, 3, 6 → average 3 ms.
| Method | Rule | Pros | Cons |
| FCFS | Arrival order | Simple | Convoy Effect |
| SJF | Shortest job first | Minimum average waiting | Needs running-time estimates, Starvation |
| SRTF | Shortest remaining time (preemptive) | Better response than SJF | Frequent switching, Starvation |
| Priority | Most important first | Urgent work handled first | Starvation of low priorities |
| RR | Take turns per Time Quantum | Fair, fast response | Switching cost rises if the Quantum is too small |
KEY: If RR's Time Quantum is too large, it ends up the same as FCFS; if it is too small, all the time goes to Context Switching.
USE: The OSes on our PCs and phones care about responsiveness, so they are based on a mix of RR and Priority.
END: RR for fairness, SJF to cut average waiting, Priority for important work first. There is no single right answer; you choose based on the goal.

#### Preemption, Starvation and Aging, and MLFQ
ONE: If the CPU **can be taken away** from a running Process, it is **Preemptive**. **Starvation**, where a job keeps getting pushed back, is prevented by **Aging**, and the practical rule that combines these ideas is **MLFQ**.
LIKE: If a cashier can say "one moment" in the middle of ringing someone up and serve an urgent customer first, that is Preemptive. If VIPs keep arriving, regular customers never get out (Starvation), but if customers who have waited a long time gradually move up in rank (Aging), their turn eventually comes.
STEP:
1. **Non-Preemptive**: Wait until the Process gives up the CPU on its own (when it finishes or waits for I/O).
2. **Preemptive**: The OS can stop a running Process, for example with a Timer Interrupt, and give the CPU to another. Most modern OSes are preemptive.
3. **Starvation**: A Process with low priority or a long running time keeps getting pushed back and never runs.
4. **Aging**: Raise a Process's priority little by little the longer it waits, so it eventually runs.
5. **MLFQ (Multi-Level Feedback Queue)**: Keep several lines with different priorities and put new jobs in the top (fastest) line.
6. Long-running jobs that use up their whole Time Quantum gradually move down to lower lines, while jobs that finish quickly or often wait for input stay in the upper lines.
7. So short jobs naturally finish first even without knowing running times in advance (an effect similar to SJF). Periodically moving every job back to the top line (Priority Boost) prevents Starvation.
WHY: In reality you cannot know a job's running time in advance. MLFQ solves this by "learning as it watches."
END: Can take the CPU away → Preemptive; keeps getting pushed back → Starvation; raise the priority of long waiters → Aging; the practical rule that ties them together → MLFQ.

### What is a Scheduler, and what separates Short-term, Medium-term, and Long-term Schedulers?
E: The Long-term Scheduler is the host deciding "how many parties do we seat today," the Medium-term Scheduler is the staff member who sends some guests out to the waiting area when it gets too crowded, and the Short-term Scheduler is the head chef constantly deciding "which ticket does the cook pick up next."
A: A Scheduler is the OS component that decides which Process gets resources, and Schedulers are classified by how often they run and what they decide. The Long-term Scheduler decides which jobs to load into Memory (the Degree of Multiprogramming), the Medium-term Scheduler decides which Processes to Swap Out to Disk, and the Short-term Scheduler picks the next Process from the Ready Queue to get the CPU and runs most often (on a millisecond scale).

### Briefly explain FCFS, SJF, SRTF, Priority, and RR.
E: They are line rules at a grocery store with only one checkout lane.
| Method | Rule | Grocery analogy | Pros / Cons |
| FCFS | First come, first served | Just the order of the line | Simple / everyone waits if the person in front has a full cart (Convoy Effect) |
| SJF | Shortest running time first, Non-Preemptive | Fewer items go first | Minimum average waiting time / needs running-time estimates, Starvation of long jobs |
| SRTF | Shortest remaining time first, Preemptive | Step aside mid-checkout when someone with fewer items arrives | Preemptive version of SJF / frequent switching, Starvation |
| Priority | Highest Priority first | VIPs first | Important work first / Starvation of low Priority |
| RR | Take turns for a fixed time (Time Quantum) | One minute per person, then back of the line | Fast response, fair / switching cost rises if the Quantum is too small; becomes FCFS if too large |
A: FCFS (First-Come First-Served) uses arrival order, SJF (Shortest Job First) runs the shortest job first (Non-Preemptive), and SRTF (Shortest Remaining Time First) runs the job with the shortest remaining time (Preemptive). Priority runs in order of priority, and RR (Round Robin) takes turns by Time Quantum, which suits Interactive systems. SJF has the shortest average waiting time, but running times are hard to know in advance.
M: Average waiting time for P1 (24), P2 (3), P3 (3) arriving together: FCFS = (0 + 24 + 27)/3 = 17, SJF = (0 + 3 + 6)/3 = 3.

### Preemptive vs Non-Preemptive, Starvation and Aging?
E: Preemptive is when a cashier can say "one moment" in the middle of a checkout and take the next customer; Non-Preemptive is waiting until one customer is done. If VIPs keep arriving, regular customers never get out (Starvation), and raising the rank of customers who have waited a long time is Aging.
A: In Preemptive Scheduling the OS can take the CPU away from a running Process, while in Non-Preemptive Scheduling it waits until the Process gives it up. Starvation is when a particular Process keeps getting pushed back and never runs, and Aging prevents it by raising Priority in proportion to waiting time.

### What is MLFQ (Multi-Level Feedback Queue)?
E: Put every customer in the "express line" first, and move customers who take a long time to slower lines. Then short customers naturally get out quickly.
A: MLFQ keeps several Queues with different Priorities, moving CPU-Bound jobs that use up their Time Quantum down to lower Queues and keeping Interactive (I/O-Bound) jobs that pause often near the top. It behaves like SJF without knowing running times in advance, and periodically moving everything back to the top (Priority Boost) prevents Starvation.

## Synchronization

#### Race Conditions and Critical Sections
ONE: When several Threads modify the same data at the same time, **the result depends on the order of execution**; that problem is a Race Condition, and the stretch of code that handles that data is a **Critical Section**.
LIKE: Two employees look at the inventory sheet at the same time. Both read "10 eggs," each uses one, and each writes "9." In reality 8 are left, but the sheet says 9.
STEP:
1. `count += 1` is one line, but to the CPU it is three steps: ① read the value → ② add 1 → ③ write the value.
2. Right after Thread A reads 10 in step ①, Thread B also reads 10 in step ①.
3. A writes 11 in steps ②③, and B also writes 11 in steps ②③.
4. Two additions happened, but the result is 11. One disappeared. This is a **Race Condition**.
5. Problems like this appear only occasionally depending on timing, so they can hide during testing and blow up in production.
6. **Critical Section**: A stretch of code that reads and modifies shared data. Only one Thread at a time may enter it (**Mutual Exclusion**).
WHY: Where many requests arrive at once, like bank balances, inventory, or seat reservations, a Race Condition becomes an incident that costs money and trust.
USE: The same concert seat being sold to two people and an online store's inventory going negative are classic examples.
KEY: Code that always produces the right result even when many Threads call it at once is called **Thread-Safe**. You can make code Thread-Safe by protecting it with a Lock, using Atomic operations, or using data that cannot be modified at all (Immutable).
END: Modifying at the same time gets tangled (Race Condition). The stretch that modifies shared data (Critical Section) must let in only one at a time.

#### Mutex and Semaphore
ONE: A **Mutex** is a lock that lets in **only one** at a time, and a **Semaphore** is a numeric counter that lets in **up to a set number (N)**.
LIKE: A Mutex is the key to a single-stall restroom; only the person who took the key can return it. A Semaphore is the "stalls available" sign outside a restroom with 3 stalls. At 0 you wait, and whenever anyone comes out, the number goes up by 1.
STEP:
1. **Mutex (Mutual Exclusion)**: Call `lock()` when entering a Critical Section and `unlock()` when leaving. If another Thread already locked it, wait until it is released.
2. A Mutex has an **owner (Ownership)**. Only the Thread that locked it can unlock it.
3. **Semaphore**: A counter holding one integer. `wait()` (the P operation) decreases the value by 1 and waits if the value is 0. `signal()` (the V operation) increases the value by 1 and wakes a waiting Thread.
4. With an initial value of N, up to N can enter at once (**Counting Semaphore**). With an initial value of 1, it behaves like a Mutex (**Binary Semaphore**).
5. A Semaphore has no notion of an owner, so **a different Thread can signal it**. That is why it is also used to enforce order, as in "start B after A finishes."
| Aspect | Mutex | Semaphore |
| How many can enter at once | 1 | N (the initial value) |
| Owner | Yes (only the locking Thread unlocks) | No (anyone can signal) |
| Main use | Protecting shared data | Limiting resource counts, enforcing order |
USE: A Connection Pool that allows at most 10 DB Connections at once, or sharing 3 printers, uses a Counting Semaphore.
END: Only one at a time → Mutex; up to N → Semaphore. Semaphores are also used to enforce order.

#### Spinlock · Condition Variable · Monitor
ONE: Ways of waiting for a Lock and tools for "waiting until a condition holds." A **Spinlock** waits by checking over and over, a **Condition Variable** sleeps and gets woken up, and a **Monitor** bundles the two so they are easy to use.
LIKE: A Spinlock is waiting outside the restroom door and turning the handle again and again. A Condition Variable is writing your name on the waitlist ("call me when a spot opens") and sitting down to wait. A Monitor is a room that comes with both the key and the waitlist attached.
STEP:
1. **Spinlock**: Keeps checking in a loop until the Lock is released (**Busy Waiting**). There is no cost of sleeping and waking, so it pays off when a Lock is held only very briefly or there are multiple Cores. Waiting long wastes CPU.
2. **Condition Variable**: Sleeps while waiting for a condition like "until the Buffer is not empty." When another Thread makes the condition true and calls `signal()`, it wakes up. It is always used together with a Mutex.
3. After waking, it must **check the condition again**, because another Thread may have taken the item first (which is why you wait with `while`, not `if`).
4. **Monitor**: A tool that bundles Mutual Exclusion and Condition Variables at the language level. Java's `synchronized` with `wait()`/`notify()` is the classic example. You do not manage Locks by hand, so there are fewer mistakes.
WHY: Locks alone cannot efficiently handle situations like "wait until data arrives." Checking constantly wastes CPU, and if you sleep, you need a way to be woken.
END: For short waits, a Spinlock; for waiting on a condition, a Condition Variable; to bundle both safely, a Monitor.

#### Three Classic Synchronization Problems
ONE: The classic problems that come up when explaining synchronization are **Producer-Consumer**, **Readers-Writers**, and **Dining Philosophers**.
LIKE: Think of a bakery. The baker (Producer) puts bread on the display shelf and customers (Consumers) take it. When the shelf is full, the baker has to wait, and when it is empty, the customers have to wait.
STEP:
1. **Producer-Consumer**: One side puts items into a fixed-size Buffer and the other side takes them out. Do not put in when it is full, do not take out when it is empty, and do not modify the Buffer at the same time.
2. Solution: use a Semaphore `empty` that counts empty slots (initial value N), a Semaphore `full` that counts filled slots (initial value 0), and a Mutex to protect the Buffer.
3. **Readers-Writers**: Many can read at the same time, but while someone is writing, nobody else may read or write. It is solved with a Read-Write Lock. If readers keep arriving, a writer can starve (Starvation), so fairness also needs thought.
4. **Dining Philosophers**: 5 people sit at a round table with one chopstick between each pair, 5 in total. To eat, a person needs both chopsticks on either side.
5. If everyone picks up their left chopstick at the same time, everyone waits forever for the right one. This is the classic example of a **Deadlock**. Numbering the chopsticks and having everyone pick up the lower number first solves it.
USE: Message queues (Producer-Consumer), read/write Locks in databases and Caches (Readers-Writers), and preventing Deadlock in code that holds multiple Locks (Dining Philosophers) show up directly in real work.
END: Putting in and taking out (Producer-Consumer), reading together but writing alone (Readers-Writers), stopping while waiting on each other (Dining Philosophers). Most synchronization problems can be explained with these three frames.

### What are Race Conditions and Critical Sections?
E: Two employees look at the inventory sheet at the same time and read "10 eggs," then each uses one and writes "9." In reality 8 are left, but the sheet says 9. The part that updates the sheet is the Critical Section.
A: A Race Condition is a situation where several Threads access shared data at the same time and the result depends on the order of execution. Even `count += 1` is three steps (read, add, write), so another Thread can cut in between them. A Critical Section is the stretch of code that handles shared data, and it must let only one Thread in at a time (Mutual Exclusion).

### Explain Thread-Safe.
E: It is an inventory method designed so the sheet is never wrong even when several employees use it at once. You can put a lock on it, give each employee a personal sheet, or use only sheets that cannot be changed at all.
A: Thread-Safe is the property of code that always produces the correct result even when several Threads call it at the same time. You achieve it by protecting the Critical Section with a Mutex, using Atomic Operations, using Thread-Local Storage, or using Immutable Objects.

### Explain the difference between a Mutex and a Semaphore.
E: A Mutex is the key to a single-stall restroom. Only the person who took the key can return it. A Semaphore is the "stalls available" sign outside a restroom with 3 stalls. At 0 you wait, and whenever anyone comes out, the number goes up by 1.
A: A Mutex is a Lock that lets only one Thread into a Critical Section at a time, and it has Ownership: only the Thread that locked it can unlock it. A Semaphore is an integer Counter that decreases on wait (P) and increases on signal (V), allowing up to N users of a resource at once, and because a different Thread can signal it, it is also used to enforce ordering.

### What are a Spinlock, a Monitor, and a Condition Variable?
| Tool | Analogy | Meaning |
| Spinlock | Waiting at the restroom door and turning the handle again and again | Busy Waiting until the Lock is acquired. Good for short sections and Multi-Core |
| Condition Variable | A "call me when a spot opens" waitlist | Used with a Mutex; sleeps until the condition holds and is woken by signal |
| Monitor | A room with both the key and the waitlist attached | A high-level tool that bundles Mutual Exclusion and Condition Variables (e.g., Java synchronized) |
A: A Spinlock waits by checking repeatedly until the Lock is released, so it has no cost of sleeping and waking but wastes CPU. A Condition Variable is a tool for sleeping while waiting for a specific condition, and a Monitor bundles Mutual Exclusion and Condition Variables at the language level to reduce mistakes.

### What are the three classic Synchronization problems?
A: The Producer-Consumer problem is about keeping a fixed-size Buffer from overflowing or underflowing between the side that puts items in and the side that takes them out, and it is solved with the Semaphores empty·full and a Mutex. The Readers-Writers problem is about letting many read at once while only one writes, and the Dining Philosophers problem is the example where Deadlock occurs if everyone picks up their left chopstick at the same time.

## Deadlock

#### Deadlock and Its 4 Conditions
ONE: A state where two or more Processes **stop forever, each waiting for a resource the other holds**. It happens only when 4 conditions **all hold at the same time**.
LIKE: Four cars enter a narrow four-way intersection with no traffic light at the same time. Each waits for the car in front to clear, but that car is waiting for the one in front of it. Nobody can move.
STEP:
1. Example: Thread A holds the knife and waits for the cutting board, while Thread B holds the cutting board and waits for the knife. Both wait forever.
2. **Mutual Exclusion**: A resource can be used by only one at a time.
3. **Hold and Wait**: You wait for another resource without letting go of the one you already have.
4. **No Preemption**: You cannot forcibly take a resource someone else holds.
5. **Circular Wait**: The waiting forms a circle. A → B → A.
6. If you break **even one** of the four, Deadlock cannot happen.
| Condition | Meaning | Restaurant analogy |
| Mutual Exclusion | Only one uses it at a time | Only one person can use the knife |
| Hold and Wait | Wait while holding what you have | Wait for the cutting board while holding the knife |
| No Preemption | Cannot take it by force | Cannot grab someone else's knife |
| Circular Wait | The waiting forms a circle | A waits for B's cutting board, B waits for A's knife |
WHY: When Deadlock happens, the program just freezes without an error, which makes the cause hard to find. You have to know the conditions to prevent it.
USE: Two database Transactions waiting for each other's row (Row) Locks is a common real case. The DB detects it and cancels one of them.
END: Deadlock = Mutual Exclusion + Hold and Wait + No Preemption + Circular Wait. Breaking just one prevents it.

#### Handling Deadlock: Prevention · Avoidance · Detection · Recovery
ONE: Deadlock is handled by **breaking a condition in advance (Prevention)**, **steering clear when it is risky (Avoidance)**, or **finding and resolving it after it happens (Detection·Recovery)**.
LIKE: In terms of intersection traffic, Prevention is installing a traffic light so it never happens in the first place, Avoidance is a traffic officer calculating "will this jam things up?" every time one car is let in, and Detection·Recovery is towing a car away when traffic locks up.
STEP:
1. **Prevention**: Structurally remove one of the 4 conditions. The most practical method is to **number the resources and always request lower numbers first**. Then no circle can form, so Circular Wait disappears.
2. **Avoidance**: Before granting a resource, calculate "after granting it, is this still a Safe State where everyone can eventually finish?" and make the request wait if it is risky. The classic method is the **Banker's Algorithm**. It requires knowing in advance the maximum each Process will need, so it is rarely used in practice.
3. **Detection**: Draw who is waiting for whom as a Graph and look for a circle (Cycle).
4. **Recovery**: Once found, resolve it by terminating a Process or forcibly taking away a resource.
5. **Ignoring it (Ostrich Algorithm)**: Treat Deadlock as rare and have the OS not deal with it. Most general-purpose OSes work this way, and developers must keep a consistent Lock order instead.
KEY: The rule used most in practice: if you need multiple Locks, take them **in the same order in all code**. And set a Timeout when acquiring a Lock.
WHY: Eliminating Deadlock completely is expensive, and leaving it alone is dangerous. You have to choose the level that fits the situation.
END: Block it in advance (numbered order), steer around it (Banker's), find and resolve it (Detection·Recovery). The practical basic is "always take Locks in the same order."

### Explain the concept of Deadlock and its conditions.
E: Four cars enter a narrow four-way intersection with no traffic light at the same time, each waiting for the car in front to clear, so nobody can move.
A: Deadlock is a state where two or more Processes can never make progress because each is waiting for a resource the other holds. It occurs only when all 4 conditions hold at the same time: Mutual Exclusion, Hold and Wait, No Preemption, and Circular Wait.
| Condition | Meaning | Restaurant analogy |
| Mutual Exclusion | A resource is used by only one at a time | Only one person can use the knife |
| Hold and Wait | Wait for another resource without releasing what you hold | Wait for the cutting board while holding the knife |
| No Preemption | Cannot forcibly take what others hold | I cannot grab someone else's knife |
| Circular Wait | The waiting forms a circle | A waits for B's cutting board, B waits for A's knife |

### What is the difference between Deadlock Prevention·Avoidance·Detection·Recovery?
E: Prevention is installing a traffic light to block it at the source, Avoidance is a traffic officer calculating every time "is it safe to let this car in?", and Detection·Recovery is towing one car away when traffic locks up.
A: Prevention structurally breaks one of the 4 conditions; numbering resources and requiring requests in order removes Circular Wait. Avoidance checks whether a Safe State is maintained before granting a resource (Banker's Algorithm), and Detection·Recovery finds a Deadlock after it occurs and terminates a Process or takes away resources. In reality, most general-purpose OSes treat it as rare, ignore it (Ostrich Algorithm), and leave it to developers.

## Memory Management

#### Contiguous Allocation and Fragmentation
ONE: Giving a Process Memory **as one contiguous chunk** is simple, but over time free space gets scattered into pieces, which is the **Fragmentation** problem.
LIKE: Think of a parking lot. The empty spots add up to 3, but they are single spots scattered here and there, so a bus that needs 3 spots cannot park. That is External Fragmentation. Parking a motorcycle in a compact-car spot leaves empty space inside the spot. That is Internal Fragmentation.
STEP:
1. **Contiguous Allocation**: Give each Process one continuous range of Memory.
2. As Processes keep starting and ending, holes of various sizes appear here and there in Memory.
3. When a new Process arrives, you have to pick which hole to put it in: **First-Fit** (the first one that fits), **Best-Fit** (the tightest fit), or **Worst-Fit** (the largest one).
4. **External Fragmentation**: The free space adds up to enough, but it is in pieces, so you cannot hand out a contiguous space. It happens with variable-size allocation.
5. **Internal Fragmentation**: Because space is handed out in fixed units, you give more than was requested and the leftover inside is wasted. It happens with fixed-size allocation.
6. **Solution**: **Compaction**, which slides the scattered pieces together to one side, is expensive. That is why **Paging**, which makes contiguity unnecessary, was introduced (the next concept).
WHY: Memory is an expensive resource. Any space you cannot use because of fragments is wasted.
END: Handing it out contiguously creates pieces outside (External); handing it out in fixed units leaves unused space inside (Internal).

#### Paging and Segmentation
ONE: Splitting Memory into **pieces of the same size (Pages)** and putting them in any free slot is **Paging**; splitting it into **meaningful units (Code·Data·Stack)** is **Segmentation**.
LIKE: Paging is cutting a book into loose sheets of the same size, putting them in any empty slot on the bookshelf, and writing in a table of contents where each page is. Segmentation is dividing the book into meaningful units like "Chapter 1·Chapter 2·Appendix" and shelving those.
STEP:
1. **Paging**: Split the Process's Memory (virtual space) into fixed-size **Pages** (usually 4KB) and the real Memory into **Frames** of the same size.
2. A Page can go into any free Frame. Since it does not need to be contiguous, **there is no External Fragmentation**.
3. Which Page is in which Frame is recorded in the **Page Table**.
4. However, the last Page may not be full, so a little Internal Fragmentation occurs (about half a Page on average).
5. **Segmentation**: Split by meaningful units (Segments) such as Code, Data, Heap, and Stack. Protection settings like "Code is read-only" and "Stack cannot be executed," and sharing, come naturally.
6. Downside: Segments vary in size, so External Fragmentation comes back.
| Aspect | Paging | Segmentation |
| Unit of division | Fixed size (e.g., 4KB) | Meaningful units, varying sizes |
| External Fragmentation | None | Occurs |
| Internal Fragmentation | A little (last Page) | None |
| Advantage | Simple to manage, no gaps | Protection·sharing come naturally |
USE: Modern OSes (Linux, Windows, macOS) use Paging by default. On x86-64, Segmentation is barely used.
END: Paging is "cut to the same size and put anywhere," Segmentation is "divide by meaning." Today Paging is the standard.

#### Swapping
ONE: A technique that, when Memory is short, **temporarily moves a Process (or Page) that is not in use right now out to Disk** and brings it back when needed.
LIKE: When the kitchen is full, you move ingredients you will not use for a while down to the basement storeroom to free up space. When you need them again, you bring them back up from storage.
STEP:
1. RAM is full, and a new Process wants Memory.
2. The OS picks a Process or Page that has not been used for a while and moves it to the **Swap area** on Disk (**Swap Out**).
3. The freed space is given to the new Process.
4. When what was moved out is needed again, it is read from Disk back into RAM (**Swap In**).
PRO: You can run more Processes at once than fit in RAM.
CON: Disk is hundreds of times (SSD) to tens of thousands of times (HDD) slower than RAM. If Swapping happens often, the computer slows down noticeably.
USE: Swapping is one reason your computer stutters when you open too many browser tabs. Linux's swap partition and Windows' pagefile are this space.
END: Swapping uses Disk as temporary storage when Memory runs short. It is convenient, but doing it too often makes things very slow.

### What Memory management strategies are there?
E: These are ways of dividing storage space among restaurants. You give each one a whole contiguous area (Contiguous Allocation), give it same-size boxes that are allowed to be scattered (Paging), give it areas by purpose (Segmentation), or move unused items out to an outside storeroom for a while (Swapping).
A: Contiguous Allocation gives a Process one chunk of space and picks free space with First-Fit·Best-Fit·Worst-Fit. Non-Contiguous Allocation includes Paging, which splits into fixed sizes, Segmentation, which splits into logical units, and a combination of the two, and on top of these there are Swapping, which moves Memory out to Disk, and Virtual Memory.

### What are External Fragmentation and Internal Fragmentation?
E: External Fragmentation is when a parking lot's empty spots add up to 3 but are single spots scattered here and there, so a bus (which needs 3 spots) cannot park. Internal Fragmentation is when a motorcycle parks in a compact-car spot and empty space is left inside the spot.
A: External Fragmentation is when free Memory adds up to enough but is in pieces, so a contiguous space cannot be handed out; it occurs with variable-size allocation (Segmentation). Internal Fragmentation is waste left inside a Block because the allocation unit is larger than the request; it occurs with fixed-size allocation (the last Page in Paging). External Fragmentation is solved with Compaction or Paging.

### What is the difference between Paging and Segmentation?
E: Paging is cutting a book into pages of the same size and putting them in any empty slot; Segmentation is dividing the book into meaningful units like "Chapter 1·Chapter 2·Appendix" and shelving those.
A: Paging splits Virtual Memory into fixed-size Pages (usually 4KB) and Physical Memory into Frames of the same size, so there is no External Fragmentation but a little Internal Fragmentation. Segmentation splits into logical units like Code·Data·Stack, so protection·sharing come naturally, but because sizes vary, External Fragmentation occurs.

### Explain Swapping.
E: When the kitchen is full, you move all of a restaurant's ingredients that will not be used for a while down to the basement storeroom, and bring them back up when needed.
A: Swapping is a technique that, when Memory is short, moves a Process (or Page) out to the Swap area on Disk (Swap Out) and brings it back when needed (Swap In). It lets more Processes run at once, but Disk is very slow, so if it happens too often, performance drops sharply.

## Virtual Memory

#### Virtual Memory
ONE: A technique that makes every Process **see "a large, clean Memory space all its own"**, while the OS actually connects it to pieces of RAM and Disk.
LIKE: The general manager tells every restaurant the same thing: "Your storage is slots 1 through 1000." In reality, the manager checks a ledger and connects those slots to free slots in the real storage or to the basement storeroom. The restaurants have no way at all to see anyone else's storage.
STEP:
1. The addresses a Process uses are **Virtual Addresses**. Every Process has its own address space starting from 0.
2. The address in real RAM is a **Physical Address**.
3. The **MMU (Memory Management Unit)** inside the CPU looks at the Page Table and converts virtual addresses to physical addresses. The hardware does this conversion automatically on every Memory access.
4. Address 0x1000 in Process A and address 0x1000 in Process B are different real locations. So they cannot see each other (**isolation**).
5. Only the Pages needed right now can be kept in RAM, with the rest left on Disk. That is how programs larger than RAM can still run.
6. Conversely, when several Processes use the same Shared Library, the same real Pages are connected to all of them to save Memory.
WHY: To separate each Process's space (safety), get past the limit of RAM size (convenience), and make sharing easy (efficiency).
USE: Every modern OS uses Virtual Memory. Every Pointer address a program prints out is a virtual address.
END: Virtual Memory is the illusion that "everyone has their own Memory," and it solves safety, size, and sharing all at once.

#### Page Tables and the TLB
ONE: A **Page Table** is a ledger that records "virtual Page number → real Frame number," and the **TLB** is a very fast note holding just the few most recently looked-up lines from it.
LIKE: The Page Table is a "virtual slot number → real slot number" ledger. If the ledger gets too thick, it is split up like "building → floor → room," and ledgers for buildings nobody uses are never made at all (Multi-Level). The TLB is a sticky note on your desk with just the few lines you look up most often.
STEP:
1. A virtual address is split into **a Page number + the position within the Page (Offset)**.
2. Look up the Page number in the Page Table to get the Frame number, then attach the Offset unchanged, and you have the real address.
3. **Problem ① size**: A single table covering the entire 64 Bit address space would be too big. So the table is split into several levels, and only the parts actually in use are created (**Multi-Level Page Table**). x86-64 usually uses 4 levels.
4. **Problem ② speed**: With a 4-level table, reading Memory once requires reading the table 4 more times. That is far too slow.
5. **TLB (Translation Lookaside Buffer)**: A small Hardware Cache inside the CPU that stores recent translation results. If the result is in the TLB (TLB Hit), the translation happens right away without reading the table.
6. Thanks to Locality, programs use the same Pages repeatedly, so most translations are resolved in the TLB.
KEY: When the Process changes, the Page Table changes too, and the TLB's contents become useless. This is one reason Context Switching is expensive.
END: The Page Table is the address-translation ledger, Multi-Level is the way of splitting the ledger to save space, and the TLB is the fast note that remembers translation results.

#### Demand Paging and Page Faults
ONE: Not loading every Page in advance and **loading a Page into RAM only at the moment it is actually used** is Demand Paging, and the event that occurs when the Page you want is not in RAM is a **Page Fault**.
LIKE: You do not take every ingredient out into the kitchen in advance; you fetch something from the basement storeroom only when the cook looks for it and it is not there. That "Huh, it's not here!" is the Page Fault.
STEP:
1. Even when a program starts running, almost no Pages are loaded at first.
2. If the CPU accesses an address and the Page Table marks it "not in RAM," a **Page Fault** occurs and control passes to the OS.
3. The OS checks whether that access is valid. If the address is not allowed at all, it terminates the program (Segmentation Fault).
4. If it is valid, the OS finds a free Frame. If there is none, it picks a Page to evict (the **Victim Page**) and frees its Frame.
5. It reads the needed Page from Disk into that Frame.
6. It updates the Page Table and **runs the instruction that caused the Page Fault again**. This time it succeeds.
PRO: Parts that are never used are never loaded, which saves Memory and lets programs start quickly.
CON: Each Page Fault is a Disk read, so it is very slow. If they happen too often, performance drops sharply.
END: Demand Paging is "fetch only when needed," and at the moment you look for something that is not there (Page Fault), the OS fetches it from Disk and reruns the instruction for you.

#### Page Replacement Algorithms
ONE: The **rule for deciding which Page to evict** when RAM has no free slot. The goal is to cause as few Page Faults as possible from then on.
LIKE: The fridge is full, but you need to put in a new ingredient. It is the rule for deciding whether to take out what went in first, what has gone unused the longest, or what gets used the least.
STEP:
1. **FIFO (First-In First-Out)**: Evict the Page that came in first. Simple, but even a frequently used Page can be kicked out just for being old.
2. **OPT (Optimal)**: Evict the Page that will not be used for the longest time in the future. It is the best in theory, but it requires knowing the future, so it cannot be used in practice. It serves as a baseline for comparing how good other methods are.
3. **LRU (Least Recently Used)**: Evict the Page that has gone unused the longest. It uses Locality ("what has not been used recently will not be used soon either") and performs well in practice. Implementing it exactly requires recording every access, which is expensive.
4. **LFU (Least Frequently Used)**: Evict the Page used the fewest times. The problem is that a Page that was used a lot long ago but not now keeps staying.
5. **Clock (Second Chance)**: Give each Page a "recently used" mark (Reference Bit) and sweep around like a clock hand: if the mark is set, clear it and give the Page one more chance; if it is not, evict the Page. It is a cheap imitation of LRU.
6. **Belady's Anomaly**: With FIFO, there are strange cases where adding Frames actually increases Page Faults. It does not happen with LRU or OPT.
USE: Not just OSes but also web Caches, database Buffers, and Redis's memory policies use LRU-family rules.
END: The ideal is OPT, the practical choice is LRU, and its cheap version is Clock. FIFO is simple but can suffer Belady's Anomaly.

#### Thrashing
ONE: A state where Memory is so short that **Page Faults happen nonstop and the CPU does no real work, only waiting on Disk**.
LIKE: Too many restaurants were packed into a small kitchen. Instead of cooking, the cook spends the whole day running up and down to the basement storeroom swapping ingredients.
STEP:
1. Running many Processes at once reduces the number of Frames each Process can get.
2. Even the Pages each Process uses frequently (its **Working Set**) do not all fit in RAM.
3. Then as soon as one Page is loaded, another has to be evicted, and the evicted Page is soon needed again. Page Faults explode.
4. The CPU sits idle waiting for Disk. But if the OS thinks "The CPU is idle? Let's add more Processes," things get even worse.
5. **Solution**: Reduce the number of Processes running at once, guarantee each Process as many Frames as its Working Set (**Working Set Model**), or adjust Frames by watching how often Page Faults occur (**Page Fault Frequency**). The fundamental fix is adding more RAM.
WHY: If your computer suddenly gets extremely slow and only the Disk activity light keeps blinking, suspect Thrashing.
END: Thrashing is the state of "more trips to the storeroom than actual work," and it is resolved by running less at once or adding Memory.

#### Copy-on-Write
ONE: A technique where, when fork() duplicates a Process, Memory is not copied right away; instead **only a Page someone tries to modify gets copied, at that moment**.
LIKE: When opening a second location, you do not photocopy the whole recipe binder; at first both locations look at the same one. Only when someone tries to change even one line of a recipe is that page copied so each location has its own.
STEP:
1. Right after fork(), the Parent and Child point to the same real Pages. At this point the Pages are marked **read-only**.
2. As long as both only read, there is no need to copy.
3. When either side tries to write to a Page, a Page Fault occurs because it is read-only.
4. The OS copies only that Page, gives the copy to the side that wants to write, and now allows the write.
5. Very often a Process calls exec() right after fork() to become a different Program. In that case there is almost nothing to copy, so a huge amount of waste is avoided.
WHY: Copying all of Memory is slow, and most of those copies were about to be thrown away anyway.
USE: Linux's fork(), the way Redis takes a Snapshot with fork when saving, and Snapshots in file systems (Btrfs, ZFS) use the same idea.
END: Copy-on-Write means "copy only when modifying." Thanks to it, fork is very fast.

### Explain Virtual Memory.
E: You tell every restaurant the same thing, "Your storage is slots 1 through 1000," while in reality the general manager checks a ledger (the Page Table) and connects those slots to free slots in the real storage or to the basement storeroom. A restaurant has no way to see anyone else's storage.
A: Virtual Memory is a technique that gives each Process its own large Address Space and maps it to real Physical Memory or Disk through the Page Table. Only the needed Pages are loaded into Memory, so programs larger than RAM can run, Processes are isolated from one another, and the same Physical Page can be shared, as with a Shared Library.

### What are a Page Table, a Multi-Level Page Table, and the TLB?
E: The Page Table is a "virtual slot number → real slot number" ledger, Multi-Level is splitting the ledger like "building → floor → room" so ledgers for unused buildings are never made, and the TLB is a sticky note with just the few lines you look up most often.
A: A Page Table is a table that converts a Virtual Page Number into a Physical Frame Number. A large Address Space makes the table huge, so it is split into several levels and only the parts in use are created; x86-64 usually uses 4 levels. The TLB (Translation Lookaside Buffer) is a Hardware Cache that stores recent translation results, eliminating the cost of reading the table several times on every access.

### What are Demand Paging and the Page Fault handling process?
E: You do not bring up every ingredient in advance; you fetch something from the basement storeroom only when the cook looks for it and it is not there. "It's not here!" is the Page Fault.
A: Demand Paging is a method that loads a Page into Memory only when it is actually accessed. Accessing a missing Page causes a Page Fault: the OS checks that the access is valid, finds a free Frame or evicts a Victim Page, reads the Page from Disk, updates the Page Table, and then reruns the instruction.

### What are Page Replacement Algorithms and Belady's Anomaly?
E: They are rules for deciding what to take out of a full fridge and send to the storeroom.
| Algorithm | Rule | Characteristics |
| FIFO | The one that came in first | Simple, Belady's Anomaly possible |
| OPT | The one that will go unused the longest in the future | Optimal, but needs to know the future, so used as a baseline |
| LRU | The one unused the longest (Least Recently Used) | Performs well in practice, expensive to implement exactly |
| LFU | The one used the least (Least Frequently Used) | Things used heavily long ago keep staying |
| Clock | Gives one more chance using a Reference Bit | A cheap approximation of LRU |
A: A Page Replacement Algorithm chooses a Page to evict when there is no free Frame, with the goal of reducing Page Faults. Belady's Anomaly is the phenomenon in FIFO where increasing the number of Frames actually increases Page Faults, and it does not occur with LRU or OPT.

### What is Thrashing?
E: Too many restaurants are packed into the kitchen, so the cook cannot cook and spends the whole day running up and down to the basement storeroom.
A: Thrashing is a state where there are not enough Frames to hold the Pages Processes need, so Page Faults happen nonstop and the CPU gets almost no real work done because it is waiting on Disk. It is solved by watching the Working Set Model or Page Fault Frequency and reducing the number of Processes running at once.

### How does Copy-on-Write make fork fast?
E: When opening a second location, you do not copy the recipe binder right away; both look at the same one, and only when someone changes even one line is that page copied.
A: Right after fork, the Parent and Child share the same Physical Pages as Read-Only, and a Page is copied only when one side tries to write to it. fork is very often followed immediately by exec, so avoiding a pointless full copy makes fork very fast.

### (Note) Cache Locality
A: This was an OS item in the original question list, but since it is a Hardware concept, it is covered under "Cache Locality" in 02 Computer Architecture. The same principle applies to Virtual Memory: programs with good Locality have a high TLB Hit Rate and few Page Faults.

## Synchronous·Asynchronous and I/O

#### Synchronous vs Asynchronous
ONE: **Synchronous** means waiting until the requested work is done before doing the next thing; **Asynchronous** means making the request, doing other work, and getting notified when it finishes.
LIKE: If you order coffee at a cafe and stand at the counter until it comes out, that is Synchronous. If you get a buzzer, go to your seat and do something else, and pick up your coffee when the buzzer goes off, that is Asynchronous.
STEP:
1. Programs often do **work that involves long waits**, like reading files or making network requests. From the CPU's point of view, this waiting is very long.
2. **Synchronous**: Wait right there until the result comes back. The code runs in order from top to bottom, so it is easy to understand.
3. **Asynchronous**: Send the request and move right on to the next line of code. When the result arrives, you are notified through a **Callback**, an **Event**, or a **Promise/Future**.
4. So with Asynchronous code, even a small number of Threads can handle a huge number of requests at the same time.
5. In exchange, the flow of the code can look jumbled, so these days the `async`/`await` syntax is used to make it read like synchronous code.
```python
import asyncio
async def main():
    a = asyncio.create_task(fetch("A"))   # just send the request
    b = asyncio.create_task(fetch("B"))   # and send the next one right away
    print(await a, await b)               # use the results once both finish
```
WHY: Having the CPU sit idle while waiting on the network is a big waste. Doing other work during the wait lets the same server handle far more users.
USE: Node.js servers, JavaScript's `fetch`, Python's `asyncio`, and apps loading data without freezing the screen are all Asynchronous.
END: Synchronous is "stand and wait"; Asynchronous is "take a buzzer and do something else."

#### Blocking vs Non-Blocking
ONE: **Blocking** means the called function does not return until its work is done; **Non-Blocking** means it **returns right away** even if things are not ready. This is a different viewpoint from Synchronous vs Asynchronous.
LIKE: Blocking/Non-Blocking is about "am I free to move right after ordering?", while Synchronous/Asynchronous is about "do I keep checking whether it is done myself, or do I get notified?"
STEP:
1. **Blocking**: When you call `read()`, you are stuck inside that function until data arrives.
2. **Non-Blocking**: When you call `read()` and there is no data, it returns immediately saying "nothing yet." You can do other work.
3. **Synchronous**: **The caller itself** checks whether the work is complete.
4. **Asynchronous**: **The callee notifies** the caller when the work is complete.
5. Combining the two criteria gives 4 cases.
| Combination | Cafe analogy | Example |
| Sync + Blocking | Stand at the counter and wait | A regular read() |
| Sync + Non-Blocking | Stay at your seat and keep asking "Is it ready?" | Non-Blocking Socket + Polling |
| Async + Non-Blocking | Take a buzzer and do something else | Node.js Callbacks, async/await |
| Async + Blocking | Take a buzzer but still wait at the counter | Inefficient, so usually avoided |
WHY: In interviews, people often mix these up as "Synchronous = Blocking." If you can explain the two axes separately, you have understood the concepts precisely.
END: Blocking/Non-Blocking is "does the function return right away?"; Sync/Async is "who tells you it is done?"

### What is the difference between Synchronous and Asynchronous?
E: Synchronous is standing at the cafe counter until your coffee comes out; Asynchronous is getting a buzzer, going to your seat to do something else, and picking up your coffee when the buzzer goes off.
A: Synchronous is a style where you wait until you receive the result of the requested work before doing the next thing, and Asynchronous is a style where you make the request, do other work, and receive the result through a Callback·Event when it completes. Doing long-waiting work like Network·Disk access Asynchronously lets a small number of Threads handle many requests.

### How is Blocking vs Non-Blocking different from Synchronous vs Asynchronous?
E: Blocking/Non-Blocking is about "am I free to move right after ordering?", and Synchronous/Asynchronous is about "do I check for completion myself, or do I get notified?"
A: Blocking means the called function does not return until its work is done, and Non-Blocking means it returns immediately even if things are not ready. Synchronous·Asynchronous is the difference between the caller checking for completion itself and the callee notifying it.
| Combination | Cafe analogy | Example |
| Sync + Blocking | Stand at the counter and wait | A regular read() |
| Sync + Non-Blocking | Stay at your seat and keep asking "Is it ready?" | Non-Blocking Socket + Polling |
| Async + Non-Blocking | Take a buzzer and do something else | Node.js Callbacks, async/await |
| Async + Blocking | Take a buzzer but still wait at the counter | Inefficient, so usually avoided |

## File System

#### Files and inodes, Hard Links and Symbolic Links
ONE: In Unix-like File Systems, a file's real information (size, permissions, data location) lives in an **inode**, and a file **name** is just a signpost pointing to that inode.
LIKE: An inode is a library's catalog card for a book (author, size, where the book is shelved). A Hard Link is attaching one more name tag to the same catalog card, and a Symbolic Link is a note that says "This book is on the 3rd floor, shelf A."
STEP:
1. **inode**: A structure holding a file's Metadata (size, owner, permissions, modification time, where the data is on Disk). It does not contain the file name.
2. **Directory (folder)**: A list of "name → inode number." The file names we see live here.
3. **Hard Link**: Creating one more name that points to the same inode. The two names are completely equal.
4. Even if you delete the original name, the content stays as long as another Hard Link remains. An inode is deleted only when no name points to it anymore.
5. **Symbolic Link (Soft Link)**: A separate small file whose content is "the path to the original." It is similar to a Windows shortcut.
6. If the original is deleted or moved, the Symbolic Link loses its destination and breaks.
| Aspect | Hard Link | Symbolic Link |
| What it points to | The same inode | The original's path (name) |
| When the original name is deleted | Content stays | Breaks |
| Linking across File Systems·to Directories | Not possible (usually not for Directories) | Possible |
USE: `ln file link` (Hard Link), `ln -s file link` (Symbolic Link). Symbolic Links are often used for linking config files and switching versions (`python` → `python3.12`).
END: A file's true identity is its inode, and names are signposts. A Hard Link adds a signpost; a Symbolic Link is a "go over there" note.

#### File Descriptor
ONE: A **small integer number** that points to a file·Socket·Pipe a Process has opened. The program reads and writes using this number.
LIKE: It is the checkout ticket you get when you borrow a book from the library. Just show the ticket, and the librarian (Kernel) knows which book it is and how far you have read.
STEP:
1. When a program calls `open("a.txt")`, the Kernel opens the file and stores its information in its own table.
2. Then it returns the number of that table entry (e.g., 3). This is the **File Descriptor (FD)**.
3. After that, you make requests by number, like `read(3, ...)` and `write(3, ...)`. The Kernel remembers how far you have read (the Offset).
4. Every Process already has 3 when it starts: **0 = stdin (standard input)**, **1 = stdout (standard output)**, **2 = stderr (standard error)**.
5. In Unix, "everything is a file," so not just files but also Network Sockets, Pipes, and devices are handled through FDs with the same `read`/`write`.
6. When you are done, you must return it with `close()`. If you keep opening without closing, you run out of FDs and get a "Too many open files" error.
USE: In the Shell, `2> error.log` means "send number 2 (stderr) to a file," and `2>&1` means "send number 2 to the same place as number 1."
END: A File Descriptor is a checkout ticket from the Kernel. 0·1·2 are input·output·error, and always close it when you are done.

### What is an inode? What is the difference between a Hard Link and a Symbolic Link?
E: An inode is a library's catalog card for a book (author, size, where the book is shelved). A Hard Link is attaching one more name tag to the same card, and a Symbolic Link is a note that says "This book is on the 3rd floor, shelf A."
A: An inode holds a file's Metadata (size, owner, permissions, timestamps, Data Block locations), and file names are managed by the Directory as name → inode number. A Hard Link is another name pointing to the same inode, so the content survives even if the original name is deleted, while a Symbolic Link is a separate file holding a path, so it breaks if the original disappears.

### What is a File Descriptor?
E: It is the checkout ticket you get when you borrow a book from the library. Just show the ticket, and the librarian knows which book it is and how far you have read.
A: A File Descriptor is a small integer that points to a File·Socket·Pipe a Process has opened, and it is an Index into the table of open Files the Kernel manages. 0 is Standard Input (stdin), 1 is Standard Output (stdout), and 2 is Standard Error (stderr), and in Unix "everything is a file," so they are all handled with the same read/write.
