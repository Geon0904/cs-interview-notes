## Complexity Analysis

#### What Is an Algorithm? Two Conditions for a Good One
ONE: An **Algorithm** is a **fixed procedure** that turns input into the desired output. A good Algorithm must **always give the right answer (correctness)** and **stay fast as the data grows (efficiency)**.
LIKE: An Algorithm is a cooking recipe. The same lasagna can take 10 minutes or 10 hours depending on the recipe. And no matter how fast it is, if it tastes wrong (correctness), it is useless.
STEP:
1. **Input and output**: For example, a sorting Algorithm takes "a list of numbers" and produces "a sorted list."
2. **Finiteness**: It must always end eventually.
3. **Correctness**: It must give the right answer for every possible input. Trying a few cases and getting them right is not a proof.
4. **Efficiency**: It is judged by **how quickly** time and Memory grow as the input size n gets larger.
5. When several Algorithms solve the same problem, the difference is invisible on small data, but on large data it can be thousands or tens of thousands of times.
WHY: No matter how fast the computer, it cannot save a bad Algorithm. Sorting a million items in O(n²) takes a trillion steps; in O(n log n), about 20 million.
USE: Algorithms are inside all Software, from search engines, map directions, recommendations, and compression to cryptography. The Coding Test in a technical interview is an exam that checks this skill.
END: Algorithm = a problem-solving recipe. It has to be right (correctness) and stay fast as the data grows (efficiency).

#### Time Complexity and a Feel for Growth Rates
ONE: **Time Complexity** describes **what shape the growth in the number of operations takes** as the input size n gets larger, and **Space Complexity** describes how the extra Memory grows.
LIKE: When customers grow from 10 to 10,000, you check whether cooking time grows "by the number of customers" or "by the square of the number of customers." You look at **the shape of the growth**, not the number of seconds.
STEP:
1. Actual time differs from computer to computer, so instead you count **how many basic operations it does** as an expression in n.
2. When n gets very large, the fastest-growing term dominates everything. So **you drop constants and smaller terms**. 3n² + 100n + 5 → O(n²).
3. Looking only at "the shape as it grows" like this is called **Asymptotic analysis**.
4. Memorize the common shapes in order from slowest growth to fastest.
| Complexity | Typical example | Feel when n = 1 million |
| O(1) | Array Index access, Hash lookup | Instant |
| O(log n) | Binary Search, Balanced Tree | About 20 steps |
| O(n) | One pass over an array | 1 million steps |
| O(n log n) | Good sorting | About 20 million steps |
| O(n²) | Nested loops | A trillion steps (practically impossible) |
| O(2ⁿ), O(n!) | Trying all subsets·permutations | Impossible once n passes 20–30 |
5. **Work backward from the input size to a target**: A computer does roughly tens of millions to hundreds of millions of simple operations per second (it varies by language). So if n is 100,000, O(n²) is risky, and you aim for O(n log n) or better.
KEY: Space Complexity also includes **the Stack built up by recursive calls**. Recursing to depth n uses O(n) Memory.
END: Complexity is "the shape of the growth as n gets bigger." Drop the constants and look only at the biggest term.

#### Big-O · Big-Ω · Big-Θ
ONE: **Big-O** means "it's no slower than this" (upper bound), **Big-Ω** means "it can't be faster than this" (lower bound), and **Big-Θ** means "it's exactly about this" (the precise growth rate).
LIKE: In terms of taxi fare, Big-O is "even in the worst traffic, it won't go over $40," Big-Ω is "even with no traffic, it'll be at least $20," and Big-Θ is "it'll be right about that much."
STEP:
1. **Big-O (Upper Bound)**: f(n) = O(g(n)) means "for large enough n, f(n) is less than or equal to a constant multiple of g(n)." Precisely, there exist a constant c > 0 and n₀ such that f(n) ≤ c·g(n) whenever n ≥ n₀.
2. **Big-Ω (Lower Bound)**: The reverse, f(n) ≥ c·g(n). "It takes at least this much."
3. **Big-Θ (Tight Bound)**: Satisfies both O and Ω. The upper and lower bounds have the same growth rate.
4. Example: 3n² + n is O(n²), and saying O(n³) is not wrong either (it is only an upper bound). But Θ(n²) is the most precise expression.
5. In practice and in interviews, when people say "this is O(n log n)," they usually mean Θ.
KEY: Big-O/Ω/Θ and **Best · Average · Worst Case** are different things. The Case is "which input" (e.g., an already sorted input), and Big-O is "how you express the growth rate in that case." You use them together, as in "Quick Sort is Θ(n²) in the Worst Case."
END: O is the ceiling, Ω is the floor, and Θ is the exact fit. The Case (kind of input) is a separate axis.

#### Tips for Calculating Complexity: Loops and Recursion
ONE: Loops are calculated as **"cost of one pass × number of passes,"** and recursion as **"how many calls it branches into and how the size shrinks."**
LIKE: For loops, you count pages read as "pages per day × number of days"; for recursion, you count the total work as "how many people you split the job among and how small a job each one gets."
STEP:
1. **Single loop**: Runs n times doing O(1) work inside, so O(n).
2. **Nested loops multiply**: Outer n times × inner n times = O(n²).
3. **Back-to-back loops add**: n iterations followed by another n iterations is O(n + n) = O(n).
4. **Loops that halve**: `while n > 1: n //= 2` is O(log n).
5. **Different inputs, different variables**: Scanning array A (length a) and B (length b) separately is O(a + b); do not lump it together as O(n). If one is nested in the other, it is O(a × b).
6. **Recursion**: Set up a recurrence from how many sub-calls one call makes and how big each is. Example: two calls on halves plus n to combine → T(n) = 2T(n/2) + n.
7. **Memory for recursion**: Uses Stack proportional to the depth of calls piled up at once.
```python
for i in range(n):          # n times
    for j in range(i, n):   # n/2 times on average → about n²/2 total → O(n²)
        ...
```
END: Multiply for nesting, add for back-to-back, log for halving, and count recursion with a recurrence.

#### Master Theorem
ONE: A formula that immediately solves the recurrence **T(n) = aT(n/b) + f(n)**, for a problem split into a subproblems of size n/b with f(n) work to combine them.
LIKE: You split a big job among a people, and collecting their results takes f(n) work. Whichever is bigger, "the total of the split-up work" or "the collecting work," decides the overall time.
STEP:
1. Compute the comparison value: **n^(log_b a)**. It shows how fast "the total amount of work split up by recursion" grows.
2. **If f(n) is clearly smaller**: The recursion dominates → Θ(n^(log_b a)).
3. **If they are the same order**: The same amount of work piles up on each of log n levels → Θ(n^(log_b a) · log n).
4. **If f(n) is clearly bigger**: The combining work dominates → Θ(f(n)) (when an extra condition called the regularity condition holds).
| Recurrence | a, b, f(n) | Result | Example |
| T(n) = 2T(n/2) + n | 2, 2, n | Θ(n log n) | Merge Sort |
| T(n) = T(n/2) + 1 | 1, 2, 1 | Θ(log n) | Binary Search |
| T(n) = 3T(n/2) + n | 3, 2, n | Θ(n^1.585) | Karatsuba multiplication |
| T(n) = 2T(n/2) + n² | 2, 2, n² | Θ(n²) | Combining cost dominates |
5. Example: Merge Sort has a = 2 and b = 2, so n^(log₂2) = n, which equals f(n) = n. So it is Θ(n log n).
WHY: You can get the running time of a Divide and Conquer Algorithm right away, without drawing a recursion tree every time.
END: Compare n^(log_b a) with f(n): if f is smaller, the recursion wins; if equal, add one more log; if bigger, f(n) wins.

#### Amortized Analysis
ONE: A method that computes **the average obtained by dividing the total cost of a sequence of operations by the number of operations**, even when some operations are occasionally expensive. It is an average guaranteed even for the worst order of operations.
LIKE: A gym's annual membership fee is a big payment all at once, but spread over a year, the daily cost is small.
STEP:
1. You keep inserting elements into a Dynamic Array. Most of the time you just drop it into an empty slot, so O(1).
2. Occasionally, when it is full, moving to a twice-as-big array costs O(n).
3. But the total moved over n insertions is 1 + 2 + 4 + … < 2n.
4. So the total cost of n insertions is O(n), and the average per insertion is O(1). This is **Amortized O(1)**.
5. **Difference from a probabilistic average**: A Hash Table's "average O(1)" relies on luck (the Key distribution). Amortized is an average where the total is guaranteed regardless of luck, in any order of operations.
USE: Used to explain the cost of Dynamic Array append, a Queue built from two Stacks, and Union-Find operations.
END: Amortized is "the average after spreading occasional big costs over everything," a promise that holds even for the worst order.

#### Proving an Algorithm Correct: Loop Invariants
ONE: A way to prove an Algorithm is correct by choosing **a property that is always true at the start of every loop iteration (Loop Invariant)** and showing it holds from beginning to end.
LIKE: Say that while sorting cards, you keep the rule "the cards in my left hand are always sorted." If it is true at the start (one card), still true each time you slip in another card, and true when you have received all the cards, then the whole hand is sorted.
STEP:
1. **Choose the invariant**: For Insertion Sort, "at the start of iteration i, the first i items are sorted."
2. **Initialization**: It is true before the loop starts. The first 1 item is obviously sorted.
3. **Maintenance**: It is still true after one iteration. Slipping the new element into its place makes the first i + 1 items sorted.
4. **Termination**: When the loop ends, the invariant is exactly the desired result. At the end i = n, so everything is sorted.
5. This is mathematical induction (topic 01) applied to a loop.
WHY: "It passed a few tests" does not guarantee it is right for every input. An invariant proves all cases at once.
USE: When asked in an interview "why is this code correct?", explaining with an invariant lets you answer logically. Invariants like "lo is always less than or equal to the answer" also help a lot in catching boundary-condition Bugs in Binary Search.
END: Loop Invariant = true at the start + maintained every time + the desired result at the end. It is the loop version of induction.

### What are Time Complexity and Space Complexity?
E: It is checking how cooking time (Time Complexity) and the counter space you need (Space Complexity) grow when customers go from 10 to 10,000. You look at "the shape of the growth," not the number of seconds.
A: Time Complexity describes how the number of basic operations grows with the input size n, and Space Complexity describes how the extra Memory needed grows. To compare Algorithms independently of Hardware, you drop constants and lower-order terms and look only at the fastest-growing term.
M: From fastest to slowest: O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) < O(n!). When n = 1 million, n log n is about 20 million and n² is a trillion.

A: f(n) = O(g(n)) means there exist a constant c > 0 and n₀ such that f(n) ≤ c·g(n) for all n ≥ n₀; it is an Asymptotic Upper Bound. Ω is the Lower Bound where f(n) ≥ c·g(n), and Θ is the exact growth rate satisfying both O and Ω. In practice, "O(n log n)" usually means Θ, and Best·Average·Worst Case is a separate distinction of "which input."

| Recurrence | a, b, f(n) | Result | Example |

#### Sorting and Stable Sorts
ONE: **Sorting** is lining up elements in a defined order, and if elements with equal values **keep their original order**, it is a **Stable Sort**.
LIKE: When students already lined up by name are re-lined by height, if two students of the same height stay in name order, it is a Stable Sort.
STEP:
1. Sorted data lets you find things quickly with Binary Search, spot duplicates easily, and assign rankings. That is why sorting is the first step of many Algorithms.
2. **Comparison Sort**: Decides order by comparing two elements (a < b?). Bubble, Insertion, Merge, Quick, Heap.
3. **Non-Comparison Sort**: Uses the value itself like an Index. Counting, Radix.
4. **In-Place**: Sorts inside the original array, using almost no extra Memory.
5. **Stable**: Keeps the original order of equal values. Merge, Insertion, Bubble, Counting, and Timsort are Stable. Quick, Heap, and Selection usually are not.
| Sorting | Average | Worst | Extra Memory | Stable |
| Bubble · Insertion | O(n²) | O(n²) | O(1) | Yes |
| Selection | O(n²) | O(n²) | O(1) | No |
| Merge | O(n log n) | O(n log n) | O(n) | Yes |
| Quick | O(n log n) | O(n²) | O(log n) | No |
| Heap | O(n log n) | O(n log n) | O(1) | No |
| Counting · Radix | O(n + k) family | O(n + k) family | O(n + k) | Yes |
KEY: When Stability matters: if you "sort by date, then sort by department," date order is kept within each department. That is only possible because it is a Stable Sort.
END: Sorting is the starting point of many problems, and keeping the original order of equal values makes it Stable.

#### Simple Sorts: Bubble · Selection · Insertion
ONE: All three are easy to understand and use O(1) extra Memory, but their average·worst case is **O(n²)**. Among them, **Insertion Sort** is very fast on nearly sorted data.
LIKE: Bubble is comparing heights with the person next to you and moving the taller one back a spot; Selection is finding the shortest of the remaining people each time and putting them at the front; Insertion is taking cards one at a time and slipping each into its place among the sorted cards in your hand.
STEP:
1. **Bubble Sort**: Compare neighboring elements and swap them if they are out of order. Each pass, the largest value rises to the end "like a bubble." If a pass makes no swaps, it is already sorted and can stop early (Best O(n)).
2. **Selection Sort**: Find the minimum of the remaining elements and swap it with the front. It always does O(n²) comparisons regardless of input. But it makes at most n swaps, which matters when swaps are expensive.
3. **Insertion Sort**: Keeps the front part sorted and slips the next element into its place within it.
4. If the data is nearly sorted, each element only has to move a little, so it is close to O(n).
5. With few elements, its simplicity actually makes it fast. That is why real-world sorts like Timsort handle small runs with Insertion Sort.
END: All three are O(n²), but for small, nearly sorted data, Insertion Sort is genuinely strong.

#### Merge Sort
ONE: A Divide and Conquer sort that **splits the array in half, sorts each half, then merges the two sorted halves**. It is always **O(n log n)** and Stable.
LIKE: Split a pile of test papers in half and have two friends each sort theirs, then merge the two sorted piles by comparing only the top papers and putting down the smaller one each time.
STEP:
1. **Divide**: Split the array in half. Keep splitting until each piece has one element (one element is already sorted).
2. **Merge**: Merge two sorted arrays. Compare the fronts of the two arrays, put the smaller into the result, and move to that array's next element. When one side runs out, attach the rest as is.
3. Merging costs as many steps as there are elements, so O(n) per level.
4. Splitting in half gives log n levels. So overall O(n log n). Recurrence: T(n) = 2T(n/2) + n.
5. It splits and merges the same way regardless of input, so Best·Average·Worst are all O(n log n).
PRO: O(n log n) is always guaranteed, and it is Stable. It only reads things in order, so it is good for sorting Linked Lists and for sorting huge files that do not fit in Memory (External Sort).
CON: It needs O(n) extra Memory to hold the result while merging.
END: Merge Sort is "split in half, then merge by comparing the fronts." Always n log n, but it needs extra space.

#### Quick Sort
ONE: Pick one reference value (**Pivot**), split the elements into **smaller on the left and larger on the right** (Partition), and sort both sides the same way again. It is O(n log n) on average and among the fastest in practice, but O(n²) in the worst case.
LIKE: Pick one student as the reference and have everyone split up: "shorter than me on the left, taller on the right." Then in the left group and the right group, pick another reference and split again, and repeat.
STEP:
1. **Pick a Pivot**: Choose one reference value from the array.
2. **Partition**: Move elements smaller than the Pivot to the left and larger ones to the right. The Pivot is now in its final position.
3. Recursively sort the left part and the right part. No separate merge step is needed.
4. If the Pivot lands near the middle each time, it splits in half, giving O(n log n).
5. **Worst case**: If the Pivot is the minimum or maximum every time, one side is empty. Choosing the first element as the Pivot on an already sorted array does exactly this, giving O(n²).
6. **Fix**: Pick the Pivot at random (Random Pivot), or use the median of the first, middle, and last values (Median-of-Three). Picking at random removes any specific bad input, making the expected time O(n log n).
PRO: It sorts in place, so extra Memory is small (recursion Stack O(log n) on average), and it scans contiguous Memory for good Cache efficiency, making it very fast in practice.
CON: It has an O(n²) worst case and is not Stable.
END: Quick Sort is "split around a reference and repeat on both sides." Its average is the fastest, but a bad Pivot gives n², so pick it at random.

#### Heap Sort
ONE: A sort that turns the array into a **Max Heap** and then repeatedly sends the largest value (the Root) to the back. It is **always O(n log n)** and sorts **In-Place**.
LIKE: It is taking the most urgent patient out of the emergency room waiting list (Heap) one at a time and lining them up in order.
STEP:
1. Turn the array into a Max Heap (Build-Heap, O(n)). Now the Root is the maximum.
2. Swap the Root (the maximum) with the last element. The maximum is now in its final place (the back).
3. Shrink the Heap by one, and push the new Root down to restore the Heap (Sift-Down, O(log n)).
4. Repeating this n times fills the array from the back with the largest values in order, and the sort is done.
5. Overall O(n log n), done inside the original array without an extra array.
PRO: O(n log n) is guaranteed even in the worst case, and extra Memory is O(1).
CON: It is not Stable, and it jumps around the array, so Cache efficiency is low and it is often slower than Quick Sort in practice.
USE: Used when the worst-case time must be guaranteed. Introsort, used by C++'s std::sort, runs Quick Sort and switches to Heap Sort if the recursion gets too deep, preventing the worst case.
END: Heap Sort is "send the maximum to the back one at a time," and its strengths are a worst-case guarantee + sorting in place.

#### Counting Sort and Radix Sort
ONE: Methods that sort without comparing elements, **using the value itself like an Index**, and can be faster than O(n log n) when the conditions fit.
LIKE: Counting Sort is setting out a bin for each test score (0–100), tossing each answer sheet into its bin, and then taking them out bin by bin. Radix Sort is sorting ZIP codes into bins one digit at a time, starting from the last digit, and repeating.
STEP:
1. **Counting Sort**: Used for integers with a narrow range of values, 0–k. Count how many of each value there are (a count array), then output them in order that many times. O(n + k).
2. If k is much larger than n (e.g., a value range of a billion), the count array is too big to use.
3. **Radix Sort**: Splits numbers by digit and does a Stable Counting Sort on each digit, from the lowest to the highest. With d digits, O(d(n + k)).
4. Why starting from the lowest digit works: each step is Stable, so the order built in earlier steps is kept among elements with the same digit value.
5. Since it does not compare, it sidesteps "the Ω(n log n) limit of comparison sorting" covered below.
CON: The shape of the Keys is restricted, like integers or fixed-length strings, and extra Memory is needed.
END: For a narrow value range use Counting; for a fixed number of digits use Radix. Since they do not compare, they can be faster than n log n.

#### The Limit of Comparison Sorting: Why Ω(n log n)?
ONE: Every Algorithm that sorts **only by comparing** elements must, in the worst case, **make roughly n log n comparisons**. A faster comparison sort cannot exist.
LIKE: Think of twenty questions. If you can only ask "yes/no" questions and there are n! possible answers (every possible order of a line), you have to ask at least log₂(n!) questions to pick the right one.
STEP:
1. There are n! ways to line up n elements. Sorting is finding the one correct one among them.
2. One comparison gives one "yes/no" answer, cutting the possible cases by at most half.
3. To narrow n! cases down to 1, you need at least log₂(n!) comparisons.
4. Mathematically, log₂(n!) is about n log₂ n (Θ(n log n)).
5. So no comparison sort makes fewer than Ω(n log n) comparisons in the worst case. Merge Sort and Heap Sort are optimal comparison sorts that match this limit exactly.
KEY: Counting Sort and Radix Sort can beat this limit because they do not compare.
END: Sorting by comparison alone hits a wall at n log n. To get past that wall, you have to use the values themselves (Counting·Radix).

#### Timsort: Sorting in the Real World
ONE: A Hybrid sort that **mixes Insertion Sort and Merge Sort**, taking advantage of the fact that real data often contains runs that are already sorted. Python's `sort()`/`sorted()` is based on it.
LIKE: It is a smart way to organize a bookshelf: leave the bundles that are already in order as they are, and just merge those bundles together.
STEP:
1. Find stretches of the data already sorted in ascending (or descending) order (**Runs**). Descending runs are reversed.
2. If a Run is too short, extend it to a set length with Insertion Sort (because Insertion Sort is fast on small stretches).
3. Merge the resulting Runs according to its rules.
4. If the data is already sorted, it ends with a single Run in O(n); even in the worst case it is O(n log n), and it is Stable.
USE: Python's sorting and Java's sorting of Object arrays are based on Timsort.
END: Timsort is a sort optimized for real data: "keep the parts that are already sorted, use Insertion for small pieces and Merge for big ones."

### How do Bubble / Selection / Insertion Sort work, and what are their complexities?
E: Bubble is comparing heights with the person next to you and moving the taller one back a spot; Selection is finding the shortest of the remaining people each time and putting them at the front; Insertion is taking cards one at a time and slipping each into its place among the sorted cards in your hand.
A: All three Sorts are O(n²) in the Average·Worst case and use O(1) extra Memory. Bubble Sort compares·swaps (Swap) adjacent elements, and Selection Sort sends the minimum to the front, always doing O(n²) comparisons but at most n swaps. Insertion Sort is close to O(n) on nearly sorted data and genuinely fast on small Arrays, so it is used as a component of Hybrid Sorts like Timsort.

### How do Merge / Heap / Quick Sort work, and what are their complexities? When is Quick Sort's worst case O(n²)?
E: Merge Sort is splitting a pile of test papers in half, having friends sort them, and merging the two sorted piles by comparing only the top papers. Quick Sort repeatedly picks a reference student (Pivot) and splits everyone into "shorter than me on the left, taller on the right." Heap Sort is taking the most urgent patient out of the emergency room waiting list (Heap) one at a time.
A: Merge Sort is Divide and Conquer that splits in half, sorts, and merges; it is always O(n log n) and Stable but needs O(n) extra Memory. Heap Sort builds a Max Heap and repeatedly sends the Root to the end; it is always O(n log n) and an In-Place Sort. Quick Sort Partitions around a Pivot; it is O(n log n) on average and fast in practice thanks to good Cache efficiency, but if the Pivot is the minimum or maximum every time (e.g., choosing the first element as the Pivot on an already sorted Array), a split with nothing on one side happens n times, giving O(n²). This is mitigated with a Random Pivot or Median-of-Three.

### How can Counting / Radix Sort be faster than O(n log n)?
E: Counting Sort is setting out a bin for each test score (0–100), tossing each answer sheet into its bin, and taking them out bin by bin. Radix Sort is sorting ZIP codes into bins one digit at a time, starting from the last digit, and repeating.
A: These two Sorts do not compare elements but use the values themselves like Indexes, so the Comparison Sort lower bound Ω(n log n) does not apply to them. Counting Sort is O(n + k) for integers with a small value range k, and Radix Sort repeats a Stable Counting Sort on each digit for O(d(n + k)). In exchange, the Key shape is restricted, like integers or fixed-length Strings, and extra Memory is needed.

### What is a Stable Sort?
E: When students already lined up by name are re-lined by height, if two students of the same height stay in name order, it is a Stable Sort.
A: A Stable Sort keeps the original relative order of elements with equal values; Merge·Insertion·Bubble·Counting Sort and Timsort are Stable, while Quick·Heap·Selection Sort generally are not. It matters when you sort by several criteria in turn, as in "sort by date, then by department."

### Why is the lower bound for Comparison Sorts Ω(n log n)?
E: If, like twenty questions, you can only ask "yes/no" questions, then when there are n! possible answers (every possible order of a line), you must ask at least log₂(n!) questions to pick the right one.
A: A Comparison Sort can be represented as a Decision Tree that branches on comparison results, and distinguishing all n! Permutations of n elements requires at least n! Leaves. A Binary Tree with that many Leaves has Height at least log₂(n!), which is Θ(n log n), so no Comparison Sort makes fewer than Ω(n log n) comparisons in the worst case.

### What is Timsort, used by Python's sorted()?
A: Timsort is a Hybrid Sort that finds already-sorted stretches (Runs) in the data, extends short ones with Insertion Sort, and Merges the Runs. Real data is often partially sorted, so it is very fast; it is Best O(n), Worst O(n log n), and Stable. Python's sort/sorted and Java's sorting of Object Arrays are based on Timsort.

## Search

#### Binary Search and Lower · Upper Bound
ONE: A search on a **sorted array** that compares with the middle value and **cuts the search range in half** each time. It is **O(log n)**, so even among a million items it finds the target in about 20 steps.
LIKE: When looking up a word in a dictionary, you open to the middle, think "it's earlier," and look only at the front half, and repeat. Even a 1,000-page dictionary takes fewer than 10 tries.
STEP:
1. **Condition**: The array must be sorted.
2. Look at the middle, mid, of the range [lo, hi].
3. If it equals the target, you are done. If the target is smaller, hi = mid − 1 (left half); if larger, lo = mid + 1 (right half).
4. If the range becomes empty, it is not there.
5. It halves each time, so the number of iterations is log₂ n.
6. **Lower Bound**: The first position **greater than or equal to** x. **Upper Bound**: The first position **greater than** x. The difference between them is the count of x. In Python, `bisect_left` and `bisect_right`.
7. **Parametric Search**: When the answer has the shape of "satisfied from some point on" (False…False True…True), like "the minimum value that satisfies a condition," you can Binary Search the answer itself. Example: "What is the minimum truck capacity needed to move all the boxes within D days?"
```python
def binary_search(a, x):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == x: return mid
        if a[mid] < x: lo = mid + 1
        else: hi = mid - 1
    return -1
```
KEY: It is easy to get the boundaries wrong (`<` vs `<=`, `mid` vs `mid ± 1`). Fixing an invariant ("the answer is always within [lo, hi]") before writing reduces mistakes. In C·Java, `lo + hi` can Overflow, so `lo + (hi − lo) / 2` is used.
END: If it is sorted, search by throwing away half each time (O(log n)). If the answer has the shape "satisfied from some point on," you can Binary Search the answer itself too.

### What are the conditions and complexity of Binary Search? What are Lower Bound / Upper Bound?
E: When looking up a word in a dictionary, you open to the middle, think "it's earlier," and look only at the front half, and repeat. Even a 1,000-page dictionary takes fewer than 10 tries.
A: Binary Search finds a target in a sorted Array in O(log n) by comparing with the middle value and halving the search range. The Lower Bound is the first position greater than or equal to x, the Upper Bound is the first position greater than x, and their difference is the count of x (Python `bisect_left` / `bisect_right`). The same principle is used for Parametric Search, which finds "the minimum value that satisfies a condition."
M: In `mid = (lo + hi) // 2`, lo + hi can Overflow depending on the language, so `lo + (hi − lo) // 2` is sometimes used (Python integers have unlimited precision, so it is not a problem there).

## Divide and Conquer

#### Divide and Conquer
ONE: A design method that **splits a problem into smaller problems of the same shape (Divide)**, **solves each one (Conquer)**, and **combines the results (Combine)**.
LIKE: It is cutting a big pizza into slices, having friends each eat their own, and gathering the results. The slices have to be independent problems that do not depend on each other.
STEP:
1. **Divide**: Split the problem into smaller problems of a similar shape.
2. **Conquer**: Solve the small problems recursively. If one is small enough, solve it directly (Base Case).
3. **Combine**: Put the small answers together to build the big answer.
4. Classic examples: Merge Sort (split and merge), Quick Sort (the work is concentrated in splitting), Binary Search (keep only half).
5. **Quickselect**: To find the k-th smallest element, you do not need to sort everything. Partition like Quick Sort and keep going down only the side containing k, for O(n) on average. Using the "Median of Medians" as the Pivot guarantees O(n) even in the worst case.
6. **Karatsuba multiplication**: Splits multiplication of big numbers into 3 smaller multiplications instead of 4, reducing O(n²) to O(n^1.585).
7. The running time is found with the Master Theorem.
KEY: If the small problems **overlap** (repeating the same computation), Divide and Conquer is wasteful. In that case, use Dynamic Programming, which stores answers and reuses them.
END: Split, solve, combine. Use it when the small problems are independent; if they overlap, go to DP.

### What is Divide and Conquer?
E: It is cutting a big pizza into several slices, having friends split them, and gathering the results. The slices have to be independent problems that do not depend on each other.
A: Divide and Conquer is a design method that splits a problem into smaller problems of the same form (Divide), solves them recursively (Conquer), and combines the results (Combine). Merge Sort, Quick Sort, Binary Search, Quickselect (finding the k-th element in O(n) on average), and the Karatsuba Algorithm (multiplying big numbers in O(n^1.585) by using 3 multiplications instead of 4) are classic examples, and the Complexity is found with the Master Theorem. If Subproblems overlap, the same computation is repeated, so Dynamic Programming is better.

## Dynamic Programming

#### The Core of Dynamic Programming: Two Conditions
ONE: A technique used when **a big problem's answer can be built from smaller problems' answers** and **the same small problem appears many times**: compute each small answer once, **store it, and reuse it**.
LIKE: When climbing stairs 1 or 2 steps at a time, the number of ways to reach the 10th step is "ways to reach the 9th + ways to reach the 8th." Instead of counting from scratch each time, if you jot down the answer for each step, it is done in one pass.
STEP:
1. **Optimal Substructure**: The optimal solution to the big problem is made of optimal solutions to smaller problems.
2. **Overlapping Subproblems**: The same small problem appears many times.
3. Solving Fibonacci with plain recursion, F(5) calls F(4) and F(3), and F(4) calls F(3) again. The same computation repeats exponentially, so it is O(2ⁿ).
4. If you store each F(k) once computed and pull it out when needed again, each value is computed only once, so it becomes O(n).
5. DP is worthwhile only when both conditions hold. If the small problems do not overlap, Divide and Conquer is simpler; if picking the current best is enough, Greedy is simpler.
```python
from functools import lru_cache

@lru_cache(maxsize=None)     # store computed values (Memoization)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)
```
END: DP = "build big answers from small answers" + "compute each small answer once and store it."

#### Five Steps for Designing a DP
ONE: Design a DP problem in the order **define the state → recurrence → initial values → computation order → reduce space**. Of these, **defining the state matters most**.
LIKE: It is like filling in a spreadsheet. First decide "what goes in each cell" (state), decide "how this cell is computed from neighboring cells" (recurrence), fill the first cells (initial values), and decide which direction to fill (order).
STEP:
1. **Define the state**: Write "what does dp[i] mean" in one sentence. Example: "dp[i] = the number of ways to climb to step i." This is most of the work. Get the state right and the rest follows.
2. **Recurrence**: Express the current state in terms of smaller states. Example: dp[i] = dp[i−1] + dp[i−2].
3. **Initial values (Base Case)**: Set the values of the smallest states. Example: dp[0] = 1, dp[1] = 1.
4. **Computation order**: Top-down (recursion + storage, Memoization) or bottom-up (fill the table starting from the small ones, Tabulation).
5. **Reduce space**: If you only need the previous one or two cells, there is no need to hold the whole table. Fibonacci needs just two variables.
KEY: The trick for defining the state is to ask "what do I need to know to get the answer?" For the knapsack problem, you need "how many items you've looked at" and "the remaining weight," so it becomes dp[i][w].
END: Decide the meaning of a cell (the state) first, and the recurrence·initial values·order follow naturally.

#### Memoization (Top-Down) vs Tabulation (Bottom-Up)
ONE: Two ways to implement DP. **Memoization** recurses down from the big problem and stores answers, and **Tabulation** fills a table upward starting from the small problems.
LIKE: Memoization is "compute it when needed and jot it down," and Tabulation is "fill the whole table in order from the start."
STEP:
1. **Memoization (Top-Down)**: Call the big problem with a recursive function, and store (Cache) each value the first time it is computed. If a value is already stored, pull it out right away.
2. Pros: You just translate the recurrence directly, so it is intuitive, and only the small problems actually needed get computed.
3. Cons: There is recursive call overhead, and deep recursion can hit the recursion depth limit (about 1000 by default in Python).
4. **Tabulation (Bottom-Up)**: Fill the table with a loop starting from the smallest problems. When solving a big problem, the small answers it needs are already filled in.
5. Pros: No recursion, so it is fast and safe, and space optimization that keeps only the last few cells is easy.
6. Cons: You have to decide the computation order yourself, and you may fill in cells you do not need.
```python
def fib(n):               # Tabulation + space optimization
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a
```
END: Memoization is easier to think about; Tabulation is faster and safer. The time complexity is usually the same.

#### Classic DP Problems
ONE: Fibonacci, the knapsack problem, LIS, LCS, and Edit Distance are DP's basic templates. Once you learn these five state definitions, most DP problems look like variations of them.
LIKE: It is like how, once you learn basic cooking skills (chopping, sautéing, boiling), new dishes look like combinations of them.
STEP:
1. **Fibonacci / climbing stairs**: dp[i] = dp[i−1] + dp[i−2]. O(n).
2. **0/1 Knapsack**: Choose whether to put each item (weight, value) into a knapsack with weight limit W to maximize value. dp[i][w] = "maximum value using the first i items with weight at most w" = max(skip item i: dp[i−1][w], take it: dp[i−1][w−wᵢ] + vᵢ). O(nW).
3. **LIS (Longest Increasing Subsequence)**: dp[i] = length of the longest increasing subsequence ending at i = max(dp[j] + 1) (j < i, a[j] < a[i]). O(n²), or O(n log n) with Binary Search.
4. **LCS (Longest Common Subsequence)**: The longest sequence that appears in both strings while keeping order. If the characters match, dp[i−1][j−1] + 1; otherwise max(above, left). O(nm). It is the principle behind diff tools.
5. **Edit Distance**: The minimum number of insertions·deletions·replacements to turn one string into another. If they match, dp[i−1][j−1]; otherwise 1 + min(insert, delete, replace). Used for spelling correction and DNA comparison.
KEY: The knapsack problem's O(nW) is exponential in the input length (number of Bits), because W is "the size of a number." This is called **Pseudo-Polynomial** time.
END: Memorize the state definitions of the basic five (Fibonacci, knapsack, LIS, LCS, Edit Distance) and half of DP is done.

### What is Dynamic Programming? What are Optimal Substructure and Overlapping Subproblems?
E: When climbing stairs 1 or 2 steps at a time, the number of ways to reach the 10th step is "ways to the 9th + ways to the 8th." Instead of counting from scratch each time, if you jot down the answer for each step, it is done in one pass.
A: Dynamic Programming (DP) is a technique that computes each answer once, stores it, and reuses it when a big problem's answer can be built from smaller problems' answers (Optimal Substructure) and the same small problem appears many times (Overlapping Subproblems). Solving Fibonacci with plain Recursion is O(2ⁿ), but with storage it is O(n). The core of the design is deciding the State (what `dp[i]` is), the Recurrence, the initial values, and the computation order.

### What are Memoization (Top-Down) vs Tabulation (Bottom-Up)?
A: Memoization recurses down from the big problem and stores computed values in a Cache; it solves only the needed Subproblems and is intuitive to implement but can hit the Recursion Depth limit. Tabulation is a loop that fills a table upward from the smallest problems; it has no Recursion Overhead and makes it easy to save Memory by keeping only the previous few cells.

### What are the classic DP problems?
| Problem | State definition | Recurrence (core) | Complexity |
| Fibonacci / climbing stairs | dp[i] = the i-th value | dp[i] = dp[i−1] + dp[i−2] | O(n) |
| 0/1 Knapsack | dp[i][w] = max value from the first i items with weight at most w | max(dp[i−1][w], dp[i−1][w−wᵢ] + vᵢ) | O(nW) (Pseudo-Polynomial) |
| LIS (Longest Increasing Subsequence) | dp[i] = length of the LIS ending at i | max(dp[j] + 1), j < i and a[j] < a[i] | O(n²), O(n log n) with Binary Search |
| LCS (Longest Common Subsequence) | dp[i][j] = LCS of the first i and first j characters | If equal dp[i−1][j−1] + 1, else max(above, left) | O(nm) |
| Edit Distance | dp[i][j] = minimum operations to turn the first i characters into the first j | If equal dp[i−1][j−1], else 1 + min(insert, delete, replace) | O(nm) |
A: Fibonacci·Knapsack·LIS·LCS·Edit Distance are the classics. Knapsack's O(nW) is exponential in the number of input Bits because W is the size of a number, making it Pseudo-Polynomial Time; Edit Distance is used in spelling correction and DNA comparison, and LCS in diff tools.

## Greedy Algorithms

#### Greedy Algorithms and Proving Them Correct
ONE: A method that, at every step, **makes the choice that looks best right now** and **never looks back**. It is fast and simple, but it needs a **proof** that those choices do not ruin the overall optimum.
LIKE: To fit as many meetings as possible into one meeting room in a day, pick "the meeting that ends earliest" first. The earlier it ends, the more time is left for the next meeting.
STEP:
1. At each moment, pick the best by a fixed criterion. Choices already made are never changed.
2. **When it works**: When the current best choice can always be part of some optimal solution (**Greedy Choice Property**) and the remaining problem has the same shape (Optimal Substructure).
3. **Meeting room scheduling (Interval Scheduling)**: Sort by end time, then repeatedly pick a meeting if it does not overlap the previous one. It is O(n log n) and optimal.
4. **Exchange Argument**: A proof method. Show that "given some optimal solution, swapping its first choice for Greedy's first choice (the meeting that ends earliest) is still feasible and does not reduce the count." Repeating this shows the Greedy solution is optimal too.
5. Classic Greedy Algorithms: Dijkstra (finalize the closest place first), Kruskal·Prim (cheapest bridge first), and Huffman Coding (combine the rarest characters first).
WHY: Greedy is much faster than DP and the code is shorter. As long as it is correct, it is the best choice.
END: Greedy = "best right now, never look back." Before using it, always prove it is correct or look for a counterexample.

#### When Greedy Fails
ONE: In problems where the best choice now can block the best choice later, Greedy gives **the wrong answer**. In those cases, use DP.
LIKE: When hiking, if you always pick the steepest uphill path at every fork, you can get stuck on top of a small hill. The real summit might require going down for a bit before climbing again.
STEP:
1. **Coin problem**: With coins of 1·3·4 cents, make 6 cents with the fewest coins. Greedy (largest coin first) gives 4 + 1 + 1 = 3 coins; the optimum is 3 + 3 = 2 coins.
2. For US coins (1·5·10·25 cents), Greedy is correct. The denominations are set up so that using the biggest coin never costs you. With different denominations, it can break.
3. **0/1 knapsack problem**: Packing "highest value per weight first" can be wrong. Items cannot be split, so leftover space gets wasted. That is why it is solved with DP.
4. **Fractional Knapsack**: If items can be split, the "by value per weight" Greedy is optimal.
5. Tip: Before using Greedy, build a few small counterexamples by hand. If even one appears, use DP or another method.
END: Greedy is the best when it is right, but there are many cases where it fails, like coins of 1·3·4 cents or 0/1 knapsack. Look for counterexamples first.

### What is a Greedy Algorithm? When does it guarantee the optimum?
E: It is picking the steepest path at every fork while hiking. If the mountain is simple, you reach the summit fastest, but you might get stuck on a small hill.
A: Greedy makes the choice that looks best right now at every step and never undoes it. It guarantees the optimum only when there is the Greedy Choice Property (the current best is part of some optimal solution) and Optimal Substructure, so it is simple and fast but must be proven correct. Dijkstra, Kruskal·Prim, and Huffman Coding are classic Greedy algorithms.

### What are Interval Scheduling and the Exchange Argument?
E: To fit as many meetings as possible into one meeting room in a day, pick "the meeting that ends earliest" first. The earlier it ends, the more time is left for the next meeting.
A: The problem of choosing as many non-overlapping Intervals as possible is solved optimally in O(n log n) by sorting by end time and picking feasible ones from the front. The Exchange Argument proves the Greedy solution is optimal by showing that "swapping some optimal solution's first choice for Greedy's first choice (the interval that ends earliest) is still feasible and does not reduce the count," and repeating this.

### What are examples where Greedy fails?
A: With coins of 1·3·4 cents, making 6 cents, Greedy picks 4 + 1 + 1 (3 coins), but the optimum is 3 + 3 (2 coins). 0/1 Knapsack can also go wrong if packed "highest value per weight first," so it is solved with DP, while for the Fractional Knapsack, where items can be split, that Greedy is optimal. For coin systems like US coins (1·5·10·25 cents), which are designed so that taking the largest coin first always gives the fewest coins, Greedy is correct.

## Graph Search

#### BFS and DFS
ONE: **BFS** spreads out **layer by layer** from the closest places (Queue), and **DFS** digs **all the way down** one path before coming back (Stack·recursion). Both are O(V + E).
LIKE: BFS is like the ripples that spread out in rings from where you toss a stone into a lake, closest first; DFS is going down one path in a maze until the end, and coming back to try another path when you hit a dead end.
STEP:
1. **BFS (Breadth-First Search)**: Put the start in a Queue, then repeatedly take out a Vertex and add all its unvisited neighbors to the Queue.
2. It looks at everything at distance 1 before anything at distance 2. So the moment something is first discovered is its **shortest distance (by number of Edges)**.
3. **DFS (Depth-First Search)**: Go into one neighbor, then into that one's neighbor, and so on. When there is nowhere left to go, back up (Backtrack) and take another path. Implemented with recursion or a Stack.
4. If DFS records each Vertex's "first discovered time" and "finished time," you can find Cycles, do Topological Sort, and get SCCs.
5. Both look at every Vertex and Edge once, so they are O(V + E) on an Adjacency List.
6. **Visited marks** are essential. Without them, you go around a Cycle forever.
```python
from collections import deque

def bfs(graph, start):
    dist = {start: 0}
    q = deque([start])
    while q:
        u = q.popleft()
        for v in graph[u]:
            if v not in dist:          # first discovered = shortest distance
                dist[v] = dist[u] + 1
                q.append(v)
    return dist
```
| Aspect | BFS | DFS |
| Tool | Queue | Stack / recursion |
| How it spreads | Layer by layer from the closest | All the way down one path |
| Good at | Shortest distance without weights | Cycle detection, topological sort, exploring every case |
END: For shortest distance (number of steps), use BFS; for digging all the way down to learn the structure, use DFS.

#### Topological Sort
ONE: In a directed Graph with no Cycles (a **DAG**), lining Vertices up so that for every arrow u → v, **u comes before v**.
LIKE: It is planning which classes to take in which order. You line up courses without breaking prerequisites, like "Intro to Programming before Data Structures." If A is a prerequisite for B and B is a prerequisite for A, neither can be taken first.
STEP:
1. **In-Degree**: The number of arrows coming into me, meaning "the number of courses I must take first."
2. **Kahn's Algorithm**: Put every Vertex with In-Degree 0 (no prerequisites) into a Queue.
3. Take one out, append it to the result, and remove the arrows going out of that Vertex. That reduces the In-Degree of the next courses by 1.
4. Put any Vertex whose In-Degree became 0 into the Queue, and repeat.
5. If, when it finishes, some Vertices never made it into the result, there is a Cycle. The Vertices in a Cycle each have to come before the others, so their In-Degree never reaches 0.
6. **DFS approach**: Reversing the order in which DFS finishes Vertices also gives a topological sort. Both are O(V + E).
KEY: The result of a topological sort is not unique; there can be many. When asked "is this a valid order?", check one by one that every arrow points from earlier to later.
USE: Course order, build systems (which file to Compile first), package installation order, Spreadsheet formula calculation order, and task scheduling.
END: Topological sort is "lining things up without breaking prerequisites," and it is impossible if there is a Cycle.

#### SCC (Strongly Connected Component)
ONE: In a directed Graph, **the largest groups of Vertices that can all reach one another**.
LIKE: In a city with lots of one-way streets, it is grouping together "neighborhoods you can drive between and back." Within one group, you can get anywhere and back.
STEP:
1. In a directed Graph, being able to go A → B does not mean you can go B → A.
2. **SCC**: The largest group in which every two Vertices can reach each other.
3. **Kosaraju's Algorithm**: Run DFS once and record the finishing order, then run DFS again on the Graph with every arrow reversed, in reverse finishing order. The Vertices reached in one run of the second DFS form one SCC.
4. **Tarjan's Algorithm**: Finds SCCs in a single DFS by recording, for each Vertex, "the oldest ancestor it can reach" (Low-Link).
5. Both are O(V + E).
6. If you compress each SCC into a single point, the resulting Graph is always a DAG with no Cycles. So it can simplify a complex Graph.
USE: Finding groups that influence each other on social networks, finding circular dependencies in programs, and solving logic problems like 2-SAT.
END: An SCC is "a group that can all reach each other," and compressing each into one point simplifies the Graph into a DAG.

### How do BFS and DFS work, what are their complexities, and what are they used for?
E: BFS is like the ripples that spread out in rings from where you toss a stone into a lake, closest first; DFS is going down one path in a maze until the end, and coming back to try another path when you hit a dead end.
A: BFS (Breadth-First Search) uses a Queue to visit Vertices level by level, closest to the start first, so it finds the Shortest Path (fewest Edges) in an Unweighted Graph. DFS (Depth-First Search) uses a Stack or Recursion to dig all the way down one direction, and is used for Cycle detection, Topological Sort, SCC, and Backtracking. On an Adjacency List, both look at every Vertex and Edge once, so they are O(V + E).
```python
from collections import deque

def bfs(graph, start):
    dist = {start: 0}
    q = deque([start])
    while q:
        u = q.popleft()
        for v in graph[u]:
            if v not in dist:          # first discovered = shortest distance
                dist[v] = dist[u] + 1
                q.append(v)
    return dist
```

### What is Topological Sort? Why is it impossible when there is a Cycle?
E: It is planning which classes to take in which order. You line them up without breaking prerequisites, like "Intro to Programming before Data Structures." If A is a prerequisite for B and B is a prerequisite for A, neither can be taken first.
A: Topological Sort is lining up the Vertices of a DAG (Directed Acyclic Graph) so that for every Edge u → v, u comes before v. It is found in O(V + E) either with Kahn's Algorithm, which puts In-Degree 0 Vertices in a Queue and removes Edges as it takes them out one by one, or by reversing the order in which DFS finishes. Vertices in a Cycle would each have to come before the others, which is a contradiction, so it is impossible; in Kahn's Algorithm, if some Vertices are never taken out, there is a Cycle.
M: The result of a Topological Sort is not unique; there can be many. If an exam asks "is this a valid order?", check the direction of every Edge one by one.

### What is an SCC (Strongly Connected Component)?
E: In a city with lots of one-way streets, it is grouping together "neighborhoods you can drive between and back." Within a group, you can get anywhere and back.
A: An SCC is a maximal set of Vertices in a Directed Graph in which every pair of Vertices can reach each other. It is found in O(V + E) with Kosaraju, which runs DFS twice (on the original Graph and on the reversed Graph), or Tarjan, which uses Low-Link in a single DFS, and compressing each SCC into one point always yields a DAG.

## Shortest Path

#### The Shortest Path Problem and Relaxation
ONE: The problem of finding the shortest path in a weighted Graph. Every Algorithm repeats the same action, **"if going through u to v is shorter, update it" (Relaxation)**; the only difference is the **order**.
LIKE: You thought it was 20 minutes from your house to school, but a friend tells you "it's 15 minutes if you cut through by the corner store," so you update your note to 15 minutes. Keep doing this and eventually only the shortest route remains.
STEP:
1. **Relaxation**: `if dist[u] + w(u, v) < dist[v]: dist[v] = dist[u] + w(u, v)`.
2. At first, set only the start to 0 and everything else to ∞, then repeat Relaxation.
3. **Single-Source**: From one start to everywhere. **All-Pairs**: Between every two points.
4. **Negative Cycle**: If there is a loop that makes the distance smaller every time you go around, the more you loop the shorter it gets, so the shortest path is not defined.
5. Choose the Algorithm to fit the situation.
| Situation | Algorithm | Time |
| No weights (all 1) | BFS | O(V + E) |
| DAG (no Cycles, negatives allowed) | Relaxation in topological order | O(V + E) |
| One start, weights ≥ 0 | Dijkstra | O((V + E) log V) |
| One start, negative Edges | Bellman-Ford | O(VE) |
| All pairs | Floyd-Warshall | O(V³) |
KEY: In a DAG, processing in topological order means that when you reach a Vertex, all the paths coming into it have already been computed. So relaxing each Edge once is enough (O(V + E)), and multiplying the weights by −1 also gives the longest path (the Critical Path of a project schedule).
END: Every shortest path Algorithm is "update when you find a shorter way," and the order of picking differs depending on the weight conditions.

#### Dijkstra's Algorithm
ONE: A shortest path Algorithm that spreads out by **finalizing the closest not-yet-finalized Vertex, one at a time**. It is correct only when **all weights are 0 or more**.
LIKE: Starting from home, you expand your map by finalizing "the closest place known so far," one at a time. Once a place is finalized, you never look at it again. But if there is a "magic tunnel that reduces your travel time when you pass through it (a negative Edge)," an answer you already finalized could be wrong.
STEP:
1. Set the start's distance to 0 and everything else to ∞.
2. Of the Vertices not yet finalized, take the one with the smallest distance and **finalize** it. A Min Heap is used to make this choice fast.
3. Relax that Vertex's neighbors (if a distance gets shorter, update it and push it onto the Heap).
4. Repeat until every Vertex is finalized. With a Binary Heap, O((V + E) log V).
5. **Why it fails with negatives**: The key assumption is "I took out the closest one, so it can't get any shorter," but with negative Edges, a different path might come back later and make it shorter.
```python
import heapq

def dijkstra(graph, s):          # graph[u] = [(v, w), ...], w >= 0
    dist = {s: 0}
    pq = [(0, s)]
    while pq:
        d, u = heapq.heappop(pq)
        if d > dist.get(u, float("inf")):
            continue                # already finalized with a shorter distance
        for v, w in graph[u]:
            nd = d + w
            if nd < dist.get(v, float("inf")):
                dist[v] = nd
                heapq.heappush(pq, (nd, v))
    return dist
```
USE: It is the basic principle behind directions in map apps and Network Routing (OSPF). Real map apps add an estimate toward the destination (A*, etc.) to make it faster.
KEY: The "collection of shortest paths from the start to each point" that Dijkstra builds can differ from the MST (Minimum Spanning Tree). In a triangle with S-A 2, S-B 2, A-B 1, the shortest path Tree is {S-A, S-B} (total 4), while the MST is {A-B, S-A} (total 3).
END: Dijkstra = a Greedy that "finalizes the closest place first." Use it only when there are no negative Edges.

#### The Bellman-Ford Algorithm
ONE: A shortest path Algorithm that repeats **relaxing every Edge, V − 1 times**. It is slow, but it handles **negative Edges** and can also detect **Negative Cycles**.
LIKE: Unlike Dijkstra, it does not rush; it quietly repeats checking every road once, (number of cities − 1) times. If some route still gets shorter after that, there must be a magic loop that shrinks every time you go around.
STEP:
1. Start at 0, everything else ∞.
2. Relax every Edge once. Repeat this V − 1 times.
3. **Why V − 1 times?** A shortest path with no Cycle uses at most V − 1 Edges. After the i-th round, "the shortest distance using at most i Edges" is final, so V − 1 rounds are enough.
4. **Detecting Negative Cycles**: If running one more round (the V-th) still shortens some distance, there is a Negative Cycle.
5. The time is O(VE), slower than Dijkstra.
USE: Problems with negative costs (finding currency arbitrage: take the log of the exchange rates and a profitable loop becomes a Negative Cycle), and it is the principle behind Distance Vector Routing (RIP).
END: Bellman-Ford = "check every road, V−1 times." Negative Edges are OK, and if one more round still shortens something, there is a Negative Cycle.

#### The Floyd-Warshall Algorithm
ONE: A DP that finds the shortest distance **between every pair of points** all at once. It checks "is it faster to go through city k?" for every pair.
LIKE: Check "is it faster to go through city 1?" for every pair of cities, then city 2, city 3, …, adding stopover candidates one at a time.
STEP:
1. Fill dist[i][j] with the direct distance (∞ if not connected, 0 for itself).
2. Increase the stopover k from 1 to V in order, and for every (i, j), do `dist[i][j] = min(dist[i][j], dist[i][k] + dist[k][j])`.
3. After stage k, dist[i][j] is "the shortest distance when only cities 1 to k may be used as stopovers." When you finish, it is the true shortest distance.
4. Three nested loops make it O(V³), and one table makes it O(V²) Memory.
5. It can handle negative Edges too, and if any dist[i][i] < 0 at the end, there is a Negative Cycle.
KEY: k (the stopover) must be the outermost loop. Changing the order makes it wrong.
USE: Used on small Graphs with up to a few hundred Vertices when you need the distance between every pair (building a city-to-city distance table).
END: Floyd-Warshall = "add stopovers one at a time and update every pair." The code is short, and it is O(V³).

### What kinds of Shortest Path problems are there, and how do you choose an Algorithm?
| Situation | Algorithm | Time |
| No weights (all 1) | BFS | O(V + E) |
| DAG (no Cycles, negatives allowed) | Relaxation in Topological Sort order | O(V + E) |
| Single-Source, weights ≥ 0 | Dijkstra (Binary Heap) | O((V + E) log V) |
| Single-Source, negative Edges | Bellman-Ford | O(VE) |
| All-Pairs | Floyd-Warshall | O(V³) |
A: Shortest Path problems split into from one Vertex to all others (Single-Source) and between every pair of Vertices (All-Pairs). Use BFS if there are no weights, Dijkstra if there are no negatives, Bellman-Ford if there are negative Edges, and Floyd-Warshall if you need every pair and there are few Vertices. If there is a Negative Cycle, the distance keeps shrinking the more you loop, so the Shortest Path is not defined.

### How does Dijkstra work, what is its complexity, and why does it fail with negative Edges?
E: Starting from home, you expand your map by finalizing "the closest place known so far," one at a time. Once a place is finalized, you never look at it again, but if somewhere there is a "magic tunnel that reduces your travel time when you pass through it (a negative Edge)," an answer you already finalized could be wrong.
A: Dijkstra sets the start's distance to 0 and the rest to ∞, then repeatedly takes the not-yet-finalized Vertex with the smallest distance from a Min Heap, finalizes it, and Relaxes its neighbors' distances. With a Binary Heap it is O((V + E) log V). The assumption that "the distance of a Vertex taken out never gets smaller" holds only when all weights are ≥ 0, so with negative Edges a finalized distance could later get shorter, giving a wrong answer.

import heapq

    dist = {s: 0}
    pq = [(0, s)]
    while pq:

### How does Bellman-Ford handle negative Edges and Negative Cycles?
E: Unlike Dijkstra, it does not rush; it quietly repeats checking every road once, (number of cities − 1) times. If some route still gets shorter after that, there must be a magic loop that shrinks every time you go around (a Negative Cycle).
A: Bellman-Ford repeats relaxing every Edge V − 1 times. A Shortest Path uses at most V − 1 Edges, so repeating that many times gives the right answer even with negative Edges, and if a value still decreases on one more round, it concludes there is a Negative Cycle. The time is O(VE), slower than Dijkstra.

### What is Floyd-Warshall?
E: Check "is it faster to go through city 1?" for every pair of cities, then city 2, city 3, …, adding stopover candidates one at a time.
A: Floyd-Warshall is a DP that finds the shortest distance between every pair of Vertices by repeating `dist[i][j] = min(dist[i][j], dist[i][k] + dist[k][j])` for stopovers k = 1…V. It takes O(V³) time and O(V²) space, can handle negative Edges, and if any Vertex has `dist[i][i] < 0` at the end, there is a Negative Cycle. It is suitable when there are up to a few hundred Vertices.

### Why can Topological Sort alone find Shortest Paths in a DAG in O(V + E)?
A: Processing a DAG in Topological Sort order means that when you reach a Vertex, every Edge coming into it has already been Relaxed, so its distance is final. So each Edge only needs to be Relaxed once, which is O(V + E) even with negative Edges. Multiplying the weights by −1 lets the same method find the Longest Path (the Critical Path of a project schedule).

### Is Dijkstra's Shortest Path Tree an MST? (a commonly missed question)
E: A Shortest Path Tree is "the collection of the fastest routes from my house to each friend's house," and an MST is "the cheapest way to lay roads connecting every house." The goals are different, so the answers can be different too.
A: No. A Shortest Path Tree minimizes the distance from the start to each Vertex individually, while an MST minimizes the total Edge weight of the whole Tree, so they can differ. For example, in a triangle with S-A 2, S-B 2, A-B 1, the Shortest Path Tree from S is {S-A, S-B} (total 4), but the MST is {A-B, S-A} (total 3). Also, the MST does not depend on a starting point, while the Shortest Path Tree differs for each starting point.

## MST (Minimum Spanning Tree)

#### MSTs and the Cut Property
ONE: An **MST (Minimum Spanning Tree)** is a Tree that **connects every Vertex with no Cycles** with **the smallest total Edge weight**.
LIKE: It is the way to connect every island village with bridges at the lowest total construction cost. Bridges that go around in a loop are unnecessary.
STEP:
1. **Spanning Tree**: A Tree that includes every Vertex of the Graph. It always has V − 1 Edges (the Tree property from topic 01).
2. **MST**: The one among them with the smallest total Edge weight. It is defined on a connected, undirected, weighted Graph.
3. **Cut Property**: If you split the Vertices into two sides in any way, the lightest Edge connecting the two sides can always be part of some MST.
4. Why: If some MST does not use that Edge, removing another (heavier) Edge that connects the two sides in that MST and swapping in this light Edge makes the total the same or smaller.
5. Thanks to this property, the Greedy of "build the cheapest bridge first" gives the right answer. Both Prim and Kruskal rely on it.
USE: Laying communication networks·power grids·road networks at minimum cost, and Clustering (removing the few most expensive Edges splits the groups).
END: An MST is "the Tree that connects everyone most cheaply," and thanks to the Cut Property it can be found with Greedy.

#### Prim vs Kruskal
ONE: **Prim** starts at one point and **grows its territory**, attaching the cheapest bridge, while **Kruskal** looks at **all bridges in order of price** and builds one as long as it does not create a Cycle.
LIKE: Prim starts at one village and expands by building, one at a time, "the cheapest bridge leading out of our territory." Kruskal lines up all candidate bridges by price and builds them in order unless they connect villages that are already connected.
STEP:
1. **Prim**: Start from any Vertex. Use a Min Heap to pick the lightest Edge connecting the current Tree to the outside and attach it to the Tree. Repeat until every Vertex is in. O(E log V).
2. **Kruskal**: Sort all Edges by weight. Going from lightest, if the two endpoints are still in different groups (checked with Union-Find), build it and merge them. If they are in the same group, building it would create a Cycle, so skip it. O(E log E).
3. Both are Greedy algorithms based on the Cut Property.
| Aspect | Prim | Kruskal |
| Approach | Grow territory from one point | Edges in order of price |
| Key tool | Min Heap | Sorting + Union-Find |
| Better for | Dense Graphs with many Edges | Sparse Graphs with few Edges |
END: Growing territory is Prim; picking the cheapest Edges first is Kruskal. Both are correct; choose based on the Graph's shape.

### What is a Minimum Spanning Tree? What is the Cut Property?
E: It is building bridges to connect every island village at the lowest total construction cost. If you split the villages into two sides in any way, building the cheapest bridge between the two sides never hurts.
A: An MST is the Spanning Tree that connects every Vertex of a connected, Undirected, Weighted Graph with no Cycles and has the smallest total Edge weight; it always has V − 1 Edges. The Cut Property says that when you split the Vertices into two sets, the lightest Edge crossing that boundary is always included in some MST, and it is the basis for the correctness of Prim and Kruskal. It is used for network wiring, power grid design, and Clustering.

### How do Prim and Kruskal work, what are their complexities, and how do they differ?
E: Prim starts at one village and expands its territory by building, one at a time, "the cheapest bridge leading out of our neighborhood." Kruskal lines up all candidate bridges by price and builds them in order as long as no Cycle forms.
A: Prim starts from one Vertex and adds the minimum Edge connecting the Tree to the outside, chosen with a Min Heap, in O(E log V), which favors Dense Graphs with many Edges. Kruskal sorts all Edges by weight and adds them while checking for Cycles with Union-Find, in O(E log E), which favors Sparse Graphs. Both are Greedy Algorithms based on the Cut Property.

## Network Flow

#### Max Flow and Min Cut
ONE: When every pipe has a capacity, **the maximum amount you can send from the source to the destination (Max Flow)** is exactly equal to **the capacity of the thinnest cross-section you would have to cut to stop the flow completely (Min Cut)**.
LIKE: In a water pipe network, how many gallons per second at most can you send from the treatment plant (Source) to the city (Sink)? It equals the smallest total capacity of the pipes you would have to cut to stop the water completely. The narrowest bottleneck decides everything.
STEP:
1. **Flow Network**: A directed Graph where each Edge has a **Capacity**. The starting point is the **Source**, and the end point is the **Sink**.
2. **Rule ①**: The Flow on each Edge cannot exceed its Capacity.
3. **Rule ②**: At every middle Vertex, what comes in must go out (Flow Conservation).
4. **Max Flow**: The maximum amount that can be sent from the Source to the Sink while following the rules.
5. **Cut**: A split of the Vertices into a Source side and a Sink side. The Cut's capacity is the total capacity of the Edges going from the Source side to the Sink side.
6. **Max-Flow Min-Cut Theorem**: The value of the Max Flow = the smallest capacity among all Cuts. No matter what you do, water cannot get through more than the narrowest cross-section, and you really can send that much.
WHY: Thanks to this theorem, problems that look different on the surface, like matching, assignment, and image segmentation, are solved with a single Algorithm.
END: The most you can send = the capacity of the narrowest bottleneck.

#### Ford-Fulkerson and the Residual Graph
ONE: Finds the Max Flow by repeatedly finding **a path that can still carry more (an Augmenting Path)** and pushing flow through it. It keeps **paths that undo flow (reverse Edges)** so earlier choices can be corrected.
LIKE: Keep finding paths that can carry more water and push as much through as possible. Along the way, you also build "undo paths" so you can send back water that went the wrong way earlier and switch to a better arrangement.
STEP:
1. **Residual Graph**: A Graph marking, on each Edge, "how much more can be sent" (the remaining capacity) and "how much of what's been sent can be pushed back" (the reverse direction).
2. Find one path from Source → Sink in the Residual Graph (an **Augmenting Path**).
3. Add Flow equal to the smallest remaining capacity along that path. Update the Residual Graph too.
4. Repeat until there are no more paths. The Flow at that point is the Max Flow.
5. **Why reverse Edges matter**: The path you chose first might have been a bad one. Pushing flow in reverse to "cancel" lets you reroute it another way, so you reach the optimum.
6. With integer capacities, it is O(E × f) (f is the Max Flow value). **Edmonds-Karp**, which finds paths with BFS, is O(VE²), guaranteeing a time that does not depend on the size of the capacities.
END: Ford-Fulkerson repeats "find a path that can carry more and push flow through," and reverse Edges let it fix mistakes.

#### Bipartite Matching
ONE: The problem of making **as many non-overlapping pairs as possible** between two groups (e.g., applicants and companies), which can be solved **by turning it into a Max Flow problem**.
LIKE: When pairing applicants with companies, if each can go to only one place, connect them with "pipes of capacity 1" and push as much water through as you can. The amount of water that flows is the maximum number of pairs.
STEP:
1. **Bipartite Graph**: The Vertices are split into two groups, and Edges exist only between the groups.
2. Create a Source and connect it to every Vertex in the left group with capacity-1 Edges.
3. Connect left to right with capacity-1 Edges wherever a pair "is possible."
4. Connect every Vertex in the right group to the Sink with capacity-1 Edges.
5. Find the Max Flow, and its value is the maximum number of matches. The middle Edges carrying a Flow of 1 are the actual pairs.
6. When the capacities are integers, an integer Max Flow exists, so each Edge's Flow is exactly 0 or 1, meaning "paired/not paired."
USE: Assigning workers to tasks, students to clubs, and ads to ad slots.
END: Matching problems are turned into a Network of capacity-1 pipes and solved with Max Flow. Turning an unfamiliar problem into a familiar one is exactly the Reduction you will learn next.

### What is the Max-Flow Min-Cut Theorem?
E: How many gallons per second at most you can send from the treatment plant (Source) to the city (Sink) in a water pipe network equals the smallest total capacity of the pipes you would have to cut to stop the water completely. The narrowest bottleneck decides everything.
A: The Max Flow problem finds the maximum amount that can be sent from the Source to the Sink in a Directed Graph where each Edge has a Capacity, while respecting Capacity and Flow Conservation (what comes in goes out). The Max-Flow Min-Cut Theorem states that this Max Flow equals the Capacity of the Cut with the smallest total Capacity among the Cuts separating the Source and the Sink.

### What are Ford-Fulkerson and the Residual Graph?
E: Keep finding paths that can still carry more water and push as much through as possible. Also keep reverse "undo paths," so water sent the wrong way earlier can be sent back and switched to a better arrangement.
A: Ford-Fulkerson repeatedly finds a Source→Sink path (an Augmenting Path) in the Residual Graph and adds Flow equal to the smallest remaining Capacity on that path, until no path is left. The Residual Graph has forward Edges for the remaining Capacity and reverse Edges for the current Flow, so earlier choices can be undone. With integer Capacities it is O(E · f) (f is the Max Flow), and Edmonds-Karp, which finds Augmenting Paths with BFS, is O(VE²).

### How do you solve Bipartite Matching with Max Flow?
E: When pairing applicants with companies, if each can go to only one place, connect them with "Capacity-1 pipes" and push as much water through as you can; that gives the maximum number of pairs.
A: Create Capacity-1 Edges from the Source to the left Vertices, from left to right (possible pairs), and from the right Vertices to the Sink; the value of the Max Flow is then the size of the Maximum Matching. With integer Capacities, an integer Max Flow exists, so each Edge's Flow of 0 or 1 directly means "paired/not paired."

## Reduction and Linear Programming

#### Reduction
ONE: A way to solve an unfamiliar problem A by **translating it into a problem B you already know how to solve**. Conversely, it is also used to show "if A is hard, then B is hard too."
LIKE: If a vending machine won't take a $20 bill, you break it into $1 bills at the store and then use the machine. You change the problem into a shape you can use.
STEP:
1. Turn A's input into B's input (transformation).
2. Solve B.
3. Turn B's answer back into A's answer.
4. If the transformation is fast and B can be solved fast, A is solved fast too.
5. Conversely, if A is known to be hard and A can be quickly transformed into B, then B is at least as hard as A. That is why Reduction is also used to prove "this problem is hard (NP-Complete)" (topic 08).
USE: Bipartite matching → Max Flow, scheduling → Linear Programming, and turning Sudoku into a SAT (satisfiability of logic formulas) problem to solve with a SAT Solver.
END: Reduction is "translating into a problem you know." It is used both to solve problems easily and to prove they are hard.

#### LP (Linear Programming) and ILP
ONE: **LP** is the problem of maximizing·minimizing a linear objective under linear constraints, and it is solved quickly. **ILP**, where the variables must be **integers**, is in general very hard.
LIKE: LP is choosing ingredient amounts freely down to the decimal, like "2.7 kg of flour, 1.3 kg of sugar," to maximize profit. ILP allows only whole numbers, like "only 2 or 3 cakes, not 2.5." That one integer condition creates situations where you have to check combinations one by one.
STEP:
1. **LP**: The variables (e.g., how many of products A and B to make), the constraints (ingredient·time limits, e.g., 2x + y ≤ 10), and the objective function (e.g., maximize profit 3x + 2y) are all linear.
2. If the variables are real numbers, it can be solved in polynomial time (Interior Point Method). The widely used **Simplex Method** is slow in the theoretical worst case but very fast in practice.
3. **ILP**: The variables must be integers. Things like the number of people, the number of trucks, and "do it or not (0/1)" decisions.
4. ILP is in general **NP-Hard**, so no fast Algorithm is known.
5. So it is solved by temporarily relaxing the integer condition to get an approximate solution with LP (**LP Relaxation**), or by **Branch and Bound**, which splits into branches and prunes the impossible ones.
USE: It is the common framework for optimization problems like production planning, delivery routes, building work schedules, and allocating ad budgets.
END: Real numbers are LP (fast); integers are ILP (hard). One integer condition makes the problem much harder.

### What is Reduction?
E: It is "translating" an unfamiliar problem into one you already know how to solve. Like breaking a $20 bill into $1 bills at the store when a vending machine won't take it.
A: Reduction turns the input of problem A into the input of problem B and turns B's solution back into A's solution. If the transformation is fast and B can be solved fast, A is solved fast too; conversely, it shows that if A is hard, B is hard too. Solving Bipartite Matching with Max Flow and Scheduling with LP are practical Reductions, and the same concept is used in NP-Complete proofs (08 Theory of Computation).

### What is the difference between LP (Linear Programming) and ILP (Integer Linear Programming)? Why is ILP hard?
E: LP is choosing ingredient amounts freely down to the decimal, like "2.7 kg of flour, 1.3 kg of sugar," to maximize profit, and ILP allows only whole numbers, like "only 2 or 3 cakes, not 2.5." That one integer constraint creates situations where you have to check the possible combinations one by one.
A: LP maximizes·minimizes a linear Objective Function under linear inequality Constraints; if the variables are real numbers, it is solved in polynomial time (Interior Point Method), and in practice the Simplex Method is fast too. ILP requires integer variables, is in general NP-Hard with no known polynomial-time Algorithm, and is solved by getting an approximate solution from the LP Relaxation (with the integer constraint removed) or with Branch and Bound.

## Essential Coding Test Techniques

#### Two Pointers and Sliding Window
ONE: A technique that moves two pointers **in one direction only**, reducing a nested-loop O(n²) to **O(n)**.
LIKE: Two Pointers is two people walking toward the middle from opposite ends of a bookshelf while searching, and Sliding Window is watching the scenery through a train window as it slides along one panel at a time. You just add the one newly visible panel and subtract the one that disappeared.
STEP:
1. **Two Pointers (from both ends)**: Find two numbers that sum to x in a sorted array. The left pointer starts at the beginning and the right at the end.
2. If the sum is less than x, move the left one step right (to increase the sum); if greater, move the right one step left (to decrease it). If equal, you found it.
3. Each pointer moves at most n times, so it is O(n).
4. **Sliding Window (same direction)**: For "the maximum sum of a contiguous stretch of length k," compute the sum of the first k, then each time the window slides one step, add the value that came in and subtract the value that left. No need to add up k values again each time.
5. The window size can also change. For "the longest substring without repeats," extend the right side, and shrink the left side when a repeat appears.
```python
def max_sum_k(a, k):
    s = best = sum(a[:k])
    for i in range(k, len(a)):
        s += a[i] - a[i - k]     # add the value coming in, subtract the one leaving
        best = max(best, s)
    return best
```
KEY: Signals: think Two Pointers first for "find a pair in a sorted array," and Sliding Window for "contiguous subarrays·substrings."
END: Push the pointers in one direction without ever moving them back, and O(n²) becomes O(n).

#### Backtracking
ONE: A method that tries possible choices one at a time and, **when it gets stuck, goes back to the previous choice** and tries a different one. The key is **cutting off paths that can't lead to an answer early (Pruning)**.
LIKE: In a maze, at each fork you pick one path and try it, and if you hit a dead end, you go back to the last fork and take another path. If you can tell early that "this path heads away from the exit," you don't have to follow it to the end.
STEP:
1. Fill in the answer one slot at a time (e.g., for N-Queen, one queen per row).
2. At each slot, pick one possible choice and move on to the next slot (recursion).
3. If a rule is broken or you cannot go further, undo the choice you just made and try another one (Backtrack).
4. If you fill every slot, you have found one answer.
5. **Pruning**: If you can already tell it cannot become an answer, you do not look below it at all. This decides the speed.
6. The worst case is exponential time (O(2ⁿ), O(n!)), but with good pruning it is much faster in practice.
```python
def subsets(nums):
    res, cur = [], []
    def go(i):
        if i == len(nums):
            res.append(cur[:]); return
        cur.append(nums[i]); go(i + 1)   # include it
        cur.pop();           go(i + 1)   # exclude it (undo)
    go(0)
    return res
```
USE: Generating all permutations·combinations·subsets, N-Queen, Sudoku, and solving mazes. Signal: the problem asks for "every possible case" and n is small (usually 20 or less).
END: Backtracking is "try it, and go back if it doesn't work," and the better you prune, the faster it gets.

#### Bitmasks and LCA
ONE: A **Bitmask** represents many on/off states **as the Bits of a single integer**, and **LCA** finds **the lowest common ancestor** of two Nodes in a Tree.
LIKE: A Bitmask is writing down the on/off state of n switches as a single number, and LCA is finding the closest common ancestor of two people in a family tree.
STEP:
1. **Bitmask**: Represent a subset of an n-element set as an n-Bit integer. If the i-th Bit is 1, element i is included.
2. `mask | (1 << i)` adds element i, `mask & (1 << i)` checks whether i is present, and looping from `0` to `2ⁿ − 1` visits every subset.
3. **Bitmask DP**: Puts "which cities have been visited" into the state as a Bitmask to solve the Traveling Salesman Problem (TSP) in O(2ⁿ · n²). It only works up to about n = 20.
4. **LCA**: The first ancestor where the paths going up from two Nodes meet. Used to find the distance between two Nodes (distance = sum of depths − 2 × depth of LCA).
5. **Binary Lifting**: If you precompute each Node's 1st, 2nd, 4th, 8th… ancestor (preprocessing O(n log n)), you can find the LCA in O(log n) per query by taking the big jumps first.
END: Pack small sets into one number with a Bitmask, and find a Tree's common ancestors quickly with power-of-two jumps (Binary Lifting).

#### Signals for Recognizing Problem Types
ONE: Most Coding Test problems are variations of a handful of techniques. If you look at the **signals (keywords)** in the problem and first think "what technique's shape is this?", you solve it faster.
LIKE: It is like a doctor seeing symptoms (fever, cough) and thinking of candidate illnesses. Looking at a problem's "symptoms" narrows down the candidate tools to use.
STEP:
1. First look at **the input size n**. It sets the target Complexity. Roughly: if n ≤ 20, even O(2ⁿ) is possible; if n is up to a few thousand, O(n²); if n is 100,000 to 1,000,000, O(n log n) or better.
2. Next, look at the signals in the problem and pick candidate techniques.
3. Solve a small example by hand with the candidate technique, and if it works, implement it.
| Signal in the problem | Technique to think of first |
| Sorted array, "find" | Binary Search, Two Pointers |
| Contiguous subarray·substring | Sliding Window, Prefix Sum |
| "Seen it before?", frequency, finding pairs | Hash Map / Hash Set |
| Top k, need the minimum repeatedly | Heap |
| Next greater element, bracket matching | Stack (Monotonic Stack) |
| Connections, shortest distance, grids | BFS / DFS |
| Precedence, dependency order | Topological Sort |
| Merging groups, connectivity | Union-Find |
| All combinations·permutations·subsets | Backtracking |
| "Number of ways," "minimum cost," a sequence of choices | Dynamic Programming |
| Sort, then pick the best at each step | Greedy |
| Prefixes, autocomplete | Trie |
| O(1) space, even·odd, representing small sets | Bit operations |
KEY: **The ability to recognize the type** matters more than solving lots of problems. A few days after solving a problem, check whether you can solve it again from scratch. Memorizing solutions is useless.
END: Set the target speed from the input size, and pick the technique from the signals in the problem.

#### The Flow of Solving a Coding Interview Problem
ONE: A coding interview is not a test of getting the right answer but a chance to see **"what would it be like to solve problems with this person?"** Think out loud and go in the order **clarify → simple approach → improve → implement → verify**.
LIKE: It is like solving a puzzle with a friend. Someone who talks through it together, saying "what if we try this?", is a better partner than someone who quietly gets it right alone.
STEP:
1. **Clarify the problem (3–5 minutes)**: Ask about input ranges, whether duplicates are allowed, empty input, and whether it is sorted. Make up a small example yourself to confirm your understanding.
2. **Start by stating a simple approach**: First state the most naive (Brute Force) solution and its Complexity. It becomes the starting point.
3. **Improve it**: Look for repeated computation, unused information, and unnecessary work. Work backward from the input size to the target Complexity.
4. **Agree on the design**: Before writing code, explain your approach and get the interviewer's agreement.
5. **Implement (15–20 minutes)**: Use meaningful variable names and split things into small helper functions. If a detail has you stuck, say "let's assume we have a function like this," move on, and fill it in later.
6. **Verify**: Trace an example through the code by hand. Check edge cases like empty input, a single element, maximum values, and duplicates.
7. **Summarize the Complexity**: State the time and space Complexity, and mention whether there is room for further improvement.
KEY: **When you're stuck**, make the example bigger and solve it by hand, then turn that process into an Algorithm; or solve it with one condition removed; or try plugging in data structures one at a time ("What if I use a Hash? A Heap? Sort first?"). And don't go silent; say what you're thinking right now. A hint from the interviewer is not a penalty but collaboration.
END: Clarify, start simple, improve, agree, implement, and verify. The key is saying this whole process out loud.

### What techniques come up often in Coding Tests?
| Technique | Analogy | When | Complexity |
| Two Pointers | Two people walking toward the middle from opposite ends of a bookshelf | Pairs summing to x in a sorted Array | O(n) |
| Sliding Window | Sliding a window one panel at a time and looking out | Maximum sum of a contiguous stretch, longest substring without repeats | O(n) |
| Backtracking | Going back when you hit a dead end in a maze | N-Queen, generating Combinations·Permutations, Sudoku | Exponential worst case, reduced by Pruning |
| Bitmask | Representing a Subset as the on/off states of n switches | Exploring every Subset, TSP (Traveling Salesman) DP | Around O(2ⁿ · n) |
| LCA (Lowest Common Ancestor) | Finding two people's closest common ancestor | Distance between two Nodes in a Tree | Preprocessing O(n log n), query O(log n) (Binary Lifting) |
A: Two Pointers and Sliding Window reduce a nested-loop O(n²) to O(n) by moving Pointers in one direction only, and Backtracking cuts down Brute Force by pruning branches that cannot lead to a solution early (Pruning). A Bitmask represents a set of up to about n ≤ 20 as one integer for Subset DP, and LCA precomputes 2ᵏ-th ancestors with Binary Lifting to answer each query in O(log n).

### How do you recognize which Algorithm technique to use for a problem?
E: Just as a doctor sees symptoms and thinks of candidate illnesses, you narrow down candidate techniques from the input size and the signals in the problem (sorted, contiguous stretch, shortest distance, number of ways, etc.).
A: First estimate the target Complexity from the input size (if n is 100,000 or more, O(n log n) or better). Then look at the signals: a sorted array suggests Binary Search·Two Pointers; a contiguous stretch, Sliding Window·Prefix Sum; frequency·finding pairs, Hash; top k, Heap; shortest distance·grids, BFS; dependency order, Topological Sort; merging groups, Union-Find; every case, Backtracking; number of ways·minimum cost, DP; and then verify with a small example.

### In what order should you work through a problem in a Coding interview?
E: Like solving a puzzle with a friend, think out loud and go in the order clarify → easy approach → improve → agree → implement → verify.
A: Clarify the problem by asking about input ranges and edge cases, state the Brute Force solution and its Complexity first, then optimize by finding repeated computation or unused information. Explain the approach and get agreement, implement it in readable code, verify by tracing examples and edge cases (empty input, a single element, duplicates) by hand, and summarize the time·space Complexity. When stuck, don't go silent; talk through your thinking.
