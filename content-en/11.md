## How the Web Works

#### How a Browser Draws the Screen (Rendering)
ONE: The Browser builds **the structure (DOM)** from HTML and **the styling rules (CSSOM)** from CSS, combines them to **calculate positions (Layout)**, and then **paints the colors (Paint)** to draw the screen.
LIKE: It's like interior construction. You build the room layout from the floor plan (HTML), set the decorating rules from the color chart (CSS), measure where the furniture goes (Layout), and paint (Paint). Moving furniture means measuring again, which is expensive.
STEP:
1. **HTML Parsing → DOM**: Reads the HTML tags and builds the Tree-shaped **DOM (Document Object Model)**. JavaScript changes the screen by modifying this DOM.
2. **CSS Parsing → CSSOM**: Reads the CSS rules and builds the CSSOM, which holds "which style applies to which element."
3. **Render Tree**: Combines the DOM and CSSOM, keeping only the elements that will actually be visible (`display: none` is left out).
4. **Layout (Reflow)**: Calculates each element's exact position and size.
5. **Paint**: Paints text, colors, borders, and shadows into pixels.
6. **Composite**: Stacks several layers (Layers) to make the final screen.
7. **JavaScript's effect**: When the Browser hits a regular `<script>` tag, it stops reading the HTML to download and run the Script. That's why you add `defer` or `async` or put Scripts at the bottom.
KEY: DOM changes that alter an element's size or position force Layout to run again, which is expensive. Batching several changes together, or moving things with methods that don't touch Layout like `transform`, makes it faster.
END: HTML → DOM, CSS → CSSOM, combine, then Layout → Paint → Composite. The key to performance is making Layout rerun less often.

#### CSR and SSR
ONE: In **CSR**, the Browser **builds the screen itself** with JavaScript; in **SSR**, the Server **builds the finished HTML** and sends it. They differ in first-screen speed, search visibility, and Server load.
LIKE: CSR is receiving furniture as parts and assembling it at home; SSR is having finished furniture delivered. Flat-pack takes longer at first, but once assembled, rearranging is easy.
STEP:
1. **CSR (Client-Side Rendering)**: The Server sends nearly empty HTML and a big JavaScript file. The Browser runs the JS, fetches data, and builds the screen.
2. CSR pros: After the first load, page transitions are fast and smooth like an app. Cons: The first screen shows up late, and search engines may see only empty HTML, which can hurt SEO (search visibility).
3. **SSR (Server-Side Rendering)**: The Server fills in the data and sends finished HTML. The first screen shows up fast and it's good for SEO.
4. SSR cons: The Server builds HTML on every request, so the load is heavy. And even once the screen is visible, buttons need a **Hydration** step that attaches the JS before they work.
5. **SSG (Static Site Generation)**: Builds all the HTML in advance at build time. Good for pages that rarely change, like blogs or docs.
6. Frameworks like Next.js pick and mix CSR·SSR·SSG per page.
END: Assembling in the Browser is CSR (fast transitions), finishing on the Server is SSR (good first screen·SEO), and building in advance is SSG.

#### Web Servers and WAS
ONE: A **Web Server** quickly hands over files that already exist (HTML, images), and a **WAS** runs code to **produce results on the spot**.
LIKE: A Web Server is the convenience store clerk handing over pre-made sandwiches, and a WAS is the kitchen that takes orders and cooks each one on the spot.
STEP:
1. **Static Content**: The same file no matter who asks. HTML, CSS, JS, images.
2. **Dynamic Content**: A different result for each request. "My order list" has to be built by querying the DB.
3. **Web Server (Nginx, Apache)**: Sends Static files very quickly, and handles acting as a **Reverse Proxy** that takes requests up front and passes them back, **Load Balancing** across several Servers, and **TLS Termination**, which decrypts HTTPS.
4. **WAS (Web Application Server, Tomcat, etc.)**: Runs Application code to do Dynamic work like DB lookups and login handling.
5. **Using them together**: Put the Web Server in front; it handles Static requests directly and passes only Dynamic requests to the WAS. This lightens the WAS's load and keeps the WAS from being exposed directly to the outside, which is safer.
END: Handing over files is the Web Server; computing and building is the WAS. Usually the Web Server goes in front and the WAS behind.

#### Building a Server with a Web Framework (a Flask Example)
ONE: A **Web Framework** is a tool built around "when a request comes to this address, run this function" (**Routing**), which also takes care of repetitive work like filling in page templates (Template) and remembering login state (Session).
LIKE: It's like a restaurant operations manual. "Orders from table 1 go to the grill cook, table 2 to the pastry chef" (Routing), "fill today's dishes into the menu template" (Template), and "remember regulars" (Session) are all laid out in advance.
STEP:
1. **Routing**: Connects each URL path to a function that handles it. In Flask, you put the `@app.route("/hello")` Decorator above the function.
2. **Request handling**: The function reads the request info (URL parameters, Form data) and queries the DB if needed.
3. **Template**: Fills data into an HTML template to make the finished page (Jinja2 in Flask). `<h1>Hello, {{ name }}</h1>`.
4. **Session**: Remembers login state. Flask's default Session lives in a signed Cookie, which prevents tampering but can still be read, so don't put sensitive information in it.
5. **Structure**: Usually follows an MVC-style structure split into data (Model)·screen (View/Template)·processing logic (Controller) (topic 10).
6. **Never store passwords as-is**; store them as a slow Hash (see the Security concepts below).
```python
from flask import Flask, render_template

app = Flask(__name__)

@app.route("/hello/<name>")          # when a request comes to this address
def hello(name):                     # run this function
    return render_template("hello.html", name=name)
```
USE: Python's Flask·Django·FastAPI, JavaScript's Express, and Java's Spring all share the same idea.
END: Web Framework = Routing (address → function) + Template (filling in templates) + Session (remembering state). It handles the repetitive work for you.

#### Native Apps · Web Apps · Hybrid Apps · PWAs
ONE: Ways to build an app include **building it in the device's own language (Native)**, **building it as a website (Web)**, **putting the web inside an app shell (Hybrid)**, and **adding app features to the web (PWA)**.
LIKE: Native is a book written directly in that country's language, a Web App is an online article anyone can read anywhere, Hybrid is an online article wrapped in a book cover, and a PWA is an online article you can put on your bookshelf and read even offline.
STEP:
1. **Native App**: Built separately in each platform's language, like Swift for iOS and Kotlin for Android. It has the best performance and can use every device feature (camera, sensors). In exchange, you build it twice and go through Store review.
2. **Web App**: A website that runs in the Browser. No installation needed, and build it once and it runs on every device. Device features and performance are limited.
3. **Hybrid App**: Puts a WebView (a Browser inside the app) inside a Native shell to run web code. You reuse web code and can still publish to the Store.
4. **PWA (Progressive Web App)**: A website equipped with a Service Worker and a Manifest. It can be installed on the home screen and use offline Caching and Push notifications. Support varies by platform (especially iOS).
5. **Cross-Platform (React Native, Flutter)**: Builds apps for both platforms from one codebase. It is distinguished from Hybrid because it uses Native UI or its own drawing engine rather than a WebView.
END: For performance·features, Native; for cost·reach, Web; in between are Hybrid·PWA·Cross-Platform.

## Authentication and Authorization

#### Authentication and Authorization
ONE: **Authentication** checks "**Who are you?**" and **Authorization** checks "**Are you allowed to do that?**" Authentication comes first, authorization after.
LIKE: Showing your ID at the hotel front desk is authentication, and the key card you get opening only your own room on the 7th floor is authorization.
STEP:
1. **Authentication**: Confirms the user really is who they claim to be: a password (something you know), an OTP·phone (something you have), a fingerprint·face (something you are).
2. Using two or more of these together is **MFA (Multi-Factor Authentication)**. Even if your password is stolen, nobody gets in without your phone.
3. **Authorization**: Checks whether an authenticated user has permission to access a particular resource or feature. Regular members can't get into the admin page.
4. Permission management: **RBAC**, which grants permissions by role (admin, editor, regular), is the most common.
5. **HTTP status codes**: If not authenticated, **401 Unauthorized** (login required); if authenticated but lacking permission, **403 Forbidden** (access denied).
KEY: 401 is named "Unauthorized," but it actually means "not authenticated." The name is confusing, so remember it by its meaning.
END: Authentication = who you are (401); authorization = what you can do (403).

#### Session-Based Authentication vs Token-Based Authentication
ONE: In the **Session** approach, **the Server stores login information** and the Client carries only a claim ticket; in the **Token** approach, **the Token itself holds the information and a signature**, and the Server only checks the signature.
LIKE: A Session is a gym locker key. The key has only a number on it, and the gym (Server) keeps your stuff. A Token is an amusement park wristband. The wristband itself says "all-day pass, valid today," and staff just check the anti-counterfeit stamp.
STEP:
1. **Session approach**: When you log in, the Server stores your user info and gives you a **Session ID** as a Cookie. On each request, it looks up the store with the Session ID to know who you are.
2. Session pros: Deleting the Session on the Server instantly forces a logout. Cons: With several Servers, you need a shared store (Redis, etc.) so the Session can be found no matter which Server gets the request.
3. **Token approach**: When you log in, the Server gives you a **signed Token** (usually a JWT) containing your user info. Send the Token with each request, and the Server only verifies the signature. The Server has nothing to store (**Stateless**).
4. Token pros: Easy to add Servers, and several services can verify the same Token. Cons: Once issued, a Token is hard to invalidate before it expires.
5. **Access Token + Refresh Token**: Make requests with a short-lived Access Token (e.g., 15 minutes), and when it expires, get a new one with a long-lived Refresh Token. If it's stolen, the damage window is short, and managing only the Refresh Token on the Server makes logout possible too.
| Aspect | Session | Token (JWT) |
| Where state lives | Server | In the Token itself (Stateless) |
| Scaling | Needs a shared Session store | Easy |
| Forced logout | Easy | Hard (offset by short expiry + Refresh) |
END: If the Server remembers, it's a Session (easy to control); if the Token carries it, it's Stateless (easy to scale).

#### JWT (JSON Web Token)
ONE: A **JWT** is a Token made of three parts, **Header.Payload.Signature**, joined by dots. The Signature **prevents tampering**, but the contents **can be read by anyone**.
LIKE: It's a letter in a clear envelope with a wax seal. Anyone can read the contents, but if the seal is broken, you know immediately that someone changed it.
STEP:
1. **Header**: Which signing method (Algorithm) was used.
2. **Payload**: Information like the user ID, permissions, and expiration time (exp) (**Claims**).
3. **Signature**: The Header and Payload signed with a Secret Key (HMAC) or a Private Key (RSA·ECDSA).
4. Each of the three parts is converted to **Base64URL** and joined with dots (.): `xxxxx.yyyyy.zzzzz`.
5. The Server recomputes the signature from the received Token's Header and Payload and compares it with the Signature. If anyone changes the Payload even slightly, the signature won't match and it's rejected.
6. **Base64URL is Encoding, not Encryption**. Anyone can decode and read the Payload, so you must not put passwords or personal information in it.
KEY: Keep expiration times short, exchange it only over HTTPS, and when putting it in a Cookie, add HttpOnly·Secure·SameSite. The Server must not blindly trust the Algorithm in the Header and should accept only the methods it allows.
END: A JWT is a signed Token that is "readable but not changeable." Don't put secrets in it.

#### OAuth 2.0 and OpenID Connect
ONE: **OAuth 2.0** is a way for a user to **lend another app limited permission to their resources** **without handing over their password**. For logins like "Sign in with Google," **OpenID Connect** is used on top of it.
LIKE: It's like a valet key. Instead of handing over the master key with the house key attached (your password), the car owner hands over a valet-only key that can only park the car (an Access Token).
STEP:
1. Example: A scheduling app wants to read your Google Calendar. Giving the app your Google password would be dangerous.
2. The app sends you to **Google's login screen (Authorization Server)**. You log in to Google directly and agree to "Grant calendar read access?"
3. Google gives the app a one-time **Authorization Code** (passed via the Browser).
4. The app's Server sends this Code to Google and exchanges it for an **Access Token**. This exchange happens Server to Server, so the Token isn't exposed to the Browser.
5. The app calls the **Resource Server** (the Google Calendar API) with the Access Token. The Token can only "read the calendar," and you can revoke the permission at any time.
6. **OIDC (OpenID Connect)**: OAuth was originally for "delegating permission." For logins that also confirm "who this person is," OIDC is layered on top of OAuth to also receive an **ID Token**.
END: OAuth = lending a limited key (Access Token) instead of your password. To also do login, add OIDC.

### What is the difference between Authentication and Authorization?
E: Showing your ID at the hotel front desk is Authentication (who you are), and the key card you get opening only your own room on the 7th floor is Authorization (what you can do).
A: Authentication confirms who a user is (password, OTP, biometrics), and Authorization checks whether an authenticated user has permission to access a particular resource. Authentication comes first and Authorization follows, and in HTTP, an authentication failure is 401 and lacking permission is 403.

### What is the difference between Session-based and Token-based authentication?
E: A Session is a gym locker key. The key has only a number on it, and the gym (Server) keeps your stuff. A Token is an amusement park wristband. The wristband itself says "all-day pass, valid today," and staff just check the anti-counterfeit stamp.
A: In the Session approach, the Server stores login information and the Client carries only a Session ID as a Cookie, so forced logout is easy, but with several Servers the Session store (Redis, etc.) must be shared. In the Token approach, the Server puts user information in a signed Token and only verifies the signature on each request, so the Server stores no state (Stateless) and scaling is easy, but invalidating an issued Token before it expires is hard. That's why a short-lived Access Token and a long-lived Refresh Token are used together.

### What is the structure of a JWT, and what should you watch out for?
A: A JWT (JSON Web Token) is a Token made of a Header (Algorithm), a Payload (Claims like the user ID·expiration time), and a Signature, joined by dots (.) with each part Base64URL-Encoded. The Signature is made with a Secret Key (HMAC) or a Private Key (RSA·ECDSA) to prevent tampering, but Encoding is not Encryption, so anyone can read the contents and sensitive information like passwords must not be put in it. Keep the expiration time short, exchange it only over HTTPS, and when putting it in a Cookie, give it the HttpOnly·Secure·SameSite attributes.

### What is OAuth 2.0? How does it work?
E: It's a valet key. Instead of handing over the master key with the house key attached (your password), the car owner hands over a valet-only key that can only park the car (an Access Token).
A: OAuth 2.0 is an Authorization Framework that lets a user delegate limited access to their resources (like a Google Calendar) to a third-party app without handing over their password. In the typical Authorization Code flow, the app sends the user to the Authorization Server for login·consent, the app's Server exchanges the Authorization Code returned by the Authorization Server for an Access Token, and then calls the Resource Server's API with that Token. OAuth itself is for Authorization; for Authentication like "Sign in with Google," OpenID Connect (OIDC) is used on top of it.

## Security

#### Hashing and Encryption, and Storing Passwords
ONE: **Encryption** is a transformation you **can reverse** if you have the Key, and a **Hash** is a one-way transformation you **can't reverse**. Passwords don't need the original, so they are stored as **a slow Hash with a Salt**.
LIKE: Encryption is a safe you can open with a key. A Hash is a blender. You can't turn juice back into fruit, but the same fruit always makes the same juice, so you can check "was this juice made from apples?"
STEP:
1. **Encryption**: Makes ciphertext with a Key and gets the original back with a Key (Decryption). Used for data you need to read again (messages, card information, etc.).
2. **Hash**: Turns input of any length into a fixed-length value. The same input always gives the same Hash, a tiny change gives a completely different Hash, and you can't work back from the Hash to the input.
3. **Checking a password**: At login, Hash the entered password the same way and compare it with the stored Hash. The original exists nowhere.
4. **Rainbow Table attack**: An attack that works backward using a precomputed table of Hashes of common passwords.
5. **Salt**: Attach a different random value for each user to the password before Hashing. Even the same password gets a different Hash, making precomputed tables useless.
6. **Slow Hashes**: SHA-256 is so fast that an attacker can try billions per second. That's why deliberately slow functions like **bcrypt, scrypt, and Argon2** are used.
KEY: If you "encrypt" passwords with AES and store them, every password is exposed the moment the Key leaks. Base64 is Encoding that anyone can reverse. The right answer is Salt + a slow Hash.
END: If you need to reverse it, Encryption; if you only need to check it, Hash. Passwords get Salt + a slow Hash like bcrypt·Argon2.

#### Digital Signatures and Certificates
ONE: A **Digital Signature** proves "who sent it and that the contents haven't changed" by **signing with a Private Key and letting anyone verify with the Public Key**, and a **Certificate** is a document in which **a Certificate Authority (CA) vouches** that "this Public Key really belongs to this site."
LIKE: A Digital Signature is like a signature only the owner can make, which anyone can compare against a sample. A Certificate is like a notary officially vouching that "this signature really belongs to this person."
STEP:
1. Review: A **Symmetric Key** locks and unlocks with the same Key, which is fast but hard to share (AES), and a **Public Key** locks with the public Key and unlocks only with the private Key, which is easy to share but slow (RSA, ECC).
2. **Signing**: Make a Hash of the message, and sign that Hash with **your Private Key**.
3. **Verifying**: The recipient compares the Hash obtained by checking the signature with **your Public Key** against a Hash they compute themselves from the received message. If they match, it's proven that "this person sent it and the contents haven't changed."
4. **The problem**: How do you know that Public Key really belongs to that person? An impostor could pass off their own Public Key as "the bank's Key."
5. **Certificate**: A document in which a trusted **CA (Certificate Authority)** signs, with its own Private Key, that "this Public Key belongs to bank.com."
6. Browsers and OSes come with a list of trusted CAs built in, so they can verify a Certificate's signature. This is how HTTPS comes to trust the other Server (topic 04).
USE: HTTPS certificates, app signing (whether an installer has been tampered with), electronic contracts, Git Commit signing.
END: Sign with the private Key, verify with the public Key. A CA vouches with a Certificate that the public Key is genuine.

#### XSS and CSRF
ONE: **XSS** is an attack where an attacker's Script **runs in another user's Browser**, and **CSRF** is an attack that makes a logged-in user's Browser **send requests the user didn't intend**.
LIKE: XSS is posting a spell on a message board that says "the moment you read this, give me your wallet," so the reader's Browser carries it out. CSRF is getting a logged-in person to click a disguised link, so a money transfer request goes out in their name.
STEP:
1. **XSS (Cross-Site Scripting)**: The attacker puts a `<script>` in a post or comment. If the site prints it to the screen as-is, the Script runs in the Browser of every user who views that post, stealing Cookies or manipulating the page.
2. **Preventing XSS**: When outputting, turn special characters like `<` and `>` into harmless text (**HTML Escape**). Set up a **CSP** that restricts where Scripts can come from, and add **HttpOnly** to Cookies so Scripts can't read them.
3. **CSRF (Cross-Site Request Forgery)**: When a Browser makes a request to a site, it automatically attaches that site's Cookies. If a hidden "transfer money" Form on an attacker's site gets sent along with my bank Cookie, the bank thinks I sent it.
4. **Preventing CSRF**: Require an unpredictable **CSRF Token** with every request, add the **SameSite** attribute to Cookies (so Cookies aren't sent with requests from other sites), check the Origin Header, and ask for the password again for important actions like transfers.
KEY: In one line: **XSS happens because the site trusts user input**, and **CSRF happens because the site trusts the Browser (its Cookies)**.
END: If my Script runs in someone else's Browser, it's XSS (prevent with Escaping); if someone else's Browser secretly sends requests, it's CSRF (prevent with Tokens·SameSite).

#### CORS and the Same-Origin Policy (Revisited)
ONE: The Browser stops Scripts from reading responses from other origins (**Same-Origin Policy**) and lifts the block when the Server sends a permission Header (**CORS**). It's a security feature, not an error.
LIKE: The Browser is a security guard who says, "Items from another store are accepted only if that store has given permission."
STEP:
1. **Origin** = Scheme (Protocol) + Host + Port. If any one of the three differs, it's a different Origin.
2. Without the Same-Origin Policy, a Script on a malicious site I visit could call a bank API with my login and read the response.
3. **CORS**: When the Server says "this Origin is allowed" with the `Access-Control-Allow-Origin` Header, the Browser passes the response along.
4. For requests that change data and the like, the Browser first checks permission with an `OPTIONS` request (**Preflight**).
5. The place to fix a CORS error is **the configuration of the Server that responds** (covered in detail in topic 04).
END: Other origins are blocked by default (SOP), and pass through when the Server permits it (CORS).

#### The Principle of Least Privilege
ONE: The principle of giving people·programs·service accounts **only the minimum permissions they truly need to do their job**.
LIKE: You give the cleaning staff only the key to the supply closet, not the key to the safe. If the key is lost, the damage stops at the closet.
STEP:
1. Give the DB account of a read-only service only SELECT permission. Even if it's hacked, data can't be deleted or changed.
2. Employees get access only to the systems their work requires.
3. Admin rights are taken only briefly when needed and then given back.
4. This way, even if a hack or mistake happens, the range the damage spreads to (**Blast Radius**) stays small.
USE: Setting cloud IAM permissions, separating DB accounts, running containers as a regular user instead of root, and having apps request only the permissions they truly need (location, camera).
END: Give out only the keys that are needed, and losing a key does little damage.

### What is the difference between Hashing and Encryption? How do you store passwords?
E: Encryption is a safe with a lock, so you can reverse it if you have the key, and a Hash is a blender, so you can't turn juice back into fruit. But the same fruit always makes the same juice, so you can check "was this juice made from apples?"
A: Encryption is a two-way transformation you can Decrypt again with the Key, and a Hash is an irreversible One-Way transformation that turns input of any length into a fixed-length value. Passwords don't need the original, so they're stored as Hashes, with a Salt (a random value different for each user) attached to block attacks using precomputed Hash tables (Rainbow Tables), and with deliberately slow functions like bcrypt·scrypt·Argon2 instead of fast Hashes like SHA-256, to make Brute Force hard.

### What are Symmetric Key·Public Key Encryption, Digital Signatures, and Certificates?
E: A Public Key is the mail slot anyone can drop letters into, and a Private Key is the mailbox key only the owner has. A Digital Signature is the reverse: a signature only the owner can make, which anyone can compare against a sample, and a Certificate is a document in which a notary (CA) vouches that "this signature really belongs to this person."
A: A Symmetric Key Encrypts·Decrypts with the same Key, which is fast but makes sharing the Key safely hard (AES), and Public Key encryption encrypts with the Public Key and decrypts only with the Private Key, solving the Key Exchange problem but slowly (RSA, ECC). A Digital Signature signs the message's Hash with the Private Key and is verified with the Public Key to confirm the sender and whether it was tampered with, and a Certificate is a document in which a CA (Certificate Authority) signs that "this Public Key belongs to this Domain." HTTPS confirms the Server with a Certificate and, after Key Exchange, encrypts data with a Symmetric Key (see 04 Network).

### What are XSS and CSRF, and how do you prevent them?
E: XSS is posting a spell on a message board that says "the moment you read this, give me your wallet," so the reader's Browser carries it out, and CSRF is getting a logged-in person to click a disguised link so a transfer request goes out in their name.
A: XSS (Cross-Site Scripting) is an attack where a Script inserted by an attacker runs in another user's Browser and steals Cookies·Sessions; it's prevented with HTML Escaping on output, CSP (Content Security Policy), and HttpOnly Cookies. CSRF (Cross-Site Request Forgery) is an attack that exploits the Browser automatically sending Cookies to make a logged-in user send requests they didn't intend; it's prevented with CSRF Tokens, SameSite Cookies, Origin Header checks, and re-authentication for important actions. In short, XSS happens because the site trusts input, and CSRF happens because the site trusts the Browser.

### What is CORS?
A: For security, the Browser applies the Same-Origin Policy, which lets Scripts read responses only from the same Origin, where Scheme (Protocol)·Host·Port all match. CORS is the mechanism by which the Server safely permits requests from other Origins by announcing "this Origin is allowed" with Headers like Access-Control-Allow-Origin, and for certain requests the Browser first checks permission with an OPTIONS Preflight before the actual request.

### What is the Principle of Least Privilege?
A: It's the principle of giving users·programs·Service Accounts only the minimum permissions they truly need to do their work. For example, giving the DB account of a read-only service only SELECT permission shrinks the range of damage (Blast Radius) if a hack or mistake happens.

## System Design

#### Talking About Load and Performance in Numbers: Percentiles and Tail Latency
ONE: A service's load is described with **concrete numbers like requests per second**, and response speed with **Percentiles (p50, p99), not averages**. That's because the experience of the slowest users dominates the whole.
LIKE: Even if the class average is 80, a few students might have scored 30. Response times are the same: even if the average is fast, some users may wait a very long time. p99 shows how long "the unluckiest 1% of users" wait.
STEP:
1. **Load in numbers**: Requests per second (RPS, QPS), read:write ratio, number of concurrent users, amount of stored data.
2. **The trap of averages**: Even if most requests take 0.1 seconds and some occasionally take 10 seconds, the average can look fine.
3. **Percentile**: A position when response times are lined up in order. **p50 (the median)** is a typical user, **p99** is the slowest 1 in 100, and **p999** is the experience of the slowest 1 in 1,000.
4. **Tail Latency amplification**: If one request calls several Servers in the background at the same time, the whole thing is slow if **even one** of them is slow. The more Servers, the higher the chance that "one of them will be slow," so tail latency dominates what users feel.
5. That's why goals are set in Percentiles, like "p99 response under 300 ms," and Monitored (**SLOs**).
KEY: Users who make many requests (e.g., VIP customers with big shopping carts) are more likely to hit slow requests, so improving p99 often improves the experience of your most important customers.
END: Describe load with concrete numbers and speed with p50·p99 instead of averages. The slowest tail decides how it feels.

#### Scale-Up vs Scale-Out
ONE: When load grows, you either **upgrade one Server (Scale-Up)** or **add more Servers (Scale-Out)**.
LIKE: When customers increase, replacing one cook with a faster one is Scale-Up, and hiring several more cooks is Scale-Out.
STEP:
1. **Scale-Up (Vertical Scaling)**: Swap in a better CPU, Memory, and Disk. No need to change the code or structure, so it's simple.
2. Limits of Scale-Up: Even the biggest Server you can buy has limits, it gets expensive, and if that one machine dies, the whole service stops (SPOF).
3. **Scale-Out (Horizontal Scaling)**: Run several identical Servers and split requests among them up front. In theory you can keep adding, and if one dies, the rest hold up.
4. Requirements for Scale-Out: You need a **Load Balancer** to split requests, and the Servers must not hold state (**Stateless**) so that any Server gives the same result. Sessions go in a shared store like Redis.
5. **Scaling Out a DB is hard**: It's the place that holds the state (data) itself, so it needs complex methods like Replication and Sharding (topic 09).
END: Growing one machine is Scale-Up (simple, but limited); adding more machines is Scale-Out (unlimited growth, needs Stateless).

#### Load Balancers (Revisited)
ONE: The attendant that **splits** requests across several Servers and **automatically removes** dead Servers. It's an essential part of Scale-Out.
LIKE: It's like the host at a busy restaurant guiding guests to open tables and not seating anyone at a broken table.
STEP:
1. Users connect only to the Load Balancer's address. They don't need to know how many Servers are behind it.
2. **Health Checks** periodically confirm whether Servers are alive, and nothing is sent to dead Servers.
3. **Distribution methods**: Round Robin (in turn), Least Connections (to the one with the fewest connections), IP Hash (the same user to the same Server).
4. **L4** splits quickly by looking only at IP·Port, and **L7** splits smartly by also looking at the URL·Headers·Cookies, like sending `/api` to A and `/images` to B (topic 04).
5. A single Load Balancer is itself a SPOF, so it's made redundant.
END: A Load Balancer is the attendant that splits requests and removes dead Servers. It's made redundant too.

#### Caching Strategies and CDNs
ONE: A **Cache** **copies frequently read data to a fast place**, and a **CDN** **copies files like photos·videos to places close to users**.
LIKE: Keeping frequently used seasonings next to the stove instead of in the pantry is a Cache, and putting distribution warehouses all over the country to ship from the closest one is a CDN.
STEP:
1. **Cache-Aside (most common)**: The app checks the Cache first. If it's there (Hit), it uses it right away; if not (Miss), it reads from the DB and puts it in the Cache.
2. **Write-Through**: When writing, write to the Cache and the DB together. They always match, but writes are slow.
3. **Write-Back**: Write to the Cache first and batch-write to the DB later. Fast, but data can be lost if the Cache dies.
4. **The hard part of caching**: When the original changes, the Cache still holds the old value. So the key is the policy of setting an expiration time (**TTL**) and deleting the Cache when the original changes (**Invalidation**).
5. **CDN (Content Delivery Network)**: Copies Static files like images, videos, and JS to **Edge Servers** around the world. A user in Chicago gets them from a Server near Chicago, which is fast, and the load on the original Server (Origin) drops.
KEY: As the famous joke goes, "There are only two hard things in computer science: cache invalidation and naming things." When using a Cache, first decide "how stale can the data be?"
END: Keep frequently read data close with a Cache and heavy files close with a CDN. The core challenge is when to refresh (TTL, Invalidation).

#### Message Queues and Message Brokers
ONE: A **Message Queue** is an in-between store where messages put in by the sender are taken out and processed by the receiver **later, at its own pace**. It loosely connects services and absorbs bursts of requests.
LIKE: It's a restaurant's order ticket rail. The server pins up an order and immediately goes to the next customer, and the kitchen works through them one at a time at its own pace.
STEP:
1. The **Producer** puts messages in, and the **Consumer** takes them out and processes them. The two don't need to know about each other directly (**Decoupling**).
2. **Asynchronous processing**: Slow work like sending a welcome email after signup or converting an uploaded image goes into the Queue, and the user gets a response right away.
3. **Shock absorber**: Even if requests suddenly flood in, the Queue holds them and the Consumer works through them steadily, so the service doesn't collapse.
4. **Two kinds of Broker**: **Traditional Queues** that delete messages once processed (RabbitMQ, etc., good for distributing work), and **Log-based Brokers** that keep messages in order in a Log, with several Consumers each remembering where they've read up to (Kafka, etc., good for rereading and ordering guarantees).
5. **Watch out**: Network problems can deliver the same message twice. So processing must give the same result even if the same message is handled twice (**Idempotency**). Example: check by order ID whether it's already been processed.
END: A Message Queue is an order ticket rail. It loosely connects services, defers slow work, and absorbs surges. Make it Idempotent to guard against duplicate processing.

#### Availability and SPOFs
ONE: **Availability** is **the fraction of time a system works normally**, and a **SPOF (Single Point of Failure)** is a part that **takes everything down if it alone dies**.
LIKE: An island with only one bridge is cut off if that bridge collapses (SPOF). Build two bridges and you can still get across if one falls (redundancy).
STEP:
1. **A feel for Availability numbers**: 99.9% means it can be down up to about 8.8 hours a year, and 99.99% about 53 minutes. Each extra 9 cuts the allowed downtime to a tenth.
2. **Finding SPOFs**: Look for places where "if this dies, it's over," like a single Server, a single DB, a single Load Balancer, or a single datacenter.
3. **Redundancy**: Have two or more of anything that plays the same role.
4. **Automatic Failover**: When the primary dies, switch to the backup automatically. If a person has to wake up at night to switch it, it's too slow.
5. **Geographic distribution**: Spread across several Availability Zones (independent datacenters) or regions to survive power outages·fires.
KEY: Every extra 9 raises the cost sharply. Decide the level of availability the service really needs and invest only that much.
END: Availability is "how rarely it stops," and you remove SPOFs with redundancy and automatic failover.

#### The 5 Steps of a System Design Interview
ONE: A System Design interview isn't about getting the right answer; it's about seeing the process of **clarifying requirements, estimating scale, drawing the big picture, digging deep into the core, and discussing bottlenecks and Trade-offs**.
LIKE: It's like an architect designing a house: first asking "How many people will live here? What's the budget?", settling on a rough size, drawing the floor plan, designing the important parts (kitchen, stairs) in detail, and then checking for weaknesses (leaks, fire).
STEP:
1. **Clarify requirements**: What are the core features? How many users? What's the read-to-write ratio? How fast must it be? Don't start drawing right away; ask questions first.
2. **Estimate scale (Back-of-the-Envelope)**: Roughly calculate requests per second, storage, and bandwidth. Example: 100 million requests a day ≈ about 1,200 per second.
3. **The big picture (High-Level Design)**: Client → Load Balancer → Application Server → Cache → DB, plus a Message Queue·CDN if needed. Draw the whole flow with boxes and arrows.
4. **Dig deep into the core**: Design the heart of this service in detail: the data model (Table design), the Sharding Key, Replication, how to invalidate the Cache, and so on.
5. **Bottlenecks and failures**: Are there SPOFs? Hot Spots? What if traffic grows 10x? Talk about the alternatives and Trade-offs for each choice.
KEY: Don't try to draw a perfect design from the start; begin with a simple version and show how you'd improve it step by step as you find where it chokes at larger scale. What the interviewer is watching is your thought process.
END: Requirements → scale estimate → big picture → core in depth → bottlenecks and Trade-offs. Design while asking questions and talking.

#### Example: Designing a URL Shortener
ONE: A service that turns a long URL into **a short code**. It converts a unique ID to **Base62**, and since reads far outnumber writes, it leans heavily on a **Cache**.
LIKE: It's like a library putting a short call number on a book instead of its long title. Know the call number and you can find the book right away.
STEP:
1. **Requirements**: Take a long URL and make a short URL; when someone visits the short URL, send them to the original. Reads far outnumber writes (Read-Heavy).
2. **Making short codes**: Issue a unique ID (1, 2, 3, …) for each new URL and convert it to **Base62** (0-9, a-z, A-Z, 62 characters in all). With 7 characters, you can make 62⁷ ≈ 3.5 trillion codes.
3. **Storage**: Store "code → original URL" in the DB.
4. **Lookups**: Cache frequently used codes in Redis to respond right away without going to the DB.
5. **Redirect**: With **301** (moved permanently), the Browser remembers it, so Server load is low; with **302** (moved temporarily), every visit goes through the Server, so you can collect click statistics. Choose based on your goal.
6. **Scaling**: As traffic grows, Scale Out the Application Servers and Shard the DB by code. Unique IDs are issued so multiple Servers don't overlap, for example by having each grab a range of IDs in advance.
END: ID → Base62 → store → Cache → Redirect. It's Read-Heavy, so the Cache is the key.

### What is the difference between Scale-Up and Scale-Out?
E: When customers increase, replacing one cook with a faster one is Scale-Up, and hiring several more cooks is Scale-Out.
A: Scale-Up (Vertical Scaling) grows a Server's CPU·Memory; there's no structural change, so it's simple, but it hits Hardware limits and that Server becomes a SPOF. Scale-Out (Horizontal Scaling) increases the number of Servers; it has fewer limits in theory and is resilient to failure, but needs a Load Balancer and a design where Servers hold no state (Sessions, etc.) (Stateless).

### What is a Load Balancer? What is the difference between L4 and L7?
A: A Load Balancer splits incoming requests across several Servers and removes dead Servers via Health Checks, improving load distribution and Availability. Distribution methods include Round Robin, which takes turns; Least Connections, which sends to the Server with the fewest connections; and IP Hash, which pins a Client IP to a Server. L4 splits quickly by looking only at IP·Port, and L7 can split precisely by looking at HTTP content like the URL·Headers·Cookies, such as sending /api to Server A and /images to Server B.

### What are caching strategies and CDNs?
E: Keeping frequently used seasonings next to the stove instead of in the pantry is a Cache, and putting distribution warehouses all over the country to ship from the closest one is a CDN.
A: The most common, Cache-Aside, has the app check the Cache first and, if it's missing (Cache Miss), read from the DB and put it in the Cache; Write-Through writes to the Cache and DB together; and Write-Back writes to the Cache first and batch-writes to the DB later, but risks data loss on failure. A Cache can drift from the original, so TTL (Time To Live, expiration time) and Invalidation policies are key. A CDN (Content Delivery Network) copies Static Content like images·videos·JS to Edge Servers close to users, reducing Latency and Origin Server load.

### Why use a Message Queue?
E: It's a restaurant's order ticket rail. The server pins up an order and immediately goes to the next customer, and the kitchen works through them one at a time at its own pace.
A: A Message Queue (Kafka, RabbitMQ) is an in-between store where Messages put in by a Producer are taken out and processed later by a Consumer. It loosens coupling between Services (Decoupling), runs slow work like sending emails·converting images Asynchronously, and holds sudden floods of requests like a Buffer so the service doesn't collapse. In exchange, Message duplication·ordering issues must be considered, and processing must give the same result even if the same Message is handled twice (Idempotency).

### What are Availability and a SPOF (Single Point of Failure)?
A: Availability is the fraction of time a system works normally; 99.9% means it can be down up to about 8.8 hours a year, and 99.99% about 53 minutes. A SPOF is a component whose failure alone stops everything, and it's removed by making Servers·DBs·Load Balancers redundant (Redundancy), with automatic Failover and deployment spread across several Availability Zones.

### Design a URL shortening service.
A: When a long URL comes in, issue a unique ID, Encode it in Base62 (0-9, a-z, A-Z) to make a short code, and store "code → original URL" in the DB. With 7 characters, 62⁷ ≈ 3.5 trillion codes are possible, and since reads far outnumber writes (Read-Heavy), frequently used codes are Cached in Redis. When a user arrives via the short link, Redirect with 301 (permanent; the Browser remembers it, so Server load is low) or 302 (temporary; every visit goes through the Server, so click statistics can be collected), and as Traffic grows, Scale Out the Servers and Shard the DB by code.

E: Just as a class with an average of 80 can still have a student who scored 30, even with a fast average response time, some users may wait a very long time.
A: Averages hide a small number of very slow requests, so response times are sorted and viewed as Percentiles. p50 is a typical user, and p99·p999 are the experience of the slowest 1%·0.1% of users. Because of Tail Latency Amplification, where one request calling several Backends is slow if even one of them is slow, tail latency dominates perceived performance, so SLOs are set as Percentiles, like "p99 under 300 ms," and Monitored.

### In what order does a System Design interview proceed?
E: It's the order of an architect who first asks "How many people will live here?", then settles on the size, draws the floor plan, designs the important parts in detail, and checks for weaknesses.
A: First, clarify requirements through questions, like features·number of users·read/write ratio·latency targets, and roughly estimate requests per second·storage·bandwidth. Then draw a High-Level Design with the Client, Load Balancer, Services, Cache, DB, and Queue, design the core in depth, like the data model·Sharding Key·Replication·Cache invalidation, and explain the bottlenecks in cases like SPOFs·Hot Spots·10x traffic along with the Trade-offs of the alternatives.

## Distributed Systems and Data Processing

#### Problems That Arise in Distributed Systems
ONE: In distributed systems, where many computers cooperate over a Network, **messages can vanish or arrive late**, **clocks can disagree with each other**, and **programs can suddenly pause and wake up again**. So you can't trust the judgment of any single computer.
LIKE: Imagine making plans with faraway friends using only letters. Letters get lost or arrive late, everyone's clock is off by a few minutes, and someone might doze off briefly, wake up, and believe a plan that's already over is still on.
STEP:
1. **Network problems**: Messages can vanish, arrive late, or arrive twice. When there's no reply, you **can't tell whether the other side is dead or just slow**. A Timeout is only a guess.
2. **Clock problems**: Each computer's clock drifts a little, and time synchronization can even make it **jump backward**. Ordering things by clock, as in "whatever was written at the later time is the latest," can lose data.
3. **Fix: logical clocks**: Instead of real time, order events with a number that increases with each event (**Lamport Timestamp**), or use a clock whose error range is known, like Google Spanner's.
4. **Process pauses**: If a process freezes for a few seconds due to Garbage Collection or the like and then wakes up, it may act as if it's still the Leader even though another Node became the new Leader in the meantime.
5. **Fix: Fencing Tokens**: Each time a node becomes Leader it gets a number that goes up by 1, and the storage rejects requests with a number smaller than one it's already seen. Writes from the old Leader that woke up are blocked.
6. **Truth by majority**: A single Node can't even be sure it's alive. That's why important decisions are made by **majority (Quorum)** agreement.
END: In distributed systems, assume the Network·clocks·processes are all untrustworthy, and respond with logical clocks·Fencing Tokens·majority votes.

#### Consistency Models and Consensus
ONE: A **Consistency Model** is the promise about **how much multiple replicas should look "like one"** to users, and **Consensus** is the problem of several Nodes **agreeing on a single value**. Raft and Paxos are the best-known consensus Algorithms.
LIKE: When classmates choose a field trip destination, the rule that a decision is made once a majority agrees, even if some can't be reached, is Consensus. And once a destination is decided, friends who get in touch later have to go along with it.
STEP:
1. **Linearizability**: The strongest promise, making multiple replicas look **as if there is only one copy**. From the moment someone changes a value, everyone sees the new value. It's needed for Leader election, Locks, and preventing duplicates (uniqueness constraints).
2. When the Network splits, you have to give up either linearizability or availability (the core of CAP, topic 09).
3. **Causal Consistency**: A weaker promise that only keeps cause-and-effect order. It keeps "reply after the original post" but doesn't guarantee the order of unrelated things. In exchange, it can stay available even when the Network splits.
4. **Consensus**: The problem of several Nodes agreeing on one value (who the Leader is, whether to COMMIT this Transaction). **Raft**, **Paxos**, and **Zab** are the classic Algorithms, and they make progress only while **a majority of Nodes are alive**. With 5 machines, 3 alive is enough.
5. **2PC (Two-Phase Commit)**: A way to COMMIT a Transaction spanning several DBs atomically. The coordinator asks "Are you ready?" (Prepare), and if everyone says "yes," it sends "COMMIT." But if the coordinator dies midway, the participants can wait indefinitely while holding Locks.
6. In practice, you don't implement consensus yourself; you leave it to coordination services like **ZooKeeper** and **etcd**. Kubernetes also uses etcd (Raft).
END: The strongest consistency is "looking like one (linearizability)," and consensus is "decided once a majority agrees." Don't build it yourself; use proven tools.

#### Batch Processing
ONE: A processing style that reads **a fixed-size set of data all at once** to produce results and **leaves the input untouched**. If there's a bug, you fix it and **just run it again**.
LIKE: It's like gathering up all the receipts piled up during the day and reconciling them at night in one go. If the math was wrong, the receipts (input) are still there, so you just recompute.
STEP:
1. **Source data and derived data**: There are source records (the source of truth), and **derived data** like Caches·search Indexes·aggregate Tables·recommendation Models can be rebuilt from the source at any time. Batch and Stream are the ways derived data gets built.
2. **MapReduce**: Extract (Key, Value) pairs from each record (**Map**), gather and sort records with the same Key together (**Shuffle**), and process each Key (**Reduce**). Example: counting how many times each word appears across all documents.
3. MapReduce writes intermediate results to Disk at every stage, so it's slow, but it's robust because on failure only that stage needs to be redone.
4. **Dataflow engines (Spark, Flink)**: Bundle several stages into one job Graph and keep intermediate results in Memory, so they're much faster.
5. **Large-scale JOINs**: Sort both sides by the same Key and merge them (Sort-Merge Join), or copy the small side to every worker and match it against the big side (Broadcast Hash Join).
6. **The biggest advantage**: Since the input doesn't change, if there's a bug in the code you can fix it and run it again.
USE: Nightly sales reconciliation, retraining recommendation Models, rebuilding search Indexes, log analysis reports.
END: Batch = process accumulated data all at once, leaving the input as is. The biggest advantage is that if it's wrong, you just rerun it.

#### Stream Processing and Idempotency
ONE: A style that processes **never-ending data as it arrives**. It can react in real time, but has to handle late-arriving data and duplicate processing.
LIKE: If Batch is reconciling a day's receipts at night, Stream is updating the ledger on the spot every time a payment happens.
STEP:
1. **Process events as soon as they arrive**: Receive and process clicks, payments, and sensor data in real time. A Message Broker (Kafka, etc.) delivers the events.
2. **CDC (Change Data Capture)**: Streams the DB's change Log to automatically keep search Indexes·Caches·Data Warehouses in sync. If the app writes directly to several systems separately (Dual Write), ordering easily gets tangled, so CDC is safer.
3. **Event Sourcing**: Instead of the current state, store the list of events of "what happened," and build the state by replaying the events from the beginning. Every change is kept as a record, like a bank's transaction history.
4. **The time problem**: The time an event happened and the time it was processed differ. Some events are sent late by a phone that was offline. So you need a policy for "when to close a 5-minute aggregation window."
5. **Exactly-Once processing**: What it really means is "even with retries, the result is **the same as processing it once**." It's achieved with Checkpoints, committing in small batches, and **Idempotent writes**.
6. **Idempotency**: The property that receiving the same request several times gives the same result as receiving it once. Example: attach a unique ID to each request and ignore IDs that have already been processed.
KEY: Integrity (data doesn't get corrupted) is never negotiable, but timeliness (immediate reflection) is often fine a few seconds late. Separating the two lets you build correct systems without heavy distributed Transactions.
END: Stream processes data as soon as it arrives, and is made Idempotent to handle late events and duplicates.

#### Encoding and Schema Evolution
ONE: Data is **turned from Objects in Memory into Bytes (Encoding)** to travel across Disks or Networks. Systems aren't updated all at once, so Schemas must evolve so that **old code and new code can read each other's data**.
LIKE: When a company changes its form templates, new employees must be able to read the old forms too, and old employees who haven't been trained yet must be able to read the new forms by skipping the fields they don't recognize.
STEP:
1. **Encoding (Serialization)**: Turns Objects into Bytes. The reverse is Decoding.
2. **Backward Compatibility**: **New code** can read **old data**.
3. **Forward Compatibility**: **Old code** can read **new data**, ignoring fields it doesn't recognize.
4. Updating servers one at a time in turn (Rolling Update) means old and new versions run side by side for a while. So compatibility in both directions is needed.
5. **JSON·XML**: Easy for people to read, but large, and number precision is ambiguous.
6. **Protocol Buffers, Avro, Thrift**: Schema-based Binary formats. They're small and fast, and support evolution through field numbers or Schema comparison rules.
7. **Evolution rules**: Add new fields only as Optional, don't create new required fields, and never reuse the number of a deleted field.
KEY: Data flows by three paths: DBs (a message to your future self), Service calls (REST, RPC), and asynchronous Messages. RPC in particular looks like a function call, but it's fundamentally different because the Network can fail, be slow, and leave you not knowing the result.
END: Data flows as Bytes, and Schemas evolve by "add only optional fields, never reuse numbers" so that it stays readable even with old and new code mixed together.

### Why shouldn't you trust Clocks in a distributed system?
E: If friends decide "who arrived first" by their own wristwatches, the order can be wrong because the watches are off by a few minutes.
A: Each Node's physical clock drifts from the others (Clock Skew) and can suddenly jump backward because of NTP synchronization, so ordering events by Timestamp (e.g., Last Write Wins) can lose recent writes. That's why order·concurrency are judged with Logical Clocks like Lamport Timestamps, which increase with each event, or Version Vectors, and when a clock is truly needed, one with a known error range is used (e.g., Spanner TrueTime). Lease-based Leaders use Fencing Tokens to reject writes from an old Leader, guarding against Process Pauses.

### What is Consensus? How does Raft work?
E: It's the rule that when choosing a field trip destination, a decision is made once a majority agrees even if some can't be reached, and once decided, friends who get in touch later go along with it too.
A: Consensus is the problem of several Nodes agreeing on a single value (the Leader, Log order, whether to Commit) despite failures, and Leader election·atomic Commit·total order Broadcast are all equivalent to it. Raft elects a Leader by majority vote each Term, the Leader replicates Log Entries to Followers and Commits once a majority has stored them, and it makes progress as long as a majority of Nodes are alive. In practice, you don't implement it yourself; you use coordination services like etcd (Raft) or ZooKeeper (Zab).

### What is the difference between Batch Processing and Stream Processing?
E: Batch is reconciling a day's receipts at night all at once, and Stream is updating the ledger on the spot every time a payment happens.
A: Batch Processing reads a fixed-size input all at once to produce results and doesn't change the input, so bugs can be fixed and rerun, and throughput is high (MapReduce, Spark). Stream Processing handles never-ending events as they arrive, so latency is short, but it needs Window policies for late-arriving events and Exactly-Once processing (Idempotent Writes, Checkpoints) to prevent duplicates on failures·retries (Kafka, Flink). CDC is also used to stream DB changes and keep derived data in sync.

### What is Idempotency? Why does it matter?
E: Whether you press the elevator button once or ten times, the elevator comes only once. It's the property that doing something several times gives the same result as doing it once.
A: Idempotency is the property that processing the same request several times leaves the result (Server state) the same as processing it once. In distributed systems, clients retry when a Network failure means no response arrived, and Message Queues can deliver the same Message twice, so it's essential for preventing duplicate payments·duplicate orders. The typical approach is attaching a unique ID (Idempotency Key) to each request and ignoring IDs already processed; in HTTP, GET·PUT·DELETE are Idempotent and POST is not.

### What are Backward Compatibility and Forward Compatibility?
E: When a company changes its form templates, new employees must be able to read the old forms (backward compatible), and old employees must be able to read the new forms by skipping fields they don't recognize (forward compatible).
A: Backward Compatibility means new code can read old data, and Forward Compatibility means old code can read new data while ignoring fields it doesn't recognize. During a Rolling Update, old and new versions run together, so both directions are needed, and in Schema-based Encodings like Protocol Buffers·Avro, they're maintained by the rules of adding new fields only as Optional, not creating new required fields, and never reusing field numbers.

## Operations Basics

#### Linux Commands and File Permissions
ONE: Most Servers run Linux, so you need to know **basic commands** and **file permissions (r·w·x)**. Permissions are expressed as numbers for **owner·group·others**.
LIKE: File permissions are like a building access badge. For the owner (Owner), the family (Group), and visitors (Others), you separately decide "can view (r), can modify (w), can run (x)."
STEP:
1. **Location·navigation·listing**: `pwd` (current location), `cd` (move), `ls -al` (detailed list including hidden files).
2. **Copy·move·delete**: `cp`, `mv`, `rm` (`-r` for a whole folder). `rm -rf` can't be undone, so be very careful.
3. **Viewing·searching contents**: `cat`, `less`, `tail -f logfile` (watch a log in real time), `grep "error" file` (find text).
4. **Processes**: `ps aux` (list running Processes), `top` (real-time resource usage), `kill PID` (terminate).
5. **Disk·Network**: `df -h` (free Disk space), `du -sh` (folder size), `curl` (HTTP requests), `ssh` (remote login).
6. **Permission numbers**: Add read r=4, write w=2, execute x=1. The order is Owner·Group·Others.
7. **755**: Owner rwx (4+2+1=7), Group r-x (4+1=5), Others r-x (5). Only the owner can modify, and anyone can read and run it. Common for Scripts and folders.
8. **644**: Owner rw- (6), everyone else r-- (4). Common for regular files.
KEY: `777`, which gives everyone every permission, is avoided for security. "It doesn't work, so let's just 777 it" is a dangerous habit.
END: Handle files·Processes·Disks with basic commands, and write permissions by adding r4·w2·x1 in owner·group·others order.

#### Containers (Docker) and VMs
ONE: A **VM** creates a **virtual computer, OS and all,** inside a computer, and a **Container** is a lightweight approach that **shares the Host OS's Kernel** and isolates only the Processes.
LIKE: VMs are like building several single-family houses on one plot of land. Each house has its own furnace·plumbing (OS). Containers are like an apartment building. The building's infrastructure (Kernel) is shared, and only the inside of each unit is independent.
STEP:
1. **VM (Virtual Machine)**: Puts a whole Guest OS on top of a Hypervisor. Isolation is strong, but each OS takes up Memory, so it's heavy and slow to start.
2. **Container**: Shares the Host OS's Kernel and separates Processes with Linux **Namespaces** (isolating them so they can't see each other) and **cgroups** (limiting CPU·Memory usage). It's light and starts in seconds.
3. **Image**: A bundle of the app plus the Libraries·settings it needs to run. The same Image runs the same way anywhere, reducing the "it works on my machine" problem.
4. **Docker**: The best-known tool for building and running Containers.
5. **Kubernetes**: An **Orchestration** tool that places large numbers of Containers across many Servers, restarts them when they die, and scales them up and down with load.
CON: Containers share the Kernel, so their isolation is weaker than VMs'. When security matters a great deal, VMs or stronger isolation technologies are used alongside them.
END: VMs isolate the whole OS (heavy and strong); Containers isolate while sharing the Kernel (light and fast). When there are many, manage them with Kubernetes.

#### Logging and Monitoring
ONE: A running service is observed through **Logs (what happened)**, **Metrics (state in numbers)**, and **Traces (where a request went)**, and when something goes wrong, you get an **Alert**.
LIKE: It's like checking speed and fuel on a car's dashboard (Metrics), replaying the moment of an accident on the dashcam (Logs), and checking where you've been on the GPS route history (Traces).
STEP:
1. **Log Levels**: Split by severity: DEBUG (detailed, for development) < INFO (normal flow) < WARN (not a problem yet, but watch out) < ERROR (a request failed) < FATAL/CRITICAL (the service can't continue).
2. Names vary a bit by Library. Log4j has TRACE at the very bottom, and Python logging uses WARNING·CRITICAL.
3. In production, usually only INFO and above are kept, to cut cost and noise. **Never put passwords·personal information in Logs.**
4. **Metrics**: Collect request counts, error rates, response times (p50, p99), and CPU·Memory usage as numbers over time and view them as graphs.
5. **Distributed Tracing**: In MSA, when one request passes through several Services, attaching the same Trace ID lets you trace where the time went.
6. **Alerts**: Set conditions like "error rate above 5%" to notify the person on call automatically. If they go off too often, people start ignoring them, so set only the ones that truly matter.
END: Logs are records of events, Metrics are a numeric dashboard, and Traces are route records. You need to look at all three together to find problems in production quickly.

### What are some commonly used Linux commands, and what does chmod 755 mean?
E: File permissions (Permissions) are like a building access badge. For the owner (Owner), the family (Group), and visitors (Others), you separately decide "can view, can modify, can run."
| What it does | Commands |
| Location·navigation·listing | pwd, cd, ls -al |
| Copy·move·delete | cp, mv, rm (-r for a whole folder) |
| Viewing·searching contents | cat, less, tail -f logfile, grep "error" file |
| Processes | ps aux, top, kill PID |
| Permissions·ownership | chmod, chown |
| Disk·Network | df -h, du -sh, curl, ssh |
A: Permissions are written as numbers adding read r=4, write w=2, execute x=1, in the order Owner·Group·Others. So 755 is Owner rwx (7), Group r-x (5), Others r-x (5): only the Owner can modify, and anyone can read and run it, which is common for Scripts and Directories. 777, which gives everyone everything, is avoided for security.

### What is the difference between Docker (Containers) and VMs (Virtual Machines)?
E: VMs are like building several single-family houses on one plot of land, so each house has its own furnace·plumbing (OS), and Containers are like an apartment building, where the building's infrastructure (Kernel) is shared and only the inside of each unit is independent.
A: A VM puts a whole Guest OS on top of a Hypervisor, so isolation is strong but it's heavy and slow to Boot. A Container shares the Host OS's Kernel while isolating Processes and limiting resources with Linux Namespaces and cgroups, so it's light and starts within seconds, and bundling the app and its runtime environment into an Image reduces the "it works on my machine" problem. In exchange, sharing the Kernel makes its isolation weaker than a VM's, and managing many Containers calls for an Orchestration tool like Kubernetes.

### How are Log Levels distinguished?
A: In general, severity increases in the order DEBUG (detailed info for development) < INFO (records of normal flow) < WARN (not a problem yet, but watch out) < ERROR (errors like failed requests) < FATAL/CRITICAL (errors the service can't continue past), and depending on the Library there's a TRACE level at the very bottom (Log4j) or the names are WARNING·CRITICAL (Python logging). Production usually keeps only INFO and above to cut cost and noise, and passwords·personal information are never put in Logs.
