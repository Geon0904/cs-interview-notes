## OOP (Object-Oriented Programming)

#### The 4 Characteristics of OOP
ONE: **OOP** builds a program as **a collaboration of Objects that each hold both data and behavior**. Its four core characteristics are **abstraction · encapsulation · inheritance · polymorphism**.
LIKE: Think of a car. The driver uses just the steering wheel and pedals without knowing what's inside the engine (abstraction), the engine is hidden under the hood (encapsulation), an electric car inherits the basics of a car (inheritance), and to the same command "accelerate," a gas car uses fuel while an electric car uses its battery (polymorphism).
STEP:
1. **Abstraction**: Model only the essentials of a complex thing that you need right now. A "member" of an online store only needs a name·address·order history, not height or blood type.
2. **Encapsulation**: Bundle data with the features that work on it into one Object, and hide the inside (Information Hiding). If the balance can't be changed directly but only through `deposit()` and `withdraw()`, invalid values can't get in.
3. **Inheritance**: A child Class inherits a parent Class's features to reuse and extend them.
4. **Polymorphism**: Each Object responds differently to the same Message (Method call). Calling `shape.area()` computes a circle's area for a circle and a rectangle's area for a rectangle.
5. Combined, these four shrink "how far a change in one place spreads," and make it easy to add new features without changing existing code.
| Characteristic | Meaning | What you gain |
| Abstraction | Model by exposing only the essentials | Hides complexity |
| Encapsulation | Bundle data and features, hide the inside | Blocks invalid access, internal changes don't affect the outside |
| Inheritance | Inherit the parent's features and extend them | Code reuse |
| Polymorphism | Different behavior per Object for the same call | Add new kinds without changing the calling code |
WHY: As programs grow, "I changed one place and something else broke" becomes the biggest problem. OOP reduces it by splitting responsibilities into Objects.
END: OOP = abstraction (only the essentials) + encapsulation (hiding) + inheritance (passing down) + polymorphism (same command, different behavior).

#### Overloading and Overriding
ONE: **Overloading** is having **several Methods with the same name that differ only in Parameters**, and **Overriding** is a child **redefining a parent's Method with the same shape**.
LIKE: Overloading is a cafe's "place order" accepting just a drink, or a drink and a coupon together. Overriding is headquarters having a recipe and a branch remaking it its own way.
STEP:
1. **Overloading**: In the same Class, have Methods with the same name but a different number or Type of Parameters, like `add(int a, int b)` and `add(int a, int b, int c)`.
2. In Java, which Method to call is decided at Compile time by looking at the Arguments.
3. **Overriding**: A child Class remakes the parent's Method with the same name·same Parameters.
4. Which Method gets called is decided at runtime by the actual Object's Type (**Dynamic Dispatch**). This is the basis of polymorphism.
5. **In Python**: Redefining a function with the same name keeps only the last one, so there is no Overloading. Instead, you get a similar effect with default Arguments or `functools.singledispatch`.
| Aspect | Overloading | Overriding |
| Where | Within the same Class | Between parent and child Classes |
| Shape | Same name, different Parameters | Same name·Parameters |
| When decided | At Compile time (Java) | At runtime |
END: Same name with different Parameters is Overloading; a child remaking the parent's version is Overriding.

#### Composition over Inheritance
ONE: Inheritance (is-a) ties you tightly to the parent, while **Composition (has-a)** holds another Object like a part and uses it, so **coupling is loose and parts are easy to swap**. Unless it is a true is-a, consider Composition first.
LIKE: Inheritance is a blood relationship: "I am a kind of car." Composition is a parts relationship: "I have an engine." You can't change your bloodline, but you can swap parts.
STEP:
1. **Problem ① with inheritance**: The child comes to rely on the parent's internal implementation. A small change to the parent's code can unexpectedly break the children (**Tight Coupling**).
2. **Problem ②**: The inheritance structure is fixed when you write the code and can't be changed at runtime.
3. **Problem ③**: You inherit every feature, even ones you don't need.
4. **Composition**: Hold another Object as a Field and use only that Object's public features (Interface). You don't need to know how it works inside (**Loose Coupling**).
5. You can even swap parts at runtime, like fitting an electric motor in a car instead of a gas engine.
```python
class Engine:
    def start(self): return "Vroom"

class Car:
    def __init__(self, engine):   # hold it as a part instead of inheriting
        self.engine = engine
    def drive(self):
        return self.engine.start()
```
KEY: Cases where "it's is-a in words but behaves differently," like a square inheriting from a rectangle, are especially dangerous (the Liskov principle in SOLID).
END: Bloodlines (inheritance) bind tightly; parts (Composition) can be swapped. When in doubt, use Composition.

#### Interfaces and Abstract Classes
ONE: An **Interface** is a list of promises about "**what it must be able to do**," and an **Abstract Class** is **an unfinished template with some common parts already built**.
LIKE: An Interface is a list of things you must be able to do, like "the items on a driving test." An Abstract Class is a template where the common parts are already built and you fill in the rest, like "a half-built house."
STEP:
1. **Interface (in Java)**: A list of Methods to implement (a Contract). It cannot have Instance Fields (state).
2. One Class can implement several Interfaces at once, like a duck that has both "can fly" and "can swim."
3. Since Java 8, you can also put default implementations in with `default` Methods.
4. **Abstract Class**: Can have state (Fields), constructors, and already-implemented Methods. Only some Methods are left as "the child must implement this."
5. A Class can inherit from only one Class (in Java), so you can have only one Abstract Class as a parent.
6. **How to choose**: "What it can do (an ability)" is an Interface; "what it is + sharing common code" is an Abstract Class.
| Aspect | Interface | Abstract Class |
| Meaning | What it can do (a role) | An unfinished common template |
| State (Fields) | None | Can have them |
| Multiple implementation | Several allowed | Inherit only one |
| When to use | Give the same ability to different kinds | Share common code among closely related kinds |
END: A list of abilities is an Interface; a half-built common template is an Abstract Class.

## SOLID and Dependency Injection

#### The SOLID Principles
ONE: **SOLID** is five principles for **object-oriented design that is easy to change**. The shared goal is "changing one place shouldn't break other places."
LIKE: Picture a well-run restaurant. The head chef's and cashier's jobs are separate (S), new dishes are just added to the menu (O), a substitute cook must make the same recipe exactly the same way (L), the servers aren't handed the cooking manual (I), and the owner relies on "a qualified cook," not a particular cook's name (D).
STEP:
1. **S · Single Responsibility**: A Class should have only one reason to change. If the order Class also calculates, sends emails, and saves to the DB, then even changing the email format means touching the order Class.
2. **O · Open-Closed**: Open for extension, closed for modification. Instead of editing an if-else every time a payment method is added, make it so you only need to add a new payment Class (using polymorphism).
3. **L · Liskov Substitution**: A child must work correctly when put in the parent's place. If a square inherits from a rectangle, "change only the width" also changes the height, breaking the parent's promise.
4. **I · Interface Segregation**: Split Interfaces small so nothing depends on Methods it doesn't use. Don't force a simple printer to implement fax·scan features.
5. **D · Dependency Inversion**: Depend on abstractions (Interfaces), not concrete Classes. If a service doesn't create `MySQLRepository` directly but relies on a `Repository` Interface, the service stays the same even if the DB changes.
| Principle | In one phrase | Violation example |
| S | One reason to change | The order Class also handles email·DB |
| O | Easy to add, no modifying | Editing an if-else for each payment method |
| L | A child must be able to stand in for the parent | Square ⊂ rectangle |
| I | Depend only on what you need | Forcing fax on a printer |
| D | Depend on abstractions, not concretions | The Service does new on a MySQL Class directly |
KEY: All of SOLID aims to **lower Coupling and raise Cohesion**. Rather than mechanically applying every principle, apply them first where things change often.
END: SOLID = one responsibility, extend by adding, substitutable children, small Interfaces, depend on abstractions. The purpose is "code that holds up under change."

#### DI (Dependency Injection) and IoC
ONE: **DI (Dependency Injection)** means an Object **receives the other Objects it needs from outside instead of creating them itself**, and handing control of creation and wiring to the outside like this is called **IoC (Inversion of Control)**.
LIKE: Instead of the cook going to the farm to get ingredients, the restaurant delivers ingredients to the kitchen. The cook just cooks, and even if the supplier changes, nothing about the cook changes.
STEP:
1. **Without DI**: Inside `OrderService`, you create it directly, like `self.repo = MySQLRepository()`. Then OrderService is tied tightly to MySQL.
2. **With DI**: Receive it through the constructor, like `OrderService(repo)`. OrderService only needs to know that "repo can save()."
3. Injection methods: through the constructor (Constructor Injection, most recommended), through a Setter, or into a Field.
4. **IoC**: Originally my code created and wired up the Objects it needed; now a Framework or outside code creates them and plugs them in for me. The direction of control is flipped, hence "inversion."
5. **Testing gets easier**: Inject a fake store (Mock) instead of a real DB, and you can Test OrderService without a DB.
```python
class OrderService:
    def __init__(self, repo):     # injected from outside
        self.repo = repo
    def place(self, order):
        self.repo.save(order)

service = OrderService(FakeRepository())   # inject a fake in Tests
```
USE: In Frameworks like Spring (Java), NestJS, and Angular, a DI Container creates Objects and injects them automatically.
END: DI = "don't create what you need; receive it and use it." It produces code that is easy to change and easy to Test.

Depending on Interfaces and receiving implementations by injection makes implementations easy to swap and makes it easy to plug in fake Objects (Mocks) for Tests. ## Design Patterns

#### What Is a Design Pattern? The Three Categories
ONE: A **Design Pattern** is a named, **proven solution to a problem that keeps coming up** in design. They split into how to create (creational), how to combine (structural), and how to collaborate (behavioral).
LIKE: Architecture has proven solutions like "this is how you do an entryway, this is how you do stairs." Code also has proven design approaches for common problems. And just saying a Pattern's name becomes a shared language that colleagues immediately understand.
STEP:
1. A Design Pattern is not finished code but a design idea: "in this situation, use this structure."
2. Four authors known as the GoF (Gang of Four) catalogued 23 of them in a 1994 book.
3. **Creational**: How to create Objects. Singleton, Factory Method, Builder, and others.
4. **Structural**: How to combine Objects into larger structures. Adapter, Decorator, Composite, Proxy, and others.
5. **Behavioral**: How Objects divide responsibilities and communicate. Observer, Strategy, Template Method, and others.
WHY: Instead of rethinking the same problem every time, you can reuse a solution many people have proven. A single sentence like "let's use Observer here" conveys the design intent.
KEY: Forcing Patterns in actually makes things more complicated. The problem comes first, and a Pattern is used only when it fits that problem.
END: Design Patterns are proven solutions to recurring design problems and a shared language among developers.

#### Creational Patterns: Singleton · Factory Method · Builder
ONE: Patterns about **how to create** Objects: **create only one (Singleton)**, **let a subclass decide what to create (Factory Method)**, and **assemble step by step (Builder)**.
LIKE: Singleton is a country's one and only central bank, Factory Method is headquarters deciding only "make a burger" while each branch makes its regional burger, and Builder is choosing bread·cheese·sauce in turn at a sandwich shop to assemble your sandwich.
STEP:
1. **Singleton**: Creates exactly one Instance of a Class and lets it be used from anywhere. Used for resources that must exist only once, like settings, a Logger, or a Connection Pool.
2. Downsides of Singleton: It is effectively a global variable, so many places become invisibly tied together, and resetting its state for each Test is hard. In Multi-Thread code, the first creation also needs synchronization so two don't get made. That is why these days people prefer having a DI Container create just one and inject it.
3. **Factory Method**: Puts the Object-creating Method in its own place and lets a subclass decide which concrete Class to create. The caller doesn't need to know "what gets made."
4. **Builder**: Instead of building a complex Object with many options through one giant constructor, assemble it step by step, like `.bread("rye").cheese("cheddar").build()`. It reads better and reduces mistakes.
END: If there should be only one, Singleton; if deciding what to make is deferred, Factory Method; if it is complex, Builder.

#### Structural Patterns: Adapter · Decorator · Composite · Proxy
ONE: Patterns about **how to combine** Objects: **connect things that don't fit (Adapter)**, **add features on top (Decorator)**, **treat one and a group the same way (Composite)**, and **a stand-in controls access (Proxy)**.
LIKE: Adapter is a travel plug adapter for overseas trips, Decorator is adding milk·syrup to coffee, Composite is how both files and folders can "show size," and Proxy is a manager who takes bookings on behalf of a celebrity.
STEP:
1. **Adapter**: Puts a converter between two Objects whose Interfaces don't match. If an external payment Library's Method names differ from our code's, wrap it in an Adapter so we can use it our way.
2. **Decorator**: Wraps the original with **the same Interface** while adding features. It can be stacked in several layers. Example: coffee → add milk → add syrup, Java's `BufferedInputStream`.
3. **Composite**: Treats individual Objects and groups of them the same way (a Tree structure). A folder's size = the sum of the sizes of the files and folders inside it, and both can be called the same way with `size()`.
4. **Proxy**: A stand-in Object receives requests in place of the original and **controls access**. Loading only when needed (Lazy Loading), permission checks, caching results, hiding remote server calls.
5. **Decorator vs Proxy**: Both wrap with the same Interface, but Decorator's purpose is "adding features" and Proxy's purpose is "controlling access."
END: Connecting is Adapter, adding on is Decorator, Trees are Composite, and stand-ins are Proxy.

#### Behavioral Patterns: Observer · Strategy · Template Method
ONE: Patterns about **how Objects collaborate and divide responsibilities**: **automatic notification of changes (Observer)**, **swapping Algorithms (Strategy)**, and **fixing the order and changing only some steps (Template Method)**.
LIKE: Observer is subscribing on YouTube and getting new-video notifications, Strategy is choosing driving·walking·transit in a directions app, and Template Method is making pasta where the steps are the same and only the sauce differs.
STEP:
1. **Observer**: When one Object's (the Subject's) state changes, it automatically notifies the many Objects (Observers) subscribed to it. For example, when an order's status changes, email·text·app Push each get notified. It is the basic structure of event systems and UIs.
2. **Strategy**: Separates an Algorithm into its own Object and swaps it at runtime. Make discount policies (flat amount, percentage, free) into Strategy Objects and plug a different policy into each order. It uses Composition.
3. **Template Method**: The parent Class defines the overall order (boil water → add pasta → add sauce → done), and the child Class implements only some steps (the sauce). It uses Inheritance.
4. **Strategy vs Template Method**: Both change part of an Algorithm, but Template Method uses inheritance, so the structure is fixed when the code is written, while Strategy uses Composition, so it can be swapped out entirely at runtime.
END: Notifications are Observer, swapping is Strategy, and fixed order + changing only some steps is Template Method.

#### The MVC Pattern
ONE: A structure that splits a program into **data·logic (Model)**, **the screen (View)**, and **handling input and connecting the two (Controller)**.
LIKE: In a restaurant, the kitchen (Model) handles the cooking and ingredients, the table setting in the dining room (View) is what the customer sees, and the server (Controller) takes orders to the kitchen and brings the results to the table.
STEP:
1. **Model**: The data and business rules (Business Logic). Rules like "the balance can't go negative" live here.
2. **View**: The screen shown to the user. It only cares about how to display the data.
3. **Controller**: Takes user input (clicks, requests), updates the Model, and picks the View to show the result.
4. Because the screen and logic are separated, you can redesign the screen while the logic stays the same, and you don't need the screen to Test the logic.
5. Variants: **MVP** (a Presenter directly drives the View) and **MVVM** (the ViewModel and View sync automatically through data binding, widely used in mobile·Frontend).
USE: It is the basis of web Frameworks (Django calls it MTV but it's the same idea, Spring MVC, Ruby on Rails) and mobile app architecture.
END: MVC = data (Model) + screen (View) + connection (Controller). Splitting them lets you change and Test each separately.

### What is a Design Pattern? How are they classified?
E: Just as architecture has proven solutions like "this is how you do stairs in an apartment building, this is how you do an entryway," code has proven design approaches for common problems. It is also a shared language: just saying a Pattern's name lets colleagues immediately understand the structure.
A: A Design Pattern is a reusable solution to a problem that recurs in Software design. The GoF split them into Creational Patterns, which deal with how to create Objects; Structural Patterns, which combine Objects into larger structures; and Behavioral Patterns, which deal with the division of responsibility and interaction between Objects.
| Pattern | Category | One-line description | Everyday analogy |
| Singleton | Creational | Create only one Instance and use it everywhere | A country's one and only central bank |
| Factory Method | Creational | A Subclass decides which Object to create | Headquarters decides only "make a burger," and each branch makes its regional burger |
| Builder | Creational | Assemble a complex Object step by step | Choosing bread·cheese·sauce in turn at a sandwich shop |
| Adapter | Structural | Convert a mismatched Interface to connect it | A travel plug adapter for overseas trips |
| Decorator | Structural | Wrap with the same Interface to add features | Adding milk and syrup to coffee |
| Composite | Structural | Treat individual Objects and groups the same way (Tree) | Both files and folders can "show size" |
| Proxy | Structural | A stand-in Object controls access (Lazy Loading·permissions·Cache) | A manager who takes bookings on behalf of a celebrity |
| Observer | Behavioral | Automatically notify Subscribers when state changes | YouTube subscriptions and new-video notifications |
| Strategy | Behavioral | Separate an Algorithm into an Object and swap it at Runtime | Choosing driving·walking·transit in a directions app |
| Template Method | Behavioral | The Parent sets the overall order, the Child implements some steps | Making pasta: same steps, only the sauce differs |

### What are the pros and cons of the Singleton Pattern?
A: Singleton is a Pattern that creates only one Instance of a Class and provides a Global Access Point, saving Memory by sharing resources that must exist only once, like a DB Connection Pool·settings·Logger. But it is Global State, so many places become coupled in hidden ways, and resetting its state for each Test is hard. Also, in Multi-Thread code the first creation needs Synchronization so two don't get created at the same time, which is why these days people prefer having a DI Container create just one and inject it.

### What is the difference between the Strategy Pattern and the Template Method Pattern?
A: Both are Patterns for changing part of an Algorithm, but Template Method uses Inheritance: the Parent fixes the order and the Child fills in the steps, and the structure is decided at Compile time. The Strategy Pattern uses Composition and receives the Algorithm Object itself by injection, so it can be swapped out entirely even at Runtime.

### What is the difference between the Decorator Pattern and the Proxy Pattern?
A: Both wrap the original with the same Interface, but their purposes differ. Decorator's purpose is adding features, so it can be stacked in several layers (Java's BufferedInputStream), while Proxy's purpose is controlling access to the original (Lazy Loading, permission checks, Cache, remote calls).

### What is the MVC Pattern?
E: In a restaurant, the kitchen (Model) handles the cooking and ingredients, the table setting in the dining room (View) is what the customer sees, and the server (Controller) takes orders to the kitchen and brings the results to the table.
A: MVC is a structure that splits an Application into the Model, which handles Data and Business Logic; the View, which handles display; and the Controller, which takes user input, updates the Model, and picks the right View. Because the screen and Logic are separated, each is easy to change and Test separately, and similar variants include MVP·MVVM.

## Programming Paradigms

#### Imperative vs Declarative
ONE: **Imperative** gives step-by-step instructions on "**how**" to do something, and **Declarative** only says "**what**" you want.
LIKE: In a taxi, saying "turn left at the next intersection, go straight 200 feet, turn right at the light" step by step is imperative, and saying just your destination, "Union Station, please," is declarative.
STEP:
1. **Imperative**: Write commands that change state, in order. "Set variable sum to 0, then loop and add each one…". Loops in C and Java.
2. **Declarative**: Write the result you want and leave the method to the system. SQL (`SELECT ... WHERE ...`), HTML (a screen with this structure), CSS.
3. Python uses both. Summing with a loop is imperative, while `sum(x for x in nums if x > 0)` is closer to declarative.
4. **Functional Programming** is one branch of declarative programming.
PRO: Declarative code shows intent clearly, making it easy to read, and the system can pick a better method on its own (like a DB's execution plan).
CON: Declarative code makes fine-grained control hard, and sometimes you can't see what is happening inside.
END: Saying "how" is imperative; saying "what" is declarative.

#### Functional Programming
ONE: A way of building programs around pure functions that **always give the same output for the same input** and **don't change anything outside**, and around **data that can't be changed**.
LIKE: It is like a vending machine. Put in the same money and press the same button and you always get the same drink, and the machine doesn't secretly change anything else.
STEP:
1. **Pure Function**: The result depends only on the input, and it doesn't change outside state (global variables, files, the screen). Changing the outside is called a **Side Effect**.
2. **Immutable Data**: Instead of changing data, you create new, changed data.
3. **First-Class Function**: Functions are stored in variables, passed around, and returned like values.
4. **Higher-Order Function**: A function that takes or returns functions. `map` (transform everything), `filter` (pick some out), `reduce` (combine into one).
5. **Compared with OOP**: OOP manages complexity by hiding state inside Objects and changing it through Methods. FP manages complexity by reducing state changes in the first place.
PRO: Results are predictable, so Testing is easy, and since shared state isn't changed, there's less worry about Race Conditions in parallel processing.
CON: Constantly creating new data can use more Memory, and it can feel awkward for work where state change is the essence (UIs, games).
USE: In practice, languages like Python, JavaScript, and Kotlin mix OOP and FP. React's function components and data processing Pipelines are FP style.
END: FP = pure functions + immutable data + functions as values. Reducing side effects makes code predictable.

### What is the difference between Imperative and Declarative Programming?
E: In a taxi, saying "turn left at the next intersection, go straight 200 feet" step by step is Imperative, and saying just your destination, "Union Station, please," is Declarative.
A: Imperative writes state-changing commands in order to describe "how" (loops in C, Java), while Declarative describes the desired result, "what," and leaves the method to the system (SQL, HTML). Functional Programming is one branch of Declarative.

### What is Functional Programming? How does it compare with OOP?
E: Functional is like a vending machine. Put in the same money and button and you always get the same drink, and the machine doesn't secretly change anything else.
A: Functional Programming centers on Pure Functions, which always give the same output for the same input and don't change outside state, Immutable Data, and First-Class and Higher-Order Functions (map, filter, reduce) that pass Functions around like values. With few Side Effects, Testing·parallel processing are easy, whereas OOP manages complexity by hiding state inside Objects and changing it through Methods. In practice, languages like Python·Kotlin·JavaScript mix the two.

## Clean Code and Testing

#### Clean Code and Refactoring
ONE: **Clean Code** is **code that other people find easy to read and change**, and **Refactoring** is **improving only the internal structure while leaving what it does on the outside unchanged**.
LIKE: Refactoring is tidying up your house without moving. The furniture layout and storage change, but the address and what the house does stay the same.
STEP:
1. **Names that reveal intent**: `days_since_signup` instead of `d`. You should know what a value is just from its name.
2. **Small functions that do one thing**: If a function does just one thing, it is easy to understand and Test.
3. **Remove duplication (DRY, Don't Repeat Yourself)**: If the same code is copied in several places, it is easy to miss one when fixing it.
4. **Constants instead of Magic Numbers**: `ADULT_AGE = 18` instead of `if age >= 18`.
5. **Consistent Style**: Use team rules and an automatic Formatter.
6. **Refactoring**: Improve the structure while keeping the behavior the same. Splitting functions, renaming, merging duplicates.
7. **Tests must come first** for it to be safe. After Refactoring, run the Tests to confirm the behavior is unchanged.
WHY: Code is written once and read dozens of times. Hard-to-read code creates Bugs every time it's changed and takes twice as long.
END: Clean Code is easy-to-read code, and Refactoring is polishing the structure with Tests as a safety net.

#### Kinds of Tests and the Test Pyramid
ONE: Tests split by scope into **Unit (one part)**, **Integration (parts connected together)**, and **E2E (a whole user scenario)**, and the Test Pyramid says to have **the most fast, cheap Unit Tests**.
LIKE: It is like a car factory inspecting each bolt (Unit), connecting the engine and transmission and inspecting them (Integration), and test-driving the finished car on the road (E2E).
STEP:
1. **Unit Test**: Tests a single function or Class in isolation from everything else. It finishes in a few ms, so you can run thousands of them often.
2. **Integration Test**: Tests whether several Modules work correctly together, or when connected to a DB·external API.
3. **E2E (End-to-End) Test**: Drives a browser like a real user to test the whole flow, "sign up → log in → order." It is slow and expensive, and sometimes fails for trivial reasons (**Flaky**).
4. **Test Pyramid**: Wide at the bottom (Unit), narrow at the top (E2E). Catch most Bugs with fast Tests, and use slow Tests only to check core scenarios.
| Kind | Scope | Speed·cost | How many |
| Unit | One function·Class | Fast and cheap | The most |
| Integration | Several Modules, DB·external connections | Medium | Medium |
| E2E | A whole user scenario | Slow, expensive, and fragile | Few |
WHY: With Tests, when you change code you can automatically check "did something else break?" They are the safety net that lets you change things with confidence.
END: Parts are Unit, connections are Integration, and the whole is E2E. Stack them wide at the bottom and narrow at the top.

#### TDD (Test-Driven Development)
ONE: A way of developing that repeats a short cycle: **write a failing Test first (Red)**, **write just enough code to pass it (Green)**, and **clean up the code (Refactor)**.
LIKE: It is writing the scorecard first, "this dish must not be too salty and must be ready in 5 minutes," before you start cooking. With a scorecard, it becomes clear what you need to make.
STEP:
1. **Red**: First write a Test for a feature that doesn't exist yet. Naturally, it fails.
2. **Green**: Write the **minimum** code that makes that Test pass. It doesn't have to be pretty.
3. **Refactor**: Clean up the code while keeping the Test passing.
4. Move on to the next small feature and repeat from Red.
PRO: Requirements become clear as Tests, the code naturally becomes easy to Test, and Refactoring becomes safe.
CON: Initial development is slower, and if requirements change often and drastically, there's the cost of changing the Tests too.
END: TDD = repeating Red (a failing Test) → Green (passing) → Refactor (cleanup).

#### Test Doubles: Mock · Stub · Fake
ONE: A **fake Object** used in Tests in place of a real Object (DB, external API, mail server) is called a Test Double. If it just returns fixed values, it's a **Stub**; if it also verifies whether it was called, it's a **Mock**.
LIKE: It is a stand-in actor on a TV shoot. A Stub is a stand-in who only says fixed lines, and a Mock is a stand-in who says the lines while also recording "how many times and what the lead actor said to me," so the director can check.
STEP:
1. Testing with a real DB or payment API is slow, costs money, and can give different results each time. So you swap in fakes.
2. **Stub**: Returns a predetermined value when called. Decide "the exchange rate API always returns 1.08," then verify that your code's **result (state)** is correct.
3. **Mock**: Records and verifies "which Method was called with which Arguments, and how many times." It checks **Behavior**, like "when an order is placed, was sending the email called exactly once?"
4. **Fake**: A simple implementation that actually works. A fake DB that stores things in Memory instead of a real DB.
5. **Spy**: Works like the real thing while recording calls. **Dummy**: An Object that just fills a spot and is never actually used.
END: Just returning values is a Stub, verifying calls is a Mock, and a simple version that works like the real thing is a Fake.

### What are Clean Code and Refactoring?
E: Refactoring is tidying up your house without moving. The furniture layout and storage change, but the house's address and what it does stay the same.
A: Clean Code is code that other people find easy to read and change, with names that reveal intent, small Functions that do one thing, no duplication (DRY, Don't Repeat Yourself), constants instead of Magic Numbers, and a consistent Style. Refactoring is improving internal structure without changing external behavior, and it can be done safely only if there are Tests to confirm the behavior stays the same.

### What is the difference between Unit·Integration·E2E Tests, and what is the Test Pyramid?
E: It is like a car factory inspecting each bolt (Unit), connecting the engine and transmission and inspecting them (Integration), and test-driving the finished car on the road (E2E).
| Kind | Scope | Speed·cost | How many |
| Unit Test | One Function·Class | Fast and cheap | The most |
| Integration Test | Several Modules, connections to a DB·external API | Medium | Medium |
| E2E Test | A whole user scenario (driving a Browser) | Slow, expensive, and fragile (Flaky) | Few |
A: A Unit Test isolates and tests the smallest unit, an Integration Test checks whether several parts work together, and an E2E (End-to-End) Test checks whether the whole flow works from the user's point of view. The Test Pyramid is the guideline to have the most fast, cheap Unit Tests and the fewest slow, expensive E2E Tests.

### What is TDD? What are its pros and cons?
E: It is writing the scorecard first, "this dish must not be too salty and must be ready in 5 minutes," before you start cooking.
A: TDD (Test-Driven Development) repeats a short cycle: write a failing Test first (Red), write only the minimum code needed to pass it (Green), then clean up the code (Refactor). Requirements become clear, the code becomes easy to Test, and Refactoring becomes safe, but initial development is slower, and frequent requirement changes bring the cost of updating the Tests.

### What is the difference between a Mock and a Stub?
E: They are stand-in actors on a TV shoot. A Stub is a stand-in who only says fixed lines, and a Mock is a stand-in who says the lines while also recording "how many times and what the lead actor said to me," so the director can check.
A: Both are Test Doubles that stand in for real Objects in Tests. A Stub returns a predetermined value when called and is used to verify the result (State) of the code under Test, while a Mock verifies calls (Behavior), like "which Method was called with which Arguments, and how many times." Other kinds include a Fake, a simple implementation that actually works like an In-Memory DB; a Spy, which records calls; and a Dummy, which just fills a spot.

## Development Process and DevOps

#### Waterfall and Agile · Scrum
ONE: **Waterfall** does plan→design→build→Test **once each, in order**, and **Agile** **builds a little at a time in short cycles and gets feedback** to correct course. **Scrum** is Agile's best-known practice.
LIKE: Waterfall is like a wedding venue: finish the entire design, then build, then inspect after it is all built. Agile is like a food truck: open small, watch how customers react, and change the menu as you go.
STEP:
1. **Waterfall Model**: Requirements → design → implementation → Test → deployment in order, and you must finish one stage before moving to the next. Plans and documents are clear. But if problems are only discovered in the Test stage, going back is expensive.
2. **Agile**: A philosophy of "deliver working Software often, and respond to change." Every short cycle produces something actually usable and gets feedback.
3. **Scrum**: Agile's best-known Framework. It repeats **Sprints** of a month or less (usually 1–4 weeks).
4. **Scrum roles**: Product Owner (decides the priorities of what to build), Scrum Master (helps the process run well), Developers (actually build it).
5. **Scrum events**: Sprint Planning (what to do this time), Daily Scrum (a short daily sync), Sprint Review (demo the results and get feedback), Retrospective (reflect on how the team works).
WHY: Requirements inevitably change as you build. Checking in short cycles lets you correct a wrong direction early.
KEY: Waterfall isn't always bad. In fields where requirements are certain and hard to change (e.g., heavily regulated systems), it can still fit.
END: Planning big all at once is Waterfall; building small and often while adjusting is Agile. Scrum is a way to practice Agile with Sprints.

#### CI/CD and DevOps
ONE: **CI** is merging code often and **automatically Building·Testing every time you merge**, and **CD** is taking that result and **automatically making it ready to deploy (Delivery) or actually deploying it (Deployment)**. **DevOps** is a culture that ties development and operations together like one team.
LIKE: At a bakery, an automatic tester tastes the dough every time it's made (CI), and bread that passes is automatically packaged and put on the shelf (CD).
STEP:
1. **CI (Continuous Integration)**: Developers merge code into the Main Branch several times a day. Every merge automatically runs the Build and Tests, so problems are noticed right away.
2. Working separately for a long time and then merging everything at once makes conflicts and Bugs explode (Integration Hell). Merging often lets you fix problems while they're small.
3. **Continuous Delivery**: Automatically keeps code that passed the Tests in a state that can be deployed at any time. The actual production deployment is approved by a person pressing a button.
4. **Continuous Deployment**: Once Tests pass, it deploys all the way to production automatically, with no human approval.
5. **DevOps**: To end the problem of development (Dev) and operations (Ops) teams working separately and blaming each other, they share responsibility like one team and pursue fast, stable deployments through automation and Monitoring.
USE: Pipelines are built with tools like GitHub Actions, GitLab CI, and Jenkins.
END: CI is "merge often and check automatically," CD is "automatically ready to deploy (Delivery) or deployed (Deployment)," and DevOps is the culture that makes it possible.

### What are the Waterfall Model, Agile, and Scrum?
E: Waterfall is like a wedding venue: finish the entire design, then build, then inspect after it is all built. Agile is like a food truck: open small, watch how customers react, and change the menu as you go.
A: The Waterfall Model proceeds through requirements→design→implementation→Test→deployment in order, so plans and documents are clear, but changes discovered late are expensive. Agile is a philosophy of releasing working Software often in short cycles and correcting course through Feedback. Scrum is Agile's best-known Framework: it runs Sprints of a month or less (usually 1–4 weeks) with the roles Product Owner·Scrum Master·Developers and the events Sprint Planning·Daily Scrum·Sprint Review·Retrospective.

### What are CI/CD and DevOps?
E: At a bakery, an automatic tester tastes the dough every time it's made (CI), and bread that passes is automatically packaged and put on the shelf (CD).
A: CI (Continuous Integration) is developers merging code into the Main Branch often, with the Build and Tests run automatically on every merge to find problems quickly. CD has two meanings: Continuous Delivery automatically keeps things in a deployable state at all times while a person approves the Production deployment, and Continuous Deployment deploys all the way to production automatically once Tests pass. DevOps is a culture and approach that ties development (Dev) and operations (Ops) together like one team and pursues fast, stable deployments through automation·Monitoring.

## Git and Collaboration

#### Git's Three Areas and the Basic Flow
ONE: **Git** is a tool for managing the history of changes to code. It moves between three areas: the **Working Directory**, where you edit files; the **Staging Area**, where you gather what goes into the next save; and the **Repository**, where saved history piles up.
LIKE: You write at your desk (Working Directory), put only what you're sending into an envelope (Staging), seal the envelope and keep it in your drawer (Commit), and mail it at the post office (Remote Repository) (push).
STEP:
1. **Working Directory**: Where you actually edit files.
2. `git add file`: Puts only the changes you want in this save onto the **Staging Area**. Even if you edited many files, you can pick and bundle just the related ones.
3. `git commit -m "message"`: Saves the Staging Area's contents as one record (**Commit**) in the **Local Repository**. Each Commit gets a unique ID (Hash).
4. `git push`: Uploads your Commits to the **Remote Repository** (GitHub, etc.) to share with the team.
5. `git fetch`: Only downloads new changes from the Remote, without merging them into your work.
6. `git pull`: fetch + merge (or rebase, depending on settings). It downloads and merges into your work.
7. **Branch**: A fork in the history. New features are worked on in a separate Branch and merged into main when finished.
WHY: There's a record of who changed what, when, and why; you can go back to a previous state when something goes wrong; and many people can work on different parts at the same time.
END: Edit (Working) → pick and pack (add) → save (commit) → share (push).

#### merge vs rebase, reset vs revert
ONE: When combining two Branches, **merge** leaves the history as is and creates a joining point, while **rebase** re-attaches your Commits to the end of the other Branch to make a single line. When undoing, **reset** erases history, while **revert** adds a new, opposite Commit.
LIKE: merge is putting up a "merge point" sign where two roads meet, and rebase is lifting your whole road and reattaching it to the end of the other road to make one straight line.
STEP:
1. **merge**: Creates a Merge Commit that joins the two Branches. The record of who split off and rejoined, and when, stays intact.
2. **rebase**: Reapplies your Commits one by one onto the very end of the target Branch. The history becomes a clean straight line, but the reapplied Commits get **new Hashes**.
3. That's why **you don't rebase a Branch that's already been pushed and pulled by others**. Your teammates' history and yours fall out of sync, causing major confusion.
4. **reset**: Moves the point the Branch points to back to a past Commit. Commits after that disappear from the history. Used to clean up local work only you use.
5. **revert**: Creates a **new Commit** that undoes a specific Commit's contents. It doesn't erase history. When canceling a Commit that's already been shared, use revert.
| Aspect | Rewrites history? | On a shared Branch |
| merge | No (adds a joining point) | Safe |
| rebase | Rewrites (new Hashes) | Avoid |
| revert | No (adds an undo Commit) | Safe |
| reset | Rewrites (removes Commits) | Avoid |
KEY: Remember just one rule: **"Don't rewrite history you've shared with others."** That's why you use merge and revert where things are shared.
END: Preserving history is merge·revert; rewriting it is rebase·reset. Never rewrite shared history.

#### Branch Strategies and Pull Requests
ONE: The rules a team sets for how to split and merge Branches are the **Branch strategy**, and the process of requesting that your changes be merged while getting a **Code Review** is a **Pull Request (PR)**.
LIKE: It is like several authors writing a book together: each writes their own manuscript separately and asks the editor-in-chief to review it, saying "please put this chapter in."
STEP:
1. **Git Flow**: A structured strategy using main, develop, feature, release, and hotfix Branches. It fits products released as versions on a fixed schedule (apps, installed Software).
2. **GitHub Flow**: Keeps only main and short-lived Feature Branches. Merge through a PR and deploy right away. It fits web services that deploy often.
3. **Trunk-Based Development**: Everyone merges into main (the Trunk) very often in small pieces. Unfinished features are hidden with Feature Flags. It pairs well with CI/CD.
4. **Pull Request**: After pushing a Feature Branch, request "please merge this into main."
5. In a PR, colleagues read the code and leave comments (**Code Review**), and CI runs the Tests automatically. If it passes, it gets merged.
WHY: Code Review catches Bugs early and gives teammates a chance to understand and learn from each other's code.
END: With a fixed release schedule, Git Flow; with frequent deploys, GitHub Flow or Trunk-Based. When merging, get a Review through a PR.

### What are Git's three areas and the basic flow?
E: You write at your desk (Working Directory), put only what you're sending into an envelope (Staging), seal the envelope and keep it in your drawer (Commit), and mail it at the post office (Remote Repository) (push).
A: Git is divided into the Working Directory, where you modify files; the Staging Area (Index), which gathers changes for the next Commit; and the Local Repository, where Commits are stored. You Stage with `git add`, save with `git commit`, and upload to the Remote with `git push`; `git fetch` only downloads Remote changes, while `git pull` does fetch plus merge (or rebase, depending on settings).

### What is the difference between merge and rebase? And reset and revert?
E: merge is putting up a "merge point" sign where two roads meet, and rebase is lifting your whole road and reattaching it to the end of the other road to make one straight line.
A: merge creates a Merge Commit joining the two Branches and preserves the History as is, while rebase reapplies your Commits onto the end of the target Branch to make a straight-line history, but the Commit Hashes change. That's why you don't rebase a Branch that's already been pushed and is used by others. For the same reason, when canceling a shared Commit, you use revert, which creates a new Commit with the opposite contents, instead of reset, which moves the Branch Pointer back.

### What are Git Flow, GitHub Flow, and PRs?
A: Git Flow is a structured strategy with main, develop, feature, release, and hotfix Branches that fits products released as versions on a fixed schedule, and GitHub Flow is a simple strategy that keeps only main and short Feature Branches, merges through PRs, and deploys right away, fitting web services that deploy often. A PR (Pull Request) is the process of requesting that your Branch's changes be merged, going through Code Review and automated Tests.

## Architecture

#### What Is Software Architecture? Hard-to-Change Decisions and Trade-offs
ONE: **Software Architecture** is the collection of **big decisions that are hard to change later**. It decides how to split the system into chunks, how the chunks communicate, and which qualities to prioritize. There is no single right answer, and **every choice gains something and loses something**.
LIKE: When building a house, you can easily change the wallpaper color later, but once you decide where the load-bearing columns go or how many floors there are, changing it is very hard. Architecture is these "column decisions."
STEP:
1. **What Architecture covers**: How to split the system into big chunks (Components, Services), how the chunks communicate (function calls, Network, Messages), and which qualities (speed, stability, scalability) matter most.
2. **Trade-off thinking**: The question isn't "which is best?" but "**in this situation, what do we gain and what do we lose?**"
3. Example ①: Synchronous calls are simple and give correct results immediately, but if the other side is slow, you're slow too. Asynchronous Messages are resilient, but error handling and tracing are hard.
4. Example ②: Putting common code in a shared Library avoids duplication but ties deployments together. Copying it into each one keeps them independent, but you have to fix Bugs multiple times.
5. **What an Architect does**: Makes the key decisions and records the **reasons**, checks that the system keeps honoring those decisions, and translates business requirements into technical requirements.
6. Knowing **the pros and cons of many technologies broadly** becomes more important than knowing one technology deeply.
KEY: The **reasons** matter as much as the decisions. Without them, the same arguments repeat, and you can't revisit a decision when its premises change.
END: Architecture is the big, hard-to-change decisions, and the core skill is Trade-off thinking: weighing "what do we gain and what do we lose."

#### Architecture Characteristics (Quality Attributes)
ONE: Separate from "**what the system does**" (its features), architecture characteristics define "**how well it must do it**." Things like availability, performance, scalability, and security.
LIKE: A car's feature is "carry people and drive." But a sports car prioritizes speed, a truck prioritizes cargo capacity, and a family car prioritizes safety. Even with the same feature, the design is completely different depending on what's prioritized.
STEP:
1. **Operational characteristics**: Availability (how rarely it goes down), performance, Scalability, Elasticity (handling sudden load spikes), reliability, recoverability.
2. **Structural characteristics**: Maintainability, extensibility, testability, deployability, portability.
3. **Cross-cutting characteristics**: Security, accessibility, legal compliance, usability.
4. **Pick only 3–7**: Trying to cover every characteristic makes the system complex until it does nothing well. Pick only the most important few.
5. **Reading hidden characteristics**: They often aren't written directly in the requirements. From "orders spike on Black Friday" you have to read elasticity, and from "there are audits by regulators" you have to read auditability.
6. **Make them measurable**: Instead of "fast," set a number like "p95 response under 200 ms." Put automatic checks (**Fitness Functions**) in the Build Pipeline to keep the Architecture from slowly eroding.
WHY: Characteristics decide the choice of Architecture Style. Even the same online store might fit MSA if "scalability comes first" or a Monolith if "shipping fast comes first."
END: Architecture characteristics are the standard for "how well." Pick the 3–7 you truly need, define them with numbers, and enforce them automatically.

#### Cohesion and Coupling
ONE: **Cohesion** is **how much the elements inside one Module are gathered for the same purpose** (higher is better), and **Coupling** is **how much Modules depend on each other** (lower is better).
LIKE: A well-organized kitchen keeps knives·cutting boards·pots together in one place (high cohesion). And remodeling the kitchen doesn't require touching the living room (low coupling). Conversely, if spoons are in the bedroom and pots are in the bathroom, cohesion is low, and if fixing the kitchen means tearing up the whole house, coupling is high.
STEP:
1. **High Cohesion**: The "order Module" contains only order-related things. It's clear what to look for and what to change.
2. **Low Cohesion**: Date calculations, email sending, and payment processing are mixed together under the name "Utils." You don't know what's where, and changing it is scary.
3. **Low Coupling**: Modules communicate only through defined Interfaces. Changing one side's internals leaves the other side alone.
4. **High Coupling**: Directly touching another Module's internal variables or implementation details. Fixing one thing breaks things in a chain reaction.
5. **Connascence**: A concept that looks more finely at "relationships where changing one side requires changing the other." They range from weak relationships, where only names need to match, to strong ones, where even execution order or timing must match. The stronger the relationship, the closer together they belong, inside the same Module.
6. **Widely used Modules must be stable**: If a Module many places depend on changes often, the impact spreads everywhere. So such Modules are made abstract and slow to change.
WHY: Nearly every design principle, like SOLID, Design Patterns, and MSA, is ultimately a tool for "high cohesion, low coupling."
END: Gather related things together (high cohesion) and keep dependence on each other low (low coupling). It is the most basic principle of good design.

#### Monolithic vs MSA (Microservice Architecture)
ONE: **Monolithic** **bundles every feature into one unit and deploys it together**, while **MSA** **splits features into small Services that each deploy on their own** and communicate over the Network.
LIKE: Monolithic is a department store with every shop in one building. Management is simple, but construction on one floor affects the whole building. MSA is a shopping street where each shop has its own building. Each shop can be fixed separately, but passing goods between them is complicated.
STEP:
1. **Monolithic**: One codebase, one deployment, one DB. Development·Testing·deployment are simple, and calls are fast because they're function calls.
2. Limits of a Monolith: As it grows, even a small change requires redeploying the whole thing, scaling just one feature is hard, and a failure in one part can spread to everything.
3. **MSA**: Splits Services by business area, like orders, payments, and shipping, and deploys and scales each independently. Failures also tend to stay contained in one Service.
4. The price of MSA: Network calls are slow and can fail, Transactions spanning several Services are hard, and operations like Monitoring·log tracing·deployment become much more complex.
5. **Modular Monolith**: One deployment, but the inside is cleanly split into Modules by business area. Most new services start here, and it's safest to split a Module out into a Service only when truly needed.
| Aspect | Monolithic | MSA |
| Deployment | All at once | Independent per Service |
| Scaling | As a whole | Only the Services that need it |
| Pros | Simple, fast calls, easy Transactions | Independent deploys, partial scaling, fault isolation |
| Cons | Changes·deploys get heavier as it grows | Network latency, distributed Transactions, complex operations |
KEY: "MSA is the latest, so it's always better" is wrong. For small teams and early-stage services, a Monolith (or Modular Monolith) is often better.
END: Bundling into one is simple; splitting is independent. Choose based on the size of the team and service.

#### Architecture Styles at a Glance
ONE: Architecture Styles split into **the monolithic family, deployed all at once**, and **the distributed family, split into several units that communicate over the Network**, and each fits different situations at different costs.
LIKE: It's like the variety of building types. Single-family homes, apartment buildings, retail buildings, and factories are each designed for their purpose, and no one type can be best for every use.
STEP:
1. **Layered**: Split into screen → logic → data layers. Familiar and good for starting quickly, but as it grows, changing one feature means touching every layer.
2. **Modular Monolith**: One deployment, Modules by business area inside. The starting point for most new services.
3. **Pipeline**: Chains processing steps (filters) in one direction. Fits data transformation, ETL, and Compilers.
4. **Microkernel (Plug-in)**: A small core + swappable Plug-ins. IDEs (VS Code), browser extensions.
5. **Service-Based**: 4–12 large Services + a shared DB. A practical middle step from a Monolith toward distribution.
6. **Event-Driven**: When something happens, publish an Event, and interested parties subscribe and react. High throughput and loose coupling, but error handling·ordering·tracing·Testing are hard.
7. **Space-Based**: Replicates data in Memory across many servers and writes to the DB later. Fits unpredictable spikes like ticket sales opening, but implementation is complex and expensive.
8. **Microservices**: Small Services by business area, each with its own DB. Fits large organizations, independent deployment, and scaling parts separately.
| Style | Good fit | Cost |
| Layered | Small apps, quick starts | The scope of changes widens as it grows |
| Modular Monolith | Most new services | Module boundaries must be kept with discipline |
| Pipeline | Data transformation, ETL | Unsuitable for interactive systems |
| Microkernel | IDEs, browsers, rules engines | The core is hard to design |
| Event-Driven | High throughput, loose coupling | Hard error handling·tracing·Testing |
| Microservices | Large organizations, independent deployment | Complex operations, distributed Transactions |
KEY: The order of choosing is ① identify the business areas and key characteristics → ② if every part needs the same characteristics, go monolithic; if they differ by part, consider distributed → ③ decide who owns the data → ④ default to synchronous communication, and use asynchronous only where scaling·elasticity is needed → ⑤ consider the team structure too.
END: Each Style fits different situations at different costs. Choose by looking at the characteristics and the team structure.

#### Microservice Details: Data Ownership, Saga, Orchestration vs Choreography
ONE: In MSA, **each Service owns its own data**, work spanning several Services is coordinated by **a central conductor (Orchestration)** or **each reacting on its own (Choreography)**, and failures are rolled back with **compensating actions (Saga)**.
LIKE: When booking a vacation package, the airline, hotel, and rental car companies are all separate. If a travel agent calls each one in turn to book, that's Orchestration; if the hotel hears the notification that the flight is booked and books itself, that's Choreography. If the hotel booking fails, canceling the flight that was already booked is a Saga.
STEP:
1. **Data ownership**: Each Service has its own DB and doesn't read other Services' DBs directly. If it needs something, it calls that Service's API. Sharing a DB effectively ties them back into one.
2. **Deciding size**: It's not "the smaller the better." Decide by looking at Transaction boundaries, the need to share data, and how often they call each other. Split too finely and you get a **distributed Monolith** where Services constantly call each other.
3. **Orchestration**: A central coordinating Service directs the order: "do step 1, then do step 2." The flow is visible at a glance, but everything depends on the center.
4. **Choreography**: Each Service listens for Events and does the next thing on its own. Coupling is loose, but the overall flow is hard to grasp.
5. **Saga Pattern**: Splits work spanning several Services into small Transactions in each Service, and if something fails midway, runs **compensating Transactions that reverse** the steps already completed. It's used instead of one giant distributed Transaction.
6. **Essential operational tools**: An API Gateway (gathering everything behind a single entrance), a Service Mesh (managing communication between Services), and centralized logs and distributed tracing (which Services a single request passed through).
END: Each Service owns its data, coordination happens through conducting (Orchestration) or reacting (Choreography), and failures are rolled back with compensating actions (Saga).

#### The 8 Fallacies of Distributed Computing
ONE: There are **8 things people commonly mistake for facts** when they first build distributed systems. The moment you choose a distributed Architecture, you must design on the premise that **all 8 are false**.
LIKE: If you believe "packages always arrive, arrive instantly, can be sent in any quantity, and nobody steals them," you're in for trouble. In reality there's loss·delay·theft·capacity limits.
STEP:
1. **The Network is reliable** → In reality, messages vanish and connections drop. You need retries and Timeouts.
2. **Latency is zero** → Network calls are thousands of times slower than function calls.
3. **Bandwidth is infinite** → Sending large data recklessly clogs things up.
4. **The Network is secure** → There is eavesdropping and attacks. You need encryption and authentication.
5. **Topology doesn't change** → Servers are added·removed and addresses change.
6. **There is one administrator** → Many teams and companies each manage their own parts.
7. **Transport cost is zero** → Data transfer and serialization cost money and CPU.
8. **The Network is homogeneous** → Different hardware, OSes, and Protocols are mixed together.
WHY: The moment you turn a function call inside a Monolith into a Network call, all of these problems appear. That's why MSA's price is high (distributed system problems are covered more in topic 11).
END: In distributed systems, design assuming "the Network is slow, drops out, is dangerous, and keeps changing."

#### ADRs and Conway's Law
ONE: An **ADR (Architecture Decision Record)** is a way of recording reasons with **one short document per important decision**, and **Conway's Law** is the observation that **a system's structure comes to resemble the organization's communication structure**.
LIKE: An ADR is like a family leaving a note about "why we knocked down this wall" when renovating the house. Years later, when someone asks "why isn't there a wall here?", they can read the note.
STEP:
1. **ADR contents**: Title, status (proposed·accepted·superseded), context (what pressures and constraints there were), decision (what was decided), and consequences (what is gained and lost).
2. Keep ADRs in the code repository. Scattering them in wikis or emails makes the same arguments repeat.
3. When a decision changes, don't delete the old ADR; mark it "superseded" and write a new ADR. The history of decisions is preserved.
4. **Conway's Law**: "Organizations that design systems produce systems that mirror their communication structure." With three teams, the system tends to become three chunks.
5. So teams are sometimes split to match the desired Architecture (the Inverse Conway Maneuver). Doing MSA requires a team structure where each team owns a Service end to end.
6. **Risk analysis and diagrams**: Risk is assessed as "likelihood × impact," and diagrams are shown at different zoom levels for different audiences (the C4 Model: system context → containers → components → code).
END: Record the reasons for decisions in ADRs, and remember that system structure mirrors team structure (Conway's Law).

#### Third-Party Libraries and External APIs
ONE: **Third-party** means Libraries or Services made by someone other than us (payments, maps, social login). They save a lot of development time, but you must also manage **the risk that you can't control them**.
LIKE: Outsourcing deliveries to an outside company is convenient because you don't need your own drivers. But if that company goes on strike or raises its prices, your shop is affected too. So you check the contract terms and prepare to be able to switch to another company.
STEP:
1. **Check the License**: Confirm whether commercial use is allowed and whether there's an obligation to publish your source (GPL, etc.).
2. **Security and maintenance**: Check for known vulnerabilities and whether it's been maintained recently. Abandoned Libraries are dangerous.
3. **Version compatibility**: Updating can change how it's used and break your code. Pin versions and upgrade carefully.
4. **Prepare for external failures**: If an external API is slow or down, your service can stall too. Set up Timeouts, Retries, and fallback behavior (Fallback).
5. **Wrap it in an Adapter**: Instead of calling an external Library directly all over your code, wrap it in one Adapter so that switching vendors later means changing just one place.
END: Third-party code saves time but is outside your control. Check License·security·compatibility, and contain the risk with Adapters and Timeouts.

### What is the difference between Monolithic and MSA (Microservice Architecture)?
E: Monolithic is a department store with every shop in one building, and MSA is a shopping street where each shop has its own building. The department store is simple to manage, but construction on one floor affects the whole building; the shopping street can be fixed shop by shop, but passing goods between them is complicated.
A: Monolithic builds every feature into one deployment unit, so development·Testing·deployment are simple, but as it grows, even small changes require redeploying the whole thing, and scaling just part of it is hard. MSA has small Services, each deployed independently by feature, communicating through APIs, enabling independent deployment·partial Scaling·Fault Isolation, but Network Latency, Distributed Transactions, and Monitoring·operational complexity increase. For small teams and early-stage services, Monolithic is often better.

### What should you watch out for when using Third-Party Libraries·external APIs?
A: Third-party means Libraries or Services made by someone other than us (payments, maps, Social Login), and they save a lot of development time. In exchange, you need to check the License, security vulnerabilities·whether it's maintained, Compatibility when versions change, and how external failures affect your service, and you should wrap it in an Adapter to make it easy to swap and set up Timeouts·Retries.

### What are Architecture characteristics (quality attributes)? How do you decide them?
E: Just as cars that all "carry people and drive" prioritize speed for a sports car, cargo capacity for a truck, and safety for a family car, it's deciding the standard for "how well," separate from features.
A: Architecture characteristics are qualities a system must have apart from its features: operational characteristics like availability·performance·scalability·elasticity, structural characteristics like maintainability·testability·deployability, and cross-cutting characteristics like security·legal compliance. Covering all of them adds complexity, so pick only the most important 3–7, read hidden characteristics from the requirements (e.g., event-driven traffic spikes → elasticity), and define them measurably, like "p95 under 200 ms," checking them automatically with Fitness Functions.

### What are Cohesion and Coupling?
E: If knives·cutting boards·pots are gathered in one place in the kitchen, cohesion is high, and if fixing the kitchen doesn't require touching the living room, coupling is low.
A: Cohesion is how much the elements in one Module are gathered for the same purpose, and higher is better; Coupling is how much Modules depend on each other, and lower is better. High cohesion makes things easy to understand and change, and low coupling keeps a change in one part from spreading to others. SOLID, Design Patterns, and drawing MSA boundaries are all tools for this goal.

### What is the Saga Pattern? What is the difference between Orchestration and Choreography?
E: Booking a flight, hotel, and rental car in turn and canceling the already-booked flight when the hotel fails is a Saga; a travel agent directing the steps in order is Orchestration, and each company hearing a notification and acting on its own is Choreography.
A: Saga is a Pattern that splits work spanning several Services into a sequence of Local Transactions per Service, and if something fails midway, runs Compensating Transactions that reverse the completed steps to restore overall consistency. In Orchestration, a central Orchestrator directs each step, so the flow is clear but depends on the center; in Choreography, each Service subscribes to Events and proceeds to the next step on its own, so coupling is loose but the overall flow is hard to trace.
