## OOP (Object-Oriented Programming)

#### OOP의 4가지 특징
ONE: **OOP**는 프로그램을 **데이터와 동작을 함께 가진 Object들의 협력**으로 만드는 방식이에요. 핵심 특징은 **추상화·캡슐화·상속·다형성** 네 가지예요.
LIKE: 자동차로 생각해 보세요. 운전자는 엔진 속을 몰라도 핸들과 페달만 쓰면 되고(추상화), 엔진은 덮개 안에 감춰져 있고(캡슐화), 전기차는 자동차의 기본을 물려받고(상속), "가속해"라는 같은 명령에 휘발유차는 연료를, 전기차는 배터리를 써요(다형성).
STEP:
1. **Abstraction (추상화)**: 복잡한 대상에서 지금 필요한 핵심만 뽑아 모델링해요. 쇼핑몰의 "회원"은 이름·주소·주문 내역만 있으면 되고, 키나 혈액형은 필요 없어요.
2. **Encapsulation (캡슐화)**: 데이터와 그 데이터를 다루는 기능을 한 Object에 묶고, 내부는 숨겨요(Information Hiding). 잔액은 직접 못 바꾸고 `deposit()`, `withdraw()`로만 바꾸게 하면 잘못된 값이 들어올 수 없어요.
3. **Inheritance (상속)**: 부모 Class의 기능을 자식 Class가 물려받아 재사용하고 확장해요.
4. **Polymorphism (다형성)**: 같은 Message(Method 호출)에 Object마다 다르게 반응해요. `shape.area()`를 부르면 원은 원 넓이를, 사각형은 사각형 넓이를 계산해요.
5. 이 네 가지가 합쳐지면 "어디를 고치면 어디까지 영향이 가는지"가 작아지고, 새 기능을 기존 코드 수정 없이 추가하기 쉬워져요.
| 특징 | 뜻 | 얻는 것 |
| Abstraction | 핵심만 드러내 모델링 | 복잡함을 숨김 |
| Encapsulation | 데이터와 기능을 묶고 내부를 감춤 | 잘못된 접근 차단, 내부 변경이 밖에 영향 없음 |
| Inheritance | 부모의 기능을 물려받아 확장 | 코드 재사용 |
| Polymorphism | 같은 호출에 Object마다 다른 동작 | 호출하는 쪽을 안 고치고 새 종류 추가 |
WHY: 프로그램이 커지면 "한 곳을 고쳤더니 다른 곳이 깨지는" 일이 가장 큰 문제가 돼요. OOP는 책임을 Object 단위로 나눠 이 문제를 줄여요.
END: OOP = 추상화(핵심만) + 캡슐화(숨기기) + 상속(물려받기) + 다형성(같은 명령 다른 동작).

#### Overloading과 Overriding
ONE: **Overloading**은 같은 이름의 Method를 **Parameter만 다르게 여러 개** 두는 것이고, **Overriding**은 자식이 부모의 Method를 **같은 모양으로 다시 정의**하는 것이에요.
LIKE: Overloading은 카페의 "주문하기"가 음료만 받기도 하고 음료와 쿠폰을 같이 받기도 하는 것이에요. Overriding은 본사 레시피가 있는데 지점이 자기 방식으로 다시 만드는 거예요.
STEP:
1. **Overloading**: 같은 Class 안에 `add(int a, int b)`와 `add(int a, int b, int c)`처럼 이름은 같고 Parameter의 개수나 Type이 다른 Method를 둬요.
2. Java에서는 Compile할 때 Argument를 보고 어느 Method를 부를지 정해요.
3. **Overriding**: 자식 Class가 부모의 Method를 같은 이름·같은 Parameter로 다시 만들어요.
4. 실행 중에 실제 Object의 Type에 따라 어느 Method가 불릴지 정해져요(**Dynamic Dispatch**). 이게 다형성의 바탕이에요.
5. **Python에서는**: 같은 이름으로 함수를 다시 정의하면 마지막 것만 남아서 Overloading이 없어요. 대신 기본값 Argument나 `functools.singledispatch`로 비슷하게 해요.
| 구분 | Overloading | Overriding |
| 위치 | 같은 Class 안 | 부모–자식 Class 사이 |
| 모양 | 이름 같고 Parameter 다름 | 이름·Parameter 모두 같음 |
| 결정 시점 | Compile 시점 (Java) | 실행 시점 |
END: 같은 이름 다른 Parameter는 Overloading, 부모 것을 자식이 다시 만들면 Overriding이에요.

#### Inheritance보다 Composition
ONE: 상속(is-a)은 부모에 단단히 묶이지만, **Composition(has-a)**은 다른 Object를 부품처럼 가지고 써서 **결합이 느슨하고 갈아 끼우기 쉬워요**. 진짜 is-a가 아니면 Composition을 먼저 고려해요.
LIKE: 상속은 "나는 자동차의 한 종류다"라는 혈연 관계예요. Composition은 "나는 엔진을 가지고 있다"라는 부품 관계예요. 혈연은 바꿀 수 없지만 부품은 갈아 끼울 수 있어요.
STEP:
1. **상속의 문제 ①**: 자식이 부모의 내부 구현에 기대게 돼요. 부모 코드를 조금 고치면 자식들이 예상치 못하게 깨질 수 있어요(**Tight Coupling**).
2. **문제 ②**: 상속 구조는 코드를 쓸 때 정해져서, 실행 중에 바꿀 수 없어요.
3. **문제 ③**: 필요 없는 기능까지 다 물려받아요.
4. **Composition**: 다른 Object를 Field로 가지고, 그 Object의 공개된 기능(Interface)만 써요. 내부가 어떻게 돌아가는지는 몰라도 돼요(**Loose Coupling**).
5. 실행 중에도 부품을 교체할 수 있어요. 자동차에 가솔린 엔진 대신 전기 모터를 끼우듯이요.
```python
class Engine:
    def start(self): return "부릉"

class Car:
    def __init__(self, engine):   # 상속 대신 부품으로 가짐
        self.engine = engine
    def drive(self):
        return self.engine.start()
```
KEY: 정사각형이 직사각형을 상속하는 것처럼 "말로는 is-a인데 행동은 다른" 경우가 특히 위험해요(SOLID의 Liskov 원칙).
END: 혈연(상속)은 강하게 묶이고, 부품(Composition)은 갈아 끼울 수 있어요. 애매하면 Composition이에요.

#### Interface와 Abstract Class
ONE: **Interface**는 "**무엇을 할 수 있어야 하는가**"라는 약속 목록이고, **Abstract Class**는 공통 부분을 **이미 일부 만들어 둔 미완성 틀**이에요.
LIKE: Interface는 "운전면허 시험 항목"처럼 할 수 있어야 할 일의 목록이에요. Abstract Class는 "반쯤 지어 둔 집"처럼 공통 부분은 이미 만들어 두고 나머지만 채우게 하는 틀이에요.
STEP:
1. **Interface (Java 기준)**: 구현해야 할 Method 목록(계약, Contract)이에요. Instance Field(상태)를 가질 수 없어요.
2. 한 Class가 여러 Interface를 동시에 구현할 수 있어요. "날 수 있다", "헤엄칠 수 있다"를 둘 다 가진 오리처럼요.
3. Java 8부터는 `default` Method로 기본 구현을 넣을 수도 있어요.
4. **Abstract Class**: 상태(Field), 생성자, 이미 구현된 Method를 가질 수 있어요. 일부 Method만 "자식이 꼭 구현해"로 남겨 둬요.
5. Class는 하나만 상속할 수 있어서(Java), Abstract Class는 하나만 부모로 둘 수 있어요.
6. **고르는 기준**: "무엇을 할 수 있나(능력)"는 Interface, "무엇인가 + 공통 코드 공유"는 Abstract Class.
| 구분 | Interface | Abstract Class |
| 의미 | 할 수 있는 일(역할) | 미완성 공통 틀 |
| 상태(Field) | 없음 | 가질 수 있음 |
| 다중 구현 | 여러 개 가능 | 하나만 상속 |
| 쓰는 때 | 서로 다른 종류에 같은 능력 부여 | 가까운 종류끼리 공통 코드 공유 |
END: 능력 목록은 Interface, 반쯤 만든 공통 틀은 Abstract Class예요.

### OOP의 4가지 특징은?
E: 자동차로 생각해 봅시다. 운전자는 엔진 속을 몰라도 핸들과 페달만 쓰면 되고(Abstraction), 엔진은 덮개 안에 감춰져 있으며(Encapsulation), 전기차는 자동차의 기본을 물려받고(Inheritance), "가속해"라는 같은 명령에 휘발유차는 연료를, 전기차는 배터리를 씁니다(Polymorphism).
| 특징 | 뜻 | 얻는 것 |
| Abstraction (추상화) | 필요한 핵심만 드러내 모델링 | 복잡함을 숨김 |
| Encapsulation (캡슐화) | Data와 기능을 묶고 내부를 감춤(Information Hiding) | 잘못된 접근 차단, 내부 변경이 밖에 영향 없음 |
| Inheritance (상속) | Parent의 속성·기능을 물려받아 확장 | 코드 재사용 |
| Polymorphism (다형성) | 같은 Message에 Object마다 다르게 반응 | 호출하는 쪽 코드를 바꾸지 않고 새 종류 추가 |
A: OOP는 프로그램을 Data와 동작을 함께 가진 Object들의 협력으로 보는 방식입니다. Abstraction으로 핵심만 모델링하고, Encapsulation으로 내부를 감추고, Inheritance로 재사용하고, Polymorphism으로 같은 Interface에 다른 구현을 끼워 넣습니다. 그 결과 변경의 영향 범위가 작아지고 확장이 쉬워집니다.

### Overloading과 Overriding의 차이는?
E: Overloading은 카페의 "주문하기"가 음료 하나만 받기도 하고 음료와 쿠폰을 같이 받기도 하는 것, Overriding은 본사 레시피가 있는데 지점이 자기 방식으로 다시 만드는 것입니다.
A: Overloading은 같은 Class에 이름은 같고 Parameter의 개수나 Type이 다른 Method를 여러 개 두는 것으로, Java에서는 Compile 시점에 어느 것을 부를지 정해집니다. Overriding은 Child Class가 Parent의 Method를 같은 Signature로 재정의하는 것으로, Runtime에 실제 Object Type에 따라 호출되어(Dynamic Dispatch) Polymorphism의 바탕이 됩니다. 참고로 Python은 같은 이름으로 다시 정의하면 마지막 것만 남아, Default Argument나 `functools.singledispatch`로 비슷한 효과를 냅니다.

### Inheritance보다 Composition을 권하는 이유는?
E: Inheritance는 "나는 자동차의 한 종류다"(is-a)라는 혈연 관계이고, Composition은 "나는 엔진을 가지고 있다"(has-a)라는 부품 관계입니다. 혈연은 바꿀 수 없지만 부품은 갈아 끼울 수 있습니다.
A: Inheritance는 Child가 Parent의 내부 구현에 강하게 묶여(Tight Coupling) Parent를 고치면 Child가 깨질 수 있고, 구조가 Compile 시점에 고정됩니다. Composition은 다른 Object를 Field로 가지고 그 Object의 공개된 Interface만 쓰므로 결합이 느슨하고(Loose Coupling) Runtime에도 부품을 교체할 수 있습니다. 그래서 진짜 is-a 관계가 아니면 Composition을 먼저 고려합니다.

### Interface와 Abstract Class의 차이는?
E: Interface는 "운전면허 시험 항목"처럼 할 수 있어야 할 일의 목록이고, Abstract Class는 "반쯤 지어 둔 집"처럼 공통 부분은 이미 만들어 두고 나머지만 채우게 하는 틀입니다.
A: (Java 기준) Abstract Class는 상태(Instance Field), Constructor, 구현된 Method를 가질 수 있고 Class는 하나만 상속할 수 있어, 가까운 종류끼리 공통 코드를 나눌 때 씁니다. Interface는 Instance Field 없이 역할(Contract, 계약)을 정의하며 여러 개를 동시에 구현할 수 있고, Java 8부터는 default Method로 기본 구현도 둘 수 있습니다. "무엇을 할 수 있는가"는 Interface, "무엇인가와 공통 구현"은 Abstract Class로 구분합니다.

## SOLID와 Dependency Injection

#### SOLID 원칙
ONE: **SOLID**는 **바꾸기 쉬운 객체지향 설계**를 위한 다섯 가지 원칙이에요. 공통 목표는 "한 곳을 고칠 때 다른 곳이 깨지지 않게" 하는 거예요.
LIKE: 잘 운영되는 식당을 떠올려 보세요. 주방장과 계산원의 일을 나누고(S), 새 메뉴는 메뉴판에 추가만 하고(O), 대신 들어온 요리사도 같은 레시피를 똑같이 만들어야 하고(L), 서빙 직원에게 요리 매뉴얼까지 주지 않고(I), 사장은 특정 요리사 이름이 아니라 "요리사 자격"에 의지해요(D).
STEP:
1. **S · Single Responsibility (단일 책임)**: Class를 바꿀 이유는 하나뿐이어야 해요. 주문 Class가 계산도 하고 메일도 보내고 DB에도 저장하면, 메일 형식만 바꿔도 주문 Class를 건드려야 해요.
2. **O · Open-Closed (개방-폐쇄)**: 확장에는 열려 있고, 수정에는 닫혀 있어야 해요. 결제 수단이 늘 때마다 if-else를 고치지 말고, 새 결제 Class를 추가만 하면 되게 만들어요(다형성 활용).
3. **L · Liskov Substitution (리스코프 치환)**: 자식은 부모 자리에 넣어도 올바르게 동작해야 해요. 정사각형이 직사각형을 상속하면 "너비만 바꾸기"가 높이까지 바꿔서 부모의 약속을 깨요.
4. **I · Interface Segregation (인터페이스 분리)**: 쓰지 않는 Method에 의존하지 않도록 Interface를 작게 나눠요. 단순 프린터에 팩스·스캔 기능까지 구현하라고 강요하면 안 돼요.
5. **D · Dependency Inversion (의존성 역전)**: 구체적인 Class가 아니라 추상(Interface)에 의존해요. 서비스가 `MySQLRepository`를 직접 만들지 말고 `Repository` Interface에 기대면, DB를 바꿔도 서비스는 그대로예요.
| 원칙 | 핵심 한마디 | 위반 예 |
| S | 바꿀 이유는 하나 | 주문 Class가 메일·DB까지 담당 |
| O | 추가는 쉽게, 수정은 없이 | 결제 수단마다 if-else 수정 |
| L | 자식은 부모를 대신할 수 있어야 | 정사각형 ⊂ 직사각형 |
| I | 필요한 것만 의존 | 프린터에 팩스까지 강요 |
| D | 구체 말고 추상에 의존 | Service가 MySQL Class를 직접 new |
KEY: SOLID는 모두 **Coupling(결합도)은 낮추고 Cohesion(응집도)은 높이기** 위한 거예요. 원칙을 기계적으로 다 적용하기보다, 자주 바뀌는 곳에 우선 적용해요.
END: SOLID = 한 가지 책임, 추가로 확장, 대체 가능한 자식, 작은 Interface, 추상에 의존. 목적은 "변경에 강한 코드"예요.

#### DI (Dependency Injection)와 IoC
ONE: **DI(의존성 주입)**는 Object가 필요한 다른 Object를 **직접 만들지 않고 밖에서 받는** 것이고, 이렇게 생성과 연결의 제어를 바깥에 넘기는 것을 **IoC(제어의 역전)**라고 해요.
LIKE: 요리사가 직접 농장에 가서 재료를 구하는 대신, 가게가 재료를 주방에 가져다줘요. 요리사는 요리만 하고, 공급처가 바뀌어도 요리사는 바뀔 게 없어요.
STEP:
1. **DI가 없을 때**: `OrderService` 안에서 `self.repo = MySQLRepository()`처럼 직접 만들어요. 그러면 OrderService가 MySQL에 꽁꽁 묶여요.
2. **DI를 쓰면**: `OrderService(repo)`처럼 생성자로 받아요. OrderService는 "repo가 save()를 할 수 있다"는 것만 알면 돼요.
3. 주입 방법: 생성자로 받기(Constructor Injection, 가장 권장), Setter로 받기, Field에 넣기.
4. **IoC**: 원래는 내 코드가 필요한 Object를 만들고 연결했는데, 이제 Framework나 바깥 코드가 대신 만들어 넣어 줘요. 제어의 방향이 뒤집혔다고 해서 "역전"이에요.
5. **Test가 쉬워져요**: 진짜 DB 대신 가짜 저장소(Mock)를 주입하면, DB 없이도 OrderService를 Test할 수 있어요.
```python
class OrderService:
    def __init__(self, repo):     # 밖에서 주입받음
        self.repo = repo
    def place(self, order):
        self.repo.save(order)

service = OrderService(FakeRepository())   # Test에서는 가짜를 주입
```
USE: Spring(Java), NestJS, Angular 같은 Framework는 DI Container가 Object를 만들고 자동으로 주입해 줘요.
END: DI = "필요한 걸 직접 만들지 말고 받아 쓰기". 바꾸기 쉽고 Test하기 쉬운 코드가 돼요.

### SOLID 원칙을 설명해 주세요.
E: 잘 운영되는 식당을 떠올려 보세요. 주방장과 계산원의 일을 나누고(S), 새 메뉴는 메뉴판에 추가만 하며(O), 대체 요리사도 같은 레시피를 똑같이 만들어야 하고(L), 서빙 직원에게 요리 매뉴얼까지 주지 않으며(I), 사장은 특정 요리사 이름이 아닌 "요리사 자격"에 의지합니다(D).
| 원칙 | 뜻 | 위반 예 |
| S · Single Responsibility | Class를 바꿀 이유는 하나뿐이어야 함 | 주문 Class가 계산도 하고 메일도 보내고 DB에도 저장 |
| O · Open-Closed | 확장에는 열려 있고 수정에는 닫혀 있어야 함 | 결제 수단이 늘 때마다 if-else를 고침 |
| L · Liskov Substitution | Child는 Parent 자리에 넣어도 올바르게 동작해야 함 | 정사각형이 직사각형을 상속해 너비만 바꾸면 높이도 바뀜 |
| I · Interface Segregation | 쓰지 않는 Method에 의존하지 않도록 작게 나눠야 함 | 프린터 Interface에 팩스·스캔까지 강제 |
| D · Dependency Inversion | 구체적인 것이 아니라 추상(Interface)에 의존해야 함 | Service가 MySQL Class를 직접 new로 생성 |
A: SOLID는 변경에 강한 OOP 설계를 위한 5가지 원칙으로, Single Responsibility·Open-Closed·Liskov Substitution·Interface Segregation·Dependency Inversion입니다. 공통 목표는 한 곳을 고칠 때 다른 곳이 깨지지 않도록 Coupling(결합도)은 낮추고 Cohesion(응집도)은 높이는 것입니다.

### DI(Dependency Injection)와 IoC(Inversion of Control)란?
E: 요리사가 직접 농장에 가서 재료를 구하는 대신, 가게가 재료를 주방에 가져다 줍니다. 요리사는 요리만 하고, 공급처가 바뀌어도 요리사는 바뀔 것이 없습니다.
A: Dependency Injection(의존성 주입)은 Object가 필요한 다른 Object를 직접 만들지 않고 Constructor나 Setter 등으로 밖에서 받는 것이며, Object 생성과 연결의 제어를 Framework나 외부에 넘기는 IoC(제어의 역전)를 구현하는 대표적인 방법입니다. Interface에 의존하고 구현체를 주입받으면 구현을 쉽게 바꿀 수 있고, Test에서 가짜 Object(Mock)를 넣기 쉽습니다. Spring의 Constructor Injection이 대표 예입니다.

## Design Pattern

#### Design Pattern이란? 세 가지 분류
ONE: **Design Pattern**은 설계에서 **반복해서 나오는 문제에 대한 검증된 해법**에 이름을 붙인 것이에요. 만드는 법(생성), 조합하는 법(구조), 협력하는 법(행위)으로 나뉘어요.
LIKE: 건축에는 "현관은 이렇게, 계단은 이렇게" 같은 검증된 해법이 있어요. 코드에도 자주 나오는 문제의 검증된 설계 방식이 있어요. 그리고 Pattern 이름만 말해도 동료가 구조를 바로 알아듣는 공통 언어가 돼요.
STEP:
1. Design Pattern은 완성된 코드가 아니라 "이런 상황엔 이런 구조"라는 설계 아이디어예요.
2. GoF(Gang of Four)라고 불리는 네 저자가 1994년 책에서 23개를 정리했어요.
3. **Creational (생성)**: Object를 어떻게 만들지. Singleton, Factory Method, Builder 등.
4. **Structural (구조)**: Object들을 어떻게 조합해 더 큰 구조를 만들지. Adapter, Decorator, Composite, Proxy 등.
5. **Behavioral (행위)**: Object들이 어떻게 책임을 나누고 소통할지. Observer, Strategy, Template Method 등.
WHY: 같은 문제를 매번 새로 고민하지 않고, 많은 사람이 검증한 해법을 재사용할 수 있어요. "여기 Observer로 하자"는 한마디로 설계 의도가 전달돼요.
KEY: Pattern을 억지로 끼워 넣으면 오히려 복잡해져요. 문제가 먼저고, Pattern은 그 문제에 맞을 때만 써요.
END: Design Pattern은 반복되는 설계 문제의 검증된 해법이자 개발자들의 공통 언어예요.

#### 생성 Pattern: Singleton · Factory Method · Builder
ONE: Object를 **어떻게 만들지**를 다루는 Pattern이에요. **하나만 만들기(Singleton)**, **무엇을 만들지 자식에게 맡기기(Factory Method)**, **단계별로 조립하기(Builder)**.
LIKE: Singleton은 나라에 하나뿐인 중앙은행, Factory Method는 본사가 "버거 만들기"만 정하고 지점이 지역 버거를 만드는 것, Builder는 샌드위치 가게에서 빵·치즈·소스를 차례로 골라 조립하는 거예요.
STEP:
1. **Singleton**: Class의 Instance를 딱 하나만 만들고, 어디서든 그것을 쓰게 해요. 설정, Logger, Connection Pool처럼 하나만 있어야 하는 자원에 써요.
2. Singleton의 단점: 사실상 전역 변수라서 여러 곳이 보이지 않게 묶이고, Test마다 상태를 초기화하기 어려워요. Multi-Thread에서 처음 만들 때 두 개가 생기지 않게 동기화도 필요해요. 그래서 요즘은 DI Container가 하나만 만들어 주입하는 방식을 더 선호해요.
3. **Factory Method**: Object를 만드는 Method를 따로 두고, 어떤 구체 Class를 만들지는 자식 Class가 정해요. 쓰는 쪽은 "무엇이 만들어지는지" 몰라도 돼요.
4. **Builder**: 옵션이 많은 복잡한 Object를 한 번에 거대한 생성자로 만들지 않고, `.bread("호밀").cheese("체다").build()`처럼 단계별로 조립해요. 읽기 쉽고 실수가 줄어요.
END: 하나만이면 Singleton, 무엇을 만들지 미루면 Factory Method, 복잡하면 Builder예요.

#### 구조 Pattern: Adapter · Decorator · Composite · Proxy
ONE: Object를 **어떻게 조합할지**를 다루는 Pattern이에요. **맞지 않는 것 연결(Adapter)**, **기능 덧붙이기(Decorator)**, **하나와 묶음을 똑같이 다루기(Composite)**, **대리인이 접근 제어(Proxy)**.
LIKE: Adapter는 해외여행용 돼지코 변환 플러그, Decorator는 커피에 우유·시럽을 추가하는 것, Composite는 파일과 폴더 모두 "크기 보기"가 되는 것, Proxy는 연예인 대신 일정을 받는 매니저예요.
STEP:
1. **Adapter**: Interface가 맞지 않는 두 Object 사이에 변환기를 둬요. 외부 결제 Library의 Method 이름이 우리 코드와 다르면 Adapter로 감싸 우리 방식으로 쓰게 해요.
2. **Decorator**: 원본과 **같은 Interface**로 감싸면서 기능을 덧붙여요. 여러 겹으로 쌓을 수 있어요. 예: 커피 → 우유 추가 → 시럽 추가, Java의 `BufferedInputStream`.
3. **Composite**: 개별 Object와 그 묶음을 같은 방식으로 다뤄요(Tree 구조). 폴더의 크기 = 안에 든 파일과 폴더 크기의 합, 그리고 둘 다 `size()`로 똑같이 부를 수 있어요.
4. **Proxy**: 원본 대신 대리 Object가 요청을 받아 **접근을 제어**해요. 필요할 때 늦게 불러오기(Lazy Loading), 권한 검사, 결과 Cache, 원격 서버 호출 감추기.
5. **Decorator vs Proxy**: 둘 다 같은 Interface로 감싸지만, Decorator는 "기능 추가"가 목적이고 Proxy는 "접근 제어"가 목적이에요.
END: 연결은 Adapter, 덧붙이기는 Decorator, Tree는 Composite, 대리인은 Proxy예요.

#### 행위 Pattern: Observer · Strategy · Template Method
ONE: Object들이 **어떻게 협력하고 책임을 나눌지**를 다루는 Pattern이에요. **변화를 자동 알림(Observer)**, **Algorithm 갈아 끼우기(Strategy)**, **순서는 고정하고 일부만 바꾸기(Template Method)**.
LIKE: Observer는 유튜브 구독과 새 영상 알림, Strategy는 길찾기 앱에서 자동차·도보·대중교통을 고르는 것, Template Method는 라면 끓이는 순서는 같고 토핑만 다른 거예요.
STEP:
1. **Observer**: 한 Object(Subject)의 상태가 바뀌면, 그것을 구독한 여러 Object(Observer)에게 자동으로 알려요. 주문 상태가 바뀌면 메일·문자·앱 Push가 각자 알림을 받는 식이에요. 이벤트 시스템과 UI의 기본 구조예요.
2. **Strategy**: Algorithm을 별도 Object로 분리하고, 실행 중에 갈아 끼워요. 할인 정책(정액, 정률, 무료)을 Strategy Object로 만들어 주문마다 다른 정책을 넣어요. Composition을 써요.
3. **Template Method**: 부모 Class가 전체 순서(물 끓이기 → 면 넣기 → 토핑 → 완성)를 정하고, 일부 단계(토핑)만 자식 Class가 구현해요. Inheritance를 써요.
4. **Strategy vs Template Method**: 둘 다 Algorithm의 일부를 바꾸지만, Template Method는 상속이라 구조가 코드를 쓸 때 고정되고, Strategy는 Composition이라 실행 중에 통째로 교체할 수 있어요.
END: 알림은 Observer, 갈아 끼우기는 Strategy, 순서 고정 + 일부만 바꾸기는 Template Method예요.

#### MVC Pattern
ONE: 프로그램을 **데이터·로직(Model)**, **화면(View)**, **입력 처리와 연결(Controller)**로 나누는 구조예요.
LIKE: 식당에서 주방(Model)은 요리와 재료를, 홀의 식탁 차림(View)은 손님이 보는 모습을, 종업원(Controller)은 주문을 받아 주방에 전하고 결과를 식탁에 내가요.
STEP:
1. **Model**: 데이터와 업무 규칙(Business Logic)이에요. "잔액은 음수가 될 수 없다" 같은 규칙이 여기 있어요.
2. **View**: 사용자에게 보여 주는 화면이에요. 데이터를 어떻게 보여 줄지만 신경 써요.
3. **Controller**: 사용자 입력(클릭, 요청)을 받아 Model을 고치고, 결과를 보여 줄 View를 골라요.
4. 화면과 로직이 분리돼서, 화면 디자인을 바꿔도 로직은 그대로고, 로직을 Test할 때 화면이 필요 없어요.
5. 변형: **MVP**(Presenter가 View를 직접 조종), **MVVM**(ViewModel과 View가 데이터 바인딩으로 자동 동기화, 모바일·Frontend에서 많이 써요).
USE: 웹 Framework(Django는 MTV라고 부르지만 같은 생각, Spring MVC, Ruby on Rails)와 모바일 앱 구조의 기본이에요.
END: MVC = 데이터(Model) + 화면(View) + 연결(Controller). 나눠 두면 각각 따로 고치고 Test할 수 있어요.

### Design Pattern이란? 어떻게 분류하나요?
E: 건축에서 "아파트 계단은 이렇게, 현관은 이렇게"처럼 검증된 해법이 있듯, 코드에도 자주 나오는 문제의 검증된 설계 방식이 있습니다. Pattern 이름만 말해도 동료가 구조를 바로 알아듣는 공통 언어이기도 합니다.
A: Design Pattern은 Software 설계에서 반복해서 나타나는 문제에 대한 재사용 가능한 해법입니다. GoF는 Object를 만드는 방법을 다루는 Creational Pattern(생성), Object를 조합해 더 큰 구조를 만드는 Structural Pattern(구조), Object 사이의 책임 분배와 상호작용을 다루는 Behavioral Pattern(행위)으로 나눕니다.
| Pattern | 분류 | 한 줄 설명 | 생활 비유 |
| Singleton | Creational | Instance를 하나만 만들고 어디서나 그것을 씀 | 나라에 하나뿐인 중앙은행 |
| Factory Method | Creational | 어떤 Object를 만들지는 Subclass가 결정 | 본사는 "버거 만들기"만 정하고 지점이 지역 버거를 만듦 |
| Builder | Creational | 복잡한 Object를 단계별로 조립 | 샌드위치 가게에서 빵·치즈·소스를 차례로 고름 |
| Adapter | Structural | 맞지 않는 Interface를 변환해 연결 | 해외여행용 돼지코 변환 플러그 |
| Decorator | Structural | 같은 Interface로 감싸 기능을 덧붙임 | 커피에 우유, 시럽을 추가 |
| Composite | Structural | 개별 Object와 묶음을 같은 방식으로 다룸(Tree) | 파일과 폴더 모두 "크기 보기" 가능 |
| Proxy | Structural | 대리 Object가 접근을 제어(Lazy Loading·권한·Cache) | 연예인 대신 일정을 받는 매니저 |
| Observer | Behavioral | 상태가 바뀌면 Subscriber들에게 자동 알림 | 유튜브 구독과 새 영상 알림 |
| Strategy | Behavioral | Algorithm을 Object로 분리해 Runtime에 교체 | 길찾기에서 자동차·도보·대중교통 선택 |
| Template Method | Behavioral | 전체 순서는 Parent가, 일부 단계는 Child가 구현 | 라면 끓이기 순서는 같고 토핑만 다름 |

### Singleton Pattern의 장단점은?
A: Singleton은 Class의 Instance를 하나만 만들고 전역 접근점(Global Access Point)을 주는 Pattern으로, DB Connection Pool·설정·Logger처럼 하나만 있어야 하는 자원을 공유해 Memory를 아낍니다. 하지만 전역 상태(Global State)라 여러 곳이 숨은 방식으로 결합되고, Test마다 상태를 초기화하기 어렵습니다. 또 Multi-Thread에서 처음 만들 때 동시에 두 개가 생기지 않도록 Synchronization이 필요하므로, 요즘은 DI Container가 하나만 만들어 주입하는 방식을 더 선호합니다.

### Strategy Pattern과 Template Method Pattern의 차이는?
A: 둘 다 Algorithm의 일부를 바꾸기 위한 Pattern이지만, Template Method는 Inheritance를 써서 Parent가 순서를 고정하고 Child가 단계를 채우며 Compile 시점에 구조가 정해집니다. Strategy Pattern은 Composition을 써서 Algorithm Object 자체를 주입받으므로 Runtime에도 통째로 교체할 수 있습니다.

### Decorator Pattern과 Proxy Pattern의 차이는?
A: 둘 다 같은 Interface로 원본을 감싸지만 목적이 다릅니다. Decorator는 기능을 덧붙이는 것이 목적이라 여러 겹으로 쌓을 수 있고(Java의 BufferedInputStream), Proxy는 원본에 대한 접근을 제어하는 것이 목적입니다(Lazy Loading, 권한 검사, Cache, 원격 호출).

### MVC Pattern이란?
E: 식당에서 주방(Model)은 요리와 재료를, 홀의 식탁 차림(View)은 손님이 보는 모습을, 종업원(Controller)은 주문을 받아 주방에 전하고 결과를 식탁에 내갑니다.
A: MVC는 Application을 Data와 Business Logic을 담당하는 Model, 화면 표시를 담당하는 View, 사용자 입력을 받아 Model을 갱신하고 알맞은 View를 고르는 Controller로 나누는 구조입니다. 화면과 Logic이 분리되어 각각 따로 고치고 Test하기 쉽고, 비슷한 변형으로 MVP·MVVM이 있습니다.

## Programming Paradigm

#### Imperative vs Declarative
ONE: **Imperative(명령형)**는 "**어떻게**" 할지 순서대로 지시하고, **Declarative(선언형)**는 "**무엇을**" 원하는지만 말해요.
LIKE: 택시에서 "다음 사거리에서 좌회전, 200m 직진, 신호에서 우회전"을 일일이 말하면 명령형, "서울역이요"라고 목적지만 말하면 선언형이에요.
STEP:
1. **Imperative**: 상태를 바꾸는 명령을 순서대로 적어요. "변수 sum을 0으로, 반복하면서 하나씩 더하고…". C, Java의 반복문.
2. **Declarative**: 원하는 결과를 적고 방법은 시스템에 맡겨요. SQL(`SELECT ... WHERE ...`), HTML(이런 구조의 화면), CSS.
3. Python에서도 둘 다 써요. 반복문으로 합계를 구하면 명령형, `sum(x for x in nums if x > 0)`은 더 선언형에 가까워요.
4. **Functional Programming**은 선언형의 한 갈래예요.
PRO: 선언형은 의도가 잘 드러나 읽기 쉽고, 시스템이 더 좋은 방법을 알아서 고를 수 있어요(DB의 실행 계획처럼).
CON: 선언형은 세밀한 제어가 어렵고, 내부에서 무슨 일이 일어나는지 보이지 않을 때가 있어요.
END: "어떻게"를 말하면 명령형, "무엇을"을 말하면 선언형이에요.

#### Functional Programming
ONE: **같은 입력에 항상 같은 출력**을 내고 **바깥을 바꾸지 않는** 순수 함수와, **바꿀 수 없는 데이터**를 중심으로 프로그램을 만드는 방식이에요.
LIKE: 자판기와 같아요. 같은 돈을 넣고 같은 버튼을 누르면 항상 같은 음료가 나오고, 자판기가 몰래 다른 걸 바꾸지 않아요.
STEP:
1. **Pure Function (순수 함수)**: 결과가 입력에만 달려 있고, 바깥 상태(전역 변수, 파일, 화면)를 바꾸지 않아요. 바깥을 바꾸는 걸 **Side Effect(부수 효과)**라고 해요.
2. **Immutable Data (불변 데이터)**: 데이터를 고치지 않고, 바뀐 새 데이터를 만들어요.
3. **First-Class Function**: 함수를 값처럼 변수에 담고 넘기고 돌려줘요.
4. **Higher-Order Function**: 함수를 받거나 돌려주는 함수예요. `map`(모두 변환), `filter`(골라내기), `reduce`(하나로 합치기).
5. **OOP와 비교**: OOP는 상태를 Object 안에 숨기고 Method로 바꿔서 복잡함을 관리해요. FP는 상태 변경 자체를 줄여서 복잡함을 관리해요.
PRO: 결과가 예측 가능해서 Test가 쉽고, 공유 상태를 안 바꾸니 병렬 처리에서 Race Condition 걱정이 적어요.
CON: 계속 새 데이터를 만들어 Memory를 더 쓸 수 있고, 상태 변화가 본질인 일(UI, 게임)에서는 표현이 어색할 수 있어요.
USE: 실무에서는 Python, JavaScript, Kotlin처럼 OOP와 FP를 섞어 써요. React의 함수형 컴포넌트, 데이터 처리 Pipeline이 FP 스타일이에요.
END: FP = 순수 함수 + 불변 데이터 + 함수를 값처럼. 부수 효과를 줄여 예측 가능한 코드를 만들어요.

### Imperative와 Declarative Programming의 차이는?
E: 택시에서 "다음 사거리에서 좌회전, 200m 직진"을 일일이 말하면 Imperative(명령형), "서울역이요"라고 목적지만 말하면 Declarative(선언형)입니다.
A: Imperative는 상태를 바꾸는 명령을 순서대로 적어 "어떻게" 할지를 기술하고(C, Java의 반복문), Declarative는 원하는 결과인 "무엇"을 기술하고 방법은 시스템에 맡깁니다(SQL, HTML). Functional Programming은 Declarative의 한 갈래입니다.

### Functional Programming이란? OOP와 비교하면?
E: Functional은 자판기와 같습니다. 같은 돈과 버튼을 넣으면 항상 같은 음료가 나오고, 자판기가 몰래 다른 것을 바꾸지 않습니다.
A: Functional Programming(함수형)은 같은 입력에 항상 같은 출력을 내고 바깥 상태를 바꾸지 않는 Pure Function, Immutable Data, Function을 값처럼 넘기는 First-Class Function과 Higher-Order Function(map, filter, reduce)을 중심으로 합니다. Side Effect(부수 효과)가 적어 Test·병렬 처리가 쉽고, OOP는 상태를 Object 안에 감추고 Method로 바꾸는 방식으로 복잡성을 관리합니다. 실무에서는 Python·Kotlin·JavaScript처럼 둘을 섞어 씁니다.

## Clean Code와 Test

#### Clean Code와 Refactoring
ONE: **Clean Code**는 **다른 사람이 읽고 고치기 쉬운 코드**이고, **Refactoring**은 **겉으로 하는 일은 그대로 두고 내부 구조만** 개선하는 작업이에요.
LIKE: Refactoring은 이사 가지 않고 집 안을 정리하는 것이에요. 가구 배치와 수납은 바뀌지만, 집 주소와 기능은 그대로예요.
STEP:
1. **의도가 드러나는 이름**: `d` 대신 `days_since_signup`. 이름만 보고 무슨 값인지 알 수 있어야 해요.
2. **작은 함수, 한 가지 일**: 함수 하나가 한 가지 일만 하면 이해하고 Test하기 쉬워요.
3. **중복 제거 (DRY, Don't Repeat Yourself)**: 같은 코드를 여러 곳에 복사하면, 고칠 때 한 곳을 빼먹기 쉬워요.
4. **Magic Number 대신 상수**: `if age > 19` 대신 `ADULT_AGE = 19`.
5. **일관된 Style**: 팀 규칙과 자동 Formatter를 써요.
6. **Refactoring**: 동작은 그대로 두고 구조를 개선해요. 함수 쪼개기, 이름 바꾸기, 중복 합치기.
7. **Test가 먼저 있어야** 안전해요. Refactoring 후 Test를 돌려 동작이 그대로인지 확인해요.
WHY: 코드는 한 번 쓰고 수십 번 읽혀요. 읽기 어려운 코드는 고칠 때마다 Bug를 만들고 시간이 배로 들어요.
END: Clean Code는 읽기 쉬운 코드이고, Refactoring은 Test를 안전망 삼아 구조를 다듬는 일이에요.

#### Test의 종류와 Test Pyramid
ONE: Test는 범위에 따라 **Unit(부품 하나)**, **Integration(부품끼리 연결)**, **E2E(사용자 시나리오 전체)**로 나뉘고, **빠르고 싼 Unit Test를 가장 많이** 두라는 게 Test Pyramid예요.
LIKE: 자동차 공장에서 나사 하나씩 검사(Unit), 엔진과 변속기를 연결해 검사(Integration), 완성차를 도로에서 시운전(E2E)하는 것과 같아요.
STEP:
1. **Unit Test**: 함수나 Class 하나를 다른 것과 떼어 놓고 검사해요. 몇 ms 만에 끝나서 수천 개를 자주 돌릴 수 있어요.
2. **Integration Test**: 여러 Module이 함께, 또는 DB·외부 API와 연결됐을 때 제대로 동작하는지 검사해요.
3. **E2E (End-to-End) Test**: 실제 사용자처럼 브라우저를 조작해 "회원 가입 → 로그인 → 주문"까지 전체 흐름을 검사해요. 느리고 비싸고, 사소한 이유로 가끔 실패하기도 해요(**Flaky**).
4. **Test Pyramid**: 아래(Unit)를 넓게, 위(E2E)를 좁게. 빠른 Test로 대부분의 Bug를 잡고, 느린 Test는 핵심 시나리오만 확인해요.
| 종류 | 범위 | 속도·비용 | 개수 |
| Unit | 함수·Class 하나 | 빠르고 쌈 | 가장 많이 |
| Integration | 여러 Module, DB·외부 연결 | 중간 | 중간 |
| E2E | 사용자 시나리오 전체 | 느리고 비싸고 깨지기 쉬움 | 적게 |
WHY: Test가 있으면 코드를 고칠 때 "다른 데가 깨지지 않았나"를 자동으로 확인할 수 있어요. 자신 있게 고칠 수 있게 해 주는 안전망이에요.
END: 부품은 Unit, 연결은 Integration, 전체는 E2E. 아래를 넓게, 위를 좁게 쌓아요.

#### TDD (Test-Driven Development)
ONE: **실패하는 Test를 먼저 쓰고(Red)**, **통과할 만큼만 코드를 쓰고(Green)**, **코드를 정리(Refactor)**하는 짧은 주기를 반복하는 개발 방식이에요.
LIKE: 요리를 하기 전에 "이 요리는 짜지 않고 5분 안에 나와야 한다"는 채점표부터 쓰는 거예요. 채점표가 있으면 무엇을 만들어야 하는지가 분명해져요.
STEP:
1. **Red**: 아직 없는 기능에 대한 Test를 먼저 써요. 당연히 실패해요.
2. **Green**: 그 Test를 통과시키는 **최소한의** 코드를 써요. 예쁘지 않아도 돼요.
3. **Refactor**: Test가 통과하는 상태를 유지하며 코드를 깔끔하게 정리해요.
4. 다음 작은 기능으로 넘어가 다시 Red부터 반복해요.
PRO: 요구사항이 Test로 명확해지고, 자연스럽게 Test하기 쉬운 구조가 되며, Refactoring이 안전해져요.
CON: 처음 개발 속도가 느려지고, 요구사항이 자주 크게 바뀌면 Test까지 함께 고치는 비용이 들어요.
END: TDD = Red(실패하는 Test) → Green(통과) → Refactor(정리)의 반복이에요.

#### Test Double: Mock · Stub · Fake
ONE: Test에서 진짜 Object(DB, 외부 API, 메일 서버) 대신 쓰는 **가짜 Object**를 Test Double이라고 해요. 정해진 값만 주면 **Stub**, 호출 여부까지 검증하면 **Mock**이에요.
LIKE: 드라마 촬영의 대역 배우예요. Stub은 정해진 대사만 하는 대역이고, Mock은 대사를 하면서 "주인공이 나에게 몇 번, 무슨 말을 했는지"도 기록해 감독에게 확인받는 대역이에요.
STEP:
1. 진짜 DB나 결제 API로 Test하면 느리고, 돈이 들고, 결과가 매번 달라질 수 있어요. 그래서 가짜로 바꿔요.
2. **Stub**: 호출하면 미리 정한 값을 돌려줘요. "환율 API는 항상 1300을 돌려준다"로 정하고, 내 코드의 **결과(상태)**가 맞는지 검증해요.
3. **Mock**: "어떤 Method가 어떤 Argument로 몇 번 불렸는지"를 기록하고 검증해요. "주문하면 메일 발송이 정확히 1번 불렸나?" 같은 **행동(Behavior)**을 확인해요.
4. **Fake**: 실제로 동작하는 간단한 구현이에요. 진짜 DB 대신 Memory에 저장하는 가짜 DB.
5. **Spy**: 진짜처럼 동작하면서 호출 기록을 남겨요. **Dummy**: 자리만 채우는, 실제로는 안 쓰이는 Object.
END: 값만 주면 Stub, 호출을 검증하면 Mock, 간단히 진짜처럼 동작하면 Fake예요.

### Clean Code와 Refactoring이란?
E: Refactoring은 이사 가지 않고 집 안을 정리하는 것입니다. 가구 배치와 수납은 바뀌지만 집의 주소와 기능은 그대로입니다.
A: Clean Code는 다른 사람이 읽고 고치기 쉬운 코드로, 의도가 드러나는 이름, 한 가지 일만 하는 작은 Function, 중복 제거(DRY, Don't Repeat Yourself), Magic Number 대신 상수, 일관된 Style을 갖춥니다. Refactoring은 외부 동작을 바꾸지 않고 내부 구조를 개선하는 것이며, 동작이 그대로인지 확인할 Test가 있어야 안전하게 할 수 있습니다.

### Unit·Integration·E2E Test의 차이와 Test Pyramid는?
E: 자동차 공장에서 나사 하나씩 검사(Unit), 엔진과 변속기를 연결해 검사(Integration), 완성차를 도로에서 시운전(E2E)하는 것과 같습니다.
| 종류 | 범위 | 속도·비용 | 개수 |
| Unit Test | Function·Class 하나 | 빠르고 싸다 | 가장 많이 |
| Integration Test | 여러 Module, DB·외부 API와의 연결 | 중간 | 중간 |
| E2E Test | 사용자 시나리오 전체(Browser 조작) | 느리고 비싸고 깨지기 쉽다(Flaky) | 적게 |
A: Unit Test는 가장 작은 단위를 격리해 검사하고, Integration Test는 여러 부분이 함께 동작하는지, E2E(End-to-End) Test는 사용자 관점에서 전체 흐름이 되는지를 검사합니다. Test Pyramid는 빠르고 싼 Unit Test를 가장 많이, 느리고 비싼 E2E를 가장 적게 두라는 가이드입니다.

### TDD란? 장단점은?
E: 요리를 하기 전에 "이 요리는 짜지 않고 5분 안에 나와야 한다"는 채점표부터 쓰는 것입니다.
A: TDD(Test-Driven Development)는 실패하는 Test를 먼저 쓰고(Red), 통과할 만큼만 최소한의 코드를 쓴 뒤(Green), 코드를 정리하는(Refactor) 짧은 주기를 반복하는 방식입니다. 요구사항이 명확해지고 Test하기 쉬운 구조가 되며 Refactoring이 안전해지지만, 초기 개발 속도가 느려지고 요구사항이 자주 바뀌면 Test 수정 비용이 듭니다.

### Mock과 Stub의 차이는?
E: 드라마 촬영의 대역 배우입니다. Stub은 정해진 대사만 하는 대역이고, Mock은 대사를 하면서 "주인공이 나에게 몇 번, 무슨 말을 했는지"도 기록해 감독에게 확인받는 대역입니다.
A: 둘 다 Test에서 진짜 Object를 대신하는 Test Double입니다. Stub은 호출하면 미리 정한 값을 돌려주어 Test할 코드의 결과(State)를 검증하는 데 쓰고, Mock은 "어떤 Method가 어떤 Argument로 몇 번 호출되었는지" 같은 호출(Behavior)을 검증합니다. 그 밖에 In-Memory DB처럼 실제로 동작하는 간단한 구현인 Fake, 호출을 기록하는 Spy, 자리만 채우는 Dummy가 있습니다.

## 개발 Process와 DevOps

#### Waterfall과 Agile · Scrum
ONE: **Waterfall**은 계획→설계→구현→Test를 **한 번씩 차례로** 하는 방식이고, **Agile**은 **짧은 주기로 조금씩 만들고 피드백을 받아** 방향을 고쳐 가는 방식이에요. **Scrum**은 Agile의 대표 실천 방법이에요.
LIKE: Waterfall은 결혼식장처럼 설계를 다 끝낸 뒤 짓고, 다 지은 뒤 검사하는 거예요. Agile은 푸드트럭처럼 작게 문을 열고 손님 반응을 보며 메뉴를 바꿔 가는 거예요.
STEP:
1. **Waterfall Model**: 요구사항 → 설계 → 구현 → Test → 배포를 순서대로, 앞 단계를 끝내야 다음으로 가요. 계획과 문서가 명확해요. 하지만 Test 단계에서야 문제를 발견하면 되돌아가는 비용이 커요.
2. **Agile**: "작동하는 Software를 자주 전달하고, 변화에 대응한다"는 철학이에요. 짧은 주기마다 실제로 쓸 수 있는 결과물을 내고 피드백을 받아요.
3. **Scrum**: Agile의 대표 Framework예요. 한 달 이하(보통 1~4주)의 **Sprint**를 반복해요.
4. **Scrum의 역할**: Product Owner(무엇을 만들지 우선순위 결정), Scrum Master(과정이 잘 돌아가게 도움), Developers(실제로 만듦).
5. **Scrum의 행사**: Sprint Planning(이번에 무엇을 할지), Daily Scrum(매일 짧은 공유), Sprint Review(결과 시연과 피드백), Retrospective(일하는 방식 회고).
WHY: 요구사항은 만들면서 바뀌기 마련이에요. 짧은 주기로 확인하면 잘못된 방향을 일찍 바로잡을 수 있어요.
KEY: Waterfall이 무조건 나쁜 건 아니에요. 요구사항이 확실하고 바뀌기 어려운 분야(예: 규제가 엄격한 시스템)에서는 여전히 맞을 수 있어요.
END: 한 번에 크게 계획하면 Waterfall, 작게 자주 만들며 고치면 Agile. Scrum은 Sprint로 Agile을 실천하는 방법이에요.

#### CI/CD와 DevOps
ONE: **CI**는 코드를 자주 합치고 **합칠 때마다 자동으로 Build·Test**하는 것, **CD**는 그 결과를 **자동으로 배포 가능한 상태로 만들거나(Delivery) 실제 배포까지(Deployment)** 하는 것이에요. **DevOps**는 개발과 운영을 한 팀처럼 묶는 문화예요.
LIKE: 빵집에서 반죽을 할 때마다 자동 검사기가 맛을 보고(CI), 통과한 빵은 자동으로 포장되어 진열대에 나가요(CD).
STEP:
1. **CI (Continuous Integration, 지속적 통합)**: 개발자들이 하루에도 여러 번 Main Branch에 코드를 합쳐요. 합칠 때마다 Build와 Test가 자동으로 돌아서, 문제가 생기면 바로 알아요.
2. 오래 따로 작업하다 한꺼번에 합치면 충돌과 Bug가 폭발해요(Integration Hell). 자주 합치면 작을 때 해결할 수 있어요.
3. **Continuous Delivery (지속적 전달)**: Test를 통과한 코드를 언제든 배포할 수 있는 상태로 자동으로 만들어 둬요. 실제 운영 배포는 사람이 버튼을 눌러 승인해요.
4. **Continuous Deployment (지속적 배포)**: Test를 통과하면 사람 승인 없이 운영까지 자동으로 배포해요.
5. **DevOps**: 개발팀(Dev)과 운영팀(Ops)이 따로 일하며 서로 탓하던 문제를 없애려고, 한 팀처럼 책임을 나누고 자동화와 Monitoring으로 빠르고 안정적인 배포를 추구해요.
USE: GitHub Actions, GitLab CI, Jenkins 같은 도구로 Pipeline을 만들어요.
END: CI는 "자주 합치고 자동 검사", CD는 "자동으로 배포 준비(Delivery) 또는 배포까지(Deployment)", DevOps는 그걸 가능하게 하는 문화예요.

### Waterfall Model과 Agile, Scrum은?
E: Waterfall(폭포수)은 결혼식장처럼 설계를 다 끝낸 뒤 짓고, 다 지은 뒤 검사하는 것입니다. Agile은 푸드트럭처럼 작게 문을 열고 손님 반응을 보며 메뉴를 바꿔 가는 것입니다.
A: Waterfall Model은 요구사항→설계→구현→Test→배포를 차례로 진행해 계획과 문서가 명확하지만 뒤늦게 발견된 변경에 비용이 큽니다. Agile은 짧은 주기로 작동하는 Software를 자주 내놓고 Feedback으로 방향을 고치는 철학입니다. Scrum은 Agile의 대표 Framework로, 한 달 이하(보통 1~4주)의 Sprint를 돌며 Product Owner·Scrum Master·Developers 역할과 Sprint Planning·Daily Scrum·Sprint Review·Retrospective(회고)를 둡니다.

### CI/CD와 DevOps란?
E: 빵집에서 반죽을 할 때마다 자동 검사기가 맛을 보고(CI), 통과한 빵은 자동으로 포장되어 진열대에 나갑니다(CD).
A: CI(Continuous Integration, 지속적 통합)는 개발자들이 코드를 자주 Main Branch에 합치고, 합칠 때마다 Build와 Test를 자동으로 돌려 문제를 빨리 찾는 것입니다. CD는 두 뜻이 있는데, Continuous Delivery(지속적 전달)는 언제든 배포할 수 있는 상태를 자동으로 만들고 운영(Production) 배포는 사람이 승인하며, Continuous Deployment(지속적 배포)는 Test를 통과하면 운영까지 자동 배포합니다. DevOps는 개발(Dev)과 운영(Ops)을 한 팀처럼 묶고 자동화·Monitoring으로 빠르고 안정적인 배포를 추구하는 문화이자 방식입니다.

## Git과 협업

#### Git의 세 영역과 기본 흐름
ONE: **Git**은 코드의 변경 기록을 관리하는 도구예요. 파일을 고치는 **Working Directory**, 다음 저장에 넣을 것을 모으는 **Staging Area**, 저장된 기록이 쌓이는 **Repository** 세 영역으로 움직여요.
LIKE: 책상 위(Working Directory)에서 글을 쓰고, 보낼 것만 봉투에 넣고(Staging), 봉투를 봉해 내 서랍에 보관하고(Commit), 우체국(Remote Repository)에 부쳐요(push).
STEP:
1. **Working Directory**: 내가 실제로 파일을 고치는 곳이에요.
2. `git add 파일`: 고친 것 중 이번 저장에 넣을 것만 **Staging Area**에 올려요. 여러 파일을 고쳤어도 관련된 것만 골라 묶을 수 있어요.
3. `git commit -m "메시지"`: Staging Area의 내용을 하나의 기록(**Commit**)으로 **Local Repository**에 저장해요. Commit마다 고유 번호(Hash)가 붙어요.
4. `git push`: 내 Commit들을 **Remote Repository**(GitHub 등)에 올려 팀과 공유해요.
5. `git fetch`: Remote의 새 변경을 가져오기만 하고 내 작업에 합치지는 않아요.
6. `git pull`: fetch + merge(설정에 따라 rebase)예요. 가져와서 내 작업에 합쳐요.
7. **Branch**: 기록의 갈래예요. 새 기능은 별도 Branch에서 작업하고, 끝나면 main에 합쳐요.
WHY: 누가, 언제, 왜 바꿨는지 기록이 남고, 문제가 생기면 이전 상태로 돌아갈 수 있고, 여러 사람이 동시에 다른 부분을 작업할 수 있어요.
END: 고치고(Working) → 골라 담고(add) → 저장하고(commit) → 공유해요(push).

#### merge vs rebase, reset vs revert
ONE: 두 Branch를 합칠 때 **merge**는 기록을 그대로 두고 합류점을 만들고, **rebase**는 내 Commit을 상대 끝에 다시 붙여 한 줄로 만들어요. 되돌릴 때 **reset**은 기록을 지우고, **revert**는 반대 Commit을 새로 추가해요.
LIKE: merge는 두 갈래 길이 만나는 지점에 "합류점" 표지판을 세우는 것이고, rebase는 내 길을 통째로 떼어 상대 길 끝에 다시 이어 붙여 한 줄로 만드는 거예요.
STEP:
1. **merge**: 두 Branch를 합치는 Merge Commit을 만들어요. 누가 언제 갈라졌다 합쳤는지 기록이 그대로 남아요.
2. **rebase**: 내 Commit들을 대상 Branch의 맨 끝에 하나씩 다시 적용해요. 기록이 일직선으로 깔끔해지지만, 다시 적용된 Commit들은 **새 Hash**를 받아요.
3. 그래서 **이미 push해서 다른 사람이 받아 간 Branch는 rebase하지 않아요**. 팀원의 기록과 내 기록이 어긋나 큰 혼란이 생겨요.
4. **reset**: Branch가 가리키는 위치를 과거 Commit으로 되돌려요. 그 뒤의 Commit은 기록에서 사라져요. 나만 쓰는 Local 작업을 정리할 때 써요.
5. **revert**: 특정 Commit의 내용을 반대로 되돌리는 **새 Commit**을 만들어요. 기록은 지우지 않아요. 이미 공유된 Commit을 취소할 때는 revert를 써요.
| 구분 | 기록을 바꾸나 | 공유된 Branch에서 |
| merge | 안 바꿈 (합류점 추가) | 안전 |
| rebase | 다시 씀 (새 Hash) | 피하기 |
| revert | 안 바꿈 (취소 Commit 추가) | 안전 |
| reset | 다시 씀 (Commit 제거) | 피하기 |
KEY: 원칙 하나만 기억하세요. **"남과 공유한 기록은 다시 쓰지 않는다."** 그래서 공유된 곳에서는 merge와 revert를 써요.
END: 기록을 보존하면 merge·revert, 다시 쓰면 rebase·reset. 공유된 기록은 다시 쓰지 않아요.

#### Branch 전략과 Pull Request
ONE: 팀이 Branch를 어떻게 나누고 합칠지 정한 규칙이 **Branch 전략**이고, 내 변경을 합쳐 달라고 요청하며 **Code Review**를 받는 절차가 **Pull Request(PR)**예요.
LIKE: 여러 작가가 함께 책을 쓸 때, 각자 원고를 따로 쓰고 편집장에게 "이 장을 넣어 주세요"라고 검토를 요청하는 것과 같아요.
STEP:
1. **Git Flow**: main, develop, feature, release, hotfix Branch를 나눠 쓰는 체계적인 전략이에요. 정해진 주기로 버전을 출시하는 제품(앱, 설치형 Software)에 맞아요.
2. **GitHub Flow**: main과 짧게 쓰고 버리는 Feature Branch만 둬요. PR로 합치고 바로 배포해요. 자주 배포하는 웹 서비스에 맞아요.
3. **Trunk-Based Development**: 모두가 main(Trunk)에 아주 자주 작은 단위로 합쳐요. 미완성 기능은 Feature Flag로 숨겨요. CI/CD와 잘 맞아요.
4. **Pull Request**: Feature Branch를 push한 뒤 "main에 합쳐 주세요"라고 요청해요.
5. PR에서는 동료가 코드를 읽고 의견을 남기고(**Code Review**), CI가 자동으로 Test를 돌려요. 통과하면 합쳐요.
WHY: Code Review는 Bug를 일찍 잡고, 팀원끼리 코드를 이해하고 배우는 기회가 돼요.
END: 출시 주기가 정해졌으면 Git Flow, 자주 배포하면 GitHub Flow나 Trunk-Based. 합칠 땐 PR로 Review를 받아요.

### Git의 세 영역과 기본 흐름은?
E: 책상 위(Working Directory)에서 글을 쓰고, 보낼 것만 봉투에 넣고(Staging), 봉투를 봉해 내 서랍에 보관하고(Commit), 우체국(Remote Repository)에 부칩니다(push).
A: Git은 파일을 수정하는 Working Directory, 다음 Commit에 넣을 변경을 모으는 Staging Area(Index), Commit이 저장되는 Local Repository로 나뉩니다. `git add`로 Staging하고 `git commit`으로 저장한 뒤 `git push`로 Remote에 올리며, `git fetch`는 Remote 변경을 가져오기만 하고 `git pull`은 fetch에 merge(또는 설정에 따라 rebase)까지 합니다.

### merge와 rebase의 차이는? reset과 revert는?
E: merge는 두 갈래 길이 만나는 지점에 "합류점" 표지판을 세우는 것이고, rebase는 내 길을 통째로 떼어 상대 길 끝에 다시 이어 붙여 한 줄로 만드는 것입니다.
A: merge는 두 Branch를 합치는 Merge Commit을 만들어 기록(History)을 그대로 보존하고, rebase는 내 Commit들을 대상 Branch 끝에 다시 적용해 일직선 기록을 만들지만 Commit Hash가 새로 바뀝니다. 그래서 이미 push해 남이 쓰는 Branch는 rebase하지 않습니다. 똑같은 이유로 공유된 Commit을 취소할 때는 Branch Pointer를 되돌리는 reset 대신, 반대 내용의 새 Commit을 만드는 revert를 씁니다.

### Git Flow와 GitHub Flow, 그리고 PR은?
A: Git Flow는 main, develop, feature, release, hotfix Branch를 두는 체계적인 전략으로 정해진 주기로 버전을 출시하는 제품에 맞고, GitHub Flow는 main과 짧은 Feature Branch만 두고 PR로 합친 뒤 바로 배포하는 단순한 전략으로 자주 배포하는 웹 서비스에 맞습니다. PR(Pull Request)은 내 Branch의 변경을 합쳐 달라고 요청하면서 Code Review와 자동 Test를 거치는 절차입니다.

## Architecture

#### Software Architecture란? 바꾸기 어려운 결정과 Trade-off
ONE: **Software Architecture**는 **나중에 바꾸기 어려운 큰 결정들**의 모음이에요. 시스템을 어떤 덩어리로 나누고, 덩어리끼리 어떻게 통신하고, 어떤 품질을 우선할지 정해요. 정답은 없고 **모든 선택은 무언가를 얻고 무언가를 잃어요**.
LIKE: 집을 지을 때 벽지 색은 나중에 쉽게 바꾸지만, 기둥 위치나 층수는 한번 정하면 바꾸기 매우 어려워요. Architecture는 이런 "기둥 결정"이에요.
STEP:
1. **Architecture가 다루는 것**: 시스템을 어떤 큰 덩어리(Component, Service)로 나눌지, 덩어리끼리 어떻게 통신할지(함수 호출, Network, Message), 어떤 품질(속도, 안정성, 확장성)을 가장 중요하게 볼지.
2. **Trade-off 사고**: 질문은 "어느 것이 최선인가?"가 아니라 "**이 상황에서 무엇을 얻고 무엇을 잃는가?**"예요.
3. 예 ①: 동기 호출은 단순하고 결과가 바로 맞지만, 상대가 느리면 나도 느려져요. 비동기 Message는 탄력적이지만 오류 처리와 추적이 어려워요.
4. 예 ②: 공통 코드를 공유 Library로 두면 중복은 없지만 배포가 서로 묶여요. 각자 복사하면 독립적이지만 Bug를 여러 번 고쳐야 해요.
5. **Architect가 하는 일**: 핵심 결정을 내리고 그 **이유**를 기록하고, 시스템이 그 결정을 계속 지키는지 확인하고, 비즈니스 요구를 기술 요구로 번역해요.
6. 기술 하나를 깊게 아는 것보다 **많은 기술의 장단점을 넓게** 아는 게 더 중요해져요.
KEY: 결정만큼 **이유**가 중요해요. 이유를 모르면 같은 논쟁을 반복하고, 전제가 바뀌었을 때 결정을 다시 검토할 수 없어요.
END: Architecture는 바꾸기 어려운 큰 결정이고, 핵심 기술은 "무엇을 얻고 무엇을 잃는가"를 따지는 Trade-off 사고예요.

#### Architecture 특성 (품질 속성)
ONE: 시스템이 "**무엇을 하는가**"(기능)와 별개로, "**얼마나 잘 해야 하는가**"를 정하는 것이 Architecture 특성이에요. 가용성, 성능, 확장성, 보안 같은 것들이에요.
LIKE: 자동차의 기능은 "사람을 태우고 달린다"예요. 하지만 스포츠카는 속도를, 트럭은 적재량을, 가족용 차는 안전을 가장 중요하게 봐요. 같은 기능이라도 무엇을 우선하느냐에 따라 설계가 완전히 달라져요.
STEP:
1. **운영 특성**: 가용성(Availability, 얼마나 안 죽나), 성능, 확장성(Scalability), 탄력성(Elasticity, 갑자기 몰리는 부하 대응), 신뢰성, 복구 가능성.
2. **구조 특성**: 유지보수성, 확장 용이성, Test 용이성, 배포 용이성, 이식성.
3. **공통 특성**: 보안, 접근성, 법규 준수, 사용성.
4. **3~7개만 고르기**: 모든 특성을 다 챙기면 시스템이 복잡해져 결국 아무것도 잘 못 해요. 가장 중요한 몇 개만 골라요.
5. **숨은 특성 읽어 내기**: 요구사항에 직접 안 적혀 있는 경우가 많아요. "블랙프라이데이에 주문이 몰린다"에서 탄력성을, "규제 기관 감사가 있다"에서 감사 추적성을 읽어 내야 해요.
6. **측정 가능하게**: "빠르게" 대신 "p95 응답 200ms 이하"처럼 숫자로 정해요. Build Pipeline에 자동 검사(**Fitness Function**)를 넣어 Architecture가 서서히 무너지는 걸 막아요.
WHY: 특성이 Architecture Style 선택을 결정해요. 같은 쇼핑몰도 "확장성 최우선"이면 MSA, "빠른 출시 최우선"이면 Monolith가 맞을 수 있어요.
END: Architecture 특성은 "얼마나 잘"의 기준이에요. 꼭 필요한 3~7개를 골라 숫자로 정하고 자동으로 지켜요.

#### Cohesion과 Coupling (응집도와 결합도)
ONE: **Cohesion(응집도)**은 한 Module 안의 요소들이 **얼마나 같은 목적으로 모여 있는가**(높을수록 좋음), **Coupling(결합도)**은 Module끼리 **얼마나 서로에게 기대는가**(낮을수록 좋음)예요.
LIKE: 잘 정리된 부엌은 칼·도마·냄비가 한곳에 모여 있어요(높은 응집도). 그리고 부엌을 리모델링해도 거실은 손댈 필요가 없어요(낮은 결합도). 반대로 숟가락은 안방에, 냄비는 화장실에 있으면 응집도가 낮고, 부엌을 고치려면 온 집을 뜯어야 하면 결합도가 높은 거예요.
STEP:
1. **높은 Cohesion**: "주문 Module"에는 주문과 관련된 것만 있어요. 무엇을 찾아야 할지, 무엇을 고쳐야 할지 분명해요.
2. **낮은 Cohesion**: "Utils"라는 이름 아래 날짜 계산, 이메일 발송, 결제 처리가 섞여 있어요. 무엇이 어디 있는지 모르고 고치기 무서워요.
3. **낮은 Coupling**: Module끼리 정해진 Interface로만 소통해요. 한쪽 내부를 바꿔도 다른 쪽은 그대로예요.
4. **높은 Coupling**: 다른 Module의 내부 변수나 구현 세부를 직접 건드려요. 하나를 고치면 연쇄적으로 깨져요.
5. **Connascence (공동 변경성)**: "한쪽을 바꾸면 다른 쪽도 바꿔야 하는 관계"를 더 세밀하게 보는 개념이에요. 이름만 맞추면 되는 약한 관계부터, 실행 순서나 타이밍까지 맞춰야 하는 강한 관계까지 있어요. 강한 관계일수록 같은 Module 안에 가깝게 둬요.
6. **많이 쓰이는 Module은 안정적이어야 해요**: 여러 곳이 의존하는 Module을 자주 바꾸면 그 영향이 사방으로 퍼져요. 그래서 그런 Module은 추상적이고 잘 안 바뀌게 만들어요.
WHY: SOLID, Design Pattern, MSA 같은 거의 모든 설계 원칙이 결국 "응집도는 높게, 결합도는 낮게"를 위한 도구예요.
END: 관련된 건 모으고(높은 응집도), 서로는 적게 기대게(낮은 결합도). 좋은 설계의 가장 기본 원칙이에요.

#### Monolithic vs MSA (Microservice Architecture)
ONE: **Monolithic**은 모든 기능을 **하나로 묶어 배포**하고, **MSA**는 기능별로 **작은 Service로 나눠 각자 배포**하고 Network로 통신해요.
LIKE: Monolithic은 모든 매장이 한 건물에 들어간 백화점이에요. 관리가 단순하지만 한 층을 공사하면 건물 전체가 영향을 받아요. MSA는 각자 건물을 가진 상점가예요. 가게별로 고칠 수 있지만, 서로 물건을 주고받기가 복잡해요.
STEP:
1. **Monolithic**: 코드 하나, 배포 하나, DB 하나. 개발·Test·배포가 단순하고, 함수 호출이라 빨라요.
2. Monolith의 한계: 커지면 작은 변경에도 전체를 다시 배포해야 하고, 특정 기능만 따로 확장하기 어렵고, 한 부분의 장애가 전체로 번질 수 있어요.
3. **MSA**: 주문, 결제, 배송처럼 업무 영역별로 Service를 나누고, 각자 독립적으로 배포하고 확장해요. 장애도 한 Service에 갇히기 쉬워요.
4. MSA의 대가: Network 호출이라 느리고 실패할 수 있고, 여러 Service에 걸친 Transaction이 어렵고, Monitoring·로그 추적·배포 같은 운영이 훨씬 복잡해요.
5. **Modular Monolith**: 배포는 하나지만 내부를 업무 영역별 Module로 깔끔하게 나눠요. 대부분의 새 서비스는 여기서 시작하고, 정말 필요할 때 Module을 Service로 떼어 내는 게 안전해요.
| 구분 | Monolithic | MSA |
| 배포 | 전체를 한 번에 | Service별 독립 |
| 확장 | 전체 단위 | 필요한 Service만 |
| 장점 | 단순, 빠른 호출, 쉬운 Transaction | 독립 배포, 부분 확장, 장애 격리 |
| 단점 | 커질수록 변경·배포 부담 | Network 지연, 분산 Transaction, 운영 복잡 |
KEY: "MSA가 최신이니 무조건 좋다"는 틀린 생각이에요. 작은 팀과 초기 서비스에는 Monolith(또는 Modular Monolith)가 더 나은 경우가 많아요.
END: 하나로 묶으면 단순하고, 나누면 독립적이에요. 팀과 서비스 규모에 맞게 골라요.

#### 여러 Architecture Style 한눈에 보기
ONE: Architecture Style은 **전체를 한 번에 배포하는 단일체 계열**과 **여러 단위로 나눠 Network로 통신하는 분산 계열**로 나뉘고, 각각 잘 맞는 상황과 대가가 달라요.
LIKE: 건물 양식이 다양한 것과 같아요. 단독주택, 아파트, 상가 건물, 공장은 각자 목적에 맞게 설계되고, 하나가 모든 용도에 최고일 수는 없어요.
STEP:
1. **Layered (계층형)**: 화면 → 로직 → 데이터 층으로 나눠요. 익숙하고 빨리 시작하기 좋지만, 커지면 기능 하나를 바꾸려고 모든 층을 건드려야 해요.
2. **Modular Monolith**: 배포는 하나, 내부는 업무 영역별 Module. 대부분의 새 서비스 출발점이에요.
3. **Pipeline**: 처리 단계(필터)를 한 방향으로 이어요. 데이터 변환, ETL, Compiler에 맞아요.
4. **Microkernel (Plug-in)**: 작은 핵심 + 갈아 끼우는 Plug-in. IDE(VS Code), 브라우저 확장 기능.
5. **Service-Based**: 큰 Service 4~12개 + 공유 DB. Monolith에서 분산으로 가는 실용적 중간 단계예요.
6. **Event-Driven**: 일이 생기면 Event를 발행하고, 관심 있는 쪽이 구독해 반응해요. 처리량이 높고 결합이 느슨하지만, 오류 처리·순서·추적·Test가 어려워요.
7. **Space-Based**: 데이터를 여러 서버의 Memory에 복제해 두고 DB에는 나중에 반영해요. 티켓 오픈처럼 예측할 수 없는 폭증에 맞지만 구현이 복잡하고 비싸요.
8. **Microservices**: 업무 영역별 작은 Service가 각자 DB를 가져요. 큰 조직, 독립 배포, 부분별 확장에 맞아요.
| Style | 잘 맞는 상황 | 대가 |
| Layered | 작은 앱, 빠른 시작 | 커질수록 수정 범위 넓어짐 |
| Modular Monolith | 대부분의 신규 서비스 | 모듈 경계를 규율로 지켜야 함 |
| Pipeline | 데이터 변환, ETL | 대화형 시스템엔 부적합 |
| Microkernel | IDE, 브라우저, 규칙 엔진 | 핵심 설계가 어려움 |
| Event-Driven | 높은 처리량, 느슨한 결합 | 오류 처리·추적·Test 어려움 |
| Microservices | 큰 조직, 독립 배포 | 운영 복잡, 분산 Transaction |
KEY: 고르는 순서는 ① 업무 영역과 핵심 특성 파악 → ② 모든 부분에 같은 특성이 필요하면 단일체, 부분마다 다르면 분산 고려 → ③ 데이터를 누가 소유할지 → ④ 동기 통신을 기본으로, 확장·탄력이 필요한 곳만 비동기 → ⑤ 팀 구조도 함께 봐요.
END: Style마다 잘 맞는 상황과 대가가 달라요. 특성과 팀 구조를 보고 골라요.

#### Microservice의 세부: 데이터 소유, Saga, Orchestration vs Choreography
ONE: MSA에서는 **Service마다 자기 데이터를 소유**하고, 여러 Service에 걸친 작업은 **중앙 지휘자(Orchestration)**나 **각자 반응(Choreography)**으로 조율하며, 실패하면 **보상 작업(Saga)**으로 되돌려요.
LIKE: 여행 패키지를 예약할 때 항공·호텔·렌터카 회사가 각자 따로 있어요. 여행사 직원이 하나씩 전화해 예약하면 Orchestration, 항공 예약이 되면 호텔이 알림을 듣고 알아서 예약하는 식이면 Choreography예요. 호텔 예약이 실패하면 이미 한 항공 예약을 취소하는 게 Saga예요.
STEP:
1. **데이터 소유**: 각 Service는 자기 DB를 가지고, 다른 Service의 DB를 직접 읽지 않아요. 필요하면 그 Service의 API를 불러요. DB를 공유하면 사실상 다시 하나로 묶여요.
2. **크기 정하기**: "작을수록 좋다"가 아니에요. Transaction 경계, 데이터 공유 필요, 서로 호출하는 빈도를 보고 정해요. 너무 잘게 쪼개면 서로 계속 부르는 **분산 Monolith**가 돼요.
3. **Orchestration**: 중앙 조정 Service가 "1번 해, 다음 2번 해"라고 순서를 지휘해요. 흐름이 한눈에 보이지만 중앙에 의존해요.
4. **Choreography**: 각 Service가 Event를 듣고 알아서 다음 일을 해요. 결합이 느슨하지만 전체 흐름을 파악하기 어려워요.
5. **Saga Pattern**: 여러 Service에 걸친 작업을 각 Service의 작은 Transaction들로 나누고, 중간에 실패하면 이미 끝난 단계를 **반대로 되돌리는 보상 Transaction**을 실행해요. 하나의 거대한 분산 Transaction 대신 쓰는 방법이에요.
6. **필수 운영 도구**: API Gateway(입구 하나로 모으기), Service Mesh(Service 간 통신 관리), 중앙 로그와 분산 추적(요청 하나가 어떤 Service들을 거쳤는지).
END: Service마다 데이터를 소유하고, 지휘(Orchestration)나 반응(Choreography)으로 조율하며, 실패는 보상 작업(Saga)으로 되돌려요.

#### 분산 컴퓨팅의 8가지 착각
ONE: 분산 시스템을 처음 만들 때 사람들이 흔히 **사실이라고 착각하는 8가지**가 있어요. 분산 Architecture를 고르는 순간, 이 8가지가 **모두 거짓**이라는 전제로 설계해야 해요.
LIKE: 택배를 보낼 때 "택배는 항상 도착한다, 바로 도착한다, 얼마든지 보낼 수 있다, 아무도 안 훔쳐 간다"고 믿으면 큰일 나요. 실제로는 분실·지연·도난·용량 제한이 다 있어요.
STEP:
1. **Network는 믿을 만하다** → 실제로는 메시지가 사라지고 연결이 끊겨요. 재시도와 Timeout이 필요해요.
2. **지연(Latency)은 0이다** → Network 호출은 함수 호출보다 수천 배 느려요.
3. **대역폭은 무한하다** → 큰 데이터를 마구 보내면 막혀요.
4. **Network는 안전하다** → 도청과 공격이 있어요. 암호화와 인증이 필요해요.
5. **구성은 변하지 않는다** → 서버가 추가·제거되고 주소가 바뀌어요.
6. **관리자는 한 명이다** → 여러 팀과 회사가 각자 관리해요.
7. **전송 비용은 0이다** → 데이터 전송과 직렬화에는 돈과 CPU가 들어요.
8. **Network는 균질하다** → 서로 다른 장비, OS, Protocol이 섞여 있어요.
WHY: Monolith 안의 함수 호출을 Network 호출로 바꾸는 순간, 이 모든 문제가 새로 생겨요. MSA의 대가가 큰 이유예요(분산 시스템의 문제는 11번 주제에서 더 다뤄요).
END: 분산 시스템에서는 "Network는 느리고, 끊기고, 위험하고, 계속 바뀐다"고 가정하고 설계해요.

#### ADR과 Conway's Law
ONE: **ADR(Architecture Decision Record)**은 **중요한 결정 하나당 짧은 문서 하나**로 이유를 남기는 방법이고, **Conway's Law**는 **시스템 구조가 조직의 소통 구조를 닮아 간다**는 관찰이에요.
LIKE: ADR은 가족이 집을 고칠 때 "왜 이 벽을 텄는지" 메모를 남겨 두는 거예요. 몇 년 뒤 다른 사람이 "이 벽 왜 없지?" 할 때 메모를 보면 알 수 있어요.
STEP:
1. **ADR 구성**: 제목, 상태(제안·승인·대체됨), 맥락(어떤 압력과 제약이 있었나), 결정(무엇을 하기로 했나), 결과(얻는 것과 잃는 것).
2. ADR은 코드 저장소에 함께 둬요. 위키나 메일에 흩어 두면 같은 논쟁이 반복돼요.
3. 결정이 바뀌면 옛 ADR을 지우지 않고 "대체됨"으로 표시하고 새 ADR을 써요. 결정의 역사가 남아요.
4. **Conway's Law**: "시스템을 설계하는 조직은 그 조직의 소통 구조를 닮은 시스템을 만든다." 팀이 셋이면 시스템도 세 덩어리가 되기 쉬워요.
5. 그래서 원하는 Architecture에 맞게 팀을 나누기도 해요(Inverse Conway Maneuver). MSA를 하려면 Service를 끝까지 책임지는 팀 구조가 필요해요.
6. **리스크 분석과 다이어그램**: 리스크는 "발생 가능성 × 영향"으로 평가하고, 다이어그램은 확대 수준을 나눠(C4 Model: 시스템 맥락 → 컨테이너 → 컴포넌트 → 코드) 대상에 맞게 보여 줘요.
END: 결정의 이유는 ADR로 남기고, 시스템 구조는 팀 구조를 닮는다는 걸(Conway's Law) 기억해요.

#### Third-Party Library와 외부 API
ONE: **Third-Party**는 우리가 아닌 외부에서 만든 Library나 Service(결제, 지도, 소셜 로그인)예요. 개발 시간을 크게 줄여 주지만, **우리가 통제할 수 없다는 위험**을 함께 관리해야 해요.
LIKE: 외부 업체에 배달을 맡기면 직접 배달원을 두지 않아도 돼서 편해요. 하지만 그 업체가 파업하거나 요금을 올리면 우리 가게도 영향을 받아요. 그래서 계약 조건을 확인하고, 다른 업체로 바꿀 수 있게 준비해 둬요.
STEP:
1. **License 확인**: 상업적으로 써도 되는지, 소스 공개 의무가 있는지(GPL 등) 확인해요.
2. **보안과 유지보수**: 알려진 취약점이 있는지, 최근까지 관리되고 있는지 확인해요. 버려진 Library는 위험해요.
3. **버전 호환성**: 업데이트하면 사용법이 바뀌어 우리 코드가 깨질 수 있어요. 버전을 고정하고 신중히 올려요.
4. **외부 장애 대비**: 외부 API가 느리거나 죽으면 우리 서비스도 멈출 수 있어요. Timeout, Retry, 대체 동작(Fallback)을 둬요.
5. **Adapter로 감싸기**: 외부 Library를 우리 코드 곳곳에서 직접 부르지 말고, Adapter 하나로 감싸 두면 나중에 다른 업체로 바꿀 때 한 곳만 고치면 돼요.
END: Third-Party는 시간을 아껴 주지만 통제 밖이에요. License·보안·호환성을 확인하고, Adapter와 Timeout으로 위험을 가둬요.

### Monolithic과 MSA(Microservice Architecture)의 차이는?
E: Monolithic은 모든 매장이 한 건물에 들어간 백화점, MSA는 각자 건물을 가진 상점가입니다. 백화점은 관리가 단순하지만 한 층을 공사하면 건물 전체가 영향을 받고, 상점가는 가게별로 나눠 고칠 수 있지만 서로 물건을 주고받기가 복잡합니다.
A: Monolithic은 모든 기능을 하나의 배포 단위로 만들어 개발·Test·배포가 단순하지만, 커질수록 작은 변경에도 전체를 다시 배포해야 하고 부분만 확장하기 어렵습니다. MSA는 기능별로 독립 배포되는 작은 Service가 API로 통신하여 독립 배포·부분 확장(Scaling)·장애 격리(Fault Isolation)가 가능하지만, Network Latency, Distributed Transaction, Monitoring·운영 복잡도가 커집니다. 작은 팀과 초기 서비스에는 Monolithic이 더 나은 경우가 많습니다.

### Third-Party Library·외부 API를 쓸 때 주의할 점은?
A: Third-Party는 우리가 아닌 외부에서 만든 Library나 Service(결제, 지도, Social Login)로, 개발 시간을 크게 줄여 줍니다. 대신 License, 보안 취약점·유지보수 여부, 버전 변경 시 호환성(Compatibility), 외부 장애가 내 서비스에 미치는 영향을 확인해야 하며, Adapter로 감싸 교체하기 쉽게 두고 Timeout·Retry를 둡니다.

### Architecture 특성(품질 속성)이란? 어떻게 정하나요?
E: 같은 "사람을 태우고 달리는" 자동차라도 스포츠카는 속도, 트럭은 적재량, 가족용 차는 안전을 가장 중요하게 보듯, 기능과 별개로 "얼마나 잘"의 기준을 정하는 것입니다.
A: Architecture 특성은 기능과 별개로 시스템이 갖춰야 할 품질로, 가용성·성능·확장성·탄력성 같은 운영 특성, 유지보수성·Test 용이성·배포 용이성 같은 구조 특성, 보안·법규 준수 같은 공통 특성이 있습니다. 모두 챙기면 복잡해지므로 가장 중요한 3~7개만 고르고, 요구사항 속 숨은 특성(예: 이벤트 폭주 → 탄력성)을 읽어 내며, "p95 200ms 이하"처럼 측정 가능하게 정의해 Fitness Function으로 자동 검사합니다.

### Cohesion과 Coupling이란?
E: 칼·도마·냄비가 부엌 한곳에 모여 있으면 응집도가 높고, 부엌을 고쳐도 거실을 건드릴 필요가 없으면 결합도가 낮은 것입니다.
A: Cohesion(응집도)은 한 Module 안의 요소들이 같은 목적을 위해 얼마나 모여 있는지로 높을수록 좋고, Coupling(결합도)은 Module끼리 서로 얼마나 의존하는지로 낮을수록 좋습니다. 높은 응집도는 이해와 변경을 쉽게 하고, 낮은 결합도는 한 부분의 변경이 다른 부분으로 퍼지지 않게 합니다. SOLID, Design Pattern, MSA의 경계 설정은 모두 이 목표를 위한 도구입니다.

### Saga Pattern이란? Orchestration과 Choreography의 차이는?
E: 항공·호텔·렌터카를 차례로 예약하다 호텔이 실패하면 이미 한 항공 예약을 취소하는 것이 Saga이고, 여행사 직원이 순서대로 지휘하면 Orchestration, 각 회사가 알림을 듣고 알아서 움직이면 Choreography입니다.
A: Saga는 여러 Service에 걸친 작업을 Service별 Local Transaction들의 연속으로 나누고, 중간에 실패하면 이미 완료된 단계를 되돌리는 Compensating Transaction(보상 트랜잭션)을 실행해 전체 일관성을 맞추는 Pattern입니다. Orchestration은 중앙 Orchestrator가 각 단계를 지휘해 흐름이 명확하지만 중앙에 의존하고, Choreography는 각 Service가 Event를 구독해 스스로 다음 단계를 진행해 결합이 느슨하지만 전체 흐름을 추적하기 어렵습니다.

## QUIZ

? 정사각형 Class가 직사각형을 상속했는데, 너비만 바꾸는 코드에 넣으면 높이까지 바뀌어 결과가 틀립니다. 어떤 원칙 위반인가요?
- Single Responsibility
- Interface Segregation
- Liskov Substitution
- Dependency Inversion
= C
! Child(정사각형)를 Parent(직사각형) 자리에 넣었을 때 Parent의 약속(너비와 높이는 따로 바뀜)이 깨지므로 Liskov Substitution 원칙 위반입니다.

? 커피 Object를 우유, 시럽 Object로 감싸 가격과 설명에 기능을 덧붙이는 구조는?
- Decorator
- Singleton
- Factory Method
- Template Method
= A
! 같은 Interface로 감싸며 기능을 겹겹이 덧붙이는 것이 Decorator입니다.

? 주문 상태가 바뀌면 메일·문자·앱 Push가 자동으로 알림을 받게 하려면 어떤 Pattern이 어울리나요?
- Adapter
- Builder
- Proxy
- Observer
= D
! 하나의 상태 변화를 여러 Subscriber에게 자동으로 알리는 일대다 관계가 Observer입니다.

? TDD의 올바른 순서는?
- 코드 작성 → Test → 배포
- 실패하는 Test → 통과시키는 최소 코드 → Refactoring
- 설계 문서 → 코드 → Test
- Refactoring → Test → 코드
= B
! Red(실패하는 Test) → Green(통과) → Refactor(정리)의 반복입니다.

? 이미 Remote에 push해 팀원들이 받아 간 Branch에서 피해야 하는 것은?
- rebase로 Commit 기록을 다시 쓰기
- revert로 취소 Commit 만들기
- 새 Commit 추가
- PR 열기
= A
! rebase는 Commit Hash를 바꿔 팀원의 기록과 어긋나게 만듭니다. revert는 기록을 지우지 않고 취소 Commit을 덧붙이므로 안전합니다.

? Test에서 "메일 발송 Method가 정확히 1번 호출되었는지"를 검증하는 Test Double은?
- Dummy
- Stub
- Fake
- Mock
= D
! Mock은 호출 여부·횟수·Argument 같은 Behavior를 검증합니다. Stub은 정해진 값만 돌려줍니다.

? Test를 통과한 변경이 사람의 승인 없이 운영 환경까지 자동 배포됩니다. 이것은?
- CI(Continuous Integration)만 한 상태
- Continuous Deployment (지속적 배포)
- Continuous Delivery (지속적 전달)
- Waterfall Model
= B
! 운영 배포까지 자동이면 Continuous Deployment, 배포 준비까지만 자동이고 운영 배포는 사람이 승인하면 Continuous Delivery입니다.
