## Web 동작 원리

#### Browser가 화면을 그리는 과정 (Rendering)
ONE: Browser는 HTML로 **구조(DOM)**를, CSS로 **꾸밈 규칙(CSSOM)**을 만들고, 둘을 합쳐 **위치를 계산(Layout)**한 뒤 **색을 칠해(Paint)** 화면을 그려요.
LIKE: 인테리어 공사와 같아요. 도면(HTML)으로 방 구조를 만들고, 색상표(CSS)로 꾸밈 규칙을 정하고, 가구 자리를 재고(Layout), 페인트를 칠해요(Paint). 가구를 옮기면 자리를 다시 재야 해서 비싼 작업이에요.
STEP:
1. **HTML Parsing → DOM**: HTML 태그들을 읽어 Tree 모양의 **DOM(Document Object Model)**을 만들어요. JavaScript는 이 DOM을 고쳐서 화면을 바꿔요.
2. **CSS Parsing → CSSOM**: CSS 규칙을 읽어 "어떤 요소에 어떤 스타일"인지 담은 CSSOM을 만들어요.
3. **Render Tree**: DOM과 CSSOM을 합쳐 실제로 화면에 보일 요소들만 모아요(`display: none`은 빠져요).
4. **Layout (Reflow)**: 각 요소의 정확한 위치와 크기를 계산해요.
5. **Paint**: 글자, 색, 테두리, 그림자를 픽셀로 칠해요.
6. **Composite**: 여러 층(Layer)을 겹쳐 최종 화면을 만들어요.
7. **JavaScript의 영향**: 일반 `<script>` 태그를 만나면 HTML 읽기를 멈추고 Script를 내려받아 실행해요. 그래서 `defer`나 `async`를 붙이거나 Script를 아래에 둬요.
KEY: 요소의 크기나 위치를 바꾸는 DOM 조작은 Layout을 다시 하게 만들어 비싸요. 여러 변경을 한 번에 모아 하거나, 위치 이동은 `transform`처럼 Layout을 건드리지 않는 방법을 쓰면 빨라져요.
END: HTML → DOM, CSS → CSSOM, 합쳐서 Layout → Paint → Composite. Layout을 덜 다시 하게 만드는 게 성능의 핵심이에요.

#### CSR과 SSR
ONE: **CSR**은 Browser가 JavaScript로 **화면을 직접 만들고**, **SSR**은 Server가 **완성된 HTML을 만들어** 보내요. 첫 화면 속도, 검색 노출, Server 부담이 달라요.
LIKE: CSR은 가구를 부품 상태로 받아 집에서 조립하는 것이고, SSR은 완성된 가구를 배달받는 거예요. 조립식은 처음엔 오래 걸리지만, 한 번 조립하면 배치를 바꾸기 쉬워요.
STEP:
1. **CSR (Client-Side Rendering)**: Server가 거의 빈 HTML과 큰 JavaScript 파일을 보내요. Browser가 JS를 실행해 데이터를 받아 화면을 만들어요.
2. CSR 장점: 처음 한 번 받고 나면 페이지 전환이 빠르고 앱처럼 부드러워요. 단점: 첫 화면이 늦게 뜨고, 검색 엔진이 빈 HTML만 볼 수 있어 SEO(검색 노출)에 불리할 수 있어요.
3. **SSR (Server-Side Rendering)**: Server가 데이터를 넣어 완성된 HTML을 만들어 보내요. 첫 화면이 빨리 보이고 SEO에 유리해요.
4. SSR 단점: 요청마다 Server가 HTML을 만들어 부담이 커요. 그리고 화면이 보여도 버튼이 동작하려면 JS를 붙이는 **Hydration** 과정이 필요해요.
5. **SSG (Static Site Generation)**: 빌드할 때 HTML을 미리 다 만들어 두는 방식이에요. 블로그나 문서처럼 잘 안 바뀌는 페이지에 좋아요.
6. Next.js 같은 Framework는 페이지마다 CSR·SSR·SSG를 골라 섞어 써요.
END: Browser에서 조립하면 CSR(전환 빠름), Server에서 완성하면 SSR(첫 화면·SEO 유리), 미리 만들어 두면 SSG예요.

#### Web Server와 WAS
ONE: **Web Server**는 이미 만들어진 파일(HTML, 이미지)을 빠르게 건네주고, **WAS**는 코드를 실행해 **그때그때 결과를 만들어요**.
LIKE: Web Server는 미리 만들어 둔 샌드위치를 건네는 편의점 직원이고, WAS는 주문을 받아 그때그때 요리하는 주방이에요.
STEP:
1. **Static Content**: 누가 요청해도 똑같은 파일이에요. HTML, CSS, JS, 이미지.
2. **Dynamic Content**: 요청마다 다른 결과예요. "내 주문 목록"은 DB를 조회해 만들어야 해요.
3. **Web Server (Nginx, Apache)**: Static 파일을 아주 빠르게 보내고, 앞에서 요청을 받아 뒤로 넘겨주는 **Reverse Proxy**, 여러 Server로 나누는 **Load Balancing**, HTTPS 암호를 푸는 **TLS Termination**을 맡아요.
4. **WAS (Web Application Server, Tomcat 등)**: Application 코드를 실행해서 DB 조회, 로그인 처리 같은 Dynamic 작업을 해요.
5. **함께 쓰는 구조**: Web Server를 앞에 두고, Static 요청은 Web Server가 직접 처리하고 Dynamic 요청만 WAS로 넘겨요. WAS의 부담이 줄고, WAS를 외부에 직접 노출하지 않아 안전해요.
END: 파일 건네기는 Web Server, 계산해서 만들기는 WAS. 보통 Web Server를 앞에, WAS를 뒤에 둬요.

#### Web Framework로 서버 만들기 (Flask 예시)
ONE: **Web Framework**는 "이 주소로 요청이 오면 이 함수를 실행하라"(**Routing**)를 중심으로, 화면 틀 채우기(Template), 로그인 상태 기억(Session) 같은 반복 작업을 대신 해 주는 도구예요.
LIKE: 식당 운영 매뉴얼과 같아요. "1번 테이블 주문은 한식 요리사에게, 2번은 양식 요리사에게"(Routing), "메뉴판 양식에 오늘 메뉴만 채워 넣기"(Template), "단골손님 기억하기"(Session)가 미리 정리돼 있어요.
STEP:
1. **Routing**: URL 경로마다 처리할 함수를 연결해요. Flask에서는 `@app.route("/hello")` Decorator를 함수 위에 붙여요.
2. **Request 처리**: 함수는 요청 정보(URL 파라미터, Form 데이터)를 읽고, 필요하면 DB를 조회해요.
3. **Template**: HTML 틀에 데이터를 채워 넣어 완성된 페이지를 만들어요(Flask는 Jinja2). `<h1>{{ name }}님 안녕하세요</h1>`.
4. **Session**: 로그인 상태를 기억해요. Flask의 기본 Session은 서명된 Cookie에 담겨서 위조는 막지만 내용은 읽힐 수 있으니 민감한 정보는 넣지 않아요.
5. **구조**: 보통 데이터(Model)·화면(View/Template)·처리 로직(Controller)으로 나누는 MVC 계열 구조를 따라요(10번 주제).
6. **비밀번호는 절대 그대로 저장하지 않고** 느린 Hash로 저장해요(아래 Security 개념).
```python
from flask import Flask, render_template

app = Flask(__name__)

@app.route("/hello/<name>")          # 이 주소로 오면
def hello(name):                     # 이 함수를 실행
    return render_template("hello.html", name=name)
```
USE: Python의 Flask·Django·FastAPI, JavaScript의 Express, Java의 Spring이 모두 같은 생각이에요.
END: Web Framework = Routing(주소 → 함수) + Template(틀 채우기) + Session(상태 기억). 반복 작업을 대신 해 줘요.

#### Native App · Web App · Hybrid App · PWA
ONE: 앱을 만드는 방법은 **기기 전용 언어로 만들기(Native)**, **웹사이트로 만들기(Web)**, **웹을 앱 껍데기에 넣기(Hybrid)**, **웹에 앱 기능 더하기(PWA)** 등이 있어요.
LIKE: Native는 그 나라 말로 직접 쓴 책, Web App은 어디서나 읽히는 인터넷 기사, Hybrid는 인터넷 기사를 책 표지로 감싼 것, PWA는 인터넷 기사인데 책장에 꽂아 두고 오프라인에서도 읽을 수 있게 한 거예요.
STEP:
1. **Native App**: iOS는 Swift, Android는 Kotlin처럼 플랫폼 언어로 각각 만들어요. 성능이 가장 좋고 기기 기능(카메라, 센서)을 전부 쓸 수 있어요. 대신 두 번 만들어야 하고 Store 심사를 거쳐요.
2. **Web App**: Browser에서 도는 웹사이트예요. 설치가 필요 없고 한 번 만들면 모든 기기에서 돌아가요. 기기 기능과 성능에 제한이 있어요.
3. **Hybrid App**: Native 껍데기 안에 WebView(앱 속 Browser)를 넣어 웹 코드를 실행해요. 웹 코드를 재사용하면서 Store에 올릴 수 있어요.
4. **PWA (Progressive Web App)**: Service Worker와 Manifest를 갖춘 웹이에요. 홈 화면에 설치하고, 오프라인 Cache, Push 알림을 쓸 수 있어요. 플랫폼마다 지원 범위가 달라요(특히 iOS).
5. **Cross-Platform (React Native, Flutter)**: 한 코드로 양쪽 앱을 만들어요. WebView가 아니라 Native UI나 자체 그리기 엔진을 써서 Hybrid와 구분해요.
END: 성능·기능은 Native, 비용·접근성은 Web, 그 사이가 Hybrid·PWA·Cross-Platform이에요.

### Browser는 HTML을 어떻게 화면에 그리나요?
E: 인테리어 공사와 같습니다. 도면(HTML)으로 방 구조를 만들고, 색상표(CSS)로 꾸밈 규칙을 정하고, 가구 자리를 재고(Layout), 페인트를 칠합니다(Paint). 가구를 옮기면 자리를 다시 재야 하므로 비싼 작업입니다.
A: Browser는 HTML을 Parsing해 DOM Tree를, CSS를 Parsing해 CSSOM을 만들고, 둘을 합친 Render Tree로 각 요소의 위치와 크기를 계산(Layout, Reflow)한 뒤 픽셀을 칠하고(Paint) Layer를 합성(Composite)합니다. 일반 script 태그는 HTML Parsing을 멈추게 하므로 defer나 async를 쓰고, Layout을 바꾸는 DOM 조작을 줄여 Reflow를 적게 하는 것이 성능의 핵심입니다.

### CSR과 SSR의 차이는?
E: CSR은 가구를 부품 상태로 받아 집에서 조립하는 것이고, SSR은 완성된 가구를 배달받는 것입니다. 조립식은 처음에 오래 걸리지만 한 번 조립하면 배치를 바꾸기 쉽습니다.
A: CSR(Client-Side Rendering)은 Server가 거의 빈 HTML과 JS를 보내고 Browser가 JS로 화면을 만들어, 초기 Loading이 느리고 SEO(검색 엔진 최적화)에 불리하지만 이후 페이지 전환이 빠릅니다. SSR(Server-Side Rendering)은 Server가 완성된 HTML을 만들어 보내 첫 화면이 빠르고 SEO에 유리하지만 Server 부담이 커지고, 화면이 반응하려면 JS를 붙이는 Hydration이 필요합니다. Next.js 같은 Framework는 페이지마다 둘을 섞거나 미리 만들어 두는 SSG(Static Site Generation)를 씁니다.

### Web Server와 WAS의 차이는?
E: Web Server는 미리 만들어 둔 샌드위치를 건네는 편의점 직원이고, WAS는 주문을 받아 그때그때 요리하는 주방입니다.
A: Web Server(Nginx, Apache)는 HTML·이미지 같은 Static File을 빠르게 주고, Reverse Proxy·Load Balancing·HTTPS 처리(TLS Termination)를 맡습니다. WAS(Web Application Server, Tomcat 등)는 Application 코드를 실행해 DB 조회 같은 Dynamic 처리를 합니다. 보통 Web Server를 앞에 두어 Static 요청은 직접 처리하고 Dynamic 요청만 WAS로 넘겨 부담을 나누고 WAS를 외부에서 감춥니다.

### Native App·Web App·Hybrid App·PWA의 차이는?
| 종류 | 만드는 방식 | 장점 | 단점 |
| Native App | 플랫폼 언어(Swift, Kotlin)로 각각 개발 | 성능 최고, 기기 기능 전부 사용 | iOS·Android 따로 개발, Store 심사 |
| Web App | Browser에서 실행되는 웹사이트 | 설치 없음, 한 번 개발로 모든 기기 | 기기 기능·성능 제한 |
| Hybrid App | Native 껍데기 안에 WebView를 넣음 | 웹 코드 재사용 + Store 배포 | Native보다 느릴 수 있음 |
| PWA (Progressive Web App) | Service Worker·Manifest를 갖춘 웹 | 홈 화면 설치, Offline Cache, Push | 플랫폼별 지원 범위 차이(특히 iOS) |
A: Native는 성능과 기기 기능이, Web은 개발·배포 비용이 강점이고, Hybrid와 PWA는 그 사이에서 웹 기술로 앱에 가까운 경험을 내는 방식입니다. React Native·Flutter는 한 코드로 양쪽 플랫폼 앱을 만드는 Cross-Platform 방식으로, WebView가 아닌 Native UI 또는 자체 Rendering Engine을 써서 Hybrid와 구분합니다.

## Authentication과 Authorization

#### Authentication과 Authorization
ONE: **Authentication(인증)**은 "**누구세요?**"를 확인하는 것이고, **Authorization(인가)**은 "**그걸 해도 되나요?**"를 확인하는 것이에요. 인증이 먼저, 인가가 뒤예요.
LIKE: 호텔 프런트에서 신분증을 보여 주는 게 인증이고, 받은 카드키로 7층 내 방만 열 수 있는 게 인가예요.
STEP:
1. **Authentication**: 사용자가 정말 그 사람인지 확인해요. 비밀번호(아는 것), OTP·휴대폰(가진 것), 지문·얼굴(나 자신).
2. 이 중 두 가지 이상을 함께 쓰면 **MFA(다중 인증)**예요. 비밀번호가 털려도 휴대폰이 없으면 못 들어와요.
3. **Authorization**: 인증된 사용자가 특정 자원이나 기능에 접근할 권한이 있는지 확인해요. 일반 회원은 관리자 페이지에 못 들어가요.
4. 권한 관리 방식: 역할(관리자, 편집자, 일반)별로 권한을 주는 **RBAC**가 가장 흔해요.
5. **HTTP 상태 코드**: 인증이 안 됐으면 **401 Unauthorized**(로그인 필요), 인증은 됐지만 권한이 없으면 **403 Forbidden**(접근 금지).
KEY: 401의 이름은 "Unauthorized"지만 실제 뜻은 "인증 안 됨"이에요. 이름이 헷갈리니 뜻으로 기억하세요.
END: 인증 = 누구인가(401), 인가 = 무엇을 할 수 있나(403).

#### Session 기반 인증 vs Token 기반 인증
ONE: **Session** 방식은 **Server가 로그인 정보를 저장**하고 Client는 번호표만 들고 다니고, **Token** 방식은 **Token 자체에 정보와 서명**을 담아 Server는 서명만 확인해요.
LIKE: Session은 목욕탕 사물함 열쇠예요. 열쇠에는 번호만 있고 짐은 가게(Server)가 보관해요. Token은 놀이공원 팔찌예요. 팔찌 자체에 "자유이용권, 오늘까지"가 적혀 있고, 직원은 위조 방지 도장만 확인해요.
STEP:
1. **Session 방식**: 로그인하면 Server가 사용자 정보를 저장하고 **Session ID**를 Cookie로 줘요. 요청마다 Session ID로 저장소를 찾아 누군지 알아요.
2. Session 장점: Server에서 Session을 지우면 즉시 강제 로그아웃할 수 있어요. 단점: Server가 여러 대면 어느 Server로 가도 Session을 찾을 수 있게 공유 저장소(Redis 등)가 필요해요.
3. **Token 방식**: 로그인하면 Server가 사용자 정보를 담고 **서명한 Token**(보통 JWT)을 줘요. 요청마다 Token을 보내면 Server는 서명만 검증해요. Server가 따로 저장할 게 없어요(**Stateless**).
4. Token 장점: Server를 늘리기 쉽고, 여러 서비스가 같은 Token을 검증할 수 있어요. 단점: 한 번 발급한 Token은 만료 전에 무효화하기 어려워요.
5. **Access Token + Refresh Token**: 짧은 수명(예: 15분)의 Access Token으로 요청하고, 만료되면 긴 수명의 Refresh Token으로 새 Access Token을 받아요. 털려도 피해 시간을 줄이고, Refresh Token만 Server에서 관리하면 로그아웃도 할 수 있어요.
| 구분 | Session | Token (JWT) |
| 상태 저장 | Server | Token 자체 (Stateless) |
| 확장 | 공유 Session 저장소 필요 | 쉬움 |
| 강제 로그아웃 | 쉬움 | 어려움 (짧은 만료 + Refresh로 보완) |
END: Server가 기억하면 Session(통제 쉬움), Token이 들고 다니면 Stateless(확장 쉬움)예요.

#### JWT (JSON Web Token)
ONE: **JWT**는 **Header.Payload.Signature** 세 부분을 점으로 이은 Token이에요. Signature가 **위조는 막지만**, 내용은 **누구나 읽을 수 있어요**.
LIKE: 투명한 봉투에 넣고 봉인 도장을 찍은 편지예요. 누구나 내용을 읽을 수 있지만, 도장이 깨지면 누가 고쳤다는 걸 바로 알 수 있어요.
STEP:
1. **Header**: 어떤 서명 방식(Algorithm)을 썼는지.
2. **Payload**: 사용자 ID, 권한, 만료 시간(exp) 같은 정보(**Claim**).
3. **Signature**: Header와 Payload를 Secret Key(HMAC)나 Private Key(RSA·ECDSA)로 서명한 값.
4. 세 부분을 각각 **Base64URL**로 바꿔 점(.)으로 이어요: `xxxxx.yyyyy.zzzzz`.
5. Server는 받은 Token의 Header와 Payload로 서명을 다시 계산해 Signature와 비교해요. 누가 Payload를 조금이라도 고치면 서명이 안 맞아 거부돼요.
6. **Base64URL은 Encoding이지 Encryption이 아니에요**. 누구나 Payload를 풀어 읽을 수 있어서, 비밀번호나 개인정보를 넣으면 안 돼요.
KEY: 만료 시간을 짧게 두고, HTTPS로만 주고받고, Cookie에 담을 때는 HttpOnly·Secure·SameSite를 붙여요. Server는 Header의 Algorithm을 그대로 믿지 말고 허용한 방식만 받아들여야 해요.
END: JWT는 "읽을 수 있지만 고칠 수 없는" 서명된 Token이에요. 비밀은 넣지 마세요.

#### OAuth 2.0과 OpenID Connect
ONE: **OAuth 2.0**은 사용자가 **비밀번호를 넘기지 않고**, 다른 앱에 **자기 자원에 대한 제한된 권한을 빌려주는** 방법이에요. "구글로 로그인" 같은 로그인에는 그 위에 **OpenID Connect**를 써요.
LIKE: 발레파킹 키와 같아요. 차 주인은 집 열쇠까지 달린 마스터키(비밀번호) 대신, 주차만 할 수 있는 발레 전용 키(Access Token)를 건네요.
STEP:
1. 예: 일정 관리 앱이 내 Google 캘린더를 읽고 싶어요. 앱에 Google 비밀번호를 주면 위험해요.
2. 앱이 나를 **Google 로그인 화면(Authorization Server)**으로 보내요. 나는 Google에 직접 로그인하고 "캘린더 읽기 권한을 줄까요?"에 동의해요.
3. Google이 앱에 일회용 **Authorization Code**를 줘요(Browser를 거쳐 전달).
4. 앱의 Server가 이 Code를 Google에 보내 **Access Token**으로 바꿔요. 이 교환은 Server끼리 해서 Token이 Browser에 노출되지 않아요.
5. 앱은 Access Token으로 **Resource Server**(Google 캘린더 API)를 호출해요. Token은 "캘린더 읽기"만 할 수 있고, 내가 언제든 권한을 취소할 수 있어요.
6. **OIDC (OpenID Connect)**: OAuth는 원래 "권한 위임"용이에요. "이 사람이 누구인지"까지 확인하는 로그인용으로는 OAuth 위에 OIDC를 얹어 **ID Token**을 함께 받아요.
END: OAuth = 비밀번호 대신 제한된 열쇠(Access Token)를 빌려주기. 로그인까지 하려면 OIDC를 더해요.

### Authentication(인증)과 Authorization(인가)의 차이는?
E: 호텔 프런트에서 신분증을 보여 주는 것이 Authentication(누구인가), 받은 카드키로 7층 내 방만 열 수 있는 것이 Authorization(무엇을 할 수 있는가)입니다.
A: Authentication은 사용자가 누구인지 확인하는 것(비밀번호, OTP, 생체 인식)이고, Authorization은 인증된 사용자가 특정 자원에 접근할 권한이 있는지 확인하는 것입니다. Authentication이 먼저이고 Authorization이 뒤따르며, HTTP에서는 인증 실패가 401, 권한 없음이 403입니다.

### Session 기반 인증과 Token 기반 인증의 차이는?
E: Session은 목욕탕 사물함 열쇠입니다. 열쇠에는 번호만 있고 짐은 가게(Server)가 보관합니다. Token은 놀이공원 팔찌입니다. 팔찌 자체에 "자유이용권, 오늘까지"가 적혀 있고 직원은 위조 방지 도장만 확인합니다.
A: Session 방식은 Server가 로그인 정보를 저장하고 Client는 Session ID만 Cookie로 들고 다녀, 강제 로그아웃이 쉽지만 Server가 여러 대면 Session 저장소(Redis 등)를 공유해야 합니다. Token 방식은 Server가 서명한 Token에 사용자 정보를 담아 주고 요청마다 서명만 검증하므로 Server가 상태를 저장하지 않아(Stateless) 확장이 쉽지만, 발급한 Token을 만료 전에 무효화하기 어렵습니다. 그래서 짧은 수명의 Access Token과 긴 수명의 Refresh Token을 함께 씁니다.

### JWT의 구조와 주의할 점은?
A: JWT(JSON Web Token)는 Header(Algorithm), Payload(사용자 ID·만료 시간 같은 Claim), Signature를 점(.)으로 잇고 각각 Base64URL로 Encoding한 Token입니다. Signature는 Secret Key(HMAC)나 Private Key(RSA·ECDSA)로 만들어 위변조를 막지만, Encoding은 Encryption이 아니라 누구나 내용을 읽을 수 있으므로 비밀번호 같은 민감 정보를 넣으면 안 됩니다. 만료 시간을 짧게 두고 HTTPS로만 주고받으며, Cookie에 담을 때는 HttpOnly·Secure·SameSite 속성을 줍니다.

### OAuth 2.0이란? 어떻게 동작하나요?
E: 발레파킹 키입니다. 차 주인은 집 열쇠까지 달린 마스터키(비밀번호) 대신, 주차만 할 수 있는 발레 전용 키(Access Token)를 건넵니다.
A: OAuth 2.0은 사용자가 비밀번호를 넘기지 않고 제3의 앱에 자신의 자원(구글 캘린더 등)에 대한 제한된 접근 권한을 위임하는 Authorization Framework입니다. 대표적인 Authorization Code 방식에서는 앱이 사용자를 Authorization Server로 보내 로그인·동의를 받고, Authorization Server가 돌려준 Authorization Code를 앱의 Server가 Access Token으로 교환한 뒤 그 Token으로 Resource Server의 API를 호출합니다. OAuth 자체는 Authorization용이며, "구글로 로그인" 같은 Authentication에는 그 위에 OpenID Connect(OIDC)를 씁니다.

## Security

#### Hash와 Encryption, 그리고 비밀번호 저장
ONE: **Encryption**은 Key가 있으면 **되돌릴 수 있는** 변환이고, **Hash**는 **되돌릴 수 없는** 단방향 변환이에요. 비밀번호는 원문이 필요 없으니 **Salt를 붙인 느린 Hash**로 저장해요.
LIKE: Encryption은 열쇠가 있으면 열 수 있는 금고예요. Hash는 믹서기예요. 주스를 과일로 되돌릴 수는 없지만, 같은 과일을 넣으면 늘 같은 주스가 나오니까 "이 주스가 사과로 만든 건가?"는 확인할 수 있어요.
STEP:
1. **Encryption (암호화)**: Key로 암호문을 만들고, Key로 다시 원문을 꺼내요(Decryption). 다시 읽어야 하는 데이터(메시지, 카드 정보 등)에 써요.
2. **Hash**: 어떤 길이의 입력이든 고정 길이 값으로 바꿔요. 같은 입력은 항상 같은 Hash, 조금만 달라도 완전히 다른 Hash, 그리고 Hash에서 입력을 거꾸로 알아낼 수 없어요.
3. **비밀번호 확인**: 로그인할 때 입력한 비밀번호를 같은 방식으로 Hash해서 저장된 Hash와 비교해요. 원문은 어디에도 없어요.
4. **Rainbow Table 공격**: 흔한 비밀번호들의 Hash를 미리 계산해 둔 표로 거꾸로 찾는 공격이에요.
5. **Salt**: 사용자마다 다른 무작위 값을 비밀번호에 붙여 Hash해요. 같은 비밀번호라도 Hash가 달라져서 미리 만든 표가 쓸모없어져요.
6. **느린 Hash**: SHA-256은 너무 빨라서 공격자가 1초에 수십억 개를 시도할 수 있어요. 그래서 **bcrypt, scrypt, Argon2**처럼 일부러 느리게 만든 함수를 써요.
KEY: 비밀번호를 AES로 "암호화"해서 저장하면 Key가 털리는 순간 모든 비밀번호가 풀려요. Base64는 아예 누구나 되돌리는 Encoding이에요. 정답은 Salt + 느린 Hash예요.
END: 되돌려야 하면 Encryption, 확인만 하면 Hash. 비밀번호는 Salt + bcrypt·Argon2 같은 느린 Hash예요.

#### Digital Signature와 Certificate
ONE: **Digital Signature**는 **Private Key로 서명하고 Public Key로 누구나 검증**해서 "누가 보냈고, 내용이 안 바뀌었다"를 증명하는 방법이고, **Certificate**는 "이 Public Key는 진짜 이 사이트 것"이라고 **인증 기관(CA)이 보증**한 문서예요.
LIKE: Digital Signature는 주인만 찍을 수 있는 인감을 누구나 대조해 볼 수 있는 거예요. Certificate는 "이 인감은 진짜 이 사람 것"이라고 구청이 보증해 주는 인감증명서예요.
STEP:
1. 복습: **Symmetric Key**는 같은 Key로 잠그고 열어 빠르지만 나누기 어렵고(AES), **Public Key**는 공개 Key로 잠그고 개인 Key로만 열어 나누기 쉽지만 느려요(RSA, ECC).
2. **서명하기**: 메시지의 Hash를 만들고, 그 Hash를 **내 Private Key**로 서명해요.
3. **검증하기**: 받는 사람은 **내 Public Key**로 서명을 풀어 나온 Hash와, 받은 메시지로 직접 만든 Hash를 비교해요. 같으면 "이 사람이 보냈고 내용이 안 바뀌었다"가 증명돼요.
4. **문제**: 그 Public Key가 진짜 그 사람 것인지 어떻게 알까요? 가짜가 자기 Public Key를 "은행 Key"라고 속일 수 있어요.
5. **Certificate**: 믿을 수 있는 **CA(Certificate Authority)**가 "이 Public Key는 bank.com의 것"이라고 자기 Private Key로 서명한 문서예요.
6. Browser와 OS에는 믿을 수 있는 CA 목록이 미리 들어 있어서, Certificate의 서명을 검증할 수 있어요. 이게 HTTPS가 상대 Server를 믿는 원리예요(04번 주제).
USE: HTTPS 인증서, 앱 서명(설치 파일이 위조되지 않았는지), 전자 계약, Git Commit 서명.
END: 서명은 개인 Key로, 검증은 공개 Key로. 그 공개 Key가 진짜임을 CA가 Certificate로 보증해요.

#### XSS와 CSRF
ONE: **XSS**는 공격자의 Script가 **다른 사용자의 Browser에서 실행**되는 공격이고, **CSRF**는 로그인된 사용자의 Browser가 **원치 않는 요청을 보내게** 만드는 공격이에요.
LIKE: XSS는 게시판에 "읽는 순간 당신의 지갑을 나에게 주시오"라는 주문서를 붙여, 읽는 사람의 Browser가 실행하게 만드는 거예요. CSRF는 로그인해 둔 사람에게 위장된 링크를 누르게 해, 그 사람 명의로 송금 요청이 나가게 만드는 거예요.
STEP:
1. **XSS (Cross-Site Scripting)**: 공격자가 게시글이나 댓글에 `<script>`를 넣어요. 사이트가 그걸 그대로 화면에 출력하면, 그 글을 보는 모든 사용자의 Browser에서 Script가 실행돼 Cookie를 훔치거나 화면을 조작해요.
2. **XSS 막기**: 출력할 때 `<`, `>` 같은 특수 문자를 무해한 글자로 바꿔요(**HTML Escape**). Script가 어디서 올 수 있는지 제한하는 **CSP**를 설정하고, Cookie에 **HttpOnly**를 붙여 Script가 못 읽게 해요.
3. **CSRF (Cross-Site Request Forgery)**: Browser는 사이트에 요청할 때 그 사이트의 Cookie를 자동으로 붙여요. 공격자 사이트에 숨겨 둔 "송금 요청" Form이 내 은행 Cookie와 함께 보내지면, 은행은 내가 보낸 줄 알아요.
4. **CSRF 막기**: 요청마다 예측할 수 없는 **CSRF Token**을 함께 보내게 하기, Cookie에 **SameSite** 속성 붙이기(다른 사이트에서 온 요청엔 Cookie를 안 보냄), Origin Header 확인, 송금 같은 중요한 작업은 비밀번호 다시 묻기.
KEY: 한 줄 요약: **XSS는 사이트가 사용자 입력을 믿어서**, **CSRF는 사이트가 Browser(Cookie)를 믿어서** 생겨요.
END: 남의 Browser에서 내 Script가 돌면 XSS(Escape로 막기), 남의 Browser가 몰래 요청을 보내면 CSRF(Token·SameSite로 막기)예요.

#### CORS와 Same-Origin Policy (다시 보기)
ONE: Browser는 다른 출처의 응답을 Script가 읽지 못하게 막고(**Same-Origin Policy**), Server가 허락 Header를 보내면 풀어 줘요(**CORS**). 보안 기능이지 오류가 아니에요.
LIKE: Browser는 "다른 가게에서 온 물건은 그 가게가 허락했을 때만 받는다"는 보안 요원이에요.
STEP:
1. **Origin** = Scheme(Protocol) + Host + Port. 셋 중 하나라도 다르면 다른 Origin이에요.
2. Same-Origin Policy가 없으면, 내가 방문한 악성 사이트의 Script가 내 로그인 정보로 은행 API를 불러 응답을 읽어 갈 수 있어요.
3. **CORS**: Server가 `Access-Control-Allow-Origin` Header로 "이 Origin은 허용"이라고 알려 주면 Browser가 응답을 넘겨줘요.
4. 데이터를 바꾸는 요청 등은 Browser가 먼저 `OPTIONS` 요청(**Preflight**)으로 허락을 확인해요.
5. CORS 오류를 고치는 곳은 **응답하는 Server의 설정**이에요(04번 주제에서 자세히 다뤘어요).
END: 다른 출처는 기본 차단(SOP), Server가 허락하면 통과(CORS)예요.

#### Principle of Least Privilege (최소 권한 원칙)
ONE: 사람·프로그램·서비스 계정에게 **일하는 데 꼭 필요한 최소한의 권한만** 주는 원칙이에요.
LIKE: 청소 담당 직원에게는 청소 도구 창고 열쇠만 주고, 금고 열쇠는 주지 않아요. 열쇠를 잃어버려도 피해가 창고에서 끝나요.
STEP:
1. 조회만 하는 서비스의 DB 계정에는 SELECT 권한만 줘요. 해킹당해도 데이터를 지우거나 고칠 수 없어요.
2. 직원은 자기 업무에 필요한 시스템에만 접근하게 해요.
3. 관리자 권한은 필요할 때만 잠시 받아 쓰고 반납해요.
4. 이렇게 하면 해킹이나 실수가 생겨도 피해가 퍼지는 범위(**Blast Radius**)가 작아져요.
USE: 클라우드 IAM 권한 설정, DB 계정 분리, 컨테이너를 root가 아닌 일반 사용자로 실행하기, 앱의 권한 요청(위치, 카메라)을 꼭 필요한 것만.
END: 필요한 열쇠만 주면, 열쇠를 잃어도 피해가 작아요.

### Hash와 Encryption의 차이는? 비밀번호는 어떻게 저장하나요?
E: Encryption(암호화)은 자물쇠가 있는 금고라 열쇠가 있으면 되돌릴 수 있고, Hash는 믹서기라 주스를 과일로 되돌릴 수 없습니다. 다만 같은 과일을 넣으면 늘 같은 주스가 나오므로 "이 주스가 사과로 만든 것인가"는 확인할 수 있습니다.
A: Encryption은 Key로 다시 Decryption할 수 있는 양방향 변환이고, Hash는 임의 길이 입력을 고정 길이 값으로 바꾸는 되돌릴 수 없는 단방향(One-Way) 변환입니다. 비밀번호는 원문을 알 필요가 없으므로 Hash로 저장하되, 사용자마다 다른 랜덤 값인 Salt를 붙여 미리 계산한 Hash 표(Rainbow Table) 공격을 막고, SHA-256 같은 빠른 Hash 대신 bcrypt·scrypt·Argon2처럼 일부러 느린 함수를 써서 Brute Force(무차별 대입)를 어렵게 합니다.

### Symmetric Key·Public Key Encryption과 Digital Signature, Certificate는?
E: Public Key는 누구나 넣을 수 있는 우체통 구멍, Private Key는 주인만 가진 우체통 열쇠입니다. Digital Signature는 반대로, 주인만 찍을 수 있는 인감을 누구나 대조해 볼 수 있는 것이고, Certificate(인증서)는 "이 인감은 진짜 이 사람 것"이라고 구청(CA)이 보증하는 서류입니다.
A: Symmetric Key는 같은 Key로 Encryption·Decryption해 빠르지만 Key를 안전하게 나누기 어렵고(AES), Public Key는 Public Key로 암호화하고 Private Key로만 복호화해 Key Exchange 문제를 풀지만 느립니다(RSA, ECC). Digital Signature는 메시지의 Hash를 Private Key로 서명하고 Public Key로 검증해 보낸 사람과 위변조 여부를 확인하며, Certificate는 CA(Certificate Authority)가 "이 Public Key는 이 Domain의 것"이라고 서명한 문서입니다. HTTPS는 Certificate로 Server를 확인하고 Key Exchange 후 Symmetric Key로 데이터를 암호화합니다(04 Network 참고).

### XSS와 CSRF는 무엇이고 어떻게 막나요?
E: XSS는 게시판에 "읽는 순간 당신의 지갑을 나에게 주시오"라는 주문서를 붙여 읽는 사람의 Browser가 실행하게 만드는 것이고, CSRF는 로그인해 둔 사람에게 위장된 링크를 누르게 해 그 사람 명의로 송금 요청을 보내게 만드는 것입니다.
A: XSS(Cross-Site Scripting)는 공격자가 넣은 Script가 다른 사용자의 Browser에서 실행되어 Cookie·Session을 훔치는 공격으로, 출력할 때 HTML Escape, CSP(Content Security Policy), HttpOnly Cookie로 막습니다. CSRF(Cross-Site Request Forgery)는 Browser가 Cookie를 자동으로 보내는 점을 이용해 로그인된 사용자가 원치 않는 요청을 보내게 하는 공격으로, CSRF Token, SameSite Cookie, Origin Header 확인, 중요한 작업의 재인증으로 막습니다. 요약하면 XSS는 사이트가 입력을 믿어서, CSRF는 사이트가 Browser를 믿어서 생깁니다.

### CORS란?
A: Browser는 보안을 위해 Scheme(Protocol)·Host·Port가 모두 같은 Origin(출처)으로만 Script가 응답을 읽게 하는 Same-Origin Policy를 적용합니다. CORS는 Server가 Access-Control-Allow-Origin 같은 Header로 "이 Origin은 허용한다"고 알려 다른 Origin의 요청을 안전하게 허락하는 방식이며, 특정 요청은 본 요청 전에 OPTIONS Preflight로 허락을 먼저 확인합니다.

### Principle of Least Privilege(최소 권한 원칙)란?
A: 사용자·프로그램·Service Account에 일을 하는 데 꼭 필요한 최소한의 권한만 주는 원칙입니다. 예를 들어 조회만 하는 서비스의 DB 계정에는 SELECT 권한만 주면, 해킹이나 실수가 생겨도 피해 범위(Blast Radius)가 줄어듭니다.

## System Design

#### 부하와 성능을 숫자로 말하기: Percentile과 Tail Latency
ONE: 서비스의 부하는 **초당 요청 수 같은 구체적인 숫자**로, 응답 속도는 **평균이 아니라 Percentile(p50, p99)**로 말해요. 가장 느린 사용자의 경험이 전체를 좌우하기 때문이에요.
LIKE: 반 평균 점수가 80점이어도, 몇 명은 30점일 수 있어요. 응답 시간도 평균이 빨라도 일부 사용자는 아주 오래 기다릴 수 있어요. p99는 "가장 운 나쁜 1%의 사용자"가 얼마나 기다리는지를 보여 줘요.
STEP:
1. **부하를 숫자로**: 초당 요청 수(RPS, QPS), 읽기:쓰기 비율, 동시 접속자 수, 저장 데이터 양.
2. **평균의 함정**: 대부분 0.1초인데 가끔 10초가 걸려도 평균은 괜찮아 보일 수 있어요.
3. **Percentile**: 응답 시간을 줄 세웠을 때의 위치예요. **p50(중앙값)**은 보통 사용자, **p99**는 100명 중 가장 느린 1명, **p999**는 1000명 중 가장 느린 1명의 경험이에요.
4. **Tail Latency 증폭**: 요청 하나가 뒤에서 여러 Server를 동시에 부르면, 그중 **하나만 느려도** 전체가 느려져요. Server가 많을수록 "누군가 하나는 느릴" 확률이 커져서, 꼬리 지연이 사용자 체감을 지배해요.
5. 그래서 목표를 "p99 응답 300ms 이하"처럼 Percentile로 정하고 Monitoring해요(**SLO**).
KEY: 많은 요청을 하는 사용자(예: 장바구니가 큰 VIP 고객)일수록 느린 요청을 겪을 확률이 높아서, p99를 개선하는 게 중요한 고객의 경험을 개선하는 경우가 많아요.
END: 부하는 구체적 숫자로, 속도는 평균 대신 p50·p99로 말해요. 가장 느린 꼬리가 체감을 정해요.

#### Scale-Up vs Scale-Out
ONE: 부하가 늘면 **Server 한 대를 더 좋게 바꾸거나(Scale-Up)**, **Server 대수를 늘려요(Scale-Out)**.
LIKE: 손님이 늘었을 때 요리사 한 명을 더 빠른 사람으로 바꾸면 Scale-Up, 요리사를 여러 명 더 두면 Scale-Out이에요.
STEP:
1. **Scale-Up (Vertical Scaling, 수직 확장)**: CPU, Memory, Disk를 더 좋은 것으로 바꿔요. 코드나 구조를 바꿀 필요가 없어 간단해요.
2. Scale-Up의 한계: 살 수 있는 가장 큰 Server에도 한계가 있고, 비싸지고, 그 한 대가 죽으면 서비스 전체가 멈춰요(SPOF).
3. **Scale-Out (Horizontal Scaling, 수평 확장)**: 같은 Server를 여러 대 두고 앞에서 요청을 나눠요. 이론상 계속 늘릴 수 있고 한 대가 죽어도 나머지가 버텨요.
4. Scale-Out의 조건: 요청을 나눌 **Load Balancer**가 필요하고, 어느 Server로 가도 같은 결과가 나오도록 Server가 상태를 갖지 않게(**Stateless**) 만들어야 해요. Session은 Redis 같은 공유 저장소에 둬요.
5. **DB는 Scale-Out이 어려워요**: 상태(데이터) 자체를 가진 곳이라, Replication과 Sharding 같은 복잡한 방법이 필요해요(09번 주제).
END: 한 대를 키우면 Scale-Up(간단, 한계 있음), 여러 대로 늘리면 Scale-Out(무한 확장, Stateless 필요)이에요.

#### Load Balancer (다시 보기)
ONE: 요청을 여러 Server에 **나눠 주고**, 죽은 Server는 **자동으로 빼는** 안내원이에요. Scale-Out의 필수 부품이에요.
LIKE: 손님이 몰리는 식당 입구 직원이 빈 테이블로 안내하고, 고장 난 테이블에는 손님을 앉히지 않는 것과 같아요.
STEP:
1. 사용자는 Load Balancer 주소로만 접속해요. 뒤에 Server가 몇 대인지 몰라도 돼요.
2. **Health Check**로 Server가 살아 있는지 주기적으로 확인하고, 죽은 Server로는 보내지 않아요.
3. **나누는 방법**: Round Robin(차례대로), Least Connections(연결이 가장 적은 곳으로), IP Hash(같은 사용자는 같은 Server로).
4. **L4**는 IP·Port만 보고 빠르게, **L7**은 URL·Header·Cookie까지 보고 `/api`는 A, `/images`는 B처럼 똑똑하게 나눠요(04번 주제).
5. Load Balancer 자체도 한 대면 SPOF가 되니 이중화해요.
END: Load Balancer는 요청을 나누고 죽은 Server를 빼는 안내원이에요. 이것도 이중화해요.

#### Cache 전략과 CDN
ONE: **Cache**는 자주 읽는 데이터를 **빠른 곳에 복사**해 두는 것이고, **CDN**은 사진·영상 같은 파일을 **사용자 가까운 곳에 복사**해 두는 거예요.
LIKE: 자주 쓰는 양념을 창고가 아니라 조리대 옆에 두는 게 Cache이고, 전국 각지에 물류 창고를 두어 가까운 곳에서 배송하는 게 CDN이에요.
STEP:
1. **Cache-Aside (가장 흔함)**: 앱이 Cache를 먼저 봐요. 있으면(Hit) 바로 쓰고, 없으면(Miss) DB에서 읽어 Cache에 넣어 둬요.
2. **Write-Through**: 쓸 때 Cache와 DB에 함께 써요. 항상 일치하지만 쓰기가 느려요.
3. **Write-Back**: Cache에 먼저 쓰고 나중에 DB에 모아 써요. 빠르지만 Cache가 죽으면 유실될 수 있어요.
4. **Cache의 어려움**: 원본이 바뀌면 Cache는 옛 값을 가지고 있어요. 그래서 만료 시간(**TTL**)을 정하고, 원본이 바뀔 때 Cache를 지우는(**Invalidation**) 정책이 핵심이에요.
5. **CDN (Content Delivery Network)**: 이미지, 동영상, JS 같은 Static 파일을 전 세계의 **Edge Server**에 복사해 둬요. 서울 사용자는 서울 근처 Server에서 받으니 빠르고, 원래 Server(Origin)의 부담도 줄어요.
KEY: 유명한 농담처럼 "컴퓨터 과학에서 어려운 건 Cache 무효화와 이름 짓기, 두 가지뿐"이에요. Cache를 쓸 땐 "얼마나 옛 데이터를 허용할지"를 먼저 정해요.
END: 자주 읽는 데이터는 Cache, 무거운 파일은 CDN으로 가까이 둬요. 핵심 과제는 언제 새로 고칠지(TTL, Invalidation)예요.

#### Message Queue와 Message Broker
ONE: **Message Queue**는 보내는 쪽이 넣은 메시지를 받는 쪽이 **자기 속도대로 나중에** 꺼내 처리하게 하는 중간 저장소예요. 서비스 사이를 느슨하게 연결하고, 몰리는 요청을 받아 줘요.
LIKE: 식당의 주문서 꽂이예요. 홀 직원은 주문서를 꽂고 바로 다음 손님을 받고, 주방은 자기 속도대로 하나씩 처리해요.
STEP:
1. **Producer**가 메시지를 넣고, **Consumer**가 꺼내 처리해요. 둘은 서로를 직접 몰라도 돼요(**Decoupling**).
2. **비동기 처리**: 회원 가입 후 환영 메일 발송, 업로드한 이미지 변환처럼 오래 걸리는 일은 Queue에 넣고 사용자에게는 바로 응답해요.
3. **완충 장치**: 요청이 갑자기 몰려도 Queue가 받아 두고 Consumer가 천천히 처리해서 서비스가 무너지지 않아요.
4. **두 종류의 Broker**: 처리된 메시지를 지우는 **전통적 Queue**(RabbitMQ 등, 작업 분배에 좋음)와, 메시지를 순서대로 Log에 남겨 여러 Consumer가 각자 읽은 위치를 기억하며 읽는 **Log 기반 Broker**(Kafka 등, 다시 읽기와 순서 보장에 좋음).
5. **주의할 점**: Network 문제로 같은 메시지가 두 번 올 수 있어요. 그래서 같은 메시지를 두 번 처리해도 결과가 같도록(**Idempotency**) 만들어야 해요. 예: 주문 ID로 이미 처리했는지 확인.
END: Message Queue는 주문서 꽂이예요. 서비스를 느슨하게 잇고, 오래 걸리는 일을 미루고, 폭주를 흡수해요. 중복 처리에 대비해 Idempotent하게 만들어요.

#### Availability와 SPOF
ONE: **Availability(가용성)**는 시스템이 **정상 동작하는 시간의 비율**이고, **SPOF(단일 장애점)**는 **그것 하나가 죽으면 전체가 죽는** 부품이에요.
LIKE: 다리가 하나뿐인 섬은 그 다리가 무너지면 고립돼요(SPOF). 다리를 두 개 놓으면 하나가 무너져도 다닐 수 있어요(이중화).
STEP:
1. **Availability 숫자 감각**: 99.9%는 1년에 약 8.8시간, 99.99%는 약 53분까지 멈출 수 있다는 뜻이에요. 9가 하나 늘 때마다 허용 시간이 10분의 1로 줄어요.
2. **SPOF 찾기**: Server 한 대, DB 한 대, Load Balancer 한 대, 데이터센터 한 곳처럼 "이게 죽으면 끝"인 곳을 찾아요.
3. **이중화 (Redundancy)**: 같은 역할을 하는 것을 두 개 이상 둬요.
4. **자동 Failover**: 주 장비가 죽으면 예비 장비로 자동 전환해요. 사람이 밤에 일어나 전환하면 늦어요.
5. **지역 분산**: 여러 Availability Zone(독립된 데이터센터)이나 지역에 나눠 배치해 정전·화재에도 버텨요.
KEY: 9를 하나 더 늘릴 때마다 비용이 크게 늘어요. 서비스에 정말 필요한 가용성 수준을 정하고 그만큼만 투자해요.
END: 가용성은 "얼마나 안 멈추나"이고, SPOF를 찾아 이중화와 자동 전환으로 없애요.

#### System Design 면접 5단계
ONE: System Design 면접은 정답 맞히기가 아니라 **요구사항을 정리하고, 규모를 추정하고, 큰 그림을 그리고, 핵심을 깊게 파고, 병목과 Trade-off를 말하는** 과정을 보는 자리예요.
LIKE: 건축가가 집을 설계할 때 "몇 명이 살아요? 예산은요?"부터 묻고, 대략적인 크기를 정하고, 평면도를 그린 다음, 중요한 부분(주방, 계단)을 자세히 설계하고, 약점(누수, 화재)을 점검하는 순서와 같아요.
STEP:
1. **요구사항 정리**: 핵심 기능은? 사용자 수는? 읽기와 쓰기 비율은? 얼마나 빨라야 하나? 바로 그리지 말고 먼저 질문해요.
2. **규모 추정 (Back-of-the-Envelope)**: 초당 요청 수, 저장 용량, 대역폭을 대략 계산해요. 예: 하루 1억 요청 ≈ 초당 약 1,200개.
3. **큰 그림 (High-Level Design)**: Client → Load Balancer → Application Server → Cache → DB, 필요하면 Message Queue·CDN. 상자와 화살표로 전체 흐름을 그려요.
4. **핵심 부분 깊게**: 데이터 모델(Table 설계), Sharding Key, Replication, Cache 무효화 방법 등 이 서비스의 핵심을 자세히 설계해요.
5. **병목과 장애**: SPOF는 없나? Hot Spot은? 트래픽이 10배가 되면? 각 선택의 대안과 Trade-off를 말해요.
KEY: 처음부터 완벽한 설계를 그리려 하지 말고, 간단한 버전에서 시작해 규모가 커질 때 어디가 막히는지 단계적으로 개선하는 모습을 보여 주세요. 면접관이 보는 건 사고 과정이에요.
END: 요구사항 → 규모 추정 → 큰 그림 → 핵심 깊게 → 병목과 Trade-off. 질문하고 말하면서 설계해요.

#### 예시: URL 단축 서비스 설계
ONE: 긴 URL을 **짧은 코드**로 바꿔 주는 서비스예요. 고유 ID를 **Base62**로 바꾸고, 조회가 훨씬 많으니 **Cache**를 적극적으로 써요.
LIKE: 도서관에서 긴 책 제목 대신 짧은 청구기호를 붙이는 것과 같아요. 청구기호만 알면 그 책이 어디 있는지 바로 찾아요.
STEP:
1. **요구사항**: 긴 URL을 받아 짧은 URL을 만들고, 짧은 URL로 들어오면 원래 URL로 보내요. 조회가 쓰기보다 훨씬 많아요(Read-Heavy).
2. **짧은 코드 만들기**: 새 URL마다 고유 ID(1, 2, 3, …)를 발급하고, 이를 **Base62**(0-9, a-z, A-Z 총 62글자)로 바꿔요. 7자리면 62⁷ ≈ 3.5조 개를 만들 수 있어요.
3. **저장**: "코드 → 원래 URL"을 DB에 저장해요.
4. **조회**: 자주 쓰이는 코드는 Redis에 Cache해서 DB까지 가지 않고 바로 응답해요.
5. **Redirect**: **301**(영구 이동)이면 Browser가 기억해서 Server 부하가 적고, **302**(임시 이동)면 매번 Server를 거쳐서 클릭 통계를 모을 수 있어요. 목적에 따라 골라요.
6. **확장**: 트래픽이 늘면 Application Server를 Scale-Out하고, DB는 코드 기준으로 Sharding해요. 고유 ID 발급은 여러 Server가 겹치지 않게 범위를 나눠 미리 받아 두는 식으로 해요.
END: ID → Base62 → 저장 → Cache → Redirect. Read-Heavy라서 Cache가 핵심이에요.

### Scale-Up과 Scale-Out의 차이는?
E: 손님이 늘었을 때 요리사 한 명을 더 빠른 사람으로 바꾸면 Scale-Up, 요리사를 여러 명 더 두면 Scale-Out입니다.
A: Scale-Up(Vertical Scaling, 수직 확장)은 Server의 CPU·Memory를 키우는 것으로 구조 변경이 없어 간단하지만 Hardware 한계가 있고 그 Server가 SPOF가 됩니다. Scale-Out(Horizontal Scaling, 수평 확장)은 Server 대수를 늘리는 것으로 이론상 한계가 적고 장애에 강하지만, Load Balancer가 필요하고 Server가 상태(Session 등)를 갖지 않도록(Stateless) 설계해야 합니다.

### Load Balancer란? L4와 L7의 차이는?
A: Load Balancer는 들어오는 요청을 여러 Server에 나눠 보내고, Health Check로 죽은 Server를 빼서 부하 분산과 Availability를 높입니다. 분배 방식에는 차례대로 나누는 Round Robin, 연결이 가장 적은 Server로 보내는 Least Connections, Client IP로 Server를 고정하는 IP Hash가 있습니다. L4는 IP·Port만 보고 빠르게 나누고, L7은 URL·Header·Cookie 같은 HTTP 내용을 보고 /api는 A Server, /images는 B Server처럼 정교하게 나눌 수 있습니다.

### Cache 전략과 CDN은?
E: 자주 쓰는 양념을 창고가 아니라 조리대 옆에 두는 것이 Cache이고, 전국 각지에 물류 창고를 두어 가까운 곳에서 배송하는 것이 CDN입니다.
A: 가장 흔한 Cache-Aside는 앱이 Cache를 먼저 보고 없으면(Cache Miss) DB에서 읽어 Cache에 넣는 방식이고, Write-Through는 쓸 때 Cache와 DB에 함께 쓰며, Write-Back은 Cache에 먼저 쓰고 나중에 DB에 모아 쓰지만 장애 시 유실 위험이 있습니다. Cache는 원본과 달라질 수 있으므로 TTL(Time To Live, 만료 시간)과 Invalidation(무효화) 정책이 핵심입니다. CDN(Content Delivery Network)은 이미지·동영상·JS 같은 Static Content를 사용자와 가까운 Edge Server에 복사해 Latency와 Origin Server 부하를 줄입니다.

### Message Queue는 왜 쓰나요?
E: 식당의 주문서 꽂이입니다. 홀 직원은 주문서를 꽂고 바로 다음 손님을 받고, 주방은 자기 속도대로 하나씩 처리합니다.
A: Message Queue(Kafka, RabbitMQ)는 Producer가 넣은 Message를 Consumer가 나중에 꺼내 처리하게 하는 중간 저장소입니다. Service 사이 결합을 느슨하게 하고(Decoupling), 메일 발송·이미지 변환 같은 오래 걸리는 일을 Asynchronous로 돌리며, 갑자기 몰린 요청을 Buffer처럼 받아 두어 서비스가 무너지지 않게 합니다. 대신 Message 중복·순서 문제를 고려해 같은 Message를 두 번 처리해도 결과가 같도록(Idempotency) 만들어야 합니다.

### Availability와 SPOF(Single Point of Failure)란?
A: Availability(가용성)는 시스템이 정상 동작하는 시간의 비율로, 99.9%는 1년에 약 8.8시간, 99.99%는 약 53분까지 멈출 수 있다는 뜻입니다. SPOF(단일 장애점)는 그것 하나가 멈추면 전체가 멈추는 구성 요소이며, Server·DB·Load Balancer를 이중화(Redundancy)하고 자동 Failover(장애 조치), 여러 Availability Zone에 분산 배치해 없앱니다.

### URL 단축 서비스를 설계해 보세요.
A: 긴 URL을 받으면 고유 ID를 발급해 Base62(0-9, a-z, A-Z)로 Encoding한 짧은 코드를 만들고 "코드 → 원래 URL"을 DB에 저장합니다. 7자리면 62⁷ ≈ 3.5조 개를 만들 수 있고, 조회가 쓰기보다 훨씬 많으므로(Read-Heavy) 자주 쓰는 코드를 Redis에 Cache합니다. 사용자가 짧은 링크로 들어오면 301(영구, Browser가 기억해 Server 부하가 적음) 또는 302(임시, 매번 Server를 거쳐 클릭 통계를 모을 수 있음)로 Redirect하고, Traffic이 늘면 Server를 Scale-Out하고 DB를 코드 기준으로 Sharding합니다.

### p99 같은 Percentile 응답 시간을 보는 이유는?
E: 반 평균이 80점이어도 30점인 학생이 있을 수 있듯, 평균 응답 시간이 빨라도 일부 사용자는 아주 오래 기다릴 수 있습니다.
A: 평균은 소수의 매우 느린 요청을 가리기 때문에, 응답 시간을 정렬한 Percentile로 봅니다. p50은 보통 사용자, p99·p999는 가장 느린 1%·0.1% 사용자의 경험입니다. 요청 하나가 여러 Backend를 부르면 그중 하나만 느려도 전체가 느려지는 Tail Latency Amplification 때문에 꼬리 지연이 체감 성능을 좌우하므로, SLO를 "p99 300ms 이하"처럼 Percentile로 정하고 Monitoring합니다.

### System Design 면접은 어떤 순서로 진행하나요?
E: 건축가가 "몇 명이 살아요?"부터 묻고, 크기를 정하고, 평면도를 그리고, 중요한 부분을 자세히 설계하고, 약점을 점검하는 순서입니다.
A: 먼저 기능·사용자 수·읽기/쓰기 비율·지연 목표 같은 요구사항을 질문으로 정리하고, 초당 요청 수·저장 용량·대역폭을 대략 추정합니다. 그다음 Client, Load Balancer, Service, Cache, DB, Queue로 High-Level Design을 그리고, 데이터 모델·Sharding Key·Replication·Cache 무효화 같은 핵심을 깊게 설계한 뒤, SPOF·Hot Spot·10배 트래픽 상황의 병목과 대안의 Trade-off를 설명합니다.

## 분산 시스템과 데이터 처리

#### 분산 시스템에서 생기는 문제들
ONE: 여러 컴퓨터가 Network로 협력하는 분산 시스템에서는 **메시지가 사라지거나 늦고**, **시계가 서로 어긋나고**, **프로그램이 갑자기 멈췄다 깨어날** 수 있어요. 그래서 한 컴퓨터의 판단만 믿으면 안 돼요.
LIKE: 멀리 떨어진 친구들과 편지로만 약속을 정한다고 생각해 보세요. 편지가 분실되거나 늦게 도착하고, 각자의 시계가 몇 분씩 다르고, 누군가 잠깐 졸다 깨어나서 이미 끝난 약속을 아직 유효하다고 믿을 수도 있어요.
STEP:
1. **Network 문제**: 메시지는 사라지거나, 늦거나, 두 번 올 수 있어요. 답이 없을 때 상대가 **죽은 건지 느린 건지 구분할 수 없어요**. Timeout은 추측일 뿐이에요.
2. **시계 문제**: 각 컴퓨터의 시계는 조금씩 어긋나고, 시간 동기화 때문에 **뒤로 갈** 수도 있어요. "더 늦은 시각에 쓴 게 최신"이라고 시계로 순서를 정하면 데이터를 잃을 수 있어요.
3. **해결: 논리 시계**: 실제 시각 대신 사건마다 증가하는 번호(**Lamport Timestamp**)로 순서를 정하거나, Google Spanner처럼 오차 범위를 아는 시계를 써요.
4. **프로세스 멈춤**: Garbage Collection 등으로 프로세스가 몇 초 멈췄다 깨어나면, 그 사이 다른 Node가 새 Leader가 됐는데도 자기가 아직 Leader라고 믿고 행동할 수 있어요.
5. **해결: Fencing Token**: Leader가 될 때마다 1씩 커지는 번호를 받고, 저장소는 이미 본 번호보다 작은 번호의 요청을 거부해요. 깨어난 옛 Leader의 쓰기가 막혀요.
6. **진실은 다수결로**: Node 하나는 자기가 살아 있는지조차 확신할 수 없어요. 그래서 중요한 결정은 **과반수(Quorum)** 동의로 정해요.
END: 분산 시스템에서는 Network·시계·프로세스 모두 믿을 수 없다고 가정하고, 논리 시계·Fencing Token·다수결로 대응해요.

#### Consistency Model과 Consensus (합의)
ONE: **Consistency Model**은 복제본이 여럿일 때 사용자에게 **얼마나 "하나처럼" 보이게 할지**의 약속이고, **Consensus**는 여러 Node가 **하나의 값에 동의**하는 문제예요. Raft, Paxos가 대표적인 합의 Algorithm이에요.
LIKE: 반 친구들이 소풍 장소를 정할 때, 일부가 연락이 안 돼도 과반수가 동의하면 결정하는 규칙이 Consensus예요. 한 번 정한 장소는 나중에 연락된 친구도 따라야 하고요.
STEP:
1. **Linearizability (선형성)**: 복제본이 여럿이어도 마치 **복사본이 하나뿐인 것처럼** 보이게 하는 가장 강한 약속이에요. 누가 값을 바꾼 순간부터 모두가 새 값을 봐요. Leader 선출, Lock, 중복 금지(유일성 제약)에 필요해요.
2. Network가 끊기면 선형성과 가용성 중 하나를 포기해야 해요(CAP의 핵심, 09번 주제).
3. **Causal Consistency (인과적 일관성)**: 원인과 결과의 순서만 지키는 더 약한 약속이에요. "원글 다음에 답글"은 지키지만, 서로 상관없는 일의 순서는 보장하지 않아요. 대신 Network가 끊겨도 가용성을 유지할 수 있어요.
4. **Consensus**: 여러 Node가 하나의 값(누가 Leader인가, 이 Transaction을 COMMIT할까)에 동의하는 문제예요. **Raft**, **Paxos**, **Zab**이 대표 Algorithm이고, **과반수 Node가 살아 있어야** 진행돼요. 5대 중 3대가 살아 있으면 돼요.
5. **2PC (Two-Phase Commit)**: 여러 DB에 걸친 Transaction을 원자적으로 COMMIT하는 방법이에요. 조정자가 "준비됐니?"(Prepare) 묻고 모두 "예"면 "COMMIT해"를 보내요. 하지만 조정자가 중간에 죽으면 참여자들이 Lock을 쥔 채 무한정 기다릴 수 있어요.
6. 실무에서는 합의를 직접 구현하지 않고 **ZooKeeper**, **etcd** 같은 조정 서비스에 맡겨요. Kubernetes도 etcd(Raft)를 써요.
END: 가장 강한 일관성은 "하나처럼 보이기(선형성)", 합의는 "과반수가 동의하면 결정". 직접 만들지 말고 검증된 도구를 써요.

#### Batch Processing (배치 처리)
ONE: **정해진 크기의 데이터를 한꺼번에** 읽어 결과를 만들고, **입력은 건드리지 않는** 처리 방식이에요. 버그가 나면 고쳐서 **다시 돌리면** 돼요.
LIKE: 하루 동안 쌓인 영수증을 밤에 한꺼번에 모아 정산하는 것과 같아요. 계산이 틀렸으면 영수증(입력)은 그대로 있으니 다시 계산하면 돼요.
STEP:
1. **원본 데이터와 파생 데이터**: 원본 기록(진실의 원천)이 있고, Cache·검색 Index·집계 Table·추천 Model 같은 **파생 데이터**는 원본에서 언제든 다시 만들 수 있어요. 파생 데이터를 만드는 방법이 Batch와 Stream이에요.
2. **MapReduce**: 각 기록에서 (Key, Value)를 뽑고(**Map**), 같은 Key끼리 모아 정렬한 뒤(**Shuffle**), Key별로 처리해요(**Reduce**). 예: 모든 문서에서 단어별 출현 횟수 세기.
3. MapReduce는 단계마다 중간 결과를 Disk에 써서 느리지만, 장애가 나도 그 단계만 다시 하면 돼서 튼튼해요.
4. **Dataflow 엔진 (Spark, Flink)**: 여러 단계를 하나의 작업 Graph로 묶고 중간 결과를 Memory에 둬서 훨씬 빨라요.
5. **대규모 JOIN**: 양쪽을 같은 Key로 정렬해 합치거나(Sort-Merge Join), 작은 쪽을 모든 작업자에게 복사해 두고 큰 쪽과 맞춰요(Broadcast Hash Join).
6. **가장 큰 장점**: 입력이 바뀌지 않으니, 코드에 버그가 있으면 고쳐서 다시 돌리면 돼요.
USE: 매일 밤 매출 정산, 추천 Model 재학습, 검색 Index 재생성, 로그 분석 보고서.
END: Batch = 쌓인 데이터를 한꺼번에, 입력은 그대로. 틀리면 다시 돌리면 되는 게 최대 장점이에요.

#### Stream Processing과 Idempotency
ONE: **끝이 없는 데이터를 도착하는 대로** 처리하는 방식이에요. 실시간으로 반응할 수 있지만, 늦게 오는 데이터와 중복 처리 문제를 다뤄야 해요.
LIKE: Batch가 하루치 영수증을 밤에 정산하는 것이라면, Stream은 결제가 일어날 때마다 바로바로 장부에 반영하는 거예요.
STEP:
1. **이벤트가 오는 즉시 처리**: 클릭, 결제, 센서 데이터를 실시간으로 받아 처리해요. Message Broker(Kafka 등)가 이벤트를 전달해요.
2. **CDC (Change Data Capture)**: DB의 변경 Log를 Stream으로 흘려서 검색 Index·Cache·Data Warehouse를 자동으로 맞춰요. 앱이 여러 시스템에 직접 따로 쓰면(Dual Write) 순서가 꼬이기 쉬워서 CDC가 더 안전해요.
3. **Event Sourcing**: 현재 상태 대신 "무슨 일이 있었는가"의 이벤트 목록을 저장하고, 상태는 이벤트를 처음부터 재생해 만들어요. 은행 거래 내역처럼 모든 변화가 기록으로 남아요.
4. **시간 문제**: 이벤트가 일어난 시각과 처리된 시각은 달라요. 휴대폰이 오프라인이었다가 늦게 보낸 이벤트도 있어요. 그래서 "5분 단위 집계 창을 언제 닫을지" 정책이 필요해요.
5. **Exactly-Once 처리**: 실제 의미는 "재시도해도 결과가 **한 번 처리한 것과 같게**"예요. Checkpoint, 작은 묶음 단위 COMMIT, 그리고 **Idempotent한 쓰기**로 달성해요.
6. **Idempotency (멱등성)**: 같은 요청을 여러 번 받아도 결과가 한 번 받은 것과 같은 성질이에요. 예: 요청마다 고유 ID를 붙이고, 이미 처리한 ID면 무시해요.
KEY: 무결성(데이터가 깨지지 않음)은 절대 타협할 수 없지만, 적시성(즉시 반영)은 몇 초 늦어도 괜찮은 경우가 많아요. 둘을 분리하면 무거운 분산 Transaction 없이도 올바른 시스템을 만들 수 있어요.
END: Stream은 오는 즉시 처리하는 방식이고, 늦게 오는 이벤트와 중복에 대비해 Idempotent하게 만들어요.

#### Encoding과 Schema Evolution
ONE: 데이터는 Memory 속 Object에서 **Byte로 바뀌어(Encoding)** Disk나 Network를 지나가요. 시스템은 한 번에 업데이트되지 않으니, **옛 코드와 새 코드가 서로의 데이터를 읽을 수 있게** Schema를 진화시켜야 해요.
LIKE: 회사 서류 양식을 바꿀 때, 새 직원은 옛 양식도 읽을 수 있어야 하고, 아직 교육을 안 받은 옛 직원도 새 양식을 받으면 모르는 칸은 건너뛰고 읽을 수 있어야 해요.
STEP:
1. **Encoding (Serialization)**: Object를 Byte로 바꿔요. 반대는 Decoding.
2. **Backward Compatibility (하위 호환)**: **새 코드가 옛 데이터**를 읽을 수 있어요.
3. **Forward Compatibility (상위 호환)**: **옛 코드가 새 데이터**를 읽고, 모르는 필드는 무시해요.
4. 서버를 한 대씩 차례로 업데이트하면(Rolling Update) 잠시 옛 버전과 새 버전이 섞여 돌아요. 그래서 두 방향 호환이 모두 필요해요.
5. **JSON·XML**: 사람이 읽기 쉽지만 크고, 숫자 정밀도가 애매해요.
6. **Protocol Buffers, Avro, Thrift**: Schema 기반 Binary 형식이에요. 작고 빠르며, 필드 번호나 Schema 비교 규칙으로 진화를 지원해요.
7. **진화 규칙**: 새 필드는 선택(Optional)으로만 추가하고, 필수 필드를 새로 만들지 않고, 지운 필드의 번호는 재사용하지 않아요.
KEY: 데이터가 흐르는 길은 세 가지예요. DB(미래의 나에게 보내는 메시지), Service 호출(REST, RPC), 비동기 Message. 특히 RPC는 함수 호출처럼 보이지만 Network는 실패하고 느리고 결과를 모를 수도 있다는 점이 근본적으로 달라요.
END: 데이터는 Byte로 바뀌어 흐르고, 옛 코드와 새 코드가 섞여도 읽을 수 있게 "선택 필드로만 추가, 번호 재사용 금지"로 Schema를 진화시켜요.

### 분산 시스템에서 시계(Clock)를 믿으면 안 되는 이유는?
E: 친구들과 각자 손목시계로 "누가 먼저 도착했나"를 정하면, 시계가 몇 분씩 다르기 때문에 순서가 틀릴 수 있습니다.
A: 각 Node의 물리 시계는 서로 어긋나고(Clock Skew), NTP 동기화 때문에 갑자기 뒤로 갈 수도 있어서 Timestamp로 이벤트 순서를 정하면(예: Last Write Wins) 최근 쓰기가 유실될 수 있습니다. 그래서 사건마다 증가하는 Lamport Timestamp 같은 Logical Clock이나 Version Vector로 순서·동시성을 판단하고, 꼭 시계가 필요하면 오차 범위를 아는 시계(예: Spanner TrueTime)를 씁니다. Lease 기반 Leader는 Process Pause에 대비해 Fencing Token으로 옛 Leader의 쓰기를 거부합니다.

### Consensus(합의)란? Raft는 어떻게 동작하나요?
E: 소풍 장소를 정할 때 일부가 연락이 안 돼도 과반수가 동의하면 결정하고, 한 번 정한 결정은 나중에 연락된 친구도 따르는 규칙입니다.
A: Consensus는 여러 Node가 장애가 있어도 하나의 값(Leader, Log 순서, Commit 여부)에 동의하는 문제로, Leader 선출·원자적 Commit·전체 순서 Broadcast가 모두 이와 같은 문제입니다. Raft는 Term마다 과반수 투표로 Leader를 뽑고, Leader가 Log Entry를 Follower에 복제해 과반수가 저장하면 Commit하며, 과반수 Node가 살아 있는 한 진행합니다. 실무에서는 직접 구현하지 않고 etcd(Raft)나 ZooKeeper(Zab) 같은 조정 서비스를 씁니다.

### Batch Processing과 Stream Processing의 차이는?
E: Batch는 하루치 영수증을 밤에 한꺼번에 정산하는 것이고, Stream은 결제가 일어날 때마다 바로 장부에 반영하는 것입니다.
A: Batch Processing은 크기가 정해진 입력을 한꺼번에 읽어 결과를 만들고 입력은 바꾸지 않아, 버그가 있으면 고쳐서 다시 돌릴 수 있고 처리량이 높습니다(MapReduce, Spark). Stream Processing은 끝없는 이벤트를 도착하는 대로 처리해 지연이 짧지만, 늦게 도착하는 이벤트를 위한 Window 정책과 장애·재시도 시 중복을 막는 Exactly-Once(Idempotent Write, Checkpoint) 처리가 필요합니다(Kafka, Flink). CDC로 DB 변경을 Stream으로 흘려 파생 데이터를 동기화하기도 합니다.

### Idempotency(멱등성)란? 왜 중요한가요?
E: 엘리베이터 버튼을 한 번 누르든 열 번 누르든 엘리베이터는 한 번만 옵니다. 여러 번 해도 결과가 한 번 한 것과 같은 성질입니다.
A: Idempotency는 같은 요청을 여러 번 처리해도 결과(Server 상태)가 한 번 처리한 것과 같은 성질입니다. 분산 시스템에서는 Network 실패로 응답을 못 받으면 재시도하고, Message Queue는 같은 Message를 두 번 전달할 수 있어서 중복 결제·중복 주문을 막으려면 필수입니다. 요청마다 고유 ID(Idempotency Key)를 붙여 이미 처리한 ID는 무시하는 방식이 대표적이며, HTTP의 GET·PUT·DELETE는 Idempotent, POST는 아닙니다.

### Backward Compatibility와 Forward Compatibility란?
E: 회사 서류 양식을 바꿀 때, 새 직원은 옛 양식을 읽을 수 있어야 하고(하위 호환), 옛 직원은 새 양식에서 모르는 칸을 건너뛰고 읽을 수 있어야 합니다(상위 호환).
A: Backward Compatibility는 새 코드가 옛 데이터를 읽을 수 있는 것이고, Forward Compatibility는 옛 코드가 새 데이터를 읽으며 모르는 필드를 무시할 수 있는 것입니다. Rolling Update 중에는 옛 버전과 새 버전이 함께 돌아 두 방향 모두 필요하며, Protocol Buffers·Avro 같은 Schema 기반 Encoding에서 새 필드는 Optional로만 추가하고, 필수 필드를 새로 만들지 않고, 필드 번호를 재사용하지 않는 규칙으로 지킵니다.

## 운영 기초

#### Linux 명령어와 파일 권한
ONE: Server는 대부분 Linux라서 **기본 명령어**와 **파일 권한(r·w·x)**을 알아야 해요. 권한은 **주인·그룹·나머지**별로 숫자로 표현해요.
LIKE: 파일 권한은 아파트 출입증과 같아요. 집주인(Owner), 가족(Group), 방문객(Others)마다 "볼 수 있다(r), 고칠 수 있다(w), 실행할 수 있다(x)"를 따로 정해요.
STEP:
1. **위치·이동·목록**: `pwd`(지금 위치), `cd`(이동), `ls -al`(숨김 파일까지 자세히 목록).
2. **복사·이동·삭제**: `cp`, `mv`, `rm`(`-r`은 폴더 통째로). `rm -rf`는 되돌릴 수 없으니 정말 조심해요.
3. **내용 보기·검색**: `cat`, `less`, `tail -f 로그파일`(실시간으로 로그 보기), `grep "error" 파일`(글자 찾기).
4. **Process**: `ps aux`(실행 중인 Process 목록), `top`(실시간 자원 사용량), `kill PID`(종료).
5. **Disk·Network**: `df -h`(Disk 남은 용량), `du -sh`(폴더 크기), `curl`(HTTP 요청), `ssh`(원격 접속).
6. **권한 숫자**: 읽기 r=4, 쓰기 w=2, 실행 x=1을 더해요. 순서는 Owner·Group·Others.
7. **755**: Owner rwx(4+2+1=7), Group r-x(4+1=5), Others r-x(5). 주인만 고치고 누구나 읽고 실행할 수 있어요. Script와 폴더에 흔히 써요.
8. **644**: Owner rw-(6), 나머지 r--(4). 일반 파일에 흔히 써요.
KEY: 모두에게 모든 권한을 주는 `777`은 보안상 피해요. "일단 안 되니까 777"은 위험한 습관이에요.
END: 기본 명령어로 파일·Process·Disk를 다루고, 권한은 r4·w2·x1을 더해 주인·그룹·나머지 순으로 써요.

#### Container(Docker)와 VM
ONE: **VM**은 컴퓨터 안에 **OS째로 가상 컴퓨터**를 만드는 것이고, **Container**는 **Host OS의 Kernel을 공유**하면서 Process만 격리하는 가벼운 방식이에요.
LIKE: VM은 한 땅에 단독주택을 여러 채 짓는 거예요. 집마다 보일러·수도(OS)가 따로 있어요. Container는 아파트예요. 건물의 기반 시설(Kernel)은 함께 쓰고, 집 안만 독립돼 있어요.
STEP:
1. **VM (Virtual Machine)**: Hypervisor 위에 Guest OS를 통째로 올려요. 격리가 강하지만, OS마다 Memory를 차지해 무겁고 켜는 데 오래 걸려요.
2. **Container**: Host OS의 Kernel을 공유하고, Linux의 **Namespace**(서로 안 보이게 격리)와 **cgroups**(CPU·Memory 사용량 제한)로 Process를 나눠요. 가볍고 몇 초 만에 떠요.
3. **Image**: 앱과 실행에 필요한 Library·설정을 하나로 묶은 꾸러미예요. 같은 Image면 어디서 실행해도 똑같이 동작해서 "내 컴퓨터에서는 되는데" 문제를 줄여요.
4. **Docker**: Container를 만들고 실행하는 가장 대표적인 도구예요.
5. **Kubernetes**: 수많은 Container를 여러 Server에 배치하고, 죽으면 다시 띄우고, 부하에 따라 늘리고 줄이는 **Orchestration** 도구예요.
CON: Container는 Kernel을 공유해서 VM보다 격리 수준이 낮아요. 보안이 아주 중요하면 VM이나 더 강한 격리 기술을 함께 써요.
END: VM은 OS째 격리(무겁고 강함), Container는 Kernel 공유 격리(가볍고 빠름). 많아지면 Kubernetes로 관리해요.

#### Logging과 Monitoring
ONE: 운영 중인 서비스는 **Log(무슨 일이 있었나)**, **Metric(숫자로 본 상태)**, **Trace(요청이 어디를 거쳤나)**로 살펴보고, 문제가 생기면 **Alert(알림)**를 받아요.
LIKE: 자동차 계기판(Metric)으로 속도와 연료를 보고, 블랙박스(Log)로 사고 순간을 돌려 보고, 내비게이션 경로 기록(Trace)으로 어디를 지나왔는지 확인하는 것과 같아요.
STEP:
1. **Log Level**: 심각도에 따라 나눠요. DEBUG(개발용 상세) < INFO(정상 흐름) < WARN(문제는 아니지만 주의) < ERROR(요청 실패) < FATAL/CRITICAL(서비스를 계속할 수 없음).
2. Library마다 이름이 조금 달라요. Log4j에는 가장 아래 TRACE가 있고, Python logging은 WARNING·CRITICAL이라고 써요.
3. 운영 환경에서는 보통 INFO 이상만 남겨서 비용과 잡음을 줄여요. **비밀번호·개인정보는 절대 Log에 남기지 않아요.**
4. **Metric**: 요청 수, 오류율, 응답 시간(p50, p99), CPU·Memory 사용량을 시간에 따라 숫자로 모아 그래프로 봐요.
5. **Distributed Tracing**: MSA에서 요청 하나가 여러 Service를 거칠 때, 같은 Trace ID를 붙여 어디서 시간이 오래 걸렸는지 추적해요.
6. **Alert**: "오류율 5% 초과" 같은 조건을 정해 담당자에게 자동으로 알려요. 너무 자주 울리면 무시하게 되니 꼭 필요한 것만 정해요.
END: Log는 사건 기록, Metric은 숫자 계기판, Trace는 경로 기록이에요. 셋을 함께 봐야 운영 중 문제를 빨리 찾아요.

### 자주 쓰는 Linux 명령어와 chmod 755의 뜻은?
E: 파일 권한(Permission)은 아파트 출입증입니다. 집주인(Owner), 가족(Group), 방문객(Others)마다 "볼 수 있다, 고칠 수 있다, 실행할 수 있다"를 따로 정합니다.
| 하는 일 | 명령어 |
| 위치·이동·목록 | pwd, cd, ls -al |
| 복사·이동·삭제 | cp, mv, rm (-r은 폴더 통째로) |
| 내용 보기·검색 | cat, less, tail -f 로그파일, grep "error" 파일 |
| Process | ps aux, top, kill PID |
| 권한·소유자 | chmod, chown |
| Disk·Network | df -h, du -sh, curl, ssh |
A: 권한은 읽기 r=4, 쓰기 w=2, 실행 x=1을 더한 숫자를 Owner·Group·Others 순서로 씁니다. 따라서 755는 Owner rwx(7), Group r-x(5), Others r-x(5)로, Owner만 수정하고 누구나 읽고 실행할 수 있는 설정이며 Script나 Directory에 흔히 씁니다. 모두에게 전부 주는 777은 보안상 피합니다.

### Docker(Container)와 VM(Virtual Machine)의 차이는?
E: VM은 한 땅에 단독주택을 여러 채 짓는 것이라 집마다 보일러·수도(OS)가 따로 있고, Container는 아파트라 건물의 기반 시설(Kernel)은 공유하고 집 안만 독립되어 있습니다.
A: VM은 Hypervisor 위에 Guest OS를 통째로 올려 격리가 강하지만 무겁고 Booting이 느립니다. Container는 Host OS의 Kernel을 공유하면서 Linux Namespace와 cgroups로 Process를 격리하고 자원을 제한하므로 가볍고 수 초 안에 뜨며, 앱과 실행 환경을 Image로 묶어 "내 컴퓨터에서는 되는데" 문제를 줄입니다. 대신 Kernel을 공유해 VM보다 격리 수준이 낮고, 많은 Container를 관리할 때는 Kubernetes 같은 Orchestration 도구를 씁니다.

### Log Level은 어떻게 구분하나요?
A: 일반적으로 DEBUG(개발용 상세 정보) < INFO(정상 흐름 기록) < WARN(문제는 아니지만 주의) < ERROR(요청 실패 같은 오류) < FATAL/CRITICAL(서비스가 계속할 수 없는 오류) 순으로 심각해지며, Library에 따라 가장 아래에 TRACE가 있거나(Log4j) 이름이 WARNING·CRITICAL입니다(Python logging). 운영 환경은 보통 INFO 이상만 남겨 비용과 잡음을 줄이고, 비밀번호·개인정보는 Log에 남기지 않습니다.
