## Data Structure 고르는 법

#### Data Structure와 Time Complexity 감각
ONE: **Data Structure**는 데이터를 담는 방식이고, **"어떤 연산을 가장 자주 하는가"**를 보고 골라요. 모든 연산이 빠른 구조는 없어요.
LIKE: 옷 정리를 떠올려 보세요. 옷걸이에 걸면 꺼내기는 빠르지만 자리를 많이 차지하고, 서랍에 개어 넣으면 공간은 아끼지만 밑에 있는 옷을 꺼내기 불편해요. 무엇을 자주 하느냐에 따라 정리법이 달라져요.
STEP:
1. 데이터로 하는 일은 대부분 네 가지예요. **접근**(i번째 꺼내기), **검색**(있는지 찾기), **삽입**(넣기), **삭제**(빼기).
2. 각 Data Structure는 어떤 일을 빠르게 하는 대신 다른 일을 포기해요.
3. 속도는 **Big-O**로 말해요. 데이터가 n개일 때 걸리는 시간이 n에 따라 어떻게 늘어나는지예요. O(1)은 n과 상관없이 일정, O(log n)은 아주 천천히 늘어남, O(n)은 n에 비례.
4. n = 100만일 때 감각: O(1)은 한 번, O(log n)은 약 20번, O(n)은 100만 번.
5. 그래서 문제를 보면 먼저 "가장 자주 하는 연산이 뭐지?"를 묻고, 그 연산이 빠른 구조를 골라요.
| 구조 | 빠른 것 | 느린 것 | 대표 용도 |
| Array | Index로 접근 O(1) | 중간 삽입·삭제 O(n) | 대부분의 목록 |
| Linked List | 위치를 알면 삽입·삭제 O(1) | i번째 접근 O(n) | 잦은 끼워 넣기, LRU Cache |
| Stack / Queue | 끝에서 넣고 빼기 O(1) | 중간 접근 불가 | 되돌리기, 대기열, DFS·BFS |
| Hash Table | 검색·삽입·삭제 평균 O(1) | 순서 없음, 최악 O(n) | 중복 검사, 빈도 세기 |
| Balanced BST | 정렬 유지 + 모두 O(log n) | Hash보다 느림 | 정렬된 데이터, 범위 검색 |
| Heap | 최솟값 확인 O(1), 꺼내기 O(log n) | 임의 검색 O(n) | 우선순위 큐, 상위 k개 |
| Trie | 길이 L 문자열 O(L) | Memory 많이 씀 | 자동완성, 접두사 검색 |
| Union-Find | 합치기·같은 그룹 확인 거의 O(1) | 나누기는 불가 | 연결 요소, Cycle 검사 |
WHY: 같은 문제라도 Data Structure 하나를 바꾸면 몇 시간 걸리던 프로그램이 1초 만에 끝나기도 해요.
END: 정답 구조는 없고, "가장 자주 하는 일"이 빠른 구조가 정답이에요.

### Data Structure는 어떻게 고르나요?
E: 옷을 자주 갈아입으면 옷걸이, 공간이 부족하면 서랍처럼, 가장 자주 하는 일이 빠른 수납법을 고릅니다.
A: 모든 연산이 빠른 Data Structure는 없으므로, 문제에서 가장 자주 하는 연산(Index 접근, 검색, 삽입·삭제, 최솟값 꺼내기, 정렬 유지 등)을 먼저 파악하고 그 연산의 Time Complexity가 가장 좋은 구조를 고릅니다. 예를 들어 "있는지 확인"이 잦으면 Hash Set, 정렬 순서와 범위 검색이 필요하면 Balanced BST, 계속 최솟값을 꺼내면 Heap을 씁니다.

## Array와 Dynamic Array

#### Array (배열)
ONE: **Array**는 같은 크기의 칸을 Memory에 **한 줄로 붙여** 놓은 구조예요. 몇 번째 칸이든 계산 한 번으로 바로 찾아가요(O(1)).
LIKE: 번호가 매겨진 사물함이 한 줄로 붙어 있어요. 첫 칸 위치와 칸 너비만 알면, 100번 칸이 어디 있는지 걸어가 보지 않고도 계산으로 바로 알 수 있어요.
STEP:
1. Array는 Memory의 연속된 공간에 원소를 차례로 놓아요.
2. i번째 원소의 주소 = **시작 주소 + i × 원소 크기**. 곱하기 한 번, 더하기 한 번이면 끝이라 O(1)이에요. 이것을 **Random Access**라고 해요.
3. **중간 삽입**: 3번 자리에 넣으려면 3번부터 끝까지를 한 칸씩 뒤로 밀어야 해요. 최악 O(n).
4. **중간 삭제**: 빈자리를 메우려고 뒤 원소들을 한 칸씩 당겨야 해요. 최악 O(n).
5. **검색**: 정렬돼 있지 않으면 처음부터 하나씩 봐야 해서 O(n). 정렬돼 있으면 Binary Search로 O(log n).
6. 원소가 붙어 있어서 Cache가 한 번에 여러 원소를 가져와요. 그래서 실제로도 매우 빨라요(02번 주제의 Spatial Locality).
PRO: 접근이 O(1)이고 Cache 효율이 좋아요. 구조가 단순하고 Memory 낭비가 없어요.
CON: 크기를 미리 정해야 하고(고정 Array), 중간 삽입·삭제가 느려요.
END: Array는 "번호로 바로 가기"의 왕이에요. 대신 중간에 끼워 넣고 빼는 건 느려요.

#### Dynamic Array와 Amortized O(1)
ONE: **Dynamic Array**는 공간이 꽉 차면 **더 큰 Array를 새로 만들어 옮기는** Array예요. 가끔 옮기는 비용이 크지만, 평균하면 끝에 넣기가 O(1)이에요.
LIKE: 책장이 꽉 차면 두 배 크기 책장을 사서 책을 전부 옮겨요. 옮기는 날은 힘들지만 그런 날은 드물고, 나머지 날에는 책을 꽂기만 하면 되니 평균하면 하루 일은 가벼워요.
STEP:
1. Python의 list, Java의 ArrayList, C++의 vector가 Dynamic Array예요.
2. 처음엔 여유 공간이 있는 Array를 잡아 두고, 끝에 넣을 때 빈칸에 쏙 넣어요. O(1).
3. 꽉 차면 더 큰 Array를 새로 만들고 기존 원소를 전부 복사해요. 이번 한 번은 O(n).
4. 크기를 2배씩 키운다고 하면, n개를 넣는 동안 복사하는 총량은 1 + 2 + 4 + … + n < 2n이에요.
5. 그래서 n번 넣는 총비용이 O(n)이고, 한 번당 평균은 O(1)이에요. 이렇게 "가끔 비싼 일을 전체에 나눠서 계산한 평균"을 **Amortized(분할 상환) O(1)**이라고 해요.
6. 키우는 비율은 구현마다 달라요. CPython list는 약 1.125배씩 키워요.
KEY: "평균 O(1)"(Hash Table처럼 확률적으로 대부분 빠름)과 "Amortized O(1)"(최악의 연속에서도 총합을 나누면 O(1))은 다른 개념이에요.
WHY: 크기를 미리 몰라도 Array의 빠른 접근을 그대로 누릴 수 있어서 가장 많이 쓰는 자료구조가 됐어요.
END: Dynamic Array는 꽉 차면 크게 이사하고, 이사 비용을 나눠 보면 넣을 때마다 O(1)이에요.

### Array의 Index 접근이 O(1)인 이유는?
E: Array는 번호가 매겨진 사물함이 한 줄로 붙어 있는 것입니다. 첫 칸 위치와 칸 너비만 알면 100번 칸이 어디인지 계산 한 번으로 바로 갈 수 있습니다.
A: Array는 같은 크기의 원소를 연속된 Memory에 저장하므로, i번째 Address를 "시작 Address + i × 원소 크기"로 한 번에 계산할 수 있어 O(1)입니다(Random Access). 대신 중간에 넣거나 빼면 뒤 원소를 모두 한 칸씩 밀어야 해서 O(n)이고, 연속 Memory라 Cache 효율이 좋습니다.

### Dynamic Array(ArrayList, Python list)의 append가 "평균 O(1)"인 이유는?
E: 책장이 꽉 차면 두 배 크기 책장을 사서 책을 전부 옮깁니다. 옮기는 날은 힘들지만 그런 날은 드물고, 나머지 날에는 책을 꽂기만 하면 되니 평균하면 하루 일은 가볍습니다.
A: Dynamic Array는 공간이 차면 더 큰 Array를 만들어 전부 복사(O(n))하지만, 크기를 일정 비율로 키우므로 복사가 드물게 일어납니다. 2배씩 키우면 n번 추가하는 동안 총 복사량이 1 + 2 + 4 + … < 2n이라 한 번당 평균 O(1)이고, 이를 Amortized(분할 상환) O(1)이라고 합니다. 늘리는 비율(Growth Factor)은 구현마다 다르며 CPython list는 약 1.125배입니다.

## Linked List

#### Linked List (연결 리스트)
ONE: **Linked List**는 데이터와 **"다음 칸의 위치(Pointer)"**를 가진 Node들을 사슬처럼 이은 구조예요. 위치를 알면 끼워 넣기·빼기가 O(1)이지만, i번째 찾기는 O(n)이에요.
LIKE: 보물찾기와 같아요. 쪽지마다 내용과 "다음 쪽지는 미끄럼틀 밑"이 적혀 있어요. 5번째 쪽지를 보려면 1번부터 차례로 따라가야 해요. 대신 중간에 쪽지를 끼워 넣을 때는 앞 쪽지의 "다음 위치"만 고쳐 쓰면 돼요.
STEP:
1. **Node** = 데이터 + 다음 Node의 주소(next).
2. 첫 Node를 **Head**라고 하고, 마지막 Node의 next는 비어 있어요(None/NULL).
3. **i번째 접근**: Head부터 next를 i번 따라가야 해서 O(n).
4. **삽입**: 넣을 자리의 앞 Node를 알고 있으면, 새 Node의 next를 뒤 Node로, 앞 Node의 next를 새 Node로 바꾸면 끝. 아무것도 밀지 않아요. O(1).
5. **삭제**: 앞 Node의 next를 지울 Node의 다음 Node로 바꾸면 끝. O(1).
6. Node들이 Memory 여기저기 흩어져 있어서 Cache 효율이 낮아요.
| 비교 | Array | Linked List |
| i번째 접근 | O(1) | O(n) |
| 위치를 알 때 삽입·삭제 | O(n) (밀기) | O(1) |
| Memory | 데이터만 | 데이터 + Pointer |
| Cache 효율 | 좋음 (연속) | 낮음 (흩어짐) |
KEY: "삽입 O(1)"은 **위치를 이미 알 때**만이에요. 그 위치를 찾느라 앞에서부터 걸어가면 결국 O(n)이에요.
USE: 실제로는 Array가 Cache 덕분에 더 빠른 경우가 많아서, Linked List는 LRU Cache처럼 "중간 Node를 이미 들고 있는" 상황에서 빛나요.
END: Linked List는 "다음 위치"를 따라가는 사슬이에요. 끼워 넣기는 쉽고, 번호로 찾기는 느려요.

#### Singly · Doubly · Circular Linked List
ONE: 다음 Node만 가리키면 **Singly**, 앞뒤를 모두 가리키면 **Doubly**, 마지막이 처음으로 이어지면 **Circular** Linked List예요.
LIKE: Singly는 앞으로만 갈 수 있는 일방통행 길, Doubly는 앞뒤로 다닐 수 있는 양방향 길, Circular는 끝이 처음과 이어진 회전 교차로예요.
STEP:
1. **Singly Linked List**: Node마다 next 하나. 구조가 단순하고 Memory를 적게 써요. 하지만 뒤로 갈 수 없고, 어떤 Node를 지우려면 그 **앞 Node**를 알아야 해요.
2. **Doubly Linked List**: Node마다 next와 prev 두 개. 양쪽으로 다닐 수 있고, Node 하나만 알아도 그 Node를 O(1)에 지울 수 있어요(앞뒤 Node를 직접 알 수 있으니까). 대신 Pointer가 하나 더 필요해요.
3. **Circular Linked List**: 마지막 Node가 다시 첫 Node를 가리켜요. 끝없이 돌아가는 일(차례대로 돌아가며 실행, 반복 재생 목록)에 맞아요. 종료 조건을 잘못 쓰면 무한 반복에 빠져요.
USE: **LRU Cache**는 Hash Table(Key로 Node를 바로 찾기) + Doubly Linked List(최근 사용 순서 유지, O(1)로 맨 앞으로 옮기거나 맨 뒤를 빼기)로 만드는 대표적인 예예요.
END: 한 방향은 Singly, 양방향은 Doubly, 고리는 Circular. 중간 Node를 바로 지워야 하면 Doubly예요.

#### Linked List의 Cycle 찾기: Floyd's Algorithm
ONE: 한 칸씩 가는 **느린 Pointer**와 두 칸씩 가는 **빠른 Pointer**를 동시에 보내서, 둘이 만나면 Cycle이 있다고 판단하는 방법이에요.
LIKE: 트랙에서 거북이는 한 칸씩, 토끼는 두 칸씩 뛰어요. 길이 일자로 끝나면 토끼가 먼저 끝에 도착하고, 원형 트랙이면 토끼가 한 바퀴 더 돌아 결국 거북이를 따라잡아요.
STEP:
1. 두 Pointer를 모두 Head에서 출발시켜요. slow는 한 칸, fast는 두 칸씩 이동해요.
2. fast가 끝(None)에 닿으면 Cycle이 없어요.
3. Cycle이 있으면 둘 다 결국 고리 안으로 들어가요.
4. 고리 안에서 fast는 slow에게 한 번에 한 칸씩 가까워져요. 그래서 반드시 만나요.
5. 시간은 O(n), 추가 Memory는 Pointer 두 개뿐이라 O(1)이에요.
```python
def has_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:
            return True
    return False
```
KEY: 같은 "빠른·느린 Pointer" 기법으로 Linked List의 **가운데 Node**도 찾아요. fast가 끝에 닿을 때 slow가 가운데에 있어요.
WHY: 방문한 Node를 Set에 모두 저장하면 O(n) Memory가 들어요. 두 Pointer만으로 같은 일을 할 수 있다는 게 핵심이에요.
END: 거북이와 토끼를 같이 보내서 만나면 Cycle이 있어요. Memory는 O(1)이에요.

### Linked List란? Array와 비교한 장단점은?
E: 보물찾기입니다. 각 쪽지에 내용과 "다음 쪽지는 놀이터 미끄럼틀 밑"이 적혀 있어서, 5번째 쪽지를 보려면 1번부터 차례로 따라가야 합니다. 대신 중간에 쪽지를 끼워 넣을 때는 앞 쪽지의 "다음 위치"만 고치면 됩니다.
A: Linked List는 Data와 다음 Node를 가리키는 Pointer를 가진 Node들을 사슬처럼 이은 구조입니다. 위치를 알고 있으면 삽입·삭제가 O(1)이고 크기를 미리 정할 필요가 없지만, i번째 원소 접근이 O(n)이고 Pointer 때문에 Memory를 더 쓰며 Node가 흩어져 있어 Cache 효율이 낮습니다.

### Singly / Doubly / Circular Linked List의 차이는?
| 종류 | 구조 | 장점 | 단점 |
| Singly | Node가 다음 Node만 가리킴 | 구조가 단순하고 Memory 적게 씀 | 뒤로 갈 수 없고, 삭제하려면 앞 Node를 알아야 함 |
| Doubly | 다음(next)과 이전(prev)을 모두 가리킴 | 양방향 이동, Node 하나만 알아도 O(1) 삭제 | Pointer가 하나 더 필요 |
| Circular | 마지막 Node가 다시 첫 Node를 가리킴 | 끝없이 순환(Round Robin Scheduling, 재생 목록 반복) | 종료 조건을 잘못 쓰면 Infinite Loop |
A: Singly Linked List는 next Pointer만, Doubly Linked List는 prev·next Pointer를 모두 가져 양방향 순회(Traversal)와 O(1) 삭제가 가능하며, Circular Linked List는 끝이 처음과 이어져 있습니다. LRU Cache는 Hash Table + Doubly Linked List로 만드는 대표적인 예입니다.

### Linked List에 Cycle이 있는지 어떻게 찾나요?
E: 트랙에서 거북이는 한 칸씩, 토끼는 두 칸씩 뛰게 합니다. 길이 일자로 끝나면 토끼가 먼저 끝에 도착하고, 원형 트랙이면 토끼가 한 바퀴 더 돌아 거북이를 따라잡습니다.
A: Floyd's Cycle Detection(Tortoise and Hare) Algorithm은 한 칸씩 가는 Slow Pointer와 두 칸씩 가는 Fast Pointer를 동시에 보내서, 둘이 만나면 Cycle이 있고 Fast Pointer가 끝(None)에 닿으면 없습니다. 시간 O(n), 추가 공간 O(1)입니다.

## Stack과 Queue

#### Stack (LIFO)
ONE: **Stack**은 **나중에 넣은 것을 먼저 꺼내는(LIFO, Last In First Out)** 구조예요. 넣기(push)와 꺼내기(pop)가 모두 O(1)이에요.
LIKE: 쌓아 올린 접시 더미예요. 새 접시는 맨 위에 올리고, 꺼낼 때도 맨 위 접시부터 꺼내요. 맨 아래 접시를 꺼내려면 위의 접시를 다 치워야 해요.
STEP:
1. **push(x)**: 맨 위에 x를 올려요.
2. **pop()**: 맨 위를 꺼내요.
3. **peek()**: 맨 위를 꺼내지 않고 보기만 해요.
4. 맨 위만 다루니 모두 O(1)이에요. 중간 원소에는 접근할 수 없어요.
5. Python에서는 list의 `append()`와 `pop()`으로 Stack을 만들어요(끝에서만 넣고 빼니 O(1)).
USE: 함수 호출 기록(Call Stack), 되돌리기(Ctrl+Z), 브라우저 뒤로 가기, 괄호 짝 검사, DFS(깊이 우선 탐색).
KEY: **괄호 짝 검사**: 여는 괄호는 push, 닫는 괄호가 나오면 pop해서 짝이 맞는지 봐요. 끝났을 때 Stack이 비어 있으면 올바른 괄호예요.
END: Stack은 접시 더미예요. 마지막에 넣은 것이 먼저 나와요.

#### Queue (FIFO)와 Circular Queue
ONE: **Queue**는 **먼저 넣은 것을 먼저 꺼내는(FIFO, First In First Out)** 구조예요. Array로 만들 때는 공간을 고리처럼 다시 쓰는 **Circular Queue**를 써요.
LIKE: Queue는 맛집 앞의 줄이에요. 먼저 선 사람이 먼저 들어가요. Circular Queue는 회전초밥 레일처럼 끝에 닿으면 다시 처음으로 돌아와서, 앞에서 접시를 가져간 빈자리가 다시 뒤쪽 자리가 돼요.
STEP:
1. **enqueue(x)**: 줄 맨 뒤(rear)에 넣어요.
2. **dequeue()**: 줄 맨 앞(front)에서 꺼내요.
3. Python list의 `pop(0)`은 뒤 원소를 모두 당겨야 해서 O(n)이에요. 그래서 Queue는 `collections.deque`를 써요(양 끝 O(1)).
4. **Array로 만든 일반 Queue의 문제**: 앞에서 꺼낸 자리를 다시 못 써요. 뒤가 꽉 차면, 앞에 빈칸이 있어도 넣을 수 없어요.
5. **Circular Queue**: front와 rear Index를 `(i + 1) % size`로 움직여서, 끝에 닿으면 0번으로 돌아오게 해요. Array를 고리처럼 다시 써요.
6. 비었을 때와 꽉 찼을 때 모두 front와 rear가 같아질 수 있어서, 한 칸을 일부러 비워 두거나 원소 개수를 따로 세서 구분해요.
USE: 프린터 대기열, 작업 대기열(Job Queue), BFS(너비 우선 탐색), 키보드 입력이나 Streaming 데이터를 담는 **Ring Buffer**.
END: Queue는 줄 서기(먼저 온 사람 먼저)이고, Array로 만들 땐 고리처럼 돌려 쓰는 Circular Queue가 정석이에요.

#### Deque와 Stack 두 개로 Queue 만들기
ONE: **Deque**는 **양쪽 끝 모두에서** O(1)로 넣고 뺄 수 있는 구조예요. 그리고 Stack 두 개를 조합하면 Queue를 만들 수 있어요.
LIKE: Deque는 앞문과 뒷문이 모두 있는 버스예요. 어느 문으로든 타고 내릴 수 있어요. Stack 두 개로 Queue 만들기는, 들어온 접시를 한 더미에 쌓았다가 꺼낼 때 다른 더미로 통째로 뒤집어 옮기면 맨 처음 접시가 맨 위로 오는 원리예요.
STEP:
1. **Deque (Double-Ended Queue)**: 앞뒤 모두 넣기·빼기가 O(1)이라 Stack으로도 Queue로도 쓸 수 있어요. Python은 `collections.deque`.
2. **Stack 2개로 Queue**: 들어오는 것은 inbox Stack에 push해요.
3. 꺼낼 때 outbox Stack이 비어 있으면, inbox의 원소를 전부 하나씩 pop해서 outbox에 push해요. 순서가 뒤집혀서 가장 먼저 들어온 게 outbox 맨 위로 와요.
4. outbox에서 pop하면 가장 먼저 들어온 원소가 나와요.
5. 원소 하나는 inbox에서 outbox로 **딱 한 번만** 옮겨져요. 그래서 가끔 옮기는 비용이 커도 평균(Amortized) O(1)이에요.
USE: 슬라이딩 윈도우 최댓값 같은 Coding Test 문제에서 Deque를 자주 써요. "Stack으로 Queue 만들기"는 면접 단골 문제예요.
END: Deque는 양쪽 문이 있는 줄이고, Stack 두 개를 뒤집어 옮기면 Queue가 돼요.

### Stack(LIFO)과 Queue(FIFO)의 차이와 쓰임새는?
E: Stack은 쌓아 올린 접시라서 마지막에 올린 접시를 가장 먼저 꺼냅니다. Queue는 맛집 줄이라서 먼저 선 사람이 먼저 들어갑니다.
A: Stack은 나중에 들어온 것이 먼저 나가는 LIFO(Last In First Out) 구조로 push·pop이 O(1)이고, Call Stack, 되돌리기(Ctrl+Z), Browser 뒤로 가기, 괄호 짝 검사, DFS에 씁니다. Queue는 먼저 들어온 것이 먼저 나가는 FIFO(First In First Out) 구조로, 프린터 대기열, Job Queue, BFS에 씁니다. Python에서 Queue는 `list.pop(0)`이 O(n)이라 `collections.deque`를 씁니다.

### Circular Queue는 왜 필요한가요?
E: 회전초밥 레일처럼 끝에 닿으면 다시 처음으로 돌아옵니다. 앞에서 접시를 가져가 빈 자리가 다시 뒤쪽 자리가 됩니다.
A: Array로 만든 일반 Queue는 앞에서 꺼낸 자리를 다시 쓰지 못해 뒤가 꽉 차면 앞에 빈칸이 있어도 삽입할 수 없습니다. Circular Queue는 front·rear Index를 `(i + 1) % size`로 옮겨 Array를 고리처럼 재사용하고, Full과 Empty 상태를 구분하려고 한 칸을 비워 두거나 개수를 따로 셉니다. Streaming Buffer, 키보드 입력 Buffer(Ring Buffer)에 씁니다.

### Deque란? Stack 2개로 Queue를 만드는 법은?
A: Deque(Double-Ended Queue)는 양쪽 끝에서 모두 O(1)로 넣고 뺄 수 있는 Queue입니다. Stack 2개로 Queue를 만들려면 들어오는 것은 inbox에 push하고, 꺼낼 때 outbox가 비어 있으면 inbox를 통째로 엎어 outbox에 옮긴 뒤 outbox에서 pop합니다. 원소 하나가 최대 한 번만 옮겨지므로 평균(Amortized) O(1)입니다.

## Hash Table

#### Hash Table의 원리
ONE: Key를 **Hash Function**으로 숫자로 바꾸고, 그 숫자로 저장할 칸(Bucket)을 바로 정해서, 검색·삽입·삭제를 **평균 O(1)**에 하는 구조예요.
LIKE: 아파트 택배함에서 호수(Key)를 넣으면 규칙(Hash Function)에 따라 칸 번호가 바로 나와요. 택배함을 하나씩 열어 볼 필요 없이 한 번에 찾아가요.
STEP:
1. Bucket이라는 칸들이 있는 Array를 준비해요.
2. Key를 Hash Function에 넣으면 정수(Hash 값)가 나와요. 예: `hash("apple")`.
3. **칸 번호 = Hash 값 % 칸 수**. 그 칸에 (Key, Value)를 저장해요.
4. 찾을 때도 같은 계산으로 칸 번호를 구해 바로 가요. 계산 한 번이니 평균 O(1)이에요.
5. **Collision(충돌)**: 서로 다른 Key가 같은 칸에 떨어질 수 있어요. 칸 수보다 Key 종류가 많으면 반드시 생겨요(비둘기집 원리).
6. 운 나쁘게 모든 Key가 한 칸에 몰리면, 그 칸 안에서 하나씩 비교해야 해서 **최악 O(n)**이에요.
USE: Python의 dict와 set, Java의 HashMap, 데이터베이스의 Hash Index, Cache. "본 적 있나?", "몇 번 나왔나?", "짝이 있나?" 문제의 기본 도구예요.
CON: 순서가 없어서 "정렬된 순서로 보기"나 "범위 검색"은 못 해요. 그럴 땐 Balanced BST를 써요.
END: Hash Table은 "계산으로 칸을 바로 찾는" 구조예요. 평균 O(1), 충돌이 몰리면 최악 O(n)이에요.

#### Collision 해결: Chaining vs Open Addressing
ONE: 같은 칸에 여러 Key가 오면 **줄줄이 매달거나(Chaining)**, **다른 빈칸을 찾아 넣어요(Open Addressing)**.
LIKE: Chaining은 택배함 한 칸에 택배가 여러 개 오면 끈으로 줄줄이 매달아 두는 거예요. Open Addressing은 내 칸이 차 있으면 옆 칸, 그 옆 칸을 보면서 빈칸에 넣는 거예요.
STEP:
1. **Chaining**: 각 칸이 작은 목록(Linked List 등)이에요. 충돌하면 그 목록에 이어 붙여요.
2. Chaining은 구현이 단순하고, 칸보다 원소가 많아도 동작해요. Java HashMap은 Chaining을 쓰고, 한 칸에 너무 많이 몰리면 그 칸을 Tree로 바꿔 최악을 줄여요.
3. **Open Addressing**: 모든 원소를 Array 안에 직접 넣어요. 칸이 차 있으면 정해진 규칙으로 다음 칸을 찾아요(**Probing**).
4. Probing 방법: **Linear Probing**(바로 옆 칸부터), **Quadratic Probing**(1, 4, 9칸씩 건너뛰며), **Double Hashing**(두 번째 Hash Function으로 건너뛸 간격 결정).
5. Open Addressing은 원소가 붙어 있어 Cache 효율이 좋지만, 칸이 많이 차면 빈칸을 찾느라 급격히 느려지고, 삭제할 때는 "여기 있었음" 표시를 남겨야 해서 까다로워요. Python dict가 Open Addressing을 써요.
| 구분 | Chaining | Open Addressing |
| 충돌 처리 | 칸에 목록으로 매달기 | 다른 빈칸 찾기 |
| 가득 찰 때 | 계속 동작 | 급격히 느려짐 |
| Cache 효율 | 낮음 | 좋음 |
| 삭제 | 쉬움 | 까다로움 |
| 예 | Java HashMap | Python dict |
END: 충돌은 피할 수 없어요. 매달거나(Chaining), 옆 칸을 찾거나(Open Addressing) 둘 중 하나로 해결해요.

#### Load Factor · Rehashing · 좋은 Hash Function
ONE: 칸이 얼마나 찼는지(**Load Factor**)가 높아지면 테이블을 키워 다시 배치하고(**Rehashing**), Key를 고르게 퍼뜨리는 **좋은 Hash Function**을 써야 O(1)이 유지돼요.
LIKE: 주차장이 거의 다 차면 빈자리를 찾느라 오래 돌아야 해요. 그래서 주차장이 75%쯤 차면 두 배 크기 주차장으로 옮기고 차를 다시 배치해요.
STEP:
1. **Load Factor = 저장된 원소 수 ÷ 칸 수**. 높을수록 충돌이 늘어요.
2. 기준(예: Java HashMap은 0.75)을 넘으면 칸 수를 보통 2배로 늘린 새 Array를 만들어요.
3. 칸 수가 바뀌면 `Hash % 칸 수`도 바뀌니, 모든 Key를 새 칸에 다시 넣어야 해요. 이게 **Rehashing**이에요. 한 번은 O(n)이지만 드물어서 평균 O(1)이 유지돼요.
4. **좋은 Hash Function의 조건 ①**: 같은 Key에는 항상 같은 값(Deterministic).
5. **조건 ②**: Key들을 칸에 고르게 퍼뜨려요(Uniform Distribution). 한쪽에 몰리면 충돌이 늘어요.
6. **조건 ③**: 빨리 계산돼요.
7. **보안 측면**: 공격자가 일부러 같은 칸에 떨어지는 Key를 잔뜩 보내면 서버가 O(n)으로 느려져요. 그래서 Python은 실행할 때마다 문자열 Hash에 무작위 값을 섞어 이를 막아요.
KEY: 비밀번호 저장용 Hash(SHA-256, bcrypt)는 목적이 달라요. 거꾸로 계산할 수 없어야 하고, bcrypt처럼 일부러 느리게 만들기도 해요. Hash Table용 Hash는 빠른 게 중요해요.
END: 차면 키우고(Rehashing), 고르게 퍼뜨리면(좋은 Hash) Hash Table은 계속 O(1)로 동작해요.

### Hash Table이란? 평균 O(1)인 이유와 최악 O(n)인 경우는?
E: 아파트 택배함에서 호수(Key)를 넣으면 규칙(Hash Function)에 따라 칸 번호가 바로 나오는 것입니다. 거의 항상 한 번에 찾지만, 운 나쁘게 모두 같은 칸에 몰리면 그 칸 안에서 하나씩 뒤져야 합니다.
A: Hash Table은 Hash Function으로 Key를 Array Index(Bucket)로 바꿔 Value를 저장하는 구조로, 계산 한 번에 위치를 찾으므로 Search·Insert·Delete가 평균 O(1)입니다. 하지만 많은 Key가 같은 Bucket에 Collision(충돌)하면 그 안을 하나씩 비교해야 해서 최악 O(n)이 됩니다. Python dict·set, Java HashMap이 대표적입니다.

### 좋은 Hash Function의 조건은?
A: 같은 Key에는 항상 같은 값을 내고(Deterministic), Key들을 Bucket에 고르게 흩뜨리며(Uniform Distribution), 빠르게 계산되어야 합니다. 비밀번호 저장용 Cryptographic Hash(SHA-256, bcrypt)는 여기에 더해 역산이 불가능해야 하므로, Hash Table용 Hash와는 목적이 다릅니다.

### Collision 해결: Chaining vs Open Addressing은?
E: Chaining은 택배함 한 칸에 여러 개가 오면 줄줄이 매달아 두는 것, Open Addressing은 내 칸이 차 있으면 옆 빈칸을 찾아 넣는 것입니다.
A: Chaining은 각 Bucket을 Linked List(또는 Tree)로 두고 충돌한 항목을 이어 붙이며, 구현이 단순하고 가득 차도 동작합니다. Open Addressing은 Array 안에서 다른 빈 자리를 찾는 방식(Linear Probing, Quadratic Probing, Double Hashing)으로 Cache 효율이 좋지만 Load Factor가 높아지면 급격히 느려지고 삭제가 까다롭습니다. Java HashMap은 Chaining, Python dict는 Open Addressing을 씁니다.

### Load Factor와 Rehashing이란?
A: Load Factor(부하율)는 저장된 항목 수 ÷ Bucket 수로, 높을수록 Collision이 늘어 느려집니다. 그래서 일정 값(예: Java HashMap은 0.75)을 넘으면 Bucket Array를 보통 두 배로 키우고 모든 Key를 다시 배치하는 Rehashing을 합니다. Rehashing 자체는 O(n)이지만 드물게 일어나 평균 O(1)이 유지됩니다.

## Tree 기본

#### Tree와 기본 용어
ONE: **Tree**는 맨 위 하나(**Root**)에서 아래로 가지를 치며 내려가는, **Cycle이 없는 계층 구조**예요.
LIKE: 가족 족보나 회사 조직도예요. 맨 위의 한 사람(Root)에서 아래로 갈라지고, 아래에 아무도 없는 사람이 Leaf예요.
STEP:
1. **Node**: 데이터를 담은 한 점. **Edge**: Node를 잇는 선.
2. **Root**: 맨 위 Node. 부모가 없어요.
3. **Parent / Child**: 바로 위가 부모, 바로 아래가 자식. 부모가 같으면 **Sibling(형제)**.
4. **Leaf**: 자식이 없는 Node.
5. **Depth (깊이)**: Root에서 그 Node까지 내려온 Edge 수. Root의 Depth는 0.
6. **Height (높이)**: 그 Node에서 가장 먼 Leaf까지의 Edge 수. Tree의 Height는 Root의 Height예요.
7. **Subtree**: 어떤 Node와 그 아래 전체도 하나의 Tree예요. 그래서 Tree 문제는 재귀(Recursion)로 풀기 좋아요.
WHY: Tree에서 대부분의 연산 시간은 **Height**에 비례해요. Height를 낮게 유지하는 게 Tree 설계의 핵심이에요.
USE: 파일 시스템(폴더 안의 폴더), HTML 문서 구조(DOM), 회사 조직도, 데이터베이스 Index, 컴파일러의 문법 트리.
END: Tree는 Root에서 갈라져 내려가는 Cycle 없는 구조이고, 성능은 Height가 정해요.

#### Binary Tree의 종류: Full · Complete · Perfect
ONE: 자식이 최대 2개인 **Binary Tree**는 모양에 따라 **Full**(자식 0 또는 2), **Complete**(왼쪽부터 빈틈없이), **Perfect**(모든 층이 꽉 참)로 나뉘어요.
LIKE: 극장 좌석으로 생각해 보세요. Complete는 앞줄부터, 그리고 각 줄은 왼쪽부터 채운 상태예요. 마지막 줄만 오른쪽이 비어 있을 수 있어요. Perfect는 빈자리 하나 없는 만석이에요.
STEP:
1. **Binary Tree**: 모든 Node의 자식이 최대 2개(Left, Right).
2. **Full Binary Tree**: 모든 Node가 자식이 0개이거나 정확히 2개. 하나만 있는 Node가 없어요.
3. **Complete Binary Tree**: 마지막 층을 빼고 모두 꽉 찼고, 마지막 층은 **왼쪽부터** 채워요.
4. **Perfect Binary Tree**: 모든 층이 꽉 찼어요. Height가 h면 Node는 2ʰ⁺¹ − 1개예요.
5. Node가 n개인 Complete Binary Tree의 Height는 약 log₂ n이에요. 아주 낮아요.
KEY: Complete Binary Tree는 빈틈이 없어서 **Pointer 없이 Array 하나로** 저장할 수 있어요. 그래서 Heap이 이 모양을 써요. 교재마다 Full과 Perfect의 이름을 바꿔 쓰기도 해서, 면접에서는 이름과 함께 조건을 말하는 게 안전해요.
END: 최대 2개면 Binary, 0 또는 2면 Full, 왼쪽부터 빈틈없으면 Complete, 꽉 차면 Perfect예요.

#### Tree Traversal (순회)
ONE: Tree의 모든 Node를 한 번씩 방문하는 방법이에요. **Root를 언제 방문하느냐**에 따라 Preorder·Inorder·Postorder가 되고, 층별로 방문하면 Level-Order예요.
LIKE: 조직도를 읽는 방법이 여러 가지인 것과 같아요. 팀장을 먼저 보고 팀원들을 볼 수도(Preorder), 팀원을 다 보고 마지막에 팀장을 볼 수도(Postorder), 직급별로 층층이 볼 수도(Level-Order) 있어요.
STEP:
1. **Preorder (전위)**: Root → Left → Right. 부모를 먼저 방문해요. Tree 복사, 폴더 구조 출력에 써요.
2. **Inorder (중위)**: Left → Root → Right. 부모를 가운데 방문해요. **BST를 Inorder로 돌면 정렬된 순서**가 나와요.
3. **Postorder (후위)**: Left → Right → Root. 자식을 다 본 뒤 부모를 방문해요. Tree 삭제, 폴더 용량 계산(자식 크기를 다 더한 뒤 부모 계산)에 써요.
4. 위 세 가지는 한 방향으로 끝까지 내려갔다 돌아오는 **DFS(깊이 우선)**이고, 재귀로 짧게 쓸 수 있어요.
5. **Level-Order**: 위층부터, 같은 층은 왼쪽부터. **Queue**를 써서 구현하는 **BFS(너비 우선)**예요. 가장 얕은 Leaf 찾기에 좋아요.
6. 모두 모든 Node를 한 번씩 보니 O(n)이에요.
```python
def inorder(node):
    if node is None:
        return
    inorder(node.left)
    print(node.val)      # Root를 가운데에서 방문
    inorder(node.right)
```
END: Root를 먼저(Pre), 가운데(In), 나중에(Post) 방문하면 DFS, 층별로 방문하면 BFS(Level-Order)예요.

### Tree란? Root·Leaf·Depth·Height는?
E: 가족 족보나 회사 조직도입니다. 맨 위 한 명(Root)에서 아래로 갈라지고, 아래에 아무도 없는 사람이 Leaf입니다.
A: Tree는 Cycle이 없는 계층형 Graph로, Root에서 시작해 Parent-Child 관계로 내려가고 Child가 없는 Node를 Leaf라고 합니다. Depth(깊이)는 Root에서 그 Node까지의 Edge 수, Height(높이)는 그 Node에서 가장 먼 Leaf까지의 Edge 수입니다. File System, HTML DOM, 조직도가 Tree 구조입니다.

### Binary / Full / Complete / Perfect Binary Tree의 차이는?
| 종류 | 조건 | 비유 |
| Binary Tree (이진 트리) | 모든 Node의 Child가 최대 2개 | 자녀가 둘 이하인 가족 |
| Full Binary Tree (정 이진 트리) | 모든 Node의 Child가 0개 또는 2개 | 자녀가 없거나 딱 둘 |
| Complete Binary Tree (완전 이진 트리) | 마지막 층만 빌 수 있고, 마지막 층은 왼쪽부터 채움 | 극장 좌석을 앞줄부터, 왼쪽부터 채움 |
| Perfect Binary Tree (포화 이진 트리) | 모든 층이 꽉 참 (Height h면 Node 2ʰ⁺¹ − 1개) | 빈자리 없는 만석 |
A: Binary Tree는 Child가 최대 둘인 Tree이고, Full Binary Tree는 모든 Node가 Child를 0개 또는 2개 갖고, Complete Binary Tree는 마지막 층을 제외하고 꽉 차 있으며 마지막 층은 왼쪽부터 채워집니다. Perfect Binary Tree는 모든 층이 꽉 찬 Tree입니다. Complete Binary Tree는 빈틈이 없어 Array로 저장하기 좋아서 Heap에 씁니다.
M: 교재에 따라 Full과 Perfect의 이름을 바꿔 쓰기도 해서, 면접에서는 이름보다 조건을 함께 말하는 것이 안전합니다.

### Preorder·Inorder·Postorder·Level-Order Traversal은?
E: "Root를 언제 방문하느냐"로 이름이 정해집니다. Preorder는 먼저, Inorder는 가운데, Postorder는 마지막. Level-Order는 조직도를 층별로 위에서부터 읽는 것입니다.
| Traversal | 순서 | 쓰임새 |
| Preorder (전위) | Root → Left → Right | Tree 복사, 폴더 구조 출력 |
| Inorder (중위) | Left → Root → Right | BST에서 오름차순 정렬 결과 |
| Postorder (후위) | Left → Right → Root | Tree 삭제, 폴더 용량 계산 |
| Level-Order (레벨) | 층별로 위에서 아래, 왼쪽에서 오른쪽 | BFS, 최단 깊이 찾기 (Queue 사용) |
A: Preorder·Inorder·Postorder Traversal은 Root를 방문하는 시점이 각각 처음·중간·마지막인 DFS(깊이 우선) 순회이고, Level-Order Traversal은 Queue를 써서 층별로 방문하는 BFS(너비 우선) 순회입니다. 모두 모든 Node를 한 번씩 보므로 O(n)이고, BST를 Inorder Traversal하면 값이 정렬된 순서로 나옵니다.

## BST와 Balanced Tree

#### BST (Binary Search Tree)
ONE: **BST**는 모든 Node에서 **왼쪽은 더 작고, 오른쪽은 더 큰** 값만 오도록 정리한 Binary Tree예요. 검색·삽입·삭제 시간이 Tree 높이에 비례해요.
LIKE: 숫자 맞히기 게임에서 "더 작아"라고 하면 왼쪽, "더 커"라고 하면 오른쪽으로 가는 갈림길 지도예요. 갈림길마다 후보가 절반씩 줄어들어요.
STEP:
1. **규칙**: 어떤 Node든, 왼쪽 Subtree의 모든 값 < 그 Node < 오른쪽 Subtree의 모든 값.
2. **검색**: Root에서 시작해 찾는 값이 작으면 왼쪽, 크면 오른쪽으로 내려가요. Leaf까지 가도 없으면 없는 거예요.
3. **삽입**: 검색하듯 내려가다가 빈자리에 새 Node를 붙여요.
4. **삭제**: Leaf면 그냥 지우고, 자식이 하나면 자식을 그 자리로 올리고, 자식이 둘이면 오른쪽에서 가장 작은 값(또는 왼쪽에서 가장 큰 값)으로 바꿔치기한 뒤 그 Node를 지워요.
5. 시간은 모두 **O(h)**(h = Height)예요. 균형 잡혀 있으면 h ≈ log n이라 아주 빨라요.
6. **최악의 경우**: 1, 2, 3, 4…처럼 정렬된 순서로 넣으면 계속 오른쪽에만 붙어서 한 줄짜리(Skewed) Tree가 돼요. h = n이 되어 Linked List처럼 O(n)이에요.
KEY: BST를 Inorder로 돌면 오름차순 정렬 결과가 나와요. 그래서 BST는 "정렬된 상태를 유지하면서 넣고 빼기"에 좋아요.
END: BST는 "작으면 왼쪽, 크면 오른쪽"인 갈림길이고, 균형이 깨지면 O(n)까지 느려질 수 있어요.

#### Balanced Tree: AVL Tree와 Red-Black Tree
ONE: 삽입·삭제 때마다 **Rotation(회전)**으로 모양을 고쳐서 Height를 항상 **O(log n)**으로 지키는 BST예요. 엄격한 **AVL**과 느슨한 **Red-Black**이 대표적이에요.
LIKE: 천장에 다는 모빌의 양쪽 무게가 크게 다르면 줄 거는 위치를 돌려 다시 수평을 맞춰요. AVL은 "양쪽 차이 1cm도 안 돼"라는 깐깐한 반장, Red-Black은 "두 배만 안 넘으면 괜찮아"라는 너그러운 반장이에요.
STEP:
1. 일반 BST는 넣는 순서에 따라 한쪽으로 기울 수 있어요. 그래서 스스로 균형을 잡는 BST가 필요해요.
2. **Rotation**: 부모와 자식의 위아래 관계를 바꿔서 기운 쪽을 끌어올리는 작업이에요. BST 규칙(왼쪽 < 부모 < 오른쪽)은 그대로 지켜요.
3. **AVL Tree**: 모든 Node에서 왼쪽·오른쪽 Subtree의 Height 차이(**Balance Factor**)를 1 이하로 유지해요. 깨지면 경우(LL, RR, LR, RL)에 따라 한 번 또는 두 번 회전해요.
4. **Red-Black Tree**: Node에 빨강·검정 색을 칠하고 규칙을 지켜요. Root는 검정, 빨강 Node가 연달아 나올 수 없음, 어떤 Node에서 아래 Leaf까지 가는 모든 경로의 검정 Node 수가 같음 등.
5. 이 규칙 덕분에 가장 긴 경로가 가장 짧은 경로의 2배를 넘지 않아서 Height가 O(log n)으로 보장돼요(정확히는 2·log₂(n + 1) 이하).
6. **차이**: AVL은 더 엄격하게 균형을 맞춰 **검색이 약간 빠르고**, Red-Black은 회전을 덜 해서 **삽입·삭제가 약간 빨라요**.
USE: Java의 TreeMap, C++의 std::map처럼 "정렬된 Map"이 Red-Black Tree로 구현돼요. Linux Kernel의 Process Scheduler 같은 곳에도 Red-Black Tree가 쓰여요.
END: Balanced Tree는 회전으로 높이를 log n으로 지켜요. 검색 위주면 AVL, 변경이 잦으면 Red-Black이에요.

### BST(Binary Search Tree)란? 최악의 경우 O(n)이 되는 이유는?
E: 숫자 맞히기 게임에서 "더 작아" 하면 왼쪽, "더 커" 하면 오른쪽으로 가는 갈림길 지도입니다. 그런데 1, 2, 3, 4… 순서대로 넣으면 갈림길이 아니라 외길 한 줄이 되어 버립니다.
A: BST는 모든 Node에서 Left Subtree는 더 작고 Right Subtree는 더 큰 값만 갖는 Binary Tree로, Search·Insert·Delete가 Tree Height h에 비례하는 O(h)입니다. Balanced 상태면 h = O(log n)이지만, 정렬된 순서로 넣으면 한쪽으로만 길어져(Skewed) h = n이 되고 Linked List처럼 O(n)이 됩니다.

### AVL Tree는 어떻게 균형을 유지하나요?
E: 모빌(천장에 다는 장난감)의 양쪽 무게가 크게 다르면 줄 거는 위치를 돌려 다시 수평을 맞춥니다.
A: AVL Tree는 모든 Node에서 Left·Right Subtree Height 차이(Balance Factor)를 1 이하로 유지하는 BST입니다. 삽입·삭제 후 균형이 깨지면 LL·RR·LR·RL 경우에 따라 한 번 또는 두 번 Rotation(회전)해 Height를 O(log n)으로 지킵니다.

### Red-Black Tree의 규칙과 AVL과의 차이는?
E: AVL이 "양쪽 키 차이 1cm도 안 돼"라고 엄격하게 관리하는 반장이라면, Red-Black Tree는 "대충 두 배만 넘지 않으면 괜찮아"라는 반장입니다. 덜 엄격한 대신 자리를 덜 바꿉니다.
A: Red-Black Tree는 ① 모든 Node는 Red 또는 Black, ② Root는 Black, ③ Leaf(NIL)는 Black, ④ Red Node의 Child는 모두 Black(Red가 연속 불가), ⑤ 어떤 Node에서 그 아래 Leaf까지의 모든 경로는 Black Node 수가 같다는 규칙으로 Height를 2log₂(n + 1) 이하로 지킵니다. AVL은 더 엄격하게 균형을 맞춰 조회가 조금 빠르고, Red-Black은 삽입·삭제 때 Rotation이 적어 변경이 잦은 곳에 유리해서 Java TreeMap, C++ std::map, Linux Scheduler(CFS) 등에 쓰입니다.

## Heap과 Priority Queue

#### Heap과 Priority Queue
ONE: **Heap**은 **부모가 항상 자식보다 작은(Min Heap) 또는 큰(Max Heap)** Complete Binary Tree예요. 최솟값(최댓값)을 O(1)에 보고, O(log n)에 꺼내요.
LIKE: 응급실 대기열이에요. 온 순서가 아니라 가장 급한 환자가 항상 맨 앞에 와요. 새 환자가 오면 상태를 보고 몇 칸만 자리를 바꿔요. 전체를 줄 세우지는 않아요.
STEP:
1. **Min Heap 규칙**: 모든 부모 ≤ 자식. 그래서 Root가 항상 최솟값이에요.
2. 형제끼리는 순서가 없어요. 완전히 정렬된 구조가 아니라 "맨 위만 확실한" 구조예요.
3. **삽입**: 맨 끝(마지막 층의 왼쪽부터 빈자리)에 넣고, 부모보다 작으면 부모와 자리를 바꾸며 위로 올라가요(**Sift-Up**). 최대 Height만큼, O(log n).
4. **최솟값 꺼내기**: Root를 꺼내고, 맨 끝 원소를 Root로 옮긴 뒤, 자식 중 더 작은 쪽과 자리를 바꾸며 아래로 내려가요(**Sift-Down**). O(log n).
5. **최솟값 보기**: Root를 보면 끝. O(1).
6. **Priority Queue**: "우선순위가 가장 높은 것부터 꺼내는 Queue"라는 개념이고, Heap이 그 대표적인 구현이에요.
USE: 작업 우선순위 처리, Dijkstra 최단 경로, Heap Sort, "상위 k개 찾기", 실시간 중앙값 구하기. Python의 `heapq`는 Min Heap이에요(Max Heap이 필요하면 값에 −를 붙여 넣어요).
END: Heap은 "맨 위만 항상 최소(최대)"인 Tree이고, Priority Queue의 표준 구현이에요.

#### Array로 표현하는 Heap과 Build-Heap O(n)
ONE: Heap은 빈틈없는 Complete Binary Tree라서 **Array 하나로** 저장하고 Index 계산으로 부모·자식을 찾아요. n개로 Heap을 한 번에 만드는 데는 **O(n)**이면 충분해요.
LIKE: 피라미드를 쌓는다고 생각해 보세요. 아래쪽 벽돌이 가장 많지만 그 벽돌들은 거의 움직일 거리가 없고, 멀리 움직여야 하는 위쪽 벽돌은 몇 개 없어요.
STEP:
1. Tree를 위층부터, 왼쪽부터 차례로 Array에 담아요.
2. 0번부터 시작하면 i번 Node의 **부모 = (i − 1) // 2**, **왼쪽 자식 = 2i + 1**, **오른쪽 자식 = 2i + 2**.
3. Pointer가 필요 없어서 Memory를 아끼고 Cache 효율도 좋아요.
4. **Build-Heap**: 원소를 하나씩 삽입하면 O(n log n)이에요. 대신 Array를 그대로 두고, 마지막 부모 Node부터 Root까지 **거꾸로 Sift-Down**하면 더 빨라요.
5. Node의 절반은 Leaf라 움직이지 않아요. 높이 1인 Node는 최대 1칸, 높이 2인 Node는 최대 2칸만 내려가는데, 높은 Node일수록 개수가 절반씩 줄어요.
6. 이 작업량을 다 더하면 O(n)이에요. Python의 `heapq.heapify()`가 이 방식이에요.
KEY: 0번부터 시작하는 Array Heap에서 Index 5의 부모는 (5 − 1) // 2 = 2예요. 1번부터 시작하는 교재에서는 부모 = i // 2, 자식 = 2i, 2i + 1이에요.
END: Heap은 Array 하나로 표현하고(부모 (i−1)//2, 자식 2i+1·2i+2), 한 번에 만들 땐 아래에서부터 Sift-Down해서 O(n)이에요.

### Heap(Binary Heap), Min Heap, Max Heap이란?
E: 응급실 대기열입니다. 온 순서가 아니라 가장 급한 환자가 항상 맨 앞에 오고, 새 환자가 오면 상태를 보고 몇 칸만 자리를 바꿉니다. 전체를 줄 세우지는 않습니다.
A: Binary Heap은 Complete Binary Tree이면서, Min Heap은 Parent가 항상 Child보다 작거나 같고 Max Heap은 항상 크거나 같은 구조입니다. Root가 최솟값(최댓값)이라 확인은 O(1), 삽입과 Root 삭제는 위아래로 자리를 바꾸며(Sift-Up/Sift-Down) O(log n)입니다. Sibling(형제)끼리는 순서가 없어서 완전히 정렬된 구조는 아니고, Priority Queue·Dijkstra·Heap Sort·Top-K 문제에 씁니다. Python heapq는 Min Heap입니다.

### Heap을 Array로 구현할 때 Parent·Child Index는?
A: 0번부터 시작하는 Array에서 i번 Node의 Parent는 `(i − 1) // 2`, Left Child는 `2i + 1`, Right Child는 `2i + 2`입니다(1번부터 시작하면 Parent `i // 2`, Child `2i`와 `2i + 1`). Complete Binary Tree라 빈칸이 없으므로 Pointer 없이 Array만으로 Tree를 표현합니다.

### n개 원소로 Heap을 만드는 Build-Heap이 O(n)인 이유는?
E: 피라미드에서 아래쪽 벽돌이 가장 많지만 그들은 거의 움직일 거리가 없고, 멀리 움직여야 하는 위쪽 벽돌은 몇 개 없습니다.
A: 마지막 Internal Node부터 Root까지 거꾸로 Sift-Down하면, Node의 절반인 Leaf는 움직이지 않고 Height h인 Node는 많아야 n/2ʰ⁺¹개라 작업량의 합이 Σ h · n/2ʰ⁺¹ = O(n)입니다. 원소를 하나씩 삽입하면 O(n log n)이므로 더 빠르고, Python `heapq.heapify`가 이 방식입니다.

## Disk용 Tree

#### B-Tree
ONE: Node 하나에 **Key를 수백 개** 담아 넓고 낮게 만든 Balanced Tree예요. 느린 Disk를 **몇 번만 읽어도** 원하는 데이터를 찾을 수 있어요.
LIKE: 도서관 색인 카드함이에요. 서랍 하나에 "가~까", "나~다"처럼 여러 구간이 한꺼번에 들어 있어서, 서랍을 몇 번만 열면 원하는 책에 도착해요. 서랍을 여는 일(Disk 읽기)이 가장 비싸니까 여는 횟수를 줄이는 게 핵심이에요.
STEP:
1. Disk(SSD·HDD)는 RAM보다 훨씬 느리고, 한 번 읽을 때 작은 조각이 아니라 큰 덩어리(Page, 보통 수 KB)를 통째로 가져와요.
2. Binary Tree는 Node 하나에 Key가 하나라 Height가 높아요. 10억 개면 약 30층이고, 층마다 Disk를 읽으면 너무 느려요.
3. **B-Tree**는 Node 하나를 Disk Page 하나 크기로 만들고, 그 안에 Key를 수백 개 넣어요. 자식도 수백 개예요.
4. 그래서 Tree가 아주 넓고 낮아져요. Node 하나에 자식이 수백 개면, 3~4층만으로 수십억 개 Key를 담을 수 있어요.
5. 모든 Leaf가 같은 깊이에 있고, 삽입·삭제 때 Node를 나누거나(Split) 합치며(Merge) 균형을 유지해요.
WHY: Disk 접근 한 번이 Memory 접근보다 수백~수만 배 느려서, "몇 번 읽느냐"가 성능을 결정해요.
USE: 데이터베이스 Index와 File System(NTFS, ext4의 일부, Btrfs 등)의 기본 구조예요.
END: B-Tree는 "Node 하나 = Disk Page 하나"로 넓고 낮게 만들어 Disk 읽기 횟수를 줄여요.

#### B+Tree와 DB Index
ONE: **B+Tree**는 실제 데이터를 **맨 아래 Leaf에만** 두고, Leaf끼리 **옆으로 줄줄이 연결**한 B-Tree예요. 범위 검색이 특히 빨라서 대부분의 DB Index가 B+Tree예요.
LIKE: 위쪽 서랍에는 "어느 방향으로 가라"는 이정표만 두고, 실제 책 카드는 맨 아래 칸에만 둬요. 맨 아래 칸들은 옆으로 이어져 있어서 "가~다 책 전부"를 옆으로 훑으며 꺼낼 수 있어요.
STEP:
1. **Internal Node**(위쪽 Node)는 길잡이 Key만 가져요. 실제 데이터(또는 행의 위치)는 없어요.
2. 그래서 Internal Node에 Key를 더 많이 넣을 수 있어 Tree가 더 낮아져요.
3. **Leaf Node**에 모든 실제 데이터가 있고, Leaf끼리 Linked List처럼 옆으로 연결돼 있어요.
4. **한 개 검색**: 항상 Leaf까지 내려가니 검색 시간이 일정해요.
5. **범위 검색** (`WHERE age BETWEEN 20 AND 30`): 20이 있는 Leaf를 한 번 찾은 뒤, 옆으로 쭉 훑기만 하면 돼요. 다시 위로 올라갈 필요가 없어요.
| 구분 | B-Tree | B+Tree |
| 데이터 위치 | 모든 Node | Leaf에만 |
| Leaf 연결 | 없음 | 옆으로 연결 |
| 범위 검색 | 위아래로 오가야 함 | Leaf를 옆으로 훑기 |
USE: MySQL(InnoDB), PostgreSQL 등 대부분의 관계형 DB Index가 B+Tree예요(09번 주제의 Index에서 다시 나와요).
END: B+Tree는 데이터를 바닥(Leaf)에만 두고 옆으로 이어서, 범위 검색을 빠르게 해요.

### B-Tree란? 왜 Database와 File System에서 쓰나요?
E: 도서관 색인 카드함입니다. 서랍 하나에 "가~까", "나~다"처럼 여러 구간이 한 번에 들어 있어서, 서랍을 몇 번만 열면 원하는 책에 도착합니다. 서랍을 여는 것(Disk 읽기)이 가장 비싼 일이라 열기 횟수를 줄이는 것이 핵심입니다.
A: B-Tree는 Node 하나에 Key를 여러 개 담고 Child도 여러 개인 Balanced Multi-way Search Tree로, 모든 Leaf가 같은 Depth에 있습니다. Node 크기를 Disk Page 크기에 맞춰 한 번 읽을 때 많은 Key를 가져오므로 Tree Height가 매우 낮아지고, 그만큼 느린 Disk 접근(I/O) 횟수가 줄어듭니다.

### B+Tree는 B-Tree와 무엇이 다르고, 왜 Index에 더 적합한가요?
E: B+Tree는 위쪽 서랍에는 "어느 방향으로 가라"는 이정표만 두고, 실제 책 카드는 맨 아래 칸에만 둡니다. 맨 아래 칸들은 옆으로 줄줄이 이어져 있어서 "가~다 책 전부"를 옆으로 훑으며 꺼낼 수 있습니다.
A: B+Tree는 실제 Data(또는 Record 위치)를 Leaf Node에만 두고 Internal Node는 길잡이 Key만 가지며, Leaf끼리 Linked List로 이어져 있습니다. Internal Node에 Key를 더 많이 담아 Height가 낮고, 모든 검색이 Leaf까지 가므로 성능이 일정하며, Range Query(`WHERE age BETWEEN 20 AND 30`)는 Leaf를 옆으로 훑으면 되어 매우 빠릅니다. 그래서 MySQL InnoDB 같은 대부분의 DB Index가 B+Tree를 씁니다.

## Trie

#### Trie (Prefix Tree)
ONE: 문자열을 **글자 하나씩 나눠 가지를 따라 저장**하는 Tree예요. 길이 L인 단어의 검색·삽입이 저장된 단어 수와 상관없이 **O(L)**이에요.
LIKE: 국어사전 색인 탭을 글자 하나씩 따라가는 나무예요. "사" 아래에 "사과", "사랑", "사자"가 모여 있어서, "사"까지만 쳐도 그 아래 단어들이 바로 보여요.
STEP:
1. Root는 비어 있고, 각 Edge(또는 Node)가 글자 하나를 나타내요.
2. "cat"을 넣으면 Root → c → a → t로 내려가며 Node를 만들고, 마지막 Node에 "단어 끝" 표시를 해요.
3. "car"를 넣으면 c → a까지는 이미 있으니 그대로 쓰고, r만 새로 만들어요. 앞글자(**Prefix**)가 같은 단어는 가지를 공유해요.
4. **검색**: 글자를 따라 내려가기만 하면 돼서 단어 길이 L만큼만 걸려요. 단어가 100만 개 저장돼 있어도 O(L).
5. **접두사 검색(자동완성)**: "ca"까지 내려간 다음, 그 아래 있는 모든 단어를 모으면 끝이에요.
PRO: 접두사로 찾기가 매우 빠르고, 같은 접두사를 공유해 정리돼 있어요.
CON: Node마다 자식 Pointer를 여러 개 가져서 Memory를 많이 써요.
USE: 검색창 자동완성, 맞춤법 검사, 전화번호부 접두사 검색, Router의 IP 주소 검색(가장 긴 접두사 일치).
END: Trie는 글자를 따라 내려가는 나무이고, "이 글자로 시작하는 단어"를 찾는 데 최고예요.

### Trie란? 자동완성(Autocomplete)에 쓰이는 이유는?
E: 국어사전의 색인 탭을 글자 하나씩 따라가는 나무입니다. "사" → "사과", "사랑", "사자"처럼 앞글자를 공유하므로, "사"까지만 치면 그 아래 단어가 바로 보입니다.
A: Trie(Prefix Tree)는 String을 글자 단위로 나눠 Edge에 저장하는 Tree로, 길이 L인 단어의 Search·Insert가 저장된 단어 수와 상관없이 O(L)입니다. 같은 Prefix(접두사)를 가진 단어가 한 가지에 모여 있어 Autocomplete·Prefix Search·Spell Check에 좋지만, Node마다 Child Pointer를 두어 Memory를 많이 씁니다.

## Graph 표현

#### Graph를 저장하는 두 가지 방법: Adjacency Matrix vs Adjacency List
ONE: Graph는 **V × V 표(Adjacency Matrix)**나 **Vertex별 이웃 목록(Adjacency List)**으로 저장해요. 실제 Graph는 대부분 Edge가 적어서 List를 기본으로 써요.
LIKE: Adjacency Matrix는 전국 도시끼리의 거리표예요. 도시가 1000개면 칸이 100만 개예요. Adjacency List는 사람마다 가진 친구 연락처 목록이에요. 친구 수만큼만 적으면 돼요.
STEP:
1. Graph는 Vertex(점)와 Edge(선)로 이루어져요(01번 주제). 방향이 있으면 Directed, 비용이 붙으면 Weighted Graph예요.
2. **Adjacency Matrix (인접 행렬)**: V × V 표를 만들고, u와 v가 연결되면 `M[u][v] = 1`(또는 가중치)로 적어요.
3. Matrix는 "u와 v가 연결됐나?"를 O(1)에 알 수 있어요. 하지만 Memory가 항상 O(V²)이고, 한 Vertex의 이웃을 모두 보려면 한 줄 전체(V칸)를 봐야 해요.
4. **Adjacency List (인접 리스트)**: Vertex마다 연결된 이웃만 목록으로 적어요. Memory는 O(V + E).
5. List는 이웃을 모두 보는 게 이웃 수만큼만 걸려서, BFS·DFS를 O(V + E)에 할 수 있어요.
6. **Sparse vs Dense**: SNS나 도로망은 Vertex 수에 비해 Edge가 아주 적어요(Sparse). 친구가 수십억 명인 사람은 없으니까요. 그래서 대부분 List를 써요. Edge가 아주 많은(Dense) 작은 Graph에서는 Matrix가 편해요.
| 방식 | Memory | u-v 연결 확인 | 이웃 모두 보기 | 언제 |
| Adjacency Matrix | O(V²) | O(1) | O(V) | Edge가 많은 Dense Graph |
| Adjacency List | O(V + E) | O(이웃 수) | O(이웃 수) | 대부분의 Sparse Graph |
END: 연결 확인이 잦고 Graph가 빽빽하면 Matrix, 그 외 대부분은 List예요.

### Graph란? Directed·Undirected·Weighted Graph는?
E: 지하철 노선도입니다. 역은 Vertex, 역 사이 선로는 Edge입니다. 일방통행 길이 있으면 Directed Graph, 역 사이 소요 시간이 적혀 있으면 Weighted Graph입니다.
A: Graph는 Vertex(Node)와 그 사이를 잇는 Edge로 관계를 표현하는 구조입니다. Edge에 방향이 있으면 Directed Graph(팔로우 관계), 없으면 Undirected Graph(친구 관계)이고, Edge에 비용이 붙으면 Weighted Graph(도로 거리)입니다. Tree는 Cycle이 없는 Connected Graph의 한 종류입니다.

### Adjacency Matrix vs Adjacency List, 언제 무엇을 쓰나요?
| 방식 | 비유 | Memory | "u-v Edge 있나?" | 이웃 모두 보기 | 언제 |
| Adjacency Matrix | 전국 도시끼리 거리표 (칸이 V × V) | O(V²) | O(1) | O(V) | Edge가 많은 Dense Graph |
| Adjacency List | 사람마다 친구 연락처 목록 | O(V + E) | O(Degree) | O(Degree) | Edge가 적은 Sparse Graph (대부분) |
A: Adjacency Matrix(인접 행렬)는 V × V 표로 Edge 존재를 O(1)에 확인하지만 Memory가 O(V²)이고, Adjacency List(인접 리스트)는 Vertex마다 이웃 목록만 저장해 O(V + E) Memory로 충분합니다. 실제 Graph(SNS, 도로망)는 대부분 Sparse해서 Adjacency List를 쓰고, BFS·DFS도 Adjacency List에서 O(V + E)입니다.

## Disjoint Set (Union-Find)

#### Union-Find (서로소 집합)
ONE: 겹치지 않는 그룹들을 관리하면서 **"두 원소가 같은 그룹인가?"(find)**와 **"두 그룹 합치기"(union)**를 거의 O(1)에 하는 자료구조예요.
LIKE: 동아리마다 회장이 한 명 있어요. "둘이 같은 동아리야?"는 각자의 회장을 찾아 비교하면 되고, 두 동아리를 합치려면 한쪽 회장을 다른 쪽 회장 밑에 두면 돼요. 한 번 회장을 찾아간 사람은 다음부터 회장에게 바로 보고하게 하면 더 빨라져요.
STEP:
1. 원소마다 "내 부모"를 가리키고, 그룹마다 맨 위의 대표(Root)가 있어요. 처음엔 모두 자기 자신이 대표예요.
2. **find(x)**: 부모를 따라 올라가 대표를 찾아요. 두 원소의 대표가 같으면 같은 그룹이에요.
3. **union(a, b)**: 두 대표를 찾아서, 한쪽 대표를 다른 쪽 대표 밑에 붙여요.
4. 그냥 붙이면 Tree가 한 줄로 길어져 find가 O(n)이 될 수 있어요. 그래서 두 가지 요령을 써요.
5. **Union by Rank**: 낮은 Tree를 높은 Tree 밑에 붙여서 높이가 덜 자라게 해요.
6. **Path Compression**: find로 올라가는 길에 만난 모든 Node를 대표에게 직접 연결해요. 다음엔 한 번에 찾아요.
7. 두 요령을 함께 쓰면 연산 하나가 사실상 상수 시간(아주 천천히 자라는 함수 α(n))이에요.
```python
parent = list(range(n)); rank = [0] * n

def find(x):
    if parent[x] != x:
        parent[x] = find(parent[x])   # Path Compression
    return parent[x]

def union(a, b):
    ra, rb = find(a), find(b)
    if ra == rb: return False          # 이미 같은 그룹
    if rank[ra] < rank[rb]: ra, rb = rb, ra
    parent[rb] = ra                    # 낮은 Tree를 높은 Tree 밑에
    if rank[ra] == rank[rb]: rank[ra] += 1
    return True
```
CON: 합치기는 쉽지만 한 번 합친 그룹을 다시 나누는 건 못 해요.
USE: Kruskal Algorithm(최소 비용으로 모든 도시 잇기), Graph의 연결 요소 찾기, Cycle 검사(이미 같은 그룹인 두 점을 이으면 Cycle), SNS 친구 그룹 묶기.
END: Union-Find는 "대표 찾기 + 대표끼리 합치기"이고, 두 요령(Rank, Path Compression)으로 거의 O(1)이 돼요.

### Union-Find란? Path Compression과 Union by Rank는 왜 필요한가요?
E: 동아리마다 회장이 한 명 있습니다. "둘이 같은 동아리야?"는 각자의 회장을 찾아 비교하면 되고(find), 두 동아리를 합치려면 한쪽 회장을 다른 쪽 회장 밑에 두면 됩니다(union). 한 번 회장을 찾아간 사람은 다음부터 회장에게 바로 보고하게 하면(Path Compression) 더 빨라집니다.
A: Union-Find는 서로 겹치지 않는 Set들을 Tree Forest로 표현해, find(Root 찾기)로 같은 Set인지 확인하고 union으로 두 Set을 합칩니다. 그냥 합치면 Tree가 한 줄로 길어져 O(n)이 될 수 있어서, 낮은 Tree를 높은 Tree 밑에 붙이는 Union by Rank와 find 도중 만난 Node를 Root에 직접 잇는 Path Compression을 함께 씁니다. 둘을 쓰면 연산당 거의 상수 시간(Inverse Ackermann Function α(n))이고, Kruskal MST와 Connected Component 찾기에 씁니다.
```python
parent = list(range(n)); rank = [0] * n

def find(x):
    if parent[x] != x:
        parent[x] = find(parent[x])   # Path Compression
    return parent[x]

def union(a, b):
    ra, rb = find(a), find(b)
    if ra == rb: return False          # 이미 같은 Set
    if rank[ra] < rank[rb]: ra, rb = rb, ra
    parent[rb] = ra                    # 낮은 Tree를 높은 Tree 밑에
    if rank[ra] == rank[rb]: rank[ra] += 1
    return True
```
