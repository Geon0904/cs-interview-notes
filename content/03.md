## OS 기본

#### Operating System과 Kernel
ONE: **Operating System(OS)**은 CPU·Memory·Disk 같은 하드웨어를 여러 프로그램이 **안전하고 공평하게** 나눠 쓰도록 관리하는 프로그램이고, 그 핵심 부분이 **Kernel**이에요.
LIKE: 식당이 수십 개 모인 식당 거리를 떠올려 보세요. 각 식당(프로그램)은 장사만 신경 쓰고, 전기·가스·창고 배정·청소 순서는 거리 전체의 총괄 매니저(OS)가 맡아요. 매니저 사무실에서 실제 설비를 만지는 핵심 직원이 Kernel이에요.
STEP:
1. **OS가 없다면?** 모든 프로그램이 하드웨어를 직접 다뤄야 하고, 한 프로그램이 다른 프로그램의 Memory를 마음대로 덮어쓸 수도 있어요.
2. **OS가 하는 일 ①**: 하드웨어를 쉽게 쓰게 해 줘요. 프로그램은 "파일 열어 줘"라고만 하면 되고, Disk 회로를 몰라도 돼요.
3. **OS가 하는 일 ②**: 자원을 나눠 줘요. CPU 시간, Memory 공간, 파일, 네트워크를 프로그램들에게 배분해요.
4. **OS가 하는 일 ③**: 서로 지켜 줘요(Isolation). 한 프로그램이 죽거나 나쁜 짓을 해도 다른 프로그램과 시스템은 무사하게요.
5. **Kernel**: OS 중에서 하드웨어를 직접 관리하는 핵심이에요. 파일 탐색기나 설정 앱 같은 것은 OS에 포함돼도 Kernel은 아니에요.
6. **User Mode / Kernel Mode**: CPU에는 두 가지 모드가 있어요. 일반 프로그램은 **User Mode**에서 돌아서 위험한 명령(하드웨어 직접 제어, 남의 Memory 접근)을 못 해요. Kernel만 **Kernel Mode**에서 모든 명령을 쓸 수 있어요.
WHY: 한 프로그램의 Bug나 악성 코드가 컴퓨터 전체를 망가뜨리지 못하게 하려고요. 위험한 일은 믿을 수 있는 Kernel만 하게 막아 두는 거예요.
USE: Windows, macOS, Linux, Android, iOS가 모두 OS이고, 서버의 대부분은 Linux Kernel 위에서 돌아가요.
KEY: 프로그램이 Kernel의 도움이 필요할 때는 정해진 입구인 **System Call**로만 부탁할 수 있어요(다음 개념).
END: OS는 하드웨어를 대신 관리하고 나눠 주고 지켜 주는 총괄 매니저이고, 위험한 일은 Kernel Mode의 Kernel만 할 수 있어요.

#### System Call (시스템 콜)
ONE: 일반 프로그램이 Kernel에게 **"파일 읽어 줘", "새 Process 만들어 줘"처럼 공식적으로 부탁하는 입구**예요.
LIKE: 식당 직원은 가스 밸브나 분전함을 직접 만질 수 없어요. 필요하면 매니저 사무실 창구에 정해진 요청서를 내요. "창고에서 재료 꺼내 주세요(read)", "직원 한 명 더 써 주세요(fork)". 이 요청서가 System Call이에요.
STEP:
1. 프로그램이 파일을 읽고 싶어요. 하지만 User Mode에서는 Disk를 직접 만질 수 없어요.
2. 그래서 `read` 같은 System Call을 호출해요. 그러면 CPU가 특별한 명령(x86-64의 `syscall`)으로 **Kernel Mode로 전환**해요.
3. Kernel이 요청이 안전한지 확인하고(이 파일을 읽을 권한이 있나?), 실제로 Disk에서 데이터를 가져와요.
4. 결과를 프로그램에 넘겨주고 다시 **User Mode로 돌아와요**.
5. 우리가 쓰는 Python의 `open()`, C의 `printf()` 같은 함수도 내부에서는 결국 System Call을 불러요.
| 분야 | 대표 System Call |
| 파일 | open, read, write, close |
| Process | fork, exec, wait, exit |
| Memory | mmap, brk |
| Network | socket, connect, send, recv |
WHY: 위험한 일은 Kernel만 하게 하되, 프로그램이 필요한 기능은 쓸 수 있게 하려면 "정해진 창구"가 필요해요.
CON: User Mode ↔ Kernel Mode 전환에는 비용이 들어요. 그래서 데이터를 1 Byte씩 여러 번 읽기보다 한 번에 크게 읽는 게 빨라요(Buffering).
END: System Call은 프로그램이 Kernel에게 일을 맡기는 유일한 공식 창구이고, 호출할 때마다 Kernel Mode로 잠깐 다녀와요.

#### Interrupt (인터럽트)
ONE: CPU에게 **"지금 처리해야 할 일이 생겼어!"라고 알리는 신호**예요. CPU는 하던 일을 잠깐 멈추고 그 일을 처리한 뒤 돌아와요.
LIKE: 요리하는 중에 초인종이 울리면, 하던 일에 표시를 해 두고 문을 열어 준 다음 돌아와서 이어서 요리해요. 요리사가 1초마다 문 앞에 가서 손님이 왔는지 확인하는 것(Polling)보다 훨씬 효율적이에요.
STEP:
1. **Hardware Interrupt**: 키보드를 누르거나, 네트워크로 데이터가 도착하거나, Disk 읽기가 끝나면 장치가 CPU에 신호를 보내요.
2. **Timer Interrupt**: 일정 시간마다 울리는 알람이에요. OS가 한 프로그램이 CPU를 독차지하지 못하게 주기적으로 제어권을 되찾는 데 써요.
3. **Software Interrupt / Exception**: 0으로 나누기, 없는 Memory 접근(Page Fault), System Call처럼 프로그램 실행 중에 생기는 사건이에요.
4. **처리 과정 ①**: CPU가 지금 하던 일의 상태(Register, PC)를 저장해요.
5. **처리 과정 ②**: **Interrupt Vector Table**에서 "이 Interrupt는 이 함수가 처리"라는 정보를 찾아 그 처리 함수(**ISR, Interrupt Service Routine**)를 실행해요.
6. **처리 과정 ③**: 처리가 끝나면 저장해 둔 상태를 복구하고 하던 일로 돌아가요.
WHY: 장치들은 언제 일이 생길지 몰라요. 계속 확인(Polling)하면 CPU가 낭비되고, Interrupt를 쓰면 일이 생겼을 때만 반응하면 돼요.
USE: 키보드 입력, 마우스 움직임, 네트워크 패킷 도착, 그리고 여러 프로그램이 번갈아 실행되는 것(Timer Interrupt) 모두 Interrupt 덕분이에요.
END: Interrupt는 "일 생기면 불러 줘" 방식이에요. CPU는 상태를 저장하고 → 처리하고 → 복구해서 돌아와요.

### OS와 Kernel이란? User Mode와 Kernel Mode를 나누는 이유는?
E: 식당 직원(일반 프로그램)은 가스 밸브나 분전함을 직접 만지면 안 됩니다. 필요하면 관리인(Kernel)에게 부탁하고, 관리인만 위험한 설비에 접근합니다.
A: Kernel은 OS의 핵심으로 Hardware를 직접 관리하는 부분입니다. CPU는 User Mode에서 위험한 명령(Device 제어, 다른 Process Memory 접근)을 막고, Kernel Mode에서만 허용합니다. 이렇게 나눠야 한 프로그램의 Bug나 악성 코드가 시스템 전체를 망가뜨리지 못합니다.

### System Call이란?
E: 직원이 관리인에게 내는 공식 요청서입니다. "창고에서 파일 좀 꺼내 주세요(read)", "새 직원 한 명 더 써 주세요(fork)".
A: System Call은 사용자 프로그램이 Kernel의 기능(File, Process, Network, Memory)을 쓰기 위한 입구입니다. 호출하면 Trap 명령(x86-64의 syscall)으로 Kernel Mode로 전환되고, Kernel이 일을 처리한 뒤 User Mode로 돌아옵니다. read, write, open, fork, exec가 대표적입니다.

### Interrupt란? 처리 과정은?
E: 요리 중에 초인종이 울리면 하던 일에 표시를 해 두고 문을 열어 주고 돌아와 이어서 합니다. 요리사가 1초마다 문을 확인하는 것(Polling)보다 훨씬 효율적입니다.
A: Interrupt는 CPU에게 "지금 처리해야 할 일이 생겼다"고 알리는 신호로, 키보드·Timer·Disk 같은 Hardware Interrupt와 System Call·Exception(0으로 나누기, Page Fault) 같은 Software Interrupt가 있습니다. CPU는 현재 상태를 저장하고, Interrupt Vector Table에서 처리 루틴(ISR, Interrupt Service Routine)을 찾아 실행한 뒤, 상태를 복구해 하던 일로 돌아갑니다.

## Process

#### Program과 Process, 그리고 Address Space
ONE: **Program**은 Disk에 저장된 실행 파일이고, **Process**는 그 Program이 Memory에 올라와 **실제로 실행 중인 상태**예요.
LIKE: Program은 책장에 꽂힌 요리책이고, Process는 그 요리책을 펴서 지금 영업 중인 식당이에요. 같은 요리책으로 식당을 두 개 열 수도 있어요. Chrome 창을 여러 개 띄우는 것처럼요.
STEP:
1. Program(예: `chrome.exe`)은 Disk에 가만히 있는 파일이에요. 아무 일도 하지 않아요.
2. 실행하면 OS가 Memory에 공간을 마련하고 Program을 올려요. 이제 Process가 됐어요.
3. OS는 Process마다 번호(**PID, Process ID**)와 자원(Memory 공간, 열린 파일, CPU 시간)을 줘요.
4. 각 Process는 자기만의 Memory 공간(**Address Space**)을 가져요. 다른 Process의 공간은 볼 수도 만질 수도 없어요.
5. Address Space는 네 구역으로 나뉘어요.
| 영역 | 들어가는 것 | 식당 비유 |
| Code (Text) | 실행할 기계어 명령 | 벽에 붙은 요리법 |
| Data | Global 변수, static 변수 | 항상 같은 자리에 있는 기본 양념 |
| Heap | 실행 중 malloc/new로 만드는 데이터 | 필요할 때 빌리는 추가 선반 (위로 늘어남) |
| Stack | 함수 호출마다 Local 변수·Return Address | 주문마다 쌓았다 치우는 접시 (아래로 늘어남) |
WHY: Process마다 공간을 분리해야 한 프로그램이 죽어도 다른 프로그램이 무사하고, 서로의 데이터를 훔쳐볼 수 없어요.
USE: 작업 관리자(Windows)나 `ps`·`top`(Linux)에서 보이는 목록이 바로 Process들이에요.
KEY: Heap은 낮은 주소에서 위로, Stack은 높은 주소에서 아래로 자라서 서로를 향해 늘어나요.
END: Program은 요리책, Process는 영업 중인 식당이에요. 식당마다 자기 창고(Address Space)가 따로 있어요.

#### PCB와 Process State (프로세스 상태)
ONE: OS는 Process마다 **PCB(Process Control Block)**라는 정보 카드를 만들어 관리하고, Process는 **New → Ready → Running → Waiting → Terminated** 상태를 오가요.
LIKE: 매니저가 식당마다 인사카드를 갖고 있어요. 가게 번호, 지금 영업 중인지, 요리사가 어디까지 했는지가 적혀 있어서, 요리사가 잠시 다른 가게에 갔다 와도 카드를 보고 바로 이어서 할 수 있어요.
STEP:
1. **PCB에 들어가는 것**: PID, 현재 상태, Program Counter(다음에 실행할 명령 위치), Register 값, 우선순위(Priority), Memory 정보(Page Table), 열린 파일 목록.
2. **New**: Process가 막 만들어지는 중이에요.
3. **Ready**: 실행할 준비는 됐고 CPU 차례를 기다려요. 요리사를 기다리며 줄 선 주문서예요.
4. **Running**: 지금 CPU에서 실행 중이에요. CPU Core 하나에는 한 순간에 하나만 Running일 수 있어요.
5. **Waiting (Blocked)**: Disk 읽기나 키보드 입력처럼 무언가를 기다리는 중이라 CPU가 있어도 실행할 수 없어요. 재료 배달을 기다리는 주문서예요.
6. **Terminated**: 실행이 끝났어요.
7. **상태가 바뀌는 순간들**: Running 중에 Timer Interrupt가 오면 → Ready로, I/O를 요청하면 → Waiting으로, I/O가 끝나면 → Ready로 돌아가요.
WHY: CPU는 Process들을 번갈아 실행해요. 멈췄다가 다시 시작하려면 "어디까지 했는지"를 어딘가에 저장해 둬야 하는데, 그게 PCB예요.
USE: Linux의 `top`에서 보이는 `R`(Running), `S`(Sleeping, 기다리는 중), `Z`(Zombie) 같은 표시가 Process 상태예요.
END: PCB는 Process의 인사카드이고, Process는 Ready(줄 서기) ↔ Running(실행) ↔ Waiting(기다림)을 오가요.

#### fork · exec · wait: Process 만들기
ONE: Unix/Linux에서는 **fork()로 지금 Process를 복제**하고, **exec()로 다른 Program으로 갈아타고**, **wait()로 자식이 끝나기를 기다려요**.
LIKE: fork는 식당을 통째로 복사해 옆에 똑같은 분점을 내는 것, exec는 분점의 간판과 메뉴를 완전히 다른 가게로 바꾸는 것, wait는 본점이 분점의 영업 종료 보고를 기다리는 것이에요.
STEP:
1. **fork()**: 지금 Process(Parent)를 거의 그대로 복제해 Child Process를 만들어요. 코드도, 변수 값도, 실행 위치도 같아요.
2. fork() 다음 줄부터는 Parent와 Child가 **둘 다** 실행돼요. 둘을 구분하려면 반환값을 봐요. Parent는 Child의 PID를 받고, Child는 0을 받아요.
3. **exec()**: 현재 Process의 Memory를 새 Program으로 통째로 덮어써요. PID는 그대로지만 하는 일은 완전히 바뀌어요.
4. 터미널에서 `ls`를 치면, Shell이 fork()로 자기 복제본을 만들고, 그 Child가 exec()로 `ls` Program이 돼요.
5. **wait()**: Parent가 Child가 끝날 때까지 기다리고, Child의 종료 결과(Exit Status)를 받아요.
6. **출력 순서**: fork 후 Parent와 Child는 따로 Scheduling돼요. 누가 먼저 실행될지는 OS 마음이라 wait 같은 동기화가 없으면 출력 순서를 장담할 수 없어요.
```c
pid_t pid = fork();
if (pid == 0) {            // Child
    execlp("ls", "ls", NULL);
} else {                   // Parent
    wait(NULL);            // Child가 끝날 때까지 기다림
}
```
KEY: fork()를 n번 연달아 호출하면, 만들어진 Process들도 다음 fork를 실행하므로 Process가 2ⁿ개가 돼요.
WHY: "복제 + 갈아타기"로 나누면 Child가 새 Program이 되기 전에 입출력 연결이나 환경을 마음대로 준비할 수 있어요. Shell의 `>` 리다이렉션이 이 방식으로 구현돼요.
END: fork = 복제, exec = 갈아타기, wait = 기다리기. 터미널에서 명령을 칠 때마다 이 세 가지가 일어나요.

#### Zombie Process와 Orphan Process
ONE: **Zombie**는 끝났는데 부모가 종료 결과를 안 가져가서 기록만 남은 Process, **Orphan**은 부모가 먼저 끝나서 홀로 남은 Process예요.
LIKE: Zombie는 분점이 문을 닫았는데 본점이 폐업 서류에 도장을 안 찍어서 주소록에 이름만 남은 상태예요. Orphan은 본점이 먼저 문을 닫아서 분점만 남은 상태예요.
STEP:
1. Child가 끝나면 OS는 Child의 Memory는 정리하지만, "어떻게 끝났는지"(Exit Status)를 담은 작은 기록은 남겨 둬요. Parent가 확인할 수 있게요.
2. Parent가 wait()를 부르면 그 기록을 가져가고, 그제야 기록도 사라져요.
3. **Zombie Process**: Parent가 wait()를 안 불러서 기록이 계속 남은 상태예요. Memory는 거의 안 쓰지만 Process Table 칸(PID)을 차지해요.
4. Zombie가 수없이 쌓이면 PID가 바닥나서 새 Process를 만들 수 없게 돼요.
5. **Orphan Process**: Parent가 먼저 끝나 버린 Child예요. Linux에서는 init(PID 1) 같은 Process가 입양해서, 나중에 대신 wait()로 정리해 줘요.
WHY: 서버 프로그램이 Child를 계속 만들면서 wait를 빼먹으면 Zombie가 쌓이는 실제 장애가 생겨요.
USE: `ps`에서 상태가 `Z`나 `<defunct>`로 보이면 Zombie예요. 해결은 Parent가 wait()를 하도록 고치거나 Parent를 종료하는 거예요(그러면 init이 입양해 정리해요).
END: 끝났는데 정리 안 된 게 Zombie, 부모를 잃은 게 Orphan. 부모는 자식을 wait()로 꼭 거둬야 해요.

### Process란? Program과의 차이는?
E: Program은 책장에 꽂힌 요리책, Process는 그 요리책으로 지금 실제 영업 중인 식당입니다. 같은 요리책으로 식당을 두 개 열 수도 있습니다(Chrome 창 여러 개).
A: Program은 Disk에 저장된 Executable(실행 파일)이고, Process는 그것이 Memory에 올라와 실행 중인 상태입니다. Process는 자기만의 Address Space, Register 상태, 열린 File 같은 자원을 OS로부터 받습니다.

### Process Address Space는 어떻게 구성되나요?
| 영역 | 들어가는 것 | 식당 비유 |
| Code (Text) | 실행할 기계어 명령 | 벽에 붙은 요리법 |
| Data | Global 변수, static 변수 | 항상 같은 자리에 있는 기본 양념 |
| Heap | 실행 중 malloc/new로 만드는 데이터 | 필요할 때 빌리는 추가 선반 (위로 늘어남) |
| Stack | Function Call마다 Local 변수·Return Address | 주문마다 쌓았다 치우는 접시 (아래로 늘어남) |
A: Process Address Space는 Code·Data·Heap·Stack 영역으로 나뉩니다. Heap은 낮은 Address에서 위로, Stack은 높은 Address에서 아래로 자라 서로를 향해 늘어납니다.

### PCB에는 무엇이 들어 있나요?
E: 매니저가 식당마다 갖고 있는 인사카드입니다. 가게 번호, 지금 영업 중인지, 요리사가 어디까지 했는지가 적혀 있어서 요리사가 돌아와도 바로 이어서 할 수 있습니다.
A: PCB(Process Control Block)는 OS가 Process마다 유지하는 정보 묶음으로, PID, Process State, Program Counter와 Register 값, Scheduling 정보(Priority), Memory 관리 정보(Page Table), 열린 File 목록 등이 들어 있습니다. Context Switching 때 여기에 상태를 저장하고 불러옵니다.

### Process State는?
E: 식당 예약 접수(New) → 줄 서서 요리사 기다림(Ready) → 요리 중(Running) → 재료 배달 기다림(Waiting) → 영업 종료(Terminated).
A: Process는 New, Ready, Running, Waiting(Blocked), Terminated 상태를 오갑니다. 실행 중 Timer Interrupt가 오면 Ready로, I/O를 요청하면 Waiting으로 가고, I/O가 끝나면 다시 Ready 상태가 됩니다.

### fork(), exec(), wait()는 어떻게 동작하나요? fork 후 출력 순서는 왜 정해져 있지 않나요?
E: fork는 식당을 통째로 복사해 옆에 똑같은 분점을 내는 것, exec는 분점 간판과 메뉴를 완전히 다른 가게로 바꾸는 것, wait는 본점이 분점의 영업 종료 보고를 기다리는 것입니다. 본점과 분점 중 누가 먼저 손님을 받을지는 매니저(Scheduler) 마음입니다.
A: fork()는 현재 Process를 복제해 Child를 만들고, Parent에게는 Child의 PID를, Child에게는 0을 반환합니다. exec()는 현재 Process의 Memory를 새 Program으로 덮어쓰고, wait()는 Child가 끝날 때까지 Parent를 멈춰 둡니다. fork 후 Parent와 Child는 독립적으로 Scheduling되므로 wait 같은 Synchronization이 없으면 출력 순서를 보장할 수 없습니다.
M: fork()를 연속 n번 호출하면 모든 Process가 다음 fork를 실행하므로 Process는 총 2ⁿ개가 됩니다.

### Zombie Process와 Orphan Process란?
E: Zombie는 분점이 문을 닫았는데 본점이 폐업 서류에 도장을 안 찍어 주소록에 이름만 남은 상태, Orphan은 본점이 먼저 문을 닫아 분점만 남은 상태입니다.
A: Zombie Process는 종료했지만 Parent가 wait()로 종료 상태(Exit Status)를 가져가지 않아 Process Table에 항목이 남은 상태입니다. Orphan Process는 Parent가 먼저 종료된 Child로, Linux에서는 init(PID 1) 같은 Process가 입양해 대신 정리해 줍니다.

## Thread

#### Thread와 Process의 차이
ONE: **Thread**는 하나의 Process 안에서 **동시에 진행되는 실행 흐름**이에요. 같은 Process의 Thread들은 Memory를 함께 쓰고, 각자 "어디까지 했는지"만 따로 가져요.
LIKE: Process가 독립된 식당 건물이라면, Thread는 그 식당 안에서 동시에 진행 중인 주문서들이에요. 주문서들은 같은 주방과 창고를 함께 쓰고, 각자의 진행 메모(Register)와 작업대(Stack)만 따로 가져요. 다른 식당의 창고는 못 써요.
STEP:
1. Process 하나에는 처음에 Thread가 하나 있어요(Main Thread).
2. Thread를 더 만들면, 한 Process 안에서 여러 일이 동시에 진행돼요. 예: 브라우저가 화면을 그리면서 동시에 파일을 내려받기.
3. **공유하는 것**: Code, Data(Global 변수), Heap, 열린 파일.
4. **따로 갖는 것**: Stack, Register, Program Counter. 각자 다른 함수를 실행 중일 수 있으니까요.
5. 그래서 Thread끼리는 변수 하나로 바로 데이터를 주고받을 수 있지만, 동시에 같은 변수를 고치면 문제가 생길 수 있어요(뒤에서 배울 Synchronization).
| 항목 | Process | Thread |
| Memory | 독립된 Address Space | Code·Data·Heap 공유, Stack만 별도 |
| 만들기·전환 비용 | 큼 | 작음 |
| 데이터 주고받기 | IPC 필요 | 공유 변수로 바로 (동기화 필요) |
| 오류의 영향 | 다른 Process는 무사 | Process 전체가 죽을 수 있음 |
WHY: 한 프로그램 안에서 여러 일을 동시에 하면서도, Process를 여러 개 만드는 것보다 훨씬 가볍게 하려고요.
USE: 웹 서버가 요청마다 Thread를 하나씩 맡기거나, 게임이 그래픽·소리·네트워크를 각각 다른 Thread로 처리해요.
END: Process는 건물, Thread는 그 안의 작업 흐름이에요. Thread는 가볍지만 Memory를 공유하니 조심해서 써야 해요.

#### Multi-Thread vs Multi-Process
ONE: 여러 일을 동시에 하려면 **Thread를 여러 개** 쓰거나 **Process를 여러 개** 쓸 수 있어요. Thread는 가볍고 빠르고, Process는 안전하고 튼튼해요.
LIKE: 손님이 늘었을 때 같은 건물에서 주문서를 더 돌리는 것(Multi-Thread)은 싸고 빠르지만, 같은 주방을 쓰니 서로 부딪히지 않게 조심해야 해요. 새 건물을 하나 더 짓는 것(Multi-Process)은 비싸지만 한 가게에 불이 나도 다른 가게는 멀쩡해요.
STEP:
1. **Multi-Thread의 장점**: 만들고 전환하는 비용이 작아요. Memory를 공유하니 데이터를 복사 없이 바로 주고받아요.
2. **Multi-Thread의 단점**: 공유 데이터를 동시에 고치면 꼬여요(Race Condition). 한 Thread가 치명적인 오류를 내면 Process 전체가 죽어요.
3. **Multi-Process의 장점**: Memory가 분리돼 있어 하나가 죽어도 나머지는 살아요. 보안상 격리도 돼요.
4. **Multi-Process의 단점**: 만드는 비용과 Memory 사용이 커요. 데이터를 주고받으려면 IPC를 써야 해요.
5. **선택 기준**: 속도와 데이터 공유가 중요하면 Thread, 안정성과 격리가 중요하면 Process.
USE: Chrome은 탭마다 Process를 따로 둬서, 한 탭이 멈춰도 다른 탭은 멀쩡해요(Multi-Process). 반면 많은 서버 프로그램은 요청을 Thread Pool로 처리해요(Multi-Thread).
END: 가볍고 빠르게는 Multi-Thread, 안전하고 튼튼하게는 Multi-Process예요.

#### User-Level Thread와 Kernel-Level Thread
ONE: **User-Level Thread**는 Kernel 모르게 프로그램(Library)이 관리하는 Thread이고, **Kernel-Level Thread**는 Kernel이 직접 알고 관리하는 Thread예요.
LIKE: User-Level Thread는 식당 점장이 몰래 나눠 준 보조 주문서예요. 총괄 매니저(Kernel)는 그런 게 있는 줄 몰라서 그 식당에 요리사를 한 명만 보내 줘요. Kernel-Level Thread는 매니저에게 정식으로 등록한 주문서라서, 매니저가 요리사를 여러 명 보내 동시에 처리해 줄 수 있어요.
STEP:
1. **User-Level Thread**: Library가 Thread 전환을 직접 해요. Kernel에 부탁하지 않으니 전환이 아주 빨라요.
2. 단점: Kernel은 이 Process를 Thread 하나짜리로 봐요(Many-to-One). 그래서 한 Thread가 Disk 읽기처럼 기다리는 System Call을 하면 Process 전체가 멈추고, CPU Core가 여러 개여도 하나만 써요.
3. **Kernel-Level Thread**: Kernel이 Thread 하나하나를 알고 Scheduling해요. 여러 Core에서 진짜로 동시에 돌 수 있고, 하나가 기다려도 나머지는 계속 돌아요.
4. 단점: 만들고 전환할 때 Kernel을 거쳐야 해서 조금 더 비싸요.
5. Linux와 Windows는 우리가 만드는 Thread 하나를 Kernel Thread 하나와 1:1로 연결해요(**One-to-One Model**).
USE: Go 언어의 goroutine처럼 아주 가벼운 실행 단위 여러 개를 소수의 Kernel Thread 위에서 돌리는 방식(Many-to-Many)도 있어요.
END: User-Level은 빠르지만 Kernel이 몰라서 한계가 있고, Kernel-Level은 조금 무겁지만 여러 Core를 제대로 써요.

### Process와 Thread의 차이를 알려주세요.
E: Process는 독립된 식당 건물이고, Thread는 그 식당 안에서 동시에 진행 중인 주문서입니다. 주문서들은 같은 주방·창고를 쓰고, 각자 "어디까지 했는지" 메모(Register)와 개인 작업대(Stack)만 따로 갖습니다. 다른 식당의 창고는 못 씁니다.
A: Process는 독립된 Address Space와 자원을 가진 실행 단위이고, Thread는 Process 안의 실행 흐름입니다. 같은 Process의 Thread는 Code·Data·Heap·열린 File을 공유하고 Stack·Register·PC만 따로 갖습니다. 그래서 Thread는 생성·전환이 가볍고 통신이 쉽지만, 한 Thread의 치명적 오류가 Process 전체를 종료시킵니다.
| 항목 | Process | Thread |
| Memory | 독립된 Address Space | Code·Data·Heap 공유, Stack만 별도 |
| 생성·전환 비용 | 큼 | 작음 |
| 통신 | IPC 필요 | 공유 변수로 바로 가능 (Synchronization 필요) |
| 오류 영향 | 다른 Process는 무사 | Process 전체가 종료될 수 있음 |

### Multi-Process 대신 Multi-Thread를 사용하는 이유는?
E: 손님이 늘었을 때 새 건물을 하나 더 짓는 것(Multi-Process)보다 같은 건물에서 주문서를 더 돌리는 것(Multi-Thread)이 싸고 빠릅니다. 대신 같은 주방을 쓰니 서로 부딪히지 않게 조심해야 합니다.
A: Thread는 Address Space를 공유해서 생성·Context Switching 비용과 Memory 사용이 적고, IPC 없이 데이터를 주고받을 수 있습니다. 대신 공유 데이터에 대한 Synchronization이 필요하고, 한 Thread의 오류가 전체로 번집니다. 안정성·보안이 중요하면 Multi-Process(예: Chrome의 탭 분리)를 택합니다.

### User-Level Thread와 Kernel-Level Thread의 차이는?
E: User-Level Thread는 식당 안에서 점장이 몰래 나눠 준 보조 주문서라서 총괄 매니저(Kernel)는 그런 게 있는 줄 모릅니다. 그래서 빠르게 바꿀 수 있지만, 매니저는 요리사를 식당당 한 명만 보내 줍니다.
A: User-Level Thread는 Library가 Kernel 모르게 관리해 전환이 빠르지만, Many-to-One Model에서는 한 Thread가 Blocking System Call을 하면 전부 멈추고 여러 Core를 못 씁니다. Kernel-Level Thread는 Kernel이 직접 Scheduling해 여러 Core에서 병렬로 돌지만 생성·전환 비용이 큽니다. Linux와 Windows는 User Thread와 Kernel Thread를 One-to-One으로 잇습니다.

## Context Switching과 IPC

#### Context Switching (문맥 교환)
ONE: CPU가 실행 중인 Process(또는 Thread)를 다른 것으로 바꿀 때, **지금 상태를 저장하고 다음 것의 상태를 불러오는** 작업이에요.
LIKE: 요리사가 A 주문서를 하다가 B 주문서로 넘어갈 때, A에 "양파 썰기까지 함"이라고 적어 두고 B의 메모를 읽고 이어서 해요. 메모를 쓰고 읽는 동안은 요리가 멈추니까, 너무 자주 바꾸면 손해예요.
STEP:
1. Timer Interrupt나 System Call 때문에 Kernel Mode로 들어가요.
2. 지금 Process의 Register와 Program Counter를 그 Process의 PCB에 저장하고, 상태를 Running → Ready(또는 Waiting)로 바꿔요.
3. Scheduler가 다음에 실행할 Process를 골라요.
4. 고른 Process의 PCB에서 Register와 Program Counter를 꺼내 CPU에 복구해요. 다른 Process라면 Memory 지도(Page Table)도 바꿔요.
5. User Mode로 돌아가면, 새 Process가 멈췄던 곳부터 이어서 실행돼요.
WHY: CPU Core 하나로 여러 프로그램을 "동시에" 돌리는 것처럼 보이게 하려면, 아주 짧은 시간마다 번갈아 실행해야 해요. 그때마다 Context Switching이 일어나요.
CON: 저장·복구하는 동안은 쓸모 있는 일을 못 해요. 게다가 새 Process로 바뀌면 Cache와 TLB에 이전 Process의 데이터만 있어서(차가워진 상태) 한동안 느려요.
KEY: 같은 Process 안의 Thread끼리 바꿀 때는 Memory 지도(Page Table)를 바꿀 필요가 없어서, Process끼리 바꾸는 것보다 가벼워요.
END: Context Switching은 "메모하고 → 다음 메모 읽고 → 이어서 하기"이고, 꼭 필요하지만 공짜는 아니에요.

#### IPC (Inter-Process Communication)
ONE: Process들은 Memory가 분리돼 있어서 직접 데이터를 주고받을 수 없어요. 그래서 OS가 제공하는 **통신 방법(IPC)**으로 대화해요.
LIKE: 식당들은 서로의 창고에 들어갈 수 없어요. 대신 가게 사이 파이프(Pipe), 공용 우편함(Message Queue), 함께 쓰는 공동 창고(Shared Memory), 전화(Socket), 초인종(Signal)으로 소통해요.
STEP:
1. **Pipe**: 한쪽에서 넣으면 다른 쪽에서 나오는 일방통행 통로예요. Shell의 `ls | grep txt`가 Pipe예요.
2. **Message Queue**: 메시지 단위로 넣고 꺼내는 우편함이에요.
3. **Shared Memory**: 같은 실제 Memory 공간을 두 Process에 연결해요. 복사가 없어 가장 빠르지만, 동시에 고치지 않도록 동기화를 직접 해야 해요.
4. **Socket**: 네트워크 통신 방식이에요. 같은 컴퓨터뿐 아니라 다른 컴퓨터와도 대화할 수 있어요.
5. **Signal**: 아주 짧은 알림만 보내요. 터미널에서 Ctrl+C를 누르면 SIGINT Signal이 가서 프로그램이 멈춰요.
| 방식 | 비유 | 특징 |
| Pipe | 일방통행 파이프 | 한 방향, 보통 Parent-Child 사이 (Named Pipe는 아무나) |
| Message Queue | 공용 우편함 | 메시지 단위로 넣고 꺼냄 |
| Shared Memory | 같이 쓰는 창고 | 가장 빠름, 동기화는 직접 |
| Socket | 전화 | 다른 컴퓨터와도 통신 |
| Signal | 초인종 | 짧은 알림만 |
WHY: Process를 분리해 안전하게 만든 대신, 협력이 필요할 때 쓸 정식 통로가 필요해요.
KEY: Pipe·Message Queue·Socket은 Kernel을 거쳐 데이터를 복사하고, Shared Memory는 복사 없이 같은 공간을 보기 때문에 빠른 대신 책임이 커요.
END: IPC는 분리된 Process들이 대화하는 OS의 공식 통로예요. 빠르게는 Shared Memory, 간단하게는 Pipe, 멀리는 Socket.

### Context Switching이 무엇인지 설명하고 과정을 나열해 주세요.
E: 요리사가 A 주문서를 하다가 B 주문서로 넘어갈 때, A에 "양파 썰기까지 함"을 적어 두고 B의 메모를 읽고 이어서 합니다. 메모를 쓰고 읽는 동안에는 요리가 멈추므로, 자주 바꾸면 손해입니다.
A: Context Switching은 CPU가 실행 중인 Process(또는 Thread)를 바꿀 때 현재 상태를 저장하고 다음 것의 상태를 불러오는 작업입니다. 저장·복구 시간에는 유용한 일을 못 하고, Cache·TLB도 식어서(Cold) Overhead가 생깁니다.
1. Timer Interrupt나 System Call로 Kernel Mode에 들어갑니다.
2. 현재 Process의 Register·PC를 PCB에 저장하고 상태를 바꿉니다(Running → Ready 또는 Waiting).
3. Scheduler가 다음에 실행할 Process를 고릅니다.
4. 새 Process의 PCB에서 Register·PC를 복구하고, 다른 Process라면 Address Space(Page Table)도 바꿉니다.
5. User Mode로 돌아가 새 Process가 멈췄던 곳부터 실행됩니다.
M: 같은 Process의 Thread 사이 전환은 Address Space를 바꾸지 않아도 되므로 Process 전환보다 가볍습니다.

### IPC(Inter-Process Communication) 방식은?
| 방식 | 비유 | 특징 |
| Pipe | 두 가게 사이 일방통행 파이프 | 한 방향, 보통 Parent-Child 사이 (Named Pipe는 아무나) |
| Message Queue | 공용 우편함 | Message 단위로 넣고 꺼냄 |
| Shared Memory | 두 가게가 같이 쓰는 창고 | 가장 빠르지만 Synchronization을 직접 해야 함 |
| Socket | 전화 | 다른 컴퓨터와도 통신 가능 |
| Signal | 초인종 | 짧은 알림만 전달 (예: Ctrl+C의 SIGINT) |
A: Process는 Memory가 분리되어 있어 OS가 제공하는 IPC로 통신합니다. Pipe·Message Queue·Socket은 Kernel을 거쳐 데이터를 복사하고, Shared Memory는 같은 Physical Memory를 양쪽에 연결해 빠르지만 Synchronization을 직접 책임져야 합니다.

## CPU Scheduling

#### CPU Scheduling과 Scheduler
ONE: Ready 상태로 줄 선 Process들 중에서 **다음에 누구에게 CPU를 줄지 정하는 것**이 CPU Scheduling이고, 그걸 정하는 OS 부품이 **Scheduler**예요.
LIKE: 요리사(CPU Core)는 한 번에 주문서 하나만 처리할 수 있어요. 주문서가 잔뜩 밀려 있을 때 "다음엔 뭘 할까"를 정하는 주방장이 Scheduler예요.
STEP:
1. Process 수는 보통 CPU Core 수보다 훨씬 많아요. 그래서 순서를 정해 번갈아 실행해야 해요.
2. **좋은 Scheduling의 기준**은 여러 가지예요.
3. **CPU Utilization**: CPU가 놀지 않고 일하는 비율. 높을수록 좋아요.
4. **Throughput**: 단위 시간에 끝내는 작업 수. 많을수록 좋아요.
5. **Waiting Time / Turnaround Time**: 줄 서서 기다린 시간 / 도착부터 끝날 때까지 걸린 시간. 짧을수록 좋아요.
6. **Response Time**: 요청 후 첫 반응까지 걸린 시간. 키보드를 눌렀을 때 바로 반응해야 하는 프로그램에서 중요해요.
7. **Scheduler의 종류**: Short-term(다음에 CPU를 줄 Process를 밀리초 단위로 결정), Medium-term(Memory가 부족하면 일부 Process를 Disk로 잠시 내보냄), Long-term(어떤 작업을 Memory에 올릴지 결정, 주로 Batch 시스템).
WHY: 기준들이 서로 부딪혀요. 짧은 작업을 먼저 하면 평균 대기 시간은 줄지만 긴 작업이 계속 밀릴 수 있어요. 그래서 상황에 맞는 규칙이 필요해요.
END: Scheduler는 "다음은 누구?"를 정하는 주방장이고, 효율·공평·빠른 반응 사이에서 균형을 잡아요.

#### Scheduling Algorithm: FCFS · SJF · SRTF · Priority · RR
ONE: 줄 선 Process에게 CPU를 주는 규칙들이에요. **먼저 온 순서**, **짧은 순서**, **중요한 순서**, **조금씩 돌아가며** 등이 있어요.
LIKE: 계산대가 하나뿐인 마트에서 줄 서는 규칙을 정한다고 생각해 보세요. 그냥 온 순서대로 할 수도, 물건 적은 사람 먼저 할 수도, VIP 먼저 할 수도, 한 사람당 1분씩 돌아가며 할 수도 있어요.
STEP:
1. **FCFS (First-Come First-Served)**: 먼저 온 순서대로 끝까지 처리해요. 단순하지만, 앞에 카트를 가득 채운 사람이 있으면 뒤의 모두가 오래 기다려요(**Convoy Effect**).
2. **SJF (Shortest Job First)**: 실행 시간이 가장 짧은 작업부터 해요. 평균 대기 시간이 가장 짧아요. 하지만 실행 시간을 미리 알기 어렵고, 긴 작업은 계속 밀릴 수 있어요.
3. **SRTF (Shortest Remaining Time First)**: SJF인데, 더 짧은 작업이 새로 오면 지금 작업을 멈추고 양보해요(Preemptive).
4. **Priority**: 우선순위가 높은 작업부터 해요. 중요한 일이 먼저 되지만, 낮은 우선순위 작업은 영원히 못 할 수도 있어요.
5. **RR (Round Robin)**: 정해진 짧은 시간(**Time Quantum**)씩 돌아가며 실행하고, 다 못 끝내면 줄 맨 뒤로 가요. 모두가 금방 차례를 받아서 반응이 빨라요.
6. **예시**: 동시에 도착한 P1(24ms), P2(3ms), P3(3ms). FCFS 순서(P1→P2→P3)면 대기 시간이 0, 24, 27 → 평균 17ms. SJF 순서(P2→P3→P1)면 0, 3, 6 → 평균 3ms.
| 방식 | 규칙 | 장점 | 단점 |
| FCFS | 온 순서 | 단순 | Convoy Effect |
| SJF | 짧은 작업 먼저 | 평균 대기 최소 | 실행 시간 예측 필요, Starvation |
| SRTF | 남은 시간 짧은 순 (선점) | SJF보다 반응 좋음 | 전환 잦음, Starvation |
| Priority | 중요한 것 먼저 | 급한 일 먼저 처리 | 낮은 순위 Starvation |
| RR | Time Quantum씩 교대 | 공평, 응답 빠름 | Quantum 너무 작으면 전환 비용↑ |
KEY: RR의 Time Quantum이 너무 크면 결국 FCFS와 같아지고, 너무 작으면 Context Switching만 하다 시간이 다 가요.
USE: 우리가 쓰는 PC·휴대폰 OS는 반응성이 중요해서 RR과 Priority를 섞은 방식을 바탕으로 해요.
END: 공평하게는 RR, 평균 대기를 줄이려면 SJF, 중요한 일 먼저는 Priority. 정답은 하나가 아니라 목표에 따라 골라요.

#### Preemptive, Starvation과 Aging, 그리고 MLFQ
ONE: 실행 중인 Process에게서 **CPU를 빼앗을 수 있으면 Preemptive**예요. 계속 밀려서 못 하는 **Starvation**은 **Aging**으로 막고, 이런 아이디어를 모은 실전형 규칙이 **MLFQ**예요.
LIKE: 계산원이 손님 계산 도중에도 "잠시만요" 하고 급한 손님을 먼저 받을 수 있으면 Preemptive예요. VIP만 계속 오면 일반 손님은 영원히 못 나가는데(Starvation), 오래 기다린 손님의 등급을 조금씩 올려 주면(Aging) 결국 차례가 와요.
STEP:
1. **Non-Preemptive (비선점)**: Process가 스스로 CPU를 내놓을 때까지(끝나거나 I/O를 기다릴 때) 기다려요.
2. **Preemptive (선점)**: OS가 Timer Interrupt 등으로 실행 중인 Process를 멈추고 다른 Process에게 CPU를 줄 수 있어요. 현대 OS는 대부분 선점형이에요.
3. **Starvation (기아)**: 우선순위가 낮거나 실행 시간이 긴 Process가 계속 밀려서 영원히 실행되지 못하는 상황이에요.
4. **Aging (에이징)**: 오래 기다릴수록 우선순위를 조금씩 올려 줘서 결국 실행되게 해요.
5. **MLFQ (Multi-Level Feedback Queue)**: 우선순위가 다른 줄을 여러 개 두고, 새 작업은 맨 위 줄(빠른 줄)에 넣어요.
6. Time Quantum을 다 써 버리는 오래 걸리는 작업은 점점 아래 줄로 내려가고, 금방 끝나거나 자주 입력을 기다리는 작업은 위 줄에 남아요.
7. 그래서 실행 시간을 미리 몰라도 짧은 작업이 자연스럽게 먼저 끝나요(SJF와 비슷한 효과). 그리고 주기적으로 모든 작업을 맨 위 줄로 올려(Priority Boost) Starvation을 막아요.
WHY: 실제로는 작업의 실행 시간을 미리 알 수 없어요. MLFQ는 "지켜보면서 배우는" 방식으로 이 문제를 풀어요.
END: 빼앗을 수 있으면 Preemptive, 계속 밀리면 Starvation, 오래 기다리면 올려 주는 게 Aging, 이걸 엮은 실전 규칙이 MLFQ예요.

### Scheduler가 무엇이고, Short-term·Medium-term·Long-term으로 나누는 기준은?
E: Long-term Scheduler는 "오늘 몇 팀을 가게에 들일까"를 정하는 입구 직원, Medium-term Scheduler는 너무 붐빌 때 일부 손님을 잠시 밖 대기석으로 보내는 직원, Short-term Scheduler는 "요리사가 다음에 어느 주문서를 잡을까"를 수시로 정하는 주방장입니다.
A: Scheduler는 어떤 Process에 자원을 줄지 정하는 OS 구성 요소이고, 호출 빈도와 결정 대상으로 나눕니다. Long-term Scheduler는 어떤 작업을 Memory에 올릴지(Degree of Multiprogramming), Medium-term Scheduler는 어떤 Process를 Disk로 Swap Out할지, Short-term Scheduler는 Ready Queue에서 다음에 CPU를 줄 Process를 정하며 가장 자주(밀리초 단위) 호출됩니다.

### FCFS, SJF, SRTF, Priority, RR을 간략히 설명해 주세요.
E: 계산대가 하나뿐인 마트에서 줄 서는 규칙들입니다.
| 방식 | 규칙 | 마트 비유 | 장점 / 단점 |
| FCFS | 먼저 온 순서 | 그냥 줄 순서 | 단순 / 앞사람 카트가 가득하면 모두 기다림(Convoy Effect) |
| SJF | 실행 시간 짧은 순, Non-Preemptive | 물건 적은 사람 먼저 | 평균 대기 시간 최소 / 실행 시간 예측 필요, 긴 작업 Starvation |
| SRTF | 남은 시간 짧은 순, Preemptive | 더 적은 사람이 오면 중간에 양보 | SJF의 Preemptive 버전 / 전환 잦음, Starvation |
| Priority | Priority 높은 순 | VIP 먼저 | 중요한 일 먼저 / 낮은 Priority Starvation |
| RR | 정해진 시간(Time Quantum)씩 돌아가며 | 한 사람당 1분씩 계산 후 다시 줄 뒤로 | 응답 빠름, 공평 / Quantum이 너무 작으면 전환 비용↑, 크면 FCFS와 같아짐 |
A: FCFS(First-Come First-Served)는 도착 순서, SJF(Shortest Job First)는 실행 시간이 짧은 순서(Non-Preemptive), SRTF(Shortest Remaining Time First)는 남은 시간이 짧은 순서(Preemptive)입니다. Priority는 우선순위 순서이고, RR(Round Robin)은 Time Quantum만큼씩 돌아가며 실행해 대화형(Interactive) 시스템에 적합합니다. SJF는 평균 대기 시간이 가장 짧지만 실행 시간을 미리 알기 어렵습니다.
M: 동시에 도착한 P1(24), P2(3), P3(3)의 평균 대기 시간: FCFS = (0 + 24 + 27)/3 = 17, SJF = (0 + 3 + 6)/3 = 3.

### Preemptive vs Non-Preemptive, Starvation과 Aging은?
E: Preemptive(선점형)는 계산 도중에도 직원이 "잠시만요" 하고 다음 손님을 받을 수 있는 것, Non-Preemptive(비선점형)는 한 손님이 끝날 때까지 기다리는 것입니다. VIP만 계속 오면 일반 손님은 영원히 못 나가는데(Starvation, 기아), 오래 기다린 손님의 등급을 조금씩 올려 주는 것이 Aging입니다.
A: Preemptive Scheduling은 OS가 실행 중인 Process에서 CPU를 빼앗을 수 있고, Non-Preemptive는 Process가 스스로 내놓을 때까지 기다립니다. Starvation은 특정 Process가 계속 밀려 실행되지 못하는 것이고, Aging은 기다린 시간만큼 Priority를 높여 이를 막습니다.

### MLFQ(Multi-Level Feedback Queue)란?
E: 모든 손님을 일단 "빠른 줄"에 세우고, 오래 걸리는 손님은 점점 느린 줄로 보냅니다. 그러면 짧은 손님은 자연스럽게 빨리 나갑니다.
A: MLFQ는 Priority가 다른 여러 Queue를 두고, Time Quantum을 다 쓰는 CPU-Bound 작업은 아래 Queue로 내리고 자주 멈추는 Interactive(I/O-Bound) 작업은 위에 남깁니다. 실행 시간을 미리 몰라도 SJF처럼 동작하고, 주기적으로 모두 위로 올려(Priority Boost) Starvation을 막습니다.

## Synchronization (동기화)

#### Race Condition과 Critical Section
ONE: 여러 Thread가 같은 데이터를 동시에 고칠 때 **실행 순서에 따라 결과가 달라지는 문제**가 Race Condition이고, 그 데이터를 다루는 코드 구간이 **Critical Section**이에요.
LIKE: 두 직원이 동시에 재고 장부를 봤어요. 둘 다 "계란 10개"를 읽고, 각자 하나씩 쓴 뒤 "9개"라고 고쳐 써요. 실제로는 8개 남았는데 장부에는 9개라고 적혀 있어요.
STEP:
1. `count += 1`은 한 줄이지만 CPU 입장에서는 세 단계예요: ① 값 읽기 → ② 1 더하기 → ③ 값 쓰기.
2. Thread A가 ①에서 10을 읽은 직후, Thread B도 ①에서 10을 읽어요.
3. A가 ②③으로 11을 쓰고, B도 ②③으로 11을 써요.
4. 두 번 더했는데 결과는 11이에요. 하나가 사라졌어요. 이게 **Race Condition(경쟁 상태)**이에요.
5. 이런 문제는 실행 타이밍에 따라 가끔만 생겨서, 테스트에서 안 보이다가 실제 서비스에서 터지기도 해요.
6. **Critical Section(임계 영역)**: 공유 데이터를 읽고 고치는 코드 구간이에요. 한 번에 한 Thread만 들어가게 해야 해요(**Mutual Exclusion, 상호 배제**).
WHY: 은행 잔액, 재고, 좌석 예약처럼 동시에 여러 요청이 오는 곳에서 Race Condition은 돈과 신뢰를 잃는 사고가 돼요.
USE: 콘서트 티켓 예매에서 같은 좌석이 두 명에게 팔리는 문제, 쇼핑몰 재고가 마이너스가 되는 문제가 대표적이에요.
KEY: 여러 Thread가 동시에 호출해도 항상 올바른 결과를 내는 코드를 **Thread-Safe**하다고 해요. Lock으로 보호하거나, Atomic 연산을 쓰거나, 아예 고칠 수 없는(Immutable) 데이터를 쓰면 Thread-Safe하게 만들 수 있어요.
END: 동시에 고치면 꼬여요(Race Condition). 공유 데이터를 고치는 구간(Critical Section)은 한 번에 한 명만 들어가게 해야 해요.

#### Mutex와 Semaphore
ONE: **Mutex**는 한 번에 **한 명만** 들어가게 하는 자물쇠이고, **Semaphore**는 **정해진 수(N명)까지** 들어가게 하는 숫자 카운터예요.
LIKE: Mutex는 칸이 하나뿐인 화장실 열쇠예요. 열쇠를 가져간 사람만 돌려놓을 수 있어요. Semaphore는 칸이 3개인 화장실 앞 "빈 칸 수" 전광판이에요. 0이면 기다리고, 누구든 나오면 숫자가 1 올라가요.
STEP:
1. **Mutex (Mutual Exclusion)**: Critical Section에 들어갈 때 `lock()`, 나올 때 `unlock()`을 해요. 다른 Thread가 이미 잠갔으면 풀릴 때까지 기다려요.
2. Mutex에는 **주인(Ownership)**이 있어요. 잠근 Thread만 풀 수 있어요.
3. **Semaphore**: 정수 하나를 가진 카운터예요. `wait()`(P 연산)는 값을 1 줄이고, 값이 0이면 기다려요. `signal()`(V 연산)은 값을 1 늘리고, 기다리던 Thread를 깨워요.
4. 초깃값이 N이면 동시에 N개까지 들어갈 수 있어요(**Counting Semaphore**). 초깃값이 1이면 Mutex처럼 동작해요(**Binary Semaphore**).
5. Semaphore는 주인 개념이 없어서 **다른 Thread가 signal할 수 있어요**. 그래서 "A가 끝나면 B를 시작해"처럼 순서를 맞추는 데도 써요.
| 구분 | Mutex | Semaphore |
| 동시에 들어갈 수 있는 수 | 1 | N (초깃값) |
| 주인 | 있음 (잠근 Thread만 해제) | 없음 (누구나 signal) |
| 주 용도 | 공유 데이터 보호 | 자원 개수 제한, 순서 맞추기 |
USE: DB Connection이 10개뿐일 때 동시에 10개까지만 쓰게 하는 Connection Pool, 프린터 3대를 나눠 쓰는 문제에 Counting Semaphore를 써요.
END: 한 명만은 Mutex, N명까지는 Semaphore. 순서를 맞출 때도 Semaphore를 써요.

#### Spinlock · Condition Variable · Monitor
ONE: Lock을 기다리는 방법과 "조건이 될 때까지 기다리는" 도구들이에요. **Spinlock**은 계속 확인하며 기다리고, **Condition Variable**은 잠들었다 깨어나고, **Monitor**는 이 둘을 묶어 쉽게 쓰게 해요.
LIKE: Spinlock은 화장실 문 앞에서 계속 문고리를 돌려 보며 기다리는 것, Condition Variable은 "빈자리 나면 불러 주세요"라고 대기 명단에 이름을 적고 앉아서 기다리는 것, Monitor는 열쇠와 대기 명단이 함께 붙어 있는 방이에요.
STEP:
1. **Spinlock**: Lock이 풀릴 때까지 반복문으로 계속 확인해요(**Busy Waiting**). 잠들고 깨는 비용이 없어서, Lock을 아주 잠깐만 잡는 경우나 Core가 여러 개일 때 유리해요. 오래 기다리면 CPU를 낭비해요.
2. **Condition Variable**: "Buffer가 비어 있지 않을 때까지" 같은 조건을 기다리며 잠들어요. 다른 Thread가 조건을 만들고 `signal()`하면 깨어나요. 항상 Mutex와 함께 써요.
3. 깨어나면 조건을 **다시 확인**해야 해요. 그 사이 다른 Thread가 먼저 가져갔을 수 있으니까요(그래서 `if`가 아니라 `while`로 기다려요).
4. **Monitor**: Mutual Exclusion과 Condition Variable을 언어 차원에서 묶은 도구예요. Java의 `synchronized`와 `wait()`/`notify()`가 대표적이에요. 직접 Lock을 다루지 않아도 돼서 실수가 줄어요.
WHY: Lock만으로는 "데이터가 들어올 때까지 기다리기" 같은 상황을 효율적으로 처리할 수 없어요. 계속 확인하면 CPU 낭비, 잠들면 깨워 줄 방법이 필요해요.
END: 짧게 기다리면 Spinlock, 조건을 기다리면 Condition Variable, 둘을 안전하게 묶으면 Monitor예요.

#### 고전 동기화 문제 3가지
ONE: 동기화를 설명할 때 자주 나오는 대표 문제로 **Producer-Consumer**, **Readers-Writers**, **Dining Philosophers**가 있어요.
LIKE: 빵집으로 생각해 보세요. 제빵사(Producer)가 진열대에 빵을 놓고 손님(Consumer)이 가져가요. 진열대가 꽉 차면 제빵사는 기다리고, 비면 손님이 기다려야 해요.
STEP:
1. **Producer-Consumer (생산자-소비자)**: 크기가 정해진 Buffer에 넣는 쪽과 꺼내는 쪽이 있어요. 꽉 차면 넣지 말고, 비면 꺼내지 말아야 하고, 동시에 Buffer를 고치면 안 돼요.
2. 해결: 빈칸 수를 세는 Semaphore `empty`(초깃값 N), 찬 칸 수를 세는 Semaphore `full`(초깃값 0), Buffer 보호용 Mutex를 함께 써요.
3. **Readers-Writers (읽기-쓰기)**: 여러 명이 동시에 읽는 건 괜찮지만, 누가 쓰는 동안에는 아무도 읽거나 쓰면 안 돼요. Read-Write Lock으로 풀어요. 읽는 사람만 계속 오면 쓰는 사람이 굶을 수 있어서(Starvation) 공평성도 고민해야 해요.
4. **Dining Philosophers (식사하는 철학자)**: 원탁에 5명이 앉고, 사이사이 젓가락이 1개씩 총 5개 있어요. 밥을 먹으려면 양쪽 젓가락 2개가 필요해요.
5. 모두가 동시에 왼쪽 젓가락을 집으면, 모두 오른쪽 젓가락을 영원히 기다려요. 이게 **Deadlock**의 대표 예예요. 젓가락에 번호를 매겨 작은 번호부터 집게 하면 해결돼요.
USE: 메시지 큐(Producer-Consumer), 데이터베이스와 Cache의 읽기·쓰기 Lock(Readers-Writers), 여러 Lock을 잡는 코드의 Deadlock 예방(Dining Philosophers)이 실무에서 그대로 나와요.
END: 넣고 빼기(Producer-Consumer), 동시에 읽기·혼자 쓰기(Readers-Writers), 서로 기다리다 멈춤(Dining Philosophers). 동기화 문제는 이 세 가지 틀로 대부분 설명돼요.

### Race Condition과 Critical Section이란?
E: 두 직원이 동시에 재고 장부를 보고 "계란 10개"를 읽은 뒤, 각자 하나씩 쓰고 "9개"라고 고쳐 씁니다. 실제로는 8개인데 장부에는 9개가 남습니다. 장부를 고치는 부분이 Critical Section(임계 영역)입니다.
A: Race Condition(경쟁 상태)은 여러 Thread가 공유 데이터에 동시에 접근해 실행 순서에 따라 결과가 달라지는 상황입니다. `count += 1`도 읽기·더하기·쓰기 세 단계라 중간에 끼어들 수 있습니다. Critical Section은 공유 데이터를 다루는 코드 구간으로, 한 번에 한 Thread만 들어가게(Mutual Exclusion, 상호 배제) 만들어야 합니다.

### Thread-Safe에 대해 설명해 주세요.
E: 여러 직원이 동시에 써도 장부가 절대 틀리지 않게 만든 재고 관리 방법입니다. 자물쇠를 채우거나, 각자 개인 장부를 쓰거나, 아예 고칠 수 없는 장부만 쓰는 방법이 있습니다.
A: Thread-Safe는 여러 Thread가 동시에 호출해도 항상 올바른 결과를 내는 코드의 성질입니다. Critical Section을 Mutex로 보호하거나, Atomic Operation을 쓰거나, Thread-Local Storage를 쓰거나, Immutable Object를 써서 만듭니다.

### Mutex와 Semaphore의 차이를 설명해 주세요.
E: Mutex는 칸이 하나뿐인 화장실 열쇠입니다. 열쇠를 가져간 사람만 돌려놓을 수 있습니다. Semaphore는 칸이 3개인 화장실 앞의 "빈 칸 수" 전광판입니다. 0이면 기다리고, 누구든 나오면 숫자가 1 올라갑니다.
A: Mutex는 한 번에 하나의 Thread만 Critical Section에 들어가게 하는 Lock이고, Lock을 건 Thread만 풀 수 있는 소유(Ownership) 개념이 있습니다. Semaphore는 정수 Counter로 wait(P)에서 감소, signal(V)에서 증가하며 동시에 N개까지 자원을 쓰게 하고, 다른 Thread가 signal할 수 있어 순서 제어에도 씁니다.

### Spinlock, Monitor, Condition Variable이란?
| 도구 | 비유 | 뜻 |
| Spinlock | 화장실 문 앞에서 계속 문고리를 돌려 보며 기다림 | Lock을 얻을 때까지 Busy Waiting. 짧은 구간·Multi-Core에서 유리 |
| Condition Variable | "빈자리 나면 불러 주세요" 대기 명단 | Mutex와 함께 쓰며, 조건이 될 때까지 잠들었다가 signal로 깨어남 |
| Monitor | 열쇠와 대기 명단이 붙어 있는 방 | Mutual Exclusion과 Condition Variable을 묶은 고수준 도구 (예: Java synchronized) |
A: Spinlock은 Lock이 풀릴 때까지 반복 확인하며 기다려 잠들고 깨는 비용이 없지만 CPU를 낭비합니다. Condition Variable은 특정 조건을 기다리며 잠들게 하는 도구이고, Monitor는 Mutual Exclusion과 Condition Variable을 언어 차원에서 묶어 실수를 줄입니다.

### 고전 Synchronization 문제 3가지는?
A: Producer-Consumer 문제는 크기가 정해진 Buffer에 넣는 쪽과 꺼내는 쪽이 넘치거나 비지 않게 하는 문제로, Semaphore empty·full과 Mutex로 풉니다. Readers-Writers 문제는 여러 명이 동시에 읽되 쓰기는 혼자 하게 하는 문제이고, Dining Philosophers(식사하는 철학자) 문제는 모두가 왼쪽 젓가락을 동시에 집으면 Deadlock이 생기는 예입니다.

## Deadlock (교착 상태)

#### Deadlock과 4가지 조건
ONE: 둘 이상의 Process가 **서로 상대가 가진 자원을 기다리며 영원히 멈춘** 상태예요. 4가지 조건이 **모두 동시에** 성립할 때만 생겨요.
LIKE: 신호등 없는 좁은 네거리에 차 4대가 동시에 들어왔어요. 각자 앞 차가 빠지기를 기다리는데, 앞 차도 그 앞 차를 기다려요. 아무도 움직일 수 없어요.
STEP:
1. 예: Thread A는 칼을 쥐고 도마를 기다리고, Thread B는 도마를 쥐고 칼을 기다려요. 둘 다 영원히 기다려요.
2. **Mutual Exclusion (상호 배제)**: 자원을 한 번에 한 명만 쓸 수 있어요.
3. **Hold and Wait (점유와 대기)**: 이미 가진 자원을 놓지 않은 채 다른 자원을 기다려요.
4. **No Preemption (비선점)**: 남이 가진 자원을 강제로 빼앗을 수 없어요.
5. **Circular Wait (순환 대기)**: 기다림이 원을 그려요. A → B → A.
6. 넷 중 **하나라도 깨면** Deadlock은 생기지 않아요.
| 조건 | 뜻 | 식당 비유 |
| Mutual Exclusion | 한 번에 하나만 사용 | 칼은 한 명만 쓸 수 있음 |
| Hold and Wait | 가진 것을 쥔 채 기다림 | 칼을 든 채 도마를 기다림 |
| No Preemption | 강제로 못 빼앗음 | 남의 칼을 빼앗을 수 없음 |
| Circular Wait | 기다림이 원을 그림 | A는 B의 도마, B는 A의 칼을 기다림 |
WHY: Deadlock이 생기면 프로그램이 에러 없이 그냥 멈춰 버려서 원인을 찾기 어려워요. 조건을 알아야 예방할 수 있어요.
USE: 데이터베이스에서 두 Transaction이 서로의 행(Row) Lock을 기다리는 경우가 흔한 실제 사례예요. DB는 이를 감지해 한쪽을 취소해요.
END: Deadlock = 상호 배제 + 점유와 대기 + 비선점 + 순환 대기. 하나만 깨도 막을 수 있어요.

#### Deadlock 대처법: Prevention · Avoidance · Detection · Recovery
ONE: Deadlock은 **조건을 미리 깨서 막거나(Prevention)**, **위험할 때 피하거나(Avoidance)**, **생긴 뒤 찾아서 푸는(Detection·Recovery)** 방법으로 다뤄요.
LIKE: 네거리 교통으로 비유하면, Prevention은 신호등을 설치해 처음부터 막는 것, Avoidance는 교통경찰이 차 한 대를 들여보낼 때마다 "꽉 막히지 않을까" 계산하는 것, Detection·Recovery는 막히면 차 한 대를 견인해서 푸는 거예요.
STEP:
1. **Prevention (예방)**: 4가지 조건 중 하나를 구조적으로 없애요. 가장 실용적인 방법은 **자원에 번호를 매기고 항상 작은 번호부터 요청**하게 하는 거예요. 그러면 원이 생길 수 없어 Circular Wait가 사라져요.
2. **Avoidance (회피)**: 자원을 주기 전에 "줘도 모두가 언젠가 끝날 수 있는 안전한 상태(Safe State)인가?"를 계산해서, 위험하면 기다리게 해요. 대표 방법이 **Banker's Algorithm(은행원 알고리즘)**이에요. 각 Process가 최대 얼마나 필요한지 미리 알아야 해서 실제로는 잘 안 써요.
3. **Detection (탐지)**: 누가 누구를 기다리는지 Graph로 그려서 원(Cycle)이 있는지 찾아요.
4. **Recovery (회복)**: 찾으면 Process 하나를 종료하거나, 자원을 강제로 빼앗아서 풀어요.
5. **무시하기 (Ostrich Algorithm)**: Deadlock이 드물다고 보고 OS는 신경 쓰지 않아요. 대부분의 범용 OS가 이 방식이고, 대신 개발자가 Lock 순서를 지켜야 해요.
KEY: 실무에서 가장 많이 쓰는 규칙: 여러 Lock을 잡아야 하면 **모든 코드에서 같은 순서로** 잡아요. 그리고 Lock을 잡을 때 Timeout을 둬요.
WHY: Deadlock은 완전히 없애려면 비싸고, 그냥 두면 위험해요. 상황에 맞는 수준을 골라야 해요.
END: 미리 막기(번호 순서), 피해 가기(Banker's), 찾아서 풀기(Detection·Recovery). 실무의 기본은 "Lock은 항상 같은 순서로"예요.

### Deadlock의 개념과 조건을 설명해 주세요.
E: 신호등 없는 좁은 네거리에 차 4대가 동시에 들어와, 각자 앞 차가 빠지기를 기다리며 아무도 못 움직이는 상황입니다.
A: Deadlock은 두 개 이상의 Process가 서로 상대가 가진 자원을 기다리며 영원히 진행하지 못하는 상태입니다. Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait의 4가지 조건이 모두 동시에 성립해야 발생합니다.
| 조건 | 뜻 | 식당 비유 |
| Mutual Exclusion (상호 배제) | 자원을 한 번에 하나만 씀 | 칼은 한 명만 쓸 수 있음 |
| Hold and Wait (점유와 대기) | 가진 것을 놓지 않고 다른 것을 기다림 | 칼을 든 채 도마를 기다림 |
| No Preemption (비선점) | 남의 것을 강제로 못 빼앗음 | 남의 칼을 내가 빼앗을 수 없음 |
| Circular Wait (순환 대기) | 기다림이 원을 그림 | A는 B의 도마를, B는 A의 칼을 기다림 |

### Deadlock Prevention·Avoidance·Detection·Recovery의 차이는?
E: Prevention(예방)은 신호등을 설치해 원천 차단, Avoidance(회피)는 교통 경찰이 매번 "이 차를 들여보내도 안전한가"를 계산, Detection·Recovery(탐지·회복)는 막히면 차 한 대를 견인해 풀어 주는 것입니다.
A: Prevention은 4가지 조건 중 하나를 구조적으로 깨는 것으로, 자원에 번호를 매겨 순서대로만 요청하게 하면 Circular Wait가 사라집니다. Avoidance는 자원을 주기 전에 Safe State가 유지되는지 검사하는 것(Banker's Algorithm)이고, Detection·Recovery는 생긴 뒤 찾아서 Process를 종료하거나 자원을 빼앗습니다. 실제 범용 OS는 대부분 드물다고 보고 무시하고(Ostrich Algorithm) 개발자에게 맡깁니다.

## Memory Management

#### 연속 할당과 Fragmentation (단편화)
ONE: Process에게 Memory를 **한 덩어리로 연속해서** 주면 단순하지만, 시간이 지나면 빈 공간이 조각조각 흩어지는 **Fragmentation** 문제가 생겨요.
LIKE: 주차장으로 생각해 보세요. 빈칸을 다 합치면 3칸인데 여기저기 1칸씩 떨어져 있어서 3칸짜리 버스를 못 대는 게 External Fragmentation이에요. 경차 칸에 오토바이를 세워 칸 안에 빈 공간이 남는 게 Internal Fragmentation이에요.
STEP:
1. **Contiguous Allocation (연속 할당)**: Process마다 Memory의 연속된 한 구간을 줘요.
2. Process들이 시작하고 끝나기를 반복하면, Memory 중간중간에 크기가 제각각인 빈 구멍이 생겨요.
3. 새 Process가 오면 어느 구멍에 넣을지 골라야 해요. **First-Fit**(처음 맞는 곳), **Best-Fit**(가장 딱 맞는 곳), **Worst-Fit**(가장 큰 곳).
4. **External Fragmentation (외부 단편화)**: 빈 공간을 다 합치면 충분한데, 조각나 있어서 연속된 공간을 못 줘요. 크기가 제각각인 할당에서 생겨요.
5. **Internal Fragmentation (내부 단편화)**: 정해진 단위로 나눠 주다 보니, 요청보다 크게 줘서 안쪽에 남는 낭비예요. 고정 크기 할당에서 생겨요.
6. **해결**: 흩어진 조각을 한쪽으로 몰아 붙이는 **Compaction(압축)**은 비싸요. 그래서 "연속일 필요가 없게" 만드는 **Paging**이 나왔어요(다음 개념).
WHY: Memory는 비싼 자원이에요. 조각 때문에 쓸 수 없는 공간이 생기면 그만큼 낭비예요.
END: 연속으로 주면 바깥에 조각(External)이 생기고, 고정 단위로 주면 안쪽에 남는 공간(Internal)이 생겨요.

#### Paging과 Segmentation
ONE: Memory를 **같은 크기 조각(Page)**으로 나눠 아무 빈칸에나 넣는 게 **Paging**, **의미 단위(Code·Data·Stack)**로 나누는 게 **Segmentation**이에요.
LIKE: Paging은 책을 모두 같은 크기의 낱장으로 잘라 책장의 아무 빈칸에나 꽂고, 몇 쪽이 어디 있는지 목차에 적어 두는 거예요. Segmentation은 책을 "1장·2장·부록"처럼 의미 단위로 나눠 꽂는 거예요.
STEP:
1. **Paging**: Process의 Memory(가상 공간)를 고정 크기 **Page**(보통 4KB)로, 실제 Memory를 같은 크기 **Frame**으로 나눠요.
2. Page는 아무 빈 Frame에나 들어갈 수 있어요. 연속일 필요가 없으니 **External Fragmentation이 없어요**.
3. 어느 Page가 어느 Frame에 있는지는 **Page Table**에 적어 둬요.
4. 단, 마지막 Page는 꽉 안 찰 수 있어서 Internal Fragmentation이 조금 생겨요(평균 반 Page 정도).
5. **Segmentation**: Code, Data, Heap, Stack처럼 의미 있는 단위(Segment)로 나눠요. "Code는 읽기만", "Stack은 실행 금지"처럼 보호 설정과 공유가 자연스러워요.
6. 단점: Segment 크기가 제각각이라 다시 External Fragmentation이 생겨요.
| 구분 | Paging | Segmentation |
| 나누는 단위 | 고정 크기 (예: 4KB) | 의미 단위, 크기 제각각 |
| External Fragmentation | 없음 | 생김 |
| Internal Fragmentation | 조금 (마지막 Page) | 없음 |
| 장점 | 관리 단순, 빈틈없이 사용 | 보호·공유가 자연스러움 |
USE: 현대 OS(Linux, Windows, macOS)는 Paging을 기본으로 써요. x86-64에서 Segmentation은 거의 쓰지 않아요.
END: Paging은 "같은 크기로 잘라 아무 데나", Segmentation은 "의미대로 나눠서". 지금은 Paging이 표준이에요.

#### Swapping
ONE: Memory가 부족하면 당장 안 쓰는 Process(또는 Page)를 **Disk로 잠시 내보냈다가** 필요할 때 다시 올리는 기법이에요.
LIKE: 주방이 꽉 차면, 한동안 안 쓸 재료를 지하 창고로 내려 두고 공간을 비워요. 그 재료가 다시 필요하면 창고에서 올려와요.
STEP:
1. RAM이 가득 찼는데 새 Process가 Memory를 원해요.
2. OS가 한동안 안 쓴 Process나 Page를 골라 Disk의 **Swap 영역**으로 옮겨요(**Swap Out**).
3. 비워진 공간을 새 Process에게 줘요.
4. 내보낸 것이 다시 필요해지면 Disk에서 읽어 RAM으로 올려요(**Swap In**).
PRO: RAM보다 더 많은 Process를 동시에 실행할 수 있어요.
CON: Disk는 RAM보다 수백 배(SSD)에서 수만 배(HDD)까지 느려요. Swap이 자주 일어나면 컴퓨터가 눈에 띄게 느려져요.
USE: 브라우저 탭을 너무 많이 열었을 때 컴퓨터가 버벅이는 이유 중 하나가 Swapping이에요. Linux의 swap 파티션, Windows의 pagefile이 이 공간이에요.
END: Swapping은 Memory가 모자랄 때 Disk를 임시 창고로 쓰는 것이고, 편리하지만 너무 자주 하면 매우 느려져요.

### Memory 관리 전략에는 무엇이 있나요?
E: 창고 공간을 식당들에게 나눠 주는 방법입니다. 통째로 연속된 구역을 주거나(Contiguous Allocation), 같은 크기 상자 단위로 흩어져 있어도 되게 주거나(Paging), 용도별 구역으로 주거나(Segmentation), 안 쓰는 물건은 바깥 창고로 잠시 빼 둡니다(Swapping).
A: Contiguous Allocation(연속 할당)은 Process에 한 덩어리 공간을 주며 빈 공간을 First-Fit·Best-Fit·Worst-Fit으로 고릅니다. Non-Contiguous Allocation(불연속 할당)에는 고정 크기로 나누는 Paging, 논리적 단위로 나누는 Segmentation, 둘을 섞은 방식이 있고, 더해서 Memory를 Disk로 내보내는 Swapping과 Virtual Memory가 있습니다.

### External Fragmentation과 Internal Fragmentation은?
E: External Fragmentation(외부 단편화)은 주차장에 빈칸이 합치면 3칸인데 여기저기 1칸씩 떨어져 있어 버스(3칸짜리)를 못 대는 것, Internal Fragmentation(내부 단편화)은 경차 칸에 오토바이를 세워 칸 안에 빈 공간이 남는 것입니다.
A: External Fragmentation은 빈 Memory를 모두 합치면 충분하지만 조각나 있어 연속된 공간을 내줄 수 없는 것이고, 가변 크기 할당(Segmentation)에서 생깁니다. Internal Fragmentation은 할당 단위가 요청보다 커서 Block 안에 남는 낭비이고, 고정 크기 할당(Paging의 마지막 Page)에서 생깁니다. External Fragmentation은 Compaction(압축)이나 Paging으로 해결합니다.

### Paging과 Segmentation의 차이는?
E: Paging은 책을 모두 같은 크기 페이지로 잘라 아무 빈 칸에나 꽂는 것, Segmentation은 책을 "1장·2장·부록"처럼 의미 단위로 나눠 꽂는 것입니다.
A: Paging은 Virtual Memory를 고정 크기 Page(보통 4KB)로, Physical Memory를 같은 크기 Frame으로 나눠 External Fragmentation이 없지만 Internal Fragmentation이 조금 생깁니다. Segmentation은 Code·Data·Stack처럼 논리적 단위로 나눠 보호·공유가 자연스럽지만 크기가 제각각이라 External Fragmentation이 생깁니다.

### Swapping에 대해 설명해 주세요.
E: 주방이 꽉 차면 한동안 안 쓸 식당의 재료를 통째로 지하 창고로 내려 두고, 다시 필요할 때 올립니다.
A: Swapping은 Memory가 부족할 때 Process(또는 Page)를 Disk의 Swap 영역으로 내보내고(Swap Out) 필요할 때 다시 올리는(Swap In) 기법입니다. 더 많은 Process를 동시에 돌릴 수 있지만, Disk는 매우 느려서 너무 자주 일어나면 성능이 크게 떨어집니다.

## Virtual Memory

#### Virtual Memory (가상 메모리)
ONE: 모든 Process에게 **"너만의 크고 깨끗한 Memory 공간"이 있는 것처럼** 보여 주고, 실제로는 OS가 RAM과 Disk에 나눠 연결해 주는 기법이에요.
LIKE: 매니저가 모든 식당에게 "당신 창고는 1번부터 1000번 칸까지예요"라고 똑같이 말해 줘요. 실제로는 매니저가 대장을 보면서 진짜 창고의 빈칸이나 지하 창고에 연결해 줘요. 식당들은 남의 창고를 볼 방법이 아예 없어요.
STEP:
1. Process가 쓰는 주소는 **Virtual Address(가상 주소)**예요. 모든 Process가 0번부터 시작하는 자기만의 주소 공간을 가져요.
2. 실제 RAM의 주소는 **Physical Address(물리 주소)**예요.
3. CPU 안의 **MMU(Memory Management Unit)**가 Page Table을 보고 가상 주소를 물리 주소로 바꿔요. 이 변환은 Memory에 접근할 때마다 하드웨어가 자동으로 해요.
4. Process A의 0x1000번지와 Process B의 0x1000번지는 서로 다른 실제 위치예요. 그래서 서로를 볼 수 없어요(**격리**).
5. 지금 필요한 Page만 RAM에 올리고 나머지는 Disk에 둘 수 있어요. 그래서 RAM보다 큰 프로그램도 실행돼요.
6. 반대로, 여러 Process가 같은 Shared Library를 쓸 때는 같은 실제 Page를 함께 연결해 Memory를 아껴요.
WHY: Process마다 공간을 분리하고(안전), RAM 크기의 한계를 넘고(편리), 공유도 쉽게(효율) 하려고요.
USE: 모든 현대 OS가 Virtual Memory를 써요. 프로그램에서 출력한 Pointer 주소는 모두 가상 주소예요.
END: Virtual Memory는 "모두에게 자기만의 Memory가 있는 것처럼" 보여 주는 착시이고, 그 덕에 안전·크기·공유 문제를 한 번에 풀어요.

#### Page Table과 TLB
ONE: **Page Table**은 "가상 Page 번호 → 실제 Frame 번호"를 적어 둔 대장이고, **TLB**는 그중 최근에 찾은 몇 줄만 적어 둔 아주 빠른 메모예요.
LIKE: Page Table은 "가상 칸 번호 → 진짜 칸 번호" 대장이에요. 대장이 너무 두꺼우면 "동 → 층 → 호수"처럼 나눠서, 아무도 안 쓰는 동의 대장은 아예 만들지 않아요(Multi-Level). TLB는 자주 찾는 몇 줄만 적어 책상에 붙여 둔 포스트잇이에요.
STEP:
1. 가상 주소는 **Page 번호 + Page 안의 위치(Offset)**로 나뉘어요.
2. Page Table에서 Page 번호를 찾아 Frame 번호로 바꾸고, Offset은 그대로 붙이면 실제 주소가 돼요.
3. **문제 ① 크기**: 64 Bit 주소 공간 전체에 대한 표를 한 장으로 만들면 너무 커요. 그래서 표를 여러 단계로 나누고, 실제로 쓰는 부분만 만들어요(**Multi-Level Page Table**). x86-64는 보통 4단계를 써요.
4. **문제 ② 속도**: 4단계 표라면 Memory 한 번 읽으려고 표를 4번 더 읽어야 해요. 너무 느려요.
5. **TLB (Translation Lookaside Buffer)**: 최근에 변환한 결과를 저장하는 CPU 안의 작은 Hardware Cache예요. TLB에 있으면(TLB Hit) 표를 안 읽고 바로 변환해요.
6. 프로그램은 Locality 덕분에 같은 Page를 반복해서 쓰기 때문에, 대부분의 변환이 TLB에서 해결돼요.
KEY: Process가 바뀌면 Page Table도 바뀌어서 TLB의 내용이 쓸모없어져요. Context Switching이 비싼 이유 중 하나예요.
END: Page Table은 주소 변환 대장, Multi-Level은 대장을 나눠 공간을 아끼는 방법, TLB는 변환 결과를 기억하는 빠른 메모예요.

#### Demand Paging과 Page Fault
ONE: Page를 미리 다 올리지 않고 **실제로 쓰는 순간에만 RAM에 올리는** 방식이 Demand Paging이고, 쓰려는 Page가 RAM에 없어서 생기는 사건이 **Page Fault**예요.
LIKE: 재료를 미리 전부 주방에 꺼내 두지 않고, 요리사가 찾았는데 없을 때만 지하 창고에서 가져와요. "어, 없네!"가 Page Fault예요.
STEP:
1. 프로그램을 실행해도 처음에는 Page를 거의 안 올려요.
2. CPU가 어떤 주소에 접근했는데 Page Table에 "RAM에 없음"으로 표시돼 있으면 **Page Fault**가 생기고 OS로 제어가 넘어가요.
3. OS가 그 접근이 올바른지 확인해요. 아예 허용되지 않은 주소면 프로그램을 종료해요(Segmentation Fault).
4. 올바르면 빈 Frame을 찾아요. 없으면 내보낼 Page(**Victim Page**)를 골라 비워요.
5. Disk에서 필요한 Page를 읽어 그 Frame에 올려요.
6. Page Table을 고치고, Page Fault가 났던 명령을 **다시 실행**해요. 이번에는 성공해요.
PRO: 쓰지 않는 부분은 아예 안 올리니 Memory를 아끼고, 프로그램이 빨리 시작돼요.
CON: Page Fault 하나하나가 Disk 읽기라 아주 느려요. 너무 자주 일어나면 성능이 크게 떨어져요.
END: Demand Paging은 "필요할 때만 가져오기"이고, 없는 걸 찾는 순간(Page Fault)에 OS가 Disk에서 가져와 다시 실행해 줘요.

#### Page Replacement Algorithm (페이지 교체)
ONE: RAM에 빈칸이 없을 때 **어떤 Page를 내보낼지 정하는 규칙**이에요. 목표는 앞으로 Page Fault가 가장 적게 나게 하는 거예요.
LIKE: 냉장고가 꽉 찼는데 새 재료를 넣어야 해요. 가장 먼저 넣은 것을 뺄지, 가장 오래 안 쓴 것을 뺄지, 가장 적게 쓴 것을 뺄지 정하는 규칙이에요.
STEP:
1. **FIFO (First-In First-Out)**: 가장 먼저 들어온 Page를 내보내요. 단순하지만, 자주 쓰는 Page도 오래됐다는 이유로 쫓겨날 수 있어요.
2. **OPT (Optimal)**: 앞으로 가장 오랫동안 안 쓸 Page를 내보내요. 이론상 최고지만 미래를 알아야 해서 실제로는 못 써요. 다른 방식이 얼마나 좋은지 비교하는 기준으로 써요.
3. **LRU (Least Recently Used)**: 가장 오랫동안 안 쓴 Page를 내보내요. "최근에 안 쓴 건 앞으로도 안 쓸 것"이라는 Locality를 이용해 실제 성능이 좋아요. 정확히 구현하려면 접근할 때마다 기록해야 해서 비싸요.
4. **LFU (Least Frequently Used)**: 가장 적게 쓴 Page를 내보내요. 예전에 많이 쓰고 지금은 안 쓰는 Page가 계속 남는 문제가 있어요.
5. **Clock (Second Chance)**: Page마다 "최근에 쓰였음" 표시(Reference Bit)를 두고 시계바늘처럼 돌면서, 표시가 있으면 지우고 한 번 더 기회를 주고, 없으면 내보내요. LRU를 싸게 흉내 낸 방식이에요.
6. **Belady's Anomaly**: FIFO에서는 Frame을 늘렸는데 오히려 Page Fault가 늘어나는 이상한 경우가 있어요. LRU와 OPT에서는 생기지 않아요.
USE: OS뿐 아니라 웹 Cache, 데이터베이스 Buffer, Redis의 메모리 정책에서도 LRU 계열 규칙을 써요.
END: 이상은 OPT, 실전은 LRU, 그 저렴한 버전이 Clock이에요. FIFO는 단순하지만 Belady's Anomaly가 생길 수 있어요.

#### Thrashing (스래싱)
ONE: Memory가 너무 부족해서 **Page Fault가 끊임없이 일어나고, CPU가 실제 일은 못 하고 Disk만 기다리는** 상태예요.
LIKE: 작은 주방에 식당을 너무 많이 넣었어요. 요리사가 요리는 못 하고 하루 종일 지하 창고를 오르내리며 재료만 바꿔 와요.
STEP:
1. Process를 많이 동시에 돌리면 각 Process가 받을 수 있는 Frame이 줄어요.
2. 각 Process가 자주 쓰는 Page들(**Working Set**)조차 RAM에 다 못 들어가요.
3. 그러면 Page를 올리자마자 다른 Page를 내보내야 하고, 내보낸 Page를 곧 다시 찾아요. Page Fault가 폭발해요.
4. CPU는 Disk를 기다리느라 놀고 있어요. 그런데 OS가 "CPU가 놀고 있네? Process를 더 넣자" 하면 상황이 더 나빠져요.
5. **해결**: 동시에 돌리는 Process 수를 줄이거나, Process마다 Working Set만큼 Frame을 보장하거나(**Working Set Model**), Page Fault 빈도를 보고 Frame을 조절해요(**Page Fault Frequency**). 근본적으로는 RAM을 늘려요.
WHY: 컴퓨터가 갑자기 극도로 느려지고 Disk 표시등만 계속 깜빡이면 Thrashing을 의심해요.
END: Thrashing은 "일보다 창고 왕복이 더 많은" 상태이고, 동시에 돌리는 양을 줄이거나 Memory를 늘려야 풀려요.

#### Copy-on-Write
ONE: fork()로 Process를 복제할 때 Memory를 바로 복사하지 않고, **누군가 고치려는 순간에 그 Page만 복사**하는 기법이에요.
LIKE: 분점을 낼 때 레시피 노트를 통째로 복사하지 않고 일단 같이 봐요. 누군가 레시피 한 줄이라도 고치려 할 때, 그 페이지만 복사해서 각자 가져요.
STEP:
1. fork() 직후 Parent와 Child는 같은 실제 Page를 함께 가리켜요. 이때 Page들을 **읽기 전용**으로 표시해요.
2. 둘 다 읽기만 하면 복사할 필요가 없어요.
3. 어느 한쪽이 Page에 쓰려고 하면, 읽기 전용이라 Page Fault가 나요.
4. OS가 그 Page만 복사해서 쓰려는 쪽에게 따로 주고, 이제 쓰기를 허락해요.
5. fork() 직후 바로 exec()로 다른 Program이 되는 경우가 아주 많아요. 이때는 복사할 일이 거의 없어서 엄청난 낭비를 피해요.
WHY: Memory 전체를 복사하는 건 느리고, 대부분은 곧 버려질 복사였어요.
USE: Linux의 fork(), Redis가 저장할 때 fork로 Snapshot을 뜨는 방식, 파일 시스템(Btrfs, ZFS)의 Snapshot에서 같은 아이디어를 써요.
END: Copy-on-Write는 "고칠 때만 복사"예요. 덕분에 fork가 매우 빨라요.

### Virtual Memory에 대해 설명해 주세요.
E: 모든 식당에게 "당신 창고는 1번부터 1000번 칸까지예요"라고 똑같이 말해 주고, 실제로는 매니저가 대장(Page Table)을 보며 진짜 창고의 빈 칸이나 지하 창고에 연결해 줍니다. 식당은 남의 창고를 볼 방법이 없습니다.
A: Virtual Memory는 Process마다 독립된 큰 Address Space를 주고, Page Table을 통해 실제 Physical Memory나 Disk에 대응시키는 기법입니다. 필요한 Page만 Memory에 올리므로 RAM보다 큰 프로그램도 실행되고, Process끼리 격리되며, Shared Library처럼 같은 Physical Page를 공유할 수도 있습니다.

### Page Table, Multi-Level Page Table, TLB란?
E: Page Table은 "가상 칸 번호 → 진짜 칸 번호" 대장, Multi-Level은 대장을 "동 → 층 → 호수"처럼 나눠 안 쓰는 동의 대장은 아예 만들지 않는 것, TLB는 자주 찾는 몇 줄만 적어 둔 포스트잇입니다.
A: Page Table은 Virtual Page Number를 Physical Frame Number로 바꾸는 표입니다. Address Space가 크면 표도 거대해지므로 여러 단계로 나누어 쓰는 부분만 만들고, x86-64는 보통 4단계를 씁니다. TLB(Translation Lookaside Buffer)는 최근 변환 결과를 저장하는 Hardware Cache라서, 매번 표를 여러 번 읽는 비용을 없앱니다.

### Demand Paging과 Page Fault 처리 과정은?
E: 재료를 미리 전부 올려 두지 않고, 요리사가 찾았는데 없을 때만 지하 창고에서 가져옵니다. "없네!"가 Page Fault입니다.
A: Demand Paging(요구 페이징)은 실제로 접근할 때만 Page를 Memory에 올리는 방식입니다. 없는 Page에 접근하면 Page Fault가 나서, OS가 접근이 유효한지 확인하고, 빈 Frame을 찾거나 Victim Page(희생 페이지)를 내보낸 뒤, Disk에서 읽어 오고, Page Table을 고친 다음 그 명령을 다시 실행합니다.

### Page Replacement Algorithm과 Belady's Anomaly는?
E: 냉장고가 꽉 찼을 때 무엇을 빼서 창고로 보낼지 정하는 규칙입니다.
| Algorithm | 규칙 | 특징 |
| FIFO | 가장 먼저 들어온 것 | 단순, Belady's Anomaly 가능 |
| OPT | 앞으로 가장 오랫동안 안 쓸 것 | 최적이지만 미래를 알아야 해서 비교 기준용 |
| LRU | 가장 오랫동안 안 쓴 것 (Least Recently Used) | 실제로 성능 좋음, 정확히 구현하면 비쌈 |
| LFU | 가장 적게 쓴 것 (Least Frequently Used) | 예전에 많이 쓴 것이 계속 남는 문제 |
| Clock | Reference Bit로 한 번 더 기회를 줌 | LRU를 싸게 근사 |
A: Page Replacement Algorithm은 빈 Frame이 없을 때 내보낼 Page를 고르며, Page Fault를 줄이는 것이 목표입니다. Belady's Anomaly는 FIFO에서 Frame 수를 늘렸는데 오히려 Page Fault가 늘어나는 현상이고, LRU와 OPT에서는 일어나지 않습니다.

### Thrashing이란?
E: 주방에 식당을 너무 많이 넣어서, 요리사가 요리는 못 하고 하루 종일 지하 창고를 오르내리는 상황입니다.
A: Thrashing은 Process들에게 필요한 Page를 담을 Frame이 부족해 Page Fault가 끊임없이 일어나고, CPU가 Disk를 기다리느라 실제 일을 거의 못 하는 상태입니다. Working Set Model이나 Page Fault Frequency를 보고 동시에 돌리는 Process 수를 줄여 해결합니다.

### Copy-on-Write는 fork를 어떻게 빠르게 만드나요?
E: 분점을 낼 때 레시피 노트를 바로 복사하지 않고 같이 보다가, 누군가 한 줄이라도 고칠 때 그 페이지만 복사합니다.
A: fork 직후 Parent와 Child는 같은 Physical Page를 Read-Only로 공유하고, 어느 쪽이 쓰려고 할 때 그 Page만 복사합니다. fork 후 곧바로 exec를 하는 경우가 많아서, 쓸모없는 전체 복사를 피해 fork를 매우 빠르게 만듭니다.

### (참고) Cache의 Locality
A: 원래 질문 리스트의 OS 항목이지만 Hardware 개념이라 02 Computer Architecture의 "Cache의 Locality"에 정리했습니다. Virtual Memory에도 같은 원리가 적용되어, Locality가 좋은 프로그램은 TLB Hit Rate(적중률)가 높고 Page Fault가 적습니다.

## Synchronous·Asynchronous와 I/O

#### Synchronous vs Asynchronous (동기와 비동기)
ONE: **Synchronous**는 요청한 일이 끝날 때까지 기다렸다가 다음 일을 하고, **Asynchronous**는 요청만 해 두고 다른 일을 하다가 끝나면 알림을 받아요.
LIKE: 카페에서 커피를 주문하고 카운터 앞에서 커피가 나올 때까지 서 있으면 Synchronous예요. 진동벨을 받아 자리에 가서 다른 일을 하다가 벨이 울리면 가지러 가면 Asynchronous예요.
STEP:
1. 프로그램은 파일 읽기, 네트워크 요청처럼 **오래 기다려야 하는 일**을 자주 해요. CPU 입장에서 이 기다림은 아주 길어요.
2. **Synchronous**: 결과가 올 때까지 그 자리에서 기다려요. 코드가 위에서 아래로 순서대로 실행돼서 이해하기 쉬워요.
3. **Asynchronous**: 요청을 보내 놓고 바로 다음 코드로 넘어가요. 결과가 오면 **Callback**, **Event**, **Promise/Future** 같은 방식으로 알려 줘요.
4. 그래서 Asynchronous를 쓰면 적은 수의 Thread로도 수많은 요청을 동시에 처리할 수 있어요.
5. 대신 코드 흐름이 뒤죽박죽 보일 수 있어서, 요즘은 `async`/`await` 문법으로 동기 코드처럼 읽히게 써요.
```python
import asyncio
async def main():
    a = asyncio.create_task(fetch("A"))   # 요청만 보내 두고
    b = asyncio.create_task(fetch("B"))   # 바로 다음 요청도 보냄
    print(await a, await b)               # 둘 다 끝나면 결과 사용
```
WHY: 네트워크를 기다리는 동안 CPU가 노는 건 큰 낭비예요. 기다리는 시간에 다른 일을 하면 같은 서버로 훨씬 많은 사용자를 받을 수 있어요.
USE: Node.js 서버, JavaScript의 `fetch`, Python의 `asyncio`, 앱에서 화면이 멈추지 않게 데이터를 불러오는 것 모두 Asynchronous예요.
END: Synchronous는 "서서 기다리기", Asynchronous는 "진동벨 받고 딴 일 하기"예요.

#### Blocking vs Non-Blocking
ONE: **Blocking**은 호출한 함수가 일을 끝낼 때까지 돌아오지 않는 것, **Non-Blocking**은 준비가 안 됐어도 **바로 돌아오는** 것이에요. 동기·비동기와는 보는 관점이 달라요.
LIKE: Blocking/Non-Blocking은 "주문한 뒤 내 몸이 바로 자유로워지느냐"의 문제이고, Synchronous/Asynchronous는 "완료를 내가 계속 확인하느냐, 알림을 받느냐"의 문제예요.
STEP:
1. **Blocking**: `read()`를 부르면 데이터가 올 때까지 그 함수 안에서 멈춰 있어요.
2. **Non-Blocking**: `read()`를 부르면 데이터가 없을 경우 "아직 없어요"라고 즉시 돌아와요. 나는 다른 일을 할 수 있어요.
3. **Synchronous**: 완료 여부를 **호출한 쪽이 직접** 확인해요.
4. **Asynchronous**: 완료되면 **호출당한 쪽이 알려** 줘요.
5. 두 기준을 조합하면 4가지 경우가 나와요.
| 조합 | 카페 비유 | 예 |
| Sync + Blocking | 카운터에 서서 기다림 | 일반적인 read() |
| Sync + Non-Blocking | 자리에 있다가 계속 "됐어요?" 물어봄 | Non-Blocking Socket + Polling |
| Async + Non-Blocking | 진동벨 받고 다른 일 | Node.js Callback, async/await |
| Async + Blocking | 진동벨을 받고도 카운터에서 기다림 | 비효율적이라 보통 피함 |
WHY: 면접에서 "동기 = Blocking"으로 섞어 쓰는 경우가 많아요. 두 축을 나눠서 설명할 수 있으면 개념을 정확히 이해한 거예요.
END: Blocking/Non-Blocking은 "함수가 바로 돌아오나", Sync/Async는 "끝난 걸 누가 알려 주나"예요.

### Synchronous와 Asynchronous의 차이는?
E: Synchronous(동기)는 카페 카운터 앞에서 커피가 나올 때까지 서 있는 것, Asynchronous(비동기)는 진동벨을 받고 자리에 가서 다른 일을 하다가 벨이 울리면 가지러 가는 것입니다.
A: Synchronous는 요청한 작업의 결과를 받을 때까지 기다렸다가 다음 일을 하는 방식이고, Asynchronous는 요청만 해 두고 다른 일을 하다가 완료되면 Callback·Event로 결과를 받는 방식입니다. Network·Disk처럼 기다리는 시간이 긴 작업을 Asynchronous로 하면 적은 Thread로 많은 요청을 처리할 수 있습니다.

### Blocking vs Non-Blocking은 Synchronous vs Asynchronous와 무엇이 다른가요?
E: Blocking/Non-Blocking은 "주문한 뒤 바로 내 몸이 자유로워지느냐", Synchronous/Asynchronous는 "완료를 내가 확인하느냐, 알림을 받느냐"의 문제입니다.
A: Blocking은 호출한 함수가 일을 끝낼 때까지 돌아오지 않는 것이고, Non-Blocking은 준비가 안 됐어도 즉시 돌아오는 것입니다. Synchronous·Asynchronous는 완료를 호출한 쪽이 직접 확인하느냐, 호출된 쪽이 알려 주느냐의 차이입니다.
| 조합 | 카페 비유 | 예 |
| Sync + Blocking | 카운터에 서서 기다림 | 일반적인 read() |
| Sync + Non-Blocking | 자리에 있다가 계속 "됐어요?" 물어봄 | Non-Blocking Socket + Polling |
| Async + Non-Blocking | 진동벨 받고 다른 일 | Node.js의 Callback, async/await |
| Async + Blocking | 진동벨을 받고도 카운터에서 기다림 | 비효율적이라 보통 피함 |

## File System

#### File과 inode, Hard Link와 Symbolic Link
ONE: Unix 계열 File System에서 파일의 실제 정보(크기, 권한, 데이터 위치)는 **inode**에 있고, 파일 **이름**은 그 inode를 가리키는 표지판일 뿐이에요.
LIKE: inode는 도서관의 책 카드(저자, 크기, 책이 꽂힌 위치)예요. Hard Link는 같은 책 카드에 이름표를 하나 더 붙이는 것이고, Symbolic Link는 "이 책은 3층 A서가에 있음"이라고 적힌 안내 쪽지예요.
STEP:
1. **inode**: 파일의 Metadata(크기, 주인, 권한, 수정 시간, 데이터가 Disk 어디에 있는지)를 담은 구조예요. 파일 이름은 들어 있지 않아요.
2. **Directory(폴더)**: "이름 → inode 번호" 목록이에요. 우리가 보는 파일 이름은 여기에 있어요.
3. **Hard Link**: 같은 inode를 가리키는 이름을 하나 더 만드는 거예요. 두 이름은 완전히 동등해요.
4. 원래 이름을 지워도, 다른 Hard Link가 남아 있으면 내용은 그대로예요. inode는 자기를 가리키는 이름이 하나도 없을 때 비로소 지워져요.
5. **Symbolic Link (Soft Link)**: "원본의 경로"를 내용으로 담은 별도의 작은 파일이에요. Windows의 바로 가기와 비슷해요.
6. 원본을 지우거나 옮기면 Symbolic Link는 갈 곳을 잃어 깨져요.
| 구분 | Hard Link | Symbolic Link |
| 가리키는 것 | 같은 inode | 원본의 경로(이름) |
| 원본 이름 삭제 시 | 내용 유지 | 깨짐 |
| 다른 File System·Directory 연결 | 불가 (Directory는 보통 불가) | 가능 |
USE: `ln file link`(Hard Link), `ln -s file link`(Symbolic Link). 설정 파일 연결, 버전 전환(`python` → `python3.12`)에 Symbolic Link를 많이 써요.
END: 파일의 진짜 정체는 inode이고, 이름은 표지판이에요. Hard Link는 표지판 추가, Symbolic Link는 "저쪽으로 가세요" 쪽지예요.

#### File Descriptor
ONE: Process가 연 파일·Socket·Pipe를 가리키는 **작은 정수 번호**예요. 프로그램은 이 번호로 읽고 써요.
LIKE: 도서관에서 책을 빌리면 받는 대출 번호표예요. 번호표만 보여 주면, 사서(Kernel)가 어떤 책을 어디까지 읽었는지 다 알고 있어요.
STEP:
1. 프로그램이 `open("a.txt")`를 하면, Kernel이 파일을 열고 정보를 자기 쪽 목록에 저장해요.
2. 그리고 그 목록의 번호(예: 3)를 돌려줘요. 이게 **File Descriptor(FD)**예요.
3. 이후에는 `read(3, ...)`, `write(3, ...)`처럼 번호로 요청해요. 지금 어디까지 읽었는지(Offset)는 Kernel이 기억해요.
4. 모든 Process는 시작할 때 3개를 이미 갖고 있어요. **0 = stdin(표준 입력)**, **1 = stdout(표준 출력)**, **2 = stderr(표준 오류)**.
5. Unix에서는 "모든 것이 파일"이라서, 파일뿐 아니라 Network Socket, Pipe, 장치도 FD로 똑같이 `read`/`write`해요.
6. 다 쓰면 `close()`로 반납해야 해요. 계속 열기만 하면 FD가 바닥나서 "Too many open files" 오류가 나요.
USE: Shell에서 `2> error.log`는 "2번(stderr)을 파일로 보내라"는 뜻이고, `2>&1`은 "2번을 1번과 같은 곳으로"라는 뜻이에요.
END: File Descriptor는 Kernel이 준 대출 번호표예요. 0·1·2는 입력·출력·오류이고, 다 쓰면 꼭 close해요.

### inode란? Hard Link와 Symbolic Link의 차이는?
E: inode는 도서관의 책 카드(저자, 크기, 책이 꽂힌 위치)입니다. Hard Link는 같은 카드에 이름표를 하나 더 붙이는 것이고, Symbolic Link는 "이 책은 3층 A서가에 있음"이라고 적힌 안내 쪽지입니다.
A: inode는 파일의 Metadata(크기, 소유자, 권한, 시간, Data Block 위치)를 담고, 파일 이름은 Directory가 이름 → inode 번호로 관리합니다. Hard Link는 같은 inode를 가리키는 또 다른 이름이라 원본 이름을 지워도 내용이 남고, Symbolic Link는 경로를 담은 별도 파일이라 원본이 사라지면 깨집니다.

### File Descriptor란?
E: 도서관에서 책을 빌리면 받는 대출 번호표입니다. 번호표만 보여 주면 어떤 책을 어디까지 읽었는지 사서가 알고 있습니다.
A: File Descriptor는 Process가 연 File·Socket·Pipe를 가리키는 작은 정수로, Kernel이 관리하는 열린 File 목록의 Index입니다. 0은 Standard Input(stdin), 1은 Standard Output(stdout), 2는 Standard Error(stderr)이고, Unix에서는 "모든 것이 파일"이라 같은 read/write로 다룹니다.

- Heap
- Code
- Global 변수
- Stack
= D

? 다음 중 Deadlock의 4가지 필요조건이 아닌 것은?
- 자원을 강제로 빼앗을 수 있음
- Mutual Exclusion
- Hold and Wait
- Circular Wait
= A
! 필요조건은 "No Preemption", 즉 강제로 빼앗을 수 없는 것입니다. 빼앗을 수 있다면 Deadlock을 풀 수 있습니다.

- 10
- 0
= B
! P2 → P3 → P1 순서이므로 대기 시간은 0, 3, 6이고 평균 3입니다. 17은 FCFS의 답입니다.

? Paging이 없애는 Fragmentation은?
- Internal Fragmentation
- 둘 다
- External Fragmentation
- 없음
= C
! 같은 크기 Frame을 아무 데나 배치하므로 External Fragmentation은 없고, 마지막 Page의 Internal Fragmentation은 남습니다.

? 프린터 3대를 여러 Thread가 나눠 쓸 때, 동시에 최대 3개까지만 쓰게 하려면 가장 알맞은 도구는?

- 초깃값이 3인 Semaphore

? Child Process가 종료했는데 Parent가 wait()을 하지 않아 Process Table에 남아 있는 상태는?
- Orphan Process
