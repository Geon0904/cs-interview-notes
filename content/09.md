@intro Database는 데이터를 안전하게 저장하고 빠르게 꺼내는 시스템입니다. 이 주제는 **은행**으로 생각하면 쉽습니다. 장부(Table)에 기록하고, 색인(Index)으로 빨리 찾고, 송금은 "출금과 입금이 둘 다 되거나 둘 다 안 되거나"(Transaction)여야 하며, 창구가 여러 개여도 잔액이 꼬이지 않아야(Concurrency Control) 합니다.
@one Relational Database는 데이터를 Key로 연결된 Table에 저장하고 SQL로 다루며, Normalization으로 중복을 줄이고 Index로 조회를 빠르게 하며 Transaction의 ACID로 동시에 많은 요청이 와도 데이터의 정확성을 지킵니다.

## Database 기본

#### Database와 DBMS: 왜 파일이 아니라 DB를 쓸까
ONE: **Database**는 정리된 데이터의 모음이고, **DBMS**는 그 데이터를 **여러 사람이 동시에, 안전하게, 빠르게** 쓰도록 관리하는 소프트웨어예요.
LIKE: 은행으로 생각해 보세요. 돈을 장롱에 넣어 두면(파일) 누가 얼마를 꺼냈는지 엉키고, 불이 나면 다 잃어요. 은행(DBMS)은 장부를 정확히 쓰고, 창구가 여러 개여도 잔액이 꼬이지 않게 하고, 정전이 나도 기록을 지켜요.
STEP:
1. **파일로만 저장하면 생기는 문제 ①**: 100명이 같은 파일을 동시에 고치면 누구 것이 남을지 알 수 없어요.
2. **문제 ②**: 저장 도중 전원이 나가면 파일이 반만 써진 채로 깨질 수 있어요.
3. **문제 ③**: 같은 정보를 여러 파일에 복사해 두면, 한 곳만 고쳐져 서로 달라져요.
4. **DBMS가 해 주는 일**: 동시 접근 정리(Concurrency Control), 묶음 작업의 전부/전무 보장(Transaction), 장애 후 복구(Recovery), 규칙 위반 차단(Constraint로 Integrity 보장), 빠른 검색(Index), 권한 관리.
5. 그리고 **SQL**이라는 공통 언어로 "무엇을 원하는지"만 말하면, "어떻게 찾을지"는 DBMS가 알아서 정해요.
WHY: 쇼핑몰 주문, 은행 송금, 회원 정보처럼 틀리면 안 되고 동시에 많은 요청이 오는 데이터는 DBMS 없이 안전하게 다룰 수 없어요.
USE: MySQL, PostgreSQL, Oracle, SQL Server(관계형), MongoDB, Redis, Cassandra(NoSQL).
KEY: 좋은 데이터 시스템이 지켜야 할 세 가지 목표는 **Reliability**(장애가 나도 올바르게 동작), **Scalability**(부하가 늘어도 버틸 방법이 있음), **Maintainability**(여러 사람이 오래 운영하고 바꾸기 쉬움)예요.
END: DBMS는 데이터를 위한 은행이에요. 동시 접근, 장애, 중복 문제를 대신 해결해 줘요.

#### Relational Model과 Key
ONE: **Relational Model**은 데이터를 **표(Table)**로 저장하고, 표끼리는 **Key**로 연결하는 방식이에요.
LIKE: 학교의 명부들을 떠올려 보세요. "학생 명부"와 "동아리 명부"가 따로 있고, 동아리 명부에는 학생 이름 대신 학번만 적어요. 학번으로 학생 명부를 찾아가면 나머지 정보가 나와요.
STEP:
1. **Table (Relation)**: 하나의 주제에 대한 표예요. 예: students.
2. **Row (Tuple)**: 표의 한 줄, 즉 하나의 기록이에요. 학생 한 명.
3. **Column (Attribute)**: 표의 한 칸 종류예요. 이름, 학번, 학과.
4. **Schema**: Table 이름, Column 이름과 Type, 규칙(Constraint)을 정한 설계도예요.
5. **Key**: Row를 구분하거나 다른 Table과 연결하는 Column이에요.
| Key | 뜻 |
| Super Key | Row를 유일하게 구분하는 Column 조합 (쓸데없는 Column이 섞여도 됨) |
| Candidate Key | 유일하면서 더 줄일 수 없는 최소 조합 |
| Primary Key (PK) | Candidate Key 중 대표로 고른 것. NULL과 중복 불가 |
| Alternate Key | PK로 뽑히지 않은 나머지 Candidate Key |
| Foreign Key (FK) | 다른 Table의 PK를 가리키는 Column. 없는 Row를 가리키지 못하게 막음 |
6. **Referential Integrity (참조 무결성)**: Foreign Key는 실제로 존재하는 Row만 가리킬 수 있어요. 없는 학번을 동아리 명부에 적으려 하면 DB가 거부해요.
WHY: 정보를 주제별 Table로 나누고 Key로 이으면, 같은 정보를 여러 번 적지 않아도 되고 고칠 때 한 곳만 고치면 돼요.
END: 관계형 DB는 "표 + Key로 연결"이에요. PK는 각 줄의 신분증, FK는 다른 표를 가리키는 화살표예요.

### DBMS는 파일에 그냥 저장하는 것과 무엇이 다른가요?
E: Excel 파일 하나를 100명이 동시에 고치면 누구 것이 남을지 알 수 없고, 저장 도중 전원이 나가면 파일이 깨집니다. DBMS는 이런 사고를 막는 은행 직원입니다.
A: DBMS는 여러 사용자의 동시 접근 제어(Concurrency Control), Transaction과 장애 복구(Recovery), Constraint(제약 조건)로 Integrity(무결성) 보장, SQL 같은 Query Language, Index를 통한 빠른 검색, 권한 관리를 제공합니다. File System은 이런 기능을 Application이 직접 구현해야 해서 데이터 중복과 불일치가 생기기 쉽습니다.

### Relational Model의 Table·Row·Column·Schema란?
A: Relational Model은 데이터를 Table(Relation)로 표현하고, Row(Tuple)는 하나의 Record, Column(Attribute)은 하나의 항목입니다. Schema는 Table 이름, Column 이름과 Data Type, Constraint를 정의한 설계도이고, Table끼리는 Key로 관계를 맺습니다.

### Key의 종류는?
E: 학생을 구분하는 방법입니다. 학번이나 주민번호처럼 한 명을 정확히 가리키는 것이 Candidate Key이고, 그중 대표로 고른 학번이 Primary Key, 반 명단에 적힌 "담임 교사 번호"처럼 다른 Table을 가리키는 것이 Foreign Key입니다.
| Key | 뜻 |
| Super Key | Row를 유일하게 구분하는 Column의 조합 (필요 없는 Column이 들어가도 됨) |
| Candidate Key | 유일성을 유지하며 더는 줄일 수 없는 최소 Super Key |
| Primary Key (PK) | Candidate Key 중 대표로 고른 것, NULL 불가 + 중복 불가 |
| Alternate Key | Primary Key로 뽑히지 않은 나머지 Candidate Key |
| Foreign Key (FK) | 다른 Table의 Primary Key를 참조하는 Column, Referential Integrity(참조 무결성) 보장 |
A: Super Key는 유일성만, Candidate Key는 유일성과 최소성을 모두 만족하며, Primary Key는 Candidate Key 중 하나로 NULL이 될 수 없습니다. Foreign Key는 다른 Table의 Primary Key를 가리켜 존재하지 않는 Row를 참조하지 못하게 막습니다(Referential Integrity).

## SQL

#### SQL 기본: SELECT와 실행 순서
ONE: **SQL**은 DB에게 **"무엇을 원하는지"**만 말하는 언어예요. "어떻게 찾을지"는 DB가 알아서 정해요.
LIKE: 식당에서 "매운 김치찌개 하나요"라고만 주문하면 되고, 재료를 어디서 꺼내고 어떤 순서로 끓일지는 주방이 정하는 것과 같아요.
STEP:
1. **CRUD**: 만들기(INSERT), 읽기(SELECT), 고치기(UPDATE), 지우기(DELETE).
2. **SELECT 기본**: `SELECT 컬럼 FROM 테이블 WHERE 조건 ORDER BY 정렬 LIMIT 개수`.
3. **WHERE**: 조건에 맞는 Row만 남겨요.
4. **GROUP BY**: 같은 값끼리 묶어 COUNT, SUM, AVG 같은 집계를 만들어요.
5. **HAVING**: 묶은 **뒤의 그룹**을 걸러요. WHERE는 묶기 **전의 Row**를 걸러서 집계 함수를 쓸 수 없어요.
6. **논리적 실행 순서**: 쓰는 순서와 달라요. FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. 그래서 SELECT에서 붙인 별명(alias)을 WHERE에서 쓸 수 없어요.
```sql
SELECT dept, AVG(salary) AS avg_sal
FROM employees
WHERE hire_year >= 2020        -- 1) Row를 먼저 거름
GROUP BY dept                  -- 2) 부서별로 묶음
HAVING AVG(salary) > 5000      -- 3) 그룹을 거름
ORDER BY avg_sal DESC;         -- 4) 정렬
```
KEY: SQL은 **선언형(Declarative)** 언어예요. "어떻게"를 DB가 정하니까, DB 엔진이 좋아지면 Query를 고치지 않아도 빨라질 수 있어요.
END: SQL은 "무엇을"만 말하는 언어이고, WHERE는 Row를, HAVING은 그룹을 걸러요.

#### JOIN: 여러 Table 합치기
ONE: **JOIN**은 Key로 연결된 여러 Table을 **하나의 결과로 합치는** 방법이에요. 짝이 없는 Row를 남길지 버릴지에 따라 종류가 나뉘어요.
LIKE: "학생 명단"과 "동아리 가입 명단"을 합친다고 해 봐요. INNER는 두 명단에 모두 있는 학생만, LEFT는 학생 전원을 남기고 동아리가 없으면 빈칸으로 둬요.
STEP:
1. **INNER JOIN**: 양쪽에 짝이 있는 Row만 남겨요.
2. **LEFT (OUTER) JOIN**: 왼쪽 Table의 Row는 모두 남기고, 오른쪽에 짝이 없으면 NULL로 채워요.
3. **RIGHT (OUTER) JOIN**: 반대로 오른쪽을 모두 남겨요.
4. **FULL OUTER JOIN**: 양쪽 모두 남기고, 짝 없는 쪽은 NULL.
5. **CROSS JOIN**: 모든 조합을 만들어요. Row 수 = m × n.
6. **SELF JOIN**: 같은 Table을 두 번 써요. 예: 직원 Table에서 "직원과 그 직원의 상사"를 함께 보기.
```sql
-- 주문이 한 번도 없는 고객 찾기
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```
KEY: "주문 없는 고객", "가입만 하고 활동 안 한 회원"처럼 **없는 것 찾기**는 LEFT JOIN 후 오른쪽이 NULL인 Row를 고르는 게 대표 패턴이에요.
END: 짝 있는 것만은 INNER, 한쪽을 다 남기려면 LEFT/RIGHT, 다 남기려면 FULL이에요.

#### Subquery와 View
ONE: **Subquery**는 Query 안에 들어간 Query이고, **View**는 Query에 이름을 붙여 저장해 둔 **가상 Table**이에요.
LIKE: Subquery는 "평균 키보다 큰 학생"을 찾을 때, 먼저 "평균 키"를 따로 계산해 끼워 넣는 거예요. View는 자주 쓰는 복잡한 검색 조건에 "우수 학생 명단"이라는 이름을 붙여 두고 표처럼 꺼내 쓰는 거예요.
STEP:
1. **Subquery**: `WHERE salary > (SELECT AVG(salary) FROM emp)`처럼 다른 Query의 결과를 값이나 임시 Table로 써요.
2. Subquery는 WHERE, FROM, SELECT 자리에 모두 들어갈 수 있어요.
3. **View**: `CREATE VIEW top_students AS SELECT ...`로 만들고, 이후엔 `SELECT * FROM top_students`처럼 Table처럼 써요.
4. 일반 View는 데이터를 따로 저장하지 않고, 조회할 때마다 원래 Query를 실행해요.
5. **보안**: 민감한 Column(주민번호 등)을 뺀 View만 보여 주면, 필요한 정보만 안전하게 공유할 수 있어요.
6. **Materialized View**: 결과를 실제로 저장해 두는 View예요. 조회는 빠르지만 원본이 바뀌면 다시 계산(Refresh)해야 해요.
END: Subquery는 Query 속 Query, View는 이름 붙인 저장된 Query예요.

#### SQL 명령의 분류: DDL · DML · DCL · TCL
ONE: SQL 명령은 하는 일에 따라 **구조 정의(DDL)**, **데이터 조작(DML)**, **권한(DCL)**, **Transaction(TCL)**으로 나뉘어요.
LIKE: 도서관으로 비유하면, 책장 만들기·치우기(DDL), 책 넣고 빼고 찾기(DML), 열쇠 주고 뺏기(DCL), "이 정리 작업 확정/취소"(TCL)예요.
STEP:
1. **DDL (Data Definition)**: CREATE, ALTER, DROP, TRUNCATE. Table 구조를 다뤄요.
2. **DML (Data Manipulation)**: SELECT, INSERT, UPDATE, DELETE. 데이터를 다뤄요(SELECT만 따로 DQL이라고 부르기도 해요).
3. **DCL (Data Control)**: GRANT, REVOKE. 권한을 주고 빼앗아요.
4. **TCL (Transaction Control)**: COMMIT, ROLLBACK, SAVEPOINT. Transaction을 확정하거나 취소해요.
5. **DELETE vs TRUNCATE vs DROP**: DELETE는 Row를 하나씩 지우고 Rollback할 수 있어요. TRUNCATE는 Table을 통째로 비워 빠르지만 DBMS에 따라 Rollback이 안 돼요. DROP은 Table 자체를 없애요.
END: 구조는 DDL, 데이터는 DML, 권한은 DCL, 확정·취소는 TCL이에요.

### JOIN의 종류는?
E: "학생 명단"과 "동아리 가입 명단"을 합치는 방법입니다. INNER는 두 명단에 모두 있는 학생만, LEFT는 학생 전원을 두고 동아리가 없으면 빈칸으로 둡니다.
| JOIN | 결과 |
| INNER JOIN | 양쪽에 일치하는 Row만 |
| LEFT (OUTER) JOIN | 왼쪽 Table 전부 + 오른쪽 일치 Row (없으면 NULL) |
| RIGHT (OUTER) JOIN | 오른쪽 Table 전부 + 왼쪽 일치 Row |
| FULL OUTER JOIN | 양쪽 전부, 일치하지 않는 쪽은 NULL |
| CROSS JOIN | 모든 조합 (Row 수 = m × n) |
| SELF JOIN | 같은 Table끼리 (예: 직원과 그 직원의 상사) |
A: INNER JOIN은 Join 조건에 맞는 Row만, LEFT/RIGHT OUTER JOIN은 한쪽 Table의 모든 Row와 맞는 Row를 보여 주고 없으면 NULL로 채웁니다. FULL OUTER는 양쪽 모두, CROSS는 모든 조합, SELF는 같은 Table을 두 번 쓰는 Join입니다. "주문이 한 번도 없는 고객 찾기"는 LEFT JOIN 후 오른쪽이 NULL인 Row를 고르는 것이 대표 예입니다.

### WHERE와 HAVING의 차이, GROUP BY의 동작은?
E: WHERE는 반을 나누기 전에 학생을 거르는 것이고, HAVING은 반별로 평균을 낸 뒤 "평균 80점 이상인 반"만 고르는 것입니다.
A: GROUP BY는 같은 값을 가진 Row를 묶어 COUNT·SUM·AVG 같은 Aggregate(집계)를 만듭니다. WHERE는 Group을 만들기 전에 개별 Row를 걸러 Aggregate Function을 쓸 수 없고, HAVING은 Group을 만든 뒤 집계 결과로 Group을 걸러냅니다. 논리적 실행 순서는 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT입니다.
```sql
SELECT dept, AVG(salary) AS avg_sal
FROM employees
WHERE hire_year >= 2020        -- Row를 먼저 걸러냄
GROUP BY dept
HAVING AVG(salary) > 5000      -- Group을 걸러냄
ORDER BY avg_sal DESC;
```

### Subquery와 View란?
A: Subquery는 다른 Query 안에 들어간 Query로, `WHERE salary > (SELECT AVG(salary) FROM emp)`처럼 값이나 임시 Table을 만듭니다. View는 Query에 이름을 붙여 저장한 가상 Table로, 복잡한 Query를 단순하게 쓰고 민감한 Column을 숨겨 보안에 도움을 줍니다. 일반 View는 데이터를 저장하지 않고 조회할 때마다 원래 Query를 실행합니다.

### DDL, DML, DCL, TCL의 차이는?
| 분류 | 하는 일 | 명령어 |
| DDL (Data Definition) | Table 구조를 만들고 바꿈 | CREATE, ALTER, DROP, TRUNCATE |
| DML (Data Manipulation) | 데이터를 조회·추가·수정·삭제 | SELECT, INSERT, UPDATE, DELETE |
| DCL (Data Control) | 권한을 주고 빼앗음 | GRANT, REVOKE |
| TCL (Transaction Control) | Transaction을 확정·취소 | COMMIT, ROLLBACK, SAVEPOINT |
A: DDL은 Schema를, DML은 데이터를, DCL은 권한을, TCL은 Transaction을 다룹니다. DELETE는 Row를 하나씩 지워 Rollback할 수 있고, TRUNCATE는 Table을 통째로 비워 빠르지만 DBMS에 따라 Rollback이 안 되며, DROP은 Table 자체를 없앱니다. SELECT를 따로 DQL(Data Query Language)로 분류하기도 합니다.

## Normalization과 Anomaly

#### Anomaly (이상 현상)
ONE: 한 Table에 **여러 종류의 정보를 섞어** 저장하면, 넣기·고치기·지우기 때 이상한 문제가 생겨요. 이게 Anomaly예요.
LIKE: 한 장부에 "학생, 수강 과목, 교수 연구실 번호"를 전부 적어 두면 문제가 생겨요. 수강생 없는 새 교수는 적을 수 없고, 연구실이 옮겨지면 수백 줄을 다 고쳐야 하고, 마지막 수강생이 취소하면 교수 정보까지 사라져요.
STEP:
1. **Insertion Anomaly (삽입 이상)**: 다른 데이터가 없으면 넣을 수 없어요. 수강생이 없으면 새 교수 정보를 저장할 자리가 없어요.
2. **Update Anomaly (갱신 이상)**: 같은 정보가 여러 줄에 중복돼서, 일부만 고치면 서로 달라져요. 연구실 번호를 몇 줄만 고치면 어느 게 맞는지 모르게 돼요.
3. **Deletion Anomaly (삭제 이상)**: 지우려는 데이터와 함께 필요한 정보까지 사라져요. 마지막 수강 기록을 지우면 교수 정보도 없어져요.
4. 원인은 모두 **"한 Table에 여러 주제의 정보가 중복"**돼 있기 때문이에요.
5. **해결**: 주제별로 Table을 나눠요(학생 Table, 교수 Table, 수강 Table). 이게 Normalization이에요.
END: 여러 주제를 한 Table에 섞으면 넣기·고치기·지우기가 꼬여요. 주제별로 나누면 해결돼요.

#### Functional Dependency와 Normal Form
ONE: **Functional Dependency(X → Y)**는 "X를 알면 Y가 하나로 정해진다"는 관계이고, **Normalization**은 "각 정보는 그것을 정하는 주인 Table에만 둔다"는 원칙으로 Table을 나누는 과정이에요.
LIKE: 학번을 알면 이름이 정해지니 "학번 → 이름"이에요. 그러면 이름은 학번이 주인인 학생 Table에만 두면 돼요. 수강 Table에 이름을 또 적을 필요가 없어요.
STEP:
1. **Functional Dependency**: X 값이 같으면 Y 값도 항상 같아요. 학번 → 이름, 학과 → 학과장.
2. **1NF**: 모든 칸에 더 쪼갤 수 없는 값 **하나**만(Atomic Value). 위반 예: 전화번호 칸에 "010-1, 010-2" 두 개.
3. **2NF**: 1NF + Key가 여러 Column일 때, Key의 **일부에만** 종속된 Column이 없어야 해요(Partial Dependency 제거). 위반 예: Key가 (학번, 과목)인데 "학생 이름"은 학번에만 종속.
4. **3NF**: 2NF + Key가 아닌 Column이 **다른 Key가 아닌 Column을 결정**하지 않아야 해요(Transitive Dependency 제거). 위반 예: 학번 → 학과 → 학과장. 학과장은 학과 Table로 옮겨요.
5. **BCNF**: 모든 결정자(Determinant, 화살표 왼쪽)가 Candidate Key여야 해요. 3NF보다 조금 더 엄격해요.
6. 단계가 오를수록 중복과 Anomaly는 줄지만, Table이 늘어 JOIN이 많아져요.
| Normal Form | 조건 | 위반 예 |
| 1NF | 칸마다 값 하나 | 전화번호 칸에 번호 두 개 |
| 2NF | 부분 종속 제거 | (학번, 과목) Key에서 이름은 학번에만 종속 |
| 3NF | 이행 종속 제거 | 학번 → 학과 → 학과장 |
| BCNF | 모든 결정자가 Candidate Key | 강의실 → 과목인데 강의실이 Key가 아님 |
END: "누가 이 정보의 주인인가?"를 따져 주인 Table에만 두는 게 정규화예요. 1NF → 2NF → 3NF → BCNF로 갈수록 중복이 줄어요.

#### Denormalization (반정규화)
ONE: 읽기 성능을 위해 **일부러 중복을 허용**하는 것이에요. 대신 쓰기가 복잡해지고 불일치 위험이 커져요.
LIKE: 정리 원칙대로라면 물건은 한곳에만 둬야 하지만, 자주 쓰는 가위를 거실과 부엌에 하나씩 더 두면 찾으러 다니는 시간이 줄어요. 대신 가위를 바꿀 때 여러 개를 다 바꿔야 해요.
STEP:
1. 정규화를 많이 하면 Table이 잘게 나뉘어, 화면 하나를 그리려고 JOIN을 여러 번 해야 해요.
2. 데이터가 커지면 JOIN이 느려져요.
3. **Denormalization**: 자주 함께 읽는 정보를 한 Table에 같이 두거나, 매번 계산하기 비싼 값(게시글의 댓글 수 등)을 미리 저장해 둬요.
4. 대신 원본이 바뀌면 복사본도 함께 고쳐야 해요. 하나라도 놓치면 값이 서로 달라져요.
WHY: 쓰기보다 읽기가 훨씬 많은 서비스(대부분의 웹 서비스)에서는 읽기를 빠르게 하는 게 더 중요할 때가 많아요.
END: 반정규화는 "읽기 속도를 위해 중복을 일부러 허용"하는 선택이고, 쓰기 복잡도라는 대가를 치러요.

### Insertion·Update·Deletion Anomaly(이상 현상)란?
E: 한 장부에 "학생, 수강 과목, 교수 연구실 번호"를 전부 적어 두면 문제가 생깁니다. 수강생이 없는 새 교수는 적을 수 없고(Insertion), 연구실이 옮겨지면 수강생 수백 줄을 다 고쳐야 하고(Update), 마지막 수강생이 취소하면 교수 정보까지 사라집니다(Deletion).
A: Anomaly는 한 Table에 여러 종류의 정보가 중복되어 생기는 문제입니다. Insertion Anomaly는 다른 데이터가 없으면 넣을 수 없는 것, Update Anomaly는 중복된 값을 일부만 고쳐 불일치가 생기는 것, Deletion Anomaly는 지우려는 데이터와 함께 필요한 정보까지 사라지는 것이며, Normalization으로 Table을 나눠 해결합니다.

### 1NF·2NF·3NF와 BCNF는? Functional Dependency란?
E: Functional Dependency(함수 종속) X → Y는 "X를 알면 Y가 하나로 정해진다"입니다. 학번을 알면 이름이 정해지므로 학번 → 이름입니다. Normalization은 "각 정보는 그것을 정하는 주인 Table에만 둔다"는 정리 원칙입니다.
| Normal Form | 조건 | 예시로 본 위반 |
| 1NF | 모든 칸에 더 쪼갤 수 없는 값 하나(Atomic Value) | 전화번호 칸에 "010-1, 010-2" 두 개 |
| 2NF | 1NF + Composite Key의 일부에만 종속된 Column이 없음(Partial Dependency 제거) | (학번, 과목) Key에서 "학생 이름"은 학번에만 종속 |
| 3NF | 2NF + Key가 아닌 Column이 다른 Key가 아닌 Column을 결정하지 않음(Transitive Dependency 제거) | 학번 → 학과 → 학과장 |
| BCNF | 모든 Determinant(결정자)가 Candidate Key | "강의실 → 과목"인데 강의실이 Candidate Key가 아님 |
A: Functional Dependency X → Y는 X 값이 같으면 Y 값도 반드시 같다는 관계입니다. 1NF는 Atomic Value만, 2NF는 Partial Functional Dependency 제거, 3NF는 Transitive Functional Dependency 제거, BCNF는 모든 Determinant가 Candidate Key인 상태입니다. 단계가 올라갈수록 중복과 Anomaly가 줄어들지만 Table과 JOIN이 늘어납니다.

### Denormalization(반정규화)은 언제 하나요?
A: Denormalization은 읽기 성능을 위해 일부러 중복을 허용하는 것으로, JOIN이 너무 많아 조회가 느리거나 집계 값(댓글 수 등)을 매번 계산하기 부담스러울 때 합니다. 대신 데이터를 고칠 때 여러 곳을 함께 고쳐야 해서 쓰기가 복잡해지고 불일치 위험이 커집니다.

## Index

#### Index의 원리
ONE: **Index**는 특정 Column 값과 그 Row의 위치를 **정렬해서 따로 저장**해 둔 자료구조예요. 전체를 훑는 O(n) 대신 O(log n)에 찾게 해 줘요.
LIKE: 두꺼운 책 뒤의 "찾아보기"예요. 단어를 찾으려고 첫 장부터 넘기지 않고, 찾아보기에서 쪽수를 바로 찾아 그 쪽으로 가요.
STEP:
1. Index가 없으면 `WHERE email = 'a@b.com'`을 찾으려고 Table 전체를 처음부터 끝까지 봐야 해요(**Full Table Scan**, O(n)).
2. email Column에 Index를 만들면, DB가 email 값과 Row 위치를 정렬된 구조로 따로 저장해요.
3. 이제 정렬된 구조에서 빠르게 찾아(O(log n)) 해당 Row로 바로 가요.
4. **B+Tree**: 대부분의 DB Index 구조예요. Node 하나를 Disk Page 크기에 맞춰 높이가 낮고(Disk 읽기가 적음), Leaf끼리 연결돼 있어 범위 검색과 정렬에도 강해요(06번 주제).
5. **Hash Index**: 같음(=) 검색은 아주 빠르지만, 순서가 없어서 범위 검색(`BETWEEN`, `>`)과 정렬을 못 해요.
WHY: 데이터가 100만 줄이면 Full Scan은 100만 번, Index는 약 20번 비교로 끝나요.
END: Index는 책의 찾아보기예요. 정렬해 둔 덕분에 전체를 넘기지 않고 바로 찾아가요.

#### Index의 비용과 Index가 안 쓰이는 경우
ONE: Index는 공짜가 아니에요. **공간을 더 쓰고, 쓰기를 느리게** 만들어요. 그리고 조건을 잘못 쓰면 Index가 있어도 **안 쓰여요**.
LIKE: 책에 내용을 추가할 때마다 찾아보기도 고쳐야 해요. 그리고 "그", "이" 같은 단어는 찾아보기에 있어도 거의 모든 쪽에 나와서 쓸모가 없어요.
STEP:
1. **공간 비용**: Index도 별도로 저장되니 Disk를 더 써요.
2. **쓰기 비용**: INSERT·UPDATE·DELETE마다 Table뿐 아니라 Index도 고쳐야 해요. Index가 많을수록 쓰기가 느려져요.
3. 그래서 모든 Column에 Index를 만들지 않고, **자주 검색하는 조건**을 보고 골라서 만들어요.
4. **Index가 안 쓰이는 경우 ①**: 값의 종류가 적은 Column(성별처럼 **Cardinality**가 낮음). 결국 Table의 절반을 읽어야 해서 Full Scan이 더 나을 수 있어요.
5. **②**: Column에 함수를 씌운 조건. `WHERE YEAR(created) = 2026`은 정렬 순서를 못 써요. `WHERE created >= '2026-01-01' AND created < '2027-01-01'`로 바꿔요.
6. **③**: 앞에 %가 붙은 LIKE. `'%kim'`은 시작 위치를 정할 수 없어요. `'kim%'`은 괜찮아요.
7. **④**: Type이 달라 자동 변환이 일어나는 비교, Composite Index의 첫 Column을 안 쓰는 조건, 아주 작은 Table.
KEY: 실제로 Index를 쓰는지는 **EXPLAIN**으로 실행 계획(Execution Plan)을 확인해요. 추측하지 말고 확인하세요.
END: Index는 읽기를 빠르게 하는 대신 공간과 쓰기 비용을 내요. 함수·앞쪽 %·낮은 Cardinality는 Index를 무력하게 해요.

#### Clustered Index vs Non-Clustered Index
ONE: **Clustered Index**는 Table 데이터 **자체가** Index 순서로 정렬돼 저장된 것이고, **Non-Clustered Index**는 데이터와 **따로** 있는 목록이 데이터 위치를 가리키는 것이에요.
LIKE: Clustered는 국어사전처럼 책 내용 자체가 가나다순으로 정렬된 거예요. Non-Clustered는 책 뒤의 찾아보기처럼, 따로 모아 둔 목록이 본문 쪽수를 가리키는 거예요.
STEP:
1. **Clustered Index**: Row들이 Disk에 Index Key 순서대로 놓여요. 데이터를 정렬하는 방법은 하나뿐이니 Table당 **하나만** 만들 수 있어요.
2. 범위 검색(`WHERE id BETWEEN 100 AND 200`)이 매우 빨라요. 원하는 Row들이 붙어 있으니까요.
3. MySQL InnoDB에서는 Primary Key가 Clustered Index예요.
4. **Non-Clustered (Secondary) Index**: 데이터와 별도의 구조예요. 여러 개 만들 수 있어요.
5. 찾은 뒤 실제 Row를 가지러 한 번 더 가야 해요. InnoDB에서는 Secondary Index가 Primary Key 값을 가리키고, 그 PK로 Clustered Index를 한 번 더 찾아요.
6. **Covering Index**: Query에 필요한 Column이 모두 Index 안에 들어 있으면, Row를 가지러 갈 필요 없이 Index만 읽고 끝나서 매우 빨라요.
END: Clustered는 데이터 자체가 정렬된 것(하나뿐), Non-Clustered는 따로 있는 찾아보기(여러 개)예요.

#### 여러 종류의 Index: Composite · Covering · Inverted · Vector
ONE: Index는 B+Tree 하나만 있는 게 아니에요. **여러 Column 묶음**, **Query를 Index만으로 끝내기**, **단어 검색**, **비슷한 것 찾기**용 Index가 따로 있어요.
LIKE: 도서관 색인도 여러 종류가 있어요. "저자 + 출판연도" 순 색인, 책 내용 요약까지 적힌 색인, "이 단어가 나오는 책 목록" 색인, "이 책과 비슷한 책" 추천 목록.
STEP:
1. **Composite Index (복합 인덱스)**: 여러 Column을 묶은 Index예요. `(last_name, first_name)`이면 전화번호부처럼 성으로 먼저, 같은 성 안에서 이름으로 정렬돼요.
2. 그래서 **왼쪽 Column부터** 써야 Index를 탈 수 있어요(**Leftmost Prefix**). `last_name`만 검색은 OK, `first_name`만 검색은 Index를 제대로 못 써요.
3. **Covering Index**: Query에 필요한 Column이 Index에 다 있어서 Table을 안 읽어도 되는 경우예요.
4. **Inverted Index (역색인)**: "단어 → 그 단어가 나오는 문서 목록"이에요. 검색 엔진(Elasticsearch)과 전문 검색(Full-Text Search)의 기본 구조예요.
5. **Spatial Index**: 지도 위 "내 주변 1km 안의 가게"처럼 위치 검색용이에요.
6. **Vector Index**: 문장·이미지를 숫자 Vector(Embedding)로 바꿔 저장하고 "가장 비슷한 것"을 빠르게 찾아요. AI 검색(RAG)에 쓰여요(16번 주제).
END: 묶어서 정렬하면 Composite(왼쪽부터), Index만으로 끝나면 Covering, 단어 검색은 Inverted, 비슷한 것 찾기는 Vector Index예요.

### Index란? 왜 B+Tree로 만드나요?
E: 두꺼운 책 뒤의 "찾아보기"입니다. 단어를 찾으려고 첫 장부터 넘기지 않고 찾아보기에서 쪽수를 바로 찾습니다.
A: Index는 특정 Column의 값과 Row 위치를 정렬해 저장한 별도 자료구조로, 전체 Table을 훑는 O(n) 대신 O(log n)에 찾게 합니다. 대부분 B+Tree를 쓰는데, Node 하나가 Disk Page에 맞춰 높이가 낮아 Disk 읽기가 적고, Leaf가 연결되어 Range Query(범위 검색)·정렬에도 강하기 때문입니다(06 Data Structure 참고). Hash Index는 같음(=) 검색은 빠르지만 범위 검색을 못 합니다.

### Index의 단점과, Index가 있어도 안 쓰이는 경우는?
E: 책에 내용을 추가할 때마다 찾아보기도 고쳐야 하고, "그"나 "이" 같은 단어는 찾아보기에 있어도 거의 모든 쪽에 나와서 쓸모가 없습니다.
A: Index는 저장 공간을 더 쓰고, INSERT·UPDATE·DELETE마다 Index도 고쳐야 해서 쓰기가 느려집니다. 또 값의 종류가 적은 Column(성별처럼 Cardinality가 낮은 Column), Column에 함수를 적용한 조건(`WHERE YEAR(created) = 2026`), 앞에 %가 붙은 LIKE(`'%kim'`), Implicit Type Conversion(암시적 형변환), Composite Index의 첫 번째 Column을 쓰지 않는 조건, 작은 Table에서는 Optimizer가 Index 대신 Full Table Scan을 고를 수 있습니다. EXPLAIN으로 실제 Execution Plan(실행 계획)을 확인합니다.

### Clustered Index vs Non-Clustered Index는?
E: Clustered는 국어사전처럼 책 내용 자체가 가나다순으로 정렬된 것이고, Non-Clustered는 책 뒤의 찾아보기처럼 따로 모아 둔 목록이 본문 위치를 가리키는 것입니다.
A: Clustered Index는 Table 데이터 자체를 Index Key 순서로 저장해 Table당 하나만 만들 수 있고, 범위 조회가 매우 빠릅니다(MySQL InnoDB에서는 Primary Key). Non-Clustered(Secondary) Index는 데이터와 따로 있는 구조가 Row 위치(InnoDB에서는 Primary Key 값)를 가리키므로 여러 개 만들 수 있지만, 찾은 뒤 데이터를 한 번 더 읽어야 합니다.

### Composite Index와 Covering Index란?
E: Composite Index는 전화번호부처럼 "성 → 이름" 순으로 정렬된 색인이라 성부터 찾아야 하고, Covering Index는 색인 카드에 필요한 정보가 다 적혀 있어 본문을 펼칠 필요가 없는 경우입니다.
A: Composite Index는 여러 Column을 순서대로 묶어 정렬한 Index로, 맨 왼쪽 Column부터 조건에 써야 Index를 효율적으로 씁니다(Leftmost Prefix Rule). Covering Index는 Query가 필요로 하는 모든 Column이 Index에 들어 있어 Table(또는 Clustered Index)을 다시 읽지 않고 Index만으로 결과를 내는 경우로, 추가 Disk 읽기가 없어 빠릅니다.

## Transaction과 Concurrency Control

#### Transaction과 ACID
ONE: **Transaction**은 **"전부 되거나, 전부 안 되거나"** 해야 하는 작업 묶음이고, 이를 지키는 네 가지 성질이 **ACID**예요.
LIKE: A가 B에게 1만 원을 보낼 때 "A 계좌에서 빼기"와 "B 계좌에 더하기"는 한 묶음이에요. 빼기만 되고 더하기가 안 되면 돈이 사라져요.
STEP:
1. **Atomicity (원자성)**: 묶음 안의 작업이 전부 성공하거나, 하나라도 실패하면 전부 취소(Rollback)돼요. 중간 상태는 없어요.
2. **Consistency (일관성)**: Transaction 전후로 규칙(잔액은 음수 불가 등)이 지켜져요. 사실 이건 DB만이 아니라 Application이 올바른 규칙을 정해야 지켜져요.
3. **Isolation (격리성)**: 여러 Transaction이 동시에 실행돼도 서로의 중간 상태를 보거나 방해하지 않아요.
4. **Durability (지속성)**: 한 번 COMMIT된 결과는 정전이나 장애가 나도 사라지지 않아요.
5. 사용법: `BEGIN` → 여러 SQL → 성공하면 `COMMIT`, 문제가 생기면 `ROLLBACK`.
| 성질 | 뜻 | 송금 예 |
| Atomicity | 전부 아니면 전무 | 출금·입금 둘 다 되거나 둘 다 안 됨 |
| Consistency | 규칙 유지 | 잔액이 음수가 되지 않음 |
| Isolation | 동시 실행 간섭 없음 | 다른 송금이 중간 상태를 못 봄 |
| Durability | 확정되면 영구 | 완료 후 정전돼도 기록 유지 |
WHY: 송금, 주문, 좌석 예약처럼 "반만 된 상태"가 큰 사고가 되는 일에 반드시 필요해요.
END: Transaction은 "전부 아니면 전무" 묶음이고, ACID가 그 약속의 네 가지 내용이에요.

#### Isolation Level과 이상 현상
ONE: Isolation을 완벽히 지키면 느려지기 때문에, DB는 **격리 수준(Isolation Level)**을 골라 **정확성과 속도 사이를 조절**하게 해 줘요. 수준이 낮을수록 빠르지만 이상한 현상이 생겨요.
LIKE: Dirty Read는 친구가 아직 "전송"도 안 누른 메시지 초안을 보는 것, Non-Repeatable Read는 같은 글을 두 번 읽었는데 그 사이 내용이 바뀐 것, Phantom Read는 같은 검색을 두 번 했는데 없던 글이 새로 나타난 거예요.
STEP:
1. **Dirty Read**: 다른 Transaction이 아직 COMMIT하지 않은 값을 읽어요. 그 Transaction이 Rollback하면 나는 존재하지도 않은 값을 본 셈이에요.
2. **Non-Repeatable Read**: 같은 Row를 두 번 읽었는데, 그 사이 다른 Transaction이 고치고 COMMIT해서 값이 달라져요.
3. **Phantom Read**: 같은 조건으로 두 번 조회했는데, 그 사이 다른 Transaction이 Row를 추가·삭제해서 결과 개수가 달라져요.
4. 격리 수준 4단계(아래로 갈수록 엄격):
| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read |
| Read Uncommitted | 발생 | 발생 | 발생 |
| Read Committed | 막음 | 발생 | 발생 |
| Repeatable Read | 막음 | 막음 | 발생 (SQL 표준 기준) |
| Serializable | 막음 | 막음 | 막음 |
5. **기본값**: MySQL InnoDB는 Repeatable Read(Next-Key Lock으로 Phantom도 대부분 막아요), PostgreSQL·Oracle·SQL Server는 Read Committed예요.
WHY: 모든 Transaction을 하나씩 차례로 실행하면 완벽하지만 너무 느려요. 서비스마다 허용할 수 있는 이상 현상을 골라 속도를 얻어요.
END: 격리 수준은 "얼마나 엄격하게 서로를 막을지" 다이얼이에요. 엄격할수록 정확하고, 느슨할수록 빨라요.

#### Snapshot Isolation과 Write Skew
ONE: **Snapshot Isolation**은 각 Transaction이 **시작 시점의 사진(Snapshot)**을 보게 하는 방식이에요. 많은 문제를 막지만, 서로 **다른 Row를 고쳐서 규칙이 깨지는 Write Skew**는 못 막아요.
LIKE: 부부의 두 통장 잔액 합이 항상 0 이상이어야 한다는 규칙이 있어요. 남편과 아내가 동시에 "합계가 충분하네"를 확인하고, 각자 자기 통장에서 큰돈을 빼요. 각자는 규칙을 지킨다고 생각했지만, 결과적으로 합계가 마이너스가 돼요.
STEP:
1. **Snapshot Isolation**: Transaction이 시작할 때의 데이터 사진을 보며 일해요. 다른 사람이 중간에 고쳐도 내 사진은 안 바뀌어서, Dirty Read와 Non-Repeatable Read가 없어요. 보통 MVCC로 구현해요.
2. **Write Skew**: 두 Transaction이 같은 조건을 각자 읽고(합계 확인), 그 결과를 바탕으로 **서로 다른 Row**를 고쳐요(각자 자기 통장).
3. 같은 Row를 고친 게 아니라서 충돌로 감지되지 않아요. 그래서 Snapshot Isolation은 이걸 막지 못해요.
4. 또 다른 예: "당직 의사는 최소 1명"인데 두 의사가 동시에 "다른 사람이 있네" 확인하고 각자 당직을 빼면 0명이 돼요.
5. **해결**: Serializable 수준을 쓰거나, 확인한 Row들에 명시적으로 Lock을 걸어요(`SELECT ... FOR UPDATE`).
6. **Serializable 구현 방법 3가지**: 진짜로 하나씩 차례로 실행하기, **2PL**(비관적, Lock으로 막기), **SSI(Serializable Snapshot Isolation)**(낙관적, 일단 실행하고 COMMIT할 때 충돌 검사).
WHY: "Repeatable Read면 안전하다"고 생각하기 쉽지만, 동시에 여러 Row를 읽고 판단하는 로직에서는 Write Skew가 실제 버그를 만들어요.
END: Snapshot Isolation은 사진을 보며 일하는 방식이고, 서로 다른 Row를 고쳐 규칙이 깨지는 Write Skew는 Serializable이나 명시적 Lock으로 막아요.

#### 2PL과 MVCC: 동시성 제어 방법
ONE: **2PL**은 **Lock으로 막아서** 순서를 지키는 방법이고, **MVCC**는 **여러 버전을 보관해서** 읽기와 쓰기가 서로 막지 않게 하는 방법이에요.
LIKE: 2PL은 도서관에서 책을 빌려 가는 동안 아무도 못 고치게 하는 것이고, MVCC는 누군가 책을 고치는 동안에도 다른 사람에게는 고치기 전 사본을 보여 주는 거예요.
STEP:
1. **Lock 종류**: **Shared Lock**(읽기용, 여럿이 함께 잡을 수 있음), **Exclusive Lock**(쓰기용, 혼자만 잡음).
2. **2PL (Two-Phase Locking)**: Lock을 **얻기만 하는 단계**(Growing)와 **풀기만 하는 단계**(Shrinking)를 나눠요. 한 번이라도 Lock을 풀면 다시는 새 Lock을 얻지 않아요. 이 규칙을 지키면 결과가 어떤 순서로 하나씩 실행한 것과 같아져요(Serializability).
3. 2PL의 단점: 읽는 사람과 쓰는 사람이 서로 기다리고, Deadlock이 생길 수 있어요.
4. **MVCC (Multi-Version Concurrency Control)**: 데이터를 고칠 때 덮어쓰지 않고 새 버전을 만들어요. 옛 버전도 잠시 보관해요.
5. 읽는 Transaction은 자기 시점의 버전(Snapshot)을 봐요. Isolation Level에 따라 Transaction 시작 시점이나 각 Query 시작 시점의 버전이에요.
6. 그래서 **읽기는 쓰기를 막지 않고, 쓰기도 읽기를 막지 않아요**. 같은 Row를 동시에 쓰는 경우만 충돌로 처리해요.
USE: PostgreSQL, MySQL InnoDB, Oracle이 MVCC를 써요. 오래된 버전은 나중에 청소해요(PostgreSQL의 VACUUM).
END: 막아서 지키면 2PL, 버전을 나눠서 피하면 MVCC예요. 요즘 DB는 대부분 MVCC를 바탕으로 해요.

#### COMMIT · ROLLBACK과 WAL, Recovery
ONE: DB는 데이터를 바꾸기 **전에 변경 내용을 Log에 먼저** 적어요(**WAL, Write-Ahead Logging**). 그래서 장애가 나도 Log를 보고 끝난 일은 다시 하고, 덜 끝난 일은 되돌려요.
LIKE: 작업 내용을 먼저 일지에 적어 두면, 정전이 나도 일지를 보고 끝난 일은 다시 하고 덜 끝난 일은 되돌릴 수 있어요.
STEP:
1. **COMMIT**: Transaction의 변경을 확정해요. 이 순간부터는 사라지면 안 돼요(Durability).
2. **ROLLBACK**: Transaction 시작 전 상태로 되돌려요.
3. **WAL**: 데이터 파일을 바꾸기 전에, "무엇을 어떻게 바꿀지"를 Log 파일 끝에 순서대로 먼저 써요. Log 쓰기는 파일 끝에 이어 쓰는 거라 빨라요.
4. COMMIT은 Log가 Disk에 안전하게 기록된 순간 완료돼요. 실제 데이터 파일은 나중에 천천히 반영해도 돼요.
5. **장애 후 복구**: Log를 읽으면서 COMMIT된 Transaction은 다시 적용하고(**Redo**), COMMIT되지 않은 Transaction은 취소해요(**Undo**).
6. 이렇게 Atomicity와 Durability를 함께 지켜요.
USE: WAL은 Replication에도 쓰여요. Primary의 Log를 Replica에 보내 똑같이 재생하면 복제가 돼요.
END: "먼저 일지, 나중에 실행". WAL 덕분에 장애가 나도 확정된 건 살리고, 덜 된 건 되돌려요.

### Transaction과 ACID란?
E: A가 B에게 1만 원을 보낼 때 "A 계좌에서 빼기"와 "B 계좌에 더하기"는 한 묶음입니다. 빼기만 되고 더하기가 안 되면 돈이 사라집니다.
A: Transaction은 논리적으로 한 덩어리인 작업 단위이고, ACID 성질을 보장해야 합니다.
| 성질 | 뜻 | 송금 예시 |
| Atomicity (원자성) | 전부 성공하거나 전부 취소 | 출금·입금이 둘 다 되거나 둘 다 안 됨 |
| Consistency (일관성) | Constraint를 지킨 상태에서 다시 지킨 상태로 | 잔액이 음수가 되지 않음 |
| Isolation (격리성) | 동시에 실행되어도 서로 끼어들지 않음 | 다른 송금이 중간 상태를 보지 못함 |
| Durability (지속성) | Commit되면 장애가 나도 남음 | 송금 완료 후 정전돼도 기록 유지 |

### Isolation Level 4단계와 Dirty Read·Non-Repeatable Read·Phantom Read는?
E: Dirty Read는 친구가 아직 "전송"도 안 누른 메시지 초안을 보는 것, Non-Repeatable Read는 같은 글을 두 번 읽었는데 그 사이 내용이 바뀐 것, Phantom Read는 같은 검색을 두 번 했는데 없던 글이 새로 나타난 것입니다.
| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read |
| Read Uncommitted | 발생 | 발생 | 발생 |
| Read Committed | 막음 | 발생 | 발생 |
| Repeatable Read | 막음 | 막음 | 발생 (SQL 표준 기준) |
| Serializable | 막음 | 막음 | 막음 |
A: Isolation Level은 성능과 정확성 사이의 조절장치로, 수준이 높을수록(표에서 아래로 갈수록) 이상 현상은 줄지만 동시 처리량이 떨어집니다. Dirty Read는 Commit되지 않은 데이터를 읽는 것, Non-Repeatable Read는 같은 Row를 다시 읽었을 때 값이 바뀐 것, Phantom Read는 같은 조건으로 다시 조회했을 때 Row가 생기거나 사라진 것입니다. 기본값은 MySQL InnoDB가 Repeatable Read(Next-Key Lock으로 Phantom도 대부분 막음), PostgreSQL·Oracle·SQL Server가 Read Committed입니다.

### Lock 기반 Concurrency Control(2PL)과 MVCC는?
E: 2PL은 도서관에서 책을 빌려 가는 동안 아무도 못 고치게 하는 것, MVCC는 누군가 고치는 동안에도 다른 사람에게는 고치기 전 사본을 보여 주는 것입니다.
A: 2PL(Two-Phase Locking)은 Lock을 얻기만 하는 Growing Phase와 풀기만 하는 Shrinking Phase를 나눠 Serializability(직렬화 가능성)를 보장하며, Shared Lock(읽기)과 Exclusive Lock(쓰기)을 씁니다. 대신 기다림과 Deadlock이 생길 수 있습니다. MVCC(Multi-Version Concurrency Control)는 데이터의 여러 Version을 보관해 읽기는 특정 시점의 Snapshot(Isolation Level에 따라 Transaction 시작 시점 또는 각 Query 시작 시점)을 보게 하므로, 읽기와 쓰기가 서로를 막지 않아 PostgreSQL·MySQL InnoDB·Oracle이 씁니다.

### COMMIT과 ROLLBACK, Log와 Recovery는?
E: 작업 내용을 먼저 일지에 적어 두면, 정전이 나도 일지를 보고 끝난 일은 다시 하고 덜 끝난 일은 되돌릴 수 있습니다.
A: COMMIT은 Transaction의 변경을 확정하고, ROLLBACK은 Transaction 시작 전 상태로 되돌립니다. DB는 데이터를 바꾸기 전에 변경 내용을 Log에 먼저 기록하는 WAL(Write-Ahead Logging)을 써서, 장애가 나면 Commit된 것은 Log로 다시 적용(Redo)하고 Commit되지 않은 것은 취소(Undo)해 Atomicity와 Durability를 지킵니다.

### Snapshot Isolation에서도 생길 수 있는 Write Skew란?
E: 부부가 동시에 "두 통장 합계가 충분하네"를 확인하고 각자 자기 통장에서 큰돈을 빼면, 각자는 규칙을 지켰다고 생각했지만 합계가 마이너스가 됩니다.
A: Write Skew는 두 Transaction이 같은 조건을 읽고 그 결과를 근거로 서로 다른 Row를 수정해, 함께 보면 규칙(Invariant)이 깨지는 이상 현상입니다. 같은 Row를 수정하지 않아 Snapshot Isolation(MVCC 기반 Repeatable Read)의 쓰기 충돌 검사로는 잡히지 않습니다. Serializable Isolation(SSI, 2PL)을 쓰거나 읽은 Row에 `SELECT ... FOR UPDATE`로 Lock을 걸어 막습니다.

## SQL vs NoSQL, Distributed Database

#### Data Model 고르기: Relational · Document · Graph · Key-Value · Wide-Column
ONE: 데이터를 **어떤 모양으로 저장하느냐**가 Data Model이에요. 표(Relational), 한 덩어리 문서(Document), 관계망(Graph), 단순 Key-Value 등이 있고, **데이터의 모양과 쓰는 방식**에 맞춰 골라요.
LIKE: 관계형 DB는 칸이 미리 정해진 Excel 장부라 정확하고 서로 연결하기 좋아요. Document DB는 모양이 자유로운 수납 상자, Graph DB는 인맥 지도, Key-Value는 번호표만 보고 물건을 꺼내는 사물함이에요.
STEP:
1. **Relational (SQL)**: 정형 데이터와 다대다 관계에 강해요. JOIN, Schema로 규칙 보장, ACID Transaction. 대신 계층형 데이터는 여러 Table로 쪼개져요.
2. **Document (MongoDB 등)**: JSON 같은 문서 하나에 관련 정보를 통째로 담아요. 한 번에 읽기 좋고(Locality), 구조를 바꾸기 쉬워요. 대신 JOIN과 다대다 관계가 약해요.
3. **Graph (Neo4j 등)**: 점(Node)과 관계(Edge)가 핵심이에요. "친구의 친구의 친구" 같은 깊은 관계 탐색에 강하고, 대량 집계에는 약해요.
4. **Key-Value (Redis, DynamoDB)**: Key로 Value를 바로 꺼내요. 아주 빠르고 단순해요. Cache, Session에 많이 써요.
5. **Wide-Column (Cassandra, HBase)**: 엄청난 양의 쓰기와 수평 확장에 강해요. 대신 질의가 유연하지 않아요. Log, 시계열 데이터에 써요.
6. **Schema-on-Write vs Schema-on-Read**: 관계형은 쓸 때 형식을 검사해요. Document DB의 "Schema가 유연하다"는 말은 Schema가 없다는 게 아니라 **읽을 때 해석한다**는 뜻이에요. 결국 코드는 데이터 모양을 가정해요.
| 종류 | 강점 | 약점 | 어울리는 곳 |
| Relational | JOIN, 규칙 보장, Transaction | 계층 데이터 쪼개짐 | 결제, 주문, 회원 |
| Document | 한 덩어리 읽기, 구조 유연 | JOIN·다대다 약함 | 상품 상세, 콘텐츠 |
| Graph | 깊은 관계 탐색 | 대량 집계 | 친구 추천, 사기 탐지 |
| Key-Value | 매우 빠름 | 검색 기능 단순 | Cache, Session |
| Wide-Column | 대량 쓰기, 수평 확장 | 질의 유연성 낮음 | Log, 시계열 |
KEY: "SQL vs NoSQL" 중 하나가 항상 낫지 않아요. 한 서비스에서 주문은 PostgreSQL, Cache는 Redis, 검색은 Elasticsearch처럼 여러 DB를 함께 쓰는 경우가 많아요.
END: 데이터의 모양과 접근 방식을 먼저 보고 Data Model을 골라요. 정확성·관계는 관계형, 유연성·규모는 NoSQL 계열이 강해요.

#### Replication (복제)
ONE: **같은 데이터를 여러 서버에 복사**해 두는 것이에요. 한 대가 죽어도 서비스가 살아 있고, 읽기를 여러 대로 나눌 수 있어요.
LIKE: 중요한 문서를 여러 장 복사해 다른 사무실에 보관하는 것과 같아요. 한 사무실에 불이 나도 문서는 남아 있고, 여러 사람이 각자 가까운 사무실에서 읽을 수 있어요.
STEP:
1. **Single-Leader (가장 흔함)**: Leader(Primary) 한 대만 쓰기를 받고, 변경을 Follower(Replica)들에게 전달해요. 읽기는 Follower들이 나눠 받아요. 단순하고 쓰기 충돌이 없어요. Leader가 죽으면 Follower 하나를 새 Leader로 올려야 해요(**Failover**).
2. **Multi-Leader**: 여러 곳에서 쓰기를 받아요. 여러 데이터센터나 오프라인 편집에 쓰지만, 같은 데이터를 두 곳에서 동시에 고치면 충돌을 해결해야 해요.
3. **Leaderless**: 아무 서버에나 쓰고 여러 서버에서 읽어요. 복제본 n개 중 w개에 쓰고 r개에서 읽을 때 **w + r > n**이면, 읽은 서버 중 적어도 하나는 최신 값을 갖고 있어요(**Quorum**).
4. **Synchronous vs Asynchronous**: 동기 복제는 Follower가 받았다고 답해야 COMMIT돼서 안전하지만, 느린 Follower 하나가 전체를 느리게 해요. 비동기 복제는 빠르지만 Leader가 갑자기 죽으면 최근 쓰기를 잃을 수 있어요. 실무에서는 Follower 하나만 동기로 두는 절충을 많이 써요.
5. **Replication Lag (복제 지연)이 만드는 이상한 현상**: 방금 쓴 글이 새로고침하면 안 보임(자기 쓰기 읽기 위반), 새로고침할 때마다 시간이 뒤로 감(단조 읽기 위반), 답글이 원글보다 먼저 보임(인과 순서 위반).
6. **충돌 해결 방법**: 마지막 쓰기가 이김(Last Write Wins, 간단하지만 데이터 유실 가능), 버전 정보로 동시 쓰기를 감지해 병합, 자동으로 병합되는 자료구조(**CRDT**).
KEY: "방금 쓴 내 글은 Leader에서 읽기"처럼 상황에 맞게 읽을 곳을 고르면 Replication Lag 문제를 많이 줄일 수 있어요.
END: Replication은 같은 데이터를 여러 곳에 두는 것이고, 안전(동기)과 속도(비동기) 사이, 그리고 복제 지연 문제를 함께 고민해야 해요.

#### Sharding (Partitioning)
ONE: 데이터가 한 서버에 다 안 들어가거나 쓰기가 너무 많으면, **데이터를 나눠서 서로 다른 서버에** 저장해요. 이게 Sharding이에요.
LIKE: 전화번호부가 너무 두꺼워지면 ㄱ~ㅁ, ㅂ~ㅎ 두 권으로 나눠요. Replication은 같은 전화번호부를 여러 권 복사하는 것이고, Sharding은 내용을 나눠 각각 다른 책으로 만드는 거예요.
STEP:
1. **Key 범위로 나누기 (Range)**: 이름 ㄱ~ㅁ은 1번 서버, ㅂ~ㅎ은 2번 서버. 범위 검색이 쉽지만, 특정 범위에 데이터나 요청이 몰릴 수 있어요(예: 날짜로 나누면 오늘 데이터만 한 서버에 몰림).
2. **Key의 Hash로 나누기**: Hash 값으로 서버를 정해요. 고르게 퍼지지만, 범위 검색을 하려면 모든 서버를 봐야 해요.
3. **Hot Spot (핫스팟)**: 아주 인기 있는 Key 하나(유명 연예인 계정 등)에 요청이 몰리는 건 어떤 방식으로도 자동 해결되지 않아요. Key 뒤에 무작위 숫자를 붙여 여러 개로 쪼개는 식으로 직접 처리해요.
4. **Rebalancing (재조정)**: 서버를 추가·제거하면 데이터를 옮겨야 해요. "Hash % 서버 수"로 나누면 서버 수가 바뀔 때 거의 모든 Key가 이동해서 피해요. 대신 처음부터 작은 Partition을 아주 많이 만들어 두고 서버에 나눠 맡기거나, **Consistent Hashing**을 써요.
5. **단점**: 여러 Shard에 걸친 JOIN과 Transaction이 어려워져요. 그래서 함께 자주 쓰는 데이터는 같은 Shard에 두도록 Key를 정하는 게 중요해요.
| 구분 | Replication | Sharding |
| 하는 일 | 같은 데이터를 여러 곳에 복사 | 데이터를 나눠 여러 곳에 분산 |
| 얻는 것 | 장애 대비, 읽기 분산 | 저장 용량·쓰기 확장 |
| 어려운 점 | 복제 지연, 충돌 | Shard 간 JOIN·Transaction |
END: Replication은 복사, Sharding은 나누기. 실무에서는 Shard마다 Replica를 두어 둘을 함께 써요.

#### CAP Theorem
ONE: 분산 시스템에서 **Network가 끊겼을 때(Partition)**, **모두가 같은 최신 데이터를 보게 할지(Consistency)**와 **모든 요청에 응답할지(Availability)** 중 하나를 골라야 한다는 정리예요.
LIKE: 두 은행 지점 사이 전화선이 끊겼어요. "서로 확인될 때까지 거래를 멈춘다"(Consistency)와 "일단 각자 거래를 받는다"(Availability) 중 하나만 고를 수 있어요.
STEP:
1. **Consistency (C)**: 모든 Node가 같은 최신 데이터를 보여 줘요(여기서는 선형성, 즉 복사본이 하나인 것처럼 보이는 강한 일관성).
2. **Availability (A)**: 살아 있는 Node는 모든 요청에 응답해요.
3. **Partition Tolerance (P)**: Network가 끊겨 Node끼리 연락이 안 돼도 시스템이 동작해요.
4. 여러 대의 서버를 Network로 잇는 이상 Partition은 언젠가 반드시 생겨요. 그래서 P는 사실상 포기할 수 없어요.
5. 그러니 실제 질문은 **"Partition이 생기면 C와 A 중 무엇을 지킬까?"**예요.
6. **CP**: 일관성을 지키려고 일부 요청을 거절하거나 기다리게 해요. 은행 잔액, 재고처럼 틀리면 안 되는 데이터.
7. **AP**: 잠깐 옛 데이터를 보여 주더라도 계속 응답해요. SNS 좋아요 수, 피드처럼 잠시 달라도 괜찮은 데이터.
KEY: Partition이 없는 평소에도 "일관성을 높이면 느려진다"는 Latency와의 줄다리기가 있어요. 그래서 실제 설계는 C/A 이분법보다 "어느 정도의 일관성을 얼마의 속도에 살까"의 문제예요.
END: Network가 끊기면 "정확하게 멈출지(CP), 일단 응답할지(AP)"를 골라야 해요.

### SQL(Relational)과 NoSQL의 차이는? 언제 무엇을 쓰나요?
E: Relational DB는 칸이 미리 정해진 Excel 장부라 정확하고 서로 연결하기 좋습니다. NoSQL은 모양이 자유로운 수납 상자라 무엇이든 빨리 넣고, 상자를 여러 창고에 나눠 두기 쉽습니다.
| 종류 | 저장 방식 | 대표 제품 | 어울리는 곳 |
| Key-Value | Key 하나에 Value 하나 | Redis, DynamoDB | Cache, Session |
| Document | JSON 같은 Document | MongoDB | 구조가 자주 바뀌는 데이터 |
| Wide-Column | Row마다 다른 Column 묶음 | Cassandra, HBase | 대량 쓰기, Log·Time Series |
| Graph | Node와 관계(Edge) | Neo4j | 친구 추천, 관계 탐색 |
A: Relational DB는 고정된 Schema, JOIN, ACID Transaction이 강점이라 결제·주문처럼 정확성과 관계가 중요한 데이터에 맞고, 주로 성능을 높일 때 Server를 키우는 Scale-Up을 합니다. NoSQL은 Schema가 유연하고 여러 Server로 나누는 Scale-Out(수평 확장)이 쉬워 대용량·빠르게 바뀌는 데이터에 맞지만, 제품에 따라 JOIN이나 Strong Consistency(강한 일관성)가 약할 수 있습니다. 둘 중 하나가 늘 낫다기보다 데이터 모양과 일관성 요구에 맞춰 고르며, 한 서비스에서 함께 쓰는 경우도 많습니다.

### CAP Theorem이란?
E: 두 지점에 있는 은행 지점 사이 전화선이 끊겼습니다(Network Partition). 이때 "서로 확인될 때까지 거래를 멈춘다"(Consistency)와 "일단 각자 거래를 받는다"(Availability) 중 하나만 고를 수 있습니다.
A: CAP Theorem은 분산 시스템이 Consistency(모든 Node가 같은 최신 데이터), Availability(모든 요청에 응답), Partition Tolerance(네트워크가 끊겨도 동작)를 동시에 모두 보장할 수 없다는 정리입니다. 실제 분산 환경에서 Network Partition은 피할 수 없으므로, Partition이 생겼을 때 Consistency(CP)와 Availability(AP) 중 무엇을 우선할지 고르는 문제로 이해합니다.

### Sharding과 Replication의 차이는?
E: Sharding은 전화번호부를 ㄱ~ㅁ, ㅂ~ㅎ 두 권으로 나누는 것이고, Replication은 같은 전화번호부를 여러 권 복사해 두는 것입니다.
A: Sharding은 데이터를 Key 기준으로 나눠 여러 Server에 다른 부분을 저장해 쓰기와 저장 용량을 확장합니다. Replication은 같은 데이터를 여러 Server에 복제해 읽기 분산과 장애 대비(High Availability)를 얻으며, 보통 Primary가 쓰기를 받고 Replica가 읽기를 나눠 받습니다. Sharding은 여러 Shard에 걸친 JOIN·Transaction이 어렵고, Replication은 Replication Lag(복제 지연) 때문에 Replica에서 잠깐 옛 데이터가 보일 수 있습니다.

### Leader 기반 Replication에서 Replication Lag 때문에 생기는 문제와 해결책은?
E: 원본 장부(Leader)의 변경이 복사본(Follower)에 늦게 도착해서, 복사본을 보면 방금 내가 쓴 내용이 아직 없거나 시간이 거꾸로 가는 것처럼 보입니다.
A: 비동기 Replication에서는 Follower가 Leader보다 늦어, 방금 쓴 데이터가 안 보이는 Read-Your-Writes 위반, 새로고침마다 데이터가 과거로 돌아가는 Monotonic Read 위반, 답글이 원글보다 먼저 보이는 Causal Order 위반이 생길 수 있습니다. 방금 쓴 사용자의 읽기는 Leader로 보내기, 한 사용자는 항상 같은 Replica에서 읽기, 인과 관계가 있는 쓰기를 같은 순서로 전달하기 등으로 완화합니다.

## 실무 주제

#### 저장 엔진: B-Tree vs LSM-Tree
ONE: DB가 데이터를 Disk에 저장하는 방식(Storage Engine)은 크게 **제자리에서 고쳐 쓰는 B-Tree**와 **모았다가 순서대로 몰아 쓰는 LSM-Tree**로 나뉘어요.
LIKE: B-Tree는 정리된 서류철에서 해당 페이지를 찾아 바로 고쳐 쓰는 방식이에요. LSM-Tree는 새 메모를 일단 책상 위 바구니에 쌓아 두다가, 차면 정렬해서 새 파일로 철하고, 가끔 여러 파일을 합쳐 정리하는 방식이에요.
STEP:
1. **B-Tree 계열 (대부분의 관계형 DB)**: 데이터를 고정 크기 Page로 나누고, 바뀐 값은 그 Page를 **제자리에서 덮어써요**. 덮어쓰다 장애가 나면 깨질 수 있어서 WAL에 먼저 기록해요.
2. B-Tree는 읽기가 예측 가능하고 빨라요. 어떤 Key든 몇 번의 Page 읽기로 찾아요.
3. **LSM-Tree 계열 (RocksDB, Cassandra 등)**: 쓰기를 먼저 Memory의 정렬된 Buffer에 모아요.
4. Buffer가 차면 정렬된 파일(**SSTable**)로 Disk에 **순서대로 한 번에** 써요. Disk는 순서대로 쓰기가 빨라서 쓰기 처리량이 매우 높아요.
5. 파일이 쌓이면 백그라운드에서 여러 파일을 합치고 지워진 값을 정리해요(**Compaction**).
6. 읽을 때는 여러 파일을 확인해야 해서 느릴 수 있어요. 그래서 "이 파일엔 그 Key가 확실히 없다"를 빠르게 알려 주는 **Bloom Filter**를 함께 써요.
| 구분 | B-Tree | LSM-Tree |
| 쓰기 방식 | 제자리 덮어쓰기 + WAL | 모아서 순서대로 쓰기 |
| 강점 | 읽기 지연이 안정적 | 쓰기 처리량, 압축률 |
| 약점 | 쓰기가 상대적으로 느림 | 읽기 시 여러 파일 확인, Compaction 비용 |
| 예 | MySQL InnoDB, PostgreSQL | RocksDB, Cassandra, LevelDB |
KEY: 일반적인 경향일 뿐이고, 실제 성능은 자기 서비스의 작업량으로 직접 측정해 봐야 해요.
END: 읽기 위주면 B-Tree, 쓰기가 폭발적으로 많으면 LSM-Tree가 유리한 경향이 있어요.

#### OLTP와 OLAP
ONE: **OLTP**는 사용자 요청을 처리하는 **"몇 줄 빨리 읽고 쓰기"**, **OLAP**는 분석을 위한 **"수백만 줄 훑어서 집계하기"**예요. 목적이 달라서 저장 방식도 달라요.
LIKE: OLTP는 편의점 계산대예요. 손님 한 명 한 명의 결제를 빠르게 처리해요. OLAP는 본사 분석팀이에요. 한 달치 전국 매출을 모아 "어떤 상품이 잘 팔렸나"를 분석해요.
STEP:
1. **OLTP (Online Transaction Processing)**: 주문, 결제, 회원 가입처럼 Key로 몇 개의 Row를 읽고 써요. 빠른 응답과 정확성이 중요해요. PostgreSQL, MySQL.
2. **OLAP (Online Analytical Processing)**: "지난달 지역별 매출 합계"처럼 아주 많은 Row를 훑어서 집계해요. 분석가와 대시보드가 써요.
3. **Row-Oriented (행 지향)**: 한 Row의 모든 Column을 붙여 저장해요. 한 사람의 정보를 통째로 읽는 OLTP에 좋아요.
4. **Column-Oriented (열 지향)**: 같은 Column 값끼리 붙여 저장해요. "매출 Column만 다 더하기"처럼 필요한 Column만 읽을 수 있고, 비슷한 값이 연속돼 압축도 잘 돼요. OLAP에 좋아요.
5. **Data Warehouse**: 분석 전용 DB예요. 운영 DB(OLTP)의 데이터를 **ETL/ELT**(추출·변환·적재)로 옮겨 와요. 분석 Query가 운영 서비스를 느리게 하지 않게 분리하는 거예요.
6. **Star Schema**: 분석용 설계의 전형이에요. 가운데 사건 기록(**Fact Table**, 예: 판매 기록)을 두고, 주변에 설명 정보(**Dimension Table**, 예: 상품, 매장, 날짜)를 둘러싸요.
| 구분 | OLTP | OLAP |
| 접근 | Key로 몇 줄 읽고 쓰기 | 수백만 줄 훑어 집계 |
| 사용자 | 최종 사용자, 앱 | 분석가, 대시보드 |
| 저장 | 행 지향 | 열 지향 + 압축 |
| 예 | PostgreSQL, MySQL | Data Warehouse (BigQuery, Snowflake 등) |
END: 서비스 처리는 OLTP(행 지향), 분석은 OLAP(열 지향)로 나누고, ETL로 데이터를 옮겨요.

#### Redis와 Cache
ONE: **Redis**는 데이터를 **Memory에** 두는 아주 빠른 Key-Value 저장소예요. 자주 읽는 데이터를 앞에 두는 **Cache**로 가장 많이 써요.
LIKE: 창고(Disk DB)까지 가지 않고, 계산대 옆 서랍(Memory)에 자주 찾는 물건을 넣어 두는 거예요.
STEP:
1. Memory는 Disk보다 훨씬 빨라서 Redis는 보통 1ms도 안 걸려 응답해요.
2. 단순 문자열뿐 아니라 List, Hash, Set, **Sorted Set**(점수 순 정렬) 같은 자료구조를 지원해요.
3. 명령을 기본적으로 한 Thread에서 차례로 실행해서, 명령 하나하나가 Atomic해요.
4. **Cache 사용 패턴 (Cache-Aside)**: 먼저 Redis에서 찾고, 없으면 DB에서 읽어 Redis에 넣어 둬요. 다음부터는 Redis에서 바로 꺼내요.
5. Cache에는 유효 시간(**TTL**)을 정해 오래된 값이 계속 남지 않게 해요. 원본이 바뀌면 Cache를 지우거나 갱신해야 해요(Cache Invalidation).
6. Memory 데이터는 전원이 꺼지면 사라지니, 필요하면 Snapshot(**RDB**)이나 명령 Log(**AOF**)로 Disk에 남겨요.
USE: DB 앞의 Cache, 로그인 Session 저장, 요청 횟수 제한(Rate Limiting), Sorted Set으로 실시간 랭킹, Pub/Sub 메시지.
KEY: "Cache는 원본이 아니다"를 기억하세요. Cache가 사라져도 원본 DB에서 다시 만들 수 있어야 해요.
END: Redis는 Memory 위의 빠른 서랍이고, 자주 읽는 데이터를 Cache해서 DB 부담을 크게 줄여요.

#### SQL Injection
ONE: 사용자 입력이 SQL 문장에 **그대로 이어 붙여질 때**, 공격자가 입력에 SQL 코드를 섞어 **Query의 의미를 바꾸는** 공격이에요.
LIKE: 주문서의 "이름" 칸에 "홍길동, 그리고 금고 문 열어 주세요"라고 적었는데, 직원이 그 문장을 그대로 지시로 따르는 상황이에요.
STEP:
1. 위험한 코드: `"SELECT * FROM users WHERE id = '" + input + "'"`처럼 입력을 문자열로 이어 붙여요.
2. 공격자가 입력에 `' OR '1'='1`을 넣으면 Query가 `WHERE id = '' OR '1'='1'`이 돼요. '1'='1'은 항상 참이라 모든 사용자가 조회돼요.
3. 로그인을 우회하거나, 데이터를 빼내거나, 심하면 Table을 지울 수도 있어요.
4. **핵심 방어: Prepared Statement (Parameter Binding)**: SQL 문장의 틀과 값을 분리해서 보내요. 값 자리는 `?`로 비워 두고, 입력은 "값"으로만 전달돼서 SQL 문법으로 해석되지 않아요.
5. **함께 쓰는 방어**: ORM 사용, 입력 검증, DB 계정에 최소 권한만 주기(Least Privilege), 오류 메시지에 DB 정보 숨기기.
```sql
-- 위험: 문자열을 이어 붙임
"SELECT * FROM users WHERE id = '" + input + "'"
-- 안전: Placeholder(?)에 값만 전달
SELECT * FROM users WHERE id = ?
```
KEY: HTTPS는 전송 구간을 암호화할 뿐 SQL Injection을 막지 못해요. 근본 해결책은 Prepared Statement예요.
END: 입력을 SQL에 이어 붙이면 입력이 명령이 돼요. 틀과 값을 분리(Prepared Statement)하면 막혀요.

#### Stored Procedure
ONE: 여러 SQL을 **DB 안에 함수처럼 저장**해 두고 이름으로 호출하는 기능이에요.
LIKE: 자주 하는 복잡한 업무를 매번 설명하지 않고, 담당 직원에게 "3번 업무 처리해 주세요"라고만 말하는 것과 같아요.
STEP:
1. `CREATE PROCEDURE`로 여러 SQL과 조건문을 묶어 DB에 저장해요.
2. Application은 `CALL 이름(인자)`로 실행해요.
3. **장점**: 여러 SQL을 한 번의 호출로 실행해 Network 왕복이 줄어요. Procedure 단위로 권한을 줄 수 있어요.
4. **단점**: 업무 로직이 DB 안에 흩어져서 버전 관리, Test, Debugging이 어려워요. 특정 DB 제품의 문법에 묶여 다른 DB로 옮기기 어려워요.
5. 그래서 요즘은 로직을 Application 코드에 두고, Stored Procedure는 성능이 꼭 필요한 곳에만 쓰는 경우가 많아요.
END: Stored Procedure는 DB 안의 저장된 함수예요. 빠르지만 관리가 어려워서 요즘은 아껴 써요.

### Redis란? 어디에 쓰나요?
E: 창고(Disk DB)까지 가지 않고 계산대 옆 서랍(Memory)에 자주 찾는 물건을 넣어 두는 것입니다.
A: Redis는 데이터를 Memory에 두는 Key-Value Store로, String뿐 아니라 List·Hash·Set·Sorted Set 같은 자료구조를 지원해 매우 빠릅니다. Cache, 로그인 Session, Rate Limiting(요청 횟수 제한), Sorted Set을 이용한 랭킹, Pub/Sub 메시징 등에 쓰입니다. 명령은 기본적으로 한 Thread에서 차례로 실행되어 개별 명령이 Atomic하고, Memory 데이터는 RDB Snapshot이나 AOF Log로 Disk에 남길 수 있습니다.

### Stored Procedure의 장단점은?
A: Stored Procedure는 여러 SQL을 DB 안에 함수처럼 저장해 두고 호출하는 것입니다. Network 왕복(Round Trip)이 줄고 권한을 Procedure 단위로 줄 수 있다는 장점이 있습니다. 반면 Business Logic이 DB에 흩어져 Version 관리·Test·Debugging이 어렵고 특정 DB 제품에 묶여, 요즘은 Logic을 Application 코드에 두는 경우가 많습니다.

### SQL Injection이란? 어떻게 막나요?
E: 주문서의 "이름" 칸에 "홍길동, 그리고 금고 문 열어 주세요"라고 적었는데 직원이 그 문장을 그대로 지시로 따르는 상황입니다.
A: SQL Injection은 사용자 입력이 SQL 문장의 일부로 그대로 합쳐질 때, 공격자가 `' OR '1'='1` 같은 입력으로 Query의 의미를 바꿔 인증을 우회하거나 데이터를 빼내는 공격입니다. 입력값을 SQL과 분리해 값으로만 전달하는 Prepared Statement(Parameter Binding)가 핵심 방어이고, ORM 사용, Input Validation(입력 검증), DB 계정 Least Privilege(최소 권한), Error Message 숨기기를 함께 씁니다.
```sql
-- 위험: 문자열을 이어 붙임
"SELECT * FROM users WHERE id = '" + input + "'"
-- 안전: Placeholder(?)에 값만 전달
SELECT * FROM users WHERE id = ?
```

### B-Tree와 LSM-Tree 저장 엔진의 차이는?
E: B-Tree는 서류철에서 해당 페이지를 찾아 바로 고쳐 쓰는 방식이고, LSM-Tree는 새 메모를 바구니에 모았다가 정렬해서 새 파일로 철하고 가끔 합쳐 정리하는 방식입니다.
A: B-Tree는 고정 크기 Page를 제자리에서 덮어쓰고 장애 대비로 WAL을 쓰며, 읽기 지연이 안정적이라 대부분의 관계형 DB가 씁니다. LSM-Tree는 쓰기를 Memory의 정렬 Buffer(Memtable)에 모았다가 정렬된 파일(SSTable)로 순차 기록하고 백그라운드 Compaction으로 병합하므로 쓰기 처리량과 압축률이 좋습니다. 대신 읽을 때 여러 파일을 확인해야 해 Bloom Filter로 보완하며, RocksDB·Cassandra가 대표적입니다.

### OLTP와 OLAP의 차이는?
E: OLTP는 손님 한 명씩 빠르게 결제하는 편의점 계산대, OLAP는 한 달치 전국 매출을 모아 분석하는 본사 분석팀입니다.
A: OLTP는 사용자 요청에 따라 Key로 소수의 Row를 읽고 쓰는 작업으로 빠른 응답과 Transaction이 중요하며 행 지향 저장을 씁니다. OLAP는 수백만 Row를 훑어 집계하는 분석 작업으로, 필요한 Column만 읽고 압축이 잘 되는 열 지향 저장(Column Store)과 Data Warehouse를 씁니다. 운영 DB의 데이터는 ETL/ELT로 Warehouse에 옮기고, Fact Table과 Dimension Table로 이루어진 Star Schema로 설계하는 경우가 많습니다.

## QUIZ

? 회원 목록을 모두 보여 주되, 주문이 있으면 주문 정보도 붙이고 없으면 비워 두려면 어떤 JOIN을 쓰나요?
- INNER JOIN
- LEFT JOIN (회원 기준)
- CROSS JOIN
- SELF JOIN
= B
! LEFT JOIN은 왼쪽(회원) Table의 모든 Row를 남기고, 짝이 없는 오른쪽 Column은 NULL로 채웁니다. INNER JOIN은 주문 없는 회원을 빼 버립니다.

? "주문 건수가 5건 이상인 고객"처럼 Group으로 묶은 결과를 거르는 조건은 어디에 쓰나요?
- WHERE
- ORDER BY
- LIMIT
- HAVING
= D
! WHERE는 Group으로 묶기 전 개별 Row를, HAVING은 GROUP BY로 묶은 뒤의 Group을 거릅니다.

? 학생 Table에 학번 → 학과, 학과 → 학과장 종속이 있어 학과장이 중복됩니다. 이를 없애는 Normal Form은?
- 1NF
- 2NF
- 3NF
- 4NF
= C
! Key가 아닌 Column(학과)이 다른 Key가 아닌 Column(학과장)을 결정하는 Transitive Dependency를 없애는 것이 3NF입니다.

? 다른 Transaction이 아직 Commit하지 않은 값을 읽었는데 그 Transaction이 Rollback되었습니다. 이 현상은?
- Dirty Read
- Phantom Read
- Non-Repeatable Read
- Deadlock
= A
! Commit되지 않은 데이터를 읽는 것이 Dirty Read이며, Read Committed 이상에서 막힙니다.

? name Column에 B+Tree Index가 있을 때, Index를 효율적으로 쓰기 가장 어려운 조건은?
- name = 'kim'
- name LIKE 'kim%'
- name BETWEEN 'a' AND 'k'
- name LIKE '%kim'
= D
! B+Tree는 앞부분부터 정렬되어 있어 앞에 %가 붙으면 시작 위치를 정할 수 없습니다. 'kim%'처럼 앞부분이 고정되면 범위 검색으로 Index를 씁니다.

? 로그인 Query에 사용자 입력을 문자열로 이어 붙이고 있습니다. 가장 근본적인 해결책은?
- Prepared Statement로 값을 Binding
- 비밀번호 길이 제한
- HTTPS 적용
- Index 추가
= A
! 입력을 SQL 문장과 분리해 값으로만 전달하면 입력이 Query 구조를 바꿀 수 없습니다. HTTPS는 전송 구간을 암호화할 뿐 Injection을 막지 못합니다.

? Network Partition이 생겼을 때 "잠깐 옛 데이터가 보여도 계속 응답한다"를 고른 시스템은 CAP에서 무엇을 우선했나요?
- Consistency (C)
- Partition Tolerance만 포기
- Availability (A)
- 세 가지 모두
= C
! Partition 중에도 응답을 계속하는 쪽은 Availability(AP)를 고른 것이고, 대신 Node 사이 데이터가 잠시 다를 수 있습니다.
