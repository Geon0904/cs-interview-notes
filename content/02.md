@intro Computer Architecture는 코드 한 줄이 실제 기계 안에서 어떻게 실행되는지를 다룹니다. 컴퓨터를 **식당 주방**으로 보면 쉬워요. CPU는 요리사, Register는 요리사 손, Cache는 조리대, Memory(RAM)는 냉장고, Storage(SSD)는 지하 창고입니다.
@one 컴퓨터는 Memory에 담긴 명령(Instruction)을 CPU가 하나씩 가져와 실행하고, 느린 Memory를 기다리는 시간을 줄이려고 빠르고 작은 Cache부터 느리고 큰 Disk까지 Memory Hierarchy를 두고 있습니다.

## 컴퓨터의 구성

#### 컴퓨터를 이루는 4가지: CPU · Memory · Storage · Bus
ONE: 컴퓨터는 **계산하는 CPU**, **잠깐 기억하는 Memory**, **오래 보관하는 Storage**, 그리고 이 셋을 잇는 **Bus**로 이루어져 있어요.
LIKE: 식당 주방을 떠올려 보세요. 요리사(CPU)가 요리를 하고, 오늘 쓸 재료는 냉장고(Memory)에, 오래 둘 재료는 지하 창고(Storage)에 있어요. 재료를 나르는 복도가 Bus예요.
STEP:
1. **CPU (Central Processing Unit)**: 실제로 계산하고 판단하는 부품이에요. "3 더하기 5", "이 값이 10보다 큰가?" 같은 아주 작은 일을 1초에 수십억 번 해요.
2. **Memory (RAM)**: CPU가 지금 쓰는 프로그램과 데이터를 올려 두는 작업대예요. 빠르지만 전원이 꺼지면 내용이 모두 사라져요. 이런 성질을 **Volatile(휘발성)**이라고 해요.
3. **Storage (SSD·HDD)**: 사진, 게임, 문서 파일을 오래 보관하는 창고예요. 전원이 꺼져도 남아 있어요(**Non-Volatile, 비휘발성**). 대신 RAM보다 훨씬 느려요.
4. **Bus**: 부품 사이로 신호를 나르는 길이에요. "어디로"(Address), "무엇을"(Data), "읽을지 쓸지"(Control)를 실어 날라요.
5. 게임을 실행하면 이렇게 움직여요: Storage에 있던 게임 파일이 → RAM으로 올라오고 → CPU가 RAM에서 명령을 하나씩 가져와 실행해요.
WHY: 빠른 저장 장치는 비싸고 작고, 큰 저장 장치는 싸지만 느려요. 부품 하나로 "빠르고, 크고, 싸고, 꺼져도 남는" 것을 모두 만들 수는 없어서 역할을 나눴어요.
USE: 휴대폰, 노트북, 서버, 게임기 모두 같은 구조예요. "RAM이 부족해서 느리다", "SSD로 바꾸니 부팅이 빨라졌다" 같은 말이 모두 이 구조에서 나와요.
KEY: RAM은 **작업대**, Storage는 **창고**예요. 프로그램은 창고에서 작업대로 옮겨져야 실행될 수 있어요.
END: 컴퓨터 = 계산(CPU) + 잠깐 기억(RAM) + 오래 보관(Storage) + 연결 통로(Bus). 이 넷의 속도 차이가 컴퓨터 구조 전체를 이해하는 출발점이에요.

#### Von Neumann Architecture (프로그램 내장 방식)
ONE: 프로그램(명령)도 데이터처럼 Memory에 넣어 두고, CPU가 거기서 명령을 하나씩 꺼내 실행하는 방식이에요.
LIKE: 요리법 종이와 재료를 같은 냉장고에 넣어 두는 주방이에요. 요리법 종이만 바꿔 넣으면 같은 주방에서 김밥도, 라면도 만들 수 있어요.
STEP:
1. 아주 초기의 컴퓨터(예: ENIAC)는 하는 일을 바꾸려면 사람이 케이블과 스위치를 직접 다시 연결해야 했어요.
2. 그래서 나온 생각이 "명령도 숫자로 바꿔서 Memory에 저장하자"예요. 이것을 **Stored-Program(프로그램 내장)** 방식이라고 해요.
3. 이제 CPU는 Memory에서 명령을 가져와 → 해석하고 → 실행하고 → 다음 명령을 가져오는 일만 반복하면 돼요.
4. 다른 일을 시키고 싶으면 다른 프로그램을 Memory에 올리기만 하면 돼요. 그래서 컴퓨터 한 대로 게임도, 문서 작업도 할 수 있어요.
WHY: 하드웨어를 바꾸지 않고 소프트웨어만 바꿔서 무엇이든 시킬 수 있게 하려고요. 오늘날 "앱을 설치한다"는 개념 자체가 이 아이디어 덕분이에요.
USE: 거의 모든 일반 컴퓨터(PC, 휴대폰, 서버)가 이 방식을 바탕으로 해요.
PRO: 하나의 기계로 어떤 프로그램이든 실행할 수 있고, 구조가 단순해요.
CON: 명령과 데이터가 같은 통로(Bus)로 Memory를 오가요. CPU는 매우 빠른데 Memory는 상대적으로 느려서, CPU가 Memory를 기다리느라 노는 시간이 생겨요. 이것을 **Von Neumann Bottleneck(병목)**이라고 해요.
KEY: 이 병목을 줄이려고 CPU 가까이에 작고 빠른 **Cache**를 두고, CPU에 가장 가까운 L1 Cache는 명령용과 데이터용으로 따로 나누기도 해요.
END: "프로그램도 데이터다"라는 아이디어가 오늘날 컴퓨터의 출발점이고, 그 대가인 병목을 줄이려는 노력이 Cache와 Memory Hierarchy로 이어져요.

### Von Neumann Architecture(폰 노이만 구조)란?
E: 요리법(Program)과 재료(Data)를 같은 냉장고(Memory)에 넣어 두고, 요리사(CPU)가 요리법을 한 줄씩 꺼내 읽으며 요리하는 방식입니다. 요리법만 바꾸면 같은 주방에서 다른 요리를 만들 수 있습니다.
A: Von Neumann Architecture는 Program(Instruction)과 Data를 같은 Memory에 저장하고 CPU가 순서대로 Instruction을 가져와 실행하는 Stored-Program(프로그램 내장) 방식입니다. Instruction과 Data가 같은 통로(Bus)를 쓰기 때문에 Memory 속도가 전체 속도를 제한하는 "Von Neumann Bottleneck"이 생깁니다.

### CPU·Memory·Storage·Bus의 역할은?
E: CPU는 요리사, Memory는 지금 쓸 재료를 두는 냉장고(전원을 끄면 비워짐), Storage는 오래 보관하는 창고(전원을 꺼도 남음), Bus는 재료를 나르는 복도입니다.
A: CPU는 Instruction을 해석하고 계산하며, Memory(RAM)는 실행 중인 Program과 Data를 담는 Volatile(휘발성) 저장소입니다. Storage(SSD·HDD)는 전원이 꺼져도 남는 Non-Volatile(비휘발성) 저장소이고, Bus는 이들 사이에서 Address·Data·Control 신호를 전달합니다.

## CPU 동작 원리

#### CPU 안의 부품: Register · ALU · Control Unit · Program Counter
ONE: CPU 안에는 값을 잠깐 쥐는 **Register**, 계산하는 **ALU**, 지휘하는 **Control Unit**, 다음 할 일을 가리키는 **Program Counter**가 있어요.
LIKE: 요리사의 몸으로 생각해 보세요. 손(Register)에 재료를 쥐고, 칼과 도마(ALU)로 손질하고, 머리(Control Unit)가 순서를 지휘하고, 손가락(Program Counter)이 요리법의 "지금 읽을 줄"을 짚고 있어요.
STEP:
1. **Register**: CPU 안의 아주 작은 저장 칸이에요. x86-64 CPU에는 일반 용도 Register가 16개 있고, 각각 64 Bit(8 Byte) 값을 담아요. 컴퓨터에서 가장 빠른 저장 공간이에요.
2. **ALU (Arithmetic Logic Unit)**: 덧셈·뺄셈 같은 산술 연산과 AND·OR·크기 비교 같은 논리 연산을 하는 계산기예요.
3. **Control Unit (제어 장치)**: 명령을 읽고 "이건 덧셈이니 ALU는 더하고, 결과는 이 Register에 넣어"처럼 각 부품에 신호를 보내요.
4. **Program Counter (PC)**: 다음에 실행할 명령이 Memory 어디(Address)에 있는지 적어 둔 특별한 Register예요. x86-64에서는 `rip`이라고 불러요.
WHY: CPU는 Memory보다 훨씬 빨라서, 계산할 값을 매번 Memory에서 가져오면 너무 느려요. 그래서 지금 계산할 값은 CPU 안의 Register에 두고 바로 써요.
KEY: 계산은 보통 "Memory에서 Register로 가져오기 → ALU로 계산 → 결과를 Register에 두기 → 필요하면 Memory에 저장" 순서로 일어나요.
END: Register는 손, ALU는 도구, Control Unit은 지휘자, PC는 책갈피예요. 이 넷이 함께 명령 하나를 처리해요.

#### Instruction Cycle (Fetch → Decode → Execute)
ONE: CPU는 명령을 **가져오고(Fetch) → 해석하고(Decode) → 실행하는(Execute)** 일을 쉬지 않고 반복해요.
LIKE: 요리법을 따라 요리할 때 ① 다음 줄을 읽고 ② "양파를 썰라는 뜻이구나" 이해하고 ③ 실제로 써는 것과 같아요. 그리고 다시 ①로 돌아가요.
STEP:
1. **Fetch**: PC가 가리키는 Address에서 명령을 가져와요.
2. PC는 바로 다음 명령을 가리키도록 앞으로 이동해요.
3. **Decode**: Control Unit이 "무슨 명령이지? 어떤 값이 필요하지?"를 해석해요.
4. **Execute**: ALU가 계산하거나, Memory에서 값을 읽거나 쓰거나, 다른 위치로 이동해요.
5. 결과를 Register(또는 Memory)에 기록하고, 다시 1번으로 돌아가요.
6. `if`나 반복문처럼 흐름을 바꾸는 **Branch(분기) 명령**은 PC 값을 다른 Address로 바꿔서 "바로 다음 줄"이 아닌 곳으로 이동시켜요.
WHY: 아무리 복잡한 프로그램도 결국 이 단순한 사이클의 반복이에요. 이걸 알면 "CPU가 빠르다 = 이 사이클을 1초에 아주 많이 돈다"는 뜻이 이해돼요.
USE: CPU 성능을 말할 때 쓰는 **Clock(클럭)**, 예를 들어 3 GHz는 1초에 30억 번 박자를 맞춘다는 뜻이에요. 명령 하나가 몇 박자에 끝나는지는 명령과 CPU마다 달라요.
END: CPU의 일은 "가져오기 → 해석 → 실행"의 끝없는 반복이고, PC가 그 순서를 이끌어요.

#### Pipelining과 Hazard
ONE: 명령 처리를 여러 단계로 나누고 여러 명령을 **겹쳐서** 처리해, 같은 시간에 더 많은 명령을 끝내는 기술이에요.
LIKE: 빨래 바구니 3개를 처리한다고 해 봐요. 한 바구니를 세탁·건조·개기까지 다 끝내고 다음 바구니를 시작하면 오래 걸려요. 첫 바구니를 건조기에 넣는 순간 두 번째 바구니를 세탁기에 넣으면 기계들이 쉬지 않아 전체가 빨라져요.
STEP:
1. 명령 처리를 예를 들어 5단계(Fetch · Decode · Execute · Memory 접근 · Write-back)로 나눠요.
2. 명령 1이 Decode 단계로 넘어가면, 비어 있는 Fetch 단계에서는 명령 2를 가져와요.
3. 이렇게 하면 단계마다 서로 다른 명령이 동시에 들어 있어서, 이상적으로는 매 박자마다 명령이 하나씩 끝나요.
4. 중요한 점: 명령 **하나**가 처음부터 끝까지 걸리는 시간(**Latency**)은 줄지 않아요. 늘어나는 건 **단위 시간당 끝나는 명령 수(Throughput)**예요.
5. 그런데 겹쳐서 처리하다 보면 다음 명령을 바로 진행할 수 없는 상황이 생겨요. 이것을 **Hazard**라고 해요.
| Hazard 종류 | 무슨 일이 생기나 | 해결 방법 |
| Structural | 두 명령이 같은 부품을 동시에 쓰려고 함 | 부품을 늘리거나 차례를 기다림 |
| Data | 앞 명령의 결과가 아직 안 나왔는데 다음 명령이 그 값이 필요함 | Forwarding(결과를 바로 넘겨줌), Stall(잠깐 멈춤) |
| Control | Branch 결과를 알기 전에는 다음에 어떤 명령을 가져올지 모름 | Branch Prediction(분기 예측) |
WHY: 부품들이 놀지 않게 해서 같은 시간에 더 많은 일을 하려고요. 현대 CPU는 모두 Pipelining을 써요.
PRO: Throughput이 크게 올라가요.
CON: Hazard 때문에 기다리는 시간(Stall)이 생기고, 분기 예측이 틀리면 미리 가져온 명령을 버려야 해서 손해가 나요.
END: Pipelining은 "명령 하나를 빨리"가 아니라 "여러 명령을 겹쳐서 많이" 처리하는 기술이에요.

#### CISC vs RISC
ONE: 복잡하고 다양한 명령을 많이 가진 설계가 **CISC**, 단순하고 크기가 일정한 명령 위주로 만든 설계가 **RISC**예요.
LIKE: CISC는 "김치찌개 만들어"라는 큰 주문 하나를 알아듣는 요리사, RISC는 "썰어", "넣어", "끓여"처럼 짧은 주문만 받지만 그걸 아주 빠르고 규칙적으로 처리하는 요리사예요.
STEP:
1. CPU가 알아듣는 명령의 목록을 **ISA (Instruction Set Architecture, 명령어 집합)**라고 해요. CPU와 소프트웨어 사이의 약속이에요.
2. **CISC (Complex Instruction Set Computer)**: 명령 하나가 많은 일을 하고, 명령마다 길이가 달라요. 대표: Intel·AMD의 **x86**.
3. **RISC (Reduced Instruction Set Computer)**: 명령이 단순하고 길이가 대부분 일정해요. Memory는 Load(읽기)·Store(쓰기) 명령으로만 다루고, 계산은 Register끼리 해요. 대표: **ARM**, **RISC-V**.
4. 명령이 단순하고 규칙적이면 Pipelining이 쉬워지고 회로가 단순해져서 전력을 덜 써요.
5. 오늘날에는 경계가 흐려졌어요. 최신 x86도 내부에서는 복잡한 명령을 단순한 **Micro-op**으로 쪼개서 실행해요.
| 구분 | CISC (x86) | RISC (ARM) |
| 명령 | 복잡·다양, 길이 제각각 | 단순, 길이 대부분 일정 |
| 강점 | 오랫동안 쌓인 소프트웨어 호환성 | 전력 대비 성능(Performance per Watt) |
| 주 사용처 | 많은 PC·서버 | 휴대폰, 태블릿, Apple M 시리즈 Mac |
WHY: 같은 일을 "큰 명령 적게"로 할지 "작은 명령 많이"로 할지에 따라 회로의 복잡도, 속도, 전력 소비가 달라지기 때문이에요.
END: 둘 다 같은 프로그램을 실행할 수 있어요. 차이는 명령을 크게 줄지 작게 줄지이고, 전력이 중요한 곳에서 RISC(ARM)가 강해요.

### Instruction Cycle(Fetch → Decode → Execute)이란?
E: 요리사가 ① 요리법에서 다음 줄을 읽고(Fetch), ② "양파를 썰라"는 뜻을 이해하고(Decode), ③ 실제로 써는(Execute) 일을 끝없이 반복합니다. "다음에 읽을 줄"을 손가락으로 짚고 있는 것이 Program Counter입니다.
A: CPU는 Program Counter(PC)가 가리키는 Address에서 Instruction을 가져오고(Fetch), 어떤 연산인지 해석하고(Decode), ALU 등으로 실행한 뒤(Execute) 결과를 Register나 Memory에 씁니다. PC는 다음 Instruction을 가리키도록 증가하고, Branch Instruction이면 다른 Address로 바뀝니다.

### Register, ALU, Control Unit, Program Counter란?
| 부품 | 비유 | 역할 |
| Register | 요리사의 손 | CPU 안의 가장 빠르고 작은 저장 공간 |
| ALU (Arithmetic Logic Unit) | 칼과 도마 | 덧셈·비교·논리 연산을 수행 |
| Control Unit (제어 장치) | 주방장 | Instruction을 해석해 각 부품에 신호를 보냄 |
| Program Counter (PC) | 요리법을 짚는 손가락 | 다음에 실행할 Instruction의 Address를 저장 |
A: Register는 CPU 내부의 초고속 저장소, ALU는 산술·논리 연산기, Control Unit은 Instruction을 해석해 흐름을 지휘하는 부분입니다. PC는 다음 Instruction의 Address를 담는 Register로, x86-64에서는 rip이라고 부릅니다.

### Pipelining과 Hazard란?
E: 빨래방에서 세탁·건조·개기를 한 바구니씩 끝내고 다음 바구니를 시작하면 느립니다. 첫 바구니를 말리는 동안 두 번째를 빨면 전체가 빨라집니다. 다만 "이 빨래가 끝나야 다음 것을 정할 수 있다"는 상황이면 기다려야 하는데, 이것이 Hazard입니다.
A: Pipelining은 Instruction 처리를 여러 단계(예: Fetch·Decode·Execute·Memory·Write-back)로 나눠 여러 Instruction을 겹쳐 실행해 Throughput(처리량)을 높입니다. Instruction 하나의 실행 시간(Latency) 자체는 줄지 않습니다. Hazard는 Structural Hazard(자원 충돌), Data Hazard(앞 Instruction의 결과가 필요), Control Hazard(Branch)가 있고, Forwarding·Stall·Branch Prediction으로 완화합니다.

### CISC vs RISC, ARM이 Mobile에서 강한 이유는?
E: CISC는 "김치찌개 만들기" 같은 큰 명령을 한 번에 받는 요리사, RISC는 "썰기·넣기·끓이기"처럼 작고 단순한 명령만 받아 빠르게 처리하는 요리사입니다.
A: CISC(x86)는 길이가 제각각인 복잡한 Instruction을 많이 갖고, RISC(ARM, RISC-V)는 고정 길이의 단순한 Instruction과 Load/Store 구조를 씁니다. ARM은 단순한 구조 덕분에 전력 대비 성능(Performance per Watt)이 좋아 휴대폰과 노트북에 널리 쓰입니다. 참고로 최신 x86도 내부에서는 Instruction을 단순한 Micro-op(마이크로 연산)으로 쪼개 실행합니다.

## Data Representation (데이터 표현)

#### Bit와 Byte: 모든 것은 0과 1
ONE: 컴퓨터는 숫자, 글자, 사진, 소리까지 모든 정보를 **0과 1**로 저장해요. 0 또는 1 하나를 **Bit**, Bit 8개 묶음을 **Byte**라고 해요.
LIKE: 전등 스위치를 생각해 보세요. 켜짐(1)과 꺼짐(0) 두 가지뿐이지만, 스위치 8개를 나란히 두면 켜고 끄는 조합이 256가지가 돼요. 조합마다 번호나 뜻을 정해 두면 무엇이든 표현할 수 있어요.
STEP:
1. **왜 0과 1일까?** 전기 회로는 "전압이 높다/낮다"처럼 두 상태를 구분하는 게 가장 확실하고 싸게 만들 수 있어요.
2. **Bit 1개** = 2가지(0, 1). **Bit 2개** = 4가지(00, 01, 10, 11). Bit가 하나 늘 때마다 경우의 수가 2배가 돼요.
3. **Byte (8 Bit)** = 2⁸ = **256가지**예요. 0부터 255까지의 숫자를 담을 수 있어요.
4. **숫자**는 2진법(Binary)으로 써요. 10진법이 1·10·100의 자리라면, 2진법은 1·2·4·8의 자리예요. 예: 13 = 8 + 4 + 1이니까 `1101`.
5. **글자**는 글자마다 번호를 정한 표를 써요. **ASCII**는 영어 알파벳·숫자·기호 128개에 번호를 붙였어요(예: 'A' = 65). **Unicode**는 한글·한자·이모지까지 전 세계 글자에 번호를 붙였어요(예: '가' = U+AC00). 이 번호를 Byte로 저장하는 가장 흔한 방법이 **UTF-8**이고, 한글 한 글자는 UTF-8에서 3 Byte예요.
6. **색**은 빨강(R)·초록(G)·파랑(B) 빛의 세기를 각각 0~255로 정해요. (255, 0, 0)은 빨강, (255, 255, 255)는 흰색이에요. 이렇게 하면 256 × 256 × 256 = 약 1,677만 가지 색을 만들 수 있어요.
7. **사진**은 색 점(**Pixel**)을 바둑판처럼 늘어놓은 것이고, **영상**은 사진을 1초에 수십 장씩 빠르게 넘기는 거예요.
KEY: 같은 Bit 묶음도 **어떻게 해석하느냐**에 따라 뜻이 달라져요. `01000001`을 숫자로 읽으면 65, ASCII 글자로 읽으면 'A'예요. 그래서 파일 형식(.txt, .png, .mp3)이 "이 Bit들을 이렇게 읽어라"라는 약속 역할을 해요.
USE: 파일 크기(KB, MB, GB), 인터넷 속도(Mbps = 1초에 수백만 Bit), 글자가 깨지는 현상(저장할 때와 읽을 때 Encoding이 다를 때) 모두 이 개념에서 나와요.
END: 컴퓨터 속 모든 것은 0과 1이고, 그 0과 1에 "어떤 뜻을 붙일지 정한 약속"이 숫자·글자·색·소리를 만들어요.

#### 정수의 한계: Integer Overflow
ONE: 정수를 담는 칸의 크기(Bit 수)가 정해져 있어서, 담을 수 있는 가장 큰 수를 넘으면 값이 엉뚱하게 바뀌는 현상이에요.
LIKE: 자동차 주행 거리계가 999999km에서 1km를 더 가면 000000으로 돌아가는 것과 같아요. 숫자 칸이 6개뿐이라 7번째 자리를 담을 곳이 없거든요.
STEP:
1. C 같은 언어에서 `int`는 보통 **32 Bit**예요. 32 Bit로 만들 수 있는 조합은 2³² = 약 43억 가지예요.
2. 음수도 담아야 하니 절반은 음수, 나머지 절반은 0과 양수에 써요. 그래서 범위는 **-2,147,483,648 ~ 2,147,483,647 (약 ±21억)**이에요.
3. 2,147,483,647에 1을 더하면? 일반적인 컴퓨터에서는 반대쪽 끝인 **-2,147,483,648**이 나와요. 거리계가 한 바퀴 도는 것과 같아요.
4. 주의할 점: C 언어 규칙에서 부호 있는 정수(signed int)의 Overflow는 **Undefined Behavior(정의되지 않은 동작)**라서 결과를 믿고 쓰면 안 돼요. 부호 없는 정수(unsigned)는 0으로 돌아가는 동작이 규칙으로 정해져 있어요.
5. **Python**의 정수는 필요한 만큼 자동으로 커져서 이런 Overflow가 생기지 않아요. 대신 그만큼 느리고 Memory를 더 써요.
WHY: 돈, 시간, 조회 수처럼 계속 커지는 숫자를 다룰 때 Overflow는 실제 사고로 이어져요.
USE: 2014년 12월, '강남스타일'의 조회 수가 32 Bit signed 정수의 최댓값(2,147,483,647)에 이르자 YouTube는 조회 수 저장을 64 Bit 정수로 바꿨어요. 또 1970년부터 흐른 초를 32 Bit signed 정수로 저장하는 시스템은 2038년 1월 19일에 한계를 넘어요(**Year 2038 Problem**). 그래서 요즘은 시간을 64 Bit로 저장해요.
KEY: 큰 수가 나올 수 있으면 처음부터 64 Bit 정수(C의 `long long`, `int64_t`)를 쓰고, 계산 전에 범위를 확인해요.
END: 컴퓨터의 정수는 "칸 수가 정해진 계산기"예요. 칸을 넘치면 값이 틀어지므로 범위를 미리 생각해야 해요.

#### Floating-Point (부동 소수점)와 0.1 + 0.2
ONE: 소수를 "숫자 × 2의 거듭제곱" 꼴로 저장하는 방식이에요. 아주 큰 수와 아주 작은 수를 모두 담을 수 있지만, 대부분의 소수는 **근삿값**으로 저장돼요.
LIKE: 과학 시간에 쓰는 표기법 6.02 × 10²³을 떠올려 보세요. 숫자 부분(6.02)과 소수점을 몇 자리 옮길지(23)만 적으면 엄청 큰 수도 짧게 쓸 수 있어요. 대신 숫자 부분의 칸 수가 정해져 있어서 끝자리는 반올림돼요.
STEP:
1. **Fixed-Point(고정 소수점)**: "소수점 아래는 무조건 2자리"처럼 소수점 자리를 고정해요. 단순하지만 담을 수 있는 범위가 좁아요.
2. **Floating-Point(부동 소수점)**: 소수점 위치를 옮길 수 있게(float = 떠다니는) 만든 방식이에요. 표준 규칙의 이름은 **IEEE 754**예요.
3. 세 부분으로 나눠 저장해요: **Sign**(부호, + 또는 −), **Exponent**(지수, 소수점을 몇 칸 옮길지), **Mantissa**(가수, 실제 숫자들). 64 Bit `double`은 1 + 11 + 52 Bit로 나눠 써요.
4. 문제는 여기서 생겨요. 10진법에서 1/3 = 0.3333…이 끝없이 이어지듯, **2진법에서는 0.1이 끝없이 이어지는 소수**예요. Mantissa 칸이 52개뿐이니 어딘가에서 잘라 반올림해야 해요.
5. 그래서 0.1도 0.2도 "아주 살짝 다른 값"으로 저장되고, 둘을 더하면 `0.30000000000000004`가 나와요. 결국 `0.1 + 0.2 == 0.3`은 `False`예요.
6. 이건 Bug가 아니라 IEEE 754의 정상 동작이고, Python·JavaScript·Java 모두 똑같아요.
KEY:
- 실수끼리는 `==` 대신 "충분히 가까운가"로 비교해요. Python에서는 `math.isclose(a, b)`를 써요.
- 돈 계산은 소수 대신 정수(원·센트 단위)나 `decimal` 같은 10진 소수 타입을 써요.
PRO: 아주 큰 수부터 아주 작은 수까지 넓은 범위를 적은 Bit로 표현하고, 하드웨어가 빠르게 계산해 줘요.
CON: 대부분의 소수가 근삿값이라 작은 오차가 생기고, 계산을 반복하면 오차가 쌓일 수 있어요.
END: Floating-Point는 "넓은 범위를 얻는 대신 정확함을 조금 포기한" 표현이에요. 그래서 비교할 땐 오차를 허용하고, 돈은 정수로 다뤄요.

#### Endian (Byte를 놓는 순서)
ONE: 여러 Byte로 된 숫자를 Memory에 **어느 쪽 Byte부터** 놓을지 정한 순서예요.
LIKE: 날짜를 "2026-10-23"(큰 단위부터)으로 쓰는 곳과 "23-10-2026"(작은 단위부터)으로 쓰는 곳이 있는 것과 같아요. 같은 날짜라도 순서를 모르면 잘못 읽어요.
STEP:
1. 숫자 `0x12345678`은 4 Byte예요: `12`, `34`, `56`, `78`. 여기서 `12`가 가장 큰 자리, `78`이 가장 작은 자리예요.
2. Memory는 번호(Address)가 붙은 칸이 일렬로 늘어선 모양이라, 이 4 Byte를 4칸에 차례로 넣어야 해요.
3. **Big Endian**: 큰 자리부터 넣어요 → `12 34 56 78`. 사람이 읽는 순서와 같아요.
4. **Little Endian**: 작은 자리부터 넣어요 → `78 56 34 12`.
5. Intel·AMD의 x86 CPU는 Little Endian이고, 네트워크로 데이터를 보낼 때는 Big Endian을 표준으로 써요(**Network Byte Order**).
WHY: 서로 다른 순서를 쓰는 기계끼리 데이터를 주고받거나 파일을 Byte 단위로 읽을 때, 순서를 맞추지 않으면 숫자가 완전히 다른 값으로 읽혀요.
USE: 네트워크 프로그래밍(`htonl` 같은 변환 함수), 파일 형식 분석, 이미지·오디오 파일의 Header 읽기에서 꼭 따져야 해요.
END: Endian은 "Byte를 어느 끝부터 놓을지"에 대한 약속이고, 다른 약속을 쓰는 곳끼리는 반드시 변환해야 해요.

#### Parity Bit와 Hamming Code (오류 찾기·고치기)
ONE: 데이터에 검사용 Bit를 덧붙여서, 저장이나 전송 중에 Bit가 뒤집혔는지 **알아내거나(Parity)**, 어디가 틀렸는지 찾아 **고치는(Hamming Code)** 방법이에요.
LIKE: 친구에게 사과 상자를 보내면서 "사과 개수는 짝수야"라는 쪽지를 붙이는 게 Parity예요. 받은 사람이 세어 보고 홀수면 "뭔가 잘못됐다"는 걸 알아요. Hamming Code는 이런 쪽지를 여러 장, 서로 다른 칸 묶음마다 붙여서 "몇 번 칸이 틀렸는지"까지 알아내는 방법이에요.
STEP:
1. 전기 잡음이나 우주에서 날아온 입자 때문에 Memory나 전선 속 Bit가 가끔 0↔1로 뒤집혀요.
2. **Even Parity(짝수 Parity)**: 데이터 속 1의 개수가 짝수가 되도록 Bit 하나를 덧붙여요. 예: `1011`은 1이 3개(홀수)라서 Parity Bit 1을 붙여 `1011` + `1`로 보내요.
3. 받는 쪽은 1의 개수를 세어 홀수면 오류가 있다는 걸 알아요.
4. 한계: Bit 2개가 동시에 뒤집히면 다시 짝수가 돼서 알아채지 못해요. 그리고 **어느** Bit가 틀렸는지 몰라서 고칠 수도 없어요.
5. **Hamming Code**: Parity Bit 여러 개가 각각 다른 위치 묶음을 검사하게 배치해요. 어떤 검사들이 실패했는지 조합을 보면 틀린 Bit의 위치가 나오고, 그 Bit를 뒤집어 고쳐요. 대표적인 **Hamming(7,4)**는 Data 4 Bit에 Parity 3 Bit를 붙여 7 Bit로 보내고, 1 Bit 오류를 고칠 수 있어요.
USE: 서버용 **ECC Memory**는 Hamming 계열의 코드로 Bit 오류를 자동으로 고쳐요. QR 코드가 조금 가려져도 읽히는 것도 오류 정정 코드 덕분이에요(QR은 Reed-Solomon이라는 다른 방식을 써요).
PRO: Parity는 Bit 하나만 더하면 되니 아주 싸요. Hamming Code는 오류를 고칠 수까지 있어요.
CON: Parity는 오류가 있다는 것만 알고 고치지 못해요. Hamming Code는 검사용 Bit가 더 많이 필요해요.
END: 덧붙인 몇 Bit로 "틀렸는지"를 알면 Detection(감지), "어디가 틀렸는지"까지 알면 Correction(정정)이에요.

### Bit와 Byte란? 컴퓨터는 글자와 색을 어떻게 0과 1로 저장하나요?
E: 스위치 8개를 켜고 끄는 조합은 256가지입니다. 조합마다 "65번은 A", "이 조합은 빨강"처럼 뜻을 정해 두면 무엇이든 0과 1로 적을 수 있습니다.
A: Bit는 0 또는 1을 담는 정보의 최소 단위이고, 8 Bit가 1 Byte로 256가지 값을 표현합니다. 숫자는 2진법으로, 글자는 ASCII나 Unicode 같은 번호표(Encoding, 예: UTF-8)로, 색은 R·G·B 세기의 조합으로, 이미지는 Pixel의 격자로 저장합니다. 같은 Bit라도 해석 규칙에 따라 숫자도 글자도 될 수 있습니다.

### Integer Overflow란?
E: 주행 거리계가 999999에서 한 칸 더 가면 000000이 되는 것처럼, 정수 칸이 담을 수 있는 최댓값을 넘으면 값이 엉뚱하게 바뀝니다.
A: 고정된 Bit 수로 정수를 저장하기 때문에 표현 범위를 넘는 결과가 나오면 생기는 현상입니다. 32 Bit signed int의 범위는 약 ±21억(-2,147,483,648 ~ 2,147,483,647)이고, 최댓값에 1을 더하면 보통 최솟값으로 넘어갑니다. C에서 signed Overflow는 Undefined Behavior이므로 64 Bit 타입을 쓰거나 계산 전에 범위를 검사합니다. Python 정수는 임의 정밀도라 Overflow가 없습니다.

### Fixed-Point와 Floating-Point의 차이는?
E: Fixed-Point(고정 소수점)는 "소수점 아래 두 자리"처럼 자리를 못 박은 가격표이고, Floating-Point(부동 소수점)는 6.02 × 10²³처럼 "숫자 × 거듭제곱"으로 소수점을 옮겨 아주 큰 수와 아주 작은 수를 모두 담는 과학 표기법입니다.
A: Fixed-Point는 소수점 위치가 정해져 있어 범위는 좁지만 정밀도(Precision)가 일정합니다. Floating-Point(IEEE 754)는 Sign(부호)·Exponent(지수)·Mantissa(가수)로 수를 표현해 넓은 범위를 다루고, 64 Bit double은 Sign 1 Bit·Exponent 11 Bit·Mantissa 52 Bit입니다.

### 0.1 + 0.2 == 0.3이 False인 이유는?
E: Decimal로 1/3을 쓰면 0.3333…이 끝없이 이어져서 어딘가에서 잘라야 합니다. Binary에서는 0.1이 바로 그런 끝없는 소수입니다.
A: 0.1과 0.2는 Binary Floating-Point로 정확히 표현되지 않아 가장 가까운 값으로 반올림(Rounding)되고, 그 오차 때문에 합이 0.30000000000000004가 됩니다. 그래서 실수는 == 대신 `math.isclose()`로 비교하고, 돈 계산은 `decimal`이나 정수(원 단위)를 씁니다.

### Big Endian과 Little Endian이란?
E: 날짜를 2026-10-23(큰 단위부터)으로 쓸지, 23-10-2026(작은 단위부터)으로 쓸지의 차이입니다.
A: 여러 Byte로 된 값을 Memory에 놓는 순서로, Big Endian은 가장 큰 자리 Byte(MSB)를 낮은 Address에, Little Endian은 가장 작은 자리 Byte(LSB)를 낮은 Address에 둡니다. 0x12345678을 Little Endian으로 저장하면 78 56 34 12 순서이고, x86은 Little Endian, Network 전송(Network Byte Order)은 Big Endian을 씁니다.

### Parity Bit와 Hamming Code는 오류를 어떻게 찾고 고치나요?
E: Parity는 "박스 안 사과 개수는 짝수여야 한다"는 꼬리표입니다. 개수가 홀수면 무언가 잘못됐다는 것은 알지만 어느 사과가 문제인지는 모릅니다. Hamming Code는 꼬리표를 여러 장 겹쳐 붙여 어느 자리가 틀렸는지까지 짚습니다.
A: Parity Bit는 1의 개수를 짝수(또는 홀수)로 맞추는 Bit 하나로, 홀수 개의 Bit 오류를 감지(Detection)할 뿐 고치지는 못합니다. Hamming Code는 여러 Parity Bit를 서로 다른 위치 조합에 두어 1 Bit 오류의 위치를 찾아 고칩니다(Correction). 대표적인 Hamming(7,4)는 Data 4 Bit에 Parity 3 Bit를 붙입니다.

## Memory Hierarchy와 Cache

#### Memory Hierarchy (메모리 계층)
ONE: 빠르지만 작고 비싼 저장소부터 느리지만 크고 싼 저장소까지 **층층이 쌓아** 쓰는 구조예요.
LIKE: 요리사는 소금처럼 자주 쓰는 건 손 닿는 조리대에, 오늘 쓸 재료는 냉장고에, 나머지는 지하 창고에 둬요. 전부 조리대에 두면 좋겠지만 조리대는 작고 비싸요.
STEP:
1. 위에서 아래로 쌓인 순서: **Register → L1 Cache → L2 Cache → L3 Cache → RAM → SSD/HDD**.
2. 위로 갈수록 빠르고, 작고, 비싸요. 아래로 갈수록 느리고, 크고, 싸요.
3. CPU는 먼저 가장 가까운 L1에서 데이터를 찾아요. 있으면(**Cache Hit**) 바로 쓰고, 없으면(**Cache Miss**) 한 층 아래로 내려가 찾은 다음 위층에 복사해 둬요.
4. 프로그램은 쓰던 데이터를 또 쓰는 경향이 강해서(바로 다음에 배울 Locality), 대부분의 요청이 위층에서 해결돼요.
5. 그래서 거의 Cache만큼 빠르면서도, 용량은 RAM과 SSD만큼 쓰는 효과를 얻어요.
| 층 | 대략적인 접근 시간 | L1을 1초로 늘려 보면 |
| L1 Cache | 약 1ns | 1초 |
| RAM | 약 100ns | 약 1분 40초 |
| SSD | 수십~수백 µs | 수 시간 ~ 며칠 |
| HDD | 수 ms | 수 주 ~ 수 개월 |
WHY: 빠른 저장소만으로 큰 용량을 만들면 너무 비싸고, 싼 저장소만 쓰면 CPU가 계속 기다려야 해요. 계층 구조는 둘의 장점만 모으려는 타협이에요.
USE: CPU Cache뿐 아니라 웹 브라우저 Cache, CDN, Redis 같은 Cache Server도 똑같은 원리예요. "자주 쓰는 건 가까이에 둔다."
END: Memory Hierarchy는 "자주 쓰는 건 빠른 곳에, 나머지는 싼 곳에"라는 정리 정돈 규칙이에요.

#### Cache와 Locality (지역성)
ONE: 프로그램은 Memory를 골고루 쓰지 않고 **방금 쓴 것과 그 옆에 있는 것**을 또 쓰는 경향이 있어요. 이 성질이 Locality이고, Cache는 이걸 이용해요.
LIKE: 방금 쓴 소금은 곧 또 써요(시간). 소금 옆의 후추도 곧 쓸 가능성이 커요(공간). 그래서 요리사는 창고에 갈 때 소금 한 봉지가 아니라 양념 선반 한 칸을 통째로 가져와요.
STEP:
1. **Temporal Locality(시간 지역성)**: 최근에 쓴 데이터는 곧 다시 써요. 예: 반복문의 변수 `i`, 합계 변수 `sum`.
2. **Spatial Locality(공간 지역성)**: 방금 쓴 주소 근처를 곧 써요. 예: Array를 0번, 1번, 2번… 순서대로 읽기.
3. Cache는 데이터를 1 Byte씩이 아니라 **Cache Line**(x86에서 보통 64 Byte) 덩어리로 가져와요. Array의 0번을 읽으면 바로 옆 원소들도 함께 따라와요.
4. 그래서 Array를 순서대로 읽으면 두 번째 원소부터는 대부분 Cache Hit이에요.
5. 반대로 Memory를 여기저기 건너뛰며 읽으면 매번 새 덩어리를 가져와야 해서 느려져요.
KEY: 2차원 Array를 **행(Row) 순서**로 돌면 빠르고 **열(Column) 순서**로 돌면 느려요. C와 NumPy의 기본 Array는 한 행이 Memory에 연달아 놓이는 **Row-Major** 방식이라, 행 방향으로 읽어야 Spatial Locality를 살릴 수 있어요.
```c
// 빠름: 한 행을 옆으로 읽기 (Memory에서 연속)
for (i = 0; i < N; i++) for (j = 0; j < N; j++) sum += a[i][j];
// 느림: 열 방향으로 읽기 (Memory에서 N칸씩 건너뜀)
for (j = 0; j < N; j++) for (i = 0; i < N; i++) sum += a[i][j];
```
WHY: 같은 계산이라도 Memory를 읽는 순서만 바꿔서 몇 배 빨라질 수 있어요.
END: Cache는 "곧 다시 쓸 것과 옆에 있는 것"을 미리 가까이 가져오는 장치이고, Locality에 맞게 코드를 쓰면 공짜로 빨라져요.

#### Cache Mapping과 Cache Miss의 3가지 원인
ONE: Memory의 데이터가 Cache의 **어느 자리에 들어갈 수 있는지** 정한 규칙이 Mapping이고, 찾는 데이터가 Cache에 없는 경우가 Miss예요.
LIKE: 교실 자리 배치로 생각해 보세요. 출석번호 끝자리로 자리가 정해진 교실(Direct Mapped), 아무 데나 앉는 교실(Fully Associative), 분단은 번호로 정해지고 분단 안에서는 자유인 교실(Set Associative)이 있어요.
STEP:
1. Cache는 Memory보다 훨씬 작아서, 여러 Memory 주소가 같은 Cache 자리를 나눠 써야 해요.
2. **Direct Mapped**: 주소마다 갈 수 있는 자리가 딱 1곳이에요. 찾기는 쉽고 빠르지만, 같은 자리를 쓰는 두 데이터를 번갈아 쓰면 서로 계속 쫓아내요.
3. **Fully Associative**: 아무 자리에나 들어갈 수 있어요. 자리 다툼은 가장 적지만, 모든 자리를 한꺼번에 비교하는 회로가 비싸서 큰 Cache에는 쓰기 어려워요.
4. **n-way Set Associative**: 주소가 갈 Set(묶음)은 정해져 있고, 그 Set 안의 n개 자리 중 아무 곳에나 들어가요. 실제 CPU Cache는 대부분 이 방식이에요.
5. 자리가 꽉 차면 누군가를 내보내야 해요. 보통 가장 오래 안 쓴 것을 내보내요(**LRU, Least Recently Used** 또는 그 근사 방식).
| Miss 종류 (3C) | 원인 | 줄이는 방법 |
| Compulsory | 처음 접근해서 아직 Cache에 없음 | Prefetch(미리 가져오기), 더 큰 Cache Line |
| Capacity | 쓰는 데이터 전체가 Cache보다 큼 | Cache 키우기, 한 번에 다루는 데이터 줄이기 |
| Conflict | 자리 규칙 때문에 같은 자리를 두고 다툼 | Associativity(n) 늘리기 |
WHY: Mapping 방식에 따라 Cache를 찾는 속도와 Hit 비율이 달라지고, Miss의 원인을 알아야 무엇을 고칠지 정할 수 있어요.
END: Mapping은 "찾기 쉬움"과 "자리 다툼 적음" 사이의 타협이고, Miss는 처음이라서(Compulsory), 공간이 부족해서(Capacity), 자리 규칙 때문에(Conflict) 생겨요.

#### Write-Through vs Write-Back
ONE: Cache의 값을 바꿀 때 Memory에도 **바로 같이 쓸지(Write-Through)**, **나중에 한꺼번에 쓸지(Write-Back)** 정하는 방식이에요.
LIKE: 용돈 기입장을 쓸 때마다 엄마 장부에도 바로 옮겨 적으면 Write-Through, 내 메모장에 적어 두었다가 메모장을 정리할 때만 한 번에 옮기면 Write-Back이에요.
STEP:
1. CPU가 값을 바꾸면 먼저 Cache의 값이 바뀌어요. 이제 Cache와 Memory의 값이 달라질 수 있어요.
2. **Write-Through**: 쓸 때마다 Memory에도 즉시 써요. 두 곳이 항상 같아서 단순하지만, 매번 느린 Memory까지 가야 해요.
3. **Write-Back**: Cache에만 쓰고 "바뀌었음" 표시(**Dirty Bit**)를 해 둬요.
4. 그 Cache 자리를 다른 데이터에 내줘야 할 때(**Eviction**), Dirty 표시가 있으면 그때 Memory에 한 번 써요.
5. 같은 값을 여러 번 바꿔도 Memory에는 마지막에 한 번만 쓰니 훨씬 빨라요.
| 구분 | Write-Through | Write-Back |
| 쓰기 속도 | 느림 | 빠름 |
| 구현 | 단순 | 복잡 (Dirty Bit 관리) |
| Memory와 일치 | 항상 일치 | 잠시 다를 수 있음 |
USE: 대부분의 현대 CPU Cache는 Write-Back을 써요. 데이터베이스 앞에 Cache를 둘 때도 "바로 DB에 쓸까, 모았다가 쓸까"라는 똑같은 고민이 나와요.
END: 단순함과 일치가 중요하면 Write-Through, 속도가 중요하면 Write-Back이에요.

### Memory Hierarchy가 있는 이유는?
E: 요리사는 자주 쓰는 소금을 손 닿는 조리대에, 오늘 쓸 재료는 냉장고에, 나머지는 지하 창고에 둡니다. 전부 조리대에 두면 좋겠지만 조리대는 작고 비쌉니다.
A: 빠른 Memory는 비싸고 작고, 큰 Memory는 싸지만 느리기 때문에 Register → L1·L2·L3 Cache → RAM → SSD/HDD로 계층(Hierarchy)을 둡니다. 자주 쓰는 Data를 위 계층에 두면 대부분의 접근을 빠르게 처리하면서도 저렴한 큰 용량을 쓸 수 있습니다.
M: 대략적인 자릿수: L1 Cache 약 1ns, RAM 약 100ns, SSD 수십~수백 µs, HDD 수 ms. RAM은 L1보다 약 100배, HDD는 RAM보다 약 10만 배 느립니다.

### Cache의 Locality(지역성)에 대해 설명해 주세요.
E: Temporal Locality(시간 지역성)는 "방금 쓴 소금은 곧 또 쓴다", Spatial Locality(공간 지역성)는 "방금 쓴 소금 옆의 후추도 곧 쓴다"입니다. 그래서 요리사는 창고에 갈 때 양념 하나가 아니라 양념 선반 한 칸을 통째로 가져옵니다.
A: Locality는 Program이 Memory를 골고루가 아니라 몰아서 쓰는 성질입니다. Temporal Locality는 최근 접근한 Data를 곧 다시 쓰는 것(반복문 변수), Spatial Locality는 근처 Address를 곧 쓰는 것(Array 순회)입니다. Cache는 이를 이용해 Data를 Block(Cache Line, x86에서 보통 64 Byte) 단위로 가져옵니다.
M: 2차원 Array를 행(Row) 순서로 돌면 빠르고 열(Column) 순서로 돌면 느린 이유가 Spatial Locality입니다(C와 NumPy 기본 Array는 Row-Major 저장).

### Cache Mapping 방식과 Cache Miss의 3가지 종류는?
E: Direct Mapped는 "출석번호 끝자리로 자리가 정해진 교실", Fully Associative는 "아무 데나 앉는 교실", Set Associative는 "분단은 정해져 있고 분단 안에서는 자유"입니다.
A: Direct Mapped는 Block마다 들어갈 자리가 하나, Fully Associative는 어디든, n-way Set Associative는 정해진 Set의 n개 자리 중 하나입니다. Miss의 3C는 처음 접근해서 생기는 Compulsory, Cache가 작아서 생기는 Capacity, 같은 자리를 두고 다투는 Conflict입니다.

### Write-Through vs Write-Back은?
E: 가계부를 쓸 때마다 은행 앱에도 바로 입력하면 Write-Through, 메모지에 적어 두었다가 메모지를 버릴 때만 한 번에 옮기면 Write-Back입니다.
A: Write-Through는 Cache와 Memory에 동시에 써서 단순하고 일관성(Consistency)이 좋지만 쓰기가 느립니다. Write-Back은 Cache에만 쓰고 변경 표시(Dirty Bit)를 해 두었다가 Block이 밀려날 때(Eviction) Memory에 써서 빠르지만 구현이 복잡합니다.

## Assembly와 Function Call (x86-64)

#### Stack Frame과 call · ret
ONE: 함수를 부를 때마다 그 함수가 쓸 **임시 공간(Stack Frame)**을 Stack에 쌓고, 함수가 끝나면 치우고 원래 자리로 돌아가는 구조예요.
LIKE: 책을 읽다가 각주를 보러 갈 때 지금 페이지에 책갈피를 꽂아요. 각주를 읽다가 또 다른 각주로 가면 책갈피를 하나 더 꽂고요. 돌아올 때는 **가장 나중에 꽂은 책갈피부터** 빼면서 돌아와요. 이렇게 "나중에 넣은 것을 먼저 빼는" 구조가 Stack이에요.
STEP:
1. **Stack**은 접시 쌓기처럼 위에 쌓고 위에서 빼는(**LIFO, Last In First Out**) Memory 영역이에요.
2. `main`이 `f()`를 부르면, CPU의 `call` 명령이 **돌아올 주소(Return Address)**, 즉 `f()`를 부른 바로 다음 명령의 주소를 Stack에 넣고 `f`로 이동해요.
3. `f`는 Stack 위에 자기 공간을 잡아요. 여기에 **Local Variable(지역 변수)**과 잠시 보관할 Register 값이 들어가요. 이 한 덩어리가 **Stack Frame**이에요.
4. `f`가 끝나면 자기 공간을 치우고 `ret` 명령을 실행해요. `ret`은 Stack에서 Return Address를 꺼내 그곳으로 돌아가요.
5. 함수가 또 다른 함수를 부르면 Frame이 계속 쌓이고, 끝나는 순서대로 하나씩 사라져요.
6. x86-64에서 Stack은 **높은 주소에서 낮은 주소 방향**으로 자라요. 맨 위를 가리키는 Register가 `rsp`(Stack Pointer)예요.
KEY:
- 함수가 끝나면 그 함수의 Local Variable은 사라져요. 그래서 Local Variable의 주소를 함수 밖으로 돌려주면 위험해요.
- 재귀(Recursion)가 끝없이 깊어지면 Frame이 Stack 크기를 넘어 **Stack Overflow**로 프로그램이 죽어요.
USE: Error가 났을 때 보이는 Call Stack(Python의 Traceback)이 바로 그 순간 쌓여 있던 함수 호출 목록이에요. 디버깅의 기본 정보예요.
END: 함수 호출 = 돌아올 주소를 넣고 이동(`call`) → 일하기 → 주소를 꺼내 복귀(`ret`). 그 사이에 쓰는 임시 공간이 Stack Frame이에요.

#### Calling Convention (함수 호출 약속)
ONE: 함수를 부르는 쪽과 불리는 쪽이 **"인자는 어디에 넣고, 결과는 어디서 받고, 어떤 Register는 누가 지킬지"**를 미리 정해 둔 약속이에요.
LIKE: 친구에게 책상을 잠깐 빌려줄 때 정하는 규칙 같아요. "숙제는 첫 번째 서랍에 넣어 둘게(인자). 다 하면 답은 맨 위 서랍에 둬(반환값). 왼쪽 서랍은 써도 되지만 원래대로 돌려놔(Callee-Saved). 오른쪽 서랍은 마음대로 써, 필요한 건 내가 미리 챙길게(Caller-Saved)."
STEP:
1. Register는 CPU에 몇 개 없는 공용 칸이라 모든 함수가 같은 Register를 함께 써요. 규칙이 없으면 서로의 값을 덮어써 버려요.
2. **인자 전달**: Linux·macOS가 쓰는 System V AMD64 규약에서는 정수·Pointer 인자 6개를 `rdi, rsi, rdx, rcx, r8, r9` 순서로 Register에 넣고, 7번째부터는 Stack에 넣어요.
3. **반환값**: `rax`에 담아 돌려줘요.
4. **Caller-Saved**: 불린 함수(Callee)가 마음대로 바꿔도 되는 Register예요. 부른 쪽(Caller)이 호출 뒤에도 그 값이 필요하면 미리 저장해 둬요.
5. **Callee-Saved**: 불린 함수가 쓰고 싶으면 먼저 저장해 두고, 돌아가기 전에 원래대로 복구해야 하는 Register예요.
| 구분 (System V AMD64) | Register |
| 인자 1~6번 | rdi, rsi, rdx, rcx, r8, r9 |
| 반환값 | rax |
| Callee-Saved | rbx, rbp, r12, r13, r14, r15 (그리고 rsp) |
| Caller-Saved | rax, rcx, rdx, rsi, rdi, r8, r9, r10, r11 |
WHY: 서로 다른 사람이 서로 다른 Compiler로 만든 코드도 이 약속만 지키면 서로 호출할 수 있어요. 남이 만든 Library를 쓸 수 있는 이유예요.
KEY: 운영체제마다 약속이 달라요. Windows x64는 인자를 `rcx, rdx, r8, r9` 순서로 넘겨요. System V 순서 암기법은 "Di Si Dx Cx 8 9"예요.
END: Calling Convention은 함수끼리의 "Register 사용 규칙"이고, 덕분에 따로 만든 코드끼리도 안전하게 서로를 부를 수 있어요.

### Stack Frame이란? call과 ret은 무엇을 하나요?
E: 책을 읽다가 각주를 보러 갈 때 지금 페이지에 책갈피를 꽂고, 다 보면 책갈피로 돌아옵니다. 함수를 부를 때마다 쓰는 메모장(Local Variable + 돌아올 자리)을 쌓아 둔 것이 Stack Frame입니다.
A: Stack Frame은 Function Call 하나가 쓰는 Stack 영역으로, Return Address·저장된 Register·Local Variable이 들어갑니다. call은 다음 Instruction의 Address(Return Address)를 Stack에 push하고 함수로 Jump하며, ret은 그 Address를 pop해 돌아갑니다. x86-64에서 Stack은 높은 Address에서 낮은 Address로 자랍니다.

### Caller-Saved와 Callee-Saved Register의 차이는?
E: 친구(Callee)에게 책상을 잠깐 빌려줄 때, 친구가 "내가 쓴 뒤 원래대로 돌려놓을게"라고 약속한 서랍이 Callee-Saved, "이 서랍은 내가 막 쓸 거니까 필요하면 네가 미리 챙겨"라고 한 서랍이 Caller-Saved입니다.
A: Caller-Saved Register는 호출된 함수가 마음대로 바꿀 수 있어서, 호출하는 쪽(Caller)이 호출 후에도 값이 필요하면 미리 저장합니다. Callee-Saved Register는 호출된 함수(Callee)가 쓰려면 먼저 저장하고 돌아가기 전에 복구해야 합니다.
| 구분 (System V AMD64) | Register |
| Callee-Saved | rbx, rbp, r12, r13, r14, r15 (그리고 rsp) |
| Caller-Saved | rax, rcx, rdx, rsi, rdi, r8, r9, r10, r11 |

### Function Argument는 어떤 Register로 전달되나요?
A: Linux·macOS가 쓰는 System V AMD64 Calling Convention에서 정수·Pointer Argument 6개는 rdi, rsi, rdx, rcx, r8, r9 순서로 전달하고, 7번째부터는 Stack에 둡니다. Return Value는 rax에 담깁니다. Windows는 다른 규약(rcx, rdx, r8, r9)을 씁니다.
M: 암기법: "Di Si Dx Cx 8 9" (rdi, rsi, rdx, rcx, r8, r9).

## C Memory Model

#### Memory 주소와 Pointer
ONE: Memory는 번호(**Address**)가 붙은 아주 긴 Byte 칸들의 줄이고, **Pointer**는 그 번호를 담는 변수예요.
LIKE: 사물함이 수십억 개 늘어선 복도를 떠올려 보세요. 사물함마다 번호가 있어요. Pointer는 물건 자체가 아니라 "15번 사물함에 있어"라고 적힌 쪽지예요.
STEP:
1. 변수를 만들면 Memory 어딘가에 칸이 잡혀요. `int x = 7;`이면 4 Byte짜리 칸에 7이 들어가요.
2. `&x`는 "x의 주소"예요. `0x7ffd1000` 같은 번호가 나와요.
3. `int *p = &x;`처럼 주소를 담는 변수가 Pointer예요.
4. `*p`는 "p가 가리키는 칸의 값"이에요. 이렇게 주소를 따라가는 것을 **Dereference**라고 해요. `*p = 10;`이라고 쓰면 x가 10으로 바뀌어요.
5. **Array**는 같은 크기의 칸이 나란히 붙은 것이에요. 첫 칸의 주소만 알면 `arr[i]`는 "첫 칸에서 i칸 뒤"로 계산해서 바로 찾아가요. 그래서 `arr[i]`는 `*(arr + i)`와 같아요.
6. 단, Array와 Pointer가 완전히 같지는 않아요. `sizeof(arr)`는 Array 전체 크기, `sizeof(p)`는 Pointer 하나의 크기(64 Bit 환경에서 8 Byte)예요.
```c
int x = 7;
int *p = &x;   // p에는 x의 주소가 들어감
*p = 10;       // p가 가리키는 곳(x)에 10을 씀 → 이제 x는 10
```
WHY: 큰 데이터를 통째로 복사하지 않고 "어디 있는지"만 넘길 수 있고, 함수가 바깥 변수를 직접 바꿀 수 있어요.
KEY: C에서 함수에 변수를 넘기면 **복사본**이 가요(**Call by Value**). 함수 안에서 원본을 바꾸고 싶으면 주소를 넘겨야 해요. 두 값을 맞바꾸는 `swap(&a, &b)`가 대표적인 예예요.
USE: Linked List·Tree 같은 자료구조, Heap Memory, 운영체제와 하드웨어 제어에서 Pointer가 핵심이에요. Python과 Java는 Pointer를 직접 보여 주지 않지만, 내부적으로는 객체를 가리키는 **Reference(참조)**를 써요.
END: Pointer는 "값"이 아니라 "값이 있는 곳의 번호"예요. `&`는 번호 얻기, `*`는 번호로 찾아가기예요.

#### Stack vs Heap, malloc · free와 Memory Leak
ONE: **Stack**은 함수가 끝나면 자동으로 치워지는 임시 공간이고, **Heap**은 프로그래머가 직접 빌리고(`malloc`) 직접 돌려줘야(`free`) 하는 공간이에요.
LIKE: Stack은 식당이 알아서 치워 주는 일회용 접시, Heap은 내가 빌려서 내가 반납해야 하는 렌탈 물품이에요. 반납을 잊으면 창고의 빈 공간이 점점 줄어드는데, 이게 Memory Leak이에요.
STEP:
1. **Stack**: 함수 안에서 만든 Local Variable이 들어가요. 함수가 시작되면 생기고 끝나면 자동으로 사라져요. 빠르지만 크기가 작아요(보통 수 MB).
2. **Heap**: 실행 중에야 크기를 알 수 있거나, 함수가 끝나도 남아 있어야 하는 데이터를 둬요. `malloc(크기)`로 빌리면 그 공간의 주소(Pointer)를 받아요.
3. 다 쓰면 `free(pointer)`로 직접 돌려줘야 해요. C는 대신 치워 주지 않아요.
4. **Memory Leak**: `free`를 하지 않은 채 그 주소마저 잃어버리면, 그 공간은 프로그램이 끝날 때까지 아무도 못 써요. 오래 켜 두는 서버에서 이게 계속 쌓이면 결국 Memory가 바닥나요.
5. **초기화하지 않은 변수**: C에서 값을 넣지 않은 Local Variable이나 `malloc`으로 받은 공간에는 이전에 쓰던 **쓰레기 값(Garbage Value)**이 남아 있을 수 있어요. 항상 값을 넣은 다음에 쓰세요(`calloc`은 0으로 채워서 줘요).
6. **Valgrind** 같은 도구를 쓰면 Leak, 잘못된 접근, 초기화 안 된 값의 사용을 찾아 줘요.
| 구분 | Stack | Heap |
| 할당·해제 | 자동 (함수 시작·끝) | 수동 (`malloc`·`free`) |
| 속도 | 매우 빠름 | 상대적으로 느림 |
| 크기 | 작음 (보통 수 MB) | 큼 (Memory가 허락하는 만큼) |
| 수명 | 함수가 끝나면 사라짐 | `free`할 때까지 |
| 흔한 실수 | 너무 깊은 재귀 → Stack Overflow | Memory Leak, Double Free |
KEY: Python·Java 같은 언어는 더 이상 안 쓰는 Heap 공간을 언어가 자동으로 회수해 줘서(**Garbage Collection**) `free`를 쓰지 않아도 돼요. 대신 회수하는 데 시간이 들어요.
END: 함수 안에서 잠깐 쓰면 Stack, 오래 쓰거나 크기가 변하면 Heap이에요. Heap은 "빌렸으면 반드시 반납"이 원칙이에요.

#### Memory 오류 3가지: Dangling Pointer · Double Free · Buffer Overflow
ONE: C는 Memory를 올바르게 쓰는지 검사해 주지 않아서, 이미 반납한 곳을 쓰거나, 두 번 반납하거나, 칸을 넘쳐 쓰는 실수가 생길 수 있어요.
LIKE: 사물함으로 비유하면 이미 반납한 사물함 번호로 계속 물건을 넣는 것(Dangling Pointer), 반납한 사물함을 또 반납하는 것(Double Free), 한 칸에 너무 많이 넣어 옆 칸 물건까지 밀어내는 것(Buffer Overflow)이에요.
STEP:
1. **Dangling Pointer**: `free`한 뒤에도 그 주소를 그대로 가진 Pointer예요. 이 Pointer로 읽거나 쓰는 것을 **Use-After-Free**라고 해요. 그 공간은 이미 다른 데이터가 쓰고 있을 수 있어요.
2. **Double Free**: 같은 공간을 두 번 `free`하는 것이에요. Memory를 관리하는 장부가 망가져요.
3. **Buffer Overflow**: Array 크기를 넘어서 쓰는 것이에요. 10칸짜리 Array에 20개를 넣으면 뒤쪽 10개가 옆의 다른 데이터를 덮어써요. C는 Array 길이를 확인해 주지 않아요.
4. 세 가지 모두 **Undefined Behavior**예요. 바로 죽을 수도 있고, 멀쩡해 보이다가 나중에 이상해질 수도 있어서 찾기 어려워요.
WHY: 단순한 Bug가 아니라 **보안 구멍**이 되기 때문이에요. Buffer Overflow로 Stack의 Return Address를 덮어쓰면, 공격자가 원하는 코드로 이동하게 만들 수 있어요.
KEY:
- `free` 후에는 Pointer를 `NULL`로 바꿔 두기
- 길이를 확인하는 함수 쓰기 (`gets` 대신 `fgets`)
- AddressSanitizer, Valgrind 같은 도구로 검사하기
USE: 그래서 이런 실수를 언어가 막아 주는 **Memory-Safe** 언어(Rust, Go, Java, Python 등)를 쓰는 곳이 늘고 있어요.
END: C의 자유에는 책임이 따라요. "반납한 곳은 쓰지 않기, 한 번만 반납하기, 칸 수를 넘지 않기"를 지켜야 해요.

#### C 문자열과 Null 문자
ONE: C의 문자열은 글자들의 Array이고, 끝에 **Null 문자(`\0`)**를 붙여서 "여기서 끝"을 표시해요.
LIKE: 줄 서기에서 마지막 사람 뒤에 "여기까지" 팻말을 세워 두는 것과 같아요. C는 줄의 길이를 따로 적어 두지 않아서, 팻말이 나올 때까지 한 명씩 세어야 길이를 알 수 있어요.
STEP:
1. `char s[] = "hi";`는 Memory에 `'h'`, `'i'`, `'\0'` 3칸으로 저장돼요. 글자는 2개인데 칸은 3개예요.
2. `strlen(s)`는 `\0`이 나올 때까지 세서 2를 돌려줘요. 그래서 길이를 구하는 데 글자 수만큼 시간이 걸려요.
3. `\0`을 넣을 칸을 깜빡하거나 `\0`이 지워지면, 문자열 함수들이 끝을 못 찾고 옆 Memory까지 계속 읽어 버려요. 이것도 Buffer Overflow의 흔한 원인이에요.
KEY: 문자열을 담을 Array는 항상 **글자 수 + 1**칸이 필요해요.
USE: Python과 Java의 문자열은 길이를 따로 저장하고 범위도 검사해 줘서 이런 문제가 생기지 않아요.
END: C 문자열 = 글자들 + 끝 표시 `\0`. 끝 표시 한 칸을 항상 챙겨야 해요.

#### Struct Padding
ONE: CPU가 데이터를 빨리 읽을 수 있도록, Compiler가 Struct 멤버 사이에 **빈 Byte(Padding)**를 끼워 넣는 것이에요.
LIKE: 4칸 단위로 칸막이가 있는 선반에 상자를 넣는다고 해 봐요. 1칸짜리 작은 상자 바로 뒤에 4칸짜리 큰 상자를 넣으면 큰 상자가 칸막이에 걸쳐서 꺼내기 불편해요. 그래서 작은 상자 뒤에 3칸을 비우고 큰 상자를 칸막이에 맞춰 넣어요.
STEP:
1. CPU는 4 Byte 데이터가 4의 배수 주소에, 8 Byte 데이터가 8의 배수 주소에 있을 때 가장 빠르게 읽어요. 이것을 **Alignment(정렬)**라고 해요.
2. `struct { char c; int i; }`에서 `char`는 1 Byte, `int`는 4 Byte예요.
3. `c`가 0번 주소에 놓이면, `i`는 4의 배수인 4번 주소부터 놓여야 해요. 그래서 1~3번 자리에 빈 3 Byte가 들어가요.
4. 결과는 1 + 4 = 5 Byte가 아니라 **8 Byte**예요(일반적인 64 Bit 환경).
5. 멤버를 **큰 것부터** 선언하면 Padding을 줄일 수 있어요.
```c
struct A { char c; double d; char e; };  // 1 + 빈칸 7 + 8 + 1 + 빈칸 7 = 24 Byte
struct B { double d; char c; char e; };  // 8 + 1 + 1 + 빈칸 6 = 16 Byte
```
WHY: 정렬이 안 맞으면 CPU가 Memory를 두 번 읽어야 하거나, 어떤 CPU는 아예 오류를 내기 때문이에요.
USE: 수백만 개의 Struct를 다루는 프로그램, 네트워크 Packet이나 파일 형식처럼 Byte 배치가 정확해야 하는 곳에서 중요해요.
PRO: 데이터를 빠르고 안전하게 읽을 수 있어요.
CON: 빈 Byte만큼 Memory를 낭비해요.
END: Padding은 "속도를 위해 칸막이에 맞춘 빈자리"이고, 큰 멤버부터 배치하면 낭비를 줄일 수 있어요.

### Pointer란? Array와 Pointer의 관계는?
E: Pointer는 물건 자체가 아니라 "사물함 15번에 있어"라고 적힌 쪽지입니다. Array는 나란히 붙은 사물함이라, 처음 번호만 알면 몇 칸 뒤로 가서 다른 칸을 찾을 수 있습니다.
A: Pointer는 다른 변수의 Memory Address를 저장하는 변수이고, `*p`로 그 Address의 값에 접근합니다(Dereference). Array 이름은 대부분의 식에서 첫 원소를 가리키는 Pointer로 바뀌어(Array Decay) `arr[i]`는 `*(arr + i)`와 같습니다. 다만 `sizeof(arr)`는 Array 전체 크기라서 Array와 Pointer가 완전히 같은 것은 아닙니다.

### C에서 함수가 넘겨받은 변수의 원본을 바꾸려면?
E: 친구에게 숙제를 복사해서 주면 친구가 고쳐도 내 숙제는 그대로입니다. 내 숙제를 고치게 하려면 "내 사물함 번호"를 알려 줘야 합니다.
A: C는 Argument를 복사해서 넘기는 Call by Value만 지원하므로, 함수 안에서 매개변수를 바꿔도 원본은 그대로입니다. 원본을 바꾸려면 변수의 Address를 넘기고 함수 안에서 Pointer로 Dereference해 씁니다. 예: `swap(&a, &b)`.

### Stack vs Heap Memory, malloc/free와 Memory Leak이란?
E: Stack은 식당이 알아서 치워 주는 일회용 접시, Heap은 내가 빌려서 내가 반납해야 하는 렌탈 물품입니다. 빌리고 반납을 잊으면 창고에 빈 공간이 점점 사라지는데, 이것이 Memory Leak입니다.
A: Stack은 함수의 Local Variable이 자동으로 할당·해제되는 빠르고 작은 영역이고, Heap은 malloc으로 필요한 만큼 할당하고 free로 직접 해제하는 영역입니다. 할당한 Heap Memory를 해제하지 않고 Address를 잃으면 Memory Leak이고, Valgrind 같은 도구로 찾습니다.

### Dangling Pointer, Double Free, Buffer Overflow란?
| 오류 | 비유 | 뜻 |
| Dangling Pointer | 이미 반납한 사물함 번호를 아직 쓰는 것 | 해제된 Memory를 가리키는 Pointer (사용 시 Use-After-Free) |
| Double Free | 이미 반납한 물건을 또 반납 | 같은 Memory를 두 번 free |
| Buffer Overflow | 사물함 한 칸에 넘치게 넣어 옆 칸까지 덮음 | Array 범위를 넘어 쓰기 |
A: 세 가지 모두 C가 Memory Safety를 검사하지 않아서 생기는 Bug이고, Undefined Behavior(정의되지 않은 동작)를 일으킵니다. 특히 Buffer Overflow는 Return Address를 덮어 공격자가 코드를 실행하게 만드는 보안 취약점(Vulnerability)이 됩니다. free 후 Pointer를 NULL로 두고, 길이를 검사하는 함수를 써서 예방합니다.

### C 문자열은 끝을 어떻게 알 수 있나요?
E: 줄 맨 끝에 "여기까지" 팻말을 세워 두는 것처럼, 글자들 뒤에 끝 표시 하나를 붙여 둡니다.
A: C 문자열은 char Array이고 끝에 Null 문자(`'\0'`)를 붙여 끝을 표시합니다. 그래서 "hi"는 3 Byte가 필요하고, `strlen`은 `'\0'`까지 세므로 O(n)입니다. `'\0'`이 빠지면 문자열 함수가 Array 밖까지 읽어 Buffer Overflow가 생길 수 있습니다.

### Struct 크기에 Padding이 들어가는 이유는?
E: 택배 상자를 선반에 쌓을 때 큰 상자는 칸 경계에 맞춰야 꺼내기 쉽습니다. 작은 상자 뒤에 빈칸을 남겨서라도 경계를 맞춥니다.
A: CPU는 Data가 자기 크기의 배수 Address에 정렬(Alignment)되어 있을 때 빠르게 읽기 때문에, Compiler가 Member 사이에 빈 Byte(Padding)를 넣습니다. 일반적인 64 Bit 환경에서 `struct { char c; int i; }`는 1 + 4가 아니라 8 Byte입니다. 큰 Member부터 선언하면 Padding을 줄일 수 있습니다.

## Compile과 Link

#### C Program의 Build 과정 (4단계)
ONE: 사람이 쓴 C 코드는 **Preprocessing → Compile → Assemble → Link** 4단계를 거쳐 CPU가 실행할 수 있는 파일이 돼요.
LIKE: 책 만들기와 같아요. ① 원고에 참고 자료를 붙여 넣고 ② 기계가 읽는 말로 번역하고 ③ 인쇄하고 ④ 여러 챕터를 한 권으로 제본해요.
STEP:
1. **Preprocessing(전처리)**: `#include <stdio.h>` 자리에 그 파일의 내용을 붙여 넣고, `#define`으로 정한 이름을 값으로 바꿔요. (`hello.c` → `hello.i`)
2. **Compile(컴파일)**: C 코드를 그 CPU의 **Assembly**(사람이 읽을 수 있는 형태의 기계 명령)로 번역해요. 문법 오류는 여기서 잡혀요. (`hello.i` → `hello.s`)
3. **Assemble(어셈블)**: Assembly를 0과 1로 된 기계어로 바꿔 **Object File**을 만들어요. (`hello.s` → `hello.o`)
4. **Link(링크)**: 내가 만든 Object File들과 `printf` 같은 Library 코드를 합치고, "이 함수는 여기에 있다"는 주소를 연결해 **Executable(실행 파일)**을 만들어요. (`hello.o` → `hello`)
```sh
gcc hello.c -o hello   # 4단계를 한 번에 실행
./hello                # 만들어진 실행 파일 실행
```
WHY: CPU는 C를 모르고 기계어만 알아요. 그리고 큰 프로그램은 파일을 나눠 따로 Compile한 뒤 합치면, 바뀐 파일만 다시 Compile하면 돼서 빨라요.
KEY: `undefined reference to ...` 오류는 Link 단계 오류예요. 함수의 선언은 있는데 실제 코드(정의)를 찾지 못했다는 뜻이에요.
END: Build = 붙여 넣기(Preprocessing) → 번역(Compile) → 기계어로(Assemble) → 합치기(Link).

#### Static Linking vs Dynamic Linking
ONE: Library 코드를 실행 파일 안에 **복사해 넣으면 Static Linking**, 실행할 때 **밖에서 불러오면 Dynamic Linking**이에요.
LIKE: Static은 참고한 책의 내용을 내 보고서 뒤에 통째로 복사해 붙이는 것이고, Dynamic은 "도서관 3층 ○○ 책 참고"라고만 적어 두고 읽을 때 빌려 보는 거예요.
STEP:
1. 프로그램은 `printf`처럼 남이 만든 Library 함수를 많이 써요.
2. **Static Linking**: Link 단계에서 필요한 Library 코드를 실행 파일 안에 복사해 넣어요. 실행 파일 하나만 있으면 어디서든 돌아가요.
3. **Dynamic Linking**: 실행 파일에는 "이 Library가 필요해"라는 표시만 남겨요. 실행할 때 운영체제가 **Shared Library**(Linux `.so`, Windows `.dll`, macOS `.dylib`)를 찾아 연결해요.
4. 여러 프로그램이 같은 Shared Library를 쓰면 Memory에 한 벌만 올려 함께 쓸 수 있어요.
| 구분 | Static | Dynamic |
| 실행 파일 크기 | 큼 | 작음 |
| 실행에 필요한 것 | 파일 하나면 충분 | 맞는 Library가 설치돼 있어야 함 |
| Library 보안 업데이트 | 다시 Build해야 반영 | Library만 바꾸면 모든 프로그램에 반영 |
| Memory | 프로그램마다 따로 | 여러 프로그램이 공유 가능 |
KEY: "○○.dll을 찾을 수 없습니다" 같은 오류는 Dynamic Linking에서 필요한 Library가 없을 때 나요.
END: 혼자서도 확실히 돌아가야 하면 Static, 용량과 업데이트가 중요하면 Dynamic이에요.

### C Program의 Build 과정은?
E: ① 원고에 참고 자료를 붙여 넣고(Preprocessing), ② 기계가 읽는 말로 번역하고(Compile·Assemble), ③ 여러 챕터를 한 권으로 제본합니다(Link).
A: Preprocessor가 #include와 #define을 펼치고, Compiler가 Assembly로 번역하고, Assembler가 기계어 Object File(.o)을 만듭니다. 마지막으로 Linker가 여러 Object File과 Library를 합쳐 함수 Address를 연결하고 Executable(실행 파일)을 만듭니다.

### Static Linking과 Dynamic Linking의 차이는?
E: Static Linking은 참고문헌을 책 뒤에 통째로 복사해 붙이는 것, Dynamic Linking은 "도서관 3층 책 참고"라고만 적고 읽을 때 빌려보는 것입니다.
A: Static Linking은 Library 코드를 Executable에 복사해 넣어 혼자 실행되지만 파일이 커집니다. Dynamic Linking은 실행할 때 Shared Library(.so, .dll)를 불러와 용량을 아끼고 Library만 따로 업데이트할 수 있지만, 대상 컴퓨터에 맞는 Library가 있어야 합니다.
